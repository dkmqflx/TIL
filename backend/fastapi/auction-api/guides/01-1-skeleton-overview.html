1-1 개요와 설계

uv 프로젝트를 만들고, 폴더를 실무 모양으로 나누고, 환경별 설정을 분리하고, Docker로 Postgres·Redis를 띄운 뒤, GET /health가 두 인프라에 진짜로 연결되는지 확인하는 출발점을 만듭니다.

1-1 개요와 설계 1-2 구현 1-3 실행·확인
한 줄 요약. 이 문서를 끝까지 따라 하면 curl localhost:8000/health가 {"status":"ok","db":true,"redis":true}를 돌려주는, 테스트까지 통과하는 프로젝트 뼈대가 생깁니다. 기능은 아직 없지만 2~10단계가 전부 이 위에 쌓입니다.

학습 목표

  • uv로 프로젝트를 만들고 Python 버전을 고정한다
  • 라우터·서비스·리포지토리 폴더를 미리 나눠 "실무 프로젝트 모양"을 잡는다
  • pydantic-settings로 APP_ENV=dev|test|prod별 설정을 한 클래스로 관리한다
  • Docker compose로 Postgres(5435)·Redis(6380)를 띄운다
  • lifespan으로 앱 종료 시 연결을 정리하고, /health로 연결 상태를 확인한다
🎯

이 단계의 목표

이 단계를 끝내면 실행 가능한 프로젝트 뼈대가 생깁니다. 브라우저에서 /docs를 열면 Swagger가 뜨고, /health를 호출하면 앱이 실제로 DB와 Redis에 접속해서 살아 있는지 알려 줍니다. 아직 경매도 입찰도 없지만, 다음 단계부터는 이 뼈대 위에 파일만 하나씩 얹으면 됩니다.

시작하기 전에 세 가지가 설치돼 있어야 합니다. uv(uv --version), Docker Desktop(docker ps가 에러 없이 돌아야 함), 그리고 Python 3.13입니다. Python은 uv가 없으면 알아서 내려받기도 하지만, 이 가이드는 3.13이 이미 있다고 가정합니다.

작업 디렉터리. 모든 명령은 til/backend/fastapi/auction-api/ 안에서 실행합니다. 이 폴더에는 이미 guides/(지금 읽는 문서)와 planning/(설계 문서)이 있습니다. 그 옆에 app/, tests/, pyproject.toml 같은 것들이 이번 단계에서 새로 생깁니다.
🏢

왜 필요한가 — 실무에서는 첫날에 이걸 한다

self-study에서는 주차마다 main.py 파일 하나에 코드를 몰아 썼습니다. 배우기엔 그게 제일 좋지만, 실제 회사 프로젝트를 열어 보면 첫 커밋부터 폴더가 나뉘어 있고, 설정은 환경별로 갈라져 있고, DB는 Docker로 뜨고, 헬스체크 엔드포인트가 있습니다. 왜냐하면 이 네 가지가 없으면 두 번째 사람이 합류하는 순간부터 문제가 생기기 때문입니다. "내 컴퓨터에서는 되는데요"의 절반은 설정과 인프라 차이에서 나옵니다.

특히 /health는 별것 아닌 것 같아도 실무에서 가장 자주 호출되는 엔드포인트입니다. 배포 직후 운영자가 제일 먼저 두드리고, 로드밸런서가 몇 초마다 두드리고, Docker와 CI가 "앱이 준비됐나"를 판단할 때 두드립니다. 10단계에서 Docker healthcheck와 GitHub Actions가 바로 이 엔드포인트를 보게 됩니다.

그리고 이 단계에서 잡는 폴더 구조와 get_db, get_redis, get_settings 세 함수는 앞으로 모든 단계가 그대로 가져다 씁니다. 그래서 여기서 이름을 정확히 맞춰 두는 게 중요합니다.

🏗️

비유 — 집 짓기 전에 터를 고르고 수도·전기를 연결한다

집을 지을 때 첫날에 벽돌부터 쌓지 않습니다. 먼저 터를 고르고(폴더 구조), 수도와 전기를 끌어오고(Postgres·Redis 컨테이너), 계량기가 제대로 돌아가는지 확인합니다(/health). 이 작업은 눈에 보이는 결과물이 없어서 지루하지만, 나중에 방을 하나씩 늘릴 때(2~10단계) 매번 수도관을 새로 파지 않아도 되게 해 줍니다.
설정(Settings)은 라벨 붙은 열쇠고리입니다. 자취방 열쇠, 회사 열쇠, 본가 열쇠를 열쇠고리 하나에 라벨 붙여 두면 어디를 가든 고리 하나만 들고 다니면 됩니다. Settings 클래스가 그 열쇠고리이고, APP_ENV=dev|test|prod가 라벨입니다. 코드는 항상 get_settings().database_url이라고만 부르고, 그게 개발용 DB인지 테스트용 DB인지는 .env나 환경변수가 결정합니다. 3단계에서 테스트가 auction_test DB를 따로 쓰는 것도, 10단계에서 CI가 다른 주소로 붙는 것도 코드 수정 없이 이 라벨만 바꿔서 됩니다.
🗺️

설계 그림 — 무엇이 어디에 연결되나

이번 단계에서 만드는 것을 한 장으로 그리면 아래와 같습니다. 클라이언트가 /health를 부르면 FastAPI 앱이 Postgres에 SELECT 1을, Redis에 PING을 한 번씩 보내고, 둘 다 성공하면 200, 하나라도 실패하면 503을 돌려줍니다.

앱은 두 인프라에 직접 물어보고 그 결과를 정직하게 돌려준다.

두 번째 그림은 시간 순서입니다. 앱이 켜질 때 엔진과 Redis 클라이언트 객체를 만들지만(import 시점), 실제 TCP 연결은 첫 요청이 올 때 비로소 맺어집니다. 그리고 앱이 꺼질 때 lifespan의 yield 아래쪽이 실행되어 연결을 정리합니다. Week 7·01에서 배운 lifespan이 바로 이 "켜질 때 / 꺼질 때" 훅입니다.

객체 생성은 import 시점, 연결은 첫 사용 시점, 정리는 lifespan 종료 시점.
