코드를 다 만들었다는 전제입니다. 아직이라면 1-2 구현를 먼저 끝내고 오세요.
▶️

실행·확인 — 이 출력이 나와야 한다

이제 하나씩 돌려 봅니다. 각 명령 아래에 적힌 것은 검증 당시 실제로 나온 출력입니다. 시간이나 버전 숫자는 달라도 되지만, 내용이 다르면 어딘가 잘못된 겁니다.

1. 코드 스타일 검사

bash
uv run ruff check .
# All checks passed!

2. 인프라 띄우기

-d는 백그라운드로 띄우라는 뜻입니다. 처음엔 이미지를 내려받느라 시간이 좀 걸립니다. 몇 초 기다렸다가 ps로 확인했을 때 두 줄 모두 (healthy)여야 합니다.

bash
docker compose up -d
docker compose ps
# NAME            STATUS                    PORTS
# auction-db      Up 13 seconds (healthy)   0.0.0.0:5435->5432/tcp
# auction-redis   Up 13 seconds (healthy)   0.0.0.0:6380->6379/tcp

3. 설정이 제대로 읽히는지

첫 줄은 .env의 값이 찍혀야 하고(debug가 True인 것에 주목), 두 번째 줄은 명령 앞에 붙인 환경변수가 .env의 dev를 이기는지 확인하는 것입니다.

bash
uv run python -c "from app.core.config import get_settings; print(get_settings().model_dump())"
# {'app_env': 'dev', 'database_url': 'postgresql+asyncpg://auction:auction_pw@localhost:5435/auction', 'redis_url': 'redis://localhost:6380/0', 'debug': True}

APP_ENV=prod uv run python -c "from app.core.config import get_settings; print(get_settings().app_env)"
# prod

4. 테스트 통과

⑥에서 실패했던 테스트가 이제 통과해야 합니다. 경고(warning)가 하나도 없어야 정상입니다.

bash
uv run pytest -q
# .                                                                        [100%]
# 1 passed in 4.51s

5. 서버 띄우고 직접 호출

터미널 하나에서 서버를 띄우고, 다른 터미널에서 curl을 칩니다. --reload는 파일을 저장할 때마다 서버를 자동으로 재시작해 주는 개발용 옵션입니다. 브라우저에서 http://localhost:8000/docs를 열면 Swagger에 /health가 보입니다.

bash터미널 1
uv run uvicorn app.main:app --reload
# INFO:     Uvicorn running on http://127.0.0.1:8000 (Press CTRL+C to quit)
# INFO:     Application startup complete.
bash터미널 2
curl -s localhost:8000/health
# {"status":"ok","db":true,"redis":true}

6. 장애 상황도 확인 — Redis를 껐다 켜기

헬스체크가 "정직한지" 보는 가장 쉬운 방법입니다. Redis 컨테이너만 멈추면 상태 코드가 503으로 바뀌고 redis가 false가 되어야 합니다. 다시 켜면 곧바로 200으로 돌아옵니다 — 서버를 재시작할 필요가 없다는 점에 주목하세요. 연결은 요청 때마다 새로 시도되기 때문입니다.

bash터미널 2
docker compose stop redis
curl -i -s localhost:8000/health
# HTTP/1.1 503 Service Unavailable
# ...
# {"status":"degraded","db":true,"redis":false}

docker compose start redis
curl -s localhost:8000/health
# {"status":"ok","db":true,"redis":true}

확인이 끝나면 터미널 1에서 Ctrl+C로 서버를 끕니다. 로그에 Application shutdown complete.가 찍히는데, 그 직전에 lifespan의 yield 아래쪽(aclose, dispose)이 실행된 것입니다.

✅

완료 기준 체크리스트

아래가 전부 체크되면 1단계는 끝입니다. 하나라도 안 되면 위 실행·확인 절로 돌아가서 어느 명령에서 어긋나는지 찾으세요.

  • cat .python-version이 3.13, uv run python --version이 Python 3.13.x
  • uv run ruff check . → All checks passed!
  • docker compose ps에서 auction-db, auction-redis 둘 다 (healthy)
  • uv run pytest -q → 1 passed, 경고 없음
  • curl -s localhost:8000/health → {"status":"ok","db":true,"redis":true}
  • Redis를 멈추면 503 + "redis":false, 다시 켜면 200
  • http://localhost:8000/docs에 /health가 보임
  • .env는 git 상태에 안 보이고, .env.example은 보임 (git status로 확인)
여기서 커밋하세요. 1단계 결과물을 한 커밋으로 남깁니다. 예: git commit -m "add(be(fastapi)): auction-api 1단계 — 프로젝트 뼈대·설정·헬스체크". 다음 단계에서 뭔가 꼬여도 이 지점으로 돌아올 수 있습니다.
⚠️

함정 & 실무 팁

uv init --bare는 Python 버전을 고정하지 않는다. .python-version 파일을 만들지 않기 때문에 이 머신에서는 3.14로 가상환경이 잡혔습니다. 그래서 가이드는 uv python pin 3.13을 먼저 실행합니다. 이미 3.14로 만들어 버렸다면 uv python pin 3.13 후 uv sync를 다시 돌리면 3.13으로 바뀝니다.
Starlette 1.6부터 TestClient는 httpx2를 요구한다. self-study 자료에는 httpx라고 돼 있고 그걸 깔아도 테스트는 돌아가지만, StarletteDeprecationWarning: Using httpx with starlette.testclient is deprecated; install httpx2 instead라는 경고가 뜹니다. 경고 없는 상태를 기준으로 삼기 위해 httpx2를 씁니다. 3단계에서 비동기 클라이언트를 도입할 때 다시 다룹니다.
포트 충돌. 이 머신은 5432와 5434를 다른 컨테이너가 쓰고 있어서 5435·6380을 골랐습니다. docker compose up에서 port is already allocated가 나오면 docker ps --format '{{.Names}} {{.Ports}}'로 누가 쓰는지 보고, compose와 .env의 포트를 둘 다 바꾸세요. 하나만 바꾸면 접속이 안 됩니다.
.env는 절대 커밋하지 않는다. 지금은 개발용 비밀번호라 괜찮아 보여도, 한 번 올라간 파일은 git 히스토리에 영원히 남습니다. 커밋 전 git status에 .env가 보이면 .gitignore가 잘못된 겁니다. 공유할 것은 .env.example뿐입니다.
til 루트 .gitignore와의 관계. 루트 파일에는 .venv가 없어서 이 프로젝트의 .gitignore가 꼭 필요합니다. 그리고 루트가 docs/를 통째로 무시하고 있기 때문에, 이 프로젝트 안에서는 docs/라는 폴더명을 쓰지 마세요. 만들어도 커밋이 안 됩니다. 그래서 가이드는 guides/, 설계 문서는 planning/입니다.
엔진과 Redis 클라이언트를 모듈 수준에서 만들어도 되는 이유. create_async_engine과 Redis.from_url은 둘 다 lazy입니다. 객체만 만들고 실제 소켓 연결은 첫 쿼리·첫 명령 때 맺습니다. 그래서 import만으로 DB에 부하를 주거나 실패하는 일이 없고, 정리(dispose, aclose)만 lifespan 종료 시점에 해 주면 됩니다. 만약 시작 시점에 "연결이 안 되면 아예 뜨지 말아라"가 필요하면 lifespan의 yield 위쪽에 SELECT 1을 한 번 날리면 됩니다.
왜 부분 장애를 503으로 알리나. 헬스체크를 읽는 쪽은 사람이 아니라 기계입니다. 로드밸런서는 200이 아니면 그 서버로 트래픽을 보내지 않고, Docker healthcheck와 CI는 상태 코드로 "준비됐다/안 됐다"를 판단합니다. JSON 안에 "redis": false라고 아무리 적어 놔도 200이면 기계는 "정상"으로 봅니다. 그래서 하나라도 실패하면 503입니다. 본문의 db·redis 필드는 사람이 원인을 빨리 찾으라고 덧붙인 것입니다.
extra="ignore"와 lru_cache. .env에 Settings가 모르는 키(예: 나중에 추가할 JWT_SECRET)가 있어도 에러 내지 말고 무시하라는 게 extra="ignore"입니다. 기본값은 에러라서, 이걸 빼먹으면 3단계에서 키를 추가하는 순간 앱이 안 뜹니다. lru_cache는 "같은 인자로 부르면 이전 결과를 재사용"하는 캐시인데, 인자가 없는 get_settings()에 붙이면 사실상 싱글턴이 됩니다. 테스트에서 설정을 바꿔치기해야 할 때는 get_settings.cache_clear()로 비웁니다.
지금은 넘어가도 되는 두 옵션. pool_pre_ping=True는 풀에서 꺼낸 커넥션이 죽어 있으면 조용히 새로 만들어 주는 옵션이고(Week 5·03 커넥션 풀), expire_on_commit=False는 커밋 후에도 객체 속성을 다시 읽지 않게 하는 옵션으로 async 세션에서는 거의 필수입니다(Week 7·01 엔진·세션). 2단계에서 모델을 만들 때 다시 만납니다.

셀프 체크

Q 엔진을 모듈 수준에서 만들었는데, 그럼 lifespan은 왜 필요한가요? 시작 시점에 만드는 것과 뭐가 다른가요?

create_async_engine은 lazy라서 만드는 시점에 연결하지 않습니다. 그래서 "언제 만드나"는 크게 중요하지 않고, 중요한 건 "언제 정리하나"입니다. 앱이 꺼질 때 풀에 남은 커넥션을 닫지 않으면 DB 쪽에 좀비 연결이 남을 수 있는데, 그 정리 시점을 잡아 주는 게 lifespan의 yield 아래쪽입니다. 시작 시점에 만들고 싶다면 yield 위에서 만들고 app.state에 넣는 방법도 있는데, 그러면 get_db가 request.app.state를 통해 꺼내야 해서 코드가 조금 길어집니다. 이 프로젝트는 단순한 쪽을 택했습니다.

Q Redis만 죽었을 때 200에 "redis": false를 돌려주면 안 되나요? 왜 굳이 503인가요?

헬스체크를 읽는 것은 로드밸런서·Docker·CI 같은 기계이고, 기계는 상태 코드만 봅니다. 200이면 "이 서버에 트래픽 보내도 됨"으로 해석하기 때문에, Redis가 죽어서 세션 조회·캐시·rate limit이 전부 실패하는 서버로 계속 요청이 흘러 들어갑니다. 503을 주면 로드밸런서가 그 서버를 잠시 빼고, 복구되면 다시 넣습니다. 본문의 db·redis 필드는 사람이 원인을 빨리 찾기 위한 부가 정보입니다.

Q .env에 APP_ENV=dev가 있는데 APP_ENV=prod uv run ...이 prod를 찍은 이유는? 이 우선순위가 실무에서 왜 중요한가요?

pydantic-settings의 우선순위는 진짜 환경변수 > .env 파일 > 코드 기본값입니다. 실무에서는 운영 서버나 CI에 .env 파일을 두지 않고 배포 시스템이 환경변수를 주입합니다. 이 우선순위 덕분에 같은 코드·같은 .env.example을 두고도 로컬은 파일로, 운영은 환경변수로 설정을 갈아 끼울 수 있고, 실수로 .env가 서버에 올라가도 환경변수가 이기므로 로컬 설정이 운영을 덮어쓰는 사고가 나지 않습니다.
