1단계 — 뼈대와 설정

uv 프로젝트를 만들고, 폴더를 실무 모양으로 나누고, 환경별 설정을 분리하고, Docker로 Postgres·Redis를 띄운 뒤, GET /health가 두 인프라에 진짜로 연결되는지 확인하는 출발점을 만듭니다.

한 줄 요약. 이 문서를 끝까지 따라 하면 curl localhost:8000/health가 {"status":"ok","db":true,"redis":true}를 돌려주는, 테스트까지 통과하는 프로젝트 뼈대가 생깁니다. 기능은 아직 없지만 2~10단계가 전부 이 위에 쌓입니다.

학습 목표

  • uv로 프로젝트를 만들고 Python 버전을 고정한다
  • 라우터·서비스·리포지토리 폴더를 미리 나눠 "실무 프로젝트 모양"을 잡는다
  • pydantic-settings로 APP_ENV=dev|test|prod별 설정을 한 클래스로 관리한다
  • Docker compose로 Postgres(5435)·Redis(6380)를 띄운다
  • lifespan으로 앱 종료 시 연결을 정리하고, /health로 연결 상태를 확인한다
🎯

이 단계의 목표

이 단계를 끝내면 실행 가능한 프로젝트 뼈대가 생깁니다. 브라우저에서 /docs를 열면 Swagger가 뜨고, /health를 호출하면 앱이 실제로 DB와 Redis에 접속해서 살아 있는지 알려 줍니다. 아직 경매도 입찰도 없지만, 다음 단계부터는 이 뼈대 위에 파일만 하나씩 얹으면 됩니다.

시작하기 전에 세 가지가 설치돼 있어야 합니다. uv(uv --version), Docker Desktop(docker ps가 에러 없이 돌아야 함), 그리고 Python 3.13입니다. Python은 uv가 없으면 알아서 내려받기도 하지만, 이 가이드는 3.13이 이미 있다고 가정합니다.

작업 디렉터리. 모든 명령은 til/backend/fastapi/auction-api/ 안에서 실행합니다. 이 폴더에는 이미 guides/(지금 읽는 문서)와 planning/(설계 문서)이 있습니다. 그 옆에 app/, tests/, pyproject.toml 같은 것들이 이번 단계에서 새로 생깁니다.
🏢

왜 필요한가 — 실무에서는 첫날에 이걸 한다

self-study에서는 주차마다 main.py 파일 하나에 코드를 몰아 썼습니다. 배우기엔 그게 제일 좋지만, 실제 회사 프로젝트를 열어 보면 첫 커밋부터 폴더가 나뉘어 있고, 설정은 환경별로 갈라져 있고, DB는 Docker로 뜨고, 헬스체크 엔드포인트가 있습니다. 왜냐하면 이 네 가지가 없으면 두 번째 사람이 합류하는 순간부터 문제가 생기기 때문입니다. "내 컴퓨터에서는 되는데요"의 절반은 설정과 인프라 차이에서 나옵니다.

특히 /health는 별것 아닌 것 같아도 실무에서 가장 자주 호출되는 엔드포인트입니다. 배포 직후 운영자가 제일 먼저 두드리고, 로드밸런서가 몇 초마다 두드리고, Docker와 CI가 "앱이 준비됐나"를 판단할 때 두드립니다. 10단계에서 Docker healthcheck와 GitHub Actions가 바로 이 엔드포인트를 보게 됩니다.

그리고 이 단계에서 잡는 폴더 구조와 get_db, get_redis, get_settings 세 함수는 앞으로 모든 단계가 그대로 가져다 씁니다. 그래서 여기서 이름을 정확히 맞춰 두는 게 중요합니다.

🏗️

비유 — 집 짓기 전에 터를 고르고 수도·전기를 연결한다

집을 지을 때 첫날에 벽돌부터 쌓지 않습니다. 먼저 터를 고르고(폴더 구조), 수도와 전기를 끌어오고(Postgres·Redis 컨테이너), 계량기가 제대로 돌아가는지 확인합니다(/health). 이 작업은 눈에 보이는 결과물이 없어서 지루하지만, 나중에 방을 하나씩 늘릴 때(2~10단계) 매번 수도관을 새로 파지 않아도 되게 해 줍니다.
설정(Settings)은 라벨 붙은 열쇠고리입니다. 자취방 열쇠, 회사 열쇠, 본가 열쇠를 열쇠고리 하나에 라벨 붙여 두면 어디를 가든 고리 하나만 들고 다니면 됩니다. Settings 클래스가 그 열쇠고리이고, APP_ENV=dev|test|prod가 라벨입니다. 코드는 항상 get_settings().database_url이라고만 부르고, 그게 개발용 DB인지 테스트용 DB인지는 .env나 환경변수가 결정합니다. 3단계에서 테스트가 auction_test DB를 따로 쓰는 것도, 10단계에서 CI가 다른 주소로 붙는 것도 코드 수정 없이 이 라벨만 바꿔서 됩니다.
🗺️

설계 그림 — 무엇이 어디에 연결되나

이번 단계에서 만드는 것을 한 장으로 그리면 아래와 같습니다. 클라이언트가 /health를 부르면 FastAPI 앱이 Postgres에 SELECT 1을, Redis에 PING을 한 번씩 보내고, 둘 다 성공하면 200, 하나라도 실패하면 503을 돌려줍니다.

앱은 두 인프라에 직접 물어보고 그 결과를 정직하게 돌려준다.

두 번째 그림은 시간 순서입니다. 앱이 켜질 때 엔진과 Redis 클라이언트 객체를 만들지만(import 시점), 실제 TCP 연결은 첫 요청이 올 때 비로소 맺어집니다. 그리고 앱이 꺼질 때 lifespan의 yield 아래쪽이 실행되어 연결을 정리합니다. Week 7·01에서 배운 lifespan이 바로 이 "켜질 때 / 꺼질 때" 훅입니다.

객체 생성은 import 시점, 연결은 첫 사용 시점, 정리는 lifespan 종료 시점.

구현 — 파일을 하나씩 만든다

아래 순서 그대로 따라 하세요. 각 코드 블록은 잘라낸 조각이 아니라 붙여넣으면 그대로 도는 전체 파일입니다. 오른쪽 위 "복사" 버튼을 쓰면 편합니다.

① uv 프로젝트 만들기

먼저 Python 버전을 고정하고, 그다음 프로젝트를 만듭니다. 순서가 중요합니다. uv init --bare는 pyproject.toml만 만들고 .python-version 파일은 만들지 않기 때문에, 먼저 pin을 하지 않으면 컴퓨터에 있는 가장 최신 Python(이 머신은 3.14)으로 가상환경이 잡힙니다. --bare는 "샘플 main.py나 README 같은 걸 만들지 말고 최소한만"이라는 뜻입니다.

bashtil/backend/fastapi/auction-api/
uv python pin 3.13
uv init --bare
uv add fastapi "uvicorn[standard]" "sqlalchemy[asyncio]" asyncpg redis pydantic-settings
uv add --dev ruff pytest httpx2

두 번째 uv add의 --dev는 "개발할 때만 필요한 도구"라는 뜻입니다. 운영 서버에 ruff나 pytest가 깔릴 필요는 없으니까요. httpx2는 테스트에서 쓸 TestClient가 요구하는 HTTP 라이브러리입니다. 예전 자료에는 httpx라고 돼 있는데, 이 프로젝트가 쓰는 Starlette 1.6부터는 httpx2를 요구합니다(아래 함정 참고).

설치가 끝나면 pyproject.toml이 생겨 있을 겁니다. 그 파일 맨 아래에 ruff와 pytest 설정을 붙여 넣습니다. ruff는 "코드 스타일 검사기 + 정리기"이고, select는 어떤 규칙을 켤지입니다(E/F는 기본 문법·오류, I는 import 정렬, UP은 최신 문법 권장, B는 흔한 버그 패턴).

tomlpyproject.toml — 맨 아래에 추가
[tool.ruff]
target-version = "py313"
line-length = 100

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B"]

[tool.pytest.ini_options]
testpaths = ["tests"]
검증 당시 버전. fastapi 0.141.1 · starlette 1.6.0 · sqlalchemy 2.0.52 · asyncpg 0.31.0 · redis 8.1.0 · pydantic-settings 2.15.0 · uvicorn 0.52.4 · httpx2 2.12.0 · pytest 9.1.1 · ruff 0.16.4. 이보다 새 버전이 깔려도 대부분 그대로 동작하지만, 뭔가 다르게 나오면 이 버전을 기준으로 비교하세요.

④ Docker compose — Postgres와 Redis

Week 5·01에서 한 것과 같은 방식이지만 두 가지가 다릅니다. 첫째, Redis가 추가됐습니다. 둘째, 호스트 포트가 5435와 6380입니다. 이 머신에서 5432(Postgres 기본)와 5434는 이미 다른 프로젝트의 컨테이너가 쓰고 있어서, 겹치지 않는 번호를 골랐습니다. 콜론 왼쪽이 내 컴퓨터 쪽 포트, 오른쪽이 컨테이너 안쪽 포트입니다. 컨테이너 안에서는 여전히 기본 포트를 쓰고, 바깥에서 접속할 때만 5435로 들어갑니다.

yamldocker-compose.yml
services:
  db:
    image: postgres:16-alpine
    container_name: auction-db
    environment:
      POSTGRES_USER: auction
      POSTGRES_PASSWORD: auction_pw
      POSTGRES_DB: auction
    ports:
      - "5435:5432"
    volumes:
      - auction-pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U auction -d auction"]
      interval: 5s
      timeout: 3s
      retries: 5

  redis:
    image: redis:7-alpine
    container_name: auction-redis
    ports:
      - "6380:6379"
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5

volumes:
  auction-pgdata:

healthcheck는 Docker가 몇 초마다 "이 컨테이너 제대로 살아 있니?"를 확인하는 명령입니다. docker compose ps에서 (healthy)라고 뜨면 접속해도 된다는 뜻입니다. volumes는 컨테이너를 지워도 DB 데이터가 남도록 별도 저장소를 붙이는 설정입니다.

⑤ 환경 파일 — .env.example과 .env

설정값은 코드에 박지 않고 .env 파일에서 읽습니다. 그런데 .env는 git에 안 올리기로 했으니, 새로 합류한 사람은 "어떤 키가 필요한지" 알 수가 없습니다. 그래서 비밀이 아닌 예시값을 담은 .env.example을 함께 두고 커밋합니다. 지금은 개발용이라 둘의 내용이 같지만, 습관을 들이는 게 목적입니다.

env.env.example
APP_ENV=dev
DATABASE_URL=postgresql+asyncpg://auction:auction_pw@localhost:5435/auction
REDIS_URL=redis://localhost:6380/0
DEBUG=true
bash
cp .env.example .env

DATABASE_URL을 뜯어보면 postgresql+asyncpg://는 "Postgres를 asyncpg 드라이버로", auction:auction_pw는 사용자와 비밀번호, localhost:5435는 compose에서 열어 둔 포트, 마지막 /auction은 DB 이름입니다. compose 파일의 값과 하나라도 다르면 접속이 안 되니 대조해 보세요.

⑥ 테스트부터 — tests/test_health.py

이제 코드를 쓸 차례인데, 구현보다 테스트를 먼저 씁니다. "이런 결과가 나와야 한다"를 먼저 적어 두고, 그걸 통과시키는 방식으로 구현하면 뭘 만들어야 하는지가 명확해집니다(4단계부터는 이 방식을 본격적으로 씁니다). with TestClient(app) as client:처럼 with 블록 안에서 쓰면 lifespan의 시작·종료가 실제로 실행됩니다.

pythontests/test_health.py
from fastapi.testclient import TestClient

from app.main import app


def test_health_reports_db_and_redis():
    with TestClient(app) as client:
        res = client.get("/health")
    assert res.status_code == 200
    assert res.json() == {"status": "ok", "db": True, "redis": True}

지금 실행하면 당연히 실패합니다. app.main이 아직 없으니까요. 그래도 한 번 돌려 보세요. "실패하는 걸 눈으로 확인하고 → 통과시킨다"가 TDD의 리듬입니다.

bash
uv run pytest -q
# ...
# ModuleNotFoundError: No module named 'app.main'
# 1 error in 1.00s

⑦ app/core/config.py — 설정 열쇠고리

BaseSettings를 상속한 클래스는 필드 이름과 같은 환경변수(대소문자 무시)를 자동으로 읽습니다. env_file=".env"를 주면 .env 파일도 읽는데, 우선순위는 진짜 환경변수 > .env 파일 > 코드의 기본값입니다. 그래서 CI나 운영 서버에서는 .env 없이 환경변수만 넣어도 되고, 로컬에서는 .env만 있으면 됩니다.

pythonapp/core/config.py
from functools import lru_cache
from typing import Literal

from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", env_file_encoding="utf-8", extra="ignore")

    app_env: Literal["dev", "test", "prod"] = "dev"
    database_url: str = "postgresql+asyncpg://auction:auction_pw@localhost:5435/auction"
    redis_url: str = "redis://localhost:6380/0"
    debug: bool = False


@lru_cache
def get_settings() -> Settings:
    return Settings()

Literal["dev", "test", "prod"]는 "이 셋 중 하나만 허용"이라는 타입입니다. 오타로 APP_ENV=prd라고 적으면 앱이 뜨는 순간 에러가 나서 바로 알 수 있습니다. @lru_cache는 get_settings()를 아무리 많이 불러도 .env 파일은 딱 한 번만 읽게 해 주는 장식자입니다. 요청마다 파일을 다시 읽을 이유가 없으니까요.

⑧ app/core/db.py — 비동기 엔진과 세션

Week 7·01에서 배운 async SQLAlchemy 구성입니다. engine은 "DB에 어떻게 접속하는지 아는 객체 + 커넥션 풀"이고, SessionLocal은 "세션을 찍어내는 공장", get_db는 요청마다 세션 하나를 열어서 건네주고 요청이 끝나면 닫아 주는 의존성입니다. Week 6·02의 yield 의존성과 모양이 같은데 async가 붙었을 뿐입니다.

pythonapp/core/db.py
from collections.abc import AsyncIterator

from sqlalchemy.ext.asyncio import AsyncSession, async_sessionmaker, create_async_engine

from app.core.config import get_settings

engine = create_async_engine(get_settings().database_url, pool_pre_ping=True)
SessionLocal = async_sessionmaker(engine, expire_on_commit=False)


async def get_db() -> AsyncIterator[AsyncSession]:
    async with SessionLocal() as session:
        yield session

engine을 함수 안이 아니라 파일 맨 위(모듈 수준)에서 만드는 게 의아할 수 있는데, create_async_engine은 이 줄이 실행되는 순간 DB에 접속하지 않습니다. 접속 정보만 기억해 뒀다가 첫 쿼리가 나갈 때 연결합니다. 그래서 import만 해도 안전하고, 정리(dispose)만 lifespan에서 해 주면 됩니다.

⑨ app/core/redis.py — Redis 클라이언트

같은 패턴입니다. Redis.from_url도 실제 연결은 첫 명령 때 맺습니다. decode_responses=True는 Redis가 돌려주는 값을 바이트가 아니라 문자열로 받겠다는 뜻으로, 매번 .decode()를 안 해도 돼서 편합니다.

pythonapp/core/redis.py
from redis.asyncio import Redis

from app.core.config import get_settings

redis_client: Redis = Redis.from_url(get_settings().redis_url, decode_responses=True)


def get_redis() -> Redis:
    return redis_client

⑩ app/routers/health.py — 진짜로 확인하는 헬스체크

"살아 있어요"만 돌려주는 헬스체크는 앱 프로세스가 떠 있다는 것밖에 증명하지 못합니다. 이 엔드포인트는 DB에 SELECT 1, Redis에 PING을 실제로 보내서 각각 성공했는지를 따로 보고합니다. 하나라도 실패하면 503으로 응답하는데, 이유는 아래 함정 절에서 설명합니다.

pythonapp/routers/health.py
from typing import Annotated

from fastapi import APIRouter, Depends, Response, status
from redis.asyncio import Redis
from sqlalchemy import text
from sqlalchemy.ext.asyncio import AsyncSession

from app.core.db import get_db
from app.core.redis import get_redis

router = APIRouter(tags=["health"])


@router.get("/health")
async def health(
    response: Response,
    db: Annotated[AsyncSession, Depends(get_db)],
    redis: Annotated[Redis, Depends(get_redis)],
) -> dict[str, str | bool]:
    db_ok = False
    redis_ok = False
    try:
        await db.execute(text("SELECT 1"))
        db_ok = True
    except Exception:
        pass
    try:
        redis_ok = bool(await redis.ping())
    except Exception:
        pass

    ok = db_ok and redis_ok
    if not ok:
        response.status_code = status.HTTP_503_SERVICE_UNAVAILABLE
    return {"status": "ok" if ok else "degraded", "db": db_ok, "redis": redis_ok}

db: Annotated[AsyncSession, Depends(get_db)]는 Week 6·02의 Annotated 스타일 그대로입니다. 인자에 response: Response를 받으면 응답 본문은 그대로 return하면서 상태 코드만 바꿀 수 있습니다. except Exception: pass는 평소엔 나쁜 습관이지만 헬스체크만큼은 예외입니다 — "연결이 됐나 안 됐나"만 알면 되고, 어떤 이유로 실패했든 결과는 False이기 때문입니다.

⑪ app/main.py — 앱 조립과 lifespan

create_app()이라는 함수로 앱을 만드는 이유는 나중에 테스트에서 "설정만 다른 앱"을 하나 더 만들기 쉽게 하려는 겁니다. lifespan은 yield를 기준으로 위가 시작, 아래가 종료인데, 이번 단계에서는 시작 때 할 일이 없어서(엔진·클라이언트는 이미 import 때 만들어졌으니) 종료 정리만 넣었습니다.

pythonapp/main.py
from collections.abc import AsyncIterator
from contextlib import asynccontextmanager

from fastapi import FastAPI

from app.core.config import get_settings
from app.core.db import engine
from app.core.redis import redis_client
from app.routers import health


@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    yield
    await redis_client.aclose()
    await engine.dispose()


def create_app() -> FastAPI:
    settings = get_settings()
    app = FastAPI(title="Auction API", debug=settings.debug, lifespan=lifespan)
    app.include_router(health.router)
    return app


app = create_app()

함정 & 실무 팁

uv init --bare는 Python 버전을 고정하지 않는다. .python-version 파일을 만들지 않기 때문에 이 머신에서는 3.14로 가상환경이 잡혔습니다. 그래서 가이드는 uv python pin 3.13을 먼저 실행합니다. 이미 3.14로 만들어 버렸다면 uv python pin 3.13 후 uv sync를 다시 돌리면 3.13으로 바뀝니다.
Starlette 1.6부터 TestClient는 httpx2를 요구한다. self-study 자료에는 httpx라고 돼 있고 그걸 깔아도 테스트는 돌아가지만, StarletteDeprecationWarning: Using httpx with starlette.testclient is deprecated; install httpx2 instead라는 경고가 뜹니다. 경고 없는 상태를 기준으로 삼기 위해 httpx2를 씁니다. 3단계에서 비동기 클라이언트를 도입할 때 다시 다룹니다.
포트 충돌. 이 머신은 5432와 5434를 다른 컨테이너가 쓰고 있어서 5435·6380을 골랐습니다. docker compose up에서 port is already allocated가 나오면 docker ps --format '{{.Names}} {{.Ports}}'로 누가 쓰는지 보고, compose와 .env의 포트를 둘 다 바꾸세요. 하나만 바꾸면 접속이 안 됩니다.
.env는 절대 커밋하지 않는다. 지금은 개발용 비밀번호라 괜찮아 보여도, 한 번 올라간 파일은 git 히스토리에 영원히 남습니다. 커밋 전 git status에 .env가 보이면 .gitignore가 잘못된 겁니다. 공유할 것은 .env.example뿐입니다.
til 루트 .gitignore와의 관계. 루트 파일에는 .venv가 없어서 이 프로젝트의 .gitignore가 꼭 필요합니다. 그리고 루트가 docs/를 통째로 무시하고 있기 때문에, 이 프로젝트 안에서는 docs/라는 폴더명을 쓰지 마세요. 만들어도 커밋이 안 됩니다. 그래서 가이드는 guides/, 설계 문서는 planning/입니다.
엔진과 Redis 클라이언트를 모듈 수준에서 만들어도 되는 이유. create_async_engine과 Redis.from_url은 둘 다 lazy입니다. 객체만 만들고 실제 소켓 연결은 첫 쿼리·첫 명령 때 맺습니다. 그래서 import만으로 DB에 부하를 주거나 실패하는 일이 없고, 정리(dispose, aclose)만 lifespan 종료 시점에 해 주면 됩니다. 만약 시작 시점에 "연결이 안 되면 아예 뜨지 말아라"가 필요하면 lifespan의 yield 위쪽에 SELECT 1을 한 번 날리면 됩니다.
왜 부분 장애를 503으로 알리나. 헬스체크를 읽는 쪽은 사람이 아니라 기계입니다. 로드밸런서는 200이 아니면 그 서버로 트래픽을 보내지 않고, Docker healthcheck와 CI는 상태 코드로 "준비됐다/안 됐다"를 판단합니다. JSON 안에 "redis": false라고 아무리 적어 놔도 200이면 기계는 "정상"으로 봅니다. 그래서 하나라도 실패하면 503입니다. 본문의 db·redis 필드는 사람이 원인을 빨리 찾으라고 덧붙인 것입니다.
extra="ignore"와 lru_cache. .env에 Settings가 모르는 키(예: 나중에 추가할 JWT_SECRET)가 있어도 에러 내지 말고 무시하라는 게 extra="ignore"입니다. 기본값은 에러라서, 이걸 빼먹으면 3단계에서 키를 추가하는 순간 앱이 안 뜹니다. lru_cache는 "같은 인자로 부르면 이전 결과를 재사용"하는 캐시인데, 인자가 없는 get_settings()에 붙이면 사실상 싱글턴이 됩니다. 테스트에서 설정을 바꿔치기해야 할 때는 get_settings.cache_clear()로 비웁니다.
지금은 넘어가도 되는 두 옵션. pool_pre_ping=True는 풀에서 꺼낸 커넥션이 죽어 있으면 조용히 새로 만들어 주는 옵션이고(Week 5·03 커넥션 풀), expire_on_commit=False는 커밋 후에도 객체 속성을 다시 읽지 않게 하는 옵션으로 async 세션에서는 거의 필수입니다(Week 7·01 엔진·세션). 2단계에서 모델을 만들 때 다시 만납니다.

셀프 체크

Q 엔진을 모듈 수준에서 만들었는데, 그럼 lifespan은 왜 필요한가요? 시작 시점에 만드는 것과 뭐가 다른가요?

create_async_engine은 lazy라서 만드는 시점에 연결하지 않습니다. 그래서 "언제 만드나"는 크게 중요하지 않고, 중요한 건 "언제 정리하나"입니다. 앱이 꺼질 때 풀에 남은 커넥션을 닫지 않으면 DB 쪽에 좀비 연결이 남을 수 있는데, 그 정리 시점을 잡아 주는 게 lifespan의 yield 아래쪽입니다. 시작 시점에 만들고 싶다면 yield 위에서 만들고 app.state에 넣는 방법도 있는데, 그러면 get_db가 request.app.state를 통해 꺼내야 해서 코드가 조금 길어집니다. 이 프로젝트는 단순한 쪽을 택했습니다.

Q Redis만 죽었을 때 200에 "redis": false를 돌려주면 안 되나요? 왜 굳이 503인가요?

헬스체크를 읽는 것은 로드밸런서·Docker·CI 같은 기계이고, 기계는 상태 코드만 봅니다. 200이면 "이 서버에 트래픽 보내도 됨"으로 해석하기 때문에, Redis가 죽어서 세션 조회·캐시·rate limit이 전부 실패하는 서버로 계속 요청이 흘러 들어갑니다. 503을 주면 로드밸런서가 그 서버를 잠시 빼고, 복구되면 다시 넣습니다. 본문의 db·redis 필드는 사람이 원인을 빨리 찾기 위한 부가 정보입니다.

Q .env에 APP_ENV=dev가 있는데 APP_ENV=prod uv run ...이 prod를 찍은 이유는? 이 우선순위가 실무에서 왜 중요한가요?

pydantic-settings의 우선순위는 진짜 환경변수 > .env 파일 > 코드 기본값입니다. 실무에서는 운영 서버나 CI에 .env 파일을 두지 않고 배포 시스템이 환경변수를 주입합니다. 이 우선순위 덕분에 같은 코드·같은 .env.example을 두고도 로컬은 파일로, 운영은 환경변수로 설정을 갈아 끼울 수 있고, 실수로 .env가 서버에 올라가도 환경변수가 이기므로 로컬 설정이 운영을 덮어쓰는 사고가 나지 않습니다.
