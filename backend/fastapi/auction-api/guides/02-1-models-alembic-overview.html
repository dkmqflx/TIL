2-1 개요와 설계

경매 도메인의 네 테이블(users·auctions·bids·payments)을 SQLAlchemy 2.0 모델로 정의하고, 첫날부터 Alembic 마이그레이션으로 DB에 만든 뒤, 제약과 인덱스가 실제로 걸렸는지 테스트로 확인합니다.

학습 목표

  • SQLAlchemy 2.0의 Mapped/mapped_column 스타일로 모델을 쓰고, 공통 컬럼은 믹스인으로 뺀다
  • 금액·시각·enum을 "실무에서 후회하지 않는 타입"으로 고른다 (BigInteger, timezone-aware, VARCHAR enum)
  • CHECK 제약·복합 인덱스·외래키 삭제 규칙을 DB 수준에 건다
  • Alembic async 환경을 설정하고 autogenerate → upgrade → check 흐름을 몸에 익힌다
  • 테스트 인프라가 없어도 "커밋 없이 rollback"으로 DB를 더럽히지 않는 테스트를 쓴다
🎯

이 단계의 목표

이 단계가 끝나면 Postgres 안에 경매 서비스의 뼈대가 되는 네 테이블이 생깁니다. 사용자(users), 경매(auctions), 입찰(bids), 결제(payments)입니다. 테이블을 손으로 CREATE TABLE 하지 않고, 파이썬 모델을 쓰면 Alembic이 그걸 읽어 마이그레이션 파일을 만들어 주고, 그 파일을 실행해서 DB에 반영합니다. 나중에 컬럼을 하나 추가할 때도 같은 흐름을 반복하면 됩니다.

전제. 1단계가 끝나 있어야 합니다. 즉 docker compose ps에서 auction-db·auction-redis가 (healthy)이고, uv run pytest -q가 1 passed여야 합니다. 이번 단계도 같은 디렉터리(til/backend/fastapi/auction-api/)에서 진행합니다.

이번 단계에서 만드는 것. app/models/ 아래 7개 파일, alembic/ 폴더와 alembic.ini, 마이그레이션 파일 1개, tests/test_models.py. 그리고 pyproject.toml의 ruff 설정을 조금 손봅니다. 9단계에서 쓸 webhook_events 테이블은 그때 새 마이그레이션으로 추가합니다 — "필요할 때 마이그레이션 하나 더"가 실무 리듬입니다.
🏢

왜 필요한가 — 스키마는 첫날부터 마이그레이션으로

self-study Week 5에서는 Base.metadata.create_all()로 테이블을 만들었습니다. 배울 때는 편하지만 실무에서는 거의 쓰지 않습니다. create_all은 "없는 테이블을 만든다"만 할 줄 알고, 이미 있는 테이블에 컬럼을 추가하거나 타입을 바꾸는 것은 못 합니다. 서비스가 한 번이라도 배포되고 나면 그 뒤의 모든 변경은 "지금 있는 데이터를 살리면서 구조만 바꾸기"인데, 그걸 해 주는 게 마이그레이션 도구(Alembic)입니다. Week 10·02에서 배웠던 걸 이번엔 프로젝트 시작 시점에 씁니다. 나중에 도입하려고 하면 "지금 DB 상태를 어떻게 첫 마이그레이션으로 잡지?"라는 골치 아픈 문제가 생기기 때문입니다.

두 번째로 중요한 건 제약을 DB에 거는 습관입니다. "금액은 0보다 커야 한다", "마감은 시작보다 뒤여야 한다" 같은 규칙은 3단계 이후 Pydantic으로도 검사하지만, DB의 CHECK 제약은 마지막 방어선입니다. 6단계에서 수십 개의 요청이 동시에 같은 경매를 두드릴 때, 애플리케이션 코드의 검사만으로는 막을 수 없는 틈이 생기는데, DB 제약은 어떤 경로로 들어오든 예외 없이 막습니다. 관리자가 psql로 직접 데이터를 고치다가 실수해도 막습니다.

세 번째는 인덱스를 지금 잡는 것입니다. 5단계 목록 조회는 "상태가 active이면서 마감이 가까운 순"으로 정렬하고, 6단계는 "이 경매의 최고 입찰"을 수시로 찾습니다. 이 두 쿼리에 맞는 복합 인덱스((status, ends_at), (auction_id, amount DESC))를 설계 시점에 같이 만들어 둡니다. 데이터가 쌓인 뒤에 인덱스를 추가하는 것도 마이그레이션으로 가능하지만, "왜 느리지?"를 겪고 나서 찾는 것보다 설계할 때 쿼리를 상상하며 잡는 편이 훨씬 쌉니다.

📐

비유 — 설계도, 공사 일지, 그리고 안전 규정

모델은 설계도, 마이그레이션은 공사 일지입니다. 건물의 설계도(app/models/)를 바꾸면, 현장에서는 "3층에 벽 하나 추가, 2층 창문 제거"처럼 변경 작업만 적은 공사 일지가 하나 생깁니다(alembic/versions/xxx.py). 일지는 날짜순으로 쌓이고, 어떤 현장이든 일지를 처음부터 순서대로 따라가면 같은 건물이 됩니다. alembic upgrade head는 "아직 안 한 일지를 전부 실행하라", downgrade는 "마지막 작업을 되돌려라"입니다. 반면 create_all은 "빈 땅에 설계도대로 한 번에 짓기"라서 이미 사람이 사는 건물에는 쓸 수 없습니다.
CHECK 제약은 건축 안전 규정입니다. 설계자가 "이 벽은 하중을 버텨야 한다"를 깜빡해도, 검사관(DB)이 규정에 어긋나는 시공을 승인하지 않습니다. 애플리케이션 코드는 설계자이고 실수할 수 있지만, CHECK (amount > 0)은 어떤 경로로 데이터가 들어오든 예외 없이 적용됩니다. 그래서 규칙 중에서도 "절대 깨지면 안 되는 것"은 DB에 새깁니다.
인덱스는 책 뒤의 색인입니다. "active인 경매를 마감 순으로"를 자주 찾는다면 그 순서로 정리된 색인((status, ends_at))을 미리 만들어 두면 됩니다. 색인이 없으면 매번 책을 처음부터 끝까지 넘겨야 하고(전체 스캔), 데이터가 10만 건이 되는 순간 체감됩니다.
🗺️

설계 그림 — 네 테이블의 관계

사용자 한 명은 여러 경매를 열 수 있고(판매자), 여러 입찰을 할 수 있으며(입찰자), 경매 하나에는 여러 입찰이 붙고, 낙찰되면 결제가 정확히 하나 생깁니다. auctions에서 users로 가는 화살표가 둘(seller_id, winner_id)이라는 점을 눈여겨보세요 — 코드에서 이걸 따로 알려 줘야 하는 지점이 있습니다.

users를 세 테이블이 참조하고, auctions는 users를 두 번(판매자·낙찰자) 참조한다. payments.auction_id는 UNIQUE라 경매당 결제 한 건.

두 번째 그림은 Alembic이 일하는 흐름입니다. 핵심은 모델과 DB 사이에 "파일"이 하나 끼어 있다는 점입니다. 모델을 고쳐도 DB는 바로 안 바뀝니다. revision --autogenerate가 모델과 DB의 차이를 계산해 파일로 적고, 그 파일을 검토한 뒤 upgrade head로 실행해야 비로소 DB가 바뀝니다. DB 안의 alembic_version 테이블이 "어느 일지까지 실행했는지"를 기억합니다.

모델을 바꾸면 → 일지를 만들고 → 실행한다. 세 단계가 분리돼 있어서 실행 전에 사람이 검토할 수 있다.
