실행·확인 — 이 출력이 나와야 한다

1. Alembic 상태

current는 "DB가 어느 일지까지 실행됐나", history는 "일지 목록", check는 "모델과 DB가 지금 같은가"입니다. check가 No new upgrade operations detected.를 찍으면 모델과 DB가 완전히 일치한다는 뜻입니다. 10단계 CI에서 이 명령으로 "마이그레이션 안 만들고 모델만 고친 커밋"을 잡아냅니다.

bash
uv run alembic current
# 8d6a60ccfea0 (head)
uv run alembic history
# <base> -> 8d6a60ccfea0 (head), create users auctions bids payments
uv run alembic check
# No new upgrade operations detected.

2. DB에 진짜로 걸렸는지 — psql로 확인

3. 테스트 통과

⑨에서 실패했던 두 테스트가 이제 통과합니다. 1단계의 헬스체크 테스트까지 합쳐 4개입니다. 테스트가 끝난 뒤 users에 행이 남아 있지 않은지도 확인해 보세요 — rollback이 제대로 됐다는 증거입니다.

bash
uv run pytest -q
# ....                                                                     [100%]
# 4 passed in 0.67s

uv run ruff check .
# All checks passed!

docker compose exec db psql -U auction -d auction -tAc 'select count(*) from users'
# 0

4. 되돌렸다가 다시 적용 — 마이그레이션의 왕복

마이그레이션의 진짜 가치는 "되돌릴 수 있다"입니다. downgrade base로 맨 처음 상태(테이블 없음)로 돌아갔다가 upgrade head로 다시 올라옵니다. downgrade() 함수가 제대로 쓰였는지 확인하는 습관입니다. 되돌린 상태에서 \dt를 치면 alembic_version만 남습니다.

bash
uv run alembic downgrade base
# INFO  [alembic.runtime.migration] Running downgrade 8d6a60ccfea0 -> , create users auctions bids payments
docker compose exec db psql -U auction -d auction -c '\dt'
#  public | alembic_version | table | auction
uv run alembic upgrade head
# INFO  [alembic.runtime.migration] Running upgrade  -> 8d6a60ccfea0, create users auctions bids payments
uv run pytest -q
# 4 passed in 0.52s
✅

완료 기준 체크리스트

  • uv run python -c "from app.models import Base; print(sorted(Base.metadata.tables))" → 네 테이블
  • uv run alembic current → <rev> (head), uv run alembic check → No new upgrade operations detected.
  • \d auctions에 CHECK 4개 · 인덱스 3개 · FK 2개(CASCADE / SET NULL), \d bids에 (auction_id, amount DESC)
  • uv run pytest -q → 4 passed, 경고 없음, 테스트 후 users 행 수 0
  • uv run ruff check . → All checks passed!
  • alembic downgrade base → upgrade head 왕복이 에러 없이 됨
  • git status에 alembic.ini, alembic/, app/models/*.py, tests/test_models.py가 보이고 .env는 안 보임
여기서 커밋하세요. 마이그레이션 파일은 반드시 함께 커밋합니다 — 다른 사람(그리고 CI)이 같은 스키마를 만들 수 있어야 하니까요. 예: git commit -m "add(be(fastapi)): auction-api 2단계 — 도메인 모델과 첫 마이그레이션"

함정 & 실무 팁

enum을 VARCHAR로 저장한 이유 (native enum을 안 쓴 이유). Postgres에는 진짜 ENUM 타입이 있고 SQLAlchemy 기본값(native_enum=True)은 그걸 씁니다. 저장 공간이 조금 작고 DB가 값을 검사해 주는 장점이 있지만, 값을 하나 추가할 때마다 ALTER TYPE ... ADD VALUE가 필요하고, 이 명령은 트랜잭션 안에서 못 쓰는 등 제약이 많으며, Alembic autogenerate가 enum 값 변경을 감지하지 못합니다. 카테고리처럼 자주 늘어나는 값에는 부담입니다. native_enum=False는 그냥 VARCHAR(20)이라 값 추가가 파이썬 코드 수정만으로 끝납니다. 대신 DB가 값을 검사하지 않으므로 검증은 Pydantic(3단계 이후)이 맡습니다. 둘 다 정답이 될 수 있고, 팀에서 하나로 정해 일관되게 쓰는 게 중요합니다.
autogenerate가 못 보는 것들. 컬럼·테이블·인덱스·이름 붙은 제약의 추가/삭제는 잘 잡지만, 테이블 이름 변경은 "삭제 + 추가"로 잡아서 데이터가 날아가고, enum 값 변경·server_default 변경·CHECK 제약의 내용 변경은 종종 놓칩니다. 그래서 생성된 파일을 반드시 읽어 보고, 필요하면 op.rename_table·op.alter_column으로 손으로 고칩니다. 자세한 목록은 Week 10·02 autogenerate의 한계.
alembic 폴더 이름과 ruff. 프로젝트에 alembic/ 폴더가 있으면 ruff의 import 정렬이 from alembic import context를 내 코드로 간주해 app 옆에 두려 합니다. ①에서 known-third-party = ["alembic"]을 넣은 이유입니다. 폴더 이름을 migrations로 바꿔 피하는 팀도 많습니다(alembic init -t async migrations + alembic.ini의 script_location 수정).
돈은 절대 float으로 저장하지 않는다. 0.1 + 0.2 != 0.3인 부동소수점으로 금액을 다루면 합계가 어긋납니다. 원 단위 정수(BigInteger)가 가장 단순하고, 소수점이 필요한 통화라면 Numeric(precision, scale)을 씁니다. Integer(약 21억)가 아니라 BigInteger인 이유는 경매 최고가가 21억을 넘는 날이 올 수도 있기 때문입니다 — 나중에 타입을 바꾸는 마이그레이션은 테이블 락을 잡아 고통스럽습니다.
시각은 항상 DateTime(timezone=True) + UTC. timezone=False(기본값)로 만들면 "09:00"이 한국 9시인지 UTC 9시인지 DB가 모릅니다. 서버가 여러 대이거나 클라우드로 옮기는 순간 마감 시각이 9시간 어긋나는 사고가 납니다. 테스트에서 datetime.now(UTC)를 쓴 것도, created_at.tzinfo is not None을 확인한 것도 그래서입니다. 표시할 때만 사용자의 시간대로 바꿉니다.
expire_on_commit=False와 refresh(). 1단계에서 세션 공장에 expire_on_commit=False를 줬습니다. async 세션에서는 커밋 후 속성을 읽을 때 자동으로 재조회(lazy load)가 일어나면 안 되기 때문입니다. 대신 server_default로 DB가 채운 값(created_at)은 파이썬 객체에 없으니, 필요하면 await session.refresh(obj)로 명시적으로 읽어 옵니다. 테스트의 refresh(auction)이 그 예입니다.
Base.metadata.create_all()은 이 프로젝트에서 금지. Alembic과 create_all을 섞으면 "DB엔 테이블이 있는데 alembic_version은 비어 있는" 상태가 되어 upgrade head가 "이미 테이블이 있다"며 실패합니다. 스키마를 만드는 방법은 오직 alembic upgrade head 하나입니다. 3단계의 테스트 DB도 마이그레이션으로 만듭니다.
모델을 고쳤을 때의 루틴. ① 모델 수정 → ② uv run alembic revision --autogenerate -m "무엇을 왜" → ③ 생성된 파일 읽기 → ④ uv run alembic upgrade head → ⑤ uv run alembic check로 일치 확인 → ⑥ 모델과 마이그레이션을 같은 커밋에. 이 루틴을 9단계(webhook_events 추가)에서 한 번 더 합니다.
alembic 명령은 프로젝트 루트에서. env.py가 app.core.config를 import하는데, 이게 되는 건 alembic.ini의 prepend_sys_path = .("현재 폴더를 import 경로에 추가") 덕분입니다. guides/나 app/ 안에서 실행하면 ModuleNotFoundError: No module named 'app'이 납니다. .env도 현재 폴더에서 읽으므로 같은 이유로 루트여야 합니다.

셀프 체크

Q 3단계부터 Pydantic이 요청을 검증할 텐데, 왜 DB에도 CHECK 제약을 거나요? 중복 아닌가요?

검증 위치가 다릅니다. Pydantic은 HTTP 요청이라는 한 경로만 지킵니다. 하지만 데이터는 배치 스크립트, 관리자의 psql, 8단계 워커, 나중에 붙을 다른 서비스 등 여러 경로로 들어옵니다. DB 제약은 경로와 무관하게 마지막 방어선입니다. 특히 6단계처럼 동시 요청이 몰릴 때 "앱이 검사한 시점"과 "DB에 쓰는 시점" 사이에 상태가 바뀔 수 있는데, 제약은 쓰는 시점에 원자적으로 적용됩니다. Pydantic 검증은 사용자에게 친절한 에러 메시지를 주기 위한 것이고, CHECK는 데이터가 절대 깨지지 않게 하기 위한 것입니다. 역할이 다르니 둘 다 둡니다.

Q native_enum=False로 저장하면 DB가 status='banana' 같은 값을 막지 못하는데, 괜찮은가요?

트레이드오프입니다. native ENUM은 DB가 값을 검사하지만 값을 추가할 때 ALTER TYPE이 필요하고 autogenerate가 그 변경을 못 잡아 운영 중 실수가 잦습니다. VARCHAR는 값 검증을 애플리케이션(Pydantic + StrEnum)이 하고, DB 변경 없이 값을 늘릴 수 있습니다. 정말 DB 수준 검증이 필요하면 CheckConstraint("status IN ('scheduled','active','ended','cancelled')")를 추가하는 절충도 있습니다 — 이건 autogenerate가 이름으로 추적할 수 있어서 native ENUM보다 다루기 쉽습니다. 중요한 건 "왜 이 선택을 했는지"를 설명할 수 있는 것입니다.

Q 개발 초기라 데이터도 없는데 그냥 create_all() 쓰다가 나중에 Alembic을 붙이면 안 되나요?

가능은 하지만 "나중에" 붙이는 순간 두 가지 문제를 만납니다. 첫째, 이미 테이블이 있는 DB에 첫 마이그레이션을 적용하려면 alembic stamp head로 "이미 적용된 셈 치자"고 속여야 하는데, 여러 환경(내 PC, 동료 PC, 스테이징)의 상태가 제각각이면 어느 것을 stamp해야 할지 꼬입니다. 둘째, 그동안 모델 변경 이력이 없어서 "언제 무엇이 바뀌었나"를 복원할 수 없습니다. 첫 마이그레이션이 빈 DB에서 시작하면 모든 환경이 같은 일지를 처음부터 재생할 수 있어서, 처음부터 Alembic을 쓰는 비용이 가장 쌉니다.
