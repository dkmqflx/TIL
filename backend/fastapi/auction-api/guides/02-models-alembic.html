2단계 — 모델링 + Alembic

경매 도메인의 네 테이블(users·auctions·bids·payments)을 SQLAlchemy 2.0 모델로 정의하고, 첫날부터 Alembic 마이그레이션으로 DB에 만든 뒤, 제약과 인덱스가 실제로 걸렸는지 테스트로 확인합니다.

한 줄 요약. 이 문서를 끝내면 uv run alembic upgrade head 한 줄로 DB 스키마가 만들어지고, psql로 들여다보면 CHECK 제약·인덱스·외래키가 전부 걸려 있으며, uv run pytest -q가 4 passed를 찍습니다. 아직 API는 없지만 3단계부터 만드는 모든 기능이 이 테이블 위에서 돕니다.

학습 목표

  • SQLAlchemy 2.0의 Mapped/mapped_column 스타일로 모델을 쓰고, 공통 컬럼은 믹스인으로 뺀다
  • 금액·시각·enum을 "실무에서 후회하지 않는 타입"으로 고른다 (BigInteger, timezone-aware, VARCHAR enum)
  • CHECK 제약·복합 인덱스·외래키 삭제 규칙을 DB 수준에 건다
  • Alembic async 환경을 설정하고 autogenerate → upgrade → check 흐름을 몸에 익힌다
  • 테스트 인프라가 없어도 "커밋 없이 rollback"으로 DB를 더럽히지 않는 테스트를 쓴다
🎯

이 단계의 목표

이 단계가 끝나면 Postgres 안에 경매 서비스의 뼈대가 되는 네 테이블이 생깁니다. 사용자(users), 경매(auctions), 입찰(bids), 결제(payments)입니다. 테이블을 손으로 CREATE TABLE 하지 않고, 파이썬 모델을 쓰면 Alembic이 그걸 읽어 마이그레이션 파일을 만들어 주고, 그 파일을 실행해서 DB에 반영합니다. 나중에 컬럼을 하나 추가할 때도 같은 흐름을 반복하면 됩니다.

전제. 1단계가 끝나 있어야 합니다. 즉 docker compose ps에서 auction-db·auction-redis가 (healthy)이고, uv run pytest -q가 1 passed여야 합니다. 이번 단계도 같은 디렉터리(til/backend/fastapi/auction-api/)에서 진행합니다.

이번 단계에서 만드는 것. app/models/ 아래 7개 파일, alembic/ 폴더와 alembic.ini, 마이그레이션 파일 1개, tests/test_models.py. 그리고 pyproject.toml의 ruff 설정을 조금 손봅니다. 9단계에서 쓸 webhook_events 테이블은 그때 새 마이그레이션으로 추가합니다 — "필요할 때 마이그레이션 하나 더"가 실무 리듬입니다.

왜 필요한가 — 스키마는 첫날부터 마이그레이션으로

self-study Week 5에서는 Base.metadata.create_all()로 테이블을 만들었습니다. 배울 때는 편하지만 실무에서는 거의 쓰지 않습니다. create_all은 "없는 테이블을 만든다"만 할 줄 알고, 이미 있는 테이블에 컬럼을 추가하거나 타입을 바꾸는 것은 못 합니다. 서비스가 한 번이라도 배포되고 나면 그 뒤의 모든 변경은 "지금 있는 데이터를 살리면서 구조만 바꾸기"인데, 그걸 해 주는 게 마이그레이션 도구(Alembic)입니다. Week 10·02에서 배웠던 걸 이번엔 프로젝트 시작 시점에 씁니다. 나중에 도입하려고 하면 "지금 DB 상태를 어떻게 첫 마이그레이션으로 잡지?"라는 골치 아픈 문제가 생기기 때문입니다.

두 번째로 중요한 건 제약을 DB에 거는 습관입니다. "금액은 0보다 커야 한다", "마감은 시작보다 뒤여야 한다" 같은 규칙은 3단계 이후 Pydantic으로도 검사하지만, DB의 CHECK 제약은 마지막 방어선입니다. 6단계에서 수십 개의 요청이 동시에 같은 경매를 두드릴 때, 애플리케이션 코드의 검사만으로는 막을 수 없는 틈이 생기는데, DB 제약은 어떤 경로로 들어오든 예외 없이 막습니다. 관리자가 psql로 직접 데이터를 고치다가 실수해도 막습니다.

세 번째는 인덱스를 지금 잡는 것입니다. 5단계 목록 조회는 "상태가 active이면서 마감이 가까운 순"으로 정렬하고, 6단계는 "이 경매의 최고 입찰"을 수시로 찾습니다. 이 두 쿼리에 맞는 복합 인덱스((status, ends_at), (auction_id, amount DESC))를 설계 시점에 같이 만들어 둡니다. 데이터가 쌓인 뒤에 인덱스를 추가하는 것도 마이그레이션으로 가능하지만, "왜 느리지?"를 겪고 나서 찾는 것보다 설계할 때 쿼리를 상상하며 잡는 편이 훨씬 쌉니다.

비유 — 설계도, 공사 일지, 그리고 안전 규정

모델은 설계도, 마이그레이션은 공사 일지입니다. 건물의 설계도(app/models/)를 바꾸면, 현장에서는 "3층에 벽 하나 추가, 2층 창문 제거"처럼 변경 작업만 적은 공사 일지가 하나 생깁니다(alembic/versions/xxx.py). 일지는 날짜순으로 쌓이고, 어떤 현장이든 일지를 처음부터 순서대로 따라가면 같은 건물이 됩니다. alembic upgrade head는 "아직 안 한 일지를 전부 실행하라", downgrade는 "마지막 작업을 되돌려라"입니다. 반면 create_all은 "빈 땅에 설계도대로 한 번에 짓기"라서 이미 사람이 사는 건물에는 쓸 수 없습니다.
CHECK 제약은 건축 안전 규정입니다. 설계자가 "이 벽은 하중을 버텨야 한다"를 깜빡해도, 검사관(DB)이 규정에 어긋나는 시공을 승인하지 않습니다. 애플리케이션 코드는 설계자이고 실수할 수 있지만, CHECK (amount > 0)은 어떤 경로로 데이터가 들어오든 예외 없이 적용됩니다. 그래서 규칙 중에서도 "절대 깨지면 안 되는 것"은 DB에 새깁니다.
인덱스는 책 뒤의 색인입니다. "active인 경매를 마감 순으로"를 자주 찾는다면 그 순서로 정리된 색인((status, ends_at))을 미리 만들어 두면 됩니다. 색인이 없으면 매번 책을 처음부터 끝까지 넘겨야 하고(전체 스캔), 데이터가 10만 건이 되는 순간 체감됩니다.

설계 그림 — 네 테이블의 관계

사용자 한 명은 여러 경매를 열 수 있고(판매자), 여러 입찰을 할 수 있으며(입찰자), 경매 하나에는 여러 입찰이 붙고, 낙찰되면 결제가 정확히 하나 생깁니다. auctions에서 users로 가는 화살표가 둘(seller_id, winner_id)이라는 점을 눈여겨보세요 — 코드에서 이걸 따로 알려 줘야 하는 지점이 있습니다.

users를 세 테이블이 참조하고, auctions는 users를 두 번(판매자·낙찰자) 참조한다. payments.auction_id는 UNIQUE라 경매당 결제 한 건.

두 번째 그림은 Alembic이 일하는 흐름입니다. 핵심은 모델과 DB 사이에 "파일"이 하나 끼어 있다는 점입니다. 모델을 고쳐도 DB는 바로 안 바뀝니다. revision --autogenerate가 모델과 DB의 차이를 계산해 파일로 적고, 그 파일을 검토한 뒤 upgrade head로 실행해야 비로소 DB가 바뀝니다. DB 안의 alembic_version 테이블이 "어느 일지까지 실행했는지"를 기억합니다.

모델을 바꾸면 → 일지를 만들고 → 실행한다. 세 단계가 분리돼 있어서 실행 전에 사람이 검토할 수 있다.
🔧

구현 — 파일을 하나씩 만든다

순서는 의존성 → 모델 → 테스트(실패 확인) → Alembic → 마이그레이션 생성·실행입니다. 각 코드 블록은 붙여넣으면 그대로 도는 전체 파일이고, "(수정)"이 붙은 블록만 기존 파일의 일부를 바꾸는 것입니다.

① Alembic 설치와 ruff 설정

Alembic은 운영 서버에서도 마이그레이션을 실행해야 하므로 --dev 없이 일반 의존성으로 넣습니다.

bash
uv add alembic
# 검증 당시: alembic 1.19.1

그리고 pyproject.toml의 ruff 설정 두 곳을 손봅니다. 이유가 둘 있습니다. 첫째, 잠시 뒤 프로젝트 안에 alembic/이라는 폴더가 생기는데, ruff는 그걸 보고 "alembic은 이 프로젝트의 자체 모듈이구나"라고 오해합니다. 그러면 from alembic import context를 외부 라이브러리가 아닌 내 코드 취급해서 import 정렬을 틀리게 잡습니다. known-third-party로 바로잡습니다. 둘째, Alembic이 자동 생성하는 마이그레이션 파일은 우리 스타일 규칙(줄 길이, 따옴표)을 안 지키는데, 자동 생성물을 매번 손으로 고치는 건 의미가 없으니 검사에서 뺍니다.

toml(수정) pyproject.toml — [tool.ruff] 부터 [tool.ruff.lint.isort] 까지를 이렇게 바꾼다
[tool.ruff]
target-version = "py313"
line-length = 100
extend-exclude = ["alembic/versions"]  # 자동 생성 파일은 검사 제외

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B"]

[tool.ruff.lint.isort]
known-third-party = ["alembic"]  # 프로젝트에 alembic/ 폴더가 있어 1st-party 로 오인하는 것 방지
무엇이 바뀌었나. 1단계의 [tool.ruff]에 extend-exclude 한 줄이 추가됐고, [tool.ruff.lint.isort] 섹션이 새로 생겼습니다. [tool.pytest.ini_options]는 그대로 둡니다.

② app/models/base.py — 모든 모델의 부모와 공통 컬럼

Base는 Week 5·02의 DeclarativeBase 그대로입니다. 여기에 믹스인 두 개를 추가합니다. 네 테이블 모두 id(UUID)와 created_at을 갖는데, 매번 같은 두 줄을 복사하지 않고 작은 클래스로 빼서 상속시키는 방식입니다. sort_order는 믹스인 컬럼이 테이블에서 몇 번째에 올지 정하는 옵션인데, 이게 없으면 믹스인의 컬럼은 자식 클래스 컬럼 뒤에 붙어서 id가 맨 마지막 컬럼이 되는 어색한 테이블이 됩니다.

pythonapp/models/base.py
import uuid
from datetime import datetime

from sqlalchemy import DateTime, func
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column


class Base(DeclarativeBase):
    """모든 모델의 부모. Base.metadata 에 테이블 정의가 모인다 (Alembic 이 이걸 본다)."""


class UUIDPrimaryKeyMixin:
    id: Mapped[uuid.UUID] = mapped_column(primary_key=True, default=uuid.uuid4, sort_order=-100)


class CreatedAtMixin:
    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), server_default=func.now(), nullable=False, sort_order=100
    )

두 가지 선택을 설명하면, UUID를 기본키로 쓴 이유는 경매 ID가 URL에 노출되기 때문입니다. 정수 ID는 /auctions/1, /auctions/2처럼 다음 번호가 뻔해서 남의 경매를 순서대로 긁어갈 수 있습니다. default=uuid.uuid4는 파이썬 쪽에서 값을 만들어 INSERT하라는 뜻입니다. server_default=func.now()는 반대로 DB가 값을 채우게 하는 것인데, 여러 서버의 시계가 조금씩 달라도 DB 시계 하나를 기준으로 통일되는 장점이 있습니다.

③ app/models/enums.py — 상태와 분류

경매 상태·카테고리·결제 상태처럼 "정해진 값 중 하나"는 파이썬 StrEnum으로 정의합니다. 문자열을 상속하기 때문에 AuctionStatus.ACTIVE == "active"가 참이고, JSON으로 내보낼 때도 그냥 문자열이 됩니다. 맨 아래 enum_values는 SQLAlchemy가 DB에 저장할 값 목록을 만들어 주는 작은 도우미입니다 — 이게 없으면 SQLAlchemy는 이름("ACTIVE")을 저장하는데, 우리는 값("active")을 저장하고 싶습니다.

pythonapp/models/enums.py
from enum import StrEnum


class AuctionStatus(StrEnum):
    SCHEDULED = "scheduled"  # 시작 전
    ACTIVE = "active"  # 입찰 받는 중
    ENDED = "ended"  # 마감 (낙찰 또는 유찰)
    CANCELLED = "cancelled"  # 판매자가 취소 (입찰 0건일 때만)


class AuctionCategory(StrEnum):
    ELECTRONICS = "electronics"
    FASHION = "fashion"
    HOME = "home"
    BOOKS = "books"
    HOBBY = "hobby"
    ETC = "etc"


class PaymentStatus(StrEnum):
    PENDING = "pending"  # 낙찰 직후, 결제 대기
    PAID = "paid"
    EXPIRED = "expired"  # 기한 내 미결제


def enum_values(enum_cls: type[StrEnum]) -> list[str]:
    """Enum(values_callable=...) 용 — DB 에 이름("ACTIVE") 대신 값("active") 을 저장한다."""
    return [m.value for m in enum_cls]

④ app/models/user.py — 사용자

가장 단순한 모델입니다. 믹스인 두 개와 Base를 상속하면 id와 created_at이 자동으로 따라옵니다. Mapped[str]처럼 | None이 없는 타입은 NOT NULL이 됩니다(Week 5·02의 nullable 규칙). 비밀번호는 절대 평문으로 저장하지 않으므로 컬럼 이름부터 password_hash입니다 — 해싱은 3단계에서 합니다.

pythonapp/models/user.py
from sqlalchemy import String
from sqlalchemy.orm import Mapped, mapped_column

from app.models.base import Base, CreatedAtMixin, UUIDPrimaryKeyMixin


class User(UUIDPrimaryKeyMixin, CreatedAtMixin, Base):
    __tablename__ = "users"

    email: Mapped[str] = mapped_column(String(255), unique=True)
    password_hash: Mapped[str] = mapped_column(String(255))
    nickname: Mapped[str] = mapped_column(String(50))

⑤ app/models/auction.py — 경매 (핵심 테이블)

가장 긴 모델이니 위에서부터 읽어 내려가겠습니다. __table_args__에는 컬럼이 아닌 테이블 수준 정의(CHECK 제약, 복합 인덱스)를 넣습니다. 제약마다 name=을 꼭 붙이세요. 이름이 없으면 DB가 임의의 이름을 붙이는데, 나중에 마이그레이션으로 제약을 지우거나 바꿀 때 그 이름을 알아야 해서 곤란해집니다.

users로 가는 외래키가 둘입니다. seller_id는 판매자라 필수이고 ondelete="CASCADE"(판매자가 탈퇴하면 경매도 삭제), winner_id는 낙찰 전엔 비어 있으니 | None이고 SET NULL(낙찰자가 탈퇴해도 경매 기록은 남기되 낙찰자만 비움)입니다. 이렇게 같은 테이블로 가는 관계가 둘이면 relationship()에 foreign_keys=로 "이 관계는 이 컬럼을 쓴다"를 명시해야 합니다. 안 하면 SQLAlchemy가 어느 컬럼으로 조인할지 몰라 에러를 냅니다.

pythonapp/models/auction.py
import uuid
from datetime import datetime
from typing import TYPE_CHECKING

from sqlalchemy import (
    BigInteger,
    CheckConstraint,
    DateTime,
    Enum,
    ForeignKey,
    Index,
    String,
    Text,
    func,
)
from sqlalchemy.orm import Mapped, mapped_column, relationship

from app.models.base import Base, CreatedAtMixin, UUIDPrimaryKeyMixin
from app.models.enums import AuctionCategory, AuctionStatus, enum_values

if TYPE_CHECKING:
    from app.models.bid import Bid
    from app.models.user import User


class Auction(UUIDPrimaryKeyMixin, CreatedAtMixin, Base):
    __tablename__ = "auctions"
    __table_args__ = (
        CheckConstraint("starting_price > 0", name="ck_auctions_starting_price_positive"),
        CheckConstraint("current_price > 0", name="ck_auctions_current_price_positive"),
        CheckConstraint("min_increment > 0", name="ck_auctions_min_increment_positive"),
        CheckConstraint("ends_at > starts_at", name="ck_auctions_ends_after_starts"),

    fileConfig(config.config_file_name)

target_metadata = Base.metadata


def run_migrations_offline() -> None:
    """DB 연결 없이 SQL 만 출력하는 모드 (alembic upgrade head --sql)."""
    url = config.get_main_option("sqlalchemy.url")
    context.configure(
        url=url,
        target_metadata=target_metadata,
        literal_binds=True,
        dialect_opts={"paramstyle": "named"},
        compare_type=True,
    )
    with context.begin_transaction():
        context.run_migrations()


def do_run_migrations(connection: Connection) -> None:
    context.configure(connection=connection, target_metadata=target_metadata, compare_type=True)
    with context.begin_transaction():
        context.run_migrations()


async def run_async_migrations() -> None:
    """asyncpg 엔진으로 연결한 뒤, 동기 API 인 Alembic 을 run_sync 로 감싸 실행한다."""
    connectable = async_engine_from_config(
        config.get_section(config.config_ini_section, {}),
        prefix="sqlalchemy.",
        poolclass=pool.NullPool,
    )
    async with connectable.connect() as connection:
        await connection.run_sync(do_run_migrations)
    await connectable.dispose()


def run_migrations_online() -> None:
    asyncio.run(run_async_migrations())


if context.is_offline_mode():
    run_migrations_offline()
else:
    run_migrations_online()

함정 & 실무 팁

enum을 VARCHAR로 저장한 이유 (native enum을 안 쓴 이유). Postgres에는 진짜 ENUM 타입이 있고 SQLAlchemy 기본값(native_enum=True)은 그걸 씁니다. 저장 공간이 조금 작고 DB가 값을 검사해 주는 장점이 있지만, 값을 하나 추가할 때마다 ALTER TYPE ... ADD VALUE가 필요하고, 이 명령은 트랜잭션 안에서 못 쓰는 등 제약이 많으며, Alembic autogenerate가 enum 값 변경을 감지하지 못합니다. 카테고리처럼 자주 늘어나는 값에는 부담입니다. native_enum=False는 그냥 VARCHAR(20)이라 값 추가가 파이썬 코드 수정만으로 끝납니다. 대신 DB가 값을 검사하지 않으므로 검증은 Pydantic(3단계 이후)이 맡습니다. 둘 다 정답이 될 수 있고, 팀에서 하나로 정해 일관되게 쓰는 게 중요합니다.
autogenerate가 못 보는 것들. 컬럼·테이블·인덱스·이름 붙은 제약의 추가/삭제는 잘 잡지만, 테이블 이름 변경은 "삭제 + 추가"로 잡아서 데이터가 날아가고, enum 값 변경·server_default 변경·CHECK 제약의 내용 변경은 종종 놓칩니다. 그래서 생성된 파일을 반드시 읽어 보고, 필요하면 op.rename_table·op.alter_column으로 손으로 고칩니다. 자세한 목록은 Week 10·02 autogenerate의 한계.
alembic 폴더 이름과 ruff. 프로젝트에 alembic/ 폴더가 있으면 ruff의 import 정렬이 from alembic import context를 내 코드로 간주해 app 옆에 두려 합니다. ①에서 known-third-party = ["alembic"]을 넣은 이유입니다. 폴더 이름을 migrations로 바꿔 피하는 팀도 많습니다(alembic init -t async migrations + alembic.ini의 script_location 수정).
돈은 절대 float으로 저장하지 않는다. 0.1 + 0.2 != 0.3인 부동소수점으로 금액을 다루면 합계가 어긋납니다. 원 단위 정수(BigInteger)가 가장 단순하고, 소수점이 필요한 통화라면 Numeric(precision, scale)을 씁니다. Integer(약 21억)가 아니라 BigInteger인 이유는 경매 최고가가 21억을 넘는 날이 올 수도 있기 때문입니다 — 나중에 타입을 바꾸는 마이그레이션은 테이블 락을 잡아 고통스럽습니다.
시각은 항상 DateTime(timezone=True) + UTC. timezone=False(기본값)로 만들면 "09:00"이 한국 9시인지 UTC 9시인지 DB가 모릅니다. 서버가 여러 대이거나 클라우드로 옮기는 순간 마감 시각이 9시간 어긋나는 사고가 납니다. 테스트에서 datetime.now(UTC)를 쓴 것도, created_at.tzinfo is not None을 확인한 것도 그래서입니다. 표시할 때만 사용자의 시간대로 바꿉니다.
expire_on_commit=False와 refresh(). 1단계에서 세션 공장에 expire_on_commit=False를 줬습니다. async 세션에서는 커밋 후 속성을 읽을 때 자동으로 재조회(lazy load)가 일어나면 안 되기 때문입니다. 대신 server_default로 DB가 채운 값(created_at)은 파이썬 객체에 없으니, 필요하면 await session.refresh(obj)로 명시적으로 읽어 옵니다. 테스트의 refresh(auction)이 그 예입니다.
Base.metadata.create_all()은 이 프로젝트에서 금지. Alembic과 create_all을 섞으면 "DB엔 테이블이 있는데 alembic_version은 비어 있는" 상태가 되어 upgrade head가 "이미 테이블이 있다"며 실패합니다. 스키마를 만드는 방법은 오직 alembic upgrade head 하나입니다. 3단계의 테스트 DB도 마이그레이션으로 만듭니다.
모델을 고쳤을 때의 루틴. ① 모델 수정 → ② uv run alembic revision --autogenerate -m "무엇을 왜" → ③ 생성된 파일 읽기 → ④ uv run alembic upgrade head → ⑤ uv run alembic check로 일치 확인 → ⑥ 모델과 마이그레이션을 같은 커밋에. 이 루틴을 9단계(webhook_events 추가)에서 한 번 더 합니다.
alembic 명령은 프로젝트 루트에서. env.py가 app.core.config를 import하는데, 이게 되는 건 alembic.ini의 prepend_sys_path = .("현재 폴더를 import 경로에 추가") 덕분입니다. guides/나 app/ 안에서 실행하면 ModuleNotFoundError: No module named 'app'이 납니다. .env도 현재 폴더에서 읽으므로 같은 이유로 루트여야 합니다.

셀프 체크

Q 3단계부터 Pydantic이 요청을 검증할 텐데, 왜 DB에도 CHECK 제약을 거나요? 중복 아닌가요?

검증 위치가 다릅니다. Pydantic은 HTTP 요청이라는 한 경로만 지킵니다. 하지만 데이터는 배치 스크립트, 관리자의 psql, 8단계 워커, 나중에 붙을 다른 서비스 등 여러 경로로 들어옵니다. DB 제약은 경로와 무관하게 마지막 방어선입니다. 특히 6단계처럼 동시 요청이 몰릴 때 "앱이 검사한 시점"과 "DB에 쓰는 시점" 사이에 상태가 바뀔 수 있는데, 제약은 쓰는 시점에 원자적으로 적용됩니다. Pydantic 검증은 사용자에게 친절한 에러 메시지를 주기 위한 것이고, CHECK는 데이터가 절대 깨지지 않게 하기 위한 것입니다. 역할이 다르니 둘 다 둡니다.

Q native_enum=False로 저장하면 DB가 status='banana' 같은 값을 막지 못하는데, 괜찮은가요?

트레이드오프입니다. native ENUM은 DB가 값을 검사하지만 값을 추가할 때 ALTER TYPE이 필요하고 autogenerate가 그 변경을 못 잡아 운영 중 실수가 잦습니다. VARCHAR는 값 검증을 애플리케이션(Pydantic + StrEnum)이 하고, DB 변경 없이 값을 늘릴 수 있습니다. 정말 DB 수준 검증이 필요하면 CheckConstraint("status IN ('scheduled','active','ended','cancelled')")를 추가하는 절충도 있습니다 — 이건 autogenerate가 이름으로 추적할 수 있어서 native ENUM보다 다루기 쉽습니다. 중요한 건 "왜 이 선택을 했는지"를 설명할 수 있는 것입니다.

Q 개발 초기라 데이터도 없는데 그냥 create_all() 쓰다가 나중에 Alembic을 붙이면 안 되나요?

가능은 하지만 "나중에" 붙이는 순간 두 가지 문제를 만납니다. 첫째, 이미 테이블이 있는 DB에 첫 마이그레이션을 적용하려면 alembic stamp head로 "이미 적용된 셈 치자"고 속여야 하는데, 여러 환경(내 PC, 동료 PC, 스테이징)의 상태가 제각각이면 어느 것을 stamp해야 할지 꼬입니다. 둘째, 그동안 모델 변경 이력이 없어서 "언제 무엇이 바뀌었나"를 복원할 수 없습니다. 첫 마이그레이션이 빈 DB에서 시작하면 모든 환경이 같은 일지를 처음부터 재생할 수 있어서, 처음부터 Alembic을 쓰는 비용이 가장 쌉니다.
