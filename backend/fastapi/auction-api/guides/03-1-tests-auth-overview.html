3-1 개요와 설계

테스트마다 깨끗하게 롤백되는 테스트 전용 DB를 갖추고, 그 위에서 회원가입·로그인·refresh 회전·로그아웃·/users/me를 TDD로 만듭니다. 이 단계의 fixture는 4~10단계 모든 테스트가 그대로 씁니다.

3-1 개요와 설계 3-2 구현 3-3 실행·확인
한 줄 요약. 이 문서를 끝내면 uv run pytest -q가 13 passed를 찍고(경고 0), curl로 가입 → 로그인 → 토큰으로 /users/me → refresh → 로그아웃까지 한 바퀴 돌며, Redis에 살아 있는 refresh 토큰이 생겼다 사라지는 걸 눈으로 확인합니다.

학습 목표

  • 앱을 import하기 전에 환경변수를 바꿔 테스트 DB/Redis로 갈아 끼우는 원리를 이해한다
  • "테스트 하나 = 트랜잭션 하나, 끝나면 롤백"을 SAVEPOINT로 구현하고, 서비스가 commit()해도 왜 안전한지 설명할 수 있다
  • 비밀번호 해싱(bcrypt), JWT access/refresh 분리, refresh 회전을 코드로 옮긴다
  • NestJS Guard에 해당하는 get_current_user 의존성을 만들고 표준 에러 형태로 401·409를 돌려준다
  • pytest-asyncio의 이벤트 루프 범위(session)가 왜 필요한지 안다
🎯

이 단계의 목표

이 단계가 끝나면 두 가지가 생깁니다. 하나는 테스트 인프라입니다. tests/conftest.py 한 파일이 테스트 전용 DB(auction_test)를 만들고 마이그레이션하고, 테스트마다 트랜잭션을 열었다가 롤백해서 어떤 테스트도 다른 테스트에 흔적을 남기지 않게 합니다. 다른 하나는 인증입니다. 이메일·비밀번호로 가입하고, 로그인하면 access 토큰(15분)과 refresh 토큰(7일)을 받고, access 토큰으로 /users/me를 부르고, refresh 토큰으로 새 쌍을 받고, 로그아웃하면 그 refresh 토큰이 죽습니다.

전제. 2단계가 끝나 있어야 합니다. uv run pytest -q → 4 passed, uv run alembic check → No new upgrade operations detected., 컨테이너 두 개 (healthy). 이번 단계도 til/backend/fastapi/auction-api/에서 진행합니다.

이번 단계에서 만드는 것. 테스트 쪽 3개(conftest.py, factories.py, test_auth.py), 앱 쪽 9개(core/exceptions.py, core/security.py, core/deps.py, schemas/user.py, schemas/auth.py, repositories/user.py, services/auth.py, routers/auth.py, routers/users.py). 그리고 기존 파일 5개를 손봅니다(pyproject.toml, .env.example, config.py, main.py, 그리고 1·2단계 테스트 두 개를 새 fixture로 옮깁니다). 회원가입 이메일 OTP는 이 프로젝트에선 만들지 않고, 그 자리에 있던 BackgroundTasks는 9단계 모의 결제 서버에서 씁니다.
🏢

왜 필요한가 — 실무 맥락

왜 인증보다 테스트 인프라를 먼저 만들까요. 4단계부터 만드는 기능은 전부 "로그인한 사용자가 자기 경매를 다룬다"는 전제 위에 있습니다. 그 테스트를 쓰려면 매번 사용자를 만들고, 로그인하고, 토큰을 헤더에 넣어야 합니다. 이걸 테스트마다 손으로 하면 테스트가 길어지고 결국 안 쓰게 됩니다. 그래서 이번 단계에서 create_user()와 login_headers() 같은 공장 함수, 그리고 자동으로 롤백되는 db_session을 만들어 두면 이후 테스트는 본론만 적으면 됩니다.

인증 쪽에서 실무가 self-study와 다른 점은 refresh 토큰입니다. Week 8에서는 access 토큰 하나만 발급했습니다. 그런데 access 토큰을 길게 주면 유출됐을 때 오래 악용되고, 짧게 주면 사용자가 15분마다 다시 로그인해야 합니다. 그래서 실무는 둘을 나눕니다. access는 짧게(15분), refresh는 길게(7일) 주되 refresh는 서버가 기억해서 로그아웃이나 유출 시 즉시 죽일 수 있게 합니다. 그리고 refresh를 한 번 쓰면 새 것으로 바꿔 주고 옛 것은 폐기하는 회전(rotation)을 합니다 — 훔친 refresh 토큰을 나중에 쓰면 이미 폐기돼 있어 막힙니다.

테스트를 개발 DB에서 돌리면 안 되는 이유. 2단계 스모크 테스트는 커밋 없이 롤백만 해서 개발 DB를 더럽히지 않았습니다. 하지만 이제 서비스 코드가 commit()을 호출합니다. 테스트가 개발 DB에 커밋하면 다음 테스트가 "이미 가입된 이메일" 409를 받고 실패하고, 내가 Swagger로 만들어 둔 데이터도 섞입니다. 테스트 전용 DB + 롤백은 선택이 아니라 필수입니다.
🎟️

비유 — 연습장, 입장 팔찌, 재발급 창구

롤백 세션은 연습장에 쓰고 찢어 버리기입니다. 시험 공부할 때 연습장에 풀이를 잔뜩 써도 다음 문제는 새 페이지에서 시작하죠. 테스트가 시작될 때 DB 트랜잭션을 열고(새 페이지), 테스트 안에서 가입·로그인·입찰을 마음껏 하고(풀이), 테스트가 끝나면 롤백합니다(찢어 버림). 그런데 서비스 코드는 중간에 commit()을 부릅니다. 이걸 진짜 커밋으로 처리하면 페이지를 찢을 수 없으니, SQLAlchemy에게 "세션의 commit은 SAVEPOINT(책갈피)만 확정해라"고 시킵니다. 책갈피는 페이지 안의 표시일 뿐이라 페이지째 찢으면 같이 사라집니다. 그게 join_transaction_mode="create_savepoint"입니다.
access 토큰은 입장 팔찌, refresh 토큰은 재발급 창구 티켓입니다. 놀이공원 팔찌(access)는 보여주기만 하면 어디든 들어가지만 15분짜리라 금방 만료됩니다. 만료되면 재발급 창구에 티켓(refresh)을 내는데, 창구 직원은 장부(Redis)에서 그 티켓 번호(jti)를 찾아 지우고 새 팔찌와 새 티켓을 줍니다. 같은 티켓을 또 내면 장부에 없으니 거절됩니다(회전). 퇴장(로그아웃)할 때 티켓을 반납하면 장부에서 지워지고, 이미 차고 있는 팔찌는 15분 뒤 저절로 죽습니다.
🗺️

설계 그림

그림 두 장으로 정리합니다. 첫 장은 요청이 지나가는 길입니다. 1단계에서 잡아 둔 폴더가 처음으로 다 채워집니다 — 라우터는 요청을 Pydantic으로 검증해 서비스에 넘기고, 서비스는 규칙을 검사해 리포지토리(Postgres)와 Redis를 만지고, 결과를 라우터가 응답 모델로 돌려줍니다. 서비스는 HTTPException을 import하지 않습니다. 대신 UnauthorizedError 같은 도메인 예외를 던지고, main.py에 등록한 핸들러가 {"code", "message"} JSON과 상태 코드로 번역합니다.

로그인 한 번에 두 저장소를 만진다. 사용자는 Postgres에서 찾고, 발급한 refresh 토큰의 id(jti)는 Redis에 TTL과 함께 적어 둔다.

둘째 장은 테스트가 도는 동안의 시간표입니다. 핵심은 순서입니다. conftest.py의 맨 위에서 환경변수를 바꾼 다음에 앱 모듈을 import합니다. 1단계에서 확인했듯 환경변수는 .env보다 우선하므로, 이 순서만 지키면 app.core.db.engine도 redis_client도 처음부터 테스트 주소로 만들어집니다. 앱 코드는 테스트를 위해 한 줄도 바꾸지 않습니다.

환경변수 교체는 앱 모듈이 import되기 전에 한 번, DB 준비는 세션에 한 번, 트랜잭션은 테스트마다. 모든 테스트가 하나의 이벤트 루프(session scope) 위에서 돈다.
