3단계 — 테스트 인프라 + 인증

테스트마다 깨끗하게 롤백되는 테스트 전용 DB를 갖추고, 그 위에서 회원가입·로그인·refresh 회전·로그아웃·/users/me를 TDD로 만듭니다. 이 단계의 fixture는 4~10단계 모든 테스트가 그대로 씁니다.

한 줄 요약. 이 문서를 끝내면 uv run pytest -q가 13 passed를 찍고(경고 0), curl로 가입 → 로그인 → 토큰으로 /users/me → refresh → 로그아웃까지 한 바퀴 돌며, Redis에 살아 있는 refresh 토큰이 생겼다 사라지는 걸 눈으로 확인합니다.

학습 목표

  • 앱을 import하기 전에 환경변수를 바꿔 테스트 DB/Redis로 갈아 끼우는 원리를 이해한다
  • "테스트 하나 = 트랜잭션 하나, 끝나면 롤백"을 SAVEPOINT로 구현하고, 서비스가 commit()해도 왜 안전한지 설명할 수 있다
  • 비밀번호 해싱(bcrypt), JWT access/refresh 분리, refresh 회전을 코드로 옮긴다
  • NestJS Guard에 해당하는 get_current_user 의존성을 만들고 표준 에러 형태로 401·409를 돌려준다
  • pytest-asyncio의 이벤트 루프 범위(session)가 왜 필요한지 안다

이 단계의 목표

이 단계가 끝나면 두 가지가 생깁니다. 하나는 테스트 인프라입니다. tests/conftest.py 한 파일이 테스트 전용 DB(auction_test)를 만들고 마이그레이션하고, 테스트마다 트랜잭션을 열었다가 롤백해서 어떤 테스트도 다른 테스트에 흔적을 남기지 않게 합니다. 다른 하나는 인증입니다. 이메일·비밀번호로 가입하고, 로그인하면 access 토큰(15분)과 refresh 토큰(7일)을 받고, access 토큰으로 /users/me를 부르고, refresh 토큰으로 새 쌍을 받고, 로그아웃하면 그 refresh 토큰이 죽습니다.

전제. 2단계가 끝나 있어야 합니다. uv run pytest -q → 4 passed, uv run alembic check → No new upgrade operations detected., 컨테이너 두 개 (healthy). 이번 단계도 til/backend/fastapi/auction-api/에서 진행합니다.

이번 단계에서 만드는 것. 테스트 쪽 3개(conftest.py, factories.py, test_auth.py), 앱 쪽 9개(core/exceptions.py, core/security.py, core/deps.py, schemas/user.py, schemas/auth.py, repositories/user.py, services/auth.py, routers/auth.py, routers/users.py). 그리고 기존 파일 5개를 손봅니다(pyproject.toml, .env.example, config.py, main.py, 그리고 1·2단계 테스트 두 개를 새 fixture로 옮깁니다). 회원가입 이메일 OTP는 이 프로젝트에선 만들지 않고, 그 자리에 있던 BackgroundTasks는 9단계 모의 결제 서버에서 씁니다.

왜 필요한가 — 실무 맥락

왜 인증보다 테스트 인프라를 먼저 만들까요. 4단계부터 만드는 기능은 전부 "로그인한 사용자가 자기 경매를 다룬다"는 전제 위에 있습니다. 그 테스트를 쓰려면 매번 사용자를 만들고, 로그인하고, 토큰을 헤더에 넣어야 합니다. 이걸 테스트마다 손으로 하면 테스트가 길어지고 결국 안 쓰게 됩니다. 그래서 이번 단계에서 create_user()와 login_headers() 같은 공장 함수, 그리고 자동으로 롤백되는 db_session을 만들어 두면 이후 테스트는 본론만 적으면 됩니다.

인증 쪽에서 실무가 self-study와 다른 점은 refresh 토큰입니다. Week 8에서는 access 토큰 하나만 발급했습니다. 그런데 access 토큰을 길게 주면 유출됐을 때 오래 악용되고, 짧게 주면 사용자가 15분마다 다시 로그인해야 합니다. 그래서 실무는 둘을 나눕니다. access는 짧게(15분), refresh는 길게(7일) 주되 refresh는 서버가 기억해서 로그아웃이나 유출 시 즉시 죽일 수 있게 합니다. 그리고 refresh를 한 번 쓰면 새 것으로 바꿔 주고 옛 것은 폐기하는 회전(rotation)을 합니다 — 훔친 refresh 토큰을 나중에 쓰면 이미 폐기돼 있어 막힙니다.

테스트를 개발 DB에서 돌리면 안 되는 이유. 2단계 스모크 테스트는 커밋 없이 롤백만 해서 개발 DB를 더럽히지 않았습니다. 하지만 이제 서비스 코드가 commit()을 호출합니다. 테스트가 개발 DB에 커밋하면 다음 테스트가 "이미 가입된 이메일" 409를 받고 실패하고, 내가 Swagger로 만들어 둔 데이터도 섞입니다. 테스트 전용 DB + 롤백은 선택이 아니라 필수입니다.
🎟️

비유 — 연습장, 입장 팔찌, 재발급 창구

롤백 세션은 연습장에 쓰고 찢어 버리기입니다. 시험 공부할 때 연습장에 풀이를 잔뜩 써도 다음 문제는 새 페이지에서 시작하죠. 테스트가 시작될 때 DB 트랜잭션을 열고(새 페이지), 테스트 안에서 가입·로그인·입찰을 마음껏 하고(풀이), 테스트가 끝나면 롤백합니다(찢어 버림). 그런데 서비스 코드는 중간에 commit()을 부릅니다. 이걸 진짜 커밋으로 처리하면 페이지를 찢을 수 없으니, SQLAlchemy에게 "세션의 commit은 SAVEPOINT(책갈피)만 확정해라"고 시킵니다. 책갈피는 페이지 안의 표시일 뿐이라 페이지째 찢으면 같이 사라집니다. 그게 join_transaction_mode="create_savepoint"입니다.
access 토큰은 입장 팔찌, refresh 토큰은 재발급 창구 티켓입니다. 놀이공원 팔찌(access)는 보여주기만 하면 어디든 들어가지만 15분짜리라 금방 만료됩니다. 만료되면 재발급 창구에 티켓(refresh)을 내는데, 창구 직원은 장부(Redis)에서 그 티켓 번호(jti)를 찾아 지우고 새 팔찌와 새 티켓을 줍니다. 같은 티켓을 또 내면 장부에 없으니 거절됩니다(회전). 퇴장(로그아웃)할 때 티켓을 반납하면 장부에서 지워지고, 이미 차고 있는 팔찌는 15분 뒤 저절로 죽습니다.
🗺️

설계 그림

그림 두 장으로 정리합니다. 첫 장은 요청이 지나가는 길입니다. 1단계에서 잡아 둔 폴더가 처음으로 다 채워집니다 — 라우터는 요청을 Pydantic으로 검증해 서비스에 넘기고, 서비스는 규칙을 검사해 리포지토리(Postgres)와 Redis를 만지고, 결과를 라우터가 응답 모델로 돌려줍니다. 서비스는 HTTPException을 import하지 않습니다. 대신 UnauthorizedError 같은 도메인 예외를 던지고, main.py에 등록한 핸들러가 {"code", "message"} JSON과 상태 코드로 번역합니다.

로그인 한 번에 두 저장소를 만진다. 사용자는 Postgres에서 찾고, 발급한 refresh 토큰의 id(jti)는 Redis에 TTL과 함께 적어 둔다.

둘째 장은 테스트가 도는 동안의 시간표입니다. 핵심은 순서입니다. conftest.py의 맨 위에서 환경변수를 바꾼 다음에 앱 모듈을 import합니다. 1단계에서 확인했듯 환경변수는 .env보다 우선하므로, 이 순서만 지키면 app.core.db.engine도 redis_client도 처음부터 테스트 주소로 만들어집니다. 앱 코드는 테스트를 위해 한 줄도 바꾸지 않습니다.

환경변수 교체는 앱 모듈이 import되기 전에 한 번, DB 준비는 세션에 한 번, 트랜잭션은 테스트마다. 모든 테스트가 하나의 이벤트 루프(session scope) 위에서 돈다.

① 의존성 설치

JWT는 PyJWT, 비밀번호 해싱은 pwdlib의 bcrypt 백엔드, 이메일 형식 검증은 Pydantic의 EmailStr이 쓰는 email-validator입니다. 테스트 쪽은 async def 테스트를 돌려 주는 pytest-asyncio만 추가합니다. HTTP 클라이언트는 1단계에서 넣은 httpx2를 그대로 씁니다.

bash

# 검증 당시: pyjwt 2.13.0 · pwdlib 0.3.1 · bcrypt 5.0.0 · email-validator 2.3.0
uv add --dev pytest-asyncio
# 검증 당시: pytest-asyncio 1.4.0

② pyproject.toml — pytest-asyncio 설정

asyncio_mode = "auto"는 async def로 쓴 테스트와 fixture를 마커 없이 자동으로 인식하라는 뜻입니다. 나머지 두 줄이 중요합니다. 기본값은 테스트마다 새 이벤트 루프인데, asyncpg와 redis의 커넥션은 자기를 만든 루프에 묶여 있어서 다음 테스트의 새 루프에서 꺼내 쓰면 "attached to a different loop" 에러가 납니다. 세션 전체가 루프 하나를 쓰게 하면 커넥션 풀이 처음부터 끝까지 같은 루프 위에 있어 문제가 사라집니다.

toml(수정) pyproject.toml — [tool.pytest.ini_options] 섹션을 이렇게 바꾼다
[tool.pytest.ini_options]
testpaths = ["tests"]
asyncio_mode = "auto"                          # async def 테스트를 마커 없이 실행
asyncio_default_fixture_loop_scope = "session" # fixture 도 세션 전체에서 하나의 이벤트 루프
asyncio_default_test_loop_scope = "session"    # 테스트도 같은 루프 → DB/Redis 커넥션 풀이 루프를 넘나들지 않는다
무엇이 바뀌었나. testpaths는 그대로이고 asyncio_* 세 줄이 추가됐습니다. [tool.ruff] 쪽은 손대지 않습니다.

③ .env.example — JWT 비밀키

JWT 서명에 쓰는 비밀키입니다. HS256은 키가 32바이트 이상이어야 안전하다고 RFC 7518이 정해 두었고, PyJWT 2.10부터는 짧은 키를 쓰면 InsecureKeyLengthWarning을 냅니다. 개발용 기본값도 그 길이를 맞춰 둡니다. 운영에서는 python -c "import secrets; print(secrets.token_hex(32))"로 만든 값을 환경변수로 주입합니다.

④ app/core/config.py — 인증 설정 세 개

토큰 수명을 코드에 박지 않고 설정으로 뺍니다. 나중에 테스트에서 "access 1초짜리"로 줄이거나, 운영에서 정책이 바뀔 때 코드 수정 없이 환경변수로 바꿀 수 있습니다.

python(수정) app/core/config.py
from functools import lru_cache
from typing import Literal

from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", env_file_encoding="utf-8", extra="ignore")

    app_env: Literal["dev", "test", "prod"] = "dev"
    database_url: str = "postgresql+asyncpg://auction:auction_pw@localhost:5435/auction"
    redis_url: str = "redis://localhost:6380/0"
    debug: bool = False

    # 인증 — 프로덕션에서는 반드시 환경변수/시크릿 매니저로 주입한다
    jwt_secret: str = "dev-only-change-me-in-prod-please-use-32-bytes-or-more"
    access_token_minutes: int = 15
    refresh_token_days: int = 7


@lru_cache
def get_settings() -> Settings:
    return Settings()

⑤ tests/conftest.py — 테스트 인프라의 전부

이 파일이 이번 단계의 심장입니다. 위에서부터 읽어 보세요. 첫 블록은 환경변수 교체입니다. Settings 클래스만 가져와(get_settings()는 부르지 않습니다 — 부르는 순간 캐시됩니다) .env의 주소를 읽고, DB 이름을 auction_test로, Redis DB 번호를 15로 바꿔 환경변수에 넣습니다. 그 아래에서야 앱 모듈을 import합니다. ruff는 "import는 파일 맨 위에"라고 잔소리하니 noqa: E402로 "의도한 것"임을 표시합니다.

prepare_test_database는 세션에 한 번만 도는 동기 fixture입니다. CREATE DATABASE는 트랜잭션 안에서 실행할 수 없어서 AUTOCOMMIT으로 연결하고, 없을 때만 만듭니다. 그리고 alembic upgrade head를 파이썬 API로 실행합니다 — 환경변수가 바뀌어 있으니 env.py의 get_settings()가 자연스럽게 테스트 DB를 가리킵니다. 동기 fixture인 이유는 Alembic의 env.py가 안에서 asyncio.run()을 호출하기 때문에, 이미 도는 루프 안(async fixture)에서는 부를 수 없어서입니다.

db_session이 롤백의 핵심입니다. 커넥션을 하나 빌려 begin()으로 트랜잭션을 열고, 그 커넥션에 묶인 세션을 만듭니다. join_transaction_mode="create_savepoint" 덕에 서비스의 commit()은 SAVEPOINT만 확정하고, 테스트가 끝나면 conn.rollback()이 전부 지웁니다. client는 앱의 get_db를 이 세션으로 바꿔치기한 뒤 ASGITransport로 앱을 직접 호출합니다 — 포트를 열지 않으니 빠르고, 테스트와 앱이 같은 세션·같은 트랜잭션을 공유해서 테스트에서 flush()만 한 사용자를 앱이 볼 수 있습니다.

pythontests/conftest.py
"""테스트 공통 fixture.

핵심 아이디어 세 가지
1) 앱을 import 하기 *전에* 환경변수를 바꿔치기해서 앱 전체가 테스트 DB/Redis 를 보게 한다.
   (환경변수는 .env 보다 우선한다 — 1단계에서 확인한 규칙)
2) 테스트 DB 는 세션 시작 때 한 번만 만들고 마이그레이션한다.
3) 테스트마다 트랜잭션을 열고, 끝나면 롤백한다 → 연습장에 쓰고 찢어 버리기.
"""

import asyncio
import os
from collections.abc import AsyncIterator

from app.core.config import Settings  # 클래스만 가져온다 (get_settings() 는 아직 호출하지 않는다)

_dev = Settings()  # .env 의 값을 읽어 테스트용 주소를 파생한다
os.environ["APP_ENV"] = "test"
os.environ["DATABASE_URL"] = _dev.database_url.rsplit("/", 1)[0] + "/auction_test"
os.environ["REDIS_URL"] = _dev.redis_url.rsplit("/", 1)[0] + "/15"

# ── 여기부터는 환경변수가 바뀐 뒤라, 앱 모듈이 테스트 DB/Redis 주소로 초기화된다 ──
import pytest  # noqa: E402
from alembic import command  # noqa: E402
from alembic.config import Config  # noqa: E402

"""도메인 예외와 표준 에러 응답.

서비스 계층은 HTTP 를 모른다 — HTTPException 대신 여기 있는 AppError 계열만 던진다.
라우터 바깥의 핸들러가 AppError 를 {"code", "message"} 형태의 JSON 으로 번역한다.
4단계에서 NotFound / Forbidden / InvalidState 가 이 위에 추가된다.

from fastapi import FastAPI, Request, status
from fastapi.responses import JSONResponse


class AppError(Exception):
    code = "APP_ERROR"
    status_code = status.HTTP_400_BAD_REQUEST
    message = "요청을 처리할 수 없습니다"

    def __init__(self, message: str | None = None) -> None:
        if message is not None:
            self.message = message
        super().__init__(self.message)


class UnauthorizedError(AppError):
    code = "UNAUTHORIZED"
    status_code = status.HTTP_401_UNAUTHORIZED
    message = "인증이 필요합니다"


class EmailAlreadyExistsError(AppError):
    code = "EMAIL_ALREADY_EXISTS"
    status_code = status.HTTP_409_CONFLICT
    message = "이미 가입된 이메일입니다"


async def app_error_handler(request: Request, exc: AppError) -> JSONResponse:
    headers = {"WWW-Authenticate": "Bearer"} if exc.status_code == 401 else None
    return JSONResponse(
        status_code=exc.status_code,
        content={"code": exc.code, "message": exc.message},
        headers=headers,
    )


def register_exception_handlers(app: FastAPI) -> None:
    app.add_exception_handler(AppError, app_error_handler)  # type: ignore[arg-type]

⑩ app/core/security.py — 해싱과 JWT (순수 계산)

이 파일에는 DB도 Redis도 없습니다. 문자열을 받아 문자열을 돌려주는 함수뿐이라 테스트하기 쉽고 어디서든 재사용됩니다. create_token이 토큰마다 고유한 jti를 넣는 게 포인트입니다 — refresh 토큰을 Redis에서 찾고 지우는 열쇠가 됩니다. type 클레임은 access 토큰을 refresh 자리에 끼워 넣는 장난을 막습니다. decode_token은 만료·서명 불일치·타입 불일치를 전부 TokenError 하나로 모아 호출자가 401로 바꾸기 쉽게 합니다.

pythonapp/core/security.py
"""비밀번호 해싱과 JWT 발급/검증. 여기엔 DB 도 Redis 도 없다 — 순수 계산만."""

import uuid
from datetime import UTC, datetime, timedelta
from typing import Any, Literal

import jwt
from pwdlib import PasswordHash
from pwdlib.hashers.bcrypt import BcryptHasher

from app.core.config import get_settings

ALGORITHM = "HS256"
TokenType = Literal["access", "refresh"]

_password_hash = PasswordHash((BcryptHasher(),))


def hash_password(raw: str) -> str:
    return _password_hash.hash(raw)


def verify_password(raw: str, hashed: str) -> bool:
    return _password_hash.verify(raw, hashed)


class TokenError(Exception):
    """서명 불일치, 만료, 타입 불일치 등 — 호출자가 401 로 바꾼다."""


def create_token(subject: str, token_type: TokenType, expires_delta: timedelta) -> tuple[str, str]:
    """(토큰 문자열, jti) 를 돌려준다. jti 는 토큰마다 다른 고유 id — refresh 폐기에 쓴다."""
    now = datetime.now(UTC)
    jti = uuid.uuid4().hex
    payload = {
        "sub": subject,
        "type": token_type,
        "jti": jti,
        "iat": now,
        "exp": now + expires_delta,
    }
    token = jwt.encode(payload, get_settings().jwt_secret, algorithm=ALGORITHM)
    return token, jti


def create_access_token(user_id: uuid.UUID) -> str:
    minutes = get_settings().access_token_minutes
    token, _ = create_token(str(user_id), "access", timedelta(minutes=minutes))
    return token


def create_refresh_token(user_id: uuid.UUID) -> tuple[str, str, int]:
    """(토큰, jti, 만료까지 남은 초). 마지막 값은 Redis TTL 로 그대로 쓴다."""
    ttl = timedelta(days=get_settings().refresh_token_days)
    token, jti = create_token(str(user_id), "refresh", ttl)
    return token, jti, int(ttl.total_seconds())


def decode_token(token: str, expected_type: TokenType) -> dict[str, Any]:
    try:
        payload = jwt.decode(token, get_settings().jwt_secret, algorithms=[ALGORITHM])
    except jwt.PyJWTError as exc:  # 만료(ExpiredSignatureError) 도 여기에 포함된다
        raise TokenError(str(exc)) from exc
    if payload.get("type") != expected_type:
        raise TokenError(f"{expected_type} 토큰이 아닙니다")
    return payload

⑬ app/services/auth.py — 규칙

네 함수가 각각 한 가지 규칙을 맡습니다. login은 이메일이 없어도, 비밀번호가 틀려도 같은 메시지를 냅니다 — 다르게 알려주면 공격자가 "이 이메일은 가입돼 있구나"를 알아냅니다. refresh의 redis.delete()가 회전의 핵심입니다. Redis의 DEL은 원자적이라 같은 토큰으로 동시에 두 요청이 와도 하나만 1을 받고, 나머지는 0을 받아 401이 됩니다. logout은 이미 죽은 토큰이 와도 조용히 성공합니다(멱등) — 사용자가 로그아웃 버튼을 두 번 눌러도 에러를 보면 안 되니까요.

pythonapp/services/auth.py
"""인증 규칙. HTTP 를 모른다 — 도메인 예외(AppError) 만 던진다."""

import uuid

from redis.asyncio import Redis
from sqlalchemy.ext.asyncio import AsyncSession

from app.core.exceptions import EmailAlreadyExistsError, UnauthorizedError
from app.core.security import (
    TokenError,
    create_access_token,
    create_refresh_token,
    decode_token,
    hash_password,
    verify_password,
)
from app.models import User
from app.repositories import user as user_repo
from app.schemas.auth import LoginRequest, SignupRequest, TokenPair


def _refresh_key(jti: str) -> str:
    return f"refresh:{jti}"


async def signup(db: AsyncSession, data: SignupRequest) -> User:
    if await user_repo.get_by_email(db, data.email) is not None:
        raise EmailAlreadyExistsError()
    user = await user_repo.create(
        db, email=data.email, password_hash=hash_password(data.password), nickname=data.nickname
    )
    await db.commit()
    await db.refresh(user)  # DB 가 채운 created_at 을 읽어 온다
    return user


async def _issue_token_pair(redis: Redis, user_id: uuid.UUID) -> TokenPair:
    access = create_access_token(user_id)
    refresh, jti, ttl = create_refresh_token(user_id)
    await redis.set(_refresh_key(jti), str(user_id), ex=ttl)  # 살아 있는 refresh 토큰 목록
    return TokenPair(access_token=access, refresh_token=refresh)


async def login(db: AsyncSession, redis: Redis, data: LoginRequest) -> TokenPair:
    user = await user_repo.get_by_email(db, data.email)
    # 이메일이 없는 경우와 비밀번호가 틀린 경우를 구분해 알려주지 않는다 (계정 존재 여부 노출 방지)
    if user is None or not verify_password(data.password, user.password_hash):
        raise UnauthorizedError("이메일 또는 비밀번호가 올바르지 않습니다")
    return await _issue_token_pair(redis, user.id)


async def refresh(redis: Redis, refresh_token: str) -> TokenPair:
    try:
        payload = decode_token(refresh_token, expected_type="refresh")
    except TokenError as exc:
        raise UnauthorizedError("refresh 토큰이 유효하지 않습니다") from exc
    # DEL 은 원자적이다: 같은 토큰으로 동시에 두 번 와도 한 쪽만 1 을 받는다 → 회전(rotation)
    deleted = await redis.delete(_refresh_key(payload["jti"]))
    if not deleted:
        raise UnauthorizedError("이미 사용됐거나 폐기된 refresh 토큰입니다")
    return await _issue_token_pair(redis, uuid.UUID(payload["sub"]))


async def logout(redis: Redis, refresh_token: str) -> None:
    try:
        payload = decode_token(refresh_token, expected_type="refresh")
    except TokenError:
        return  # 이미 못 쓰는 토큰이면 할 일이 없다 — 로그아웃은 멱등
    await redis.delete(_refresh_key(payload["jti"]))

get_current_user가 Week 8·02의 것과 다른 점은 둘입니다. 첫째, OAuth2PasswordBearer 대신 HTTPBearer를 씁니다. 전자는 Swagger에서 "아이디/비밀번호 폼으로 로그인"을 흉내내는데 우리 로그인은 JSON 바디라 맞지 않습니다. HTTPBearer는 Swagger의 Authorize 버튼에 토큰을 붙여 넣는 칸만 띄웁니다. 둘째, auto_error=False로 두어 헤더가 없을 때 FastAPI가 알아서 403을 내지 않고 None을 주게 하고, 우리가 표준 에러 형태의 401로 통일합니다. CurrentUser·DbSession·RedisClient는 Week 6·02에서 본 Annotated 별칭입니다.

"""라우터에서 쓰는 공용 의존성. NestJS 의 Guard 역할을 get_current_user 가 한다."""

import uuid
from typing import Annotated

from fastapi import Depends
from fastapi.security import HTTPAuthorizationCredentials, HTTPBearer
from redis.asyncio import Redis
from sqlalchemy.ext.asyncio import AsyncSession

from app.core.db import get_db
from app.core.exceptions import UnauthorizedError
from app.core.redis import get_redis
from app.core.security import TokenError, decode_token
from app.models import User
from app.repositories import user as user_repo

DbSession = Annotated[AsyncSession, Depends(get_db)]
RedisClient = Annotated[Redis, Depends(get_redis)]

# auto_error=False: 헤더가 없어도 FastAPI 가 403 을 내지 않고 None 을 준다 → 우리가 401 로 통일
_bearer = HTTPBearer(auto_error=False)


async def get_current_user(
    credentials: Annotated[HTTPAuthorizationCredentials | None, Depends(_bearer)],
    db: DbSession,
) -> User:
    if credentials is None:
        raise UnauthorizedError("인증 토큰이 필요합니다")
    try:
        payload = decode_token(credentials.credentials, expected_type="access")
    except TokenError as exc:
        raise UnauthorizedError("토큰이 유효하지 않거나 만료됐습니다") from exc
    user = await user_repo.get_by_id(db, uuid.UUID(payload["sub"]))
    if user is None:
        raise UnauthorizedError("존재하지 않는 사용자입니다")
    return user


CurrentUser = Annotated[User, Depends(get_current_user)]

함정 & 실무 팁

환경변수 교체는 반드시 앱 import보다 먼저. conftest.py에서 from app.main import app을 맨 위로 올리는 순간(ruff의 자동 정렬이 그렇게 하고 싶어 합니다) 앱은 개발 DB로 초기화되고, 그 뒤에 환경변수를 바꿔도 이미 늦습니다. 그래서 noqa: E402가 붙어 있고, 그 줄들을 위로 옮기면 안 됩니다. 증상은 "테스트가 개발 DB에 데이터를 남긴다"입니다.
"attached to a different loop" / "Event loop is closed". pytest-asyncio 기본값(테스트마다 새 루프)에서 나는 에러입니다. asyncpg·redis 커넥션은 자기를 만든 루프에 묶입니다. 해결은 ②의 asyncio_default_*_loop_scope = "session". 같은 이유로 스레드에서 별도 루프를 돌리는 TestClient를 섞어 쓰지 않고 AsyncClient로 통일했습니다.
HS256 키는 32바이트 이상. PyJWT가 InsecureKeyLengthWarning을 내면 JWT_SECRET이 짧은 것입니다. 개발용 기본값도 길게 잡아 두었고, 운영 키는 secrets.token_hex(32)(64자)로 만드세요. 키가 바뀌면 기존 토큰은 전부 무효가 됩니다 — 배포 시 키 교체는 "전원 로그아웃"과 같습니다.
bcrypt는 72바이트까지만 봅니다. 그 이상은 조용히 잘려서 "비밀번호 뒤쪽을 틀려도 로그인되는" 황당한 일이 생깁니다. 그래서 SignupRequest.password에 max_length=72를 걸어 422로 막습니다. 한글은 한 글자가 3바이트라는 것도 기억하세요(max_length는 글자 수 기준이라 완벽한 방어는 아니지만 실용적입니다).
로그아웃해도 access 토큰은 15분간 살아 있습니다. JWT는 서버가 기억하지 않으니 refresh 토큰만 죽인 것입니다. "로그아웃 즉시 모든 요청 차단"이 꼭 필요하면 access 토큰의 jti를 Redis 블랙리스트에 남은 수명만큼 넣고 get_current_user에서 확인하는 방법이 있습니다. 대신 요청마다 Redis를 한 번 더 치는 비용이 듭니다 — 수명이 15분이면 대개 감수합니다.
HTTPBearer(auto_error=False)인 이유. 기본값 True면 헤더가 없을 때 FastAPI가 403 {"detail": "Not authenticated"}를 냅니다. 상태 코드도 형태도 우리 표준과 다릅니다. False로 두고 우리가 UnauthorizedError를 던지면 401 + 표준 JSON + WWW-Authenticate로 통일됩니다.
테스트 DB는 지우지 않습니다. 매번 만들고 지우면 느려서, 한 번 만들고 마이그레이션만 올립니다. 마이그레이션을 손으로 꼬아서 테스트 DB가 이상해졌다면 docker compose exec db psql -U auction -c 'DROP DATABASE auction_test;' 후 다시 pytest를 돌리면 새로 만듭니다.
Redis는 트랜잭션 롤백이 없습니다. 그래서 테스트마다 15번 DB를 FLUSHDB합니다. 반드시 번호가 다른 DB여야 합니다 — REDIS_URL이 /0인 채로 flushdb를 부르면 개발 중 로그인한 세션이 전부 날아갑니다. 운영 Redis 주소로 테스트를 돌리면… 상상하고 싶지 않습니다.

Q JWT는 서버가 상태를 안 가져도 되는 게 장점인데, 왜 refresh 토큰은 Redis에 저장하나요? 그럼 세션 방식과 뭐가 다른가요?

둘을 섞은 것입니다. 요청마다 검사하는 access 토큰은 stateless라 Redis를 치지 않습니다 — 초당 수천 번 오는 일반 요청에는 이게 중요합니다. 반면 refresh는 15분에 한 번 정도만 쓰이니 서버가 기억해도 부담이 없고, 대신 "즉시 폐기"라는 세션의 장점을 얻습니다. 로그아웃, 비밀번호 변경, 기기 분실 시 refresh만 지우면 최대 15분 안에 모든 접근이 끊깁니다. 순수 JWT만 쓰면 7일짜리 토큰을 유출당했을 때 7일 동안 막을 방법이 없습니다. 자주 쓰는 건 stateless로 빠르게, 드물고 위험한 건 stateful로 통제 가능하게 — 이 조합이 실무 표준입니다.

Q 서비스가 db.commit()을 호출하는데 테스트가 끝나면 어떻게 데이터가 사라지나요?

db_session fixture가 커넥션 수준에서 BEGIN을 먼저 열고, 세션을 그 커넥션에 join_transaction_mode="create_savepoint"로 묶기 때문입니다. 이 모드에서 세션의 commit()은 진짜 COMMIT이 아니라 RELEASE SAVEPOINT가 되고, 바깥 트랜잭션은 열린 채 남습니다. 테스트가 끝나면 fixture가 conn.rollback()으로 바깥 트랜잭션을 통째로 되돌리니 SAVEPOINT 안에서 확정했던 것까지 전부 사라집니다. 서비스 코드는 자기가 테스트 안에 있는지 모르고, 운영과 똑같이 commit()을 부릅니다 — 테스트 때문에 앱 코드를 바꾸지 않는 게 핵심입니다.

Q 로그인 실패 시 "이메일이 없습니다"와 "비밀번호가 틀렸습니다"를 구분해 주면 사용자에게 친절하지 않나요?

친절하지만 위험합니다. 구분해 주는 순간 로그인 API가 "이 이메일이 가입돼 있는지"를 누구에게나 알려 주는 조회 API가 됩니다. 공격자는 이메일 목록을 넣어 가입 여부를 긁어 가고(계정 열거, user enumeration), 그 목록으로 피싱이나 비밀번호 대입을 합니다. 그래서 두 경우 모두 같은 401과 같은 메시지를 냅니다. 같은 이유로 회원가입의 409 "이미 가입된 이메일"도 엄밀히는 정보를 노출하는데, 가입 화면에서는 UX상 대개 허용하고, 대신 rate limit(6단계에서 배우는 Redis INCR)으로 대량 조회를 막습니다.
