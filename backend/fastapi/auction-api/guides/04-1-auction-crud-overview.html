4-1 개요와 설계

로그인한 판매자가 경매를 등록·수정·취소하고 누구나 조회합니다. "누가, 어떤 상태에서 할 수 있나"라는 규칙을 도메인 예외로 표현하고, 그 예외와 FastAPI가 내는 422·404까지 전부 {"code","message"} 한 가지 껍데기로 나가게 만듭니다. 이 단계부터는 테스트를 먼저 쓰고(TDD) 구현합니다.

4-1 개요와 설계 4-2 구현 4-3 실행·확인
한 줄 요약. 이 문서를 끝내면 uv run pytest -q가 28 passed를 찍고, curl로 경매를 등록 → 조회 → 수정 → 남이 수정하면 403 → 취소 → 다시 취소하면 409 → 없는 경매 404까지 한 바퀴 돌며, 모든 에러 응답이 같은 모양임을 확인합니다.

학습 목표

  • "형식" 검증(Pydantic, 422)과 "규칙" 검증(서비스, 403/404/409)을 다른 층에 두는 이유를 안다
  • 상태 머신(scheduled → active → ended | cancelled)을 코드 한 곳에서만 바꾸도록 설계한다
  • 소유권 검사(판매자만)와 입찰 유무 검사를 도메인 예외로 표현한다
  • FastAPI 기본 422·404를 우리 표준 에러 껍데기로 감싼다
  • PATCH 부분 수정에서 "안 보낸 필드"와 "null로 보낸 필드"를 구분한다(exclude_unset)
  • 타임존이 없는 시각을 왜 거부해야 하는지 설명할 수 있다
🎯

이 단계의 목표

이 단계가 끝나면 경매의 생애 첫 절반이 API로 열립니다. 판매자가 POST /auctions로 경매를 올리면 시작 시각에 따라 active(바로 시작) 또는 scheduled(예약)가 되고, 누구나 GET /auctions/{id}로 봅니다. 판매자는 입찰이 붙기 전까지만 PATCH로 제목·설명·마감을 고치거나 POST …/cancel로 취소할 수 있습니다. 나머지 절반 — 입찰이 붙고, 마감되고, 낙찰되는 흐름 — 은 6·8단계입니다.

전제. 3단계가 끝나 있어야 합니다. uv run pytest -q → 13 passed, 컨테이너 두 개 (healthy). 이번 단계도 til/backend/fastapi/auction-api/에서 진행하고, 새로 설치하는 패키지는 없습니다.

이번 단계에서 만드는 것. 새 파일 5개(schemas/auction.py, repositories/auction.py, services/auction.py, routers/auctions.py, tests/test_auctions.py), 손보는 파일 3개(core/exceptions.py는 예외 계층으로 확장, main.py는 라우터 한 줄, tests/factories.py는 create_auction 추가). 목록 조회 GET /auctions는 페이지네이션·필터가 붙는 5단계 몫이라 여기서는 만들지 않습니다.
🏢

왜 필요한가 — 실무 맥락

CRUD는 self-study Week 6에서 이미 했습니다. 그때 ToDo는 "있으면 고치고 없으면 404"가 전부였죠. 실무의 CRUD가 어려운 이유는 동사가 아니라 조건입니다. 누가(판매자만), 어떤 상태에서(끝난 경매는 안 됨), 무엇이 없을 때(입찰이 하나라도 있으면 안 됨) 할 수 있는가. 이 조건들을 라우터 안에 if로 쌓기 시작하면 6단계에서 입찰 규칙이, 8단계에서 마감 규칙이 더해질 때 아무도 못 읽는 코드가 됩니다. 그래서 조건을 서비스의 도메인 예외로 뽑아내고, 라우터는 그 예외를 모르게 둡니다.

두 번째 실무 요소는 표준 에러 껍데기입니다. 3단계에서 우리 예외는 {"code","message"}로 나갔지만, Pydantic 검증 실패는 FastAPI 기본인 {"detail": [...]}로, 없는 라우트는 {"detail": "Not Found"}로 나갔습니다. 프론트 입장에서는 에러를 세 가지 모양으로 처리해야 하는 셈입니다. 이번 단계에서 셋을 하나로 합칩니다. 프론트는 code 하나로 분기하고(AUCTION_HAS_BIDS면 "입찰이 있어 수정할 수 없어요" 토스트), message는 그대로 보여주거나 다국어 사전의 키로 씁니다.

이 단계부터 TDD입니다. 3단계까지는 "테스트 인프라를 만드는" 단계라 구현 후 테스트를 붙이기도 했지만, 규칙이 많아지는 지금부터는 테스트가 곧 명세입니다. "남이 수정하면 403", "입찰 있으면 409"를 먼저 테스트로 적어 두면, 구현하다가 규칙 하나를 빠뜨려도 빨간불이 알려 줍니다. 순서는 실패하는 테스트 → 구현 → 통과. 익숙해지면 규칙을 코드로 옮기는 속도가 오히려 빨라집니다.
📦

비유 — 택배 상태와 주방·홀

상태 머신은 택배 상태입니다. 택배는 접수 → 배송 중 → 배송 완료로만 흐르고, 완료된 택배를 다시 접수 상태로 돌릴 수는 없습니다. 접수 단계에서만 주소를 바꿀 수 있고, 기사님이 집어 들면(입찰이 붙으면) 더는 못 바꿉니다. 경매도 같습니다. scheduled → active → ended가 정방향이고, cancelled는 입찰이 없을 때만 옆으로 빠지는 길입니다. 이 화살표를 누가 그을 수 있는지(판매자만, 워커만)를 코드 한 곳 — services/auction.py — 에서만 정하면, 나중에 규칙이 바뀌어도 그 파일만 보면 됩니다.
도메인 예외는 주방이 외치는 말, 핸들러는 홀 직원의 번역입니다. 주방(서비스)은 "재료 없음!", "주문 취소됨!"처럼 사실만 외칩니다. 손님에게 어떤 표정으로 뭐라고 말할지는 홀 직원(예외 핸들러)이 정합니다. 주방이 손님 응대까지 하면(서비스가 HTTPException을 던지면) 주방을 다른 가게(CLI, 배치 워커, 8단계의 마감 워커)로 옮길 때 응대 매뉴얼까지 딸려 갑니다. 주방은 요리만, 홀은 응대만 — 그래서 서비스 파일에는 fastapi를 import하는 줄이 한 줄도 없습니다.
🗺️

설계 그림

그림 두 장입니다. 첫 장은 상태 머신입니다. 네모가 네 개뿐이라 단순해 보이지만, 이 그림이 곧 services/auction.py의 규칙 전부입니다. 등록 시점에 starts_at이 지금 이하면 active, 미래면 scheduled. 수정과 취소는 파란 상자 안(열려 있고 입찰이 없을 때)에서만 됩니다. 정방향 화살표 두 개는 8단계 워커가 긋습니다 — 이번 단계에는 그 코드가 없지만, 상태 이름과 전이 규칙을 지금 정해 두기 때문에 8단계는 이 파일에 함수 두 개를 더하는 일이 됩니다.

화살표를 긋는 주체가 둘뿐이다. 판매자(4단계: 등록·취소)와 마감 워커(8단계: 활성화·종료). 입찰자는 상태를 바꾸지 못하고 current_price·bid_count만 올린다(6단계).

둘째 장은 에러가 나가는 길입니다. 3단계에서는 우리 AppError만 핸들러를 거쳤습니다. 이번에 Pydantic의 RequestValidationError와 Starlette의 HTTPException(없는 라우트 404, 잘못된 메서드 405)까지 같은 파일의 핸들러로 보냅니다. 예외 클래스는 계층으로 둡니다 — NotFoundError(404) 아래 AuctionNotFoundError, ConflictError(409) 아래 AuctionHasBidsError — 그래서 새 도메인 예외를 만들 때 상태 코드를 다시 고민하지 않고 부모만 고르면 됩니다.

에러의 출처는 셋이지만 출구는 하나. 상태 코드와 code는 출처가 정하고, 모양은 핸들러가 통일한다.
