3. 경매 등록 → 조회

마감 시각은 "지금부터 3일 뒤"를 파이썬으로 만들어 넣습니다(타임존 +00:00이 붙어 나옵니다). 응답에서 status가 active, current_price가 시작가와 같고 version이 0인 것을 보세요.

echo $CREATED | python3 -m json.tool --no-ensure-ascii

함정 & 실무 팁

서비스에서 HTTPException을 던지고 싶어질 때. 당장은 그게 빠릅니다. 하지만 8단계 워커는 HTTP 없이 services/auction.py를 호출하고, 그때 서비스가 HTTPException을 던지면 워커는 "403이 뭔데?"가 됩니다. 규칙 위반은 도메인 예외로, HTTP 번역은 핸들러로. 이 경계를 지키면 서비스 테스트도 HTTP 없이 함수 호출만으로 쓸 수 있습니다.
400 · 409 · 422 고르기. 형식이 틀리면 422(Pydantic이 알아서), 의미가 틀리면 우리도 422(InvalidPeriodError — 마감이 시작보다 빠름은 DB를 봐야 아는 의미 오류), 현재 상태와 충돌하면 409(입찰이 있어서, 이미 끝나서). 400은 "뭐가 틀렸는지 더 구체적으로 말할 수 없을 때"만 남겨 두세요. 코드를 잘 고르면 프론트가 재시도할지(409는 새로고침 후 재시도 여지), 입력을 고칠지(422) 판단할 수 있습니다.
exclude_unset과 exclude_none은 다릅니다. PATCH에 {"description": null}을 보내는 것과 description을 아예 안 보내는 것은 의도가 다릅니다(비우기 vs 건드리지 않기). model_dump(exclude_unset=True)는 "요청에 있었나"를 기준으로 하므로 이 둘을 구분합니다. exclude_none=True로 바꾸면 "null로 비우기"가 영영 불가능해집니다. 지금 AuctionUpdate는 description에 None이 오면 setattr로 None을 넣으려다 DB의 NOT NULL에 걸립니다 — 비우고 싶으면 ""을 보내는 것으로 약속하거나, 스키마에서 None을 ""로 바꾸는 validator를 두세요.
타임존 없는 시각은 버그의 온상입니다. DB 컬럼은 timestamptz라 저장은 항상 UTC이고, 응답의 Z가 그 표시입니다. 클라이언트가 +09:00로 보내도 같은 순간으로 저장되니 프론트는 자기 타임존으로 보여주기만 하면 됩니다. 문제는 타임존 없는 값입니다 — Pydantic은 naive datetime을 그대로 받아 주고, asyncpg는 그걸 UTC로 간주합니다. 서울 사용자가 "오후 6시 마감"이라고 보냈는데 UTC 18시(서울 새벽 3시)로 저장되는 식입니다. 그래서 스키마 입구에서 막습니다.
commit() 뒤에 refresh()를 부르는 이유. created_at·updated_at은 DB가 채웁니다(server_default·onupdate). 세션이 expire_on_commit=False라 커밋 후에도 객체는 살아 있지만, DB가 바꾼 값은 다시 읽어야 응답에 실립니다. 안 읽으면 updated_at이 수정 전 값으로 나갑니다. SQLAlchemy 2.0은 PostgreSQL에서 RETURNING으로 INSERT 직후 값을 가져오기도 하지만, "커밋 후 응답할 객체는 refresh"를 습관으로 두면 안전합니다.
상태 전이는 한 파일에서만. auction.status = ...라고 쓰는 줄이 services/auction.py 밖에 생기면 안 됩니다. 8단계 워커가 활성화·마감을 맡을 때도 이 파일에 activate()·close()를 더해서 부릅니다. 상태를 바꾸는 코드가 한 곳이면 "어떤 상태에서 어떤 상태로 갈 수 있나"를 그 파일의 docstring 하나로 설명할 수 있습니다.
Starlette의 HTTPException을 등록해야 404가 잡힙니다. fastapi.HTTPException은 starlette.exceptions.HTTPException의 자식입니다. 라우트가 없을 때 던지는 쪽은 Starlette 라우터라 부모를 던집니다. FastAPI 쪽 클래스로 핸들러를 등록하면 자식만 잡혀서 /nope는 여전히 {"detail":"Not Found"}로 나갑니다. 테스트 test_unknown_route_uses_standard_envelope가 이걸 지킵니다.
@router.post("")와 trailing slash. prefix가 /auctions일 때 경로를 "/"로 쓰면 최종 경로는 /auctions/가 되고, 슬래시 없는 POST /auctions는 307 리다이렉트를 받습니다. 리다이렉트를 따라가지 않는 클라이언트(일부 fetch 설정, 로드밸런서)에서는 그냥 실패로 보입니다. 빈 문자열로 쓰면 /auctions 정확히 하나만 생깁니다.

셀프 체크

Q 서비스에서 바로 raise HTTPException(status_code=403) 하면 코드가 더 짧은데, 왜 도메인 예외를 따로 만드나요?

서비스를 HTTP 바깥에서도 쓰기 위해서입니다. 8단계의 마감 워커는 웹 요청 없이 services/auction.py를 직접 호출하고, 9단계의 웹훅 처리도 결제 서비스를 호출합니다. 서비스가 HTTPException을 던지면 그 호출자들은 HTTP 개념을 억지로 알아야 합니다. 도메인 예외(AuctionHasBidsError)는 "입찰이 있다"는 사실만 말하고, 그걸 403으로 할지 409로 할지는 HTTP 층(핸들러)이 정합니다. 덤으로 예외 클래스가 계층이라 새 규칙을 추가할 때 부모(ConflictError)만 고르면 상태 코드와 껍데기가 자동으로 따라옵니다. 그리고 서비스 단위 테스트를 HTTP 없이 pytest.raises(AuctionHasBidsError)로 쓸 수 있습니다.

Q "입찰이 있어서 수정 불가"는 409, "마감이 시작보다 빠름"은 422로 했습니다. 둘 다 400으로 하면 안 되나요?

되긴 하지만 정보를 버리는 것입니다. 422는 "요청 자체가 의미상 틀렸다 — 입력을 고쳐서 다시 보내라"는 뜻이고, 409는 "요청은 멀쩡한데 서버의 현재 상태와 충돌한다 — 상태가 바뀌면 같은 요청이 성공할 수도 있다"는 뜻입니다. 마감 시각을 고치면 422는 해결되지만, 409는 입찰이 취소되지 않는 한 같은 요청을 아무리 보내도 실패합니다. 프론트는 이 차이로 "입력칸을 빨갛게" 할지 "새로고침해서 최신 상태를 보라"고 할지 정합니다. 400은 이 둘을 구분할 수 없을 때의 마지막 선택지입니다.

Q PATCH로 {"description": null}을 보내면 어떻게 되나요? 안 보내는 것과 무엇이 다른가요?

안 보내면 model_dump(exclude_unset=True)에 description이 아예 없어서 건드리지 않습니다. null을 보내면 "설정됐다(set)"로 기록되어 {"description": None}이 나오고, 서비스가 setattr(auction, "description", None)을 하다가 DB의 NOT NULL 제약에 걸려 500이 납니다 — 지금 구현의 빈틈입니다. 실무에서는 셋 중 하나를 약속합니다: (1) 비우기는 ""으로만 허용하고 null은 422, (2) validator가 None을 ""으로 바꾼다, (3) 컬럼을 nullable로 만든다. 어느 쪽이든 "null = 비우기, 생략 = 유지"라는 구분이 가능해야 하고, 그걸 가능하게 하는 게 exclude_unset입니다(exclude_none이면 구분이 사라집니다).
