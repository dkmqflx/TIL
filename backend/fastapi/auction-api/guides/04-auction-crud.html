4단계 — 경매 등록·조회·수정·취소

로그인한 판매자가 경매를 등록·수정·취소하고 누구나 조회합니다. "누가, 어떤 상태에서 할 수 있나"라는 규칙을 도메인 예외로 표현하고, 그 예외와 FastAPI가 내는 422·404까지 전부 {"code","message"} 한 가지 껍데기로 나가게 만듭니다. 이 단계부터는 테스트를 먼저 쓰고(TDD) 구현합니다.

한 줄 요약. 이 문서를 끝내면 uv run pytest -q가 28 passed를 찍고, curl로 경매를 등록 → 조회 → 수정 → 남이 수정하면 403 → 취소 → 다시 취소하면 409 → 없는 경매 404까지 한 바퀴 돌며, 모든 에러 응답이 같은 모양임을 확인합니다.

학습 목표

  • "형식" 검증(Pydantic, 422)과 "규칙" 검증(서비스, 403/404/409)을 다른 층에 두는 이유를 안다
  • 상태 머신(scheduled → active → ended | cancelled)을 코드 한 곳에서만 바꾸도록 설계한다
  • 소유권 검사(판매자만)와 입찰 유무 검사를 도메인 예외로 표현한다
  • FastAPI 기본 422·404를 우리 표준 에러 껍데기로 감싼다
  • PATCH 부분 수정에서 "안 보낸 필드"와 "null로 보낸 필드"를 구분한다(exclude_unset)
  • 타임존이 없는 시각을 왜 거부해야 하는지 설명할 수 있다
🎯

이 단계의 목표

이 단계가 끝나면 경매의 생애 첫 절반이 API로 열립니다. 판매자가 POST /auctions로 경매를 올리면 시작 시각에 따라 active(바로 시작) 또는 scheduled(예약)가 되고, 누구나 GET /auctions/{id}로 봅니다. 판매자는 입찰이 붙기 전까지만 PATCH로 제목·설명·마감을 고치거나 POST …/cancel로 취소할 수 있습니다. 나머지 절반 — 입찰이 붙고, 마감되고, 낙찰되는 흐름 — 은 6·8단계입니다.

전제. 3단계가 끝나 있어야 합니다. uv run pytest -q → 13 passed, 컨테이너 두 개 (healthy). 이번 단계도 til/backend/fastapi/auction-api/에서 진행하고, 새로 설치하는 패키지는 없습니다.

이번 단계에서 만드는 것. 새 파일 5개(schemas/auction.py, repositories/auction.py, services/auction.py, routers/auctions.py, tests/test_auctions.py), 손보는 파일 3개(core/exceptions.py는 예외 계층으로 확장, main.py는 라우터 한 줄, tests/factories.py는 create_auction 추가). 목록 조회 GET /auctions는 페이지네이션·필터가 붙는 5단계 몫이라 여기서는 만들지 않습니다.

왜 필요한가 — 실무 맥락

CRUD는 self-study Week 6에서 이미 했습니다. 그때 ToDo는 "있으면 고치고 없으면 404"가 전부였죠. 실무의 CRUD가 어려운 이유는 동사가 아니라 조건입니다. 누가(판매자만), 어떤 상태에서(끝난 경매는 안 됨), 무엇이 없을 때(입찰이 하나라도 있으면 안 됨) 할 수 있는가. 이 조건들을 라우터 안에 if로 쌓기 시작하면 6단계에서 입찰 규칙이, 8단계에서 마감 규칙이 더해질 때 아무도 못 읽는 코드가 됩니다. 그래서 조건을 서비스의 도메인 예외로 뽑아내고, 라우터는 그 예외를 모르게 둡니다.

두 번째 실무 요소는 표준 에러 껍데기입니다. 3단계에서 우리 예외는 {"code","message"}로 나갔지만, Pydantic 검증 실패는 FastAPI 기본인 {"detail": [...]}로, 없는 라우트는 {"detail": "Not Found"}로 나갔습니다. 프론트 입장에서는 에러를 세 가지 모양으로 처리해야 하는 셈입니다. 이번 단계에서 셋을 하나로 합칩니다. 프론트는 code 하나로 분기하고(AUCTION_HAS_BIDS면 "입찰이 있어 수정할 수 없어요" 토스트), message는 그대로 보여주거나 다국어 사전의 키로 씁니다.

이 단계부터 TDD입니다. 3단계까지는 "테스트 인프라를 만드는" 단계라 구현 후 테스트를 붙이기도 했지만, 규칙이 많아지는 지금부터는 테스트가 곧 명세입니다. "남이 수정하면 403", "입찰 있으면 409"를 먼저 테스트로 적어 두면, 구현하다가 규칙 하나를 빠뜨려도 빨간불이 알려 줍니다. 순서는 실패하는 테스트 → 구현 → 통과. 익숙해지면 규칙을 코드로 옮기는 속도가 오히려 빨라집니다.
📦

비유 — 택배 상태와 주방·홀

상태 머신은 택배 상태입니다. 택배는 접수 → 배송 중 → 배송 완료로만 흐르고, 완료된 택배를 다시 접수 상태로 돌릴 수는 없습니다. 접수 단계에서만 주소를 바꿀 수 있고, 기사님이 집어 들면(입찰이 붙으면) 더는 못 바꿉니다. 경매도 같습니다. scheduled → active → ended가 정방향이고, cancelled는 입찰이 없을 때만 옆으로 빠지는 길입니다. 이 화살표를 누가 그을 수 있는지(판매자만, 워커만)를 코드 한 곳 — services/auction.py — 에서만 정하면, 나중에 규칙이 바뀌어도 그 파일만 보면 됩니다.
도메인 예외는 주방이 외치는 말, 핸들러는 홀 직원의 번역입니다. 주방(서비스)은 "재료 없음!", "주문 취소됨!"처럼 사실만 외칩니다. 손님에게 어떤 표정으로 뭐라고 말할지는 홀 직원(예외 핸들러)이 정합니다. 주방이 손님 응대까지 하면(서비스가 HTTPException을 던지면) 주방을 다른 가게(CLI, 배치 워커, 8단계의 마감 워커)로 옮길 때 응대 매뉴얼까지 딸려 갑니다. 주방은 요리만, 홀은 응대만 — 그래서 서비스 파일에는 fastapi를 import하는 줄이 한 줄도 없습니다.
🗺️

설계 그림

그림 두 장입니다. 첫 장은 상태 머신입니다. 네모가 네 개뿐이라 단순해 보이지만, 이 그림이 곧 services/auction.py의 규칙 전부입니다. 등록 시점에 starts_at이 지금 이하면 active, 미래면 scheduled. 수정과 취소는 파란 상자 안(열려 있고 입찰이 없을 때)에서만 됩니다. 정방향 화살표 두 개는 8단계 워커가 긋습니다 — 이번 단계에는 그 코드가 없지만, 상태 이름과 전이 규칙을 지금 정해 두기 때문에 8단계는 이 파일에 함수 두 개를 더하는 일이 됩니다.

화살표를 긋는 주체가 둘뿐이다. 판매자(4단계: 등록·취소)와 마감 워커(8단계: 활성화·종료). 입찰자는 상태를 바꾸지 못하고 current_price·bid_count만 올린다(6단계).

둘째 장은 에러가 나가는 길입니다. 3단계에서는 우리 AppError만 핸들러를 거쳤습니다. 이번에 Pydantic의 RequestValidationError와 Starlette의 HTTPException(없는 라우트 404, 잘못된 메서드 405)까지 같은 파일의 핸들러로 보냅니다. 예외 클래스는 계층으로 둡니다 — NotFoundError(404) 아래 AuctionNotFoundError, ConflictError(409) 아래 AuctionHasBidsError — 그래서 새 도메인 예외를 만들 때 상태 코드를 다시 고민하지 않고 부모만 고르면 됩니다.

에러의 출처는 셋이지만 출구는 하나. 상태 코드와 code는 출처가 정하고, 모양은 핸들러가 통일한다.

① tests/factories.py — 경매 공장 추가

3단계의 create_user 옆에 create_auction을 둡니다. 기본값은 "1분 전에 시작해 하루 뒤 마감하는, 시작가 10,000원, 입찰 0건의 active 경매"입니다. 테스트가 "입찰이 이미 있는 경매"를 원하면 bid_count=1처럼 아무 컬럼이나 덮어씁니다. 서비스를 거치지 않고 모델을 직접 만드는 이유는, 테스트의 준비 단계는 규칙 검사 대상이 아니기 때문입니다 — 규칙은 검증 단계에서 API를 통해 확인합니다.

"""테스트 데이터 공장. '유저 하나', '입찰 받는 중인 경매 하나' 를 한 줄로 만든다."""

import uuid
from datetime import UTC, datetime, timedelta

from httpx2 import AsyncClient
from sqlalchemy.ext.asyncio import AsyncSession

from app.core.security import hash_password
from app.models import Auction, AuctionCategory, AuctionStatus, User

DEFAULT_PASSWORD = "secret123"


async def create_user(
    db: AsyncSession,
    *,
    email: str | None = None,
    password: str = DEFAULT_PASSWORD,
    nickname: str = "테스터",
) -> User:
    user = User(
        email=email or f"user-{uuid.uuid4().hex[:8]}@example.com",
        password_hash=hash_password(password),
        nickname=nickname,
    )
    db.add(user)
    await db.flush()  # id, created_at 이 채워진다 (커밋은 아니다)
    return user


async def login_headers(
    client: AsyncClient, email: str, password: str = DEFAULT_PASSWORD
) -> dict[str, str]:
    res = await client.post("/auth/login", json={"email": email, "password": password})
    assert res.status_code == 200, res.text
    return {"Authorization": f"Bearer {res.json()['access_token']}"}


async def create_auction(db: AsyncSession, seller: User, **overrides: object) -> Auction:
    """기본값: 1분 전에 시작해 하루 뒤 마감하는 active 경매, 시작가 10,000원, 입찰 0건.

    overrides 로 아무 컬럼이나 덮어쓸 수 있다 (예: bid_count=1, status=AuctionStatus.ENDED).
    """
    now = datetime.now(UTC)
    values: dict[str, object] = {
        "seller_id": seller.id,
        "title": "빈티지 필름 카메라",
        "description": "",
        "category": AuctionCategory.HOBBY,
        "starting_price": 10_000,
        "current_price": 10_000,
        "min_increment": 1_000,
        "starts_at": now - timedelta(minutes=1),
        "ends_at": now + timedelta(days=1),
        "status": AuctionStatus.ACTIVE,
    }
    values.update(overrides)
    auction = Auction(**values)
    db.add(auction)
    await db.flush()
    return auction

② tests/test_auctions.py — 먼저 실패하는 테스트 15개

스펙의 규칙을 그대로 옮겼습니다. 등록 5개(201·예약·마감이 시작보다 빠름 422·타임존 없음 422·토큰 없음 401), 조회 2개(공개 200·없음 404), 수정 4개(판매자 200 + version 증가·남 403·입찰 있음 409·마감을 시작 앞으로 422), 취소 3개(200·재취소 409·입찰 있음 409), 껍데기 1개(없는 라우트도 {"code","message"}). 위의 두 헬퍼가 시각 문자열과 요청 본문을 만들어 줘서 각 테스트는 세 줄 안팎입니다.

import uuid
from datetime import UTC, datetime, timedelta

from httpx2 import AsyncClient

def _iso(delta: timedelta) -> str:
    """지금 기준 delta 만큼 떨어진 시각을 ISO 문자열(타임존 포함)로."""
    return (datetime.now(UTC) + delta).isoformat()


def _payload(**overrides: object) -> dict[str, object]:
    body: dict[str, object] = {
        "title": "맥북 프로 14 (2023)",
        "description": "박스 풀셋",
        "category": "electronics",
        "starting_price": 1_500_000,
        "min_increment": 10_000,
        "ends_at": _iso(timedelta(days=3)),
    }
    body.update(overrides)
    return body

async def test_create_auction_returns_201_and_is_active(
    client: AsyncClient, db_session: AsyncSession
):
    seller = await create_user(db_session)
    headers = await login_headers(client, seller.email)

    res = await client.post("/auctions", json=_payload(), headers=headers)

    assert res.status_code == 201, res.text
    body = res.json()
    assert body["seller_id"] == str(seller.id)
    assert body["status"] == "active"  # starts_at 을 안 주면 지금 시작
    assert body["current_price"] == body["starting_price"] == 1_500_000
    assert body["bid_count"] == 0 and body["winner_id"] is None and body["version"] == 0
    assert body["created_at"] and body["updated_at"]

"""도메인 예외와 표준 에러 응답.

서비스 계층은 HTTP 를 모른다 — HTTPException 대신 여기 있는 AppError 계열만 던진다.
라우터 바깥의 핸들러가 AppError 를 {"code", "message"} 형태의 JSON 으로 번역한다.

계층
    AppError (400)
    ├── UnauthorizedError (401)
    ├── ForbiddenError (403)      ── NotAuctionSellerError
    ├── NotFoundError (404)       ── AuctionNotFoundError
    ├── ConflictError (409)       ── EmailAlreadyExistsError, AuctionHasBidsError

같은 껍데기로 감싼다 → 클라이언트는 모든 에러를 한 가지 모양으로만 다루면 된다.

    status_code = status.HTTP_400_BAD_REQUEST

    def __init__(self, message: str | None = None) -> None:

            self.message = message
        super().__init__(self.message)

    code = "UNAUTHORIZED"
    status_code = status.HTTP_401_UNAUTHORIZED
    message = "인증이 필요합니다"


class ForbiddenError(AppError):
    code = "FORBIDDEN"
    status_code = status.HTTP_403_FORBIDDEN
    message = "권한이 없습니다"


class NotFoundError(AppError):
    code = "NOT_FOUND"
    status_code = status.HTTP_404_NOT_FOUND
    message = "찾을 수 없습니다"


class ConflictError(AppError):
    code = "CONFLICT"
    status_code = status.HTTP_409_CONFLICT
    message = "현재 상태에서는 처리할 수 없습니다"

    code = "INVALID_STATE"

    """형식은 맞지만 의미가 틀린 입력 (예: 마감이 시작보다 빠름). FastAPI 의 422 와 같은 급."""

    code = "UNPROCESSABLE"
    status_code = status.HTTP_422_UNPROCESSABLE_CONTENT
    message = "요청 값이 올바르지 않습니다"


# ── 인증 ─────────────────────────────────────────────────────────────

    code = "EMAIL_ALREADY_EXISTS"
    message = "이미 가입된 이메일입니다"

async def app_error_handler(request: Request, exc: AppError) -> JSONResponse:
    headers = {"WWW-Authenticate": "Bearer"} if exc.status_code == 401 else None
    return JSONResponse(
        status_code=exc.status_code,
        content={"code": exc.code, "message": exc.message},
        headers=headers,
    )


async def validation_error_handler(request: Request, exc: RequestValidationError) -> JSONResponse:
    """Pydantic 검증 실패(422). 기본 응답은 {"detail": [...]} 인데, 우리 껍데기로 감싸고
    필드별 상세는 "errors" 에 넣는다 — 프론트가 입력칸 옆에 메시지를 보여줄 때 쓴다.
    (loc / msg / type 만 남긴다. 기본 목록에 딸려 오는 input·ctx 는 사용자 입력을 되돌려 주거나
    파이썬 객체라 JSON 으로 못 만드는 경우가 있어 뺀다.)"""
    errors = [{"loc": e["loc"], "msg": e["msg"], "type": e["type"]} for e in exc.errors()]
    return JSONResponse(
        status_code=status.HTTP_422_UNPROCESSABLE_CONTENT,
        content={
            "code": "VALIDATION_ERROR",
            "message": "요청 값이 올바르지 않습니다",
            "errors": errors,
        },
    )


async def http_exception_handler(request: Request, exc: StarletteHTTPException) -> JSONResponse:
    """라우트 없음(404)·허용되지 않은 메서드(405) 같은 프레임워크 기본 에러도 같은 껍데기로."""
    codes = {404: "NOT_FOUND", 405: "METHOD_NOT_ALLOWED"}
    code = codes.get(exc.status_code, f"HTTP_{exc.status_code}")
    return JSONResponse(
        status_code=exc.status_code,
        content={"code": code, "message": exc.detail},
        headers=exc.headers,
    )


def register_exception_handlers(app: FastAPI) -> None:
    app.add_exception_handler(AppError, app_error_handler)  # type: ignore[arg-type]
    app.add_exception_handler(RequestValidationError, validation_error_handler)  # type: ignore[arg-type]
    app.add_exception_handler(StarletteHTTPException, http_exception_handler)  # type: ignore[arg-type]

from datetime import UTC, datetime

from pydantic import BaseModel, ConfigDict, Field, field_validator, model_validator

from app.models.enums import AuctionCategory, AuctionStatus


def _require_timezone(value: datetime | None) -> datetime | None:
    """'2026-08-26T10:00:00' 처럼 타임존이 없는 시각은 서울인지 UTC 인지 알 수 없다 → 거부."""
    if value is not None and value.tzinfo is None:
        raise ValueError("타임존 정보가 필요합니다 (예: 2026-08-26T10:00:00Z 또는 +09:00)")
    return value


class AuctionCreate(BaseModel):
    title: str = Field(min_length=1, max_length=100)
    description: str = Field(default="", max_length=2000)
    category: AuctionCategory
    starting_price: int = Field(gt=0, description="시작가(원)")
    min_increment: int = Field(default=1000, ge=100, description="최소 입찰 단위(원)")
    starts_at: datetime | None = Field(default=None, description="비우면 지금 바로 시작")
    ends_at: datetime

    _tz = field_validator("starts_at", "ends_at")(_require_timezone)

    @model_validator(mode="after")
    def ends_after_starts(self) -> "AuctionCreate":
        start = self.starts_at or datetime.now(UTC)
        if self.ends_at <= start:
            raise ValueError("마감(ends_at)은 시작(starts_at)보다 뒤여야 합니다")
        return self

"""경매 규칙. HTTP 를 모른다 — 도메인 예외(AppError 계열) 만 던진다.

상태 머신 (한 곳에서만 바꾼다)
    scheduled ──(시작 시각 도달, 8단계 워커)──▶ active ──(마감, 8단계)──▶ ended
        └────────────(판매자 취소, 입찰 0건)────────┴──▶ cancelled
"""

import uuid
from datetime import UTC, datetime

from sqlalchemy.ext.asyncio import AsyncSession

from app.core.exceptions import (
    AuctionClosedError,
    AuctionHasBidsError,
    AuctionNotFoundError,
    InvalidPeriodError,
    NotAuctionSellerError,
)
from app.models import Auction, AuctionStatus, User
from app.repositories import auction as auction_repo
from app.schemas.auction import AuctionCreate, AuctionUpdate

OPEN_STATUSES = {AuctionStatus.SCHEDULED, AuctionStatus.ACTIVE}


def _now() -> datetime:
    return datetime.now(UTC)


async def create(db: AsyncSession, seller: User, data: AuctionCreate) -> Auction:
    now = _now()
    starts_at = data.starts_at or now
    auction = Auction(
        seller_id=seller.id,
        title=data.title,
        description=data.description,
        category=data.category,
        starting_price=data.starting_price,
        current_price=data.starting_price,  # 입찰 전 현재가 = 시작가
        min_increment=data.min_increment,
        starts_at=starts_at,
        ends_at=data.ends_at,
        status=AuctionStatus.ACTIVE if starts_at <= now else AuctionStatus.SCHEDULED,
    )
    await auction_repo.add(db, auction)
    await db.commit()
    await db.refresh(auction)  # DB 가 채운 created_at / updated_at 을 읽어 온다
    return auction


async def get(db: AsyncSession, auction_id: uuid.UUID) -> Auction:
    auction = await auction_repo.get(db, auction_id)
    if auction is None:
        raise AuctionNotFoundError()
    return auction


def _ensure_seller(auction: Auction, user: User) -> None:
    if auction.seller_id != user.id:
        raise NotAuctionSellerError()


def _ensure_open_and_unbid(auction: Auction) -> None:
    """수정·취소 공통 규칙: 아직 열려 있고(scheduled/active), 입찰이 하나도 없어야 한다."""
    if auction.status not in OPEN_STATUSES:
        raise AuctionClosedError()
    if auction.bid_count > 0:
        raise AuctionHasBidsError()


async def update(
    db: AsyncSession, user: User, auction_id: uuid.UUID, data: AuctionUpdate
) -> Auction:
    auction = await get(db, auction_id)
    _ensure_seller(auction, user)
    _ensure_open_and_unbid(auction)

    changes = data.model_dump(exclude_unset=True)  # 요청에 실제로 담긴 필드만
    if "ends_at" in changes and changes["ends_at"] <= auction.starts_at:
        raise InvalidPeriodError()
    for field, value in changes.items():
        setattr(auction, field, value)
    auction.version += 1  # 6단계 낙관적 락의 재료 — 바뀔 때마다 1 증가

    await db.commit()
    await db.refresh(auction)
    return auction


async def cancel(db: AsyncSession, user: User, auction_id: uuid.UUID) -> Auction:
    auction = await get(db, auction_id)
    _ensure_seller(auction, user)
    _ensure_open_and_unbid(auction)

    auction.status = AuctionStatus.CANCELLED
    auction.version += 1
    await db.commit()
    await db.refresh(auction)
    return auction

함정 & 실무 팁

서비스에서 HTTPException을 던지고 싶어질 때. 당장은 그게 빠릅니다. 하지만 8단계 워커는 HTTP 없이 services/auction.py를 호출하고, 그때 서비스가 HTTPException을 던지면 워커는 "403이 뭔데?"가 됩니다. 규칙 위반은 도메인 예외로, HTTP 번역은 핸들러로. 이 경계를 지키면 서비스 테스트도 HTTP 없이 함수 호출만으로 쓸 수 있습니다.
400 · 409 · 422 고르기. 형식이 틀리면 422(Pydantic이 알아서), 의미가 틀리면 우리도 422(InvalidPeriodError — 마감이 시작보다 빠름은 DB를 봐야 아는 의미 오류), 현재 상태와 충돌하면 409(입찰이 있어서, 이미 끝나서). 400은 "뭐가 틀렸는지 더 구체적으로 말할 수 없을 때"만 남겨 두세요. 코드를 잘 고르면 프론트가 재시도할지(409는 새로고침 후 재시도 여지), 입력을 고칠지(422) 판단할 수 있습니다.
exclude_unset과 exclude_none은 다릅니다. PATCH에 {"description": null}을 보내는 것과 description을 아예 안 보내는 것은 의도가 다릅니다(비우기 vs 건드리지 않기). model_dump(exclude_unset=True)는 "요청에 있었나"를 기준으로 하므로 이 둘을 구분합니다. exclude_none=True로 바꾸면 "null로 비우기"가 영영 불가능해집니다. 지금 AuctionUpdate는 description에 None이 오면 setattr로 None을 넣으려다 DB의 NOT NULL에 걸립니다 — 비우고 싶으면 ""을 보내는 것으로 약속하거나, 스키마에서 None을 ""로 바꾸는 validator를 두세요.
타임존 없는 시각은 버그의 온상입니다. DB 컬럼은 timestamptz라 저장은 항상 UTC이고, 응답의 Z가 그 표시입니다. 클라이언트가 +09:00로 보내도 같은 순간으로 저장되니 프론트는 자기 타임존으로 보여주기만 하면 됩니다. 문제는 타임존 없는 값입니다 — Pydantic은 naive datetime을 그대로 받아 주고, asyncpg는 그걸 UTC로 간주합니다. 서울 사용자가 "오후 6시 마감"이라고 보냈는데 UTC 18시(서울 새벽 3시)로 저장되는 식입니다. 그래서 스키마 입구에서 막습니다.
commit() 뒤에 refresh()를 부르는 이유. created_at·updated_at은 DB가 채웁니다(server_default·onupdate). 세션이 expire_on_commit=False라 커밋 후에도 객체는 살아 있지만, DB가 바꾼 값은 다시 읽어야 응답에 실립니다. 안 읽으면 updated_at이 수정 전 값으로 나갑니다. SQLAlchemy 2.0은 PostgreSQL에서 RETURNING으로 INSERT 직후 값을 가져오기도 하지만, "커밋 후 응답할 객체는 refresh"를 습관으로 두면 안전합니다.
상태 전이는 한 파일에서만. auction.status = ...라고 쓰는 줄이 services/auction.py 밖에 생기면 안 됩니다. 8단계 워커가 활성화·마감을 맡을 때도 이 파일에 activate()·close()를 더해서 부릅니다. 상태를 바꾸는 코드가 한 곳이면 "어떤 상태에서 어떤 상태로 갈 수 있나"를 그 파일의 docstring 하나로 설명할 수 있습니다.
Starlette의 HTTPException을 등록해야 404가 잡힙니다. fastapi.HTTPException은 starlette.exceptions.HTTPException의 자식입니다. 라우트가 없을 때 던지는 쪽은 Starlette 라우터라 부모를 던집니다. FastAPI 쪽 클래스로 핸들러를 등록하면 자식만 잡혀서 /nope는 여전히 {"detail":"Not Found"}로 나갑니다. 테스트 test_unknown_route_uses_standard_envelope가 이걸 지킵니다.
@router.post("")와 trailing slash. prefix가 /auctions일 때 경로를 "/"로 쓰면 최종 경로는 /auctions/가 되고, 슬래시 없는 POST /auctions는 307 리다이렉트를 받습니다. 리다이렉트를 따라가지 않는 클라이언트(일부 fetch 설정, 로드밸런서)에서는 그냥 실패로 보입니다. 빈 문자열로 쓰면 /auctions 정확히 하나만 생깁니다.

셀프 체크

Q 서비스에서 바로 raise HTTPException(status_code=403) 하면 코드가 더 짧은데, 왜 도메인 예외를 따로 만드나요?

서비스를 HTTP 바깥에서도 쓰기 위해서입니다. 8단계의 마감 워커는 웹 요청 없이 services/auction.py를 직접 호출하고, 9단계의 웹훅 처리도 결제 서비스를 호출합니다. 서비스가 HTTPException을 던지면 그 호출자들은 HTTP 개념을 억지로 알아야 합니다. 도메인 예외(AuctionHasBidsError)는 "입찰이 있다"는 사실만 말하고, 그걸 403으로 할지 409로 할지는 HTTP 층(핸들러)이 정합니다. 덤으로 예외 클래스가 계층이라 새 규칙을 추가할 때 부모(ConflictError)만 고르면 상태 코드와 껍데기가 자동으로 따라옵니다. 그리고 서비스 단위 테스트를 HTTP 없이 pytest.raises(AuctionHasBidsError)로 쓸 수 있습니다.

Q "입찰이 있어서 수정 불가"는 409, "마감이 시작보다 빠름"은 422로 했습니다. 둘 다 400으로 하면 안 되나요?

되긴 하지만 정보를 버리는 것입니다. 422는 "요청 자체가 의미상 틀렸다 — 입력을 고쳐서 다시 보내라"는 뜻이고, 409는 "요청은 멀쩡한데 서버의 현재 상태와 충돌한다 — 상태가 바뀌면 같은 요청이 성공할 수도 있다"는 뜻입니다. 마감 시각을 고치면 422는 해결되지만, 409는 입찰이 취소되지 않는 한 같은 요청을 아무리 보내도 실패합니다. 프론트는 이 차이로 "입력칸을 빨갛게" 할지 "새로고침해서 최신 상태를 보라"고 할지 정합니다. 400은 이 둘을 구분할 수 없을 때의 마지막 선택지입니다.

Q PATCH로 {"description": null}을 보내면 어떻게 되나요? 안 보내는 것과 무엇이 다른가요?

안 보내면 model_dump(exclude_unset=True)에 description이 아예 없어서 건드리지 않습니다. null을 보내면 "설정됐다(set)"로 기록되어 {"description": None}이 나오고, 서비스가 setattr(auction, "description", None)을 하다가 DB의 NOT NULL 제약에 걸려 500이 납니다 — 지금 구현의 빈틈입니다. 실무에서는 셋 중 하나를 약속합니다: (1) 비우기는 ""으로만 허용하고 null은 422, (2) validator가 None을 ""으로 바꾼다, (3) 컬럼을 nullable로 만든다. 어느 쪽이든 "null = 비우기, 생략 = 유지"라는 구분이 가능해야 하고, 그걸 가능하게 하는 게 exclude_unset입니다(exclude_none이면 구분이 사라집니다).
