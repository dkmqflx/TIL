5단계 — 목록 조회를 실무 수준으로

GET /auctions에 커서 페이지네이션, 필터·정렬을 붙이고, 판매자 정보를 함께 실으면서도 쿼리가 딱 두 번만 나가게 만듭니다. "N+1이 없다"를 감으로 믿지 않고 쿼리를 세는 테스트로 증명하는 것이 이 단계의 핵심입니다.

한 줄 요약. 이 문서를 끝내면 uv run pytest -q가 42 passed를 찍고, 경매 12건을 limit=5로 세 장에 걸쳐 넘기며 마지막 장의 next_cursor가 null이 되는 것, 커서를 열어 보면 마지막 항목의 (정렬 기준, 마감 시각, id)가 들어 있는 것, 그리고 SQL 로그에 SELECT가 정확히 두 줄(경매 + 판매자 IN (...))만 찍히는 것을 확인합니다.

학습 목표

  • offset 페이지네이션이 "밀리는" 이유와 keyset(커서) 방식이 그것을 어떻게 피하는지 설명할 수 있다
  • 정렬 키가 같은 행(동점)을 id로 갈라 페이지 경계에서 중복·누락이 없게 만든다
  • 커서를 불투명 토큰으로 만들고, 잘못된 커서를 422로 거부한다
  • 쿼리스트링 여러 개를 Pydantic 모델 하나로 받아 검증한다
  • selectinload로 N+1을 없애고, SQLAlchemy 이벤트로 쿼리 수를 세어 테스트로 고정한다
  • async SQLAlchemy에서 lazy load가 왜 막혀 있는지(MissingGreenlet) 이해한다

이 단계의 목표

4단계의 GET /auctions/{id}는 한 건입니다. 이번에는 목록 — 사용자가 앱을 열자마자 보는 화면이자, 서비스에서 가장 많이 호출되는 API — 을 만듭니다. 끝나면 GET /auctions?status=active&category=books&min_price=50000&sort=ending_soon&limit=20&cursor=…가 동작하고, 응답은 {"items": [...], "next_cursor": "..." | null} 모양입니다. 각 항목에는 판매자 닉네임이 함께 실리지만 쿼리는 항목 수와 무관하게 두 번입니다.

이번 단계에서 만드는 것. 새 파일 2개(app/core/pagination.py, tests/test_auction_list.py), 손보는 파일 6개(tests/conftest.py에 쿼리 카운터, core/exceptions.py에 예외 하나, schemas/auction.py에 목록용 스키마 4개, repositories/auction.py에 list_page, services/auction.py에 list_auctions, routers/auctions.py에 GET ""). 4단계에서 만든 함수는 한 줄도 바뀌지 않고 더하기만 합니다.

왜 필요한가 — 실무 맥락

목록 API는 겉보기엔 SELECT * FROM auctions LIMIT 20이면 끝날 것 같지만, 실무에서 사고가 나는 지점이 세 군데 있습니다.

첫째, 페이지가 밀립니다. 흔히 쓰는 ?page=3(offset 40)은 "앞에서 40개 건너뛰고 20개"라는 뜻입니다. 그런데 경매는 실시간으로 새로 올라옵니다. 사용자가 2페이지를 보는 동안 경매가 3개 등록되면, 3페이지에는 2페이지에서 이미 본 항목 3개가 다시 나오고 그만큼의 새 항목은 영영 건너뛰어집니다. 마감 임박순 정렬이면 더 심합니다 — 매초 순서가 바뀌니까요. 그래서 실무에서는 "몇 번째부터"가 아니라 "이 항목 다음부터"를 기억하는 커서(keyset) 방식을 씁니다. 트위터·슬랙·GitHub API가 전부 이렇게 합니다.

둘째, 필터가 늘어납니다. 상태, 카테고리, 가격대, 정렬 기준, 페이지 크기… 쿼리 파라미터가 일곱 개쯤 되면 라우터 함수 시그니처가 한 화면을 넘고, "최소가가 최대가보다 크면?" 같은 교차 검증을 넣을 자리가 없습니다. FastAPI는 쿼리스트링 전체를 Pydantic 모델 하나로 받을 수 있습니다. 4단계에서 본문에 했던 검증(범위, enum, 교차 검증)을 쿼리스트링에도 똑같이 적용합니다.

셋째, N+1. 목록에 판매자 닉네임을 실으려면 경매마다 판매자를 찾아야 합니다. ORM이 편한 만큼 위험한 게 여기입니다 — auction.seller.nickname 한 줄이 항목마다 SELECT 하나를 몰래 날립니다. 20건 목록이 21번 쿼리, 50건이면 51번. 개발 PC에서는 눈치채지 못하다가 운영 DB에서 목록 API 하나가 커넥션 풀을 다 잡아먹습니다. 이번 단계는 이걸 없애는 것에 더해, 없다는 사실을 테스트로 고정합니다. 누가 나중에 selectinload 한 줄을 지우면 CI가 빨간불을 켭니다.

목록 응답은 상세 응답과 다른 모델로. AuctionRead를 그대로 쓰고 싶어지지만, 목록 20건에 2,000자짜리 description을 다 실으면 응답이 수십 KB가 됩니다. 목록 카드에 보이는 것만 담은 AuctionListItem을 따로 둡니다. 판매자도 {"id", "nickname"}만 — 이메일을 목록에 실었다가 개인정보 이슈가 되는 사고는 실제로 흔합니다.

비유 — 책갈피와 주방 왕복

offset은 페이지 번호, 커서는 책갈피입니다. 두꺼운 책을 읽다 멈출 때 "137쪽까지 읽었다"고 기억하면, 누군가 앞쪽에 페이지를 세 장 끼워 넣는 순간 137쪽은 다른 내용이 됩니다(이미 읽은 걸 또 읽거나, 세 장을 건너뜁니다). 책갈피는 다릅니다 — "이 문장 다음부터"를 물리적으로 기억하니 앞에 뭐가 끼워지든 상관없습니다. 커서에 들어 있는 것이 바로 그 "마지막 문장"입니다: 마지막으로 본 경매의 (마감 시각, id). 다음 요청은 "이것보다 뒤인 것부터 20개"가 되고, 이건 인덱스가 바로 찾아 줍니다. offset 100,000은 10만 행을 세고 버려야 하지만, 커서는 몇 페이지째든 같은 속도입니다.
N+1은 주방을 스무 번 다녀오는 홀 직원입니다. 테이블 20개의 주문을 받아 놓고, 1번 테이블 음식 가져오고, 2번 테이블 음식 가져오고… 주방(DB)까지 스무 번 왕복합니다. 한 번에 "1번부터 20번까지 다 주세요"(WHERE id IN (...))라고 하면 두 번이면 끝납니다. ORM의 selectinload가 정확히 이 "몰아서 한 번"입니다. 그리고 async SQLAlchemy는 홀 직원이 무심코 주방으로 걸어가는 것(lazy load) 자체를 막아 놓았습니다 — 그래서 N+1이 조용히 생기지는 않지만, 반복문 안에서 일부러 한 건씩 가져오면 똑같이 스무 번이 됩니다.
🗺️

설계 그림

첫 그림은 커서가 무엇을 기억하는가입니다. 목록을 (ends_at, id) 순으로 늘어놓고 다섯 개를 자르면, 커서에는 다섯 번째 항목의 키가 들어갑니다. 다음 요청은 WHERE (ends_at, id) > (커서) — Postgres의 행 비교(row comparison)입니다. "마감이 더 늦거나, 마감이 같으면 id가 더 큰 것"을 한 식으로 씁니다. LIMIT은 요청한 것보다 하나 더(limit+1) 가져옵니다. 여섯 번째가 있으면 "다음 페이지 있음", 없으면 next_cursor: null. COUNT(*)를 따로 날리지 않아도 됩니다.

키는 항상 (정렬 컬럼, id) 쌍이다. 마감 시각이 같은 행이 열 개여도 id가 순서를 확정하므로, 페이지 경계를 어디서 자르든 같은 행이 두 번 나오거나 빠지지 않는다. 회색 경매 6은 마감이 5와 같지만 id가 커서 2페이지 첫 줄이 된다.

둘째 그림은 N+1과 그 반대입니다. 왼쪽처럼 되는 코드는 이번 단계 테스트 안에 일부러 하나 들어 있습니다(test_loading_seller_row_by_row_is_n_plus_one) — "이렇게 하면 21번"을 눈으로 확인하고 나면 오른쪽 selectinload 한 줄이 왜 중요한지 잊지 않게 됩니다. 오른쪽의 두 번째 쿼리는 첫 쿼리로 얻은 seller_id들을 모아 IN (...) 한 방으로 판매자를 가져옵니다.

왼쪽은 이번 단계의 마지막 테스트가 일부러 재현하는 상황(1 + 20 = 21), 오른쪽은 list_page의 기본 동작(2). 둘 다 숫자로 테스트에 박혀 있다.

코드 배치는 4단계 그대로입니다. 커서를 만들고 푸는 순수 함수는 core/pagination.py, SQL은 repositories/auction.py의 list_page, "잘라내고 다음 커서 만들기"는 services/auction.py의 list_auctions, 쿼리스트링 검증은 schemas/auction.py의 AuctionListParams. 라우터는 여전히 한 줄입니다.

class QueryCounter:
    """실행된 SQL 문장을 모아 두는 작은 상자. N+1 을 '숫자'로 증명할 때 쓴다."""

    def __init__(self) -> None:
        self.statements: list[str] = []

    def record(self, statement: str) -> None:
        self.statements.append(statement)

    def reset(self) -> None:
        self.statements.clear()

    @property
    def selects(self) -> int:
        return sum(1 for s in self.statements if s.lstrip().upper().startswith("SELECT"))

async def _walk(client: AsyncClient, **params: object) -> list[list[dict]]:
    """next_cursor 가 None 이 될 때까지 페이지를 넘기며 items 목록을 모은다."""

    cursor: str | None = None

        assert res.status_code == 200, res.text
        body = res.json()
        pages.append(body["items"])
        cursor = body["next_cursor"]
        if cursor is None:
            return pages

async def validation_error_handler(request: Request, exc: RequestValidationError) -> JSONResponse:

    필드별 상세는 "errors" 에 넣는다 — 프론트가 입력칸 옆에 메시지를 보여줄 때 쓴다.

    파이썬 객체라 JSON 으로 못 만드는 경우가 있어 뺀다.)"""

        content={
            "code": "VALIDATION_ERROR",
            "message": "요청 값이 올바르지 않습니다",
            "errors": errors,
        },
    )

    codes = {404: "NOT_FOUND", 405: "METHOD_NOT_ALLOWED"}

        status_code=exc.status_code,
        content={"code": code, "message": exc.detail},
        headers=exc.headers,

⑤ app/core/pagination.py — 커서 만들기·풀기

순수 함수 둘뿐입니다. encode_cursor는 [정렬 기준, 시각의 ISO 문자열, id]를 JSON으로 만들고 base64url로 감싼 뒤 끝의 = 패딩을 뗍니다(URL에 그대로 넣기 좋게). decode_cursor는 그 반대인데, 어디서 실패하든 — base64가 아니든, JSON이 아니든, 항목이 셋이 아니든, 시각이나 UUID 모양이 아니든 — 전부 InvalidCursorError 하나로 모읍니다. 클라이언트가 커서를 만들 일은 없으니 "뭐가 틀렸는지" 친절할 필요가 없고, "처음부터 다시 조회하세요"면 충분합니다.

정렬 기준을 커서 안에 넣는 이유는 마지막 줄입니다. sort=newest로 받은 커서를 sort=ending_soon에 쓰면 에러 없이 엉뚱한 곳부터 읽힙니다. 조용한 오동작보다 422가 낫습니다.

pythonapp/core/pagination.py
"""커서(keyset) 페이지네이션 도구.

커서 = "마지막으로 본 항목의 정렬 키" 를 base64 로 싼 문자열.
    [정렬 기준, 정렬 키(ISO 시각), id]  →  json  →  base64url (패딩 제거)
클라이언트는 내용을 해석하지 않고 그대로 되돌려 준다(불투명 토큰).
정렬 기준을 같이 넣는 이유: newest 로 받은 커서를 ending_soon 에 쓰면 엉뚱한 곳부터 읽힌다.
"""

import base64
import json
import uuid
from datetime import datetime

from app.core.exceptions import InvalidCursorError


def encode_cursor(sort: str, key: datetime, id_: uuid.UUID) -> str:
    raw = json.dumps([sort, key.isoformat(), str(id_)]).encode()
    return base64.urlsafe_b64encode(raw).decode().rstrip("=")


def decode_cursor(cursor: str, sort: str) -> tuple[datetime, uuid.UUID]:
    """되돌려 받은 커서를 (정렬 키, id) 로. 모양이 조금이라도 다르면 InvalidCursorError."""
    try:
        padded = cursor + "=" * (-len(cursor) % 4)  # 떼어 낸 '=' 패딩을 되살린다
        sort_in, key, id_ = json.loads(base64.urlsafe_b64decode(padded))
        parsed = (datetime.fromisoformat(key), uuid.UUID(id_))
    except (ValueError, TypeError) as exc:  # base64·JSON·개수·시각·UUID 오류 전부 여기로
        raise InvalidCursorError() from exc
    if sort_in != sort:
        raise InvalidCursorError("정렬 기준이 다른 커서입니다")
    return parsed

⑦ app/repositories/auction.py — list_page

SQL이 사는 곳입니다. 필터는 있는 것만 where로 쌓고, 커서(after)가 있으면 tuple_(key, Auction.id)로 행 비교를 합니다 — 렌더링되면 (ends_at, id) > ($1, $2)입니다. 오름차순(ending_soon)이면 >, 내림차순(newest)이면 <. ORDER BY는 반드시 커서 키와 같은 두 컬럼, 같은 방향이어야 합니다(다르면 페이지가 꼬입니다). selectinload(Auction.seller) 한 줄이 두 번째 그림의 오른쪽을 만들고, limit + 1이 "다음 있음"의 재료입니다.

    await db.flush()  # INSERT → id / created_at 확보. 커밋은 서비스가 결정한다
    return auction


async def list_page(
    db: AsyncSession,
    *,
    status: AuctionStatus | None = None,
    category: AuctionCategory | None = None,
    min_price: int | None = None,
    max_price: int | None = None,
    sort: str = "ending_soon",
    limit: int = 20,
    after: tuple[datetime, uuid.UUID] | None = None,
    load_seller: bool = True,
) -> list[Auction]:
    """keyset 페이지 한 장. limit+1 건을 가져와 '다음 페이지가 있나' 를 알려 준다.
    (limit 개로 잘라내는 일은 서비스가 한다.)

    정렬 키는 (시각, id) 쌍이다. 시각이 같은 행이 여러 개여도 id 가 순서를 확정하므로
    페이지 경계에서 같은 행이 두 번 나오거나 빠지는 일이 없다.
    """
    key = Auction.ends_at if sort == "ending_soon" else Auction.created_at
    ascending = sort == "ending_soon"

    stmt = select(Auction)
    if status is not None:
        stmt = stmt.where(Auction.status == status)
    if category is not None:
        stmt = stmt.where(Auction.category == category)
    if min_price is not None:
        stmt = stmt.where(Auction.current_price >= min_price)
    if max_price is not None:
        stmt = stmt.where(Auction.current_price <= max_price)

    if after is not None:
        pair = tuple_(key, Auction.id)  # SQL: (ends_at, id) > ($1, $2)  ← 행 비교
        stmt = stmt.where(pair > after if ascending else pair < after)

    if ascending:
        stmt = stmt.order_by(key.asc(), Auction.id.asc())
    else:
        stmt = stmt.order_by(key.desc(), Auction.id.desc())

    if load_seller:
        stmt = stmt.options(selectinload(Auction.seller))  # 판매자는 IN (...) 한 방으로

    result = await db.scalars(stmt.limit(limit + 1))
    return list(result.all())

        └────────────(판매자 취소, 입찰 0건)────────┴──▶ cancelled
"""

import uuid
from datetime import UTC, datetime

from sqlalchemy.ext.asyncio import AsyncSession

from app.core.exceptions import (
    AuctionClosedError,
    AuctionHasBidsError,
    AuctionNotFoundError,
    InvalidPeriodError,
    NotAuctionSellerError,
)
from app.core.pagination import decode_cursor, encode_cursor
from app.models import Auction, AuctionStatus, User
from app.repositories import auction as auction_repo
from app.schemas.auction import AuctionCreate, AuctionListParams, AuctionUpdate

OPEN_STATUSES = {AuctionStatus.SCHEDULED, AuctionStatus.ACTIVE}


def _now() -> datetime:
    return datetime.now(UTC)


async def create(db: AsyncSession, seller: User, data: AuctionCreate) -> Auction:
    now = _now()
    starts_at = data.starts_at or now
    auction = Auction(
        seller_id=seller.id,
        title=data.title,
        description=data.description,
        category=data.category,
        starting_price=data.starting_price,
        current_price=data.starting_price,  # 입찰 전 현재가 = 시작가
        min_increment=data.min_increment,
        starts_at=starts_at,
        ends_at=data.ends_at,
        status=AuctionStatus.ACTIVE if starts_at <= now else AuctionStatus.SCHEDULED,
    )
    await auction_repo.add(db, auction)
    await db.commit()
    await db.refresh(auction)  # DB 가 채운 created_at / updated_at 을 읽어 온다
    return auction


async def list_auctions(
    db: AsyncSession, params: AuctionListParams
) -> tuple[list[Auction], str | None]:
    """한 페이지 + 다음 커서. 커서 해석/생성은 여기서, 쿼리는 리포지토리에서."""
    after = decode_cursor(params.cursor, params.sort) if params.cursor else None
    rows = await auction_repo.list_page(
        db,
        status=params.status,
        category=params.category,
        min_price=params.min_price,
        max_price=params.max_price,
        sort=params.sort,
        limit=params.limit,
        after=after,
    )
    items = rows[: params.limit]
    if len(rows) <= params.limit:  # limit+1 번째가 없다 = 마지막 페이지
        return items, None
    last = items[-1]
    key = last.ends_at if params.sort == "ending_soon" else last.created_at
    return items, encode_cursor(params.sort, key, last.id)


async def get(db: AsyncSession, auction_id: uuid.UUID) -> Auction:
    auction = await auction_repo.get(db, auction_id)
    if auction is None:
        raise AuctionNotFoundError()
    return auction


def _ensure_seller(auction: Auction, user: User) -> None:
    if auction.seller_id != user.id:
        raise NotAuctionSellerError()


def _ensure_open_and_unbid(auction: Auction) -> None:
    """수정·취소 공통 규칙: 아직 열려 있고(scheduled/active), 입찰이 하나도 없어야 한다."""
    if auction.status not in OPEN_STATUSES:
        raise AuctionClosedError()
    if auction.bid_count > 0:
        raise AuctionHasBidsError()


async def update(
    db: AsyncSession, user: User, auction_id: uuid.UUID, data: AuctionUpdate
) -> Auction:
    auction = await get(db, auction_id)
    _ensure_seller(auction, user)
    _ensure_open_and_unbid(auction)

    changes = data.model_dump(exclude_unset=True)  # 요청에 실제로 담긴 필드만
    if "ends_at" in changes and changes["ends_at"] <= auction.starts_at:
        raise InvalidPeriodError()
    for field, value in changes.items():
        setattr(auction, field, value)
    auction.version += 1  # 6단계 낙관적 락의 재료 — 바뀔 때마다 1 증가

    await db.commit()
    await db.refresh(auction)
    return auction


async def cancel(db: AsyncSession, user: User, auction_id: uuid.UUID) -> Auction:
    auction = await get(db, auction_id)
    _ensure_seller(auction, user)
    _ensure_open_and_unbid(auction)

    auction.status = AuctionStatus.CANCELLED
    auction.version += 1
    await db.commit()
    await db.refresh(auction)
    return auction

함정 & 실무 팁

offset 페이지네이션이 틀린 건 아닙니다 — 조건이 있을 뿐. 관리자 화면처럼 "3페이지로 바로 가기"가 필요하고 데이터가 거의 안 바뀌는 곳에서는 offset이 편합니다. 하지만 (1) 실시간으로 행이 끼어드는 목록, (2) 무한 스크롤, (3) 깊은 페이지(offset 10만)가 있는 곳에서는 keyset이 답입니다. 경매 목록은 셋 다 해당합니다. 둘을 섞어 쓰지는 마세요 — 같은 API에 page와 cursor가 둘 다 있으면 클라이언트가 혼란스러워합니다.
ORDER BY와 커서 키는 한 몸입니다. 정렬을 ends_at 하나로만 하고 커서도 ends_at만 담으면, 마감이 같은 행 5개가 페이지 경계에 걸릴 때 WHERE ends_at > 커서가 그 5개를 몽땅 건너뛰거나(>) 몽땅 다시 보여줍니다(>=). 그래서 항상 유일한 컬럼(id)을 마지막에 붙이고, ORDER BY도 정확히 같은 두 컬럼·같은 방향으로 씁니다. 이번 테스트의 시드가 동점을 일부러 만드는 이유입니다.
커서는 불투명(opaque) 토큰입니다. base64 안에 뭐가 들어 있는지는 서버 사정이고, 클라이언트는 받은 문자열을 그대로 돌려주기만 해야 합니다. 그래서 나중에 커서 형식을 바꿔도(정렬 컬럼 추가 등) 클라이언트 코드는 안 바뀝니다. 반대로 말하면 커서를 만들어서 보내는 클라이언트는 언제든 깨질 수 있으니 422로 명확히 거부합니다. 보안이 걱정되면(커서 안의 id로 뭔가 추측할까 봐) HMAC 서명을 붙이면 되는데, 9단계에서 웹훅 서명을 배운 뒤 적용해 보세요.
async SQLAlchemy는 lazy load를 막아 놓았습니다 — 일부러. 동기 세션에서 auction.seller는 필요할 때 몰래 SELECT를 날립니다(그래서 N+1이 조용히 생깁니다). async 세션에서 같은 짓을 하면 MissingGreenlet 에러가 납니다 — "await 없이 I/O를 하려 했다"는 뜻입니다. 처음엔 짜증나지만 축복입니다: 연관 객체가 필요하면 selectinload/joinedload로 미리 선언해야 하고, 그 선언이 곧 "쿼리 몇 번"의 문서가 됩니다. 정말 한 건씩 가져와야 하면 await db.run_sync(lambda s: a.seller)처럼 감싸는데, 반복문 안에서 그러면 21번이 됩니다(마지막 테스트가 그 증거).
selectinload vs joinedload. 둘 다 N+1을 없앱니다. joinedload는 LEFT JOIN으로 쿼리 한 번, selectinload는 IN (...)으로 두 번. 그런데 목록에는 selectinload가 낫습니다 — joinedload는 LIMIT과 만나면 SQLAlchemy가 서브쿼리로 감싸야 하고(행이 뻥튀기되니까), 1:N(경매→입찰 목록)에서는 부모 행이 자식 수만큼 중복돼 전송량이 커집니다. 다대일·목록·LIMIT이 있으면 selectinload, 단건 상세에서 다대일 하나만 붙일 땐 joinedload가 깔끔합니다.
limit + 1 트릭은 COUNT(*)를 없앱니다. "다음 페이지가 있나"를 알려고 전체 개수를 세면 목록마다 쿼리가 하나 늘고, 큰 테이블에서 COUNT(*)는 느립니다. 하나 더 가져와서 넘치면 "있음", 아니면 "없음" — 쿼리 하나로 끝납니다. 전체 개수("경매 1,234건")를 화면에 꼭 보여줘야 한다면 그건 별도 캐시(10단계)의 몫입니다.
커서 안의 시각은 타임존을 잃으면 안 됩니다. isoformat()은 aware datetime이면 +00:00을 붙이고, fromisoformat()은 그걸 되살립니다. 만약 naive로 저장했다가 되살리면 asyncpg가 UTC로 간주해 비교가 9시간 어긋납니다(4단계 함정과 같은 뿌리). 모델 컬럼이 DateTime(timezone=True)라 여기서 나오는 값은 항상 aware입니다 — 그 전제를 깨지 마세요.
쿼리 카운터가 SELECT만 세는 이유와 한계. 요청 하나에 BEGIN·ROLLBACK 같은 문장도 오가지만 그건 N+1과 무관하니 뺐습니다. 또 이 카운터는 이 프로세스의 엔진이 보낸 것만 봅니다 — 운영에서 실제 쿼리 수를 보려면 Postgres의 pg_stat_statements나 APM을 씁니다(10단계 관측성). 테스트의 역할은 "2가 3이 되는 순간 알려주기"입니다.

셀프 체크

Q ?page=3&size=20(offset)이 더 익숙한데, 커서 방식이 꼭 필요한 이유를 경매 목록으로 설명해 보세요.

offset은 "앞에서 40개를 버리고 20개"입니다. 사용자가 2페이지를 읽는 사이 새 경매 3건이 등록되면(마감 임박순이면 순서까지 바뀌면) 3페이지의 시작점이 3칸 밀려, 이미 본 항목이 다시 나오고 새 항목 3건은 건너뛰어집니다. 커서는 "이 항목(마감 시각, id) 다음부터"라 앞에 뭐가 끼어들든 이어서 읽습니다. 덤으로 OFFSET 100000은 10만 행을 세고 버리지만 WHERE (ends_at, id) > (…)는 인덱스로 바로 점프하므로 깊은 페이지도 같은 속도입니다. 대신 "3페이지로 바로 가기"는 못 합니다 — 무한 스크롤 UI에는 문제가 안 되고, 관리자 표처럼 점프가 필요하면 offset을 따로 둡니다.

Q 커서에 ends_at만 담고 id를 빼면 어떤 버그가 생기나요? 테스트의 어느 부분이 그걸 잡나요?

마감 시각이 같은 행이 페이지 경계에 걸릴 때 문제가 납니다. 시드에는 같은 시각이 5건씩 있는데 limit이 10이면 1페이지의 마지막 항목과 2페이지의 첫 항목이 같은 시각일 수 있습니다. WHERE ends_at > 커서면 같은 시각의 나머지 행이 통째로 사라지고(누락), >=면 1페이지 끝에서 본 행이 2페이지에 다시 나옵니다(중복). (ends_at, id) 쌍으로 비교하면 같은 시각 안에서도 id로 "다음"이 정해집니다. test_page_walk_covers_every_item_once가 25건의 id 집합이 정확히 한 번씩 나오는지 검사하고, test_ending_soon_is_sorted_by_ends_at_then_id가 페이지를 이어 붙였을 때 (ends_at, id)가 단조 증가하는지 검사합니다.

Q async 세션에서 auction.seller.nickname을 그냥 읽으면 무슨 일이 생기고, 그게 왜 오히려 좋은 점인가요?

MissingGreenlet 예외가 납니다. 동기 SQLAlchemy는 속성에 접근하는 순간 lazy load SELECT를 몰래 보내지만, async 드라이버는 await 없이 I/O를 할 수 없어서 그 자리에서 실패합니다. 불편해 보이지만, 덕분에 N+1이 조용히 생기는 일이 없습니다 — 연관 객체가 필요하면 selectinload(Auction.seller)처럼 쿼리 시점에 미리 선언해야 하고, 그 선언을 보면 쿼리가 몇 번 나갈지 읽힙니다. 정말 한 건만 늦게 가져와야 하면 await db.run_sync(lambda s: a.seller)나 await db.refresh(a, ["seller"])로 명시적으로 합니다. 반복문 안에서 그러면 N+1이 되는데, 그때는 코드에 그 반복문이 눈에 보이니 리뷰에서 잡힙니다.
