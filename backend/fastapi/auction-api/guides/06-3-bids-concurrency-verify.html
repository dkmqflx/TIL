FOR UPDATE 줄서기 — Postgres 안에서 직접 보기

bash터미널 2
echo "=== FOR UPDATE 줄서기 (psql 두 세션)"
docker compose exec db psql -U auction -d auction -q -c \
  "BEGIN; SELECT current_price FROM auctions WHERE id='$A' FOR UPDATE; SELECT pg_sleep(5); COMMIT;" > /dev/null & P1=$!
sleep 1
( S=$(date +%s); docker compose exec db psql -U auction -d auction -t -c \
    "SELECT current_price FROM auctions WHERE id='$A' FOR UPDATE"; echo "세션2: $(( $(date +%s) - S ))초 기다림" ) & P2=$!
sleep 1
docker compose exec db psql -U auction -d auction -c \
  "SELECT state, wait_event_type, wait_event, left(query, 34) AS query FROM pg_stat_activity WHERE query LIKE '%FOR UPDATE' AND pid <> pg_backend_pid() ORDER BY backend_start"
wait $P1 $P2
#  state  | wait_event_type |  wait_event   |               query
# --------+-----------------+---------------+------------------------------------
#  active | Lock            | transactionid | SELECT current_price FROM auctions
# (1 row)
#
#          40000
#
# 세션2: 4초 기다림        ← 세션1 이 pg_sleep(5) 로 락을 쥔 동안 세션2 는 Lock 상태로 대기

함정 & 실무 팁

① 잠그는 건 auctions 행 하나다. bids에 INSERT하는 것 자체는 경쟁이 아닙니다(행이 새로 생길 뿐). 경쟁은 "현재가·입찰 수라는 하나의 행을 읽고 쓰는 것"이고, 그 행만 잠그면 다른 경매는 전혀 방해받지 않습니다. 잠글 대상은 "내가 지키려는 불변식이 사는 행"입니다.
② FOR UPDATE는 갱신과 같은 트랜잭션 안에 있어야 한다. 잠그고 커밋한 뒤 다른 트랜잭션에서 UPDATE하면 락은 이미 풀린 뒤라 아무 효과가 없습니다. 우리 코드는 get_for_update → 검사 → 갱신 → commit이 한 세션·한 트랜잭션입니다. 그리고 populate_existing=True를 기억하세요 — 같은 세션이 그 행을 먼저 읽어 둔 적이 있으면 락을 기다렸다 받아도 옛 객체를 돌려주는 SQLAlchemy의 identity map 동작 때문입니다.
③ 데드락은 "두 행을 서로 반대 순서로" 잠글 때 난다. A가 경매1→경매2, B가 경매2→경매1 순으로 잠그면 서로 기다리다 Postgres가 한쪽을 죽입니다(deadlock detected). 우리는 트랜잭션당 행 하나만 잠그니 안전합니다. 나중에 "입찰자 지갑도 잠가야" 한다면 항상 같은 순서(예: 경매 → 지갑)로 잠그는 규칙을 정하세요.
④ 격리 수준은 기본(READ COMMITTED)으로 충분하다. "SERIALIZABLE로 올려야 하지 않나?" — 우리는 판단의 근거가 되는 행을 잠근 뒤 읽으므로, 그 값은 커밋까지 아무도 못 바꿉니다. 격리 수준을 올리면 락 없이도 충돌을 감지해 주지만(실패 → 재시도), 충돌이 잦은 경매에서는 재시도 폭주가 됩니다. 락으로 예방하는 쪽이 단순합니다.
비관적 락 (FOR UPDATE) — 이번 단계낙관적 락 (version 비교)
방식먼저 잠그고 읽는다. 뒤에 온 트랜잭션은 줄을 선다잠그지 않고 읽는다. 쓸 때 UPDATE … WHERE version = :읽었던값, 0행이면 다시
맞는 상황충돌이 잦다(경매 마감 직전, 선착순, 재고 1개)충돌이 드물다(내 프로필 수정, 관리자 두 명이 가끔 같은 글 편집)
비용줄 서는 동안 커넥션을 쥔다 → 풀 크기·lock_timeout 신경재시도 루프를 직접 짜야 하고, 실패한 요청은 일을 두 번 한다
우리 코드get_for_update + 한 트랜잭션auctions.version이 재료. 4단계부터 갱신마다 +1 해 둔 이유

⑤ rate limit 키의 함정 세 가지. (1) 거절된 요청도 센다 — 실행 예에서 carol은 422를 한 번 받았는데도 그게 카운트에 들어가 3건 뒤에 429가 났습니다. 의도한 동작입니다(스팸은 대부분 거절되는 요청이니까요). (2) 초 경계 — …:41.999와 …:42.000은 다른 키라 한도가 순간적으로 2배까지 열립니다. 정확히 하려면 슬라이딩 윈도우(Redis sorted set)나 토큰 버킷을 쓰는데, 입찰 스팸 방지 정도면 고정 창으로 충분합니다. (3) 서버 시계 — 워커가 여러 대여도 키는 Redis 하나에 모이므로 합산됩니다. 단, 서버들 시계가 어긋나면 초가 어긋납니다(NTP).
⑥ 세션 하나를 코루틴 여러 개가 나눠 쓰면 안 된다. 동시성 테스트에서 코루틴마다 async with SessionLocal()을 새로 여는 이유입니다. AsyncSession은 동시 사용이 안전하지 않고(한 커넥션에 한 번에 한 문장), 무엇보다 세션 하나 = 커넥션 하나 = 트랜잭션 하나라서 "동시"가 아예 성립하지 않습니다. 실제 서버에서는 요청마다 get_db가 세션을 새로 만드니 자연히 지켜집니다.
⑦ 락이 풀리는 순간은 commit(또는 롤백)이지 flush가 아니다. bid_repo.add의 flush()는 INSERT를 DB에 보내지만 트랜잭션은 계속 열려 있고 락도 그대로입니다. 그래서 서비스가 커밋을 책임집니다(3단계부터의 규칙). 예외로 빠져나가면 get_db의 async with가 세션을 닫으며 롤백 → 락 해제. 커밋 전에 오래 걸리는 일(외부 API 호출 등)을 넣으면 그동안 모든 입찰이 줄을 섭니다 — 9단계에서 외부 호출은 트랜잭션 밖으로 뺍니다.
⑧ 시간에 기대는 코드는 시계를 주입한다. _now()를 함수로 빼 둔 덕에 rate limit 테스트가 monkeypatch.setattr(bid_service, "_now", lambda: frozen)으로 결정적이 됐습니다. 스나이핑 테스트는 실제 시계를 쓰지만 "10초 뒤 마감"이라 창(30초) 안에 넉넉히 들어갑니다. 설정값도 monkeypatch.setattr(get_settings(), ...)로 바꿀 수 있는 건 lru_cache가 같은 객체를 돌려주기 때문입니다.
⑨ 커밋하는 테스트는 뒷정리와 격리가 전부다. TRUNCATE bids, payments, auctions, users CASCADE — FK 순서를 생각하지 않아도 되게 한 문장에 전부 적고 CASCADE. 이 테스트는 db_session(롤백 fixture)을 받지 않습니다 — 받으면 그 트랜잭션이 커넥션 하나를 쥐고 있어 헷갈립니다. 커넥션 풀은 기본 5 + overflow 10 = 15개라 50개 코루틴 중 35개는 풀에서 순서를 기다립니다(기본 pool_timeout 30초 안에 끝남). 풀보다 많이 동시에 돌리는 게 오히려 현실적입니다.
⑩ 마감이 지났는데 status가 active인 몇 초. 8단계 워커가 1초마다 닫지만 그 사이 입찰이 들어올 수 있습니다. 그래서 서비스는 status만 보지 않고 now >= ends_at도 봅니다. 워커가 닫을 때도 같은 행을 FOR UPDATE로 잠그므로(SKIP LOCKED 버전), "마감 처리 중에 입찰이 끼어드는" 일은 락이 막아 줍니다.

Q 락 없이 50명이 동시에 입찰하면 정확히 어떤 값이 어떻게 깨지나요? 실험 출력으로 설명해 보세요.

세 가지가 깨집니다. (1) current_price가 최고 입찰가보다 낮을 수 있다 — 실험에서 받아들인 최고가는 59,000인데 현재가는 50,000이었습니다. 둘 다 옛 현재가를 읽고 판단한 뒤 59,000이 먼저, 50,000이 나중에 커밋해 덮어쓴 것입니다. (2) bid_count가 bids 행 수보다 적다 — 여러 트랜잭션이 같은 bid_count를 읽고 각자 +1을 쓰니 증가분이 사라집니다(lost update). (3) 같은 금액을 여러 명이 "성공"한다 — 7명이 전부 "입찰 0건, 시작가 10,000"을 읽고 통과했습니다. 공통 원인은 "읽기와 쓰기 사이에 다른 트랜잭션의 쓰기가 끼어듦"이고, FOR UPDATE는 읽는 순간부터 커밋까지 그 행에 아무도 못 끼어들게 해서 셋을 한 번에 막습니다.

Q 비관적 락 대신 version으로 낙관적 락을 쓰면 코드가 어떻게 달라지고, 어떤 서비스에서는 그게 더 나은가요?

잠그지 않고 읽은 뒤, 쓸 때 UPDATE … WHERE id = :id AND version = :읽었던값으로 "내가 읽은 뒤 아무도 안 바꿨나"를 조건에 넣습니다. 바뀌었으면 0행이 갱신되고, 그때 409를 돌려주거나 처음부터 재시도합니다. 줄을 서지 않으니 커넥션을 쥐고 기다리는 시간이 없고, 충돌이 드문 곳(프로필 수정, 문서 편집, 관리자 설정)에서는 이게 가볍습니다. 반대로 경매 마감 직전처럼 수십 명이 같은 행을 두드리는 곳에서는 한 명 빼고 전부 실패 → 재시도 → 또 한 명 빼고 실패… 로 일이 몇 배가 됩니다. 규칙: 충돌이 잦으면 비관적, 드물면 낙관적. 우리 auctions.version은 이미 갱신마다 +1 하고 있으니 나중에 바꾸고 싶으면 서비스만 손보면 됩니다.

Q rate limit 검사를 락 뒤에 두면 무엇이 문제이고, 거절된 입찰까지 세는 게 맞나요?

락 뒤에 두면 스팸 요청이 먼저 행을 잠근 채 429를 받고 롤백합니다. 그동안 정상 입찰은 줄을 섭니다 — 한도를 막는 코드가 오히려 다른 사람의 입찰을 늦춥니다. Redis 검사는 DB 트랜잭션과 무관하게 밀리초에 끝나니 맨 앞에 두는 게 맞습니다. 거절된 요청을 세는 것도 의도입니다: rate limit의 목적은 "성공 횟수 제한"이 아니라 "서버를 두드리는 횟수 제한"이고, 스팸은 대부분 거절되는 요청입니다. 다만 UI에서 정상 사용자가 422를 받고 곧바로 다시 시도하는 흐름이 있으니 한도(초당 5)는 그걸 감안해 넉넉히 잡습니다. 실행 예에서 carol이 422 한 번 뒤 3건 만에 429를 받은 것이 이 동작입니다.
