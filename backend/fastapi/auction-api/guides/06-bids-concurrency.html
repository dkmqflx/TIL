6단계 — 입찰과 동시성

이 프로젝트의 심장입니다. POST /auctions/{id}/bids가 네 가지 규칙(본인 금지 · active만 · 최소 금액 · 마감 직전 연장)을 지키게 만들고, 50명이 같은 순간에 입찰해도 현재가와 입찰 수가 한 치도 어긋나지 않는다는 것을 테스트로 증명합니다. 무기는 SELECT … FOR UPDATE 한 줄입니다. 그리고 그 한 줄을 지우면 무엇이 깨지는지도 직접 봅니다.

한 줄 요약. 이 문서를 끝내면 uv run pytest -q가 59 passed를 찍고(그중 동시 입찰 테스트 2개), with_for_update() 한 줄을 지우고 다시 돌리면 current_price 50000 != 59000 같은 lost update가 눈앞에서 재현되며, psql 두 창으로 한쪽이 잠근 행을 다른 쪽이 Lock / transactionid 상태로 기다리는 것을 pg_stat_activity에서 확인합니다.

학습 목표

  • "읽고 → 판단하고 → 쓰는" 사이에 다른 요청이 끼어들면 무엇이 깨지는지(lost update) 설명할 수 있다
  • SELECT … FOR UPDATE(비관적 락)로 경매 행 하나를 잠가 입찰을 한 줄로 세운다
  • 비관적 락과 낙관적 락(version)의 차이와 각각이 맞는 상황을 안다
  • Redis INCR로 사용자별 초당 입찰 횟수를 제한한다
  • 롤백 fixture로는 동시성을 테스트할 수 없는 이유를 알고, 실제 커밋 세션 50개 + asyncio.gather로 증명한다
  • 시간에 의존하는 규칙(스나이핑 연장·rate limit)을 테스트에서 시계를 멈춰 결정적으로 검증한다

이 단계의 목표

4~5단계까지의 경매는 구경만 할 수 있었습니다. 이번에는 돈을 겁니다. 끝나면 POST /auctions/{id}/bids에 {"amount": 11000}을 보내면 규칙에 맞을 때만 201이 오고, 응답에는 내 입찰과 함께 경매의 바뀐 current_price·bid_count·ends_at·version이 실립니다. GET /auctions/{id}/bids로 누구나 입찰 내역을 볼 수 있습니다.

왜 필요한가 — 실무 맥락

경매 서비스가 망하는 방법은 하나입니다. "내가 더 높게 불렀는데 낙찰자가 딴 사람" — 이 문의가 한 번이라도 들어오면 신뢰는 끝입니다. 그런데 그 사고는 코드가 틀려서가 아니라 동시에 실행돼서 납니다.

입찰 처리는 세 동작입니다. 현재가를 읽고, 내 금액이 충분한지 판단하고, 현재가를 내 금액으로 씁니다. 혼자 있을 땐 완벽합니다. 문제는 bob과 carol이 0.01초 차이로 들어왔을 때입니다. 둘 다 현재가 10,000을 읽고, bob은 11,000·carol은 12,000이 충분하다고 판단하고, bob이 11,000을 쓴 직후 carol이 12,000을 씁니다 — 여기까진 운 좋게 맞습니다. 순서가 반대면? carol이 12,000을 쓴 뒤 bob이 11,000을 덮어씁니다. 현재가 11,000, 그런데 bids 테이블엔 12,000이 있습니다. bid_count는 둘 다 0을 읽어 1을 썼으니 1입니다. 행은 2개인데. 이것이 lost update이고, 부하 테스트 없이는 개발 PC에서 절대 안 보입니다.

4단계에서 4주차 내용을 떠올리면 "async라서 한 번에 하나씩 도는 거 아닌가?" 싶을 수 있습니다. 이벤트 루프는 파이썬 코드를 한 번에 하나만 돌리지만, await db.execute(...)에서 멈춰 있는 동안 다른 요청의 코드가 돌아갑니다. 읽기와 쓰기 사이에 await가 있으면 그 사이에 누가 끼어듭니다. 게다가 10단계에서 uvicorn 워커를 여러 개 띄우면 프로세스 자체가 여럿입니다. 파이썬 쪽에서 막을 방법은 없고, DB에 부탁해야 합니다.

Postgres에게 부탁하는 문장이 SELECT … FOR UPDATE입니다. "이 행은 내 트랜잭션이 끝날 때까지 나만 만진다" — 같은 행을 FOR UPDATE로 읽으려는 다른 트랜잭션은 줄을 섭니다. 내가 커밋하면 다음 사람이 들어오는데, 그 사람은 내가 바꾼 현재가를 봅니다. 읽기·판단·쓰기가 한 덩어리가 됩니다. 이 단계는 그 한 줄을 어디에 두는지, 왜 그 자리인지, 그리고 없으면 정말 깨지는지를 다룹니다.

실무에서 이 패턴이 나오는 곳. 재고 차감(마지막 1개를 두 명이 동시에 주문), 포인트 사용(잔액 1,000인데 900짜리 두 번), 좌석 예약, 쿠폰 발급 한도, 선착순 이벤트. 전부 "읽고 판단하고 쓰기"이고 전부 같은 답입니다. 면접에서 "동시성 처리 경험"을 물으면 이 단계 이야기를 하면 됩니다.

비유 — 은행 창구 번호표

은행 창구의 번호표. 통장 하나에 두 사람이 동시에 입금하러 왔다고 해 봅시다. 창구 직원이 둘을 동시에 받으면, 둘 다 "잔액 10만 원"을 보고 각자 더한 값을 적어 넣다가 한쪽 입금이 사라집니다. 그래서 은행은 번호표를 뽑게 합니다. 1번이 창구에서 통장을 만지는 동안 2번은 의자에 앉아 기다리고, 1번이 끝나면(커밋) 2번이 1번이 갱신한 잔액을 보고 시작합니다. SELECT … FOR UPDATE가 번호표이고, 트랜잭션이 "창구에 앉아 있는 시간"이며, commit이 자리를 비워 주는 순간입니다. 이 방식을 비관적 락이라고 부릅니다 — "분명 누가 동시에 올 거야"라고 비관하고 미리 줄을 세우니까요.

낙관적 락은 반대입니다. 번호표 없이 각자 통장을 복사해 가서 계산하고, 돌려놓을 때 "내가 복사해 간 뒤로 아무도 안 건드렸지?"를 확인합니다. 통장에 적힌 판(version) 번호가 그때 그대로면 덮어쓰고, 바뀌었으면 처음부터 다시 합니다. 우리 auctions.version 컬럼이 그 판 번호입니다. 동시에 오는 사람이 드물면 이게 더 빠르지만, 경매 마감 직전처럼 다들 몰려오는 곳에서는 "다시 하세요"가 폭주합니다. 그래서 입찰은 비관적 락으로 갑니다.

스나이핑 연장은 경매사의 룰입니다. 실제 경매장에서 "마감!" 직전에 누가 손을 들면 경매사는 곧바로 망치를 내리치지 않고 "30초 더 받겠습니다"라고 합니다. 마지막 0.1초에 입찰해서 아무도 대응 못 하게 하는 스나이핑을 막기 위해서입니다. 규칙 4가 그것입니다: 마감 30초 이내의 입찰은 마감을 30초 뒤로 밉니다.

rate limit은 창구 앞의 경비원입니다. 한 사람이 1초에 스무 번 번호표를 뽑으면 다른 손님이 영영 창구에 못 갑니다. 그래서 경비원이 번호표 기계 앞에서 "초당 5장까지"를 셉니다. 락(번호표)을 잡기 전에 거르는 게 핵심입니다 — 스팸이 락을 쥔 채 줄을 세우면 안 되니까요.

설계 그림

첫 그림은 두 입찰이 같은 경매 행을 두고 만나는 장면입니다. bob의 트랜잭션이 FOR UPDATE로 행을 잠근 순간부터 커밋까지, carol의 FOR UPDATE는 Postgres 안에서 멈춰 있습니다(pg_stat_activity에 wait_event_type = Lock으로 보입니다). bob이 커밋하면 carol이 깨어나는데, 이때 carol이 받는 행은 bob이 갱신한 뒤의 값입니다. carol의 12,000은 "현재가 11,000 + 단위 1,000 = 12,000 이상"이라 통과하고, 만약 carol이 11,500을 냈다면 BID_TOO_LOW로 거절됩니다. 락 없이는 둘 다 10,000을 기준으로 판단해 둘 다 통과했을 겁니다.

둘째 그림은 서비스 함수 안의 순서입니다. 순서가 곧 설계입니다. rate limit은 락 앞에(스팸이 락을 쥐지 않게), 존재·상태·본인·금액 검사는 락 뒤에(잠근 뒤의 값으로 판단해야 의미가 있으니), 갱신과 INSERT는 검사를 다 통과한 뒤에, 그리고 commit이 락을 푸는 유일한 순간입니다. 예외로 빠져나가면 세션이 닫히며 롤백되고 락도 풀립니다.

왜 bids 테이블이 아니라 auctions 행을 잠그나. 지켜야 할 것은 "경매 하나의 현재가·입찰 수"라는 한 행의 일관성입니다. 그 행을 잠그면 그 경매에 대한 입찰은 자연히 직렬화되고, 다른 경매의 입찰은 전혀 방해받지 않습니다. 테이블 전체를 잠그면(LOCK TABLE) 모든 경매가 한 줄에 서게 됩니다.

1. pyproject.toml — commits 마커 등록

pytest는 모르는 마커를 쓰면 경고를 냅니다. 이름과 설명을 등록해 두면 uv run pytest -m commits로 동시성 테스트만 골라 돌릴 수 있고, 반대로 -m "not commits"로 뺄 수도 있습니다(CI에서 빠른 단계/느린 단계를 나눌 때 씁니다). [tool.pytest.ini_options] 섹션 전체를 아래로 바꿉니다 — 맨 아래 markers 세 줄이 추가됐습니다.

2. tests/test_bids.py — 규칙 하나에 테스트 하나

위에서부터 규칙 3(금액), 규칙 1·2(누가·언제), 규칙 4(스나이핑), rate limit, 조회 순입니다. 두 가지를 눈여겨보세요. test_past_ends_at_rejects_bids_even_if_status_still_active는 "상태는 active인데 마감 시각은 지난" 경매입니다 — 8단계 워커가 닫기 전 몇 초 동안 실제로 생기는 상태라 서비스가 시각까지 봐야 합니다. 그리고 rate limit 테스트는 monkeypatch로 시계를 멈추고 한도를 2로 줄입니다. "빠르게 세 번 보내면 되지 않나" 싶지만, 세 요청이 초 경계(…:41.999 → …:42.000)에 걸치면 카운터가 새로 시작해 가끔 실패하는 flaky 테스트가 됩니다. 시간에 기대는 테스트는 시간을 통제해야 합니다.

pythontests/test_bids.py
"""입찰 규칙 테스트 — 롤백 세션 위에서 규칙 하나에 테스트 하나.

'여러 명이 동시에' 는 여기서 다루지 않는다 → test_bids_concurrency.py (실제 커밋 필요).
"""

import uuid
from datetime import UTC, datetime, timedelta

from httpx2 import AsyncClient
from sqlalchemy.ext.asyncio import AsyncSession

from app.core.config import get_settings
from app.models import AuctionStatus, User
from app.services import bid as bid_service
from tests.factories import create_auction, create_user, login_headers


async def _people(db: AsyncSession) -> tuple[User, User]:
    seller = await create_user(db, email="seller@example.com", nickname="판매자")
    bidder = await create_user(db, email="bidder@example.com", nickname="입찰자")
    return seller, bidder


async def _bid(client: AsyncClient, auction_id: uuid.UUID, amount: int, headers: dict):
    return await client.post(
        f"/auctions/{auction_id}/bids", json={"amount": amount}, headers=headers
    )


# ── 규칙 3: 금액 ──────────────────────────────────────────────────────


async def test_first_bid_at_starting_price(client: AsyncClient, db_session: AsyncSession):
    seller, bidder = await _people(db_session)
    auction = await create_auction(db_session, seller)  # 시작가 10,000 · 입찰 0건
    headers = await login_headers(client, "bidder@example.com")

    res = await _bid(client, auction.id, 10_000, headers)

    assert res.status_code == 201, res.text
    body = res.json()
    assert body["bid"]["amount"] == 10_000
    assert body["bid"]["bidder_id"] == str(bidder.id)
    assert body["current_price"] == 10_000
    assert body["bid_count"] == 1
    assert body["version"] == 1  # 경매 행이 바뀌었으니 +1


async def test_first_bid_below_starting_price_is_rejected(
    client: AsyncClient, db_session: AsyncSession
):
    seller, _ = await _people(db_session)
    auction = await create_auction(db_session, seller)
    headers = await login_headers(client, "bidder@example.com")

    res = await _bid(client, auction.id, 9_999, headers)

    assert res.status_code == 422
    assert res.json()["code"] == "BID_TOO_LOW"
    assert "10,000" in res.json()["message"]  # 최소 금액을 알려 준다


async def test_next_bid_must_exceed_current_by_min_increment(
    client: AsyncClient, db_session: AsyncSession
):
    seller, _ = await _people(db_session)
    auction = await create_auction(db_session, seller, current_price=12_000, bid_count=1)
    headers = await login_headers(client, "bidder@example.com")

    too_low = await _bid(client, auction.id, 12_500, headers)  # 12,000 + 1,000 = 13,000 미만
    assert too_low.status_code == 422
    assert "13,000" in too_low.json()["message"]

    ok = await _bid(client, auction.id, 13_000, headers)
    assert ok.status_code == 201
    assert ok.json()["current_price"] == 13_000
    assert ok.json()["bid_count"] == 2

3. tests/test_bids_concurrency.py — 진짜로 동시에

롤백 fixture(db_session)는 커넥션 하나에 트랜잭션 하나입니다. 동시성은 "서로 다른 커넥션이 같은 행을 두고 경쟁"하는 이야기라 그 위에서는 재현이 안 됩니다. 그래서 이 파일은 SessionLocal()로 세션을 직접 열어 판매자·경매·입찰자 50명을 정말 커밋하고, 코루틴 50개가 각자 세션 하나씩 들고 asyncio.gather로 동시에 place_bid를 부릅니다. 끝나면 TRUNCATE … CASCADE로 직접 치웁니다. 금액은 시작가 + i × 1,000(i = 0…49)을 섞어서 배정하고(시드 42로 고정해 재현 가능), 결과는 세 가지 등식으로 확인합니다: bids 테이블의 금액 목록 == 서비스가 받아들였다고 돌려준 목록, current_price == 그중 최댓값, bid_count == version == 받아들인 건수. 두 번째 테스트는 50명이 같은 금액을 내는 극단적 경우로, 정확히 한 명만 성공해야 합니다.

"""동시 입찰 테스트 — 롤백 세션이 아니라 **실제 커밋** 을 쓴다 (@pytest.mark.commits).

왜 롤백 세션으로는 안 되나: 롤백 fixture 는 커넥션 하나·트랜잭션 하나다. 동시성은
'서로 다른 커넥션이 같은 행을 두고 경쟁' 하는 상황이라, 세션(=커넥션) 을 여러 개 띄워
정말로 커밋해야 한다. 그래서 끝나면 TRUNCATE 로 직접 치운다.
"""

import asyncio
import random

import pytest
from redis.asyncio import Redis
from sqlalchemy import select, text

from app.core.db import SessionLocal
from app.core.exceptions import BidTooLowError
from app.models import Auction, Bid, User
from app.services import bid as bid_service
from tests.factories import create_auction, create_user

pytestmark = pytest.mark.commits

BIDDERS = 50


@pytest.fixture
async def committed_auction(redis: Redis):
    """판매자 1 + 입찰자 50 + active 경매 1 을 진짜로 커밋해 두고, 끝나면 테이블을 비운다."""
    async with SessionLocal() as db:
        seller = await create_user(db, nickname="판매자")
        auction = await create_auction(db, seller)
        bidders = [await create_user(db, nickname=f"입찰자{i}") for i in range(BIDDERS)]
        await db.commit()
    yield auction, bidders
    async with SessionLocal() as db:
        await db.execute(text("TRUNCATE bids, payments, auctions, users CASCADE"))
        await db.commit()


async def _bid_in_own_session(redis: Redis, bidder: User, auction_id, amount: int) -> int | None:
    """코루틴 하나 = 세션(커넥션) 하나. 실제 요청 하나가 그렇듯이."""
    async with SessionLocal() as db:
        try:
            await bid_service.place_bid(db, redis, bidder, auction_id, amount)
            return amount
        except BidTooLowError:
            return None


async def _fresh(auction_id) -> tuple[Auction, list[int]]:
    async with SessionLocal() as db:
        auction = await db.get(Auction, auction_id)
        assert auction is not None
        rows = await db.scalars(select(Bid.amount).where(Bid.auction_id == auction_id))
        return auction, sorted(rows.all())


async def test_50_concurrent_bids_keep_price_and_count_consistent(committed_auction, redis: Redis):
    auction, bidders = committed_auction
    amounts = [auction.starting_price + i * auction.min_increment for i in range(BIDDERS)]
    random.Random(42).shuffle(amounts)  # 도착 순서를 뒤섞는다 (재현 가능하게 시드 고정)

    pairs = zip(bidders, amounts, strict=True)
    results = await asyncio.gather(
        *(_bid_in_own_session(redis, b, auction.id, a) for b, a in pairs)
    )
    accepted = sorted(a for a in results if a is not None)

    fresh, rows = await _fresh(auction.id)
    assert accepted, "최소 한 건은 받아들여져야 한다"
    assert rows == accepted  # bids 테이블 = 서비스가 받아들였다고 말한 것
    assert fresh.current_price == max(accepted)  # 현재가 = 받아들인 것 중 최댓값
    assert fresh.bid_count == len(accepted)  # 락 없이 lost update 가 나면 여기서 깨진다
    assert fresh.version == len(accepted)


async def test_same_amount_from_50_bidders_accepts_exactly_one(committed_auction, redis: Redis):
    auction, bidders = committed_auction

    results = await asyncio.gather(
        *(_bid_in_own_session(redis, b, auction.id, auction.starting_price) for b in bidders)
    )

    assert results.count(auction.starting_price) == 1
    assert results.count(None) == BIDDERS - 1
    fresh, rows = await _fresh(auction.id)
    assert fresh.bid_count == 1 and len(rows) == 1
    assert fresh.current_price == auction.starting_price

6. app/core/exceptions.py — 429 부모와 입찰 예외 4개

4단계 계층에 status 부모를 하나 더 얹습니다: TooManyRequestsError(429). 그리고 입찰 예외 4개는 각자 알맞은 부모 밑에 — 상태가 안 맞으면 409(InvalidStateError), 자기 경매면 403, 금액이 낮으면 422(UnprocessableError, 형식은 맞고 의미가 틀린 경우), 너무 잦으면 429. 새 클래스는 code와 message만 정하면 status와 응답 껍데기는 부모가 처리합니다. """도메인 예외와 표준 에러 응답.

서비스 계층은 HTTP 를 모른다 — HTTPException 대신 여기 있는 AppError 계열만 던진다.
라우터 바깥의 핸들러가 AppError 를 {"code", "message"} 형태의 JSON 으로 번역한다.

계층
    AppError (400)
    ├── UnauthorizedError (401)

    ├── ConflictError (409)       ── EmailAlreadyExistsError, AuctionHasBidsError

async def app_error_handler(request: Request, exc: AppError) -> JSONResponse:

async def validation_error_handler(request: Request, exc: RequestValidationError) -> JSONResponse:
    """Pydantic 검증 실패(422). 기본 응답은 {"detail": [...]} 인데, 우리 껍데기로 감싸고
    필드별 상세는 "errors" 에 넣는다 — 프론트가 입력칸 옆에 메시지를 보여줄 때 쓴다.
    (loc / msg / type 만 남긴다. 기본 목록에 딸려 오는 input·ctx 는 사용자 입력을 되돌려 주거나
    파이썬 객체라 JSON 으로 못 만드는 경우가 있어 뺀다.)"""
    errors = [{"loc": e["loc"], "msg": e["msg"], "type": e["type"]} for e in exc.errors()]
    return JSONResponse(
        status_code=status.HTTP_422_UNPROCESSABLE_CONTENT,
        content={
            "code": "VALIDATION_ERROR",
            "message": "요청 값이 올바르지 않습니다",
            "errors": errors,
        },
    )


async def http_exception_handler(request: Request, exc: StarletteHTTPException) -> JSONResponse:

    )

7. app/repositories/auction.py — get_for_update

이 단계의 한 줄입니다. select(...).with_for_update()가 SQL로는 SELECT … FROM auctions WHERE id = $1 FOR UPDATE. 옵션 하나 더 — populate_existing=True. SQLAlchemy 세션은 한 번 읽은 행을 identity map에 기억해 두고, 같은 행을 다시 SELECT해도 이미 있는 파이썬 객체를 그대로 돌려줍니다(속성을 덮어쓰지 않습니다). 락을 기다리는 동안 다른 트랜잭션이 현재가를 바꿨는데 내 객체는 옛 값이면, 락을 건 의미가 없습니다. populate_existing은 "이번 결과로 객체를 덮어써라"입니다. 지금 코드에서는 요청마다 새 세션이라 실제로 걸릴 일은 없지만, 나중에 누가 같은 세션에서 get()을 먼저 부르는 순간 조용히 깨지는 함정이라 처음부터 막아 둡니다.

"""auctions 테이블 접근. 쿼리만 있고 규칙은 없다."""

import uuid
from datetime import datetime

from sqlalchemy import select, tuple_
from sqlalchemy.ext.asyncio import AsyncSession
from sqlalchemy.orm import selectinload

from app.models import Auction, AuctionCategory, AuctionStatus


async def get(db: AsyncSession, auction_id: uuid.UUID) -> Auction | None:
    return await db.get(Auction, auction_id)


async def get_for_update(db: AsyncSession, auction_id: uuid.UUID) -> Auction | None:
    """행 잠금(SELECT … FOR UPDATE). 이 트랜잭션이 커밋/롤백될 때까지 같은 행을 잠그려는
    다른 트랜잭션은 줄을 선다 → '읽고 → 판단하고 → 쓰는' 사이에 아무도 끼어들지 못한다.

    populate_existing: 이 세션이 같은 행을 이미 읽어 둔 적이 있어도 DB 의 최신 값으로 덮어쓴다.
    (락을 기다리는 동안 누가 값을 바꿨을 수 있다 — 옛 값으로 판단하면 락을 건 의미가 없다.)
    """
    stmt = (
        select(Auction)
        .where(Auction.id == auction_id)
        .with_for_update()
        .execution_options(populate_existing=True)
    )
    return await db.scalar(stmt)


async def add(db: AsyncSession, auction: Auction) -> Auction:
    db.add(auction)
    await db.flush()  # INSERT → id / created_at 확보. 커밋은 서비스가 결정한다
    return auction


async def list_page(
    db: AsyncSession,
    *,
    status: AuctionStatus | None = None,
    category: AuctionCategory | None = None,
    min_price: int | None = None,
    max_price: int | None = None,
    sort: str = "ending_soon",
    limit: int = 20,
    after: tuple[datetime, uuid.UUID] | None = None,
    load_seller: bool = True,
) -> list[Auction]:
    """keyset 페이지 한 장. limit+1 건을 가져와 '다음 페이지가 있나' 를 알려 준다.
    (limit 개로 잘라내는 일은 서비스가 한다.)

    정렬 키는 (시각, id) 쌍이다. 시각이 같은 행이 여러 개여도 id 가 순서를 확정하므로
    페이지 경계에서 같은 행이 두 번 나오거나 빠지는 일이 없다.
    """
    key = Auction.ends_at if sort == "ending_soon" else Auction.created_at
    ascending = sort == "ending_soon"

    stmt = select(Auction)
    if status is not None:
        stmt = stmt.where(Auction.status == status)
    if category is not None:
        stmt = stmt.where(Auction.category == category)
    if min_price is not None:
        stmt = stmt.where(Auction.current_price >= min_price)
    if max_price is not None:
        stmt = stmt.where(Auction.current_price <= max_price)

    if after is not None:
        pair = tuple_(key, Auction.id)  # SQL: (ends_at, id) > ($1, $2)  ← 행 비교
        stmt = stmt.where(pair > after if ascending else pair < after)

    if ascending:
        stmt = stmt.order_by(key.asc(), Auction.id.asc())
    else:
        stmt = stmt.order_by(key.desc(), Auction.id.desc())

    if load_seller:
        stmt = stmt.options(selectinload(Auction.seller))  # 판매자는 IN (...) 한 방으로

    result = await db.scalars(stmt.limit(limit + 1))
    return list(result.all())

10. app/services/bid.py — 규칙과 락

위 둘째 그림 그대로입니다. 읽을 때 순서에 주목하세요. _check_rate_limit이 락 앞에 있고, 그 뒤 get_for_update부터 commit까지가 잠긴 구간입니다. _now()를 굳이 함수로 뺀 것은 테스트가 monkeypatch로 시계를 멈추기 위해서입니다. 규칙 2에 now >= auction.ends_at이 있는 이유는 위 테스트 설명에 적었습니다. rate limit 키는 bid:rl:{user_id}:{이번 초} — INCR은 Redis 안에서 원자적이라 같은 초에 요청이 겹쳐 들어와도 정확히 셉니다. 첫 요청일 때(count == 1)만 EXPIRE 2를 걸어 1초짜리 키가 영원히 쌓이지 않게 합니다.

pythonapp/services/bid.py
"""입찰 규칙. HTTP 를 모른다 — 도메인 예외만 던진다.

핵심은 순서다: (rate limit) → **경매 행 잠금** → 규칙 검사 → 갱신 → 커밋.
잠금부터 커밋까지가 한 트랜잭션이라, 그 사이에 다른 입찰은 줄을 서서 기다린다.
그래서 '현재가 + 최소 단위' 를 계산할 때 본 값이 커밋하는 순간까지 그대로다.
"""

import uuid
from datetime import UTC, datetime, timedelta

from redis.asyncio import Redis
from sqlalchemy.ext.asyncio import AsyncSession

from app.core.config import get_settings
from app.core.exceptions import (
    AuctionNotActiveError,
    AuctionNotFoundError,
    BidRateLimitedError,
    BidTooLowError,
    OwnAuctionBidError,
)
from app.models import Auction, AuctionStatus, Bid, User
from app.repositories import auction as auction_repo
from app.repositories import bid as bid_repo


def _now() -> datetime:
    """시계를 함수로 빼 두면 테스트에서 멈추거나 돌릴 수 있다."""
    return datetime.now(UTC)


async def _check_rate_limit(redis: Redis, user_id: uuid.UUID, now: datetime) -> None:
    """사용자별 '이번 1초' 카운터. INCR 는 원자적이라 동시에 들어와도 정확히 센다."""
    key = f"bid:rl:{user_id}:{int(now.timestamp())}"
    count = await redis.incr(key)
    if count == 1:
        await redis.expire(key, 2)  # 1초짜리 키가 영원히 남지 않도록
    if count > get_settings().bid_rate_limit_per_second:
        raise BidRateLimitedError()


def minimum_bid(auction: Auction) -> int:
    """첫 입찰은 시작가 이상, 그 다음부터는 현재가 + 최소 단위 이상."""
    if auction.bid_count == 0:
        return auction.starting_price
    return auction.current_price + auction.min_increment


async def place_bid(
    db: AsyncSession, redis: Redis, bidder: User, auction_id: uuid.UUID, amount: int
) -> tuple[Bid, Auction]:
    settings = get_settings()
    now = _now()

    await _check_rate_limit(redis, bidder.id, now)  # 락을 잡기 *전에* — 스팸이 락을 쥐고 있지 않게

    auction = await auction_repo.get_for_update(db, auction_id)  # ← 여기서부터 줄을 선다
    if auction is None:
        raise AuctionNotFoundError()
    if auction.status != AuctionStatus.ACTIVE or now >= auction.ends_at:
        raise AuctionNotActiveError()
    if auction.seller_id == bidder.id:
        raise OwnAuctionBidError()
    minimum = minimum_bid(auction)
    if amount < minimum:
        raise BidTooLowError(
            f"최소 입찰액은 {minimum:,}원입니다 (현재가 {auction.current_price:,}원)"
        )

    # 규칙 4 — 마감 직전 입찰이면 마감을 늦춘다 (스나이핑 방지)
    if auction.ends_at - now < timedelta(seconds=settings.snipe_window_seconds):
        auction.ends_at = auction.ends_at + timedelta(seconds=settings.snipe_extend_seconds)

    auction.current_price = amount
    auction.bid_count += 1
    auction.version += 1
    bid = Bid(auction_id=auction.id, bidder_id=bidder.id, amount=amount)
    await bid_repo.add(db, bid)

    await db.commit()  # ← 여기서 락이 풀리고, 줄 서 있던 다음 입찰이 '바뀐 현재가' 를 본다
    await db.refresh(bid)
    await db.refresh(auction)
    return bid, auction


async def list_bids(db: AsyncSession, auction_id: uuid.UUID) -> list[Bid]:
    if await auction_repo.get(db, auction_id) is None:
        raise AuctionNotFoundError()
    return await bid_repo.list_by_auction(db, auction_id)

함정 & 실무 팁

① 잠그는 건 auctions 행 하나다. bids에 INSERT하는 것 자체는 경쟁이 아닙니다(행이 새로 생길 뿐). 경쟁은 "현재가·입찰 수라는 하나의 행을 읽고 쓰는 것"이고, 그 행만 잠그면 다른 경매는 전혀 방해받지 않습니다. 잠글 대상은 "내가 지키려는 불변식이 사는 행"입니다.
② FOR UPDATE는 갱신과 같은 트랜잭션 안에 있어야 한다. 잠그고 커밋한 뒤 다른 트랜잭션에서 UPDATE하면 락은 이미 풀린 뒤라 아무 효과가 없습니다. 우리 코드는 get_for_update → 검사 → 갱신 → commit이 한 세션·한 트랜잭션입니다. 그리고 populate_existing=True를 기억하세요 — 같은 세션이 그 행을 먼저 읽어 둔 적이 있으면 락을 기다렸다 받아도 옛 객체를 돌려주는 SQLAlchemy의 identity map 동작 때문입니다.
③ 데드락은 "두 행을 서로 반대 순서로" 잠글 때 난다. A가 경매1→경매2, B가 경매2→경매1 순으로 잠그면 서로 기다리다 Postgres가 한쪽을 죽입니다(deadlock detected). 우리는 트랜잭션당 행 하나만 잠그니 안전합니다. 나중에 "입찰자 지갑도 잠가야" 한다면 항상 같은 순서(예: 경매 → 지갑)로 잠그는 규칙을 정하세요.
④ 격리 수준은 기본(READ COMMITTED)으로 충분하다. "SERIALIZABLE로 올려야 하지 않나?" — 우리는 판단의 근거가 되는 행을 잠근 뒤 읽으므로, 그 값은 커밋까지 아무도 못 바꿉니다. 격리 수준을 올리면 락 없이도 충돌을 감지해 주지만(실패 → 재시도), 충돌이 잦은 경매에서는 재시도 폭주가 됩니다. 락으로 예방하는 쪽이 단순합니다.

⑤ rate limit 키의 함정 세 가지. (1) 거절된 요청도 센다 — 실행 예에서 carol은 422를 한 번 받았는데도 그게 카운트에 들어가 3건 뒤에 429가 났습니다. 의도한 동작입니다(스팸은 대부분 거절되는 요청이니까요). (2) 초 경계 — …:41.999와 …:42.000은 다른 키라 한도가 순간적으로 2배까지 열립니다. 정확히 하려면 슬라이딩 윈도우(Redis sorted set)나 토큰 버킷을 쓰는데, 입찰 스팸 방지 정도면 고정 창으로 충분합니다. (3) 서버 시계 — 워커가 여러 대여도 키는 Redis 하나에 모이므로 합산됩니다. 단, 서버들 시계가 어긋나면 초가 어긋납니다(NTP).
⑥ 세션 하나를 코루틴 여러 개가 나눠 쓰면 안 된다. 동시성 테스트에서 코루틴마다 async with SessionLocal()을 새로 여는 이유입니다. AsyncSession은 동시 사용이 안전하지 않고(한 커넥션에 한 번에 한 문장), 무엇보다 세션 하나 = 커넥션 하나 = 트랜잭션 하나라서 "동시"가 아예 성립하지 않습니다. 실제 서버에서는 요청마다 get_db가 세션을 새로 만드니 자연히 지켜집니다.
⑦ 락이 풀리는 순간은 commit(또는 롤백)이지 flush가 아니다. bid_repo.add의 flush()는 INSERT를 DB에 보내지만 트랜잭션은 계속 열려 있고 락도 그대로입니다. 그래서 서비스가 커밋을 책임집니다(3단계부터의 규칙). 예외로 빠져나가면 get_db의 async with가 세션을 닫으며 롤백 → 락 해제. 커밋 전에 오래 걸리는 일(외부 API 호출 등)을 넣으면 그동안 모든 입찰이 줄을 섭니다 — 9단계에서 외부 호출은 트랜잭션 밖으로 뺍니다.
⑧ 시간에 기대는 코드는 시계를 주입한다. _now()를 함수로 빼 둔 덕에 rate limit 테스트가 monkeypatch.setattr(bid_service, "_now", lambda: frozen)으로 결정적이 됐습니다. 스나이핑 테스트는 실제 시계를 쓰지만 "10초 뒤 마감"이라 창(30초) 안에 넉넉히 들어갑니다. 설정값도 monkeypatch.setattr(get_settings(), ...)로 바꿀 수 있는 건 lru_cache가 같은 객체를 돌려주기 때문입니다.
⑨ 커밋하는 테스트는 뒷정리와 격리가 전부다. TRUNCATE bids, payments, auctions, users CASCADE — FK 순서를 생각하지 않아도 되게 한 문장에 전부 적고 CASCADE. 이 테스트는 db_session(롤백 fixture)을 받지 않습니다 — 받으면 그 트랜잭션이 커넥션 하나를 쥐고 있어 헷갈립니다. 커넥션 풀은 기본 5 + overflow 10 = 15개라 50개 코루틴 중 35개는 풀에서 순서를 기다립니다(기본 pool_timeout 30초 안에 끝남). 풀보다 많이 동시에 돌리는 게 오히려 현실적입니다.
⑩ 마감이 지났는데 status가 active인 몇 초. 8단계 워커가 1초마다 닫지만 그 사이 입찰이 들어올 수 있습니다. 그래서 서비스는 status만 보지 않고 now >= ends_at도 봅니다. 워커가 닫을 때도 같은 행을 FOR UPDATE로 잠그므로(SKIP LOCKED 버전), "마감 처리 중에 입찰이 끼어드는" 일은 락이 막아 줍니다.

Q 락 없이 50명이 동시에 입찰하면 정확히 어떤 값이 어떻게 깨지나요? 실험 출력으로 설명해 보세요.

세 가지가 깨집니다. (1) current_price가 최고 입찰가보다 낮을 수 있다 — 실험에서 받아들인 최고가는 59,000인데 현재가는 50,000이었습니다. 둘 다 옛 현재가를 읽고 판단한 뒤 59,000이 먼저, 50,000이 나중에 커밋해 덮어쓴 것입니다. (2) bid_count가 bids 행 수보다 적다 — 여러 트랜잭션이 같은 bid_count를 읽고 각자 +1을 쓰니 증가분이 사라집니다(lost update). (3) 같은 금액을 여러 명이 "성공"한다 — 7명이 전부 "입찰 0건, 시작가 10,000"을 읽고 통과했습니다. 공통 원인은 "읽기와 쓰기 사이에 다른 트랜잭션의 쓰기가 끼어듦"이고, FOR UPDATE는 읽는 순간부터 커밋까지 그 행에 아무도 못 끼어들게 해서 셋을 한 번에 막습니다.

Q 비관적 락 대신 version으로 낙관적 락을 쓰면 코드가 어떻게 달라지고, 어떤 서비스에서는 그게 더 나은가요?

잠그지 않고 읽은 뒤, 쓸 때 UPDATE … WHERE id = :id AND version = :읽었던값으로 "내가 읽은 뒤 아무도 안 바꿨나"를 조건에 넣습니다. 바뀌었으면 0행이 갱신되고, 그때 409를 돌려주거나 처음부터 재시도합니다. 줄을 서지 않으니 커넥션을 쥐고 기다리는 시간이 없고, 충돌이 드문 곳(프로필 수정, 문서 편집, 관리자 설정)에서는 이게 가볍습니다. 반대로 경매 마감 직전처럼 수십 명이 같은 행을 두드리는 곳에서는 한 명 빼고 전부 실패 → 재시도 → 또 한 명 빼고 실패… 로 일이 몇 배가 됩니다. 규칙: 충돌이 잦으면 비관적, 드물면 낙관적. 우리 auctions.version은 이미 갱신마다 +1 하고 있으니 나중에 바꾸고 싶으면 서비스만 손보면 됩니다.

Q rate limit 검사를 락 뒤에 두면 무엇이 문제이고, 거절된 입찰까지 세는 게 맞나요?

락 뒤에 두면 스팸 요청이 먼저 행을 잠근 채 429를 받고 롤백합니다. 그동안 정상 입찰은 줄을 섭니다 — 한도를 막는 코드가 오히려 다른 사람의 입찰을 늦춥니다. Redis 검사는 DB 트랜잭션과 무관하게 밀리초에 끝나니 맨 앞에 두는 게 맞습니다. 거절된 요청을 세는 것도 의도입니다: rate limit의 목적은 "성공 횟수 제한"이 아니라 "서버를 두드리는 횟수 제한"이고, 스팸은 대부분 거절되는 요청입니다. 다만 UI에서 정상 사용자가 422를 받고 곧바로 다시 시도하는 흐름이 있으니 한도(초당 5)는 그걸 감안해 넉넉히 잡습니다. 실행 예에서 carol이 422 한 번 뒤 3건 만에 429를 받은 것이 이 동작입니다.
