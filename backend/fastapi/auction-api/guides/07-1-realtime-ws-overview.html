7-1 개요와 설계

경매 화면에서 남이 입찰한 순간이 새로고침 없이 보이게 만듭니다. WS /ws/auctions/{id}?token=… 로 구독하면 현재 상태 한 장(snapshot)을 받고, 그 뒤로 입찰이 들어올 때마다 bid_placed 이벤트가 밀려옵니다. 핵심은 "uvicorn 워커가 2개, 4개여도 모든 구독자가 받는다" — 그 일을 Redis Pub/Sub 가 합니다. 그리고 그것을 워커 2개를 실제로 띄워 눈으로 확인합니다.

학습 목표

  • HTTP 요청-응답으로는 안 되는 것(서버가 먼저 말 걸기)과 WebSocket 이 필요한 순간을 설명할 수 있다
  • 서비스가 커밋 뒤에 도메인 이벤트를 발행하고, 발행자는 구독자를 모른다는 Pub/Sub 의 분리를 코드로 안다
  • 프로세스(워커)마다 구독 루프 하나 + 프로세스 로컬 ConnectionManager 구조가 왜 필요한지 그림으로 설명한다
  • 소켓 인증: accept 후 4401/4404 로 닫는 이유(핸드셰이크 403 과의 차이)를 안다
  • TestClient 대신 자식 프로세스 서버 + 실제 WebSocket 클라이언트로 테스트하는 이유와 방법을 안다
  • Redis Pub/Sub 의 한계(유실, at-most-once)와 snapshot 으로 보정하는 패턴을 안다
🎯

이 단계의 목표

6단계까지는 입찰을 보내는 쪽만 있었습니다. 남의 입찰을 보려면 GET /auctions/{id}를 계속 새로고침해야 했죠. 이번 단계가 끝나면 ws://localhost:8000/ws/auctions/{id}?token=… 에 소켓을 하나 열어 두는 것만으로, 누가 입찰하든 {"type":"bid_placed","payload":{"amount":12000,"current_price":12000,"bid_count":2,…}} 가 밀려옵니다. 붙자마자 snapshot 한 장(현재가·입찰 수·마감 시각)을 먼저 받으니 화면을 그리는 데 다른 요청이 필요 없습니다.

그리고 이 단계의 진짜 확인 포인트는 워커 2개입니다. uvicorn --workers 2는 프로세스를 두 개 띄우고, 브라우저마다 어느 프로세스에 붙을지는 운입니다. bob 의 입찰을 1번 워커가 처리했는데 carol 의 소켓은 2번 워커에 있다면? 1번 워커 메모리 속 소켓 목록엔 carol 이 없습니다. 이 문제를 Redis Pub/Sub 가 풀고, 그걸 리스너 4개로 직접 봅니다.

전제. 6단계가 끝나 있어야 합니다. uv run pytest -q → 59 passed, 컨테이너 두 개 (healthy). 새로 설치하는 것은 테스트·CLI 클라이언트용 websockets 하나(dev). 작업 위치는 til/backend/fastapi/auction-api/.

이번 단계에서 만드는 것. 새 파일 7개(core/events.py, ws/manager.py, ws/bridge.py, ws/router.py, static/ws-demo.html, scripts/ws_listen.py, tests/test_ws.py), 손보는 파일 2개(services/bid.py는 커밋 뒤 한 번 발행, main.py는 구독 루프 기동·라우터·정적 파일). 6단계의 규칙·락은 한 글자도 안 바뀝니다 — 실시간은 덧붙이는 층입니다.
🏢

왜 필요한가 — 실무 맥락

경매 화면은 "지금 얼마인가"가 전부입니다. 5초마다 폴링하면 5초 늦은 값을 보여 주고, 마감 30초 전엔 그 5초가 승부를 가릅니다. 폴링 주기를 1초로 줄이면 사용자 1,000명이 초당 1,000번 GET 을 때립니다 — 대부분은 "바뀐 게 없다"는 응답입니다. 서버가 바뀐 순간에만 말해 주는 쪽이 맞고, 그게 WebSocket 입니다(9주차·01).

WebSocket 자체는 9주차에 해 봤습니다. 실무에서 어려운 건 소켓이 아니라 "누가 누구에게 알리나" 입니다. 입찰을 처리한 코드(서비스)가 소켓 목록을 뒤져 직접 send 하면, (1) 서비스가 웹소켓을 알게 되고(계층 위반), (2) 워커가 여럿이면 다른 프로세스의 소켓엔 손이 닿지 않고, (3) 나중에 "입찰 시 Slack 알림"을 붙이려면 서비스를 또 고쳐야 합니다. 그래서 서비스는 "경매 X 에 입찰이 있었다" 만 방송하고 끝냅니다. 누가 듣는지는 모릅니다. 이번 단계엔 웹소켓 중계기가 듣고, 9단계엔 알림이 들을 수 있습니다.

방송 채널이 Redis Pub/Sub 입니다(9주차·02). 이미 3단계부터 붙어 있는 Redis 에 PUBLISH auction:{id} … 한 줄이면 됩니다. 워커마다 PSUBSCRIBE auction:* 로 듣고 있다가 자기 소켓에 뿌리니, 워커 수가 몇이든 같은 코드입니다. 10단계에서 --workers 를 늘려도, 나중에 서버를 두 대로 늘려도 바뀌지 않습니다.

실무에서 같은 모양이 나오는 곳. 채팅방, 주문 상태 추적("배달 중 → 도착"), 협업 문서의 커서, 대시보드의 실시간 지표, 알림 벨. 전부 "어느 프로세스가 사건을 처리했든 관심 있는 모든 소켓에 전달"이고, 전부 브로커(Redis Pub/Sub, Kafka, NATS…)가 가운데 섭니다. 이 단계는 그중 가장 작은 버전입니다.
📻

비유 — 지점 스피커와 공용 방송

지점 스피커와 공용 방송. 은행 지점이 두 곳 있고(워커 2개), 각 지점엔 대기 손님들(소켓)과 천장 스피커(ConnectionManager)가 있습니다. 1지점 창구에서 "통장 잔액이 바뀌었습니다"가 일어나면 1지점 스피커로는 1지점 손님에게만 들립니다. 2지점 손님은 모릅니다. 그래서 본점에 공용 방송 채널(Redis Pub/Sub)을 두고, 지점마다 수신기 하나(bridge 태스크)를 답니다. 창구 직원(서비스)은 일이 끝난 뒤(커밋 뒤) 본점 채널에 한 마디만 하고, 각 지점 수신기가 그걸 받아 자기 지점 스피커로 틀어 줍니다. 창구 직원은 몇 개 지점이 듣는지 모르고, 알 필요도 없습니다.

입장 팔찌. 공연장 객석(경매 방)에 들어오려면 입구에서 팔찌(access 토큰)를 보여야 합니다. 그런데 팔찌가 없다고 입구 문 자체를 안 열어 주면(핸드셰이크 403) 손님은 왜 못 들어가는지 모릅니다. 문은 열어 주되(accept) 바로 "팔찌 없음"(4401)이라고 말하고 내보내는 게 우리 방식입니다. 객석에 앉으면 먼저 지금 무대 상황을 한 장 요약해 줍니다(snapshot). 그 뒤로는 무대에서 일이 날 때마다 스피커로 듣습니다.

공용 방송의 성질. 방송은 그 순간 듣고 있는 사람에게만 들립니다. 화장실에 간 사이의 방송은 다시 틀어 주지 않습니다(Redis Pub/Sub 는 저장하지 않는다). 그래서 객석에 다시 앉을 때마다 요약(snapshot)을 다시 받습니다 — 놓친 방송은 요약으로 메웁니다. "한 건도 놓치면 안 되는" 알림(결제 완료 같은 것)은 방송이 아니라 편지함(큐·Streams)이 맞고, 그건 9주차·02 의 Pub/Sub vs Queue 그대로입니다.

🗺️

설계 그림

첫 그림은 워커 2개일 때 이벤트가 가는 길입니다. bob 의 입찰 HTTP 요청이 워커 A 에 떨어졌습니다. 서비스는 락·규칙·커밋을 끝내고(6단계) events.publish() 로 Redis 에 PUBLISH auction:{id} 를 보냅니다. 워커 A 와 B 는 각자 lifespan 에서 띄운 bridge 태스크로 auction:* 를 구독 중이라 둘 다 그 메시지를 받고, 각자의 ConnectionManager 에 적힌 자기 소켓들에게 send_text 합니다. carol 이 워커 B 에 붙어 있어도 받습니다. 서비스 코드는 소켓을 전혀 모릅니다.

둘째 그림은 소켓 하나의 일생입니다. 순서가 곧 규칙입니다. accept 를 먼저 하고 나서 토큰을 봅니다(그래야 close 코드를 보낼 수 있습니다). 토큰이 틀리면 4401, 경매가 없으면 4404 — 4000번대는 앱이 마음대로 정하는 구간이라 HTTP 의 401/404 를 흉내 냈습니다. 통과하면 snapshot 을 먼저 보내고 그다음에 장부(ConnectionManager)에 적습니다. 장부에 적히는 순간부터 방송을 받습니다. 클라이언트가 끊으면 WebSocketDisconnect 가 나고, finally 에서 장부에서 지웁니다. DB 세션은 인증·snapshot 두 순간에만 열었다 닫습니다 — 소켓이 살아 있는 몇 분 동안 커넥션을 쥐고 있으면 풀(기본 5개)이 금방 마릅니다.

왜 snapshot 을 보내고 그다음 장부에 적나. 반대로 하면 등록 직후 도착한 bid_placed 가 snapshot 보다 먼저 클라이언트에 닿아 화면이 옛 값으로 덮일 수 있습니다. 지금 순서에서도 snapshot 을 읽은 시각과 등록 사이의 몇 밀리초에 온 이벤트는 놓칠 수 있는데, 다음 이벤트가 bid_count·version 을 통째로 실어 오므로 화면은 곧 맞춰집니다. "이벤트에 증분이 아니라 현재 값을 싣는다"가 이런 유실을 무해하게 만듭니다.
