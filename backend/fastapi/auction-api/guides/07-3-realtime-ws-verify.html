실행·확인 — 이 출력이 나와야 한다

이번 실행·확인의 목적은 하나, 워커가 2개여도 전원이 받는다 를 눈으로 보는 것입니다. 터미널 1 에 서버(워커 2), 터미널 2 에 나머지 전부. 리스너 4개를 백그라운드로 붙이고 입찰 2건을 쏜 뒤 로그를 봅니다.

# INFO:     Started server process [72961]

tok() { curl -s -X POST localhost:8000/auth/login -H "$J" \

bridge 가 정말 중계기일 뿐이라는 것과, 구독자가 워커 수만큼이라는 것을 redis-cli 로 확인합니다. PUBLISH 의 반환값이 "이 메시지를 받은 구독자 수"입니다.

bash터미널 2
echo "=== Redis 에 직접 발행해도 (bridge 는 그냥 중계기) 구독자에게 간다"
docker compose exec redis redis-cli PUBLISH auction:$A '{"type":"note","auction_id":"'$A'","payload":{"msg":"hello from redis-cli"},"at":"2026-08-25T00:00:00Z"}'
# 2          ← 이 메시지를 받은 구독자 수 = 워커 2개 (각 워커의 bridge 하나씩)
echo "=== 구독 중인 패턴 수"
docker compose exec redis redis-cli PUBSUB NUMPAT
# 1          ← 패턴은 auction:* 하나뿐 (구독자 수가 아니라 '패턴 종류' 수)

함정 & 실무 팁

accept 전에 close 하지 마세요. await ws.close() 를 accept() 전에 부르면 서버는 WebSocket close 프레임이 아니라 HTTP 403 으로 핸드셰이크를 거절합니다. 브라우저 콘솔엔 "failed: 403" 만 남고 이유를 구분할 수 없습니다. 먼저 받고(accept), 그다음 4401/4404 로 닫으면 클라이언트의 onclose 가 e.code 로 이유를 압니다. 4000~4999 는 앱이 자유롭게 쓰는 구간입니다.
토큰을 URL(query) 에 넣는 대가. 브라우저 WebSocket 은 헤더를 못 붙여서 어쩔 수 없이 URL 에 넣는데, URL 은 접근 로그·프록시 로그·브라우저 히스토리에 남습니다. 완화책: (1) 수명 짧은 access 토큰만(우리는 15분), (2) 로그에서 token= 마스킹, (3) 더 엄격히 하려면 연결 뒤 첫 메시지로 토큰을 보내고 그전엔 아무것도 안 주는 방식. 쿠키 인증이면 이 문제가 없지만 CSRF 를 따로 봐야 합니다(7주차·03).
커밋 전에 publish 하면. 구독자는 DB 에 없는 입찰을 봅니다. 그 뒤 커밋이 실패하면(커넥션 끊김, 제약 위반) 화면엔 12,000 인데 DB 는 11,000 — 다음 snapshot 까지 거짓말을 합니다. "방송은 사실이 된 뒤에". 반대로 커밋 뒤 publish 가 실패하는 경우(Redis 다운)는 입찰은 유효하되 실시간만 빠진 상태라, 치명적이지 않습니다. 그래서 publish 를 try 로 감싸 삼킬지는 팀 결정입니다(우리는 예외를 그대로 올립니다 — 입찰자는 201 을 못 받지만 DB 는 맞습니다. 8단계에서 다시 봅니다).
프로세스마다 구독 루프 하나 — 그 이상도 이하도 아니게. lifespan 밖(모듈 import 시점)에서 태스크를 만들면 루프가 아직 없어 실패하거나, --reload 에서 두 번 만들어집니다. 반대로 소켓마다 pubsub() 을 열면 소켓 1,000개 = Redis 연결 1,000개입니다. 정답은 lifespan 에서 딱 하나, 그리고 종료 시 cancel → punsubscribe → aclose.
get_message(timeout=1.0) 대 listen(). async for m in pubsub.listen() 이 더 짧지만 메시지가 없으면 영원히 기다립니다. 태스크를 cancel() 하면 깨어나긴 하지만, redis-py 버전에 따라 연결 정리가 깔끔하지 않은 이력이 있어 1초 타임아웃으로 주기적으로 깨어나는 루프가 안전합니다. 1초 지연은 종료할 때만 생기고, 메시지는 오는 즉시 돌아옵니다.
닫힌 소켓에 send_text 하면 예외. 브라우저가 탭을 닫아도 서버 장부엔 잠깐 남아 있습니다. 그 소켓에 보내면 WebSocketDisconnect/RuntimeError 가 나고, 순진하게 for ws in room: await ws.send_text() 로 돌리면 그 뒤 소켓들은 못 받습니다. gather(return_exceptions=True) 로 전부 시도하고, 실패한 것만 지우는 이유입니다.
소켓이 DB 커넥션을 붙들지 않게. Depends(get_db) 는 요청이 끝날 때 세션을 닫는데, WebSocket 의 "요청"은 소켓이 닫힐 때까지입니다. 풀 기본 크기 5 + overflow 10 이면 소켓 16개째부터 HTTP 요청들이 커넥션을 못 얻어 멈춥니다. 필요한 순간에만 SessionLocal() 을 열고 바로 닫으세요(라우터 코드 그대로).
느린 클라이언트(backpressure). send_text 는 상대가 받을 때까지 기다릴 수 있습니다. 모바일에서 화면을 껐다 켠 클라이언트 하나가 broadcast 전체를 붙들 수 있습니다. 규모가 커지면 소켓마다 큐 + 타임아웃(asyncio.wait_for(ws.send_text(), 1.0)) 을 두거나, 실시간 전달만 하는 별도 게이트웨이(예: Centrifugo, Socket.IO 서버)로 뺍니다. 지금 규모에선 gather 로 충분합니다.
Redis Pub/Sub 는 저장하지 않는다(at-most-once). 구독자가 없을 때의 메시지, 재접속하는 0.5초 사이의 메시지는 사라집니다. 그래서 (1) 접속마다 snapshot, (2) 이벤트엔 증분이 아닌 현재 값. "절대 놓치면 안 되는" 것(결제 완료 알림)은 Pub/Sub 가 아니라 Redis Streams·큐가 맞습니다 — 9주차·02 의 Pub/Sub vs Queue.
테스트가 자식 서버를 쓰는 대가. 8765 포트가 비어 있어야 하고, 자식 서버가 현재 코드를 import 하므로 --reload 없이 매번 새로 뜹니다(그래서 module 스코프). 테스트 DB 를 자식이 보게 하는 열쇠는 conftest 의 os.environ 덮어쓰기가 import 전에 일어난다는 3단계 결정입니다. 이 방식은 served_by_pid 를 검사하지 않습니다 — 워커 2개 증명은 실행·확인에서 손으로 합니다.

셀프 체크

Q Redis 없이 ConnectionManager 만으로 브로드캐스트하면 --workers 2 에서 정확히 무엇이 안 되나요? 실행·확인의 출력으로 설명해 보세요.

장부는 프로세스 메모리 안에 있습니다. 리스너 1·3 은 pid 72961, 2·4 는 72960 에 붙었습니다. bob 의 입찰 요청이 72960 에 떨어졌다면 그 프로세스의 장부엔 2·4 만 있어서 1·3 은 못 받습니다 — 사용자 입장에선 "어떤 탭은 되고 어떤 탭은 안 되는" 재현 불가능한 버그로 보입니다. Redis 를 두면 서비스는 PUBLISH 한 번만 하고, 두 프로세스의 bridge 가 각각 받아 자기 장부에 뿌립니다. redis-cli PUBLISH 의 반환값 2 가 "받은 구독자(=워커) 수"였고, 넷 다 이벤트를 받았습니다.

Q accept() 전에 close(4401) 하면 클라이언트는 무엇을 보게 되나요? 왜 우리는 accept 를 먼저 하나요?

핸드셰이크가 완료되지 않은 상태라 서버는 HTTP 403 Forbidden 으로 업그레이드 요청을 거절합니다(RED 에서 본 InvalidStatus … HTTP 403 과 같은 경로). 브라우저 onclose 는 code 1006(비정상 종료) 만 받고 이유를 모릅니다. accept 를 먼저 하면 WebSocket 프로토콜 위에서 close 프레임을 보낼 수 있어 4401(토큰) 과 4404(경매 없음) 를 구분해 전달합니다. 테스트가 exc.value.rcvd.code == 4401 을 검사할 수 있는 것도 그 덕분입니다.

Q Redis Pub/Sub 는 메시지를 저장하지 않습니다. 그럼 재접속 사이에 온 입찰은 어떻게 되나요? 결제 완료 알림도 이 방식으로 보내도 될까요?

그 메시지는 사라집니다. 대신 (1) 접속할 때마다 snapshot 으로 현재 상태를 받고, (2) 모든 이벤트가 증분(+1) 이 아닌 현재 값(bid_count: 2) 을 실으므로, 다음 이벤트 하나면 화면이 바로 맞춰집니다. 경매 화면엔 이걸로 충분합니다. 결제 완료처럼 한 건도 놓치면 안 되고 한 번만 처리돼야 하는 것은 다릅니다 — 소비자가 없을 때 보관하고, 처리 확인(ack) 이 있는 큐(Redis Streams, RabbitMQ 등) 를 씁니다. 9주차·02 의 "Pub/Sub 는 방송, 큐는 편지함" 구분이 그것이고, 9단계 웹훅은 그래서 DB 테이블로 멱등하게 처리합니다.
