7단계 — 실시간 WebSocket + Redis Pub/Sub

경매 화면에서 남이 입찰한 순간이 새로고침 없이 보이게 만듭니다. WS /ws/auctions/{id}?token=… 로 구독하면 현재 상태 한 장(snapshot)을 받고, 그 뒤로 입찰이 들어올 때마다 bid_placed 이벤트가 밀려옵니다. 핵심은 "uvicorn 워커가 2개, 4개여도 모든 구독자가 받는다" — 그 일을 Redis Pub/Sub 가 합니다. 그리고 그것을 워커 2개를 실제로 띄워 눈으로 확인합니다.

한 줄 요약. 이 문서를 끝내면 uv run pytest -q가 64 passed를 찍고(그중 WebSocket 테스트 5개는 진짜 uvicorn 자식 프로세스에 붙습니다), --workers 2로 띄운 서버에 구독자 4명을 붙였을 때 snapshot 의 served_by_pid가 두 값으로 갈리는데도 입찰 이벤트는 4명 모두에게 도착하며, redis-cli PUBLISH로 직접 쏜 메시지까지 소켓에 그대로 나옵니다.

학습 목표

  • HTTP 요청-응답으로는 안 되는 것(서버가 먼저 말 걸기)과 WebSocket 이 필요한 순간을 설명할 수 있다
  • 서비스가 커밋 뒤에 도메인 이벤트를 발행하고, 발행자는 구독자를 모른다는 Pub/Sub 의 분리를 코드로 안다
  • 프로세스(워커)마다 구독 루프 하나 + 프로세스 로컬 ConnectionManager 구조가 왜 필요한지 그림으로 설명한다
  • 소켓 인증: accept 후 4401/4404 로 닫는 이유(핸드셰이크 403 과의 차이)를 안다
  • TestClient 대신 자식 프로세스 서버 + 실제 WebSocket 클라이언트로 테스트하는 이유와 방법을 안다
  • Redis Pub/Sub 의 한계(유실, at-most-once)와 snapshot 으로 보정하는 패턴을 안다

이 단계의 목표

6단계까지는 입찰을 보내는 쪽만 있었습니다. 남의 입찰을 보려면 GET /auctions/{id}를 계속 새로고침해야 했죠. 이번 단계가 끝나면 ws://localhost:8000/ws/auctions/{id}?token=… 에 소켓을 하나 열어 두는 것만으로, 누가 입찰하든 {"type":"bid_placed","payload":{"amount":12000,"current_price":12000,"bid_count":2,…}} 가 밀려옵니다. 붙자마자 snapshot 한 장(현재가·입찰 수·마감 시각)을 먼저 받으니 화면을 그리는 데 다른 요청이 필요 없습니다.

그리고 이 단계의 진짜 확인 포인트는 워커 2개입니다. uvicorn --workers 2는 프로세스를 두 개 띄우고, 브라우저마다 어느 프로세스에 붙을지는 운입니다. bob 의 입찰을 1번 워커가 처리했는데 carol 의 소켓은 2번 워커에 있다면? 1번 워커 메모리 속 소켓 목록엔 carol 이 없습니다. 이 문제를 Redis Pub/Sub 가 풀고, 그걸 리스너 4개로 직접 봅니다.

전제. 6단계가 끝나 있어야 합니다. uv run pytest -q → 59 passed, 컨테이너 두 개 (healthy). 새로 설치하는 것은 테스트·CLI 클라이언트용 websockets 하나(dev). 작업 위치는 til/backend/fastapi/auction-api/.

이번 단계에서 만드는 것. 새 파일 7개(core/events.py, ws/manager.py, ws/bridge.py, ws/router.py, static/ws-demo.html, scripts/ws_listen.py, tests/test_ws.py), 손보는 파일 2개(services/bid.py는 커밋 뒤 한 번 발행, main.py는 구독 루프 기동·라우터·정적 파일). 6단계의 규칙·락은 한 글자도 안 바뀝니다 — 실시간은 덧붙이는 층입니다.

왜 필요한가 — 실무 맥락

경매 화면은 "지금 얼마인가"가 전부입니다. 5초마다 폴링하면 5초 늦은 값을 보여 주고, 마감 30초 전엔 그 5초가 승부를 가릅니다. 폴링 주기를 1초로 줄이면 사용자 1,000명이 초당 1,000번 GET 을 때립니다 — 대부분은 "바뀐 게 없다"는 응답입니다. 서버가 바뀐 순간에만 말해 주는 쪽이 맞고, 그게 WebSocket 입니다(9주차·01).

WebSocket 자체는 9주차에 해 봤습니다. 실무에서 어려운 건 소켓이 아니라 "누가 누구에게 알리나" 입니다. 입찰을 처리한 코드(서비스)가 소켓 목록을 뒤져 직접 send 하면, (1) 서비스가 웹소켓을 알게 되고(계층 위반), (2) 워커가 여럿이면 다른 프로세스의 소켓엔 손이 닿지 않고, (3) 나중에 "입찰 시 Slack 알림"을 붙이려면 서비스를 또 고쳐야 합니다. 그래서 서비스는 "경매 X 에 입찰이 있었다" 만 방송하고 끝냅니다. 누가 듣는지는 모릅니다. 이번 단계엔 웹소켓 중계기가 듣고, 9단계엔 알림이 들을 수 있습니다.

방송 채널이 Redis Pub/Sub 입니다(9주차·02). 이미 3단계부터 붙어 있는 Redis 에 PUBLISH auction:{id} … 한 줄이면 됩니다. 워커마다 PSUBSCRIBE auction:* 로 듣고 있다가 자기 소켓에 뿌리니, 워커 수가 몇이든 같은 코드입니다. 10단계에서 --workers 를 늘려도, 나중에 서버를 두 대로 늘려도 바뀌지 않습니다.

실무에서 같은 모양이 나오는 곳. 채팅방, 주문 상태 추적("배달 중 → 도착"), 협업 문서의 커서, 대시보드의 실시간 지표, 알림 벨. 전부 "어느 프로세스가 사건을 처리했든 관심 있는 모든 소켓에 전달"이고, 전부 브로커(Redis Pub/Sub, Kafka, NATS…)가 가운데 섭니다. 이 단계는 그중 가장 작은 버전입니다.

비유 — 지점 스피커와 공용 방송

지점 스피커와 공용 방송. 은행 지점이 두 곳 있고(워커 2개), 각 지점엔 대기 손님들(소켓)과 천장 스피커(ConnectionManager)가 있습니다. 1지점 창구에서 "통장 잔액이 바뀌었습니다"가 일어나면 1지점 스피커로는 1지점 손님에게만 들립니다. 2지점 손님은 모릅니다. 그래서 본점에 공용 방송 채널(Redis Pub/Sub)을 두고, 지점마다 수신기 하나(bridge 태스크)를 답니다. 창구 직원(서비스)은 일이 끝난 뒤(커밋 뒤) 본점 채널에 한 마디만 하고, 각 지점 수신기가 그걸 받아 자기 지점 스피커로 틀어 줍니다. 창구 직원은 몇 개 지점이 듣는지 모르고, 알 필요도 없습니다.

입장 팔찌. 공연장 객석(경매 방)에 들어오려면 입구에서 팔찌(access 토큰)를 보여야 합니다. 그런데 팔찌가 없다고 입구 문 자체를 안 열어 주면(핸드셰이크 403) 손님은 왜 못 들어가는지 모릅니다. 문은 열어 주되(accept) 바로 "팔찌 없음"(4401)이라고 말하고 내보내는 게 우리 방식입니다. 객석에 앉으면 먼저 지금 무대 상황을 한 장 요약해 줍니다(snapshot). 그 뒤로는 무대에서 일이 날 때마다 스피커로 듣습니다.

공용 방송의 성질. 방송은 그 순간 듣고 있는 사람에게만 들립니다. 화장실에 간 사이의 방송은 다시 틀어 주지 않습니다(Redis Pub/Sub 는 저장하지 않는다). 그래서 객석에 다시 앉을 때마다 요약(snapshot)을 다시 받습니다 — 놓친 방송은 요약으로 메웁니다. "한 건도 놓치면 안 되는" 알림(결제 완료 같은 것)은 방송이 아니라 편지함(큐·Streams)이 맞고, 그건 9주차·02 의 Pub/Sub vs Queue 그대로입니다.

설계 그림

첫 그림은 워커 2개일 때 이벤트가 가는 길입니다. bob 의 입찰 HTTP 요청이 워커 A 에 떨어졌습니다. 서비스는 락·규칙·커밋을 끝내고(6단계) events.publish() 로 Redis 에 PUBLISH auction:{id} 를 보냅니다. 워커 A 와 B 는 각자 lifespan 에서 띄운 bridge 태스크로 auction:* 를 구독 중이라 둘 다 그 메시지를 받고, 각자의 ConnectionManager 에 적힌 자기 소켓들에게 send_text 합니다. carol 이 워커 B 에 붙어 있어도 받습니다. 서비스 코드는 소켓을 전혀 모릅니다.

둘째 그림은 소켓 하나의 일생입니다. 순서가 곧 규칙입니다. accept 를 먼저 하고 나서 토큰을 봅니다(그래야 close 코드를 보낼 수 있습니다). 토큰이 틀리면 4401, 경매가 없으면 4404 — 4000번대는 앱이 마음대로 정하는 구간이라 HTTP 의 401/404 를 흉내 냈습니다. 통과하면 snapshot 을 먼저 보내고 그다음에 장부(ConnectionManager)에 적습니다. 장부에 적히는 순간부터 방송을 받습니다. 클라이언트가 끊으면 WebSocketDisconnect 가 나고, finally 에서 장부에서 지웁니다. DB 세션은 인증·snapshot 두 순간에만 열었다 닫습니다 — 소켓이 살아 있는 몇 분 동안 커넥션을 쥐고 있으면 풀(기본 5개)이 금방 마릅니다.

왜 snapshot 을 보내고 그다음 장부에 적나. 반대로 하면 등록 직후 도착한 bid_placed 가 snapshot 보다 먼저 클라이언트에 닿아 화면이 옛 값으로 덮일 수 있습니다. 지금 순서에서도 snapshot 을 읽은 시각과 등록 사이의 몇 밀리초에 온 이벤트는 놓칠 수 있는데, 다음 이벤트가 bid_count·version 을 통째로 실어 오므로 화면은 곧 맞춰집니다. "이벤트에 증분이 아니라 현재 값을 싣는다"가 이런 유실을 무해하게 만듭니다.

4. app/core/events.py — 이벤트 한 장과 publish()

이벤트는 type·auction_id·payload·at 네 칸짜리 Pydantic 모델입니다. model_dump_json() 이 UUID 와 datetime 을 알아서 문자열로 바꿔 주니 json.dumps 로 씨름할 일이 없습니다. publish() 는 PUBLISH auction:{id} … 한 줄이고 받은 구독자 수를 돌려줍니다 — 0 이어도 정상입니다(아무도 안 보고 있을 뿐). 채널 이름을 만드는 함수와 되돌리는 함수를 여기 같이 둬서, 채널 규칙이 바뀌면 이 파일만 고칩니다.

pythonapp/core/events.py
"""도메인 이벤트 — "경매 X 에 이런 일이 있었다" 를 한 줄(JSON)로 만들어 Redis 채널에 방송한다.

서비스는 이 모듈의 publish() 만 알면 된다. 누가 듣고 있는지(웹소켓? 알림 워커? 아무도?) 는
서비스가 신경 쓰지 않는다 — 그게 Pub/Sub 의 요점이다. 채널 이름은 auction:{id} 하나로 통일한다.
"""

import uuid
from datetime import UTC, datetime
from typing import Any

from pydantic import BaseModel, Field
from redis.asyncio import Redis

CHANNEL_PREFIX = "auction:"


class AuctionEvent(BaseModel):
    type: str  # "snapshot" | "bid_placed" | (8단계) "auction_closed" …
    auction_id: uuid.UUID
    payload: dict[str, Any] = Field(default_factory=dict)
    at: datetime = Field(default_factory=lambda: datetime.now(UTC))


def channel(auction_id: uuid.UUID | str) -> str:
    return f"{CHANNEL_PREFIX}{auction_id}"


def auction_id_from_channel(name: str) -> str:
    return name.removeprefix(CHANNEL_PREFIX)


async def publish(redis: Redis, event: AuctionEvent) -> int:
    """구독자 수를 돌려준다(듣는 사람이 없으면 0 — 그래도 에러는 아니다).
    model_dump_json() 이 UUID·datetime 을 문자열로 바꿔 준다."""
    return await redis.publish(channel(event.auction_id), event.model_dump_json())

5. app/ws/manager.py — 이 프로세스의 장부

9주차·01 의 ConnectionManager 와 같은 물건인데 두 가지가 다릅니다. (1) accept() 를 여기서 하지 않습니다 — 라우터가 인증을 끝낸 뒤 등록만 부탁합니다. (2) broadcast 가 asyncio.gather(…, return_exceptions=True) 로 동시에 보내고, 실패한 소켓(이미 끊긴 것)은 조용히 장부에서 지웁니다. 하나가 죽었다고 나머지가 못 받으면 안 되니까요. 그리고 이 장부는 프로세스 안에만 있습니다 — 그 한계를 다음 파일이 메웁니다.

pythonapp/ws/manager.py
"""ConnectionManager — **이 프로세스에** 붙어 있는 소켓들을 경매별로 묶어 두는 장부.

프로세스(워커)마다 하나씩 있고, 다른 워커의 소켓은 모른다. 워커 사이를 잇는 건 bridge.py 다.
"""

import asyncio
import logging
import uuid

from fastapi import WebSocket

logger = logging.getLogger(__name__)


class ConnectionManager:
    def __init__(self) -> None:
        self._rooms: dict[str, set[WebSocket]] = {}

    def connect(self, auction_id: uuid.UUID | str, ws: WebSocket) -> None:
        """accept() 는 라우터가 이미 했다 — 여기선 장부에 적기만."""
        self._rooms.setdefault(str(auction_id), set()).add(ws)

    def disconnect(self, auction_id: uuid.UUID | str, ws: WebSocket) -> None:
        room = self._rooms.get(str(auction_id))
        if room is None:
            return
        room.discard(ws)
        if not room:
            del self._rooms[str(auction_id)]

    def count(self, auction_id: uuid.UUID | str) -> int:
        return len(self._rooms.get(str(auction_id), ()))

    async def broadcast(self, auction_id: uuid.UUID | str, text: str) -> None:
        """방 안의 모두에게 동시에 보낸다. 끊긴 소켓은 조용히 장부에서 지운다."""
        room = list(self._rooms.get(str(auction_id), ()))
        if not room:
            return
        results = await asyncio.gather(*(ws.send_text(text) for ws in room), return_exceptions=True)
        for ws, result in zip(room, results, strict=True):
            if isinstance(result, Exception):
                logger.info("dead socket removed (auction=%s): %s", auction_id, result)
                self.disconnect(auction_id, ws)


manager = ConnectionManager()

6. app/ws/bridge.py — 워커마다 수신기 하나

redis.pubsub() 으로 전용 연결을 만들고 psubscribe("auction:*") — 경매가 몇 개든 패턴 하나로 다 듣습니다. 루프는 get_message(timeout=1.0) 을 씁니다. listen() 처럼 영원히 막히는 호출 대신 1초마다 깨어나야 서버가 내려갈 때 cancel() 을 제때 받아 구독을 정리할 수 있습니다. 메시지가 오면 채널 이름에서 경매 id 를 꺼내 manager.broadcast — 내용은 열어 보지도 않고 그대로 넘깁니다. bridge 는 중계기일 뿐 서비스가 뭘 보냈는지 모릅니다(그래서 redis-cli 로 쏜 아무 문자열도 소켓에 그대로 나옵니다).

pythonapp/ws/bridge.py
"""Redis 구독 → 이 프로세스의 소켓들로 중계.

워커가 2개면 이 루프도 2개(프로세스마다 하나) 돈다. 어느 워커가 입찰을 처리해 PUBLISH 하든
모든 워커의 루프가 같은 메시지를 받아 *자기* 소켓들에게 뿌린다. 그래서 클라이언트가 어느 워커에
붙었는지는 상관없어진다.
"""

import asyncio
import logging

from redis.asyncio import Redis

from app.core.events import CHANNEL_PREFIX, auction_id_from_channel
from app.ws.manager import ConnectionManager

logger = logging.getLogger(__name__)


async def run_bridge(redis: Redis, manager: ConnectionManager) -> None:
    """lifespan 이 create_task() 로 띄우고, 종료 때 cancel() 한다."""
    pubsub = redis.pubsub()
    await pubsub.psubscribe(f"{CHANNEL_PREFIX}*")  # auction:* 전부
    logger.info("pubsub bridge started")
    try:
        while True:
            # timeout 을 주는 이유: 메시지가 없어도 1초마다 깨어나 cancel 을 받아 줄 수 있게.
            msg = await pubsub.get_message(ignore_subscribe_messages=True, timeout=1.0)
            if msg is None:
                continue
            auction_id = auction_id_from_channel(msg["channel"])
            await manager.broadcast(auction_id, msg["data"])
    except asyncio.CancelledError:
        logger.info("pubsub bridge stopping")
        raise
    finally:
        await pubsub.punsubscribe()
        await pubsub.aclose()

7. app/ws/router.py — 소켓의 일생

pythonapp/ws/router.py
"""WS /ws/auctions/{auction_id}?token=… — 경매 하나를 구독한다.

순서: accept → 토큰 확인(실패면 4401 로 close) → 경매 확인(없으면 4404) → snapshot 한 장 보내기
→ 장부에 등록 → 클라이언트가 끊을 때까지 대기.

왜 accept 부터 하나: accept 전에 close 하면 서버는 HTTP 403 으로 핸드셰이크 자체를 거절한다.
그러면 클라이언트는 "왜" 를 알 수 없다. accept 뒤에 close(code=4401) 를 보내면 클라이언트가
close 코드를 읽어 "토큰 문제구나" 하고 처리할 수 있다. 4000~4999 는 앱이 마음대로 쓰는 구간.

DB 세션은 Depends(get_db) 로 받지 않는다 — 그러면 소켓이 살아 있는 내내 커넥션을 쥐고 있게 된다.
필요한 순간(인증·snapshot)에만 세션을 열고 바로 닫는다.
"""

import os
import uuid

from fastapi import APIRouter, WebSocket, WebSocketDisconnect

from app.core.db import SessionLocal
from app.core.events import AuctionEvent
from app.core.security import TokenError, decode_token
from app.repositories import auction as auction_repo
from app.repositories import user as user_repo
from app.ws.manager import manager

router = APIRouter(tags=["realtime"])

WS_UNAUTHORIZED = 4401
WS_NOT_FOUND = 4404


async def _user_id_from_token(token: str | None) -> uuid.UUID | None:
    if not token:
        return None
    try:
        payload = decode_token(token, expected_type="access")
    except TokenError:
        return None
    user_id = uuid.UUID(payload["sub"])
    async with SessionLocal() as db:
        if await user_repo.get_by_id(db, user_id) is None:
            return None
    return user_id


@router.websocket("/ws/auctions/{auction_id}")
async def auction_stream(ws: WebSocket, auction_id: uuid.UUID, token: str | None = None) -> None:
    await ws.accept()

    if await _user_id_from_token(token) is None:
        await ws.close(code=WS_UNAUTHORIZED, reason="invalid or missing token")
        return

    async with SessionLocal() as db:
        auction = await auction_repo.get(db, auction_id)
        if auction is None:
            await ws.close(code=WS_NOT_FOUND, reason="auction not found")
            return

            type="snapshot",
            auction_id=auction.id,
            payload={
                "status": auction.status,
                "current_price": auction.current_price,
                "bid_count": auction.bid_count,
                "ends_at": auction.ends_at,

    manager.connect(auction_id, ws)
    try:
        while True:
            await ws.receive_text()  # 클라이언트 ping 등. 끊기면 WebSocketDisconnect
    except WebSocketDisconnect:
        pass
    finally:
        manager.disconnect(auction_id, ws)

8. app/services/bid.py — 커밋 뒤에 한 줄

python(수정) app/services/bid.py
"""입찰 규칙. HTTP 를 모른다 — 도메인 예외만 던진다.

핵심은 순서다: (rate limit) → **경매 행 잠금** → 규칙 검사 → 갱신 → 커밋.
잠금부터 커밋까지가 한 트랜잭션이라, 그 사이에 다른 입찰은 줄을 서서 기다린다.
그래서 '현재가 + 최소 단위' 를 계산할 때 본 값이 커밋하는 순간까지 그대로다.
"""

import uuid
from datetime import UTC, datetime, timedelta

from redis.asyncio import Redis
from sqlalchemy.ext.asyncio import AsyncSession

from app.core import events
from app.core.config import get_settings
from app.core.exceptions import (
    AuctionNotActiveError,
    AuctionNotFoundError,
    BidRateLimitedError,
    BidTooLowError,
    OwnAuctionBidError,
)
from app.models import Auction, AuctionStatus, Bid, User
from app.repositories import auction as auction_repo
from app.repositories import bid as bid_repo


def _now() -> datetime:
    """시계를 함수로 빼 두면 테스트에서 멈추거나 돌릴 수 있다."""
    return datetime.now(UTC)


async def _check_rate_limit(redis: Redis, user_id: uuid.UUID, now: datetime) -> None:
    """사용자별 '이번 1초' 카운터. INCR 는 원자적이라 동시에 들어와도 정확히 센다."""
    key = f"bid:rl:{user_id}:{int(now.timestamp())}"
    count = await redis.incr(key)
    if count == 1:
        await redis.expire(key, 2)  # 1초짜리 키가 영원히 남지 않도록
    if count > get_settings().bid_rate_limit_per_second:
        raise BidRateLimitedError()


def minimum_bid(auction: Auction) -> int:
    """첫 입찰은 시작가 이상, 그 다음부터는 현재가 + 최소 단위 이상."""
    if auction.bid_count == 0:
        return auction.starting_price
    return auction.current_price + auction.min_increment


async def place_bid(
    db: AsyncSession, redis: Redis, bidder: User, auction_id: uuid.UUID, amount: int
) -> tuple[Bid, Auction]:
    settings = get_settings()
    now = _now()

    await _check_rate_limit(redis, bidder.id, now)  # 락을 잡기 *전에* — 스팸이 락을 쥐고 있지 않게

    auction = await auction_repo.get_for_update(db, auction_id)  # ← 여기서부터 줄을 선다
    if auction is None:
        raise AuctionNotFoundError()
    if auction.status != AuctionStatus.ACTIVE or now >= auction.ends_at:
        raise AuctionNotActiveError()
    if auction.seller_id == bidder.id:
        raise OwnAuctionBidError()
    minimum = minimum_bid(auction)
    if amount < minimum:
        raise BidTooLowError(
            f"최소 입찰액은 {minimum:,}원입니다 (현재가 {auction.current_price:,}원)"
        )

    # 규칙 4 — 마감 직전 입찰이면 마감을 늦춘다 (스나이핑 방지)
    extended = False
    if auction.ends_at - now < timedelta(seconds=settings.snipe_window_seconds):
        auction.ends_at = auction.ends_at + timedelta(seconds=settings.snipe_extend_seconds)
        extended = True

    auction.current_price = amount
    auction.bid_count += 1
    auction.version += 1
    bid = Bid(auction_id=auction.id, bidder_id=bidder.id, amount=amount)
    await bid_repo.add(db, bid)

    await db.commit()  # ← 여기서 락이 풀리고, 줄 서 있던 다음 입찰이 '바뀐 현재가' 를 본다
    await db.refresh(bid)
    await db.refresh(auction)

    # 커밋 *뒤에* 방송한다. 커밋 전에 방송하면 구독자가 "아직 DB 에 없는 입찰" 을 보게 되고,
    # 커밋이 실패하면 없던 일이 방송된 채로 남는다.
    await events.publish(
        redis,
        events.AuctionEvent(
            type="bid_placed",
            auction_id=auction.id,
            payload={
                "amount": bid.amount,
                "bidder_id": bid.bidder_id,
                "current_price": auction.current_price,
                "bid_count": auction.bid_count,
                "ends_at": auction.ends_at,
                "version": auction.version,
                "extended": extended,
            },
        ),
    )
    return bid, auction


async def list_bids(db: AsyncSession, auction_id: uuid.UUID) -> list[Bid]:
    if await auction_repo.get(db, auction_id) is None:
        raise AuctionNotFoundError()
    return await bid_repo.list_by_auction(db, auction_id)

"""터미널용 구독 클라이언트: uv run python scripts/ws_listen.py <auction_id> <token> [초]

받은 이벤트를 한 줄씩 찍는다. 워커가 여럿일 때 snapshot 의 served_by_pid 로
"나는 어느 워커에 붙었나" 를 확인하는 용도.
"""

import asyncio
import json
import sys

from websockets.asyncio.client import connect


async def main(auction_id: str, token: str, seconds: float) -> None:
    url = f"ws://127.0.0.1:8000/ws/auctions/{auction_id}?token={token}"
    async with connect(url) as ws:
        loop = asyncio.get_running_loop()
        deadline = loop.time() + seconds
        while (remaining := deadline - loop.time()) > 0:
            try:
                raw = await asyncio.wait_for(ws.recv(), timeout=remaining)
            except TimeoutError:
                break
            ev = json.loads(raw)
            print(f"[{ev['type']}] {json.dumps(ev['payload'], ensure_ascii=False)}", flush=True)


if __name__ == "__main__":
    asyncio.run(main(sys.argv[1], sys.argv[2], float(sys.argv[3]) if len(sys.argv) > 3 else 15))

함정 & 실무 팁

accept 전에 close 하지 마세요. await ws.close() 를 accept() 전에 부르면 서버는 WebSocket close 프레임이 아니라 HTTP 403 으로 핸드셰이크를 거절합니다. 브라우저 콘솔엔 "failed: 403" 만 남고 이유를 구분할 수 없습니다. 먼저 받고(accept), 그다음 4401/4404 로 닫으면 클라이언트의 onclose 가 e.code 로 이유를 압니다. 4000~4999 는 앱이 자유롭게 쓰는 구간입니다.
토큰을 URL(query) 에 넣는 대가. 브라우저 WebSocket 은 헤더를 못 붙여서 어쩔 수 없이 URL 에 넣는데, URL 은 접근 로그·프록시 로그·브라우저 히스토리에 남습니다. 완화책: (1) 수명 짧은 access 토큰만(우리는 15분), (2) 로그에서 token= 마스킹, (3) 더 엄격히 하려면 연결 뒤 첫 메시지로 토큰을 보내고 그전엔 아무것도 안 주는 방식. 쿠키 인증이면 이 문제가 없지만 CSRF 를 따로 봐야 합니다(7주차·03).
커밋 전에 publish 하면. 구독자는 DB 에 없는 입찰을 봅니다. 그 뒤 커밋이 실패하면(커넥션 끊김, 제약 위반) 화면엔 12,000 인데 DB 는 11,000 — 다음 snapshot 까지 거짓말을 합니다. "방송은 사실이 된 뒤에". 반대로 커밋 뒤 publish 가 실패하는 경우(Redis 다운)는 입찰은 유효하되 실시간만 빠진 상태라, 치명적이지 않습니다. 그래서 publish 를 try 로 감싸 삼킬지는 팀 결정입니다(우리는 예외를 그대로 올립니다 — 입찰자는 201 을 못 받지만 DB 는 맞습니다. 8단계에서 다시 봅니다).
프로세스마다 구독 루프 하나 — 그 이상도 이하도 아니게. lifespan 밖(모듈 import 시점)에서 태스크를 만들면 루프가 아직 없어 실패하거나, --reload 에서 두 번 만들어집니다. 반대로 소켓마다 pubsub() 을 열면 소켓 1,000개 = Redis 연결 1,000개입니다. 정답은 lifespan 에서 딱 하나, 그리고 종료 시 cancel → punsubscribe → aclose.
get_message(timeout=1.0) 대 listen(). async for m in pubsub.listen() 이 더 짧지만 메시지가 없으면 영원히 기다립니다. 태스크를 cancel() 하면 깨어나긴 하지만, redis-py 버전에 따라 연결 정리가 깔끔하지 않은 이력이 있어 1초 타임아웃으로 주기적으로 깨어나는 루프가 안전합니다. 1초 지연은 종료할 때만 생기고, 메시지는 오는 즉시 돌아옵니다.
닫힌 소켓에 send_text 하면 예외. 브라우저가 탭을 닫아도 서버 장부엔 잠깐 남아 있습니다. 그 소켓에 보내면 WebSocketDisconnect/RuntimeError 가 나고, 순진하게 for ws in room: await ws.send_text() 로 돌리면 그 뒤 소켓들은 못 받습니다. gather(return_exceptions=True) 로 전부 시도하고, 실패한 것만 지우는 이유입니다.
소켓이 DB 커넥션을 붙들지 않게. Depends(get_db) 는 요청이 끝날 때 세션을 닫는데, WebSocket 의 "요청"은 소켓이 닫힐 때까지입니다. 풀 기본 크기 5 + overflow 10 이면 소켓 16개째부터 HTTP 요청들이 커넥션을 못 얻어 멈춥니다. 필요한 순간에만 SessionLocal() 을 열고 바로 닫으세요(라우터 코드 그대로).
느린 클라이언트(backpressure). send_text 는 상대가 받을 때까지 기다릴 수 있습니다. 모바일에서 화면을 껐다 켠 클라이언트 하나가 broadcast 전체를 붙들 수 있습니다. 규모가 커지면 소켓마다 큐 + 타임아웃(asyncio.wait_for(ws.send_text(), 1.0)) 을 두거나, 실시간 전달만 하는 별도 게이트웨이(예: Centrifugo, Socket.IO 서버)로 뺍니다. 지금 규모에선 gather 로 충분합니다.
Redis Pub/Sub 는 저장하지 않는다(at-most-once). 구독자가 없을 때의 메시지, 재접속하는 0.5초 사이의 메시지는 사라집니다. 그래서 (1) 접속마다 snapshot, (2) 이벤트엔 증분이 아닌 현재 값. "절대 놓치면 안 되는" 것(결제 완료 알림)은 Pub/Sub 가 아니라 Redis Streams·큐가 맞습니다 — 9주차·02 의 Pub/Sub vs Queue.
테스트가 자식 서버를 쓰는 대가. 8765 포트가 비어 있어야 하고, 자식 서버가 현재 코드를 import 하므로 --reload 없이 매번 새로 뜹니다(그래서 module 스코프). 테스트 DB 를 자식이 보게 하는 열쇠는 conftest 의 os.environ 덮어쓰기가 import 전에 일어난다는 3단계 결정입니다. 이 방식은 served_by_pid 를 검사하지 않습니다 — 워커 2개 증명은 실행·확인에서 손으로 합니다.

장부는 프로세스 메모리 안에 있습니다. 리스너 1·3 은 pid 72961, 2·4 는 72960 에 붙었습니다. bob 의 입찰 요청이 72960 에 떨어졌다면 그 프로세스의 장부엔 2·4 만 있어서 1·3 은 못 받습니다 — 사용자 입장에선 "어떤 탭은 되고 어떤 탭은 안 되는" 재현 불가능한 버그로 보입니다. Q accept() 전에 close(4401) 하면 클라이언트는 무엇을 보게 되나요? 왜 우리는 accept 를 먼저 하나요?

핸드셰이크가 완료되지 않은 상태라 서버는 HTTP 403 Forbidden 으로 업그레이드 요청을 거절합니다(RED 에서 본 InvalidStatus … HTTP 403 과 같은 경로). 브라우저 onclose 는 code 1006(비정상 종료) 만 받고 이유를 모릅니다. accept 를 먼저 하면 WebSocket 프로토콜 위에서 close 프레임을 보낼 수 있어 4401(토큰) 과 4404(경매 없음) 를 구분해 전달합니다. 테스트가 exc.value.rcvd.code == 4401 을 검사할 수 있는 것도 그 덕분입니다.

Q Redis Pub/Sub 는 메시지를 저장하지 않습니다. 그럼 재접속 사이에 온 입찰은 어떻게 되나요? 결제 완료 알림도 이 방식으로 보내도 될까요?

그 메시지는 사라집니다. 대신 (1) 접속할 때마다 snapshot 으로 현재 상태를 받고, (2) 모든 이벤트가 증분(+1) 이 아닌 현재 값(bid_count: 2) 을 실으므로, 다음 이벤트 하나면 화면이 바로 맞춰집니다. 경매 화면엔 이걸로 충분합니다. 결제 완료처럼 한 건도 놓치면 안 되고 한 번만 처리돼야 하는 것은 다릅니다 — 소비자가 없을 때 보관하고, 처리 확인(ack) 이 있는 큐(Redis Streams, RabbitMQ 등) 를 씁니다. 9주차·02 의 "Pub/Sub 는 방송, 큐는 편지함" 구분이 그것이고, 9단계 웹훅은 그래서 DB 테이블로 멱등하게 처리합니다.
