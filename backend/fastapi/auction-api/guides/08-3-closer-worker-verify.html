실행·확인 — 이 출력이 나와야 한다

터미널 세 개를 씁니다. 1번은 API, 2번은 워커, 3번에서 시나리오를 돌립니다. 워커는 nohup … > worker.log & 로 띄워 로그를 파일에 남깁니다 — 나중에 grep 으로 "누가 언제 뭘 닫았나"를 보기 위해서입니다. timeout 150 은 실습이 끝나면 저절로 죽으라는 뜻입니다.

1. API 와 워커

2. 45초 뒤 마감되는 경매 — 입찰 두 건, 소켓으로 마감 지켜보기

왜 45초인가: 6단계 규칙 4 때문입니다. 마감 30초 안에 들어온 입찰은 마감을 30초 미룹니다. 15초 뒤 마감으로 잡고 바로 입찰하면 연장돼서 45초 뒤에 닫힙니다(처음 시도에서 정확히 그렇게 됐습니다). 45초로 잡고 즉시 입찰하면 창 밖이라 연장이 없습니다. 리스너(7단계 ws_listen.py)는 55초 동안 듣습니다.

bash터미널 3
J='Content-Type: application/json'
for who in alice bob carol; do
  curl -s -X POST localhost:8000/auth/signup -H "$J" \
    -d "{\"email\":\"$who@example.com\",\"password\":\"secret123\",\"nickname\":\"$who\"}" > /dev/null
done
tok() { curl -s -X POST localhost:8000/auth/login -H "$J" \
  -d "{\"email\":\"$1@example.com\",\"password\":\"secret123\"}" \
  | python3 -c 'import sys,json; print(json.load(sys.stdin)["access_token"])'; }
ALICE=$(tok alice); BOB=$(tok bob); CAROL=$(tok carol)
ENDS=$(python3 -c "from datetime import datetime, timedelta, UTC; print((datetime.now(UTC)+timedelta(seconds=45)).isoformat())")
A=$(curl -s -X POST localhost:8000/auctions -H "Authorization: Bearer $ALICE" -H "$J" \
  -d "{\"title\":\"45초 뒤 마감\",\"category\":\"hobby\",\"starting_price\":10000,\"ends_at\":\"$ENDS\"}" \
  | python3 -c 'import sys,json; d=json.load(sys.stdin); print(d["id"])')
echo "A=$A ends_at=$ENDS"
# A=65cc6f7c-4654-4a05-811a-b962f07db3ca ends_at=2026-08-25T15:06:35.851848+00:00
uv run python scripts/ws_listen.py $A $BOB 55 > listener.log 2>&1 &
L=$!
curl -s -o /dev/null -w "bob 10000 → %{http_code}\n" -X POST localhost:8000/auctions/$A/bids -H "Authorization: Bearer $BOB" -H "$J" -d '{"amount":10000}'
curl -s -o /dev/null -w "carol 12000 → %{http_code}\n" -X POST localhost:8000/auctions/$A/bids -H "Authorization: Bearer $CAROL" -H "$J" -d '{"amount":12000}'
# bob 10000 → 201
# carol 12000 → 201
echo "… 마감까지 기다리는 중 (리스너 55초)"; wait $L
cat listener.log
# [snapshot] {"status": "active", "current_price": 12000, "bid_count": 2, "ends_at": "2026-08-25T15:06:35.851848Z", "version": 2, "served_by_pid": 20639}
# [auction_closed] {"winner_id": "76de74b6-1c89-40e2-b191-5bb6a0b6f299", "final_price": 12000, "bid_count": 2, "payment_id": "26239027-7c83-4ca2-9b2b-6950fc195c44", "payment_expires_at": "2026-08-26T15:06:36.405506Z", "version": 3}
읽는 법. snapshot 의 version 2(입찰 2건) → 45초 뒤 auction_closed 에 winner_id(carol), final_price 12000, payment_id, payment_expires_at(꼭 24시간 뒤), version 3. 이 이벤트를 발행한 건 API 가 아니라 워커 프로세스입니다. 7단계 bridge 는 누가 발행했든 상관없이 소켓으로 흘려보냈습니다.

4. 활성화도 워커가 한다 — 5초 뒤 시작하는 경매

4단계에서 starts_at 이 미래면 scheduled 로 만들어 두고 "8단계 워커가 열어 준다"고 했던 그 숙제입니다.

bash터미널 3
STARTS=$(python3 -c "from datetime import datetime, timedelta, UTC; print((datetime.now(UTC)+timedelta(seconds=5)).isoformat())")
S=$(curl -s -X POST localhost:8000/auctions -H "Authorization: Bearer $ALICE" -H "$J" \
  -d "{\"title\":\"5초 뒤 시작\",\"category\":\"books\",\"starting_price\":5000,\"starts_at\":\"$STARTS\",\"ends_at\":\"2030-01-01T00:00:00Z\"}" \
  | python3 -c 'import sys,json; d=json.load(sys.stdin); print(d["id"])')
curl -s localhost:8000/auctions/$S | python3 -c 'import sys,json; d=json.load(sys.stdin); print("지금:", d["status"], "version", d["version"])'
# 지금: scheduled version 0
sleep 7
curl -s localhost:8000/auctions/$S | python3 -c 'import sys,json; d=json.load(sys.stdin); print("7초 뒤:", d["status"], "version", d["version"])'
# 7초 뒤: active version 1
grep activated worker.log
# 2026-08-26 00:06:51,877 [pid 20708] INFO app.services.closer: activated 1 auction(s): ['b2187834']
# 2026-08-26 00:06:51,892 [pid 20708] INFO worker.closer: tick: activated=1 closed=0 expired=0

5. 워커 두 개 — 같은 순간 마감되는 경매 40개

설계 그림 2 를 실제로 봅니다. 워커 1 을 내리고 같은 설정(0.3초 주기, 한 틱 5건)의 워커 두 개를 나란히 띄운 뒤, 5초 뒤 같은 시각에 마감되는 경매 40개를 만듭니다. 한 틱에 5건씩이니 두 워커가 여러 틱에 걸쳐 후보를 나눠 갖습니다. 밀리초 단위 로그를 시간순으로 섞어 보면 pid 25225 와 25226 이 번갈아 나옵니다.

bash터미널 3
pkill -f "app.workers.closer"; sleep 1   # 워커 1 은 내리고, 같은 설정의 워커 두 개를 나란히 띄운다
for n in 1 2; do
  CLOSER_INTERVAL_SECONDS=0.3 CLOSER_BATCH_SIZE=5 nohup timeout 30 uv run python -m app.workers.closer > worker$n.log 2>&1 &
done
sleep 3
ENDS=$(python3 -c "from datetime import datetime, timedelta, UTC; print((datetime.now(UTC)+timedelta(seconds=5)).isoformat())")
for i in $(seq 1 40); do   # 같은 순간에 마감되는 경매 40개 (입찰 없음 → 유찰)
  curl -s -o /dev/null -X POST localhost:8000/auctions -H "Authorization: Bearer $ALICE" -H "$J" \
    -d "{\"title\":\"동시 마감 $i\",\"category\":\"etc\",\"starting_price\":1000,\"ends_at\":\"$ENDS\"}"
done
sleep 10
echo "--- 시간순으로 섞어 보면 두 워커가 번갈아 처리한다"
grep -h "유찰" worker1.log worker2.log | sort | head -8 | sed 's/INFO app.services.closer: //'
# 2026-08-26 00:07:56,855 [pid 25225] [notify] auction=366ccd30 유찰 (입찰 0건)
# 2026-08-26 00:07:56,855 [pid 25226] [notify] auction=14cd80a9 유찰 (입찰 0건)
# 2026-08-26 00:07:56,869 [pid 25226] [notify] auction=9b4a8c51 유찰 (입찰 0건)
# 2026-08-26 00:07:56,878 [pid 25226] [notify] auction=5cb0b7bf 유찰 (입찰 0건)
# 2026-08-26 00:07:56,879 [pid 25225] [notify] auction=1edbbdd7 유찰 (입찰 0건)
# 2026-08-26 00:07:57,201 [pid 25226] [notify] auction=beec88f6 유찰 (입찰 0건)
# 2026-08-26 00:07:57,202 [pid 25225] [notify] auction=268a63ef 유찰 (입찰 0건)
# 2026-08-26 00:07:57,212 [pid 25225] [notify] auction=d198c730 유찰 (입찰 0건)
echo "--- 워커별 처리 건수"; echo "worker1: $(grep -c 유찰 worker1.log)  worker2: $(grep -c 유찰 worker2.log)"
# worker1: 24  worker2: 16          ← 비율은 매번 다르다. 합이 40 이고 아래가 '40 1' 인 것이 핵심
echo "--- 경매 40개가 각각 정확히 1번"; cat worker1.log worker2.log | grep "유찰" | sed 's/.*auction=/auction=/' | sort | uniq -c | awk '{print $1}' | sort | uniq -c
#   40 1                              ← "1번 나온 경매가 40개" (2번 나온 경매가 있으면 '  n 2' 줄이 생긴다)
비율이 24 : 16 인 이유. 후보 5건을 둘 다 뽑아 A 가 #1 을 잠그면 B 는 #1 을 건너뛰고 #2 를 잠급니다. 한 건 처리(커밋·발행·로그)가 몇 ms 라 누가 먼저 다음 후보에 닿느냐는 운입니다. 그래서 비율은 실행마다 다릅니다. 변하지 않는 건 마지막 줄 40 1 — "1번 닫힌 경매가 40개"입니다. 만약 어떤 경매가 두 번 닫혔다면 1 2 같은 줄이 생깁니다. 이 한 줄이 이 단계의 증명입니다.

함정 & 실무 팁

API 안의 BackgroundTasks / create_task 로 하지 마세요. BackgroundTasks(8주차·03)는 그 요청이 끝난 뒤 한 번 도는 것이라 "요청 없이 1초마다"엔 맞지 않고, lifespan 의 create_task 루프는 --workers 4 면 4개가 돌고 API 재시작에 사라집니다. 오늘 워커는 별도 프로세스라 10단계 compose 에서 worker 서비스로 따로 띄우고 따로 늘립니다. 7단계 bridge 는 create_task 로 둔 이유가 다릅니다 — 그건 프로세스마다 하나씩 있어야 하는 수신기이니까요.
SKIP LOCKED 는 정확성 장치가 아니라 대기 회피 장치입니다. "남이 잠근 행은 건너뛴다"는 뜻일 뿐, 남이 이미 커밋해서 락을 푼 행은 잡힙니다. 후보를 뽑은 시각과 잠근 시각 사이에 다른 워커가 닫고 커밋했으면 우리는 ended 행을 잠그게 됩니다. 그래서 잠근 뒤 status·ends_at 을 다시 봅니다. 이 재검사를 빼면 워커 두 개가 같은 경매를 두 번 닫고, payments.auction_id UNIQUE 가 마지막에 IntegrityError 로 막아 주는 처지가 됩니다(그러면 그 틱의 나머지 처리도 흔들립니다). NOWAIT 는 건너뛰는 대신 에러를 내는 변형입니다.
발행은 커밋 뒤, 그리고 발행 실패가 DB 를 되돌리지 않게. 7단계와 같은 규칙입니다. 커밋 전에 PUBLISH 하면 구독자가 "아직 DB 에 없는 낙찰"을 보고, 커밋이 실패하면 없던 일이 방송된 채 남습니다. 반대로 커밋 뒤 Redis 가 죽어서 발행이 실패하면? 낙찰은 이미 사실입니다. 소켓 구독자는 못 받지만 GET /auctions/{id} 는 ended 를 줍니다(7단계의 "snapshot 으로 보정"). 그래서 [notify] 로그(진짜라면 알림 큐)는 DB 가 진실이라는 전제로 커밋 뒤에 둡니다.
시계는 하나가 아닙니다. 워커의 datetime.now(UTC) 와 DB 의 now() 는 다른 기계의 시계일 수 있습니다(NTP 로 보통 수십 ms 안이지만). 우리는 앱 시계를 인자로 통일했습니다 — 테스트가 쥘 수 있고, 한 틱 안에서 세 함수가 같은 now 를 봅니다. 그리고 timezone-aware 여야 합니다: datetime.now()(naive) 와 DateTime(timezone=True) 컬럼을 비교하면 TypeError: can't compare offset-naive and offset-aware 가 납니다. 테스트의 NOW = datetime(…, tzinfo=UTC) 도 그래서입니다.
graceful shutdown 은 10초 안에. docker stop 은 SIGTERM 을 보내고 10초 뒤 SIGKILL 입니다(10주차·03). 우리 루프는 SIGTERM → stop.set() → 진행 중인 틱을 끝내고 → closer stopped → Redis·엔진 정리. 한 틱이 10초를 넘기면(후보 100건 × 느린 알림) 도중에 죽습니다 — 그래서 closer_batch_size 가 있고, 무거운 일(메일 발송)은 틱 안에서 직접 하지 말고 큐에 넣습니다. asyncio.sleep(interval) 대신 wait_for(stop.wait()) 를 쓴 것도 종료 지연을 없애기 위해서입니다.
한 건씩 커밋 vs 통째로. 오늘은 한 건 = 한 트랜잭션입니다. 실패의 반경이 한 건이고, 락도 한 행·수 ms 입니다. 대신 100건이면 커밋이 100번 — 건당 수 ms 라 1초 주기 워커엔 충분합니다. 반대로 "1만 건을 한 번에" 같은 배치 작업은 묶어서 커밋하되 청크(예: 500건)로 자릅니다. 기준은 "실패했을 때 되돌려도 되는 단위"입니다.
1초 폴링은 시작점이지 끝이 아닙니다. 폴링은 단순하고 견고하지만(워커가 죽었다 살아나도 그냥 다음 틱에 처리) 마감이 최대 1초 늦고, 경매가 없어도 초당 3개 쿼리를 합니다. 다음 단계들: 마감 시각을 Redis ZSET 에 넣고 ZRANGEBYSCORE 로 "지금 처리할 것"만 보기(딜레이 큐), 또는 arq·Celery beat·pg_cron 같은 스케줄러. 어느 쪽이든 실제 처리 함수는 오늘의 close_due 그대로입니다 — 트리거만 바뀝니다. 그게 규칙을 서비스에, 루프를 워커에 나눠 둔 보상입니다.
워커 테스트가 테스트 DB 를 보는 이유. 3단계 conftest.py 가 앱을 import 하기 전에 os.environ 을 바꿔 두므로, 같은 프로세스에서 app.workers.closer 를 import 하면 같은 테스트 DB·Redis 15번을 봅니다. 루프 테스트는 closer_worker.tick 을 monkeypatch 해서 시계를 고정하고 결과를 기록했습니다 — 루프의 "돌고 멈춘다"만 검사하고 규칙은 앞의 테스트에 맡깁니다. 실행·확인처럼 자식 프로세스로 띄워도 환경변수를 물려받아 테스트 DB 를 봅니다(7단계 live_server 와 같은 원리).
로그의 [notify] 는 알림이 아닙니다. 실무에서 낙찰 알림은 "한 번은 반드시, 두 번은 안 되게"여야 합니다. 로그 한 줄을 이메일 발송으로 바꾸면 (1) 발송 실패 시 재시도가 없고, (2) 워커가 발송 도중 죽으면 유실됩니다. 정석은 close_due 가 같은 트랜잭션에 notifications 행(pending)을 INSERT 하고(=아웃박스), 별도 발송 워커가 그것을 SKIP LOCKED 로 집어 보내고 sent 로 바꾸는 것 — 오늘 배운 패턴 그대로를 한 번 더 쓰는 겁니다. 9주차·02 의 "Pub/Sub 는 방송, 큐는 편지함"이 여기서도 기준입니다.

셀프 체크

Q 워커 두 개가 같은 경매를 두 번 닫지 않는 것을 무엇이 보장하나요? SKIP LOCKED 만으로 충분한가요?

아닙니다. SKIP LOCKED 는 "지금 남이 잠근 행은 건너뛴다"일 뿐, 후보를 뽑은 뒤 남이 닫고 커밋해서 락을 푼 행은 잡힙니다. 정확성은 잠근 뒤 재검사(status == active and ends_at <= now) 가 보장합니다 — 잠근 뒤 본 값은 커밋된 최신 값이고, 우리가 커밋할 때까지 아무도 못 바꾸니까요. 그리고 코드에 구멍이 나도 payments.auction_id UNIQUE 가 두 번째 대기표를 막습니다. 실행·확인의 40 1 이 세 겹이 함께 낸 결과입니다.

Q 마감 처리를 FastAPI 의 BackgroundTasks 나 lifespan 의 asyncio.create_task 로 하면 어떤 문제가 생기나요? 7단계 bridge 는 create_task 인데 왜 괜찮은가요?

BackgroundTasks 는 어떤 요청이 끝난 뒤 한 번 도는 것이라 "요청이 없어도 1초마다"엔 쓸 수 없습니다. lifespan 의 create_task 루프는 --workers 4 면 4개가 같은 경매를 닫으려 들고, API 재시작·스케일 다운에 사라지며, 무거운 마감 처리가 API 응답을 늦춥니다. 별도 프로세스면 API 와 독립적으로 죽이고 살리고 개수를 정합니다. bridge 가 create_task 여도 되는 이유는 정반대입니다 — bridge 는 프로세스마다 하나씩 있어야 하는 수신기라, 워커가 4개면 4개 있는 게 맞습니다.

Q 워커가 auction_closed 를 발행한 순간 Redis 가 죽어 있었습니다. 낙찰은 어떻게 되고, 사용자는 어떻게 알게 되나요? 낙찰 이메일도 같은 방식으로 보내도 될까요?

낙찰은 이미 커밋된 사실이라 그대로입니다 — 발행은 커밋 뒤라서 DB 가 진실입니다. 소켓 구독자는 그 이벤트를 못 받지만, 다시 접속하면 snapshot 이 ended 를 주고 GET /auctions/{id} 도 winner_id 를 줍니다(7단계의 "이벤트는 현재 값, 놓치면 snapshot"). 이메일은 다릅니다. 한 번은 반드시 가야 하고 두 번 가면 안 되니, 방송(Pub/Sub)이 아니라 편지함이 필요합니다 — close_due 가 같은 트랜잭션에 notifications(pending) 행을 넣고(아웃박스), 발송 워커가 SKIP LOCKED 로 집어 보내고 sent 로 바꿉니다. 오늘 배운 패턴을 한 번 더 쓰는 것입니다.
