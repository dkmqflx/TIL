8단계 — 마감 워커: 시간이 흐르면 저절로 일어나는 일

지금까지의 모든 일은 누군가 요청을 보내야 일어났습니다. 그런데 경매 마감은 아무도 요청하지 않습니다 — 시각이 지나면 그냥 일어나야 합니다. 이번 단계는 API 서버와 별개의 프로세스(python -m app.workers.closer)가 1초마다 시계를 보고 ① 시작 시각이 지난 경매를 열고, ② 마감 시각이 지난 경매를 닫아 낙찰자를 정하고 결제 대기표(Payment)를 끊고 auction_closed 를 방송하며, ③ 결제 기한이 지난 대기표를 만료시킵니다. 그리고 워커를 두 개 띄워도 한 경매가 두 번 닫히지 않는다는 것을 FOR UPDATE SKIP LOCKED 로 보장하고 눈으로 확인합니다.

한 줄 요약. 이 문서를 끝내면 uv run pytest -q가 71 passed를 찍고, 45초 뒤 마감되는 경매에 입찰 두 건을 넣어 두면 워커 로그에 [notify] user=76de74b6 낙찰! … 12,000원이 찍히면서 WebSocket 구독자가 auction_closed 를 받고, payments 테이블에 pending 한 행이 생기며, 같은 순간에 마감되는 경매 40개를 워커 두 개가 24 : 16 으로 나눠 처리하되 40개 전부 정확히 한 번씩 닫힙니다.

학습 목표

  • "요청이 없어도 일어나야 하는 일"을 API 프로세스 안의 BackgroundTasks/create_task 가 아니라 별도 워커 프로세스로 두는 이유를 설명할 수 있다
  • 시간에 의존하는 규칙을 now 를 인자로 받는 순수 함수로 써서, 45초를 기다리지 않고 테스트하는 법을 안다
  • SELECT … FOR UPDATE SKIP LOCKED 가 "줄 서기"(6단계) 와 어떻게 다르며 왜 워커 여러 개의 중복 처리를 막는지 안다
  • 후보 조회 → 잠금 → 재검사 → 한 건씩 커밋 → 커밋 뒤 발행, 이 순서가 각각 무엇을 막는지 안다
  • UPDATE … RETURNING 한 문장이 왜 그 자체로 안전한 배치인지 안다
  • SIGTERM 을 받으면 하던 틱을 끝내고 조용히 내려오는 루프(graceful shutdown)를 만들 수 있다

이 단계의 목표

7단계까지의 경매는 영원히 active 였습니다. ends_at 이 지나도 아무도 닫아 주지 않았고, 6단계의 입찰 서비스가 now >= ends_at 을 검사해서 입찰만 막았을 뿐입니다. 낙찰자도, 결제도 없었습니다. 이번 단계가 끝나면 uv run python -m app.workers.closer 를 띄워 두는 것만으로, 마감 시각이 지난 경매는 1초 안에 ended 가 되고 winner_id 가 채워지며 payments 에 24시간짜리 pending 행이 생기고, 7단계의 소켓 구독자들이 {"type":"auction_closed","payload":{"winner_id":…,"final_price":12000,"payment_id":…}} 를 받습니다. 시작 시각이 미래인 scheduled 경매도 같은 워커가 제때 active 로 바꿔 줍니다(4단계에서 미뤄 둔 숙제).

이 단계의 진짜 확인 포인트는 워커가 두 개일 때입니다. 10단계에서 워커 컨테이너를 2개로 늘리거나, 배포 중 옛 워커와 새 워커가 잠깐 같이 돌면, 같은 경매를 둘 다 닫으려 듭니다. 낙찰 알림이 두 번 가고 결제 대기표가 두 장 생기면 사고입니다. 그래서 "같은 순간 마감되는 경매 40개, 워커 2개"를 실제로 돌려 40개가 정확히 한 번씩 닫히는 것을 로그로 확인합니다.

전제. 7단계가 끝나 있어야 합니다. uv run pytest -q → 64 passed, 컨테이너 두 개 (healthy). 새로 설치하는 패키지는 없습니다. 마이그레이션도 없습니다 — 2단계에서 만든 payments 테이블에 status·expires_at·paid_at·external_id 가 이미 있습니다(그때 "8·9단계가 쓴다"고 적어 둔 칸들입니다). 작업 위치는 til/backend/fastapi/auction-api/.

이번 단계에서 만드는 것. 새 파일 4개(services/closer.py 규칙 세 가지, workers/closer.py 루프·시그널, repositories/payment.py, tests/test_closer.py), 손보는 파일 3개(core/config.py 설정 3개, repositories/auction.py 에 skip_locked 와 후보 조회 2개, repositories/bid.py 에 top_bid). 7단계의 bridge 는 한 줄도 안 바꿉니다 — 워커가 같은 채널에 auction_closed 를 발행하면 bridge 가 그대로 소켓으로 흘려보냅니다.

왜 필요한가 — 실무 맥락

웹 서버는 요청이 와야 움직입니다. 그런데 실무 시스템의 절반은 요청 없이 일어나는 일입니다 — 경매 마감, 구독 갱신, 예약 리마인더, 장바구니 만료, 미결제 주문 취소, 리포트 집계. 처음엔 다들 "다음 요청이 왔을 때 겸사겸사 처리하자"(lazy 처리)를 떠올립니다. 경매 조회 요청이 오면 그때 마감 여부를 보고 닫는 식이죠. 새벽 3시에 마감되는 경매를 아무도 안 보면? 아침에 첫 손님이 볼 때까지 낙찰자가 없습니다. 낙찰 알림도 그때 갑니다. 안 됩니다.

그래서 시계를 보는 별도 프로세스가 필요합니다. 이걸 API 프로세스 안의 asyncio.create_task 로 두면 안 되는 이유가 세 가지입니다. (1) uvicorn --workers 4 면 그 루프도 4개가 되어 서로 같은 경매를 닫으려 합니다(오늘 배우는 SKIP LOCKED 로 막을 순 있지만, 애초에 4개가 돌 이유가 없습니다). (2) API 를 재시작·스케일 다운하면 루프도 같이 사라집니다. (3) 마감 처리가 무거워지면(알림 100건 발송) API 응답이 느려집니다. 별도 프로세스면 API 와 독립적으로 죽이고, 살리고, 개수를 정할 수 있습니다 — 10단계 compose 에 worker 서비스가 따로 생기는 이유입니다.

워커가 별도 프로세스가 되는 순간 새 문제가 생깁니다. 두 개가 돌면? 배포 중엔 반드시 두 개가 잠깐 같이 돕니다(옛 것이 내려가기 전에 새 것이 뜹니다). 같은 경매를 둘 다 "마감 시각 지났네" 하고 닫으면 낙찰 알림이 두 번, 결제 대기표가 두 장. 6단계의 FOR UPDATE 는 "줄을 서서 내 차례에 처리"라 둘째 워커가 기다렸다가 이미 닫힌 경매를 또 닫게 됩니다(재검사가 없으면). 오늘은 그 위에 SKIP LOCKED(남이 잡은 건 건너뛴다) 와 잠근 뒤 재검사를 얹어, 워커가 몇 개든 한 경매는 정확히 한 번 닫히게 합니다.

실무에서 같은 모양이 나오는 곳. "큐에서 작업 하나를 집어 처리하는 워커 N개"는 전부 이 패턴입니다 — 이메일 발송 큐, 이미지 리사이즈, 결제 재시도, 크롤러. Postgres 를 큐로 쓰는 라이브러리(pgqueuer, procrastinate, Oban 등)의 심장도 SELECT … FOR UPDATE SKIP LOCKED LIMIT n 한 줄입니다. 오늘 손으로 만들어 두면 나중에 그런 도구를 쓸 때 안이 보입니다.

비유 — 시계 보는 경매사

시계 보는 경매사. 경매장에 경매사가 한 명 서서 1초마다 벽시계를 봅니다(closer_interval_seconds). "3번 물건, 시작 시각 됐네" → 판을 엽니다(activate_due). "7번 물건, 마감 시각 지났네" → 장부에서 최고 입찰을 찾아 망치를 내리치고(close_due: ended·winner_id), 낙찰자에게 "24시간 안에 계산대로 오세요" 대기표를 끊어 주고(Payment(pending, expires_at)), 장내 방송으로 "7번 낙찰!"을 알립니다(auction_closed 발행 — 7단계의 스피커가 받아서 객석에 틀어 줍니다). "어제 끊어 준 대기표, 24시간 지났네" → 무효 처리합니다(expire_payments). 경매사는 규칙책(services/closer.py)만 봅니다. 시계를 몇 초마다 보는지, 퇴근 신호를 어떻게 받는지는 근무 수칙(workers/closer.py)에 따로 적혀 있습니다.

경매사가 두 명이면. 바쁜 날엔 경매사를 두 명 세웁니다. 둘 다 같은 순간 "7번 마감이네" 하고 다가갑니다. 6단계 방식(FOR UPDATE)은 줄서기입니다 — 둘째가 첫째 뒤에 서서 기다렸다가, 첫째가 끝나면 7번에 또 망치를 내리칩니다(재검사가 없으면). 오늘 방식(SKIP LOCKED)은 "누가 잡고 있는 물건은 건너뛰고 다음 것" 입니다 — 둘째는 7번을 보자마자 8번으로 갑니다. 그래도 혹시 모르니, 물건을 잡은 뒤엔 다시 한 번 확인합니다(잠근 뒤 재검사): "어? 이거 이미 닫혀 있네" 하면 손을 뗍니다. 그리고 계산대는 대기표를 물건당 한 장만 받습니다(payments.auction_id UNIQUE) — 마지막 안전망입니다.

퇴근 신호. 관리자가 "오늘 그만"(SIGTERM)을 외치면, 경매사는 망치를 든 채 도망가지 않습니다. 지금 내리치던 망치까지 끝내고(현재 틱 완료), 장부를 덮고(DB·Redis 연결 정리) 나갑니다. Docker 는 docker stop 뒤 10초를 기다렸다가 강제로 끕니다 — 그 10초 안에 스스로 나가는 게 graceful shutdown 입니다.

설계 그림

첫 그림은 워커의 한 틱입니다. 루프(workers/closer.py)는 세 함수를 차례로 부르고, 함수마다 세션을 새로 엽니다. 활성화와 만료는 UPDATE … WHERE 조건 … RETURNING id 한 문장입니다 — UPDATE 는 바꾸는 행을 스스로 잠그므로 워커가 둘이어도 둘째는 첫째의 커밋을 기다렸다가 조건을 다시 보고(이미 active) 0 행을 바꿉니다. 마감만 복잡합니다. 낙찰자를 찾고 Payment 를 만들고 방송까지 해야 해서 한 문장으로 안 되니, 후보 id 목록을 락 없이 값싸게 뽑은 뒤 한 건씩 잠그고(SKIP LOCKED) 재검사하고 커밋하고, 커밋 뒤에 발행합니다.

둘째 그림은 워커 두 개가 같은 후보 목록을 봤을 때입니다. 실행·확인에서 실제로 돌린 상황 — 같은 순간 마감되는 경매 40개, 워커 두 개(pid 25225·25226), 한 틱에 최대 5건. 둘 다 후보 [#1 #2 #3 #4 #5] 를 뽑습니다. 워커 A 가 #1 을 잠그는 순간, 워커 B 의 SKIP LOCKED 는 #1 을 기다리지 않고 건너뛰어 #2 를 잠급니다. A 는 #1 을 커밋하고 #2 로 가지만 B 가 잡고 있으니 건너뛰고 #3… 이렇게 번갈아 가며 5건을 나눕니다. 둘 다 다음 틱에서 새 후보 5건을 뽑아 반복하고, 결과는 24 : 16, 합쳐서 40개 각 1회. 6단계의 FOR UPDATE(줄서기)였다면 B 는 #1 앞에서 A 를 기다렸다가, 재검사가 없으면 이미 닫힌 #1 을 또 닫습니다.

세 겹의 안전망. ① SKIP LOCKED 는 성능 장치입니다 — 기다리지 않게 해 줄 뿐, 정확성을 보장하진 않습니다. ② 정확성은 잠근 뒤 재검사가 맡습니다 — 후보를 뽑은 순간과 잠근 순간 사이에 다른 워커가 닫고 커밋했을 수 있으니, 잠근 뒤 본 status 만 믿습니다. ③ 그래도 코드에 구멍이 생기면 payments.auction_id UNIQUE 가 두 번째 대기표 INSERT 를 IntegrityError 로 막습니다. 세 겹 중 하나만 믿는 설계는 언젠가 뚫립니다.

구현 — 파일을 하나씩 만든다

순서는 늘 같습니다 — 테스트 먼저(RED), 그다음 통과시킬 코드(GREEN). 이번 테스트의 요령은 하나입니다: 시계를 인자로 넘긴다. "마감 45초 뒤"를 기다리는 테스트는 느리고 불안정합니다. 규칙 함수가 now 를 받으면, 테스트는 NOW = 2026-08-25 12:00 을 정해 두고 경매의 ends_at 을 그 1초 전으로 만들면 됩니다. 파일은 새로 4개, 손보는 건 3개입니다.

1. tests/test_closer.py — 시계를 쥔 테스트

일곱 개입니다. 앞의 다섯은 롤백 세션(db_session)으로 충분합니다 — 서비스가 commit() 해도 3단계 fixture 가 SAVEPOINT 로 받아 주고 끝나면 전부 롤백됩니다. 낙찰(winner·Payment·이벤트 세 가지를 한 번에), 유찰(winner 없음·Payment 없음·이벤트는 감), 마감 전·취소된 경매는 건드리지 않음, 활성화(두 번 돌려도 0), 결제 만료(기한 지난 pending 만). 이벤트는 events.publish 를 monkeypatch 로 기록기로 바꿔 어떤 payload 가 나갔는지 결정적으로 봅니다.

뒤의 둘은 @pytest.mark.commits — 진짜 커밋합니다. 잠금은 서로 다른 커넥션 사이에서만 의미가 있어서, 워커 두 개를 흉내 내려면 세션 두 개로 정말 커밋해야 합니다(6단계와 같은 이유). 마감된 경매 5건을 두 코루틴이 동시에 close_due 하면 합쳐서 정확히 5건, 중복 0, payments 5행. 마지막은 루프 자체: run() 이 interval=0.05 로 돌다가 stop 이 set 되면 돌아오는지, 첫 틱이 5건을 닫고 그다음 틱들은 빈손인지.

async def get_for_update(
    db: AsyncSession, auction_id: uuid.UUID, *, skip_locked: bool = False
) -> Auction | None:
    """행 잠금(SELECT … FOR UPDATE). 이 트랜잭션이 커밋/롤백될 때까지 같은 행을 잠그려는
    다른 트랜잭션은 줄을 선다 → '읽고 → 판단하고 → 쓰는' 사이에 아무도 끼어들지 못한다.

    populate_existing: 이 세션이 같은 행을 이미 읽어 둔 적이 있어도 DB 의 최신 값으로 덮어쓴다.
    (락을 기다리는 동안 누가 값을 바꿨을 수 있다 — 옛 값으로 판단하면 락을 건 의미가 없다.)

    skip_locked=True (8단계): 줄을 서지 않고, 이미 남이 잠근 행이면 None 을 돌려준다.
    입찰(6단계)은 "기다렸다가 내 차례에 처리" 가 맞지만,
    마감 워커는 "남이 하고 있으면 나는 다음 것" 이 맞다.
    """
    stmt = (
        select(Auction)
        .where(Auction.id == auction_id)
        .with_for_update(skip_locked=skip_locked)
        .execution_options(populate_existing=True)
    )
    return await db.scalar(stmt)

async def list_page(
    db: AsyncSession,
    *,
    status: AuctionStatus | None = None,
    category: AuctionCategory | None = None,
    min_price: int | None = None,
    max_price: int | None = None,
    sort: str = "ending_soon",
    limit: int = 20,
    after: tuple[datetime, uuid.UUID] | None = None,
    load_seller: bool = True,
) -> list[Auction]:
    """keyset 페이지 한 장. limit+1 건을 가져와 '다음 페이지가 있나' 를 알려 준다.
    (limit 개로 잘라내는 일은 서비스가 한다.)

    정렬 키는 (시각, id) 쌍이다. 시각이 같은 행이 여러 개여도 id 가 순서를 확정하므로
    페이지 경계에서 같은 행이 두 번 나오거나 빠지는 일이 없다.
    """
    key = Auction.ends_at if sort == "ending_soon" else Auction.created_at
    ascending = sort == "ending_soon"

    stmt = select(Auction)
    if status is not None:
        stmt = stmt.where(Auction.status == status)
    if category is not None:
        stmt = stmt.where(Auction.category == category)
    if min_price is not None:
        stmt = stmt.where(Auction.current_price >= min_price)
    if max_price is not None:
        stmt = stmt.where(Auction.current_price <= max_price)

    if after is not None:
        pair = tuple_(key, Auction.id)  # SQL: (ends_at, id) > ($1, $2)  ← 행 비교
        stmt = stmt.where(pair > after if ascending else pair < after)

    if ascending:
        stmt = stmt.order_by(key.asc(), Auction.id.asc())
    else:
        stmt = stmt.order_by(key.desc(), Auction.id.desc())

    if load_seller:
        stmt = stmt.options(selectinload(Auction.seller))  # 판매자는 IN (...) 한 방으로

    result = await db.scalars(stmt.limit(limit + 1))
    return list(result.all())

핵심 파일입니다. 세 함수 모두 HTTP·루프·시그널을 모르고, now 를 받습니다. activate_due 와 expire_payments 는 update(...).where(...).values(...).returning(id) 한 문장 + 커밋 — UPDATE 가 잠근 행은 커밋까지 다른 UPDATE 를 기다리게 하고, 기다린 쪽은 커밋된 최신 값으로 WHERE 를 다시 평가하므로(READ COMMITTED) 이미 active 인 행은 0 건으로 빠집니다. 워커가 둘이어도 안전한 이유입니다.

close_due 는 설계 그림 그대로입니다. 후보 id 목록 → 한 건씩 get_for_update(skip_locked=True) → None 이면 남의 몫 → 잠근 뒤 status·ends_at 재검사(아니면 rollback() 으로 락만 풀고 다음) → top_bid 로 낙찰자 → ended·winner_id·version+1 → 입찰이 있었으면 Payment(pending, expires_at = now + 24h) → commit() → 그리고 커밋 뒤에 auction_closed 발행과 [notify] 로그. 이메일 발송은 이 프로젝트의 비목표라 로그 한 줄이 알림을 대신합니다. 진짜라면 그 자리에 "알림 큐에 넣기"가 옵니다.

pythonapp/services/closer.py
"""시간이 흐르면 저절로 일어나야 하는 일 세 가지. HTTP 도, 루프도, 시그널도 모른다.

  activate_due   : 시작 시각이 지난 scheduled 경매 → active
  close_due      : 마감 시각이 지난 active 경매 → ended (+ 낙찰자, Payment, auction_closed 이벤트)
  expire_payments: 결제 기한이 지난 pending 결제 → expired

세 함수 모두 `now` 를 인자로 받는다. 워커는 진짜 시계를 넣고, 테스트는 원하는 시각을 넣는다.
누가 부르든(워커 1개든 2개든) 결과가 같아야 한다 — 그게 이 파일의 유일한 어려움이다.
"""

import logging
import uuid
from dataclasses import dataclass
from datetime import datetime, timedelta

from redis.asyncio import Redis
from sqlalchemy import update
from sqlalchemy.ext.asyncio import AsyncSession

from app.core import events
from app.core.config import get_settings
from app.models import Auction, AuctionStatus, Payment, PaymentStatus
from app.repositories import auction as auction_repo
from app.repositories import bid as bid_repo
from app.repositories import payment as payment_repo

logger = logging.getLogger(__name__)


@dataclass(frozen=True)
class ClosedResult:
    auction_id: uuid.UUID
    winner_id: uuid.UUID | None  # None = 유찰 (입찰 0건)
    final_price: int | None
    bid_count: int
    payment_id: uuid.UUID | None


async def activate_due(db: AsyncSession, now: datetime, *, limit: int | None = None) -> int:
    """UPDATE 한 문장. UPDATE 는 스스로 행을 잠그므로 워커가 둘이어도 안전하다 —
    둘째 워커는 첫째의 커밋을 기다렸다가 다시 조건을 보고(이미 active) 0 행을 바꾼다."""
    limit = limit or get_settings().closer_batch_size
    ids = await auction_repo.list_due_scheduled_ids(db, now, limit=limit)
    if not ids:
        return 0
    stmt = (
        update(Auction)
        .where(Auction.id.in_(ids), Auction.status == AuctionStatus.SCHEDULED)  # 조건을 한 번 더
        .values(status=AuctionStatus.ACTIVE, version=Auction.version + 1)
        .returning(Auction.id)
    )
    activated = list((await db.scalars(stmt)).all())
    await db.commit()
    if activated:
        logger.info("activated %d auction(s): %s", len(activated), [str(i)[:8] for i in activated])
    return len(activated)


async def close_due(
    db: AsyncSession, redis: Redis, now: datetime, *, limit: int | None = None
) -> list[ClosedResult]:
    """후보 목록은 락 없이 값싸게 뽑고, 실제 처리는 **한 건씩** 잠그고 커밋한다.

    왜 한 건씩인가: 100건을 한 트랜잭션에 묶으면 (1) 100번째에서 실패하면 99건이 같이 롤백되고,
    (2) 그동안 100개 행이 잠겨 입찰 요청들이 줄을 선다. 한 건씩이면 실패도 잠금도 한 건뿐이다.
    왜 skip_locked 인가: 다른 워커가 이미 잡은 행이면 기다릴 이유가 없다 — 그쪽이 끝낼 것이다.
    왜 재검사인가: 후보를 뽑은 뒤 잠그기까지 사이에 누가 이미 닫았을 수 있다(그 워커가 커밋해서
    락을 풀면 우리는 status=ended 인 행을 잠그게 된다). 잠근 *뒤에* 본 값만 믿는다.
    """
    settings = get_settings()
    limit = limit or settings.closer_batch_size
    results: list[ClosedResult] = []

    for auction_id in await auction_repo.list_due_active_ids(db, now, limit=limit):
        auction = await auction_repo.get_for_update(db, auction_id, skip_locked=True)
        if auction is None:  # 다른 워커가 잠갔거나(skip) 사라졌다 → 내 몫이 아니다
            continue
        if auction.status != AuctionStatus.ACTIVE or auction.ends_at > now:  # 잠근 뒤 재검사
            await db.rollback()  # 잠금만 풀고 다음
            continue

        top = await bid_repo.top_bid(db, auction.id)
        auction.status = AuctionStatus.ENDED
        auction.winner_id = top.bidder_id if top else None
        auction.version += 1

        payment: Payment | None = None
        if top is not None:
            payment = await payment_repo.add(
                db,
                Payment(
                    auction_id=auction.id,
                    payer_id=top.bidder_id,
                    amount=auction.current_price,
                    status=PaymentStatus.PENDING,
                    expires_at=now + timedelta(hours=settings.payment_deadline_hours),
                ),
            )
        await db.commit()  # ← 여기서 이 경매의 락이 풀린다. 아래는 커밋된 사실만 방송한다

        result = ClosedResult(
            auction_id=auction.id,
            winner_id=auction.winner_id,
            final_price=auction.current_price if top else None,
            bid_count=auction.bid_count,
            payment_id=payment.id if payment else None,
        )
        await events.publish(
            redis,
            events.AuctionEvent(
                type="auction_closed",
                auction_id=auction.id,
                payload={
                    "winner_id": result.winner_id,
                    "final_price": result.final_price,
                    "bid_count": result.bid_count,
                    "payment_id": result.payment_id,
                    "payment_expires_at": payment.expires_at if payment else None,
                    "version": auction.version,
                },
            ),
        )
        if top is not None:
            # 진짜라면 여기서 메일/푸시 큐에 넣는다. 이 프로젝트에서는 로그 한 줄이 '알림' 이다.
            logger.info(
                "[notify] user=%s 낙찰! auction=%s %s원 — %s 까지 결제해 주세요",
                str(top.bidder_id)[:8],
                str(auction.id)[:8],
                f"{auction.current_price:,}",
                payment.expires_at.isoformat(timespec="minutes") if payment else "",
            )
        else:
            logger.info("[notify] auction=%s 유찰 (입찰 0건)", str(auction.id)[:8])
        results.append(result)
    return results


async def expire_payments(db: AsyncSession, now: datetime) -> int:
    """기한 지난 pending → expired. activate_due 와 같은 'UPDATE 한 문장' 패턴."""
    stmt = (
        update(Payment)
        .where(Payment.status == PaymentStatus.PENDING, Payment.expires_at <= now)
        .values(status=PaymentStatus.EXPIRED)
        .returning(Payment.id)
    )
    expired = list((await db.scalars(stmt)).all())
    await db.commit()
    if expired:
        logger.info("expired %d payment(s): %s", len(expired), [str(i)[:8] for i in expired])
    return len(expired)

8. app/workers/closer.py — 루프, 시그널, 로그

규칙은 위에 다 있으니 여기엔 "언제 부르나·어떻게 멈추나"만 있습니다. tick() 은 함수마다 SessionLocal() 을 새로 엽니다 — 하나가 실패해도 나머지 둘은 독립적으로 커밋되고, 틱 사이에 커넥션을 쥐고 있지 않습니다. run() 은 stop 이벤트가 set 될 때까지 돌고, 한 틱이 예외로 죽어도 logger.exception 만 남기고 계속 돕니다(워커는 한 번의 실패로 죽으면 안 됩니다). 기다릴 땐 asyncio.sleep(interval) 이 아니라 wait_for(stop.wait(), timeout=interval) — 종료 신호가 오면 interval 을 다 채우지 않고 즉시 깹니다. main() 은 SIGINT/SIGTERM 을 stop.set 에 연결하고, 끝나면 Redis·엔진을 닫습니다. 워커는 자기 Redis 클라이언트를 만듭니다 — API 프로세스의 redis_client 는 다른 프로세스의 것이니까요.

pythonapp/workers/closer.py
"""마감 워커 — API 서버와 **별개의 프로세스**.  실행:  uv run python -m app.workers.closer

하는 일은 단순하다: interval 초마다 시계를 보고 services/closer 의 세 함수를 차례로 부른다.
규칙은 전부 서비스에 있고, 이 파일은 "언제 부르나 · 어떻게 멈추나 · 무엇을 남기나" 만 안다.

왜 API 안의 BackgroundTasks 나 asyncio.create_task 가 아닌가:
  - 요청이 없어도 돌아야 한다 (새벽 3시에 마감되는 경매도 제때 닫혀야 한다)
  - uvicorn --workers 4 면 태스크도 4개가 되고, 서버를 재시작하면 사라진다
  - 별도 프로세스면 API 와 독립적으로 죽이고 살리고 늘릴 수 있다 (10단계 compose 의 `worker` 서비스)
"""

import asyncio
import logging
import signal
from dataclasses import dataclass, field
from datetime import UTC, datetime

from redis.asyncio import Redis

from app.core.config import get_settings
from app.core.db import SessionLocal, engine
from app.services import closer
from app.services.closer import ClosedResult

logger = logging.getLogger("worker.closer")


@dataclass
class TickResult:
    activated: int = 0
    closed: list[ClosedResult] = field(default_factory=list)
    expired: int = 0

    @property
    def empty(self) -> bool:
        return self.activated == 0 and not self.closed and self.expired == 0


async def tick(redis: Redis, now: datetime | None = None) -> TickResult:
    """한 번의 '시계 보기'. 함수마다 세션을 새로 여는 이유: 하나가 실패해도 다른 둘은 독립적으로
    커밋되고, 세션(커넥션)을 틱 사이에 쥐고 있지 않기 위해서다."""
    now = now or datetime.now(UTC)
    result = TickResult()
    async with SessionLocal() as db:
        result.activated = await closer.activate_due(db, now)
    async with SessionLocal() as db:
        result.closed = await closer.close_due(db, redis, now)
    async with SessionLocal() as db:
        result.expired = await closer.expire_payments(db, now)
    return result


async def run(stop: asyncio.Event, redis: Redis, interval: float) -> None:
    """stop 이 set 될 때까지 interval 마다 tick. 한 틱이 실패해도 루프는 죽지 않는다(로그만)."""
    logger.info("closer started (interval=%ss)", interval)
    while not stop.is_set():
        try:
            result = await tick(redis)
            if not result.empty:
                logger.info(
                    "tick: activated=%d closed=%d expired=%d",
                    result.activated,
                    len(result.closed),
                    result.expired,
                )
        except Exception:  # noqa: BLE001 — 워커는 한 틱의 실패로 죽으면 안 된다
            logger.exception("tick failed")
        try:
            # sleep 하면 종료 신호를 interval 만큼 늦게 받는다. stop.wait() 를 기다리면 즉시 깬다.
            await asyncio.wait_for(stop.wait(), timeout=interval)
        except TimeoutError:
            pass
    logger.info("closer stopped")


async def main() -> None:
    settings = get_settings()
    logging.basicConfig(
        level=logging.INFO,
        format="%(asctime)s [pid %(process)d] %(levelname)s %(name)s: %(message)s",
    )
    redis = Redis.from_url(settings.redis_url, decode_responses=True)  # 워커 전용 클라이언트
    stop = asyncio.Event()
    loop = asyncio.get_running_loop()
    for sig in (signal.SIGINT, signal.SIGTERM):  # Ctrl-C, docker stop → 조용히 마무리
        loop.add_signal_handler(sig, stop.set)
    try:
        await run(stop, redis, settings.closer_interval_seconds)
    finally:
        await redis.aclose()
        await engine.dispose()


if __name__ == "__main__":
    asyncio.run(main())

함정 & 실무 팁

API 안의 BackgroundTasks / create_task 로 하지 마세요. BackgroundTasks(8주차·03)는 그 요청이 끝난 뒤 한 번 도는 것이라 "요청 없이 1초마다"엔 맞지 않고, lifespan 의 create_task 루프는 --workers 4 면 4개가 돌고 API 재시작에 사라집니다. 오늘 워커는 별도 프로세스라 10단계 compose 에서 worker 서비스로 따로 띄우고 따로 늘립니다. 7단계 bridge 는 create_task 로 둔 이유가 다릅니다 — 그건 프로세스마다 하나씩 있어야 하는 수신기이니까요.
SKIP LOCKED 는 정확성 장치가 아니라 대기 회피 장치입니다. "남이 잠근 행은 건너뛴다"는 뜻일 뿐, 남이 이미 커밋해서 락을 푼 행은 잡힙니다. 후보를 뽑은 시각과 잠근 시각 사이에 다른 워커가 닫고 커밋했으면 우리는 ended 행을 잠그게 됩니다. 그래서 잠근 뒤 status·ends_at 을 다시 봅니다. 이 재검사를 빼면 워커 두 개가 같은 경매를 두 번 닫고, payments.auction_id UNIQUE 가 마지막에 IntegrityError 로 막아 주는 처지가 됩니다(그러면 그 틱의 나머지 처리도 흔들립니다). NOWAIT 는 건너뛰는 대신 에러를 내는 변형입니다.
발행은 커밋 뒤, 그리고 발행 실패가 DB 를 되돌리지 않게. 7단계와 같은 규칙입니다. 커밋 전에 PUBLISH 하면 구독자가 "아직 DB 에 없는 낙찰"을 보고, 커밋이 실패하면 없던 일이 방송된 채 남습니다. 반대로 커밋 뒤 Redis 가 죽어서 발행이 실패하면? 낙찰은 이미 사실입니다. 소켓 구독자는 못 받지만 GET /auctions/{id} 는 ended 를 줍니다(7단계의 "snapshot 으로 보정"). 그래서 [notify] 로그(진짜라면 알림 큐)는 DB 가 진실이라는 전제로 커밋 뒤에 둡니다.
시계는 하나가 아닙니다. 워커의 datetime.now(UTC) 와 DB 의 now() 는 다른 기계의 시계일 수 있습니다(NTP 로 보통 수십 ms 안이지만). 우리는 앱 시계를 인자로 통일했습니다 — 테스트가 쥘 수 있고, 한 틱 안에서 세 함수가 같은 now 를 봅니다. 그리고 timezone-aware 여야 합니다: datetime.now()(naive) 와 DateTime(timezone=True) 컬럼을 비교하면 TypeError: can't compare offset-naive and offset-aware 가 납니다. 테스트의 NOW = datetime(…, tzinfo=UTC) 도 그래서입니다.
graceful shutdown 은 10초 안에. docker stop 은 SIGTERM 을 보내고 10초 뒤 SIGKILL 입니다(10주차·03). 우리 루프는 SIGTERM → stop.set() → 진행 중인 틱을 끝내고 → closer stopped → Redis·엔진 정리. 한 틱이 10초를 넘기면(후보 100건 × 느린 알림) 도중에 죽습니다 — 그래서 closer_batch_size 가 있고, 무거운 일(메일 발송)은 틱 안에서 직접 하지 말고 큐에 넣습니다. asyncio.sleep(interval) 대신 wait_for(stop.wait()) 를 쓴 것도 종료 지연을 없애기 위해서입니다.
한 건씩 커밋 vs 통째로. 오늘은 한 건 = 한 트랜잭션입니다. 실패의 반경이 한 건이고, 락도 한 행·수 ms 입니다. 대신 100건이면 커밋이 100번 — 건당 수 ms 라 1초 주기 워커엔 충분합니다. 반대로 "1만 건을 한 번에" 같은 배치 작업은 묶어서 커밋하되 청크(예: 500건)로 자릅니다. 기준은 "실패했을 때 되돌려도 되는 단위"입니다.
1초 폴링은 시작점이지 끝이 아닙니다. 폴링은 단순하고 견고하지만(워커가 죽었다 살아나도 그냥 다음 틱에 처리) 마감이 최대 1초 늦고, 경매가 없어도 초당 3개 쿼리를 합니다. 다음 단계들: 마감 시각을 Redis ZSET 에 넣고 ZRANGEBYSCORE 로 "지금 처리할 것"만 보기(딜레이 큐), 또는 arq·Celery beat·pg_cron 같은 스케줄러. 어느 쪽이든 실제 처리 함수는 오늘의 close_due 그대로입니다 — 트리거만 바뀝니다. 그게 규칙을 서비스에, 루프를 워커에 나눠 둔 보상입니다.
워커 테스트가 테스트 DB 를 보는 이유. 3단계 conftest.py 가 앱을 import 하기 전에 os.environ 을 바꿔 두므로, 같은 프로세스에서 app.workers.closer 를 import 하면 같은 테스트 DB·Redis 15번을 봅니다. 루프 테스트는 closer_worker.tick 을 monkeypatch 해서 시계를 고정하고 결과를 기록했습니다 — 루프의 "돌고 멈춘다"만 검사하고 규칙은 앞의 테스트에 맡깁니다. 실행·확인처럼 자식 프로세스로 띄워도 환경변수를 물려받아 테스트 DB 를 봅니다(7단계 live_server 와 같은 원리).
로그의 [notify] 는 알림이 아닙니다. 실무에서 낙찰 알림은 "한 번은 반드시, 두 번은 안 되게"여야 합니다. 로그 한 줄을 이메일 발송으로 바꾸면 (1) 발송 실패 시 재시도가 없고, (2) 워커가 발송 도중 죽으면 유실됩니다. 정석은 close_due 가 같은 트랜잭션에 notifications 행(pending)을 INSERT 하고(=아웃박스), 별도 발송 워커가 그것을 SKIP LOCKED 로 집어 보내고 sent 로 바꾸는 것 — 오늘 배운 패턴 그대로를 한 번 더 쓰는 겁니다. 9주차·02 의 "Pub/Sub 는 방송, 큐는 편지함"이 여기서도 기준입니다.

Q 워커 두 개가 같은 경매를 두 번 닫지 않는 것을 무엇이 보장하나요? SKIP LOCKED 만으로 충분한가요?

아닙니다. SKIP LOCKED 는 "지금 남이 잠근 행은 건너뛴다"일 뿐, 후보를 뽑은 뒤 남이 닫고 커밋해서 락을 푼 행은 잡힙니다. 정확성은 잠근 뒤 재검사(status == active and ends_at <= now) 가 보장합니다 — 잠근 뒤 본 값은 커밋된 최신 값이고, 우리가 커밋할 때까지 아무도 못 바꾸니까요. 그리고 코드에 구멍이 나도 payments.auction_id UNIQUE 가 두 번째 대기표를 막습니다. 실행·확인의 40 1 이 세 겹이 함께 낸 결과입니다.

Q 마감 처리를 FastAPI 의 BackgroundTasks 나 lifespan 의 asyncio.create_task 로 하면 어떤 문제가 생기나요? 7단계 bridge 는 create_task 인데 왜 괜찮은가요?

BackgroundTasks 는 어떤 요청이 끝난 뒤 한 번 도는 것이라 "요청이 없어도 1초마다"엔 쓸 수 없습니다. lifespan 의 create_task 루프는 --workers 4 면 4개가 같은 경매를 닫으려 들고, API 재시작·스케일 다운에 사라지며, 무거운 마감 처리가 API 응답을 늦춥니다. 별도 프로세스면 API 와 독립적으로 죽이고 살리고 개수를 정합니다. bridge 가 create_task 여도 되는 이유는 정반대입니다 — bridge 는 프로세스마다 하나씩 있어야 하는 수신기라, 워커가 4개면 4개 있는 게 맞습니다.

Q 워커가 auction_closed 를 발행한 순간 Redis 가 죽어 있었습니다. 낙찰은 어떻게 되고, 사용자는 어떻게 알게 되나요? 낙찰 이메일도 같은 방식으로 보내도 될까요?

낙찰은 이미 커밋된 사실이라 그대로입니다 — 발행은 커밋 뒤라서 DB 가 진실입니다. 소켓 구독자는 그 이벤트를 못 받지만, 다시 접속하면 snapshot 이 ended 를 주고 GET /auctions/{id} 도 winner_id 를 줍니다(7단계의 "이벤트는 현재 값, 놓치면 snapshot"). 이메일은 다릅니다. 한 번은 반드시 가야 하고 두 번 가면 안 되니, 방송(Pub/Sub)이 아니라 편지함이 필요합니다 — close_due 가 같은 트랜잭션에 notifications(pending) 행을 넣고(아웃박스), 발송 워커가 SKIP LOCKED 로 집어 보내고 sent 로 바꿉니다. 오늘 배운 패턴을 한 번 더 쓰는 것입니다.
