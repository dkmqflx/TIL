9-1 개요와 설계

8단계가 끊어 준 결제 대기표(Payment(pending))를 드디어 paid 로 바꿉니다. 그러려면 우리 서버가 처음으로 바깥 서비스를 부르고(낙찰자가 POST /payments/{id}/checkout → 우리가 결제사(PG)에 결제를 연다), 처음으로 바깥에서 걸려오는 요청을 받습니다(PG 가 "결제됐어요"를 POST /webhooks/payments 로 알려 온다 — 이것이 웹훅). 나가는 쪽은 타임아웃·재시도, 들어오는 쪽은 서명 검증·멱등 처리가 핵심입니다. 진짜 PG 대신 우리가 만든 모의 PG(mock_pg/, 8001 포트)를 씁니다 — 키 발급 없이 돌고, 배울 것은 전부 들어 있습니다.

한 줄 요약. 이 문서를 끝내면 uv run pytest -q가 87 passed를 찍고, 낙찰자가 checkout 을 누르면 모의 PG 가 external_id 를 주고 1초 뒤 서명된 웹훅을 보내와 결제가 paid 로 바뀌며, 그 웹훅을 그대로 다시 보내면 {"received":true,"duplicate":true}(아무것도 안 바뀜), 본문을 한 글자 바꾸거나 서명을 빼면 401 INVALID_SIGNATURE, PG 가 3초 넘게 대답이 없으면 두 번 더 두드린 뒤 502 PG_UNAVAILABLE 이 됩니다 — 그리고 이 모든 것을 진짜 PG 없이 respx 로 테스트합니다.

학습 목표

  • 웹훅이 무엇이고, 왜 "요청에 대한 응답"만으로는 결제 결과를 알 수 없는지 설명할 수 있다
  • 바깥으로 나가는 HTTP 호출에 타임아웃을 걸고, 다시 해도 안전한 실패에만 재시도하는 법을 안다
  • HMAC 서명을 파싱 전 원문 바이트로 검증해야 하는 이유와 compare_digest 를 쓰는 이유를 안다
  • 같은 웹훅이 두 번 와도 상태를 두 번 바꾸지 않게(멱등) event_id 장부 + INSERT … ON CONFLICT DO NOTHING 으로 막을 수 있다
  • respx 로 "PG 가 200 / 타임아웃 / 500 뒤 200" 을 연출해 외부 연동을 결정적으로 테스트할 수 있다
  • BackgroundTasks 가 "응답 먼저, 일은 나중에"에 딱 맞는 자리를 모의 PG 에서 직접 본다
🎯

이 단계의 목표

8단계까지의 결제는 대기표뿐이었습니다. 워커가 Payment(pending, expires_at = 24시간 뒤) 를 만들어 두고, 기한이 지나면 expired 로 바꿨습니다. 그런데 정작 돈을 내는 길이 없었습니다. 이번 단계가 끝나면 낙찰자가 POST /payments/{id}/checkout 을 부르는 순간 우리 서버가 PG 에 결제를 열어 external_id(PG 가 발급한 결제 번호)를 받아 두고, PG 가 결제 결과를 POST /webhooks/payments 로 알려 오면 서명을 확인하고 paid + paid_at 으로 바꾸며, 7단계 소켓 구독자에게 payment_completed 를 방송합니다. 그리고 그 웹훅이 두 번 오든, 누가 흉내 내든, PG 가 먹통이든 — 결제는 정확히 한 번만, 진짜 PG 의 말만 듣고 바뀝니다.

진짜 PG(토스·포트원 등)는 붙이지 않습니다(설계 문서의 비목표). 대신 mock_pg/main.py 라는 60줄짜리 가짜 PG 를 8001 포트에 따로 띄웁니다. 결제를 만들어 달라고 하면 external_id 를 주고, 1초 뒤 우리 서버의 callback_url 로 서명된 웹훅을 보냅니다. 진짜 PG 가 하는 일의 뼈대가 정확히 이것이라, 나중에 진짜를 붙일 때는 URL·본문 모양·서명 규칙만 그 PG 문서대로 바꾸면 됩니다.

전제. 8단계가 끝나 있어야 합니다. uv run pytest -q → 71 passed, 컨테이너 두 개 (healthy). 새로 설치하는 패키지는 httpx(앱이 PG 를 부를 때) 와 respx(테스트에서 그 호출을 가로챌 때) 둘입니다. 마이그레이션이 하나 생깁니다 — webhook_events 테이블과 payments.external_id 인덱스. 작업 위치는 til/backend/fastapi/auction-api/.

이번 단계에서 만드는 것. 새 파일 9개(core/http.py 나가는 클라이언트, models/webhook_event.py 장부, repositories/webhook_event.py, schemas/payment.py, services/pg_client.py 타임아웃·재시도, services/payment.py 규칙, routers/payments.py, routers/webhooks.py, mock_pg/main.py, tests/test_payments.py), 손보는 파일 8개(설정 5개 값, security.py 서명 두 함수, deps.py, exceptions.py 예외 8개, models/payment.py 인덱스, models/__init__.py, repositories/payment.py 조회 3개, main.py). 8단계 워커는 한 줄도 안 바꿉니다 — 오늘도 expire_payments 가 "기한 내 미결제" 를 맡습니다.
🏢

왜 필요한가 — 실무 맥락

지금까지 우리 서버는 늘 응답하는 쪽이었습니다. 클라이언트가 묻고 우리가 답했습니다. 결제는 그 모양이 깨지는 첫 지점입니다. 돈은 우리 DB 가 아니라 결제사 가 움직입니다. 카드 승인, 계좌 이체, 간편결제 — 전부 PG 서버 안에서 일어나고, 그 결과는 몇 초 뒤일 수도 몇 분 뒤일 수도 있습니다(가상계좌 입금은 며칠). 그래서 결제 연동은 반드시 두 방향입니다. ① 우리가 PG 에 "이 금액으로 결제 열어 줘"(나가는 호출). ② PG 가 우리에게 "결제 끝났어"(들어오는 호출 = 웹훅). ②를 우리가 폴링으로 대신할 수도 있지만(1초마다 "됐어?" 묻기), PG 는 그걸 싫어하고 우리도 낭비입니다. 결과가 났을 때 PG 가 우리를 부르는 게 웹훅이고, Stripe·토스·GitHub·Slack 이 전부 이 방식입니다.

들어오는 호출은 새 문제를 셋 데려옵니다. 첫째, 누가 보냈나. /webhooks/payments 는 로그인 토큰이 없습니다 — PG 는 우리 사용자가 아닙니다. 누구나 URL 만 알면 "결제됐어" 라고 POST 할 수 있습니다. 그래서 PG 와 우리만 아는 비밀키로 본문에 서명하고, 우리는 같은 계산을 해서 맞는지 봅니다(HMAC). 둘째, 몇 번 오나. PG 는 우리가 2xx 를 줄 때까지 재전송합니다. 네트워크가 잠깐 끊겨 우리 응답이 PG 에 안 닿으면, 우리는 이미 처리했는데 같은 웹훅이 또 옵니다. 두 번 처리하면 "결제 완료 알림 두 번", 환불이면 "두 번 환불". 그래서 멱등이어야 합니다 — 같은 걸 몇 번 받아도 결과가 한 번과 같게. 셋째, 언제 오나. 우리 checkout 응답이 채 끝나기도 전에 웹훅이 먼저 도착할 수도 있고, 실패 웹훅 뒤에 성공 웹훅이 올 수도 있습니다. 순서를 믿지 말고 현재 상태를 보고 판단해야 합니다.

나가는 호출도 처음입니다(7주차·02 에서 httpx 를 배웠지만 실전 규칙은 이제). 바깥 서비스는 느릴 수 있고 잠깐 죽을 수 있습니다. 타임아웃이 없으면 PG 가 멈춘 3분 동안 우리 요청 하나가 커넥션과 워커를 붙잡습니다. 재시도가 없으면 0.1초짜리 네트워크 딸꾹질에 결제가 실패합니다. 재시도를 아무 데나 하면 4xx(우리 요청이 틀린 것)를 세 번 보내 세 번 거절당합니다. 오늘은 이 규칙들을 pg_client.py 한 파일에 넣고, respx 로 "타임아웃 세 번", "500 한 번 뒤 200" 을 연출해 테스트합니다.

실무에서 같은 모양이 나오는 곳. 결제뿐 아니라 이메일 발송 결과(SendGrid), SMS 수신, GitHub push 이벤트, Slack 슬래시 명령, 배송 상태 변경 — 전부 "서명된 웹훅을 받아 멱등하게 처리" 입니다. 오늘 만드는 verify_signature + try_record(event_id) 두 조각은 그대로 다른 웹훅에도 씁니다. 그리고 진짜 PG 를 붙일 때 가장 먼저 읽을 문서 제목이 바로 "Webhook 서명 검증" 과 "멱등키(Idempotency-Key)" 입니다.

비유 — 택배 기사의 문자

택배 기사의 문자. 온라인으로 물건을 팔았다고 합시다. 당신(우리 서버)이 택배사(PG)에 접수합니다 — "이 주소로 이 물건, 착불 12,000원". 택배사는 즉시 운송장 번호(external_id)를 줍니다. 아직 배송은 안 됐습니다, 번호만 받은 겁니다(checkout → status: pending, external_id: pg_…). 며칠 뒤 기사님이 "배송 완료" 문자를 보냅니다(웹훅). 당신은 그 문자를 보고 장부에 "수금 완료" 라고 적습니다(paid).

그런데 문자는 아무나 보낼 수 있습니다. 사기꾼이 "배송 완료" 라고 문자하면? 그래서 택배사와 당신은 암호 도장을 미리 나눠 가졌습니다(pg_webhook_secret). 기사는 문자 내용 전체에 도장을 찍어 보내고(X-PG-Signature), 당신은 같은 도장을 같은 내용에 찍어 봐서 무늬가 같아야 믿습니다(HMAC). 문자에서 글자 하나라도 고치면 무늬가 완전히 달라집니다 — 그래서 받은 그대로(원문 바이트)에 도장을 대 봐야 합니다. 예쁘게 다시 타이핑한 뒤에 대 보면 절대 안 맞습니다.

그리고 기사님은 답장을 못 받으면 같은 문자를 또 보냅니다. 두 번째 문자에 또 "수금 완료" 를 적으면 장부에 12,000원이 두 번 들어옵니다. 그래서 문자마다 문자 번호(event_id)가 있고, 당신은 받은 번호를 수첩(webhook_events)에 적어 둡니다. 새 문자가 오면 먼저 수첩을 봅니다 — 이미 있는 번호면 "응, 받았어" 만 답하고(duplicate: true) 장부는 건드리지 않습니다. 수첩에 적는 것과 장부에 적는 것을 한 번에(같은 트랜잭션) 해야 합니다. 수첩에만 적고 장부를 못 적으면, 다음 문자를 "이미 처리했다" 고 넘겨 버리니까요.

접수가 안 될 때. 택배사 전화가 통화 중이면(타임아웃) 잠시 뒤 한두 번 더 겁니다(재시도). 하지만 "주소가 없는 동네입니다" 라고 거절당하면(4xx) 백 번 걸어도 같습니다 — 그건 재시도가 아니라 우리 쪽 수정 대상입니다. 그리고 세 번 걸어도 안 받으면 손님에게 "택배사 연결이 안 됩니다, 잠시 후 다시" 라고 솔직히 말합니다(502 PG_UNAVAILABLE) — 우리 잘못인 척(500) 하지도, 된 척(200) 하지도 않습니다.

설계 그림

첫 그림은 두 방향입니다. 왼쪽 절반은 우리가 부르는 쪽: 낙찰자의 checkout 요청이 오면 결제 행을 잠그고(더블클릭 두 요청이 PG 결제를 두 개 열지 않게) 규칙을 검사한 뒤 pg_client.create_payment 가 httpx 로 모의 PG 를 부릅니다. 타임아웃 3초, 타임아웃·5xx 면 0.1초·0.2초 쉬고 두 번 더. 받은 external_id 를 저장하고 커밋합니다. 오른쪽 절반은 PG 가 부르는 쪽: 모의 PG 는 응답을 준 뒤 BackgroundTasks 로 1초 기다렸다가 callback_url 에 서명된 웹훅을 POST 합니다. 우리 라우터는 원문 바이트로 서명부터 확인하고, 그다음 파싱하고, 서비스가 event_id 를 장부에 적고(처음이면), external_id 로 결제를 잠가 paid 로 바꾸고, 커밋 뒤 payment_completed 를 방송합니다.

둘째 그림은 같은 웹훅이 세 번 왔을 때입니다. 실행·확인에서 실제로 해 보는 순서 그대로입니다. 첫 번째는 정상 처리(장부 기록 + paid 가 한 트랜잭션). 두 번째는 바이트까지 똑같은 재전송 — 서명은 맞고, 장부에 event_id 가 이미 있어 INSERT … ON CONFLICT DO NOTHING 이 아무 행도 돌려주지 않습니다 → duplicate: true, 결제는 건드리지 않습니다. 세 번째는 본문을 한 글자 바꾼 것(amount: 1) — 서명이 안 맞아 파싱도 하기 전에 401 입니다. 그리고 만약 external_id 가 우리 DB 에 없다면? 장부에 적은 직후 예외를 던지므로 트랜잭션이 롤백되어 장부 기록도 사라집니다 — PG 가 재전송하면 다시 처음부터 검토합니다. "기록했지만 처리 못 한" 이벤트가 남지 않는 게 요점입니다.

왜 장부를 Redis SETNX 가 아니라 DB 테이블로 했나. 장부 기록과 결제 상태 변경이 같은 트랜잭션이어야 "기록은 됐는데 상태는 안 바뀐" 반쪽 상태가 생기지 않습니다. Redis 에 적으면 그 순간 Redis 는 확정인데 DB 커밋이 실패할 수 있고, 그러면 다음 재전송을 "이미 처리함" 으로 넘겨 결제가 영원히 pending 으로 남습니다. 같은 이유로 예외가 나면 장부 기록도 같이 롤백되는 게 맞습니다. Redis 방식은 "웹훅이 초당 수천 건이고 DB 쓰기를 아끼고 싶을 때" 의 최적화이며, 그때도 TTL 과 실패 처리를 따로 설계해야 합니다.
