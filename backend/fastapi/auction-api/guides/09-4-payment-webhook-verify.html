실행·확인 — 이 출력이 나와야 한다

터미널 세 개를 씁니다. 1번은 API, 2번에서 워커와 모의 PG 를 백그라운드로 띄우고, 3번에서 시나리오를 돌립니다. 흐름은 8단계 실행·확인의 뒤를 잇습니다 — 45초 경매가 마감되어 Payment(pending) 이 생기는 데까지가 8단계, 거기서 checkout → 웹훅 → paid 가 오늘입니다. 모의 PG 로그(mockpg.log)에 남은 서명과 본문으로 "같은 웹훅 재전송" 과 "본문 변조" 를 직접 해 봅니다.

2. 낙찰까지 — 45초 경매, 입찰 한 건, 소켓 리스너

8단계와 같은 이유로 45초입니다(30초 스나이핑 창 밖). 리스너는 75초 동안 듣습니다 — 마감 뒤 결제까지 봐야 하니까요. 입찰 뒤에 리스너가 붙어서 snapshot 에 bid_count 1 로 보이고 bid_placed 는 없습니다.

bash터미널 3
J='Content-Type: application/json'
for who in alice bob; do
  curl -s -X POST localhost:8000/auth/signup -H "$J" \
    -d "{\"email\":\"$who@example.com\",\"password\":\"secret123\",\"nickname\":\"$who\"}" > /dev/null
done
tok() { curl -s -X POST localhost:8000/auth/login -H "$J" \
  -d "{\"email\":\"$1@example.com\",\"password\":\"secret123\"}" \
  | python3 -c 'import sys,json; print(json.load(sys.stdin)["access_token"])'; }
ALICE=$(tok alice); BOB=$(tok bob)
ENDS=$(python3 -c "from datetime import datetime, timedelta, UTC; print((datetime.now(UTC)+timedelta(seconds=45)).isoformat())")
A=$(curl -s -X POST localhost:8000/auctions -H "Authorization: Bearer $ALICE" -H "$J" \
  -d "{\"title\":\"기계식 키보드\",\"category\":\"electronics\",\"starting_price\":10000,\"ends_at\":\"$ENDS\"}" \
  | python3 -c 'import sys,json; d=json.load(sys.stdin); print(d["id"])')
nohup uv run python scripts/ws_listen.py $A $BOB 75 > listener.log 2>&1 &
curl -s -X POST localhost:8000/auctions/$A/bids -H "Authorization: Bearer $BOB" -H "$J" -d '{"amount":10000}' \
  | python3 -c 'import sys,json; d=json.load(sys.stdin); print("bid ok · current_price", d["current_price"], "· bid_count", d["bid_count"])'
# bid ok · current_price 10000 · bid_count 1
echo "45초 경매가 끝나길 기다린다…"; sleep 50
grep "낙찰" worker.log | tail -1
# 2026-08-26 00:36:19,439 [pid 72335] INFO app.services.closer: [notify] user=65dbc27d 낙찰! auction=ab184d77 10,000원 — 2026-08-26T15:36+00:00 까지 결제해 주세요

3. checkout → 1초 뒤 웹훅 → paid

결제 id 는 payments 테이블에서 꺼냅니다(경매 응답엔 없습니다 — 소켓의 auction_closed 에는 있습니다; 진짜 서비스라면 낙찰자용 GET /auctions/{id}/payment 같은 길이 필요합니다). checkout 응답의 external_id 가 모의 PG 가 준 번호입니다. 3초 뒤 다시 보면 paid — 그 사이 모의 PG 가 웹훅을 보냈고(mockpg.log 의 webhook paid → 200), 우리 서버가 받아 상태를 바꾸고 payment_completed 를 방송했습니다(listener.log).

bash터미널 3
P=$(docker compose exec -T db psql -U auction -d auction -tA -c "SELECT id FROM payments WHERE auction_id='$A'")
echo "payment_id=$P"
curl -s -X POST localhost:8000/payments/$P/checkout -H "Authorization: Bearer $BOB"; echo
# {"payment_id":"a44eb25f-bebf-4979-925e-4d4bac7df99f","external_id":"pg_d7e13202c503","status":"pending"}
sleep 3   # mock_pg 가 1초 뒤 웹훅을 보낸다 — 우리는 그걸 받아 paid 로 바꾼다
curl -s localhost:8000/payments/$P -H "Authorization: Bearer $BOB" \
  | python3 -c 'import sys,json; d=json.load(sys.stdin); print("status", d["status"], "· paid_at", d["paid_at"], "· external_id", d["external_id"])'
# status paid · paid_at 2026-08-25T15:36:24.919077Z · external_id pg_d7e13202c503
grep "webhook paid" mockpg.log | tail -1
# 2026-08-26 00:36:24,925 mock_pg webhook paid → 200 {"received":true,"duplicate":false}
grep -E "^\[" listener.log
# [snapshot] {"status": "active", "current_price": 10000, "bid_count": 1, "ends_at": "…", "version": 1, …}
# [auction_closed] {"winner_id": "…", "final_price": 10000, "bid_count": 1, "payment_id": "a44eb25f-…", …}
# [payment_completed] {"payment_id": "a44eb25f-…", "amount": 10000, "paid_at": "2026-08-25T15:36:24.919077Z"}
읽는 법. 리스너 세 줄이 이 프로젝트의 결제 흐름 전체입니다: [auction_closed](8단계 워커가 발행, payment_id 포함) → [payment_completed](오늘 웹훅 핸들러가 발행). 발행한 프로세스가 워커·API 로 다르지만 채널이 같아 7단계 bridge 가 둘 다 흘려보냈습니다. paid_at 은 UTC(Z), 워커 로그는 로컬 시각 — 같은 순간입니다.

4. 같은 웹훅을 다시 · 본문을 바꿔서 · 서명 없이

모의 PG 가 로그에 남긴 서명(sig=)과 본문(body=)을 그대로 꺼내 우리 서버에 다시 보냅니다. 서명이 맞으니 401 은 아니지만, 장부에 있는 event_id 라 duplicate: true — 결제는 이미 paid 이고 아무것도 안 바뀝니다. 그다음 본문의 10000 을 1 로 바꿔 같은 서명으로 보내면 401, 서명 헤더를 빼면 401. 마지막으로 장부를 보면 event_id 가 딱 한 줄입니다.

bash터미널 3
SIG=$(grep -o 'sig=[0-9a-f]*' mockpg.log | tail -1 | cut -d= -f2)
BODY=$(grep -o 'body=.*' mockpg.log | tail -1 | cut -d= -f2-)
echo "$BODY"
# {"event_id": "evt_3f69e0856782", "external_id": "pg_d7e13202c503", "payment_id": "a44eb25f-…", "status": "paid", "amount": 10000}
curl -s -X POST localhost:8000/webhooks/payments -H "$J" -H "X-PG-Signature: $SIG" -d "$BODY"; echo
# {"received":true,"duplicate":true}          ← 같은 event_id: 받긴 했지만 아무것도 바꾸지 않았다
curl -s -w " %{http_code}\n" -X POST localhost:8000/webhooks/payments -H "$J" -H "X-PG-Signature: $SIG" \
  -d "${BODY/\"amount\": 10000/\"amount\": 1}"
# {"code":"INVALID_SIGNATURE","message":"웹훅 서명이 올바르지 않습니다"} 401   ← 본문을 바꾸면 서명이 안 맞는다
curl -s -w " %{http_code}\n" -X POST localhost:8000/webhooks/payments -H "$J" -d "$BODY"
# {"code":"INVALID_SIGNATURE","message":"웹훅 서명이 올바르지 않습니다"} 401   ← 서명 없음
docker compose exec db psql -U auction -d auction -c "SELECT event_id, received_at FROM webhook_events"
#      event_id     |          received_at
# ------------------+-------------------------------
#  evt_3f69e0856782 | 2026-08-25 15:36:24.913606+00
# (1 row)
-d "$BODY" 여야 하는 이유. curl 은 -d 문자열을 그대로 보냅니다. 만약 python -c 'json.dumps(...)' 로 본문을 새로 만들어 보내면 공백 하나 차이로 서명이 안 맞습니다 — 그게 3회차 401 의 원리이기도 합니다. 진짜 PG 대시보드의 "웹훅 재전송" 버튼도 바이트까지 같은 본문을 다시 보냅니다.

함정 & 실무 팁

서명은 원문 바이트로, 파싱 전에. 가장 흔한 실패입니다: data: PgWebhook 로 받은 뒤 json.dumps(data.model_dump()) 로 서명을 계산하면 공백·키 순서·숫자 표기가 달라져 절대 맞지 않습니다. await request.body() 가 먼저, 검증이 그다음, 파싱은 맨 나중입니다. 그리고 비교는 hmac.compare_digest — == 는 첫 불일치에서 멈춰 응답 시간이 새고, 공격자가 한 글자씩 맞춰 갈 수 있습니다. PG 마다 서명 규칙이 다릅니다(본문만 / timestamp + 본문 / 헤더 이름). 붙이기 전에 문서의 "서명 검증" 절부터 읽으세요.
2xx 는 빨리, 무거운 일은 나중에. PG 는 우리가 2xx 를 몇 초 안에 주지 않으면 실패로 보고 재전송합니다(그러면 멱등 처리가 또 돕니다 — 정상이지만 낭비). 웹훅 핸들러 안에서 이메일을 보내거나 외부 API 를 부르면 그 시간만큼 위험합니다. 우리 핸들러는 DB 쓰기 한 번과 PUBLISH 하나뿐입니다. 더 무거운 후속 작업은 8단계 방식(테이블에 적고 워커가 처리)으로 넘깁니다.
재시도는 '다시 해도 안전한' 실패에만. 타임아웃·연결 실패·5xx 는 PG 가 우리 요청을 못 받았을 가능성이 있어 재시도 가치가 있습니다. 4xx 는 받았고 거절한 것 — 재시도해도 같습니다. 그런데 타임아웃엔 함정이 있습니다: PG 가 요청을 받아 처리했는데 응답만 늦게 온 경우, 우리 재시도가 PG 결제를 두 개 만들 수 있습니다. 진짜 PG 는 그래서 Idempotency-Key 헤더(우리 payment_id 를 넣으면 됩니다)를 받아 같은 키면 같은 결제를 돌려줍니다. 모의 PG 엔 없습니다 — 셀프 체크 3번에서 이어집니다.
바깥 호출엔 예외 없이 타임아웃. httpx 기본값도 5초가 있지만, 우리는 설정으로 명시합니다(pg_timeout_seconds). 타임아웃 없는 외부 호출 하나가 PG 장애 때 우리 서버의 워커·커넥션을 전부 붙잡아 "PG 가 죽었더니 우리도 죽었다" 가 됩니다. 4주차·02 의 블로킹 함정과 같은 결말이며, 원인만 다릅니다. 그리고 PG 호출 동안 결제 행 락을 쥐고 있는 우리 설계는 편하지만 락 시간이 최대 3초 × 3회입니다 — 트래픽이 크면 "PG 호출 전에 external_id 예약 표시 후 커밋, 호출 뒤 갱신" 두 단계로 바꿉니다.
웹훅이 말하는 숫자를 믿지 마세요. 서명이 맞아도 본문의 amount 는 우리 기록과 대조합니다(AMOUNT_MISMATCH). PG 쪽 버그·설정 실수·테스트 데이터 섞임은 서명으로 못 막습니다. 마찬가지로 payment_id 도 external_id 로 찾은 결제와 같은지 봅니다. "권한은 서명이, 정합성은 대조가" — 둘은 다른 문제입니다.
순서를 믿지 마세요, 상태를 보세요. failed 뒤에 paid, paid 뒤에 뒤늦은 failed, checkout 커밋 전에 웹훅 — 전부 실제로 일어납니다. 우리 서비스는 "지금 pending 이면 바꾼다, 아니면 로그만" 으로 어느 순서든 같은 결과를 냅니다. 커밋 전 웹훅은 FOR UPDATE 락이 기다리게 해서 풀었습니다. 실행·확인에서 모의 PG 의 1초 지연을 0 으로 줄여(PG_WEBHOOK_DELAY=0) 이 경쟁을 직접 만들어 볼 수 있습니다.
장부는 남기고, 실패는 롤백. try_record 뒤에 예외가 나면 장부 기록도 같이 사라져 PG 재전송 때 다시 검토됩니다 — 의도한 설계입니다. 반대로 "처리는 됐는데 방송(PUBLISH)만 실패" 는 커밋 뒤라 상태는 유지되고, 7단계의 snapshot 이 보정합니다. 장부는 자라기만 하니 운영에선 오래된 행을 주기적으로 지웁니다(PG 의 재전송 창은 보통 며칠) — 8단계 워커에 DELETE FROM webhook_events WHERE received_at < now() - interval '30 days' 한 문장을 더하면 됩니다.
로컬에선 PG 가 localhost 를 못 부릅니다. 오늘은 모의 PG 도 내 컴퓨터라 http://localhost:8000 이 통했습니다. 진짜 PG 는 인터넷에서 우리 서버를 찾아야 하므로 로컬 개발엔 ngrok http 8000 같은 터널로 받은 공개 URL 을 PUBLIC_BASE_URL 에 넣습니다. 스테이징·운영은 당연히 HTTPS 도메인이고, 비밀키는 환경마다 다르게 발급해 회전할 수 있어야 합니다(옛 키·새 키를 잠깐 둘 다 허용하는 기간을 두는 게 정석입니다).
respx 는 httpx 만 가로챕니다. 앱이 httpx 를 쓰고 테스트 클라이언트가 httpx2 라서 둘이 섞이지 않습니다 — client.post("/payments/…")(httpx2, ASGI 직접 호출) 는 respx 를 지나가지 않고, 그 안에서 앱이 부르는 http.post("http://localhost:8001/…")(httpx) 만 가로채집니다. respx.mock(base_url=…) 안의 route.calls[0].request.content 로 "우리가 PG 에 뭘 보냈나" 까지 검사할 수 있습니다. 10주차·01 의 mocking 절이 배경입니다.

셀프 체크

Q 웹훅 라우터가 data: PgWebhook 으로 본문을 받지 않고 request.body() 를 먼저 읽는 이유는? 그리고 서명 비교에 == 대신 compare_digest 를 쓰는 이유는?

서명은 PG 가 보낸 바이트에 대해 계산됐습니다. FastAPI 가 파싱한 객체를 다시 JSON 으로 만들면 공백·키 순서·숫자 표기가 달라져 같은 내용이어도 다른 바이트가 되고, 서명이 맞지 않습니다. 그래서 원문 바이트 → 서명 검증 → 그다음 파싱입니다(검증 전엔 파싱할 이유도 없습니다 — 누가 보낸지도 모르는 본문이니까요). == 는 첫 불일치에서 멈추기 때문에 앞 글자가 맞을수록 조금 더 오래 걸리고, 그 차이를 수천 번 재면 서명을 한 글자씩 맞춰 갈 수 있습니다(타이밍 공격). compare_digest 는 길이가 같으면 항상 같은 시간이 걸립니다.

Q 같은 웹훅이 동시에 두 요청으로 들어오면 어떻게 되나요? 그리고 external_id 가 우리 DB 에 없는 웹훅이 오면 장부(webhook_events)엔 무엇이 남나요?

둘 다 INSERT … ON CONFLICT DO NOTHING RETURNING 을 실행합니다. Postgres 는 같은 PK 를 넣으려는 두 번째 트랜잭션을 첫 번째가 커밋/롤백할 때까지 기다리게 하고, 첫 번째가 커밋하면 두 번째의 INSERT 는 충돌로 아무 행도 돌려주지 않습니다 → duplicate: true. 정확히 하나만 결제를 바꿉니다 — 6단계 락과 같은 원리이지만 명시적 FOR UPDATE 없이 PK 제약 자체가 줄을 세웁니다. 모르는 external_id 면 장부에 적은 직후 PaymentNotFoundError 를 던지고, 그 트랜잭션은 커밋되지 않으므로 장부 기록도 사라집니다 — 아무것도 남지 않습니다. PG 가 재전송하면 처음부터 다시 검토하고, 그때 결제가 생겨 있으면 정상 처리됩니다. "기록은 됐는데 처리는 안 된" 이벤트가 생기지 않도록 장부와 처리를 한 트랜잭션에 둔 결과입니다.

Q checkout 중 PG 가 결제를 만들긴 했는데 응답이 3초를 넘겨 타임아웃이 났고, 우리는 재시도해서 두 번째 결제도 만들었습니다. 이제 PG 가 첫 번째 결제의 웹훅을 보내면 우리 코드는 어떻게 반응하고, 실무에선 어떻게 막나요?

우리는 두 번째 external_id 만 저장했으니 첫 번째 웹훅은 get_by_external_id_for_update 에서 못 찾아 404 — PG 는 계속 재전송하고 운영자가 봐야 합니다. 첫 번째 결제로 실제 돈이 빠졌다면 고객은 이중 결제입니다. 그래서 진짜 PG 는 결제 생성에 멱등키(Idempotency-Key 헤더 — 우리 payment_id 를 넣으면 됩니다)를 받습니다: 같은 키로 다시 부르면 새로 만들지 않고 같은 external_id 를 돌려줍니다. 그러면 타임아웃 뒤 재시도가 안전해집니다. 우리 쪽 보완은 웹훅에 실려 오는 payment_id 로도 결제를 찾아 external_id 를 맞춰 주는 것입니다(본문에 이미 있습니다). 오늘의 pg_client 에 헤더 한 줄과 mock_pg 에 "같은 payment_id 면 같은 external_id" 를 더하면 완성됩니다 — 좋은 연습 과제입니다.
