9단계 — 결제 웹훅: 밖으로 부르고, 밖에서 받고

8단계가 끊어 준 결제 대기표(Payment(pending))를 드디어 paid 로 바꿉니다. 그러려면 우리 서버가 처음으로 바깥 서비스를 부르고(낙찰자가 POST /payments/{id}/checkout → 우리가 결제사(PG)에 결제를 연다), 처음으로 바깥에서 걸려오는 요청을 받습니다(PG 가 "결제됐어요"를 POST /webhooks/payments 로 알려 온다 — 이것이 웹훅). 나가는 쪽은 타임아웃·재시도, 들어오는 쪽은 서명 검증·멱등 처리가 핵심입니다. 진짜 PG 대신 우리가 만든 모의 PG(mock_pg/, 8001 포트)를 씁니다 — 키 발급 없이 돌고, 배울 것은 전부 들어 있습니다.

한 줄 요약. 이 문서를 끝내면 uv run pytest -q가 87 passed를 찍고, 낙찰자가 checkout 을 누르면 모의 PG 가 external_id 를 주고 1초 뒤 서명된 웹훅을 보내와 결제가 paid 로 바뀌며, 그 웹훅을 그대로 다시 보내면 {"received":true,"duplicate":true}(아무것도 안 바뀜), 본문을 한 글자 바꾸거나 서명을 빼면 401 INVALID_SIGNATURE, PG 가 3초 넘게 대답이 없으면 두 번 더 두드린 뒤 502 PG_UNAVAILABLE 이 됩니다 — 그리고 이 모든 것을 진짜 PG 없이 respx 로 테스트합니다.

학습 목표

  • 웹훅이 무엇이고, 왜 "요청에 대한 응답"만으로는 결제 결과를 알 수 없는지 설명할 수 있다
  • 바깥으로 나가는 HTTP 호출에 타임아웃을 걸고, 다시 해도 안전한 실패에만 재시도하는 법을 안다
  • HMAC 서명을 파싱 전 원문 바이트로 검증해야 하는 이유와 compare_digest 를 쓰는 이유를 안다
  • 같은 웹훅이 두 번 와도 상태를 두 번 바꾸지 않게(멱등) event_id 장부 + INSERT … ON CONFLICT DO NOTHING 으로 막을 수 있다
  • respx 로 "PG 가 200 / 타임아웃 / 500 뒤 200" 을 연출해 외부 연동을 결정적으로 테스트할 수 있다
  • BackgroundTasks 가 "응답 먼저, 일은 나중에"에 딱 맞는 자리를 모의 PG 에서 직접 본다

이 단계의 목표

8단계까지의 결제는 대기표뿐이었습니다. 워커가 Payment(pending, expires_at = 24시간 뒤) 를 만들어 두고, 기한이 지나면 expired 로 바꿨습니다. 그런데 정작 돈을 내는 길이 없었습니다. 이번 단계가 끝나면 낙찰자가 POST /payments/{id}/checkout 을 부르는 순간 우리 서버가 PG 에 결제를 열어 external_id(PG 가 발급한 결제 번호)를 받아 두고, PG 가 결제 결과를 POST /webhooks/payments 로 알려 오면 서명을 확인하고 paid + paid_at 으로 바꾸며, 7단계 소켓 구독자에게 payment_completed 를 방송합니다. 그리고 그 웹훅이 두 번 오든, 누가 흉내 내든, PG 가 먹통이든 — 결제는 정확히 한 번만, 진짜 PG 의 말만 듣고 바뀝니다.

진짜 PG(토스·포트원 등)는 붙이지 않습니다(설계 문서의 비목표). 대신 mock_pg/main.py 라는 60줄짜리 가짜 PG 를 8001 포트에 따로 띄웁니다. 결제를 만들어 달라고 하면 external_id 를 주고, 1초 뒤 우리 서버의 callback_url 로 서명된 웹훅을 보냅니다. 진짜 PG 가 하는 일의 뼈대가 정확히 이것이라, 나중에 진짜를 붙일 때는 URL·본문 모양·서명 규칙만 그 PG 문서대로 바꾸면 됩니다.

전제. 8단계가 끝나 있어야 합니다. uv run pytest -q → 71 passed, 컨테이너 두 개 (healthy). 새로 설치하는 패키지는 httpx(앱이 PG 를 부를 때) 와 respx(테스트에서 그 호출을 가로챌 때) 둘입니다. 마이그레이션이 하나 생깁니다 — webhook_events 테이블과 payments.external_id 인덱스. 작업 위치는 til/backend/fastapi/auction-api/.

이번 단계에서 만드는 것. 새 파일 9개(core/http.py 나가는 클라이언트, models/webhook_event.py 장부, repositories/webhook_event.py, schemas/payment.py, services/pg_client.py 타임아웃·재시도, services/payment.py 규칙, routers/payments.py, routers/webhooks.py, mock_pg/main.py, tests/test_payments.py), 손보는 파일 8개(설정 5개 값, security.py 서명 두 함수, deps.py, exceptions.py 예외 8개, models/payment.py 인덱스, models/__init__.py, repositories/payment.py 조회 3개, main.py). 8단계 워커는 한 줄도 안 바꿉니다 — 오늘도 expire_payments 가 "기한 내 미결제" 를 맡습니다.

왜 필요한가 — 실무 맥락

지금까지 우리 서버는 늘 응답하는 쪽이었습니다. 클라이언트가 묻고 우리가 답했습니다. 결제는 그 모양이 깨지는 첫 지점입니다. 돈은 우리 DB 가 아니라 결제사 가 움직입니다. 카드 승인, 계좌 이체, 간편결제 — 전부 PG 서버 안에서 일어나고, 그 결과는 몇 초 뒤일 수도 몇 분 뒤일 수도 있습니다(가상계좌 입금은 며칠). 그래서 결제 연동은 반드시 두 방향입니다. ① 우리가 PG 에 "이 금액으로 결제 열어 줘"(나가는 호출). ② PG 가 우리에게 "결제 끝났어"(들어오는 호출 = 웹훅). ②를 우리가 폴링으로 대신할 수도 있지만(1초마다 "됐어?" 묻기), PG 는 그걸 싫어하고 우리도 낭비입니다. 결과가 났을 때 PG 가 우리를 부르는 게 웹훅이고, Stripe·토스·GitHub·Slack 이 전부 이 방식입니다.

들어오는 호출은 새 문제를 셋 데려옵니다. 첫째, 누가 보냈나. /webhooks/payments 는 로그인 토큰이 없습니다 — PG 는 우리 사용자가 아닙니다. 누구나 URL 만 알면 "결제됐어" 라고 POST 할 수 있습니다. 그래서 PG 와 우리만 아는 비밀키로 본문에 서명하고, 우리는 같은 계산을 해서 맞는지 봅니다(HMAC). 둘째, 몇 번 오나. PG 는 우리가 2xx 를 줄 때까지 재전송합니다. 네트워크가 잠깐 끊겨 우리 응답이 PG 에 안 닿으면, 우리는 이미 처리했는데 같은 웹훅이 또 옵니다. 두 번 처리하면 "결제 완료 알림 두 번", 환불이면 "두 번 환불". 그래서 멱등이어야 합니다 — 같은 걸 몇 번 받아도 결과가 한 번과 같게. 셋째, 언제 오나. 우리 checkout 응답이 채 끝나기도 전에 웹훅이 먼저 도착할 수도 있고, 실패 웹훅 뒤에 성공 웹훅이 올 수도 있습니다. 순서를 믿지 말고 현재 상태를 보고 판단해야 합니다.

나가는 호출도 처음입니다(7주차·02 에서 httpx 를 배웠지만 실전 규칙은 이제). 바깥 서비스는 느릴 수 있고 잠깐 죽을 수 있습니다. 타임아웃이 없으면 PG 가 멈춘 3분 동안 우리 요청 하나가 커넥션과 워커를 붙잡습니다. 재시도가 없으면 0.1초짜리 네트워크 딸꾹질에 결제가 실패합니다. 재시도를 아무 데나 하면 4xx(우리 요청이 틀린 것)를 세 번 보내 세 번 거절당합니다. 오늘은 이 규칙들을 pg_client.py 한 파일에 넣고, respx 로 "타임아웃 세 번", "500 한 번 뒤 200" 을 연출해 테스트합니다.

실무에서 같은 모양이 나오는 곳. 결제뿐 아니라 이메일 발송 결과(SendGrid), SMS 수신, GitHub push 이벤트, Slack 슬래시 명령, 배송 상태 변경 — 전부 "서명된 웹훅을 받아 멱등하게 처리" 입니다. 오늘 만드는 verify_signature + try_record(event_id) 두 조각은 그대로 다른 웹훅에도 씁니다. 그리고 진짜 PG 를 붙일 때 가장 먼저 읽을 문서 제목이 바로 "Webhook 서명 검증" 과 "멱등키(Idempotency-Key)" 입니다.

비유 — 택배 기사의 문자

택배 기사의 문자. 온라인으로 물건을 팔았다고 합시다. 당신(우리 서버)이 택배사(PG)에 접수합니다 — "이 주소로 이 물건, 착불 12,000원". 택배사는 즉시 운송장 번호(external_id)를 줍니다. 아직 배송은 안 됐습니다, 번호만 받은 겁니다(checkout → status: pending, external_id: pg_…). 며칠 뒤 기사님이 "배송 완료" 문자를 보냅니다(웹훅). 당신은 그 문자를 보고 장부에 "수금 완료" 라고 적습니다(paid).

그런데 문자는 아무나 보낼 수 있습니다. 사기꾼이 "배송 완료" 라고 문자하면? 그래서 택배사와 당신은 암호 도장을 미리 나눠 가졌습니다(pg_webhook_secret). 기사는 문자 내용 전체에 도장을 찍어 보내고(X-PG-Signature), 당신은 같은 도장을 같은 내용에 찍어 봐서 무늬가 같아야 믿습니다(HMAC). 문자에서 글자 하나라도 고치면 무늬가 완전히 달라집니다 — 그래서 받은 그대로(원문 바이트)에 도장을 대 봐야 합니다. 예쁘게 다시 타이핑한 뒤에 대 보면 절대 안 맞습니다.

그리고 기사님은 답장을 못 받으면 같은 문자를 또 보냅니다. 두 번째 문자에 또 "수금 완료" 를 적으면 장부에 12,000원이 두 번 들어옵니다. 그래서 문자마다 문자 번호(event_id)가 있고, 당신은 받은 번호를 수첩(webhook_events)에 적어 둡니다. 새 문자가 오면 먼저 수첩을 봅니다 — 이미 있는 번호면 "응, 받았어" 만 답하고(duplicate: true) 장부는 건드리지 않습니다. 수첩에 적는 것과 장부에 적는 것을 한 번에(같은 트랜잭션) 해야 합니다. 수첩에만 적고 장부를 못 적으면, 다음 문자를 "이미 처리했다" 고 넘겨 버리니까요.

접수가 안 될 때. 택배사 전화가 통화 중이면(타임아웃) 잠시 뒤 한두 번 더 겁니다(재시도). 하지만 "주소가 없는 동네입니다" 라고 거절당하면(4xx) 백 번 걸어도 같습니다 — 그건 재시도가 아니라 우리 쪽 수정 대상입니다. 그리고 세 번 걸어도 안 받으면 손님에게 "택배사 연결이 안 됩니다, 잠시 후 다시" 라고 솔직히 말합니다(502 PG_UNAVAILABLE) — 우리 잘못인 척(500) 하지도, 된 척(200) 하지도 않습니다.

설계 그림

첫 그림은 두 방향입니다. 왼쪽 절반은 우리가 부르는 쪽: 낙찰자의 checkout 요청이 오면 결제 행을 잠그고(더블클릭 두 요청이 PG 결제를 두 개 열지 않게) 규칙을 검사한 뒤 pg_client.create_payment 가 httpx 로 모의 PG 를 부릅니다. 타임아웃 3초, 타임아웃·5xx 면 0.1초·0.2초 쉬고 두 번 더. 받은 external_id 를 저장하고 커밋합니다. 오른쪽 절반은 PG 가 부르는 쪽: 모의 PG 는 응답을 준 뒤 BackgroundTasks 로 1초 기다렸다가 callback_url 에 서명된 웹훅을 POST 합니다. 우리 라우터는 원문 바이트로 서명부터 확인하고, 그다음 파싱하고, 서비스가 event_id 를 장부에 적고(처음이면), external_id 로 결제를 잠가 paid 로 바꾸고, 커밋 뒤 payment_completed 를 방송합니다.

둘째 그림은 같은 웹훅이 세 번 왔을 때입니다. 실행·확인에서 실제로 해 보는 순서 그대로입니다. 첫 번째는 정상 처리(장부 기록 + paid 가 한 트랜잭션). 두 번째는 바이트까지 똑같은 재전송 — 서명은 맞고, 장부에 event_id 가 이미 있어 INSERT … ON CONFLICT DO NOTHING 이 아무 행도 돌려주지 않습니다 → duplicate: true, 결제는 건드리지 않습니다. 세 번째는 본문을 한 글자 바꾼 것(amount: 1) — 서명이 안 맞아 파싱도 하기 전에 401 입니다. 그리고 만약 external_id 가 우리 DB 에 없다면? 장부에 적은 직후 예외를 던지므로 트랜잭션이 롤백되어 장부 기록도 사라집니다 — PG 가 재전송하면 다시 처음부터 검토합니다. "기록했지만 처리 못 한" 이벤트가 남지 않는 게 요점입니다.

왜 장부를 Redis SETNX 가 아니라 DB 테이블로 했나. 장부 기록과 결제 상태 변경이 같은 트랜잭션이어야 "기록은 됐는데 상태는 안 바뀐" 반쪽 상태가 생기지 않습니다. Redis 에 적으면 그 순간 Redis 는 확정인데 DB 커밋이 실패할 수 있고, 그러면 다음 재전송을 "이미 처리함" 으로 넘겨 결제가 영원히 pending 으로 남습니다. 같은 이유로 예외가 나면 장부 기록도 같이 롤백되는 게 맞습니다. Redis 방식은 "웹훅이 초당 수천 건이고 DB 쓰기를 아끼고 싶을 때" 의 최적화이며, 그때도 TTL 과 실패 처리를 따로 설계해야 합니다.

구현 — 파일을 하나씩 만든다

순서는 늘 같습니다 — 테스트 먼저(RED), 그다음 통과시킬 코드(GREEN). 이번 테스트의 요령은 둘입니다. 나가는 호출은 respx 로 가로채고(진짜 PG 없이 200·타임아웃·500 을 연출), 들어오는 웹훅은 우리가 직접 서명해서 보냅니다(서명 규칙을 아니까). 파일은 새로 9개, 손보는 것 8개 — 이번 단계가 가장 많습니다. 대신 하나하나는 짧습니다.

0. 패키지 두 개

async def won_payment(
    db: AsyncSession,
    *,
    seller: User,
    payer: User,
    amount: int = 12_000,
    expires_in: timedelta = timedelta(hours=24),
    status: PaymentStatus = PaymentStatus.PENDING,
    external_id: str | None = None,
) -> tuple[Auction, Payment]:
    """낙찰이 끝난 경매 + 결제 대기표. 8단계 close_due 가 만드는 것과 같은 모양을 직접 넣는다."""
    now = datetime.now(UTC)
    auction = await create_auction(
        db,
        seller,
        status=AuctionStatus.ENDED,
        starts_at=now - timedelta(days=2),
        ends_at=now - timedelta(days=1),
        current_price=amount,
        bid_count=1,
        winner_id=payer.id,
    )
    payment = Payment(
        auction_id=auction.id,
        payer_id=payer.id,
        amount=amount,
        status=status,
        expires_at=now + expires_in,
        external_id=external_id,
    )
    db.add(payment)
    await db.flush()
    return auction, payment


def signed(body: dict, *, tamper: bytes | None = None) -> tuple[bytes, dict[str, str]]:
    """PG 가 보내는 것과 똑같이: 본문 바이트를 비밀키로 서명해 헤더에 싣는다."""
    raw = json.dumps(body).encode()
    sig = sign_payload(raw, get_settings().pg_webhook_secret)
    return (tamper or raw), {"X-PG-Signature": sig, "Content-Type": "application/json"}

from typing import Any, Literal

import jwt
from pwdlib import PasswordHash
from pwdlib.hashers.bcrypt import BcryptHasher

from app.core.config import get_settings

ALGORITHM = "HS256"
TokenType = Literal["access", "refresh"]

_password_hash = PasswordHash((BcryptHasher(),))


def hash_password(raw: str) -> str:
    return _password_hash.hash(raw)


def verify_password(raw: str, hashed: str) -> bool:
    return _password_hash.verify(raw, hashed)


class TokenError(Exception):
    """서명 불일치, 만료, 타입 불일치 등 — 호출자가 401 로 바꾼다."""


def create_token(subject: str, token_type: TokenType, expires_delta: timedelta) -> tuple[str, str]:
    """(토큰 문자열, jti) 를 돌려준다. jti 는 토큰마다 다른 고유 id — refresh 폐기에 쓴다."""
    now = datetime.now(UTC)
    jti = uuid.uuid4().hex
    payload = {
        "sub": subject,
        "type": token_type,
        "jti": jti,
        "iat": now,
        "exp": now + expires_delta,
    }
    token = jwt.encode(payload, get_settings().jwt_secret, algorithm=ALGORITHM)
    return token, jti


def create_access_token(user_id: uuid.UUID) -> str:
    minutes = get_settings().access_token_minutes
    token, _ = create_token(str(user_id), "access", timedelta(minutes=minutes))
    return token


def create_refresh_token(user_id: uuid.UUID) -> tuple[str, str, int]:
    """(토큰, jti, 만료까지 남은 초). 마지막 값은 Redis TTL 로 그대로 쓴다."""
    ttl = timedelta(days=get_settings().refresh_token_days)
    token, jti = create_token(str(user_id), "refresh", ttl)
    return token, jti, int(ttl.total_seconds())


def decode_token(token: str, expected_type: TokenType) -> dict[str, Any]:
    try:
        payload = jwt.decode(token, get_settings().jwt_secret, algorithms=[ALGORITHM])
    except jwt.PyJWTError as exc:  # 만료(ExpiredSignatureError) 도 여기에 포함된다
        raise TokenError(str(exc)) from exc
    if payload.get("type") != expected_type:
        raise TokenError(f"{expected_type} 토큰이 아닙니다")
    return payload


# ── 웹훅 서명 (9단계) ─────────────────────────────────────────────────


def sign_payload(body: bytes, secret: str) -> str:
    """본문 *바이트 그대로* 를 비밀키로 HMAC-SHA256. 보내는 쪽(PG)과 받는 쪽(우리)이 같은 계산.
    한 바이트라도 다르면(공백 하나, 키 순서 하나) 값이 완전히 달라진다 — 그래서 파싱 전
    원문 바이트로 검사한다."""
    return hmac.new(secret.encode(), body, hashlib.sha256).hexdigest()


def verify_signature(body: bytes, signature: str | None, secret: str) -> bool:
    """compare_digest: 앞에서부터 비교하다 첫 불일치에서 멈추지 않는다 → '몇 글자까지 맞았는지' 가
    응답 시간으로 새지 않는다(타이밍 공격 방지). == 로 비교하면 안 되는 이유."""
    if not signature:
        return False
    return hmac.compare_digest(sign_payload(body, secret), signature)

from sqlalchemy.dialects.postgresql import insert
from sqlalchemy.ext.asyncio import AsyncSession

from app.models import WebhookEvent


async def try_record(db: AsyncSession, event_id: str) -> bool:
    """처음 보는 event_id 면 기록하고 True, 이미 있으면 False.

    INSERT … ON CONFLICT DO NOTHING RETURNING 은 한 문장이다. 같은 웹훅 두 개가 *동시에* 와도
    Postgres 가 줄을 세워 정확히 하나만 RETURNING 값을 받는다. (INSERT 를 그냥 하고
    IntegrityError 를 잡는 방법도 있지만, 그러면 트랜잭션이 깨져 그 뒤 쿼리를 못 한다.)
    """
    stmt = (
        insert(WebhookEvent)
        .values(event_id=event_id)
        .on_conflict_do_nothing(index_elements=[WebhookEvent.event_id])
        .returning(WebhookEvent.event_id)
    )
    return await db.scalar(stmt) is not None

12. app/services/pg_client.py — 타임아웃과 재시도, 그것만

결제 규칙을 전혀 모르는 파일입니다. 아는 건 "PG 를 어떻게 부르고, 안 되면 어떻게 하나" 뿐. 재시도 조건을 눈여겨보세요: httpx.TransportError(타임아웃·연결 실패 — 네트워크 사정) 와 5xx(PG 쪽 사정) 만 다시 시도하고, 4xx(우리 요청이 틀림) 는 즉시 502 로 끝냅니다. 백 번 다시 보내도 같은 답이니까요. 사이에 0.1s, 0.2s 를 쉽니다 — 방금 실패한 서버를 즉시 또 두드리는 건 도움이 안 됩니다(backoff). 세 번 다 실패하면 PaymentGatewayError — 핸들러가 502 로 번역합니다.

pythonapp/services/pg_client.py
"""PG 를 부르는 쪽. 타임아웃·재시도만 책임진다 — 결제 규칙은 모른다.

바깥 서비스는 느릴 수도, 잠깐 죽을 수도 있다. 그래서 (1) 오래 기다리지 않고(타임아웃),
(2) 잠깐의 사정이면 몇 번 더 두드리고(재시도), (3) 그래도 안 되면 '우리 잘못이 아닌 502' 로 끝낸다.
재시도는 *다시 해도 안전한* 실패에만 한다: 타임아웃·연결 실패·5xx. 4xx 는 우리 요청이 틀린 것이라
백 번 다시 보내도 같다.
"""

import asyncio
import logging
import uuid

import httpx

from app.core.config import get_settings
from app.core.exceptions import PaymentGatewayError

logger = logging.getLogger(__name__)


async def create_payment(
    http: httpx.AsyncClient, *, payment_id: uuid.UUID, amount: int, callback_url: str
) -> str:
    """PG 에 결제를 만들고 PG 가 발급한 external_id 를 돌려준다."""
    settings = get_settings()
    url = f"{settings.pg_base_url}/pg/payments"
    body = {"payment_id": str(payment_id), "amount": amount, "callback_url": callback_url}
    attempts = settings.pg_retries + 1
    last: Exception | None = None

    for attempt in range(1, attempts + 1):
        try:
            res = await http.post(url, json=body, timeout=settings.pg_timeout_seconds)
        except httpx.TransportError as exc:  # 타임아웃·연결 실패 — 네트워크 사정, 다시 해 볼 만하다
            last = exc
        else:
            if res.is_success:
                return res.json()["external_id"]
            if res.status_code < 500:  # 4xx: 우리 요청이 틀렸다 → 재시도 무의미
                raise PaymentGatewayError(f"결제사가 요청을 거부했습니다 ({res.status_code})")
            last = httpx.HTTPStatusError(  # 5xx: PG 쪽 사정 → 재시도
                f"PG {res.status_code}", request=res.request, response=res
            )
        logger.warning("PG create_payment 실패 (%d/%d): %r", attempt, attempts, last)
        if attempt < attempts:
            await asyncio.sleep(0.1 * attempt)  # 0.1s, 0.2s … 바로 다시 두드리지 않는다 (backoff)

    raise PaymentGatewayError() from last

"상태를 보고 판단" 이 순서 뒤집힘을 견디는 방법입니다: failed 뒤에 paid 가 와도, paid 뒤에 failed 가 늦게 와도 결과는 한 가지입니다.

"""결제 규칙. HTTP 를 모른다 — 도메인 예외만 던진다.

두 방향이 있다.
  checkout        : 우리 → PG. 낙찰자가 "결제할게요" 하면 PG 에 결제를 열고 external_id 를 받는다.
  handle_webhook  : PG → 우리. PG 가 "결제됐어요/실패했어요" 를 알려 오면 상태를 바꾼다.
웹훅은 (1) 같은 게 두 번 올 수 있고 (2) 순서가 뒤집힐 수 있고 (3) 남이 흉내 낼 수 있다.
(3) 은 라우터가 서명으로 막고, (1) 은 여기서 event_id 장부로 막고,
(2) 는 '현재 상태를 보고 판단' 으로 견딘다.
"""

import logging
import uuid
from datetime import UTC, datetime

import httpx
from redis.asyncio import Redis
from sqlalchemy.ext.asyncio import AsyncSession

from app.core import events
from app.core.config import get_settings
from app.core.exceptions import (
    AmountMismatchError,

    NotPaymentPayerError,
    PaymentExpiredError,
    PaymentNotFoundError,
    PaymentNotPendingError,

from app.models import Payment, PaymentStatus, User

from app.repositories import webhook_event as webhook_repo

def _now() -> datetime:
    return datetime.now(UTC)


async def get(db: AsyncSession, payment_id: uuid.UUID, user: User) -> Payment:
    """결제 당사자(낙찰자) 와 판매자만 본다."""
    payment = await payment_repo.get(db, payment_id)
    if payment is None:
        raise PaymentNotFoundError()
    if user.id not in (payment.payer_id, payment.auction.seller_id):
        raise ForbiddenError("결제 당사자만 볼 수 있습니다")
    return payment


async def checkout(
    db: AsyncSession, http: httpx.AsyncClient, payment_id: uuid.UUID, user: User
) -> Payment:
    """PG 에 결제를 열고 external_id 를 저장한다. 두 번 눌러도 PG 결제는 하나(멱등)."""
    payment = await payment_repo.get_for_update(db, payment_id)  # 더블클릭 두 요청이 줄을 선다
    if payment is None:
        raise PaymentNotFoundError()
    if payment.payer_id != user.id:
        raise NotPaymentPayerError()
    if payment.status != PaymentStatus.PENDING:
        raise PaymentNotPendingError()
    if payment.expires_at <= _now():
        raise PaymentExpiredError()
    if payment.external_id is not None:  # 이미 PG 결제가 열려 있다 → 같은 것을 돌려준다
        return payment

    callback_url = f"{get_settings().public_base_url}/webhooks/payments"
    external_id = await pg_client.create_payment(
        http, payment_id=payment.id, amount=payment.amount, callback_url=callback_url
    )
    payment.external_id = external_id
    await db.commit()
    await db.refresh(payment)
    return payment


async def handle_webhook(db: AsyncSession, redis: Redis, data: PgWebhook) -> bool:
    """서명이 확인된 웹훅을 처리한다. True = 전에 처리한 event_id (아무것도 바꾸지 않았다)."""
    if not await webhook_repo.try_record(db, data.event_id):
        return True  # 장부에 이미 있다 — 같은 소식이 또 온 것

    payment = await payment_repo.get_by_external_id_for_update(db, data.external_id)
    if payment is None or payment.id != data.payment_id:
        # 예외 → 트랜잭션 롤백 → 방금 적은 event_id 도 사라진다 → PG 가 재전송하면 다시 검토
        raise PaymentNotFoundError()
    if payment.amount != data.amount:  # 웹훅이 말하는 금액을 그대로 믿지 않는다
        raise AmountMismatchError()

    became_paid = False
    if data.status == "paid":
        if payment.status == PaymentStatus.PENDING:
            payment.status = PaymentStatus.PAID
            payment.paid_at = _now()
            became_paid = True
        else:  # 이미 paid/expired 인데 paid 웹훅 — 순서가 꼬였거나 늦게 온 것. 상태는 그대로
            logger.warning(
                "payment %s 는 이미 %s 인데 paid 웹훅(%s) 이 왔다 — 무시",
                str(payment.id)[:8],
                payment.status,
                data.event_id,
            )
    elif payment.status == PaymentStatus.PENDING:  # "failed": 이 PG 결제는 끝났다
        payment.external_id = None  # 비워 두면 낙찰자가 다시 checkout 해 새 PG 결제를 열 수 있다
        logger.info(
            "payment %s PG 결제 실패(%s) — 재시도 가능", str(payment.id)[:8], data.external_id
        )
    else:  # 이미 paid 인데 failed 가 늦게 왔다 — 역시 무시 (결제된 사실은 웹훅이 뒤집지 못한다)
        logger.warning(
            "payment %s 는 %s 인데 failed 웹훅 — 무시", str(payment.id)[:8], payment.status
        )

    await db.commit()  # ← event_id 기록과 상태 변경이 *함께* 확정된다 (둘 중 하나만 남지 않는다)

    if became_paid:
        await events.publish(
            redis,
            events.AuctionEvent(
                type="payment_completed",
                auction_id=payment.auction_id,
                payload={

"""모의 결제사(PG). 진짜 PG 처럼 (1) 결제 생성 요청에 즉시 external_id 를 주고,
(2) 잠시 뒤 결과를 callback_url 로 *서명해서* 보낸다. 우리 앱과 별개 프로세스로 8001 에서 돈다.

    uv run uvicorn mock_pg.main:app --port 8001
    환경변수: PG_WEBHOOK_SECRET (앱의 pg_webhook_secret 과 같아야 한다)
              PG_WEBHOOK_DELAY   (콜백까지 기다리는 초, 기본 1.0)
"""

import asyncio
import hashlib
import hmac
import json
import logging
import os
import uuid

import httpx
from fastapi import BackgroundTasks, FastAPI, HTTPException
from pydantic import BaseModel

SECRET = os.environ.get("PG_WEBHOOK_SECRET", "dev-only-pg-webhook-secret-change-me-32-bytes-min")
DELAY = float(os.environ.get("PG_WEBHOOK_DELAY", "1.0"))

logging.basicConfig(level=logging.INFO, format="%(asctime)s mock_pg %(message)s")
logger = logging.getLogger("mock_pg")
app = FastAPI(title="Mock PG")
payments: dict[str, dict] = {}  # external_id → {payment_id, amount, callback_url}


class CreatePayment(BaseModel):
    payment_id: str
    amount: int
    callback_url: str


def sign(body: bytes) -> str:
    return hmac.new(SECRET.encode(), body, hashlib.sha256).hexdigest()


async def send_webhook(external_id: str, status: str) -> None:
    await asyncio.sleep(DELAY)  # 진짜 PG 도 승인까지 시간이 걸린다
    p = payments[external_id]
    event = {
        "event_id": f"evt_{uuid.uuid4().hex[:12]}",
        "external_id": external_id,
        "payment_id": p["payment_id"],
        "status": status,
        "amount": p["amount"],
    }
    body = json.dumps(event).encode()
    headers = {"Content-Type": "application/json", "X-PG-Signature": sign(body)}
    async with httpx.AsyncClient(timeout=5.0) as http:
        try:
            res = await http.post(p["callback_url"], content=body, headers=headers)
            logger.info("webhook %s → %s %s", status, res.status_code, res.text)
        except httpx.HTTPError as exc:
            logger.warning("webhook 전송 실패: %r (진짜 PG 라면 재시도 스케줄을 잡는다)", exc)
    logger.info("sig=%s body=%s", headers["X-PG-Signature"], body.decode())  # 재전송 실험용


@app.post("/pg/payments", status_code=201)
async def create_payment(data: CreatePayment, tasks: BackgroundTasks) -> dict[str, str]:
    external_id = f"pg_{uuid.uuid4().hex[:12]}"
    payments[external_id] = data.model_dump()
    tasks.add_task(send_webhook, external_id, "paid")  # 응답을 먼저 보내고, 그 *뒤에* 콜백
    logger.info("payment created %s for %s (%s원)", external_id, data.payment_id, data.amount)
    return {"external_id": external_id}


@app.post("/pg/payments/{external_id}/fail", status_code=202)
async def fail_payment(external_id: str, tasks: BackgroundTasks) -> dict[str, str]:
    """실패 웹훅을 일부러 보내 보고 싶을 때."""
    if external_id not in payments:
        raise HTTPException(404, "unknown external_id")
    tasks.add_task(send_webhook, external_id, "failed")
    return {"external_id": external_id, "status": "failed"}

함정 & 실무 팁

서명은 원문 바이트로, 파싱 전에. 가장 흔한 실패입니다: data: PgWebhook 로 받은 뒤 json.dumps(data.model_dump()) 로 서명을 계산하면 공백·키 순서·숫자 표기가 달라져 절대 맞지 않습니다. await request.body() 가 먼저, 검증이 그다음, 파싱은 맨 나중입니다. 그리고 비교는 hmac.compare_digest — == 는 첫 불일치에서 멈춰 응답 시간이 새고, 공격자가 한 글자씩 맞춰 갈 수 있습니다. PG 마다 서명 규칙이 다릅니다(본문만 / timestamp + 본문 / 헤더 이름). 붙이기 전에 문서의 "서명 검증" 절부터 읽으세요.
2xx 는 빨리, 무거운 일은 나중에. PG 는 우리가 2xx 를 몇 초 안에 주지 않으면 실패로 보고 재전송합니다(그러면 멱등 처리가 또 돕니다 — 정상이지만 낭비). 웹훅 핸들러 안에서 이메일을 보내거나 외부 API 를 부르면 그 시간만큼 위험합니다. 우리 핸들러는 DB 쓰기 한 번과 PUBLISH 하나뿐입니다. 더 무거운 후속 작업은 8단계 방식(테이블에 적고 워커가 처리)으로 넘깁니다.
재시도는 '다시 해도 안전한' 실패에만. 타임아웃·연결 실패·5xx 는 PG 가 우리 요청을 못 받았을 가능성이 있어 재시도 가치가 있습니다. 4xx 는 받았고 거절한 것 — 재시도해도 같습니다. 그런데 타임아웃엔 함정이 있습니다: PG 가 요청을 받아 처리했는데 응답만 늦게 온 경우, 우리 재시도가 PG 결제를 두 개 만들 수 있습니다. 진짜 PG 는 그래서 Idempotency-Key 헤더(우리 payment_id 를 넣으면 됩니다)를 받아 같은 키면 같은 결제를 돌려줍니다. 모의 PG 엔 없습니다 — 셀프 체크 3번에서 이어집니다.
바깥 호출엔 예외 없이 타임아웃. httpx 기본값도 5초가 있지만, 우리는 설정으로 명시합니다(pg_timeout_seconds). 타임아웃 없는 외부 호출 하나가 PG 장애 때 우리 서버의 워커·커넥션을 전부 붙잡아 "PG 가 죽었더니 우리도 죽었다" 가 됩니다. 4주차·02 의 블로킹 함정과 같은 결말이며, 원인만 다릅니다. 그리고 PG 호출 동안 결제 행 락을 쥐고 있는 우리 설계는 편하지만 락 시간이 최대 3초 × 3회입니다 — 트래픽이 크면 "PG 호출 전에 external_id 예약 표시 후 커밋, 호출 뒤 갱신" 두 단계로 바꿉니다.
웹훅이 말하는 숫자를 믿지 마세요. 서명이 맞아도 본문의 amount 는 우리 기록과 대조합니다(AMOUNT_MISMATCH). PG 쪽 버그·설정 실수·테스트 데이터 섞임은 서명으로 못 막습니다. 마찬가지로 payment_id 도 external_id 로 찾은 결제와 같은지 봅니다. "권한은 서명이, 정합성은 대조가" — 둘은 다른 문제입니다.
순서를 믿지 마세요, 상태를 보세요. failed 뒤에 paid, paid 뒤에 뒤늦은 failed, checkout 커밋 전에 웹훅 — 전부 실제로 일어납니다. 우리 서비스는 "지금 pending 이면 바꾼다, 아니면 로그만" 으로 어느 순서든 같은 결과를 냅니다. 커밋 전 웹훅은 FOR UPDATE 락이 기다리게 해서 풀었습니다. 실행·확인에서 모의 PG 의 1초 지연을 0 으로 줄여(PG_WEBHOOK_DELAY=0) 이 경쟁을 직접 만들어 볼 수 있습니다.
장부는 남기고, 실패는 롤백. try_record 뒤에 예외가 나면 장부 기록도 같이 사라져 PG 재전송 때 다시 검토됩니다 — 의도한 설계입니다. 반대로 "처리는 됐는데 방송(PUBLISH)만 실패" 는 커밋 뒤라 상태는 유지되고, 7단계의 snapshot 이 보정합니다. 장부는 자라기만 하니 운영에선 오래된 행을 주기적으로 지웁니다(PG 의 재전송 창은 보통 며칠) — 8단계 워커에 DELETE FROM webhook_events WHERE received_at < now() - interval '30 days' 한 문장을 더하면 됩니다.
로컬에선 PG 가 localhost 를 못 부릅니다. 오늘은 모의 PG 도 내 컴퓨터라 http://localhost:8000 이 통했습니다. 진짜 PG 는 인터넷에서 우리 서버를 찾아야 하므로 로컬 개발엔 ngrok http 8000 같은 터널로 받은 공개 URL 을 PUBLIC_BASE_URL 에 넣습니다. 스테이징·운영은 당연히 HTTPS 도메인이고, 비밀키는 환경마다 다르게 발급해 회전할 수 있어야 합니다(옛 키·새 키를 잠깐 둘 다 허용하는 기간을 두는 게 정석입니다).
respx 는 httpx 만 가로챕니다. 앱이 httpx 를 쓰고 테스트 클라이언트가 httpx2 라서 둘이 섞이지 않습니다 — client.post("/payments/…")(httpx2, ASGI 직접 호출) 는 respx 를 지나가지 않고, 그 안에서 앱이 부르는 http.post("http://localhost:8001/…")(httpx) 만 가로채집니다. respx.mock(base_url=…) 안의 route.calls[0].request.content 로 "우리가 PG 에 뭘 보냈나" 까지 검사할 수 있습니다. 10주차·01 의 mocking 절이 배경입니다.

셀프 체크

Q 웹훅 라우터가 data: PgWebhook 으로 본문을 받지 않고 request.body() 를 먼저 읽는 이유는? 그리고 서명 비교에 == 대신 compare_digest 를 쓰는 이유는?

서명은 PG 가 보낸 바이트에 대해 계산됐습니다. FastAPI 가 파싱한 객체를 다시 JSON 으로 만들면 공백·키 순서·숫자 표기가 달라져 같은 내용이어도 다른 바이트가 되고, 서명이 맞지 않습니다. 그래서 원문 바이트 → 서명 검증 → 그다음 파싱입니다(검증 전엔 파싱할 이유도 없습니다 — 누가 보낸지도 모르는 본문이니까요). == 는 첫 불일치에서 멈추기 때문에 앞 글자가 맞을수록 조금 더 오래 걸리고, 그 차이를 수천 번 재면 서명을 한 글자씩 맞춰 갈 수 있습니다(타이밍 공격). compare_digest 는 길이가 같으면 항상 같은 시간이 걸립니다.

Q 같은 웹훅이 동시에 두 요청으로 들어오면 어떻게 되나요? 그리고 external_id 가 우리 DB 에 없는 웹훅이 오면 장부(webhook_events)엔 무엇이 남나요?

둘 다 INSERT … ON CONFLICT DO NOTHING RETURNING 을 실행합니다. Postgres 는 같은 PK 를 넣으려는 두 번째 트랜잭션을 첫 번째가 커밋/롤백할 때까지 기다리게 하고, 첫 번째가 커밋하면 두 번째의 INSERT 는 충돌로 아무 행도 돌려주지 않습니다 → duplicate: true. 정확히 하나만 결제를 바꿉니다 — 6단계 락과 같은 원리이지만 명시적 FOR UPDATE 없이 PK 제약 자체가 줄을 세웁니다. 모르는 external_id 면 장부에 적은 직후 PaymentNotFoundError 를 던지고, 그 트랜잭션은 커밋되지 않으므로 장부 기록도 사라집니다 — 아무것도 남지 않습니다. PG 가 재전송하면 처음부터 다시 검토하고, 그때 결제가 생겨 있으면 정상 처리됩니다. "기록은 됐는데 처리는 안 된" 이벤트가 생기지 않도록 장부와 처리를 한 트랜잭션에 둔 결과입니다.

Q checkout 중 PG 가 결제를 만들긴 했는데 응답이 3초를 넘겨 타임아웃이 났고, 우리는 재시도해서 두 번째 결제도 만들었습니다. 이제 PG 가 첫 번째 결제의 웹훅을 보내면 우리 코드는 어떻게 반응하고, 실무에선 어떻게 막나요?

우리는 두 번째 external_id 만 저장했으니 첫 번째 웹훅은 get_by_external_id_for_update 에서 못 찾아 404 — PG 는 계속 재전송하고 운영자가 봐야 합니다. 첫 번째 결제로 실제 돈이 빠졌다면 고객은 이중 결제입니다. 그래서 진짜 PG 는 결제 생성에 멱등키(Idempotency-Key 헤더 — 우리 payment_id 를 넣으면 됩니다)를 받습니다: 같은 키로 다시 부르면 새로 만들지 않고 같은 external_id 를 돌려줍니다. 그러면 타임아웃 뒤 재시도가 안전해집니다. 우리 쪽 보완은 웹훅에 실려 오는 payment_id 로도 결제를 찾아 external_id 를 맞춰 주는 것입니다(본문에 이미 있습니다). 오늘의 pg_client 에 헤더 한 줄과 mock_pg 에 "같은 payment_id 면 같은 external_id" 를 더하면 완성됩니다 — 좋은 연습 과제입니다.
