10-1 개요와 설계

기능은 9단계로 끝났습니다. 마지막 단계는 새 기능을 더하지 않습니다. 지금까지 만든 API·워커·모의 PG 를 "내 노트북에서 도는 것" 에서 "남이 운영할 수 있는 것" 으로 바꿉니다: 자주 읽는 목록에 캐시를 붙이고, 모든 로그를 JSON 한 줄 + request-id 로 통일하고, 브라우저가 부를 수 있게 CORS 를 열고, 부하 테스트로 숨은 블로킹 호출을 잡아내고, Dockerfile·compose 로 다섯 프로세스를 한 번에 띄우고, GitHub Actions 가 매 푸시마다 테스트를 돌리게 합니다.

학습 목표

  • "버전 키" 캐시가 왜 DEL·SCAN 없이 무효화되는지 설명하고, 어디서 버전을 올려야 하는지 고를 수 있다
  • request-id 가 contextvar 를 타고 같은 요청의 모든 로그(우리 코드·httpx·SQL 경고)에 자동으로 붙는 원리를 안다
  • 부하 테스트 숫자(RPS·p50·p95)만 보고 "이벤트 루프를 막는 동기 호출이 있다" 를 의심할 수 있다
  • 멀티스테이지 Dockerfile 이 왜 두 FROM 인지, 비루트 사용자와 exec-form CMD 가 왜 중요한지 안다
  • compose 안에서는 localhost 가 아니라 서비스 이름이 호스트명이라는 것, 마이그레이션은 한 컨테이너만 돌려야 한다는 것을 안다
  • GitHub Actions 서비스 컨테이너로 Postgres·Redis 를 띄워 우리 테스트 전체를 CI 에서 돌릴 수 있다
🎯

이 단계의 목표

9단계까지의 서비스는 내 노트북 전용이었습니다. 터미널 세 개에 uvicorn·워커·모의 PG 를 따로 띄우고, 로그는 사람 눈으로 읽는 한 줄짜리 텍스트였고, 목록은 부를 때마다 DB 를 갔습니다. 이번 단계가 끝나면 (1) GET /auctions 는 5초 동안 Redis 에서 답하고 경매가 바뀌는 순간 자동으로 새로 읽으며, (2) 모든 로그가 request_id 를 품은 JSON 한 줄이라 "이 요청이 왜 느렸지?" 를 한 값으로 좇을 수 있고, (3) locust 가 50명 동시 접속을 흉내 내 병목을 숫자로 보여 주며, (4) docker compose -f docker-compose.prod.yml up -d --build 한 줄로 다섯 컨테이너(app·worker·mock_pg·db·redis)가 뜨고, (5) GitHub 에 푸시할 때마다 Actions 가 ruff → 마이그레이션 → 테스트 97개를 돌립니다.

전제. 9단계가 끝나 있어야 합니다. uv run pytest -q → 87 passed, 컨테이너 두 개 (healthy), Docker Desktop 실행 중, 8000·8001 포트 비어 있음. 새로 설치하는 패키지는 locust(개발용) 하나입니다. 마이그레이션은 없습니다. 작업 위치는 til/backend/fastapi/auction-api/.

이번 단계에서 만드는 것. 새 파일 10개(core/cache.py, core/logging.py, 테스트 2개, loadtest/locustfile.py, Dockerfile, .dockerignore, docker-compose.prod.yml, .github/workflows/ci.yml, README.md), 손보는 파일 10개(설정 4개 값, alembic/env.py 한 줄, 서비스 4개에 "버전 올리기" 한 줄씩, services/auth.py 의 bcrypt 를 스레드로, 라우터, main.py, 워커, conftest.py). 기능(엔드포인트·모델·규칙)은 하나도 안 바뀝니다 — 그래서 9단계까지의 87개 테스트가 그대로 통과해야 합니다.
🏢

왜 필요한가 — 실무 맥락

실무에서 "기능이 된다" 와 "운영할 수 있다" 사이에는 네 가지 질문이 있습니다. 빠른가 — 인기 경매 목록은 초당 수백 번 읽히는데 매번 DB 를 가야 하나? 보이는가 — 새벽에 "결제가 안 돼요" 라는 문의가 오면, 그 사용자의 그 요청이 어느 워커에서 어떤 SQL 을 몇 ms 돌렸는지 찾을 수 있나? 버티는가 — 50명이 동시에 누르면 어디가 먼저 무너지나? 그걸 배포 전에 알 수 있나? 옮길 수 있는가 — 내 노트북의 uv·파이썬 버전·환경변수 없이도 다른 컴퓨터(동료, 서버, CI)에서 똑같이 뜨나? 이 넷에 답하는 도구가 각각 캐시, 구조화 로그, 부하 테스트, 컨테이너입니다.

이 중 초보자가 가장 자주 놓치는 것이 로그입니다. print() 와 텍스트 로그는 혼자 개발할 땐 충분하지만, 컨테이너 다섯 개가 같은 화면에 섞여 찍히기 시작하면 "이 줄이 어느 요청의 것인지" 를 알 수 없습니다. 그래서 운영 로그는 (1) 기계가 읽는 JSON, (2) 요청마다 고유한 request_id, (3) 응답 코드와 소요 시간이 기본입니다. 프론트가 에러 화면에 X-Request-ID 를 찍어 두면 사용자가 그 값을 알려 주는 순간 서버 로그에서 한 줄로 찾습니다 — 택배 송장번호와 같습니다.

부하 테스트는 4주차·02 에서 배운 "async 안의 동기 호출은 서버 전체를 멈춘다" 를 숫자로 보는 시간입니다. 코드 리뷰로는 놓치는 requests.get() 하나, 동기 이미지 변환 하나가 p95 를 1초로 만듭니다. 오늘은 일부러 50ms 짜리 time.sleep 을 넣고 켜고 끄며 재 봅니다 — 그리고 그 과정에서 우리 코드에 진짜로 숨어 있던 200ms 짜리 블로킹 호출(bcrypt)도 찾아냅니다.

순서에 대해. 실무에선 Dockerfile 과 CI 가 1단계에 있는 경우도 많습니다(처음부터 컨테이너로 개발). 이 커리큘럼이 10단계에 둔 이유는 "컨테이너에 넣을 것이 다 갖춰진 뒤" 가 가장 배우기 쉽기 때문입니다 — 다섯 프로세스의 역할과 환경변수를 전부 아는 지금이라야 compose 파일의 한 줄 한 줄이 왜 있는지 보입니다.
🏭

비유 — 공장과 매장, 송장번호, FAQ 종이

캐시 = 카운터 앞에 붙여 둔 FAQ 답변. 손님 100명이 같은 질문("지금 열린 경매 뭐 있어요?")을 하면 매번 창고(DB)에 다녀오는 대신 답을 종이에 적어 카운터에 붙여 둡니다. 종이엔 판 번호(v7)가 적혀 있고, 경매가 하나라도 바뀌면 벽의 판 번호판을 v8 로 넘깁니다. 그러면 v7 종이는 아무도 안 보고(찾아서 떼어낼 필요도 없이) 5초 뒤 바람에 날아갑니다(TTL). 새 손님에겐 v8 종이를 새로 적어 붙입니다. "어떤 종이를 떼야 하지?" 를 고민하지 않아도 되는 게 버전 키의 요점입니다.

request-id = 택배 송장번호. 물건 하나가 접수 → 허브 → 배송기사 → 문 앞까지 가는 동안 여러 사람 손을 거치지만, 송장번호 하나로 전 구간을 좇습니다. 우리 요청도 미들웨어 → 라우터 → 서비스 → SQL → httpx(PG 호출) 를 거치는데, 맨 앞에서 번호를 붙여 두면(contextvar) 그 뒤 어디서 찍힌 로그든 같은 번호가 따라붙습니다. 프론트가 번호를 미리 붙여 보내면(X-Request-ID 헤더) 브라우저 콘솔과 서버 로그가 같은 번호를 공유합니다.

멀티스테이지 Dockerfile = 공장과 매장. 공장(빌더 스테이지)에는 uv, 컴파일러, 캐시 같은 큰 장비가 있고 거기서 제품(.venv)을 만듭니다. 매장(런타임 스테이지)엔 제품과 진열대(파이썬)만 옮겨 놓습니다 — 장비는 안 가져갑니다. 그래서 최종 이미지가 작고, 공격 표면도 작고, 매장 직원은 관리자(root)가 아니라 일반 직원(app 사용자)입니다.

부하 테스트 = 개점 전 리허설. 손님 50명을 한 번에 들여보내 보면 카운터가 하나인지, 직원이 화장실 갈 때 줄 전체가 멈추는지(동기 호출!) 개점 전에 보입니다. locust 는 그 50명을 연기하는 배우들입니다.

🗺️

설계 그림

첫 그림은 캐시의 한 요청입니다. GET /auctions?status=active 가 오면 서비스는 먼저 Redis 에서 auction:list:version(정수, 없으면 0)을 읽고, 정렬된 파라미터와 합쳐 키를 만듭니다: auction:list:v3:limit=20,sort=ending_soon,status=active. 있으면 그 JSON 을 그대로 돌려주고(DB 0번), 없으면 5단계 그대로 DB 를 읽어 AuctionPage 를 만든 뒤 SET … EX 5 로 붙여 둡니다. 경매가 바뀌는 여섯 지점(생성·수정·취소·입찰·활성화·마감) 은 커밋 뒤에 INCR auction:list:version 한 번만 합니다 — 다음 요청은 v4 키를 찾으니 v3 은 자연히 미스이고, TTL 이 치웁니다.

둘째 그림은 운영 모양입니다. 다섯 컨테이너가 auction-prod 라는 하나의 네트워크 안에 있고, 그 안에서는 db·redis·app·mock_pg 라는 서비스 이름이 곧 호스트명입니다(localhost 는 각 컨테이너 자기 자신입니다!). 밖(호스트)에는 8000(app)과 8001(mock_pg)만 엽니다 — DB 와 Redis 는 열지 않습니다. app 만 시작할 때 alembic upgrade head 를 먼저 돌리고(sh -c "… && exec uvicorn …"), worker 는 app 이 healthy 가 된 뒤에 뜹니다(마이그레이션이 끝났다는 뜻). 세 파이썬 컨테이너는 같은 이미지(auction-api:local)에 명령만 다릅니다.

세 프로세스가 같은 이미지인 이유. 코드·의존성이 같으니 이미지를 하나만 빌드하고 command 만 바꿉니다. 이미지가 셋이면 빌드 시간도 셋, 버전이 엇갈릴 위험도 셋입니다. 진짜 운영에서는 mock_pg 가 빠지고 그 자리에 진짜 PG 의 URL 이 PG_BASE_URL 로 들어갑니다 — 코드는 안 바뀌고 환경변수만 바뀝니다(1단계의 Settings 가 여기서 빛을 봅니다).
