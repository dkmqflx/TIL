여섯 장면입니다. ① 스위치를 켠 서버에서 캐시·request-id 를 눈으로 확인 → ② 부하 테스트 A(스위치 켬) → ③ 스위치 끄고 부하 테스트 B → ④ 개발 환경 정리 → ⑤ 컨테이너 다섯 개로 전체 흐름 → ⑥ CI 와 같은 명령을 로컬에서. 터미널 두 개를 씁니다.

2. 부하 테스트 A — 50ms 동기 호출이 켜진 채

50명이 초당 10명씩 들어와 20초. 표의 req/s 와 50%(p50)·95% 열만 보면 됩니다. 상세 조회(/auctions/{id})에만 50ms 를 넣었는데 목록·입찰·로그인까지 전부 700ms 대입니다 — 한 요청의 time.sleep 이 같은 프로세스의 다른 요청들을 다 세워 두기 때문입니다. 터미널 1 을 보면 slow query 경고가 30줄 찍혀 있는데, SQL 자체가 느린 게 아니라 결과를 받아 처리할 차례가 안 와서 221ms 로 재진 것입니다. 블로킹은 남의 쿼리까지 느려 보이게 합니다.

3. 부하 테스트 B — 스위치 끔

같은 20초에 요청 수 3.3배, p50 은 790ms → 5ms. 이것이 "async 안의 동기 호출 하나" 의 값입니다. 그런데 B 에서도 로그인·가입만 240·370ms 인 것이 보입니까? 그게 bcrypt 입니다 — 아래 한 줄로 재 보면 해시 한 번에 200ms. to_thread 로 스레드에 보냈기 때문에 그 요청은 200ms 걸려도 다른 요청은 5ms 로 답합니다. 보내지 않았다면 표 전체가 A 처럼 됐을 겁니다.

bash터미널 1
# 터미널 1 에서 Ctrl-C 로 끄고, 이번엔 스위치 없이
uv run uvicorn app.main:app --port 8000
bash터미널 2
AUCTION_ID=$A uv run locust -f loadtest/locustfile.py --headless -u 50 -r 10 -t 20s --host http://localhost:8000 --only-summary
# → 아래 표 (B: 기본값). 같은 20초에 2,898 요청 · 146 req/s · p50 5ms

uv run python -c "
import time
from app.core.security import hash_password, verify_password
t=time.perf_counter(); h=hash_password('secret123'); a=(time.perf_counter()-t)*1000
t=time.perf_counter(); verify_password('secret123', h); b=(time.perf_counter()-t)*1000
print(f'hash {a:.0f} ms · verify {b:.0f} ms')"

5. 컨테이너 다섯 개 — 빌드 · 기동 · 전체 흐름

--build 가 Dockerfile 로 이미지를 만들고(337MB — uv·빌드 캐시가 없는 런타임만), compose 가 다섯을 순서대로 띄웁니다: db·redis healthy → app(마이그레이션 두 개 실행 → uvicorn) healthy → worker. 그다음은 9단계 시나리오를 컨테이너를 상대로 그대로 돌립니다 — 다른 점은 입찰과 checkout 에 X-Request-ID 를 붙여 나중에 로그에서 찾는 것뿐입니다.

bash터미널 2
J='Content-Type: application/json'
for who in alice bob; do curl -s -X POST localhost:8000/auth/signup -H "$J" -d "{\"email\":\"$who@example.com\",\"password\":\"secret123\",\"nickname\":\"$who\"}" > /dev/null; done
tok() { curl -s -X POST localhost:8000/auth/login -H "$J" -d "{\"email\":\"$1@example.com\",\"password\":\"secret123\"}" | python3 -c 'import sys,json; print(json.load(sys.stdin)["access_token"])'; }
ALICE=$(tok alice); BOB=$(tok bob)
ENDS=$(python3 -c "from datetime import datetime, timedelta, UTC; print((datetime.now(UTC)+timedelta(seconds=45)).isoformat())")
A=$(curl -s -X POST localhost:8000/auctions -H "Authorization: Bearer $ALICE" -H "$J" -d "{\"title\":\"컨테이너 속 경매\",\"category\":\"etc\",\"starting_price\":10000,\"ends_at\":\"$ENDS\"}" | python3 -c 'import sys,json; print(json.load(sys.stdin)["id"])')
echo "A=$A"
curl -s -X POST localhost:8000/auctions/$A/bids -H "Authorization: Bearer $BOB" -H "$J" -H "X-Request-ID: e2e-bid-1" -d '{"amount":10000}' | python3 -c 'import sys,json; d=json.load(sys.stdin); print("bid:", d["current_price"], d["bid_count"])'
# bid: 10000 1
echo "waiting for close..."; sleep 52
curl -s localhost:8000/auctions/$A | python3 -c 'import sys,json; d=json.load(sys.stdin); print("auction:", d["status"], "winner", (d["winner_id"] or "")[:8])'
# auction: ended winner d3ca1010            ← 컨테이너 속 워커가 닫았다
PAY=$(docker compose -f docker-compose.prod.yml exec -T db psql -U auction -d auction -tA -c "SELECT id FROM payments WHERE auction_id='$A'")
echo "PAY=$PAY"
curl -s -X POST localhost:8000/payments/$PAY/checkout -H "Authorization: Bearer $BOB" -H "X-Request-ID: e2e-checkout-1"; echo
# {"payment_id":"42e9d953-…","external_id":"pg_d5eb29153ae2","status":"pending"}
sleep 3
curl -s localhost:8000/payments/$PAY -H "Authorization: Bearer $BOB" | python3 -c 'import sys,json; d=json.load(sys.stdin); print("payment:", d["status"], "paid_at", d["paid_at"])'
# payment: paid paid_at 2026-08-25T16:47:50.907317Z   ← mock_pg 컨테이너가 http://app:8000 으로 웹훅을 보냈다

7. CI 파일 검증 — GitHub 에 올리기 전에 같은 명령을 로컬에서

Actions 를 로컬에서 실행하는 도구(act)도 있지만, 여기선 YAML 이 유효한지와 CI 가 돌릴 명령 자체가 같은 환경변수로 통과하는지만 확인합니다. 그 둘이 되면 GitHub 에서도 됩니다. 파일을 til/.github/workflows/auction-api-ci.yml 로 옮겨 커밋·푸시하면 Actions 탭에 auction-api CI 가 나타납니다.

bash터미널 2
uv run python -c "import yaml; d=yaml.safe_load(open('.github/workflows/ci.yml')); print('ci.yml ok:', list(d['jobs']['test'].keys()))"
# ci.yml ok: ['runs-on', 'services', 'env', 'steps']

# CI 와 정확히 같은 환경변수·명령을 로컬에서 (서비스 컨테이너 대신 개발용 compose 의 5435·6380)
export DATABASE_URL=postgresql+asyncpg://auction:auction_pw@localhost:5435/auction REDIS_URL=redis://localhost:6380/0
export JWT_SECRET=ci-only-secret-that-is-at-least-32-bytes-long PG_WEBHOOK_SECRET=ci-only-pg-webhook-secret-32-bytes-minimum
uv sync --frozen && uv run ruff check . && uv run ruff format --check . && uv run alembic upgrade head && uv run alembic check && uv run pytest -q
# Audited 72 packages in 2ms
# All checks passed!
# 76 files already formatted
# INFO  [alembic.runtime.migration] Will assume transactional DDL.
# No new upgrade operations detected.
# 97 passed in 66.75s (0:01:06)
unset DATABASE_URL REDIS_URL JWT_SECRET PG_WEBHOOK_SECRET

  • uv run ruff check . · ruff format --check . 통과, uv run alembic check 무변경

  • 모든 응답에 X-Request-ID, 보낸 값은 그대로 돌아오고, 터미널 로그가 JSON 한 줄에 같은 request_id
  • locust A(스위치 켬) 와 B(끔) 의 req/s·p50 이 확연히 다르다 (기준: 3배 이상)
  • docker compose -f docker-compose.prod.yml up -d --build → ps 에 5개, app·db·redis (healthy), 호스트엔 8000·8001 만

함정 & 실무 팁

로그인 사용자에 따라 달라지는 응답을 공용 키로 캐시하지 마세요. 오늘 캐시한 GET /auctions 는 누가 불러도 같은 답이라서 됐습니다. GET /users/me 나 "내 입찰 목록" 을 같은 방식으로 캐시하면 A 의 화면이 B 에게 갑니다 — 실제로 일어난 유명한 사고들입니다. 사용자별 응답은 키에 user_id 를 넣거나, 아예 캐시하지 않습니다. 규칙: 키를 만드는 재료에 응답을 결정하는 모든 것이 들어가야 한다.
버전을 올리는 자리는 커밋 뒤, 그리고 '목록에 보이는 것이 바뀌는 곳' 전부. 커밋 전에 올리면 그 사이 들어온 요청이 옛 데이터를 새 버전 키로 캐시해 5초 동안 틀린 답이 남습니다. 지점을 하나 빼먹으면(예: 워커의 활성화) 그 변경만 5초 늦게 보입니다 — TTL 이 안전망인 이유이자, TTL 을 무한으로 두면 안 되는 이유입니다. 새 기능을 추가할 때 "이게 목록을 바꾸나?" 를 체크리스트에 넣으세요.
캐시 스탬피드. 인기 키가 만료되는 순간 요청 100개가 동시에 미스를 내고 100번 DB 를 읽어 100번 SET 합니다. 오늘 규모에선 문제없지만 트래픽이 크면 (1) TTL 에 약간의 랜덤(4~6초)을 더해 만료 시각을 흩고, (2) 첫 미스만 DB 를 가고 나머지는 잠깐 기다리게 하는 락(Redis SET NX)을 둡니다. 6단계의 FOR UPDATE 와 같은 발상입니다.
print() 는 로그가 아닙니다. 컨테이너 다섯 개의 출력이 한 화면에 섞이는 순간 request_id 없는 줄은 쓸모가 없어집니다. 오늘 만든 JsonFormatter 는 logging.getLogger(__name__) 로 찍은 모든 로그에 적용되고 request_id 가 자동으로 붙습니다 — 서비스 코드에서 logger.info("bid placed", extra={{"amount": amount}}) 처럼 쓰세요. 그리고 비밀번호·토큰·카드번호는 절대 로그에 넣지 않습니다(로그는 오래 남고 많은 사람이 봅니다).
부하 테스트는 배포 환경과 비슷할 때만 숫자를 믿습니다. 오늘은 노트북에서 서버와 locust 를 같이 돌렸으니 절대값(146 req/s)은 의미가 없고 A 와 B 의 비율만 의미가 있습니다. 운영 전 측정은 스테이징에 배포하고 다른 머신에서 쏘세요. 그리고 --workers 를 늘려 나온 개선은 "블로킹이 없어졌다" 가 아니라 "블로킹을 4개 프로세스가 나눠 맞는다" 입니다.
.env 는 이미지에 들어가면 안 됩니다. .dockerignore 에 .env 가 있는 이유입니다. 이미지는 레지스트리에 올라가고 복사되고 남습니다 — 한 번 들어간 비밀은 회수할 수 없습니다. 비밀은 실행 시점에 환경변수(compose ${{JWT_SECRET}}, Actions secrets, 클라우드의 시크릿 매니저)로 넣습니다. 같은 이유로 docker-compose.prod.yml 의 기본값(:-prod-change-me…)은 로컬 확인용이지 운영값이 아닙니다.
CMD 는 exec 형식, 셸이 필요하면 exec 로 넘기기. CMD uvicorn app.main:app(셸 형식)이면 PID 1 은 sh 이고 uvicorn 은 그 자식입니다. docker stop 의 SIGTERM 은 sh 가 받고 자식에게 안 넘깁니다 → 10초 뒤 SIGKILL → 8단계의 graceful shutdown 이 무의미해지고 처리 중이던 틱이 반쯤에서 죽습니다. compose 의 app 처럼 마이그레이션 뒤에 서버를 띄워야 할 땐 sh -c "alembic … && exec uvicorn …" — exec 가 셸을 uvicorn 으로 바꿔치기해서 PID 1 이 됩니다.
마이그레이션은 한 컨테이너만. app 을 --scale app=3 으로 늘리면 셋이 동시에 alembic upgrade head 를 돌립니다. Alembic 은 락을 잡지 않아 둘이 같은 DDL 을 시도하다 하나가 죽습니다. 운영에선 마이그레이션을 배포 파이프라인의 별도 단계(한 번 실행되는 job)로 빼고, 서버 컨테이너는 서버만 띄웁니다. 오늘 compose 는 app 이 하나라서 && 로 묶은 것이지 정석은 아닙니다.
healthcheck 가 200 이라고 '준비됨' 은 아닙니다. 우리 /health 는 DB·Redis 핑까지 보므로 꽤 정직한 편입니다. 실무에선 liveness(프로세스가 살아 있나 — 죽었으면 재시작)와 readiness(트래픽을 받아도 되나 — 아니면 로드밸런서에서 뺀다)를 나눕니다. 마이그레이션 중이거나 캐시 워밍 중엔 살아 있지만 준비는 안 된 상태입니다. k8s 로 가면 두 프로브를 따로 붙입니다.
CI 의 DB 주소와 로컬의 DB 주소. Actions 서비스 컨테이너는 localhost:호스트포트 로 접근합니다(job 이 컨테이너 안이 아니라 러너 VM 에서 돌 때). 오늘은 5435·6380 으로 매핑해 로컬 기본값을 그대로 썼습니다. job 을 container: 안에서 돌리면 서비스 이름(postgres:5432)으로 바뀝니다 — compose 의 규칙과 같습니다. alembic check 를 CI 에 넣어 두면 "모델은 고쳤는데 마이그레이션을 안 만든" PR 이 여기서 잡힙니다.

셀프 체크

Q 캐시 무효화를 DEL auction:list:* 로 하지 않고 버전을 올리는 이유는? 그리고 이 방식의 대가는 무엇인가요?

Redis 에는 패턴으로 한 번에 지우는 명령이 없습니다 — KEYS/SCAN 으로 찾아서 하나씩 지워야 하고, KEYS 는 키가 많으면 Redis 전체를 멈춥니다. 게다가 "어떤 파라미터 조합이 캐시돼 있는지" 를 서버가 알 수 없습니다(커서·필터·정렬의 조합은 무한합니다). 버전 키는 그 문제를 없앱니다: 변경 지점은 INCR 하나만 하고, 읽는 쪽이 항상 최신 버전 키를 찾으니 옛 키는 자연히 안 읽힙니다. 대가는 (1) 읽을 때마다 GET version 이 한 번 더 든다(Redis 왕복 두 번 — 대개 1ms 미만), (2) 옛 키가 TTL 까지 메모리에 남는다(그래서 TTL 이 짧아야 한다), (3) 경매 하나가 바뀌어도 모든 목록 캐시가 무효화된다 — 변경이 잦으면 히트율이 떨어집니다. 그때는 키에 카테고리 같은 축을 더해 버전을 축별로 나눕니다.

Q 부하 테스트 A 에서 time.sleep(0.05) 는 상세 조회에만 있는데 왜 목록·입찰·로그인까지 전부 700ms 대가 됐나요? uvicorn --workers 4 로 띄우면 해결되나요?

uvicorn 워커 하나는 이벤트 루프 하나이고, 루프는 한 번에 한 코루틴만 실행합니다. await 에서만 다른 코루틴으로 넘어가는데 time.sleep 은 await 가 아니라 그냥 50ms 를 붙잡고 있습니다. 그 50ms 동안 목록 요청의 DB 응답이 도착해도, 입찰의 락이 풀려도, 로그인의 스레드가 끝나도 아무도 처리하지 못합니다 — 줄 전체가 섭니다. 초당 상세 조회가 12건이면 매초 600ms 가 그렇게 사라지고, 그게 모든 엔드포인트의 지연으로 번집니다(slow query 경고가 30개나 찍힌 것도 SQL 이 느린 게 아니라 결과를 받아 줄 차례가 안 와서였습니다). --workers 4 는 루프가 넷이 되니 약 4배 나아지지만, 각 워커가 똑같이 50ms 씩 멈추는 건 그대로입니다 — 트래픽이 4배 되면 원위치입니다. 치료는 동기 호출을 없애거나(httpx·asyncpg 처럼 async 라이브러리로) 스레드로 보내는 것(asyncio.to_thread, 오늘 bcrypt 에 한 일)입니다.

Q Dockerfile 이 FROM 을 두 번 쓰는 이유는? 그리고 USER app 과 exec 형식 CMD 를 빼면 각각 무슨 일이 생기나요?

첫 FROM(빌더)에는 uv 와 빌드 캐시, 컴파일에 필요한 도구가 들어가고 거기서 .venv 를 만듭니다. 둘째 FROM(런타임)은 파이썬만 있는 slim 이미지에서 시작해 빌더의 /app 만 COPY --from 합니다. 결과: 이미지가 작고(337MB — 빌더 전체를 쓰면 2배 이상), 공격 표면이 작고(uv·컴파일러가 없음), 캐시 레이어가 잘 나뉩니다(잠금 파일이 안 바뀌면 의존성 설치를 건너뜀). USER app 을 빼면 프로세스가 root 로 돕니다 — 앱에 취약점이 있을 때 컨테이너 안에서 무엇이든 할 수 있고, 컨테이너 탈출 취약점과 만나면 호스트까지 갑니다. 파일을 못 쓰는 게 아니라 못 쓰게 두는 것이 목적입니다. exec 형식을 셸 형식으로 바꾸면 PID 1 이 sh 가 되어 docker stop 의 SIGTERM 이 uvicorn·워커에 전달되지 않고, 10초 뒤 SIGKILL 로 죽습니다 — 처리 중이던 요청이 끊기고, 8단계 워커는 틱 중간에 죽어 락만 풀립니다(데이터는 트랜잭션 덕에 안전하지만 "조용한 종료" 는 없어집니다).
