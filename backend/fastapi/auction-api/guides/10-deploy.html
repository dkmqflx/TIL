10단계 — 성능·관측성·배포: 운영 모양으로

기능은 9단계로 끝났습니다. 마지막 단계는 새 기능을 더하지 않습니다. 지금까지 만든 API·워커·모의 PG 를 "내 노트북에서 도는 것" 에서 "남이 운영할 수 있는 것" 으로 바꿉니다: 자주 읽는 목록에 캐시를 붙이고, 모든 로그를 JSON 한 줄 + request-id 로 통일하고, 브라우저가 부를 수 있게 CORS 를 열고, 부하 테스트로 숨은 블로킹 호출을 잡아내고, Dockerfile·compose 로 다섯 프로세스를 한 번에 띄우고, GitHub Actions 가 매 푸시마다 테스트를 돌리게 합니다.

한 줄 요약. 이 문서를 끝내면 uv run pytest -q 가 97 passed 를 찍고, 같은 목록을 두 번 부르면 두 번째는 DB 를 안 건드리며(17.8ms → 2.2ms), 모든 응답에 X-Request-ID 가 붙고 로그가 {"ts": …, "request_id": …, "duration_ms": …} 한 줄로 나오며, locust 가 "일부러 넣은 50ms 동기 호출" 을 44 → 146 req/s, p50 790ms → 5ms 라는 숫자로 드러내고, docker compose -f docker-compose.prod.yml up -d --build 한 줄로 다섯 컨테이너가 떠서 가입 → 경매 → 입찰 → 자동 마감 → 결제 → 웹훅까지 컨테이너 안에서 전부 돕니다.

학습 목표

  • "버전 키" 캐시가 왜 DEL·SCAN 없이 무효화되는지 설명하고, 어디서 버전을 올려야 하는지 고를 수 있다
  • request-id 가 contextvar 를 타고 같은 요청의 모든 로그(우리 코드·httpx·SQL 경고)에 자동으로 붙는 원리를 안다
  • 부하 테스트 숫자(RPS·p50·p95)만 보고 "이벤트 루프를 막는 동기 호출이 있다" 를 의심할 수 있다
  • 멀티스테이지 Dockerfile 이 왜 두 FROM 인지, 비루트 사용자와 exec-form CMD 가 왜 중요한지 안다
  • compose 안에서는 localhost 가 아니라 서비스 이름이 호스트명이라는 것, 마이그레이션은 한 컨테이너만 돌려야 한다는 것을 안다
  • GitHub Actions 서비스 컨테이너로 Postgres·Redis 를 띄워 우리 테스트 전체를 CI 에서 돌릴 수 있다

이 단계의 목표

9단계까지의 서비스는 내 노트북 전용이었습니다. 터미널 세 개에 uvicorn·워커·모의 PG 를 따로 띄우고, 로그는 사람 눈으로 읽는 한 줄짜리 텍스트였고, 목록은 부를 때마다 DB 를 갔습니다. 이번 단계가 끝나면 (1) GET /auctions 는 5초 동안 Redis 에서 답하고 경매가 바뀌는 순간 자동으로 새로 읽으며, (2) 모든 로그가 request_id 를 품은 JSON 한 줄이라 "이 요청이 왜 느렸지?" 를 한 값으로 좇을 수 있고, (3) locust 가 50명 동시 접속을 흉내 내 병목을 숫자로 보여 주며, (4) docker compose -f docker-compose.prod.yml up -d --build 한 줄로 다섯 컨테이너(app·worker·mock_pg·db·redis)가 뜨고, (5) GitHub 에 푸시할 때마다 Actions 가 ruff → 마이그레이션 → 테스트 97개를 돌립니다.

전제. 9단계가 끝나 있어야 합니다. uv run pytest -q → 87 passed, 컨테이너 두 개 (healthy), Docker Desktop 실행 중, 8000·8001 포트 비어 있음. 새로 설치하는 패키지는 locust(개발용) 하나입니다. 마이그레이션은 없습니다. 작업 위치는 til/backend/fastapi/auction-api/.

이번 단계에서 만드는 것. 새 파일 10개(core/cache.py, core/logging.py, 테스트 2개, loadtest/locustfile.py, Dockerfile, .dockerignore, docker-compose.prod.yml, .github/workflows/ci.yml, README.md), 손보는 파일 10개(설정 4개 값, alembic/env.py 한 줄, 서비스 4개에 "버전 올리기" 한 줄씩, services/auth.py 의 bcrypt 를 스레드로, 라우터, main.py, 워커, conftest.py). 기능(엔드포인트·모델·규칙)은 하나도 안 바뀝니다 — 그래서 9단계까지의 87개 테스트가 그대로 통과해야 합니다.

왜 필요한가 — 실무 맥락

실무에서 "기능이 된다" 와 "운영할 수 있다" 사이에는 네 가지 질문이 있습니다. 빠른가 — 인기 경매 목록은 초당 수백 번 읽히는데 매번 DB 를 가야 하나? 보이는가 — 새벽에 "결제가 안 돼요" 라는 문의가 오면, 그 사용자의 그 요청이 어느 워커에서 어떤 SQL 을 몇 ms 돌렸는지 찾을 수 있나? 버티는가 — 50명이 동시에 누르면 어디가 먼저 무너지나? 그걸 배포 전에 알 수 있나? 옮길 수 있는가 — 내 노트북의 uv·파이썬 버전·환경변수 없이도 다른 컴퓨터(동료, 서버, CI)에서 똑같이 뜨나? 이 넷에 답하는 도구가 각각 캐시, 구조화 로그, 부하 테스트, 컨테이너입니다.

이 중 초보자가 가장 자주 놓치는 것이 로그입니다. print() 와 텍스트 로그는 혼자 개발할 땐 충분하지만, 컨테이너 다섯 개가 같은 화면에 섞여 찍히기 시작하면 "이 줄이 어느 요청의 것인지" 를 알 수 없습니다. 그래서 운영 로그는 (1) 기계가 읽는 JSON, (2) 요청마다 고유한 request_id, (3) 응답 코드와 소요 시간이 기본입니다. 프론트가 에러 화면에 X-Request-ID 를 찍어 두면 사용자가 그 값을 알려 주는 순간 서버 로그에서 한 줄로 찾습니다 — 택배 송장번호와 같습니다.

부하 테스트는 4주차·02 에서 배운 "async 안의 동기 호출은 서버 전체를 멈춘다" 를 숫자로 보는 시간입니다. 코드 리뷰로는 놓치는 requests.get() 하나, 동기 이미지 변환 하나가 p95 를 1초로 만듭니다. 오늘은 일부러 50ms 짜리 time.sleep 을 넣고 켜고 끄며 재 봅니다 — 그리고 그 과정에서 우리 코드에 진짜로 숨어 있던 200ms 짜리 블로킹 호출(bcrypt)도 찾아냅니다.

순서에 대해. 실무에선 Dockerfile 과 CI 가 1단계에 있는 경우도 많습니다(처음부터 컨테이너로 개발). 이 커리큘럼이 10단계에 둔 이유는 "컨테이너에 넣을 것이 다 갖춰진 뒤" 가 가장 배우기 쉽기 때문입니다 — 다섯 프로세스의 역할과 환경변수를 전부 아는 지금이라야 compose 파일의 한 줄 한 줄이 왜 있는지 보입니다.

비유 — 공장과 매장, 송장번호, FAQ 종이

캐시 = 카운터 앞에 붙여 둔 FAQ 답변. 손님 100명이 같은 질문("지금 열린 경매 뭐 있어요?")을 하면 매번 창고(DB)에 다녀오는 대신 답을 종이에 적어 카운터에 붙여 둡니다. 종이엔 판 번호(v7)가 적혀 있고, 경매가 하나라도 바뀌면 벽의 판 번호판을 v8 로 넘깁니다. 그러면 v7 종이는 아무도 안 보고(찾아서 떼어낼 필요도 없이) 5초 뒤 바람에 날아갑니다(TTL). 새 손님에겐 v8 종이를 새로 적어 붙입니다. "어떤 종이를 떼야 하지?" 를 고민하지 않아도 되는 게 버전 키의 요점입니다.

request-id = 택배 송장번호. 물건 하나가 접수 → 허브 → 배송기사 → 문 앞까지 가는 동안 여러 사람 손을 거치지만, 송장번호 하나로 전 구간을 좇습니다. 우리 요청도 미들웨어 → 라우터 → 서비스 → SQL → httpx(PG 호출) 를 거치는데, 맨 앞에서 번호를 붙여 두면(contextvar) 그 뒤 어디서 찍힌 로그든 같은 번호가 따라붙습니다. 프론트가 번호를 미리 붙여 보내면(X-Request-ID 헤더) 브라우저 콘솔과 서버 로그가 같은 번호를 공유합니다.

멀티스테이지 Dockerfile = 공장과 매장. 공장(빌더 스테이지)에는 uv, 컴파일러, 캐시 같은 큰 장비가 있고 거기서 제품(.venv)을 만듭니다. 매장(런타임 스테이지)엔 제품과 진열대(파이썬)만 옮겨 놓습니다 — 장비는 안 가져갑니다. 그래서 최종 이미지가 작고, 공격 표면도 작고, 매장 직원은 관리자(root)가 아니라 일반 직원(app 사용자)입니다.

부하 테스트 = 개점 전 리허설. 손님 50명을 한 번에 들여보내 보면 카운터가 하나인지, 직원이 화장실 갈 때 줄 전체가 멈추는지(동기 호출!) 개점 전에 보입니다. locust 는 그 50명을 연기하는 배우들입니다.

설계 그림

첫 그림은 캐시의 한 요청입니다. GET /auctions?status=active 가 오면 서비스는 먼저 Redis 에서 auction:list:version(정수, 없으면 0)을 읽고, 정렬된 파라미터와 합쳐 키를 만듭니다: auction:list:v3:limit=20,sort=ending_soon,status=active. 있으면 그 JSON 을 그대로 돌려주고(DB 0번), 없으면 5단계 그대로 DB 를 읽어 AuctionPage 를 만든 뒤 SET … EX 5 로 붙여 둡니다. 경매가 바뀌는 여섯 지점(생성·수정·취소·입찰·활성화·마감) 은 커밋 뒤에 INCR auction:list:version 한 번만 합니다 — 다음 요청은 v4 키를 찾으니 v3 은 자연히 미스이고, TTL 이 치웁니다.

둘째 그림은 운영 모양입니다. 다섯 컨테이너가 auction-prod 라는 하나의 네트워크 안에 있고, 그 안에서는 db·redis·app·mock_pg 라는 서비스 이름이 곧 호스트명입니다(localhost 는 각 컨테이너 자기 자신입니다!). 밖(호스트)에는 8000(app)과 8001(mock_pg)만 엽니다 — DB 와 Redis 는 열지 않습니다. app 만 시작할 때 alembic upgrade head 를 먼저 돌리고(sh -c "… && exec uvicorn …"), worker 는 app 이 healthy 가 된 뒤에 뜹니다(마이그레이션이 끝났다는 뜻). 세 파이썬 컨테이너는 같은 이미지(auction-api:local)에 명령만 다릅니다.

세 프로세스가 같은 이미지인 이유. 코드·의존성이 같으니 이미지를 하나만 빌드하고 command 만 바꿉니다. 이미지가 셋이면 빌드 시간도 셋, 버전이 엇갈릴 위험도 셋입니다. 진짜 운영에서는 mock_pg 가 빠지고 그 자리에 진짜 PG 의 URL 이 PG_BASE_URL 로 들어갑니다 — 코드는 안 바뀌고 환경변수만 바뀝니다(1단계의 Settings 가 여기서 빛을 봅니다).

캐시 4개: 같은 목록을 두 번 부르면 두 번째는 query_counter.selects == 0(5단계에서 N+1 을 잴 때 만든 그 fixture), 입찰 뒤엔 current_version == 1 이 되고 다음 호출은 DB 를 다시 간다, 경매를 API 로 만들면 빈 결과 캐시가 무효화된다, 파라미터가 다르면 키가 다르다(3개). 관측성 6개: X-Request-ID 를 안 주면 UUID 로 만들어 돌려주고 주면 그대로 돌려준다, access 로그 한 줄이 JSON 이고 request_id·method·path·status·duration_ms 를 품는다(caplog 로 레코드를 잡아 우리 JsonFormatter 로 찍어 본다), 임계값 0 으로 설치하면 pg_sleep 이 "slow query" 로 남는다, CORS preflight 가 허용 출처엔 200 + 헤더, 모르는 출처엔 400.

"""GET /auctions 캐시 — '버전 키' 방식.

두 번째 호출은 DB 를 건드리지 않고(SELECT 0), 경매가 바뀌면(생성·입찰) 버전이 올라
새 키로 다시 읽는다. 키마다 TTL 이 있어 무효화를 놓쳐도 몇 초 뒤엔 스스로 사라진다.
"""

from datetime import UTC, datetime, timedelta

from httpx2 import AsyncClient
from redis.asyncio import Redis
from sqlalchemy.ext.asyncio import AsyncSession

from app.core import cache
from app.core.config import get_settings
from app.schemas.auction import AuctionListParams
from tests.conftest import QueryCounter
from tests.factories import create_auction, create_user, login_headers


async def _seed(db: AsyncSession, n: int = 3) -> None:
    seller = await create_user(db, email="seller@example.com", nickname="판매자")
    for i in range(n):
        await create_auction(db, seller, title=f"경매 {i}")


async def test_second_call_is_served_from_cache(
    client: AsyncClient, db_session: AsyncSession, redis: Redis, query_counter: QueryCounter
):
    await _seed(db_session)
    first = await client.get("/auctions", params={"status": "active"})
    assert first.status_code == 200, first.text
    assert len(first.json()["items"]) == 3

    query_counter.reset()
    second = await client.get("/auctions", params={"status": "active"})

    assert second.json() == first.json()
    assert query_counter.selects == 0  # DB 에 한 문장도 안 갔다
    keys = await redis.keys("auction:list:v0:*")
    assert len(keys) == 1
    assert 0 < await redis.ttl(keys[0]) <= get_settings().list_cache_ttl_seconds


async def test_bid_bumps_version_and_invalidates(
    client: AsyncClient, db_session: AsyncSession, redis: Redis, query_counter: QueryCounter
):
    await _seed(db_session, n=1)
    await create_user(db_session, email="bidder@example.com", nickname="입찰자")
    before = (await client.get("/auctions")).json()
    assert before["items"][0]["current_price"] == 10_000
    assert await cache.current_version(redis) == 0

    headers = await login_headers(client, "bidder@example.com")
    res = await client.post(
        f"/auctions/{before['items'][0]['id']}/bids", json={"amount": 10_000}, headers=headers
    )
    assert res.status_code == 201, res.text
    assert await cache.current_version(redis) == 1  # 입찰이 버전을 올렸다

    query_counter.reset()
    after = (await client.get("/auctions")).json()
    assert query_counter.selects >= 1  # 새 버전 키 → 미스 → DB
    assert after["items"][0]["bid_count"] == 1


async def test_create_auction_bumps_version(
    client: AsyncClient, db_session: AsyncSession, redis: Redis
):
    await create_user(db_session, email="seller@example.com", nickname="판매자")
    headers = await login_headers(client, "seller@example.com")
    assert (await client.get("/auctions")).json()["items"] == []  # 빈 결과도 캐시된다

    ends_at = (datetime.now(UTC) + timedelta(hours=1)).isoformat()

        "/auctions",
        json={"title": "새 경매", "category": "hobby", "starting_price": 5_000, "ends_at": ends_at},

async def bump_version(redis: Redis) -> int:
    """목록에 보이는 무언가가 바뀌었다 — 생성·수정·취소·입찰·활성화·마감 뒤에 부른다."""

    fields = params.model_dump(mode="json", exclude_none=True)
    query = ",".join(f"{k}={fields[k]}" for k in sorted(fields))
    return f"{KEY_PREFIX}:v{version}:{query}"

"""입찰 규칙. HTTP 를 모른다 — 도메인 예외만 던진다.

핵심은 순서다: (rate limit) → **경매 행 잠금** → 규칙 검사 → 갱신 → 커밋.
잠금부터 커밋까지가 한 트랜잭션이라, 그 사이에 다른 입찰은 줄을 서서 기다린다.
그래서 '현재가 + 최소 단위' 를 계산할 때 본 값이 커밋하는 순간까지 그대로다.
"""

import uuid
from datetime import UTC, datetime, timedelta

from redis.asyncio import Redis
from sqlalchemy.ext.asyncio import AsyncSession

from app.core import cache, events
from app.core.config import get_settings
from app.core.exceptions import (
    AuctionNotActiveError,
    AuctionNotFoundError,
    BidRateLimitedError,
    BidTooLowError,
    OwnAuctionBidError,
)
from app.models import Auction, AuctionStatus, Bid, User
from app.repositories import auction as auction_repo
from app.repositories import bid as bid_repo


def _now() -> datetime:
    """시계를 함수로 빼 두면 테스트에서 멈추거나 돌릴 수 있다."""
    return datetime.now(UTC)


async def _check_rate_limit(redis: Redis, user_id: uuid.UUID, now: datetime) -> None:
    """사용자별 '이번 1초' 카운터. INCR 는 원자적이라 동시에 들어와도 정확히 센다."""
    key = f"bid:rl:{user_id}:{int(now.timestamp())}"
    count = await redis.incr(key)
    if count == 1:
        await redis.expire(key, 2)  # 1초짜리 키가 영원히 남지 않도록
    if count > get_settings().bid_rate_limit_per_second:
        raise BidRateLimitedError()


def minimum_bid(auction: Auction) -> int:
    """첫 입찰은 시작가 이상, 그 다음부터는 현재가 + 최소 단위 이상."""
    if auction.bid_count == 0:
        return auction.starting_price
    return auction.current_price + auction.min_increment


async def place_bid(
    db: AsyncSession, redis: Redis, bidder: User, auction_id: uuid.UUID, amount: int
) -> tuple[Bid, Auction]:
    settings = get_settings()
    now = _now()

    await _check_rate_limit(redis, bidder.id, now)  # 락을 잡기 *전에* — 스팸이 락을 쥐고 있지 않게

    auction = await auction_repo.get_for_update(db, auction_id)  # ← 여기서부터 줄을 선다
    if auction is None:
        raise AuctionNotFoundError()
    if auction.status != AuctionStatus.ACTIVE or now >= auction.ends_at:
        raise AuctionNotActiveError()
    if auction.seller_id == bidder.id:
        raise OwnAuctionBidError()
    minimum = minimum_bid(auction)
    if amount < minimum:
        raise BidTooLowError(
            f"최소 입찰액은 {minimum:,}원입니다 (현재가 {auction.current_price:,}원)"
        )

    # 규칙 4 — 마감 직전 입찰이면 마감을 늦춘다 (스나이핑 방지)
    extended = False
    if auction.ends_at - now < timedelta(seconds=settings.snipe_window_seconds):
        auction.ends_at = auction.ends_at + timedelta(seconds=settings.snipe_extend_seconds)
        extended = True

    auction.current_price = amount
    auction.bid_count += 1
    auction.version += 1
    bid = Bid(auction_id=auction.id, bidder_id=bidder.id, amount=amount)
    await bid_repo.add(db, bid)

    await db.commit()  # ← 여기서 락이 풀리고, 줄 서 있던 다음 입찰이 '바뀐 현재가' 를 본다
    await db.refresh(bid)
    await db.refresh(auction)
    await cache.bump_version(redis)  # 목록의 current_price·bid_count 가 바뀌었다

    # 커밋 *뒤에* 방송한다. 커밋 전에 방송하면 구독자가 "아직 DB 에 없는 입찰" 을 보게 되고,
    # 커밋이 실패하면 없던 일이 방송된 채로 남는다.
    await events.publish(
        redis,
        events.AuctionEvent(
            type="bid_placed",
            auction_id=auction.id,
            payload={
                "amount": bid.amount,
                "bidder_id": bid.bidder_id,
                "current_price": auction.current_price,
                "bid_count": auction.bid_count,
                "ends_at": auction.ends_at,
                "version": auction.version,
                "extended": extended,
            },
        ),
    )
    return bid, auction


async def list_bids(db: AsyncSession, auction_id: uuid.UUID) -> list[Bid]:

        raise AuctionNotFoundError()
    return await bid_repo.list_by_auction(db, auction_id)

"""시간이 흐르면 저절로 일어나야 하는 일 세 가지. HTTP 도, 루프도, 시그널도 모른다.

  activate_due   : 시작 시각이 지난 scheduled 경매 → active
  close_due      : 마감 시각이 지난 active 경매 → ended (+ 낙찰자, Payment, auction_closed 이벤트)
  expire_payments: 결제 기한이 지난 pending 결제 → expired

세 함수 모두 `now` 를 인자로 받는다. 워커는 진짜 시계를 넣고, 테스트는 원하는 시각을 넣는다.
누가 부르든(워커 1개든 2개든) 결과가 같아야 한다 — 그게 이 파일의 유일한 어려움이다.
"""

import logging
import uuid
from dataclasses import dataclass
from datetime import datetime, timedelta

from redis.asyncio import Redis
from sqlalchemy import update
from sqlalchemy.ext.asyncio import AsyncSession

from app.core import cache, events

from app.models import Auction, AuctionStatus, Payment, PaymentStatus
from app.repositories import auction as auction_repo
from app.repositories import bid as bid_repo
from app.repositories import payment as payment_repo

logger = logging.getLogger(__name__)


@dataclass(frozen=True)
class ClosedResult:
    auction_id: uuid.UUID
    winner_id: uuid.UUID | None  # None = 유찰 (입찰 0건)
    final_price: int | None
    bid_count: int
    payment_id: uuid.UUID | None


async def activate_due(db: AsyncSession, now: datetime, *, limit: int | None = None) -> int:
    """UPDATE 한 문장. UPDATE 는 스스로 행을 잠그므로 워커가 둘이어도 안전하다 —
    둘째 워커는 첫째의 커밋을 기다렸다가 다시 조건을 보고(이미 active) 0 행을 바꾼다."""
    limit = limit or get_settings().closer_batch_size
    ids = await auction_repo.list_due_scheduled_ids(db, now, limit=limit)
    if not ids:
        return 0
    stmt = (
        update(Auction)
        .where(Auction.id.in_(ids), Auction.status == AuctionStatus.SCHEDULED)  # 조건을 한 번 더
        .values(status=AuctionStatus.ACTIVE, version=Auction.version + 1)
        .returning(Auction.id)
    )
    activated = list((await db.scalars(stmt)).all())
    await db.commit()
    if activated:
        logger.info("activated %d auction(s): %s", len(activated), [str(i)[:8] for i in activated])
    return len(activated)


async def close_due(
    db: AsyncSession, redis: Redis, now: datetime, *, limit: int | None = None
) -> list[ClosedResult]:
    """후보 목록은 락 없이 값싸게 뽑고, 실제 처리는 **한 건씩** 잠그고 커밋한다.

    왜 한 건씩인가: 100건을 한 트랜잭션에 묶으면 (1) 100번째에서 실패하면 99건이 같이 롤백되고,
    (2) 그동안 100개 행이 잠겨 입찰 요청들이 줄을 선다. 한 건씩이면 실패도 잠금도 한 건뿐이다.
    왜 skip_locked 인가: 다른 워커가 이미 잡은 행이면 기다릴 이유가 없다 — 그쪽이 끝낼 것이다.
    왜 재검사인가: 후보를 뽑은 뒤 잠그기까지 사이에 누가 이미 닫았을 수 있다(그 워커가 커밋해서
    락을 풀면 우리는 status=ended 인 행을 잠그게 된다). 잠근 *뒤에* 본 값만 믿는다.
    """
    settings = get_settings()
    limit = limit or settings.closer_batch_size
    results: list[ClosedResult] = []

    for auction_id in await auction_repo.list_due_active_ids(db, now, limit=limit):
        auction = await auction_repo.get_for_update(db, auction_id, skip_locked=True)
        if auction is None:  # 다른 워커가 잠갔거나(skip) 사라졌다 → 내 몫이 아니다
            continue
        if auction.status != AuctionStatus.ACTIVE or auction.ends_at > now:  # 잠근 뒤 재검사
            await db.rollback()  # 잠금만 풀고 다음
            continue

        top = await bid_repo.top_bid(db, auction.id)
        auction.status = AuctionStatus.ENDED
        auction.winner_id = top.bidder_id if top else None
        auction.version += 1

        payment: Payment | None = None
        if top is not None:
            payment = await payment_repo.add(
                db,
                Payment(
                    auction_id=auction.id,
                    payer_id=top.bidder_id,
                    amount=auction.current_price,
                    status=PaymentStatus.PENDING,
                    expires_at=now + timedelta(hours=settings.payment_deadline_hours),
                ),
            )
        await db.commit()  # ← 여기서 이 경매의 락이 풀린다. 아래는 커밋된 사실만 방송한다
        await cache.bump_version(redis)  # 목록의 status 가 ended 로 바뀌었다

        result = ClosedResult(
            auction_id=auction.id,
            winner_id=auction.winner_id,
            final_price=auction.current_price if top else None,
            bid_count=auction.bid_count,
            payment_id=payment.id if payment else None,
        )
        await events.publish(
            redis,
            events.AuctionEvent(
                type="auction_closed",
                auction_id=auction.id,
                payload={
                    "winner_id": result.winner_id,
                    "final_price": result.final_price,
                    "bid_count": result.bid_count,
                    "payment_id": result.payment_id,
                    "payment_expires_at": payment.expires_at if payment else None,
                    "version": auction.version,
                },
            ),
        )
        if top is not None:
            # 진짜라면 여기서 메일/푸시 큐에 넣는다. 이 프로젝트에서는 로그 한 줄이 '알림' 이다.
            logger.info(
                "[notify] user=%s 낙찰! auction=%s %s원 — %s 까지 결제해 주세요",
                str(top.bidder_id)[:8],
                str(auction.id)[:8],
                f"{auction.current_price:,}",
                payment.expires_at.isoformat(timespec="minutes") if payment else "",
            )
        else:
            logger.info("[notify] auction=%s 유찰 (입찰 0건)", str(auction.id)[:8])
        results.append(result)
    return results


async def expire_payments(db: AsyncSession, now: datetime) -> int:
    """기한 지난 pending → expired. activate_due 와 같은 'UPDATE 한 문장' 패턴."""
    stmt = (
        update(Payment)
        .where(Payment.status == PaymentStatus.PENDING, Payment.expires_at <= now)
        .values(status=PaymentStatus.EXPIRED)
        .returning(Payment.id)
    )
    expired = list((await db.scalars(stmt)).all())
    await db.commit()
    if expired:
        logger.info("expired %d payment(s): %s", len(expired), [str(i)[:8] for i in expired])
    return len(expired)

하는 일은 단순하다: interval 초마다 시계를 보고 services/closer 의 세 함수를 차례로 부른다.

  - 별도 프로세스면 API 와 독립적으로 죽이고 살리고 늘릴 수 있다 (10단계 compose 의 `worker` 서비스)
"""

import asyncio
import logging
import signal
from dataclasses import dataclass, field
from datetime import UTC, datetime

from redis.asyncio import Redis

from app.core import cache
from app.core.config import get_settings
from app.core.db import SessionLocal, engine
from app.core.logging import install_slow_query_logging, setup_logging
from app.services import closer
from app.services.closer import ClosedResult

@dataclass
class TickResult:
    activated: int = 0
    closed: list[ClosedResult] = field(default_factory=list)
    expired: int = 0

    @property
    def empty(self) -> bool:
        return self.activated == 0 and not self.closed and self.expired == 0


async def tick(redis: Redis, now: datetime | None = None) -> TickResult:
    """한 번의 '시계 보기'. 함수마다 세션을 새로 여는 이유: 하나가 실패해도 다른 둘은 독립적으로
    커밋되고, 세션(커넥션)을 틱 사이에 쥐고 있지 않기 위해서다."""
    now = now or datetime.now(UTC)
    result = TickResult()
    async with SessionLocal() as db:
        result.activated = await closer.activate_due(db, now)
    if result.activated:
        await cache.bump_version(redis)  # scheduled → active: 목록의 status 가 바뀌었다
    async with SessionLocal() as db:
        result.closed = await closer.close_due(db, redis, now)
    async with SessionLocal() as db:
        result.expired = await closer.expire_payments(db, now)
    return result


async def run(stop: asyncio.Event, redis: Redis, interval: float) -> None:
    """stop 이 set 될 때까지 interval 마다 tick. 한 틱이 실패해도 루프는 죽지 않는다(로그만)."""
    logger.info("closer started (interval=%ss)", interval)
    while not stop.is_set():
        try:
            result = await tick(redis)
            if not result.empty:
                logger.info(
                    "tick: activated=%d closed=%d expired=%d",
                    result.activated,
                    len(result.closed),
                    result.expired,
                )
        except Exception:  # noqa: BLE001 — 워커는 한 틱의 실패로 죽으면 안 된다
            logger.exception("tick failed")
        try:
            # sleep 하면 종료 신호를 interval 만큼 늦게 받는다. stop.wait() 를 기다리면 즉시 깬다.
            await asyncio.wait_for(stop.wait(), timeout=interval)
        except TimeoutError:
            pass
    logger.info("closer stopped")


async def main() -> None:
    settings = get_settings()
    setup_logging()  # API 와 같은 JSON 로그 — 한 수집기에서 두 프로세스를 같은 모양으로 본다
    install_slow_query_logging(engine, settings.slow_query_ms)
    redis = Redis.from_url(settings.redis_url, decode_responses=True)  # 워커 전용 클라이언트
    stop = asyncio.Event()
    loop = asyncio.get_running_loop()
    for sig in (signal.SIGINT, signal.SIGTERM):  # Ctrl-C, docker stop → 조용히 마무리
        loop.add_signal_handler(sig, stop.set)
    try:
        await run(stop, redis, settings.closer_interval_seconds)
    finally:
        await redis.aclose()
        await engine.dispose()


if __name__ == "__main__":
    asyncio.run(main())

"""JSON 로그 · request-id · 느린 쿼리 경고.

로그 한 줄 = JSON 한 개. 사람이 아니라 수집기(Loki·CloudWatch·Datadog)가 읽는다고 생각하고 쓴다.
request_id 는 contextvar 에 둔다 — 같은 요청을 처리하는 동안 어디서 찍힌 로그든 자동으로 따라붙는다.
"""

import contextvars
import json
import logging
import sys
import time
import uuid
from collections.abc import Awaitable, Callable
from datetime import UTC, datetime

from fastapi import Request, Response
from sqlalchemy import event
from sqlalchemy.ext.asyncio import AsyncEngine

REQUEST_ID_HEADER = "X-Request-ID"
request_id_var: contextvars.ContextVar[str] = contextvars.ContextVar("request_id", default="-")

# LogRecord 가 원래 갖고 있는 속성들 — 이 밖의 것은 extra={} 로 들어온 우리 필드다
_STANDARD = set(logging.LogRecord("x", 0, "", 0, "", (), None).__dict__) | {
    "message",
    "asctime",
    "taskName",
}


class JsonFormatter(logging.Formatter):
    def format(self, record: logging.LogRecord) -> str:
        line: dict[str, object] = {
            "ts": datetime.fromtimestamp(record.created, UTC).isoformat(timespec="milliseconds"),
            "level": record.levelname,
            "logger": record.name,
            "msg": record.getMessage(),
            "request_id": getattr(record, "request_id", None) or request_id_var.get(),
        }
        for key, value in record.__dict__.items():
            if key not in _STANDARD and key != "request_id":
                line[key] = value
        if record.exc_info:
            line["exc"] = self.formatException(record.exc_info)
        return json.dumps(line, ensure_ascii=False, default=str)


def setup_logging(level: str = "INFO") -> None:
    """루트 로거 하나에 JSON 핸들러 하나. uvicorn 의 로그도 여기로 흘려보내고,
    uvicorn 의 access 로그는 끈다 — 우리 미들웨어가 request_id 와 소요 시간을 붙여 대신 남긴다."""
    handler = logging.StreamHandler(sys.stdout)
    handler.setFormatter(JsonFormatter())
    root = logging.getLogger()
    root.handlers = [handler]
    root.setLevel(level)
    for name in ("uvicorn", "uvicorn.error"):
        uv = logging.getLogger(name)
        uv.handlers = []
        uv.propagate = True
    access = logging.getLogger("uvicorn.access")
    access.handlers = []
    access.propagate = False


access_logger = logging.getLogger("app.access")
db_logger = logging.getLogger("app.db")


async def request_id_middleware(
    request: Request, call_next: Callable[[Request], Awaitable[Response]]
) -> Response:
    """들어온 X-Request-ID 가 있으면 그대로(게이트웨이·프론트가 붙인 것), 없으면 발급.
    응답 헤더로 돌려주고, 요청 한 줄을 JSON 으로 남긴다."""
    request_id = request.headers.get(REQUEST_ID_HEADER) or str(uuid.uuid4())
    token = request_id_var.set(request_id)
    started = time.perf_counter()
    status = 500  # 처리 중 예외로 끝나면 500 으로 기록된다
    try:
        response = await call_next(request)
        status = response.status_code
    finally:
        access_logger.info(
            "request",
            extra={
                "request_id": request_id,
                "method": request.method,
                "path": request.url.path,
                "status": status,
                "duration_ms": round((time.perf_counter() - started) * 1000, 1),
            },
        )
        request_id_var.reset(token)
    response.headers[REQUEST_ID_HEADER] = request_id
    return response


def install_slow_query_logging(engine: AsyncEngine, threshold_ms: int) -> Callable[[], None]:
    """커서 실행 전후 이벤트로 SQL 하나의 소요 시간을 재고, 임계값을 넘으면 WARNING.
    async 엔진도 속은 동기 엔진(engine.sync_engine)이라 거기에 건다. 되돌리는 함수를 돌려준다."""
    sync_engine = engine.sync_engine
    stack_key = f"slow_query_started:{id(sync_engine)}:{threshold_ms}"

    def before(conn, cursor, statement, parameters, context, executemany):  # noqa: ANN001
        conn.info.setdefault(stack_key, []).append(time.perf_counter())

    def after(conn, cursor, statement, parameters, context, executemany):  # noqa: ANN001
        started = conn.info.get(stack_key)
        if not started:
            return
        elapsed_ms = (time.perf_counter() - started.pop()) * 1000
        if elapsed_ms >= threshold_ms:
            db_logger.warning(
                "slow query",
                extra={
                    "duration_ms": round(elapsed_ms, 1),
                    "statement": " ".join(statement.split())[:300],
                },
            )

    event.listen(sync_engine, "before_cursor_execute", before)
    event.listen(sync_engine, "after_cursor_execute", after)

    def remove() -> None:
        event.remove(sync_engine, "before_cursor_execute", before)
        event.remove(sync_engine, "after_cursor_execute", after)

    return remove
contextvar 가 왜 필요한가. 요청 하나는 미들웨어 → 라우터 → 서비스 → SQL → httpx 를 거치는데, request_id 를 함수 인자로 다 끌고 다닐 순 없습니다. ContextVar 는 "지금 이 코루틴(과 거기서 파생된 태스크·스레드)만의 전역 변수" 입니다. 미들웨어가 한 번 set 하면 그 요청을 처리하는 동안 어디서 get 해도 같은 값이고, 동시에 처리 중인 다른 요청은 자기 값을 봅니다. 실행·확인에서 httpx 라이브러리의 자체 로그에까지 우리 request_id 가 붙는 걸 보게 됩니다 — 우리가 httpx 에 아무것도 안 넘겼는데도요.

def _refresh_key(jti: str) -> str:

async def signup(db: AsyncSession, data: SignupRequest) -> User:
    if await user_repo.get_by_email(db, data.email) is not None:
        raise EmailAlreadyExistsError()
    user = await user_repo.create(

        password_hash=await asyncio.to_thread(hash_password, data.password),
        nickname=data.nickname,
    )
    await db.commit()

    return user


async def _issue_token_pair(redis: Redis, user_id: uuid.UUID) -> TokenPair:
    access = create_access_token(user_id)
    refresh, jti, ttl = create_refresh_token(user_id)
    await redis.set(_refresh_key(jti), str(user_id), ex=ttl)  # 살아 있는 refresh 토큰 목록
    return TokenPair(access_token=access, refresh_token=refresh)


async def login(db: AsyncSession, redis: Redis, data: LoginRequest) -> TokenPair:
    user = await user_repo.get_by_email(db, data.email)
    # 이메일이 없는 경우와 비밀번호가 틀린 경우를 구분해 알려주지 않는다 (계정 존재 여부 노출 방지)
    ok = user is not None and await asyncio.to_thread(
        verify_password, data.password, user.password_hash
    )
    if not ok:
        raise UnauthorizedError("이메일 또는 비밀번호가 올바르지 않습니다")
    return await _issue_token_pair(redis, user.id)


async def refresh(redis: Redis, refresh_token: str) -> TokenPair:
    try:
        payload = decode_token(refresh_token, expected_type="refresh")
    except TokenError as exc:
        raise UnauthorizedError("refresh 토큰이 유효하지 않습니다") from exc
    # DEL 은 원자적이다: 같은 토큰으로 동시에 두 번 와도 한 쪽만 1 을 받는다 → 회전(rotation)
    deleted = await redis.delete(_refresh_key(payload["jti"]))
    if not deleted:
        raise UnauthorizedError("이미 사용됐거나 폐기된 refresh 토큰입니다")
    return await _issue_token_pair(redis, uuid.UUID(payload["sub"]))


async def logout(redis: Redis, refresh_token: str) -> None:
    try:
        payload = decode_token(refresh_token, expected_type="refresh")
    except TokenError:
        return  # 이미 못 쓰는 토큰이면 할 일이 없다 — 로그아웃은 멱등
    await redis.delete(_refresh_key(payload["jti"]))

locust 는 "사용자 한 명이 하는 일" 을 파이썬 클래스로 씁니다. on_start 에서 가입·로그인을 한 번 하고, 그 뒤엔 목록 5 : 상세 3 : 입찰 1 의 비율로 반복합니다(@task(5)). 입찰은 대부분 규칙에 걸려 422·429 로 거절되는데, 그건 서버가 일을 제대로 한 것이므로 실패로 세지 않습니다(catch_response). 9주차·03 에서 ab/wrk 로 했던 것의 "시나리오 있는" 버전입니다.

"""부하 테스트 시나리오 — 실행:
    uv run locust -f loadtest/locustfile.py --headless -u 50 -r 10 -t 20s \
        --host http://localhost:8000 --only-summary

가상 사용자 한 명 = 회원가입 → 로그인(한 번) → 목록 5 : 상세 3 : 입찰 1 비율로 반복.
AUCTION_ID 환경변수가 있으면 그 경매에 입찰하고, 없으면 active 목록의 첫 경매를 쓴다.
입찰은 422(너무 낮음)·429(rate limit)도 '정상 응답' 으로 센다 —
서버가 규칙대로 거절한 것이지 장애가 아니다.
"""

import os
import random
import uuid

from locust import HttpUser, between, task


class Bidder(HttpUser):
    wait_time = between(0.1, 0.5)  # 요청 사이 0.1~0.5초 (사람이 화면을 보는 시간)

    def on_start(self) -> None:
        email = f"load-{uuid.uuid4().hex[:8]}@example.com"
        self.client.post(
            "/auth/signup",
            json={"email": email, "password": "secret123", "nickname": "부하"},
            name="/auth/signup",
        )
        res = self.client.post(
            "/auth/login", json={"email": email, "password": "secret123"}, name="/auth/login"
        )
        self.headers = {"Authorization": f"Bearer {res.json()['access_token']}"}
        self.auction_id = os.environ.get("AUCTION_ID")
        if not self.auction_id:
            res = self.client.get("/auctions", params={"status": "active"}, name="/auctions")
            page = res.json()
            self.auction_id = page["items"][0]["id"] if page["items"] else None

    @task(5)
    def list_auctions(self) -> None:
        self.client.get("/auctions", params={"status": "active", "limit": 20}, name="/auctions")

    @task(3)
    def read_auction(self) -> None:
        if self.auction_id:
            self.client.get(f"/auctions/{self.auction_id}", name="/auctions/{id}")

    @task(1)
    def place_bid(self) -> None:
        if not self.auction_id:
            return
        # 대부분 '너무 낮음' 으로 거절된다 — 그래도 서버가 하는 일(락·규칙 검사)은 같다
        amount = random.randint(1, 500) * 1_000
        with self.client.post(
            f"/auctions/{self.auction_id}/bids",
            json={"amount": amount},
            headers=self.headers,
            name="/auctions/{id}/bids",
            catch_response=True,
        ) as res:
            if res.status_code in (201, 422, 429):
                res.success()
            else:
                res.failure(f"unexpected {res.status_code}")

7. CI 파일 검증 — GitHub 에 올리기 전에 같은 명령을 로컬에서

Actions 를 로컬에서 실행하는 도구(act)도 있지만, 여기선 YAML 이 유효한지와 CI 가 돌릴 명령 자체가 같은 환경변수로 통과하는지만 확인합니다. 그 둘이 되면 GitHub 에서도 됩니다. 파일을 til/.github/workflows/auction-api-ci.yml 로 옮겨 커밋·푸시하면 Actions 탭에 auction-api CI 가 나타납니다.

  • locust A(스위치 켬) 와 B(끔) 의 req/s·p50 이 확연히 다르다 (기준: 3배 이상)

  • 컨테이너 상대로 가입 → 45초 경매 → 입찰 → ended + winner → checkout → 3초 뒤 paid
  • logs app 에서 e2e-checkout-1 로 grep 하면 access 로그와 httpx 로그가 같은 request_id 로 나온다
  • stop worker → 로그에 closer stopped, down -v 로 깨끗이
  • ci.yml 이 yaml.safe_load 를 통과하고, CI 와 같은 명령이 로컬에서 전부 통과
여기서 커밋하세요 — 마지막입니다. 예: git commit -m "add(be(fastapi)): auction-api 10단계 — 캐시·JSON 로그·부하 테스트·Docker·CI". README.md 의 회고 세 줄을 채우고, ci.yml 을 til/.github/workflows/auction-api-ci.yml 로 옮겨 푸시하면 첫 CI 가 돕니다. 로드맵(index.html)의 "완주 후" 에 다음 갈 길을 적어 두었습니다.

함정 & 실무 팁

로그인 사용자에 따라 달라지는 응답을 공용 키로 캐시하지 마세요. 오늘 캐시한 GET /auctions 는 누가 불러도 같은 답이라서 됐습니다. GET /users/me 나 "내 입찰 목록" 을 같은 방식으로 캐시하면 A 의 화면이 B 에게 갑니다 — 실제로 일어난 유명한 사고들입니다. 사용자별 응답은 키에 user_id 를 넣거나, 아예 캐시하지 않습니다. 규칙: 키를 만드는 재료에 응답을 결정하는 모든 것이 들어가야 한다.
버전을 올리는 자리는 커밋 뒤, 그리고 '목록에 보이는 것이 바뀌는 곳' 전부. 커밋 전에 올리면 그 사이 들어온 요청이 옛 데이터를 새 버전 키로 캐시해 5초 동안 틀린 답이 남습니다. 지점을 하나 빼먹으면(예: 워커의 활성화) 그 변경만 5초 늦게 보입니다 — TTL 이 안전망인 이유이자, TTL 을 무한으로 두면 안 되는 이유입니다. 새 기능을 추가할 때 "이게 목록을 바꾸나?" 를 체크리스트에 넣으세요.
캐시 스탬피드. 인기 키가 만료되는 순간 요청 100개가 동시에 미스를 내고 100번 DB 를 읽어 100번 SET 합니다. 오늘 규모에선 문제없지만 트래픽이 크면 (1) TTL 에 약간의 랜덤(4~6초)을 더해 만료 시각을 흩고, (2) 첫 미스만 DB 를 가고 나머지는 잠깐 기다리게 하는 락(Redis SET NX)을 둡니다. 6단계의 FOR UPDATE 와 같은 발상입니다.
print() 는 로그가 아닙니다. 컨테이너 다섯 개의 출력이 한 화면에 섞이는 순간 request_id 없는 줄은 쓸모가 없어집니다. 오늘 만든 JsonFormatter 는 logging.getLogger(__name__) 로 찍은 모든 로그에 적용되고 request_id 가 자동으로 붙습니다 — 서비스 코드에서 logger.info("bid placed", extra={{"amount": amount}}) 처럼 쓰세요. 그리고 비밀번호·토큰·카드번호는 절대 로그에 넣지 않습니다(로그는 오래 남고 많은 사람이 봅니다).
부하 테스트는 배포 환경과 비슷할 때만 숫자를 믿습니다. 오늘은 노트북에서 서버와 locust 를 같이 돌렸으니 절대값(146 req/s)은 의미가 없고 A 와 B 의 비율만 의미가 있습니다. 운영 전 측정은 스테이징에 배포하고 다른 머신에서 쏘세요. 그리고 --workers 를 늘려 나온 개선은 "블로킹이 없어졌다" 가 아니라 "블로킹을 4개 프로세스가 나눠 맞는다" 입니다.
.env 는 이미지에 들어가면 안 됩니다. .dockerignore 에 .env 가 있는 이유입니다. 이미지는 레지스트리에 올라가고 복사되고 남습니다 — 한 번 들어간 비밀은 회수할 수 없습니다. 비밀은 실행 시점에 환경변수(compose ${{JWT_SECRET}}, Actions secrets, 클라우드의 시크릿 매니저)로 넣습니다. 같은 이유로 docker-compose.prod.yml 의 기본값(:-prod-change-me…)은 로컬 확인용이지 운영값이 아닙니다.
CMD 는 exec 형식, 셸이 필요하면 exec 로 넘기기. CMD uvicorn app.main:app(셸 형식)이면 PID 1 은 sh 이고 uvicorn 은 그 자식입니다. docker stop 의 SIGTERM 은 sh 가 받고 자식에게 안 넘깁니다 → 10초 뒤 SIGKILL → 8단계의 graceful shutdown 이 무의미해지고 처리 중이던 틱이 반쯤에서 죽습니다. compose 의 app 처럼 마이그레이션 뒤에 서버를 띄워야 할 땐 sh -c "alembic … && exec uvicorn …" — exec 가 셸을 uvicorn 으로 바꿔치기해서 PID 1 이 됩니다.
마이그레이션은 한 컨테이너만. app 을 --scale app=3 으로 늘리면 셋이 동시에 alembic upgrade head 를 돌립니다. Alembic 은 락을 잡지 않아 둘이 같은 DDL 을 시도하다 하나가 죽습니다. 운영에선 마이그레이션을 배포 파이프라인의 별도 단계(한 번 실행되는 job)로 빼고, 서버 컨테이너는 서버만 띄웁니다. 오늘 compose 는 app 이 하나라서 && 로 묶은 것이지 정석은 아닙니다.
healthcheck 가 200 이라고 '준비됨' 은 아닙니다. 우리 /health 는 DB·Redis 핑까지 보므로 꽤 정직한 편입니다. 실무에선 liveness(프로세스가 살아 있나 — 죽었으면 재시작)와 readiness(트래픽을 받아도 되나 — 아니면 로드밸런서에서 뺀다)를 나눕니다. 마이그레이션 중이거나 캐시 워밍 중엔 살아 있지만 준비는 안 된 상태입니다. k8s 로 가면 두 프로브를 따로 붙입니다.
CI 의 DB 주소와 로컬의 DB 주소. Actions 서비스 컨테이너는 localhost:호스트포트 로 접근합니다(job 이 컨테이너 안이 아니라 러너 VM 에서 돌 때). 오늘은 5435·6380 으로 매핑해 로컬 기본값을 그대로 썼습니다. job 을 container: 안에서 돌리면 서비스 이름(postgres:5432)으로 바뀝니다 — compose 의 규칙과 같습니다. alembic check 를 CI 에 넣어 두면 "모델은 고쳤는데 마이그레이션을 안 만든" PR 이 여기서 잡힙니다.

셀프 체크

Q 캐시 무효화를 DEL auction:list:* 로 하지 않고 버전을 올리는 이유는? 그리고 이 방식의 대가는 무엇인가요?

Redis 에는 패턴으로 한 번에 지우는 명령이 없습니다 — KEYS/SCAN 으로 찾아서 하나씩 지워야 하고, KEYS 는 키가 많으면 Redis 전체를 멈춥니다. 게다가 "어떤 파라미터 조합이 캐시돼 있는지" 를 서버가 알 수 없습니다(커서·필터·정렬의 조합은 무한합니다). 버전 키는 그 문제를 없앱니다: 변경 지점은 INCR 하나만 하고, 읽는 쪽이 항상 최신 버전 키를 찾으니 옛 키는 자연히 안 읽힙니다. 대가는 (1) 읽을 때마다 GET version 이 한 번 더 든다(Redis 왕복 두 번 — 대개 1ms 미만), (2) 옛 키가 TTL 까지 메모리에 남는다(그래서 TTL 이 짧아야 한다), (3) 경매 하나가 바뀌어도 모든 목록 캐시가 무효화된다 — 변경이 잦으면 히트율이 떨어집니다. 그때는 키에 카테고리 같은 축을 더해 버전을 축별로 나눕니다.

Q 부하 테스트 A 에서 time.sleep(0.05) 는 상세 조회에만 있는데 왜 목록·입찰·로그인까지 전부 700ms 대가 됐나요? uvicorn --workers 4 로 띄우면 해결되나요?

uvicorn 워커 하나는 이벤트 루프 하나이고, 루프는 한 번에 한 코루틴만 실행합니다. await 에서만 다른 코루틴으로 넘어가는데 time.sleep 은 await 가 아니라 그냥 50ms 를 붙잡고 있습니다. 그 50ms 동안 목록 요청의 DB 응답이 도착해도, 입찰의 락이 풀려도, 로그인의 스레드가 끝나도 아무도 처리하지 못합니다 — 줄 전체가 섭니다. 초당 상세 조회가 12건이면 매초 600ms 가 그렇게 사라지고, 그게 모든 엔드포인트의 지연으로 번집니다(slow query 경고가 30개나 찍힌 것도 SQL 이 느린 게 아니라 결과를 받아 줄 차례가 안 와서였습니다). --workers 4 는 루프가 넷이 되니 약 4배 나아지지만, 각 워커가 똑같이 50ms 씩 멈추는 건 그대로입니다 — 트래픽이 4배 되면 원위치입니다. 치료는 동기 호출을 없애거나(httpx·asyncpg 처럼 async 라이브러리로) 스레드로 보내는 것(asyncio.to_thread, 오늘 bcrypt 에 한 일)입니다.

Q Dockerfile 이 FROM 을 두 번 쓰는 이유는? 그리고 USER app 과 exec 형식 CMD 를 빼면 각각 무슨 일이 생기나요?

첫 FROM(빌더)에는 uv 와 빌드 캐시, 컴파일에 필요한 도구가 들어가고 거기서 .venv 를 만듭니다. 둘째 FROM(런타임)은 파이썬만 있는 slim 이미지에서 시작해 빌더의 /app 만 COPY --from 합니다. 결과: 이미지가 작고(337MB — 빌더 전체를 쓰면 2배 이상), 공격 표면이 작고(uv·컴파일러가 없음), 캐시 레이어가 잘 나뉩니다(잠금 파일이 안 바뀌면 의존성 설치를 건너뜀). USER app 을 빼면 프로세스가 root 로 돕니다 — 앱에 취약점이 있을 때 컨테이너 안에서 무엇이든 할 수 있고, 컨테이너 탈출 취약점과 만나면 호스트까지 갑니다. 파일을 못 쓰는 게 아니라 못 쓰게 두는 것이 목적입니다. exec 형식을 셸 형식으로 바꾸면 PID 1 이 sh 가 되어 docker stop 의 SIGTERM 이 uvicorn·워커에 전달되지 않고, 10초 뒤 SIGKILL 로 죽습니다 — 처리 중이던 요청이 끊기고, 8단계 워커는 틱 중간에 죽어 락만 풀립니다(데이터는 트랜잭션 덕에 안전하지만 "조용한 종료" 는 없어집니다).
