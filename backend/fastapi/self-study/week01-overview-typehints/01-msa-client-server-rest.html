웹 백엔드의 큰 그림 — 클라이언트–서버 · API · REST · MSA

코드를 짜기 전에, "내가 만들 서버가 전체 시스템의 어디에 서 있는지"를 먼저 그려봅니다. 면접에서 가장 먼저 물어보는 지도(map)입니다.

한 줄 요약. 백엔드는 요청을 받아 → 데이터를 처리하고 → 응답을 돌려주는 쪽이다. API는 클라이언트와 서버가 대화하는 약속, REST는 그 약속을 적는 가장 흔한 양식, MSA는 큰 서버 하나를 기능별 작은 서버 여럿으로 쪼갠 구조다.

학습 목표

  • 클라이언트–서버 모델을 한 문장으로 설명할 수 있다
  • API와 REST API가 무엇이고 왜 필요한지 안다
  • HTTP 메서드 · 상태 코드 · 자원(Resource)의 관계를 이해한다
  • 모놀리식과 MSA의 차이, 그 속에서 FastAPI의 자리를 안다
🖥️

클라이언트와 서버 — 누가 무엇을 하나

웹은 결국 요청(Request)과 응답(Response)의 끝없는 주고받음입니다. 요청하는 쪽이 Client, 응답하는 쪽이 Server입니다.

비유 — 레스토랑. 손님(클라이언트)은 직접 주방에 들어가 요리하지 않습니다. 메뉴판(API)에 적힌 이름대로 주문하면 주방(서버)이 요리해서 접시(응답)를 돌려줍니다. 손님은 주방이 가스레인지를 쓰는지 인덕션을 쓰는지 몰라도 됩니다. 이렇게 각자 자기 일만 신경 쓰고 상대의 속사정은 몰라도 되게 나눠 두는 것을 관심사의 분리라고 부릅니다.
요청은 코랄, 응답은 틸. 백엔드 개발자는 오른쪽 박스를 만든다.
🔌

API — 시스템 사이의 약속된 창구

API = Application Programming Interface. 풀어 쓰면 "프로그램끼리 대화하기 위해 미리 약속해 둔 창구"입니다 — 앞 비유의 메뉴판이 바로 이것입니다. 클라이언트는 서버가 정해둔 규칙(URL, 메서드, 데이터 형식)대로 요청해야 합니다.

프론트 경험과 연결. fetch('/api/todos')를 써봤다면 지금까지는 API를 쓰는 쪽이었고, 이제부터는 그 규칙을 정하는 쪽입니다.
📋

REST API — 가장 널리 쓰이는 API 설계 양식

API를 설계하는 방식에는 여러 스타일이 있지만, 웹에서 사실상 표준은 REST(REpresentational State Transfer)입니다. 핵심 아이디어는 단 하나 —

세상의 모든 것을 자원(Resource)으로 보고, 각 자원에 주소(URL)를 주고, 행동은 HTTP 메서드로 표현한다.

예를 들어 "할 일(todo)"이라는 자원을 다룬다면:

하고 싶은 일HTTP 메서드URL(주소)성공 상태코드
할 일 전체 조회GET/todos200 OK
특정 할 일 1건 조회GET/todos/42200 OK
새 할 일 생성POST/todos201 Created
할 일 일부 수정PATCH/todos/42200 OK
할 일 통째로 교체PUT/todos/42200 OK
할 일 삭제DELETE/todos/42204 No Content
비유 — 같은 주소, 다른 행동. 주소 /todos/42는 "42번 할 일"이라는 집 주소 하나입니다. 그 집에 대해 GET은 "안을 들여다봐", PATCH는 "내용을 고쳐", DELETE는 "허물어"입니다. 주소는 하나, 행동만 바뀝니다.

상태 코드는 응답의 한 줄 요약입니다. 자세한 건 Week 2에서 다루지만, 큰 분류만 기억해 두세요:

범위뜻대표 예시
2xx성공200 OK · 201 Created · 204 No Content
4xx클라이언트 잘못400 Bad Request · 401 Unauthorized(로그인 안 됨) · 404 Not Found
5xx서버 잘못500 Internal Server Error
🏬

모놀리식 vs MSA — 서버를 하나로 둘까, 여럿으로 쪼갤까

서비스가 커지면 "서버 하나에 모든 기능을 다 넣을 것인가, 아니면 기능별로 쪼갤 것인가"라는 질문에 부딪힙니다.

비유 — 만능 식당 vs 푸드코트. 모놀리식은 한식·중식·디저트를 한 주방에서 다 만드는 만능 식당입니다. 처음엔 단순하고 빠르지만, 디저트 담당이 실수로 불을 내면 식당 전체가 멈춥니다. MSA는 각 요리를 전문 매장으로 분리한 푸드코트 — 중식당이 문을 닫아도 디저트 가게는 멀쩡히 장사합니다.
왼쪽은 한 덩어리 앱, 오른쪽은 기능별로 나뉜 서비스들.

그래서 FastAPI는 어디에 서 있나

FastAPI는 가볍고, 비동기를 지원하고(한 요청을 기다리는 동안 다른 요청을 처리하는 방식 — Week 4에서 배웁니다), 타입 힌트만으로 명세가 자동으로 만들어집니다(명세 = "어떤 주소에 어떤 입력·출력이 있는지" 적은 API 설명서 — 03에서 직접 봅니다). 그래서 MSA의 서비스 하나를 만들기에 잘 맞고, 이 강의에서 당신은 바로 그 서비스 하나를 처음부터 끝까지 만들게 됩니다.

🔀

NestJS를 알면 이미 절반은 안다

NestJS를 써본 적이 없다면 이 섹션은 건너뛰어도 됩니다. NestJS로 서버를 만들어 봤다면 "라우트 하나에 핸들러 함수를 연결한다"는 핵심 멘탈 모델을 이미 갖고 있는 겁니다. 표현만 다를 뿐입니다.

NestJS — 데코레이터 + 클래스
@Controller('todos')
export class TodosController {
  @Get()
  findAll() {
    return this.service.findAll();
  }
}

클래스 + 메서드 데코레이터로 라우트를 선언.

FastAPI — 함수 + 데코레이터
@app.get("/todos")
def find_all():
    return service.find_all()

함수 하나 + 경로 데코레이터면 끝. 더 적은 보일러플레이트.

핵심 대응표. Nest @Controller → FastAPI APIRouter (Week 3) · Nest @Get/@Post → @app.get/@app.post · Nest DTO + class-validator → Pydantic 모델 (Week 3) · Nest Provider/DI → FastAPI Depends (Week 6). 이름표만 바꿔 끼우면 됩니다.
⚠️

자주 빠지는 함정

동사를 URL에 넣지 말 것. POST /createTodo, GET /getTodoById는 REST 위반입니다. 동작은 메서드가 이미 말하고 있으니 POST /todos, GET /todos/42로 충분합니다. 함수 이름을 주소로 부르는 이런 방식은 RPC(Remote Procedure Call, "원격 함수 호출") 스타일이라 하고, 한 API 안에 두 스타일이 섞이면 면접관이 바로 알아챕니다.
"MSA가 항상 정답"이라는 착각. MSA는 공짜가 아닙니다. 함수 호출이던 것이 네트워크 통신이 되어 느려지고 실패할 수 있고, 여러 서버에 걸친 작업을 한꺼번에 성공시키거나 되돌리기가 어려워지며(분산 트랜잭션 문제), 서버 수만큼 운영 부담이 늘어납니다. "왜 MSA를 쓰는가"만큼 "왜 안 쓰는가"도 말할 수 있어야 합니다.
✅

셀프 체크 — 면접관처럼 물어보기

Q 클라이언트와 서버를 한 문장으로 설명해 보세요.

요청을 보내고 응답을 받는 쪽이 클라이언트, 요청을 받아 처리하고 응답을 돌려주는 쪽이 서버입니다. 둘은 약속된 규칙(API)으로만 소통하며, 서로의 내부 구현을 몰라도 됩니다.

Q REST에서 PUT과 PATCH, POST의 차이는?

POST는 새 자원 생성, PUT은 자원 전체 교체, PATCH는 자원의 일부만 수정입니다. 이 강의의 ToDo API는 부분 수정을 위해 주로 PATCH를 씁니다.

Q 작은 스타트업에 MSA를 권하겠습니까?

대개는 아니요. 작은 팀은 서버 하나로 시작하는 게 개발·배포·디버깅 모두 단순합니다. 나중에 특정 기능만 따로 확장하거나 배포해야 할 때, 그 부분부터 떼어내면 됩니다.
