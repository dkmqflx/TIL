요청의 모든 입구 — Path · Query · Body · Header · Cookie · Form

클라이언트가 보내는 데이터는 요청의 여러 입구로 나뉘어 들어옵니다. 어떤 데이터를 어느 입구로 받을지 고르는 것이 API 설계의 첫 단추입니다.

한 줄 요약. 클라이언트가 보내는 데이터는 Path · Query · Body · Header · Cookie · Form 여섯 입구로 나뉘어 들어온다. FastAPI는 함수 매개변수의 선언 방식만 보고 어느 입구인지 자동으로 알아챈다.

학습 목표

  • HTTP 요청의 구조와 6가지 데이터 입구를 구분한다
  • Path / Query / Body를 언제 쓰는지 판단 기준을 갖는다
  • 각 입구를 FastAPI에서 선언하는 법을 NestJS와 비교해 익힌다
🔬

HTTP 요청의 해부도

먼저 "요청 하나가 실제로 어떻게 생겼는지"를 봅시다. curl -X POST가 만들어내는 날것의 HTTP 메시지입니다.

한 줄짜리 요청 안에 6개 입구가 흩어져 있다. FastAPI가 이걸 깔끔히 분리해준다.
비유 — 택배 상자. Path는 상자에 적힌 받는 주소(어떤 자원인가) · Query는 붙여둔 포스트잇 메모(어떻게 처리할까: 정렬·필터) · Body는 상자 속 실제 내용물(생성/수정할 데이터) · Header는 운송장의 메타 정보(형식·인증) · Cookie는 단골 회원카드입니다.
📍

Path 파라미터 — "어떤 자원인가"

URL 경로에 박혀 있는 값입니다. 특정 자원을 식별할 때 씁니다. 중괄호 {}로 선언하고, 같은 이름의 함수 매개변수로 받습니다. 타입 힌트를 달면 자동 검증됩니다.

NestJS
@Get(':id')
findOne(@Param('id') id: number) {
  return ...;
}
FastAPI
@app.get("/todos/{id}")
def find_one(id: int):
    return ...

Path 파라미터는 항상 필수입니다 — URL의 일부이니 빠질 수 없죠. /todos/abc처럼 타입이 안 맞으면 FastAPI가 422(요청 검증 실패) 응답을 자동으로 돌려줍니다 — 이 에러는 03에서 자세히 봅니다.

🔍

Query 파라미터 — "어떻게 처리할까"

URL ? 뒤의 key=value 쌍입니다. 주로 정렬·필터·페이지네이션처럼 "선택적 옵션"에 씁니다. 아래처럼 int·str 같은 기본형 타입의 매개변수를 그냥 적으면 쿼리로 받습니다.

python
# GET /todos?skip=0&limit=10&done=true
@app.get("/todos")
def list_todos(skip: int = 0, limit: int = 10, done: bool | None = None):
    # skip, limit → 기본값 있으니 선택적
    # done → None 기본값이라 생략 가능
    return {"skip": skip, "limit": limit, "done": done}
필수 vs 선택은 "기본값"이 가른다. 매개변수에 기본값이 있으면 선택적, 없으면 필수 쿼리가 됩니다. q: str → 필수, q: str = "x" → 선택. 이 규칙은 뒤에 나올 Header·Cookie·Form에도 똑같이 적용됩니다.
📦

Request Body — "생성/수정할 데이터"

POST·PATCH로 보내는 JSON 본문입니다. FastAPI에서는 Pydantic 모델(JSON의 모양을 파이썬 클래스로 선언한 것, Week 3에서 깊게)로 받습니다. 매개변수 타입이 Pydantic 모델이면 본문에서 읽습니다.

NestJS — DTO
class CreateTodoDto {
  title: string;
  done: boolean;
}
// controller
@Post()
create(@Body() dto: CreateTodoDto) {}
FastAPI — Pydantic
class CreateTodo(BaseModel):
    title: str
    done: bool

@app.post("/todos")
def create(todo: CreateTodo):
    return todo

NestJS의 DTO + class-validator 조합을, FastAPI는 Pydantic 모델 하나로 선언과 검증을 동시에 해결합니다.

🍪

Header · Cookie · Form — 나머지 입구

이들은 명시적으로 Header(), Cookie(), Form()을 써서 "이 매개변수는 이 입구에서 받아라"라고 알려줍니다. 괄호 안이 기본값입니다 — Header(None)은 "없으면 None"이니 선택, Form()처럼 비워 두면 기본값이 없으니 필수입니다.

python
from fastapi import Header, Cookie, Form

@app.get("/me")
def me(
    user_agent: str | None = Header(None),   # 헤더 User-Agent (선택)
    session: str | None = Cookie(None),      # 쿠키 session (선택)
):
    return {"ua": user_agent, "session": session}

@app.post("/login")
def login(username: str = Form(), password: str = Form()):  # 둘 다 필수
    # HTML <form>이 제출될 때 쓰는 전송 형식(application/x-www-form-urlencoded)
    # JSON이 아니라 username=a&password=b 모양으로 온다
    return {"user": username}
Header 이름 변환 규칙. Python 변수 user_agent는 HTTP 헤더 User-Agent에 자동 매핑됩니다 (언더스코어 → 하이픈, 대소문자 무시). 그리고 Form()을 쓰려면 uv add python-multipart가 필요합니다 — 안 깔면 에러가 납니다.
프론트에서는 어떻게 보내나? User-Agent 같은 표준 헤더와 쿠키는 브라우저가 요청마다 자동으로 실어 보내므로 프론트가 따로 할 일이 거의 없습니다. 단, 프론트와 API의 주소(출처)가 다르면 쿠키를 보내기 위해 fetch의 credentials 설정과 서버 쪽 CORS 허용이 필요합니다 — Week 7·03 CORS에서 다룹니다. 그 쿠키를 서버가 만들어 내려주고 다시 받는 세션 인증 흐름은 Week 8·02에서 직접 구현합니다.

인자 순서가 바뀌어도 될까?

결론부터: FastAPI 입장에선 순서가 전혀 상관없습니다. FastAPI는 인자의 위치가 아니라 이름 + Header()/Cookie()/타입 선언을 보고 어디서 값을 꺼낼지 정하기 때문입니다. user_agent와 session의 자리를 바꿔도 동작은 똑같습니다.

단, 파이썬 문법 규칙 하나 — "기본값 없는 인자가 먼저". 이건 FastAPI가 아니라 순수 파이썬 규칙입니다: 기본값이 있는 인자 뒤에 기본값 없는 인자가 올 수 없습니다. 위 예시는 Header(None)·Cookie(None) 둘 다 기본값이 있어 자유롭지만, 필수 인자와 섞이면 걸립니다.
python
# ❌ SyntaxError: non-default argument follows default argument
@app.get("/items/{item_id}")
def read(
    user_agent: str | None = Header(None),  # 기본값 있음
    item_id: int,                           # 기본값 없음 → 뒤에 못 옴!
): ...

# ✅ 필수 인자를 앞으로 옮기면 된다
def read(item_id: int, user_agent: str | None = Header(None)): ...
이 순서 고민을 없애는 표기법 — Annotated. 파이썬 typing 모듈의 Annotated[타입, 부가정보]는 타입에 메모를 붙이는 문법입니다. Annotated[str, Header()]는 "타입은 str인데, FastAPI 너는 이걸 헤더에서 꺼내"라는 뜻이죠. 출처(값을 요청의 어느 입구에서 꺼낼지)가 기본값 자리가 아니라 타입 쪽에 들어가니, 필수 매개변수는 진짜로 "기본값 없음"이 되어 위 규칙에 걸리지 않습니다. FastAPI 공식 문서가 권장하는 최신 표기이고, 동작 원리와 재사용법은 Week 6·02에서 Depends와 함께 자세히 봅니다.
python
from typing import Annotated

# 필수 헤더라면 옛 방식은 '기본값 자리'를 써야 해서 순서에 걸리지만
def read(x_token: str = Header(), item_id: int): ...            # ❌ SyntaxError

# Annotated는 출처를 타입 쪽에 두고 기본값 자리는 비워 둔다 → 순서 자유
def read(x_token: Annotated[str, Header()], item_id: int): ...  # ✅

# 선택 매개변수는 = None을 뒤에 붙이면 된다
def me(user_agent: Annotated[str | None, Header()] = None): ...
🧩

그래서 뭘 보고 구분하지? — NestJS와의 결정적 차이

지금까지 여섯 입구를 하나씩 봤습니다. 그런데 가장 헷갈리는 지점은 따로 있죠 — "그래서 FastAPI는 뭘 보고 구분하는 거야?" NestJS는 모든 파라미터에 데코레이터로 출처를 못 박지만, FastAPI는 규칙으로 구분되는 Path·Query·Body에는 아무 표시도 붙이지 않고, 규칙만으로는 구분이 안 되는 Header·Cookie·Form에만 표시를 붙입니다.

NestJS — 전부 데코레이터로 표시
@Patch(':id')
update(
  @Param('id') id: number,
  @Query('notify') notify: boolean,
  @Body() dto: UpdateTodoDto,
) { ... }
FastAPI — 아무 표시 없음
@app.patch("/todos/{id}")
def update(id: int, notify: bool, dto: UpdateTodoDto):
    ...

세 파라미터 앞에 아무 표시도 없지만, FastAPI는 딱 3가지 신호만으로 정확히 구분합니다.

신호판정위 예시
경로 {}에 같은 이름이 있다Pathid
경로에 없고, 타입이 기본형(int·str·bool…)이다Querynotify: bool
타입이 Pydantic 모델(BaseModel 상속)이다Bodydto: UpdateTodoDto

앞서 본 택배 비유로 말하면, 택배기사는 주소·메모·내용물은 생김새만으로 구분하지만 운송장 정보나 회원카드는 라벨이 붙어 있어야 알아보는 것과 같습니다. 그래서 Header·Cookie·Form에만 Header()/Cookie()/Form() 라벨을 붙이는 겁니다.

🧭

언제 무엇을 쓸까 — 결정 표

입구쓰는 경우예시필수?
Path특정 자원 식별/todos/42항상 필수
Query정렬·필터·페이지?limit=10기본값 없으면 필수, 있으면 선택 (보통 선택)
Body생성/수정 데이터JSON {title}본문 자체는 필수, 각 필드는 모델 정의에 따름
Header메타·인증 토큰AuthorizationHeader() 필수 · Header(None) 선택
Cookie세션 식별session=...Cookie() 필수 · Cookie(None) 선택
FormHTML 폼·파일로그인 폼Form() 필수 · Form(None) 선택
GET에 Body 넣지 않기. 조회용 GET 요청에 본문(Body)을 싣는 건 피하세요. 클라이언트와 서버 사이에서 요청을 전달하거나 응답을 저장해 두는 중간 장비(프록시·캐시)가 "GET에는 본문이 없다"고 가정하고 본문을 버리는 일이 많고, REST 관례에도 어긋납니다. 조회 조건은 Query로 보내는 게 정석입니다.

셀프 체크

Q FastAPI는 매개변수가 Path/Query/Body 중 무엇인지 어떻게 구분하나요?

경로의 {}와 이름이 같으면 Path, 아니면서 기본형 타입이면 Query, Pydantic 모델이면 Body입니다. 이 셋은 규칙으로 구분되니 표시가 없고, 나머지 Header·Cookie·Form만 Header() 같은 표시를 붙입니다.

Q 검색어를 받는 /search는 Query, Body 중 무엇이 맞나요?

일반적으로 GET /search?q=...처럼 Query를 씁니다. 조회는 같은 URL로 몇 번을 불러도 결과가 같아야 하고 주소를 그대로 공유·저장할 수 있어야 하므로 GET + Query가 정석입니다. 다만 검색 조건이 매우 복잡하면(중첩 필터 등) 실무에서 예외적으로 POST + Body를 쓰기도 합니다.

Q limit: int = 10과 limit: int의 차이는?

앞은 기본값 10이 있어 생략 가능한 선택 쿼리, 뒤는 기본값이 없어 반드시 보내야 하는 필수 쿼리입니다. 빠뜨리면 422(검증 실패)가 납니다.
