예외 처리 — HTTPException으로 정중하게 거절하기

좋은 API는 잘못된 요청에도 친절하고 일관된 에러를 돌려줍니다. 서버가 그냥 터져 500을 뱉는 것과, "42번 할 일은 없습니다(404)"라고 말해주는 것의 차이입니다.

한 줄 요약. 처리할 수 없는 요청을 만나면 raise HTTPException(status_code, detail)로 즉시 멈추고 의미 있는 에러를 돌려준다. 그러면 FastAPI가 {"detail": ...} JSON으로 깔끔히 응답한다.

학습 목표

  • 왜 예외를 명시적으로 처리해야 하는지 이해한다
  • HTTPException으로 404·400 등을 발생시킨다
  • FastAPI의 기본 에러 응답 형태를 안다
🤔

왜 예외 처리가 중요한가

조회한 자원이 없거나, 권한이 없거나, 비즈니스 규칙에 어긋나는 요청(예: 이미 완료된 할 일을 또 완료하기)은 늘 들어옵니다. 이때 코드를 그냥 진행시키면 어떻게 될까요?

python
@app.get("/todos/{id}")
def read_todo(id: int):
    return todos.get(id)["title"]   # id가 없으면 .get()이 None → None["title"]에서 TypeError
                                    # → FastAPI는 500 Internal Server Error를 돌려준다

서버 로그에는 TypeError가 찍히지만, 클라이언트가 받는 건 "서버가 고장났다"는 500뿐입니다. "99번 할 일이 없다"는 사실은 아무도 모릅니다.

비유 — 재료가 떨어진 식당. 주문한 메뉴의 재료가 없을 때, 좋은 식당은 "죄송합니다, 그 메뉴는 품절입니다"라고 정중히 안내합니다(404·400). 나쁜 식당은 아무 말 없이 주방에 불이 나죠(500). HTTPException은 "정중한 거절"을 코드로 표현하는 방법입니다.
🛑

HTTPException — 멈추고 에러 돌려주기

가장 흔한 패턴: 자원을 못 찾으면 404를 발생시킵니다.

python
from fastapi import FastAPI, HTTPException, status

app = FastAPI()
todos = {1: {"title": "장보기", "done": False}}

@app.get("/todos/{id}")
def read_todo(id: int):
    if id not in todos:
        raise HTTPException(
            status_code=status.HTTP_404_NOT_FOUND,
            detail=f"id={id} 할 일을 찾을 수 없습니다",
        )
    return todos[id]

존재하지 않는 /todos/99를 요청하면 이런 응답이 돌아갑니다:

bash
# HTTP/1.1 404 Not Found
{
  "detail": "id=99 할 일을 찾을 수 없습니다"
}
return이 아니라 raise. HTTPException은 반환하는 게 아니라 던집니다(raise). 던지는 순간 함수 실행이 그 자리에서 멈추고 그 아래 코드는 돌지 않으며, FastAPI가 예외를 받아 에러 응답으로 바꿔 보냅니다. 덕분에 "없으면 404 던지고 끝, 있으면 정상 처리"라는 조기 종료 흐름이 만들어집니다.

404는 "자원이 없다"일 때 쓰고, 자원은 있지만 지금 상태에서는 할 수 없는 요청이면 400을 던집니다. 같은 HTTPException에 코드와 메시지만 바꾸면 됩니다:

python
@app.post("/todos/{id}/complete")
def complete_todo(id: int):
    todo = todos.get(id)
    if todo is None:
        raise HTTPException(status_code=404, detail=f"id={id} 할 일을 찾을 수 없습니다")
    if todo["done"]:
        raise HTTPException(status_code=400, detail="이미 완료된 할 일입니다")  # 규칙 위반
    todo["done"] = True
    return todo

HTTPException에는 headers= 인자도 있어서 에러 응답에 헤더를 함께 실을 수 있습니다. 예를 들어 401(인증 필요) 응답에는 "어떤 방식으로 인증하라"는 안내인 WWW-Authenticate 헤더를 같이 보내는 게 관례라, headers={"WWW-Authenticate": "Bearer"}처럼 씁니다. 이건 Week 8 인증에서 실제로 사용합니다.

NestJS와 비교

NestJS — 예외 클래스
import { NotFoundException }
  from '@nestjs/common';

if (!todo) {
  throw new NotFoundException(
    `id=${id} 없음`
  );
}

상태별 예외 클래스(BadRequestException, ForbiddenException …)가 준비돼 있음.

FastAPI — 하나로 통일
if id not in todos:
    raise HTTPException(
        404, f"id={id} 없음"
    )

HTTPException 하나에 status_code만 바꿔 끼운다. 위처럼 위치 인자로 줄여 써도 status_code=404, detail=...과 같다.

🤖

검증 에러(422)는 자동

타입·필수 검증 실패는 직접 raise 하지 않아도 FastAPI가 함수 본문을 실행하기 전에 자동으로 422를 만들어줍니다. /todos/abc를 요청하면 이런 응답이 옵니다:

bash
{
  "detail": [
    {
      "type": "int_parsing",
      "loc": ["path", "id"],
      "msg": "Input should be a valid integer",
      "input": "abc"
    }
  ]
}

detail이 배열인 이유는 틀린 곳이 여러 개일 수 있어서입니다. 항목마다 loc은 어디서 났는지(["path", "id"] = Path 파라미터 id), type은 어떤 종류의 실패인지, msg는 사람이 읽을 설명, input은 실제로 들어온 값입니다.

다음 단계 미리보기. 지금은 라우트마다 raise를 쓰지만, 같은 에러 모양을 앱 전역에서 일관되게 만들고 싶을 때가 옵니다. 그건 Week 6의 커스텀 Exception Handler에서 다룹니다 — NestJS의 ExceptionFilter에 대응합니다.
에러 메시지에 민감 정보 금지. detail에 DB 쿼리문, 내부 경로, 스택 트레이스 같은 걸 노출하지 마세요. 공격자에게 힌트를 줍니다. 사용자에겐 "무엇이 잘못됐는지"만 알려주고, 자세한 원인은 서버 로그에 남기세요.
✅

셀프 체크

Q HTTPException은 return인가요 raise인가요? 왜 중요한가요?

raise입니다. 예외를 던지는 건 함수를 그 자리에서 끝내는 것이라, 잘못된 요청이 아래 정상 처리 코드까지 흘러가지 못하게 막아 줍니다.

Q 검증 실패(422)와 직접 던지는 404의 차이는?

422는 요청 데이터의 타입·필수 검증 실패로 FastAPI가 자동 생성합니다(함수 본문 실행 전). 404는 "형식은 맞지만 해당 자원이 없다"처럼 비즈니스 상황이라 개발자가 직접 raise HTTPException(404) 해야 합니다.

Q 기본 에러 응답의 JSON 구조는?

{"detail": ...}입니다. detail에는 문자열(HTTPException) 또는 검증 에러 배열(422)이 담깁니다.

Week 2 마무리. 요청의 입구 → 메서드·상태 코드 → 예외 처리까지, 이제 HTTP를 제대로 다루는 손을 갖췄습니다. 다음 주는 검증의 핵심 Pydantic과 응답 설계(response_model)로 들어갑니다 — NestJS DTO·class-validator가 어떻게 한 곳으로 합쳐지는지 보게 됩니다.
