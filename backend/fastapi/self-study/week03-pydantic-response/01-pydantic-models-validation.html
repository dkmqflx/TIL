Pydantic 모델 & 검증 — FastAPI를 떠받치는 엔진

NestJS의 DTO + class-validator가 하던 일을, FastAPI에서는 Pydantic 모델 하나가 통째로 합니다. 선언과 검증이 한 곳에서 일어나죠.

한 줄 요약. Pydantic 모델은 요청 데이터의 검사기다. 타입이 맞는지, 길이·범위 규칙을 지키는지 검사해서 통과하면 파이썬 객체로 바꿔 주고(이걸 파싱이라 부른다), 틀리면 422로 돌려보낸다. 클래스에 타입만 적으면 이 검사기가 공짜로 생긴다.

학습 목표

  • BaseModel로 데이터 모델을 정의하고 자동 검증을 받는다
  • Field로 세부 제약(길이·범위·기본값)을 건다
  • 중첩 모델과 커스텀 validator를 작성한다
  • model_dump/model_validate로 직렬화·역직렬화한다
🔍

Pydantic이란 — 타입 힌트로 하는 검증

Pydantic은 "타입 힌트를 읽어 실제로 데이터를 검증·변환"해주는 라이브러리입니다. Week 1에서 "타입 힌트는 런타임(프로그램이 실제로 실행되는 시점)에 살아남는다"고 했죠? Pydantic이 바로 그 힌트를 런타임에 읽어 일하는 주인공입니다.

비유 — 공항 입국 심사대. 해외에서 들어온 승객(요청 JSON)은 입국 심사대(Pydantic 모델)를 통과해야 합니다. 여권 형식이 맞는지(타입), 비자 기간이 유효한지(제약)를 검사해서, 통과하면 입국 도장(파싱된 파이썬 객체)을 찍고, 문제가 있으면 정중히 돌려보냅니다(422). 심사대 덕분에 공항 안 — 즉 "할 일을 저장한다"처럼 실제 서비스 동작을 하는 코드(비즈니스 로직) — 에는 늘 "검증된 데이터"만 돌아다닙니다.
📦

BaseModel 기초

BaseModel을 상속하고 필드에 타입 힌트를 적으면 끝입니다. NestJS DTO와 나란히 보죠.

NestJS — DTO + 데코레이터
import { IsString, IsBoolean }
  from 'class-validator';

class CreateTodoDto {
  @IsString()
  title: string;

  @IsBoolean()
  done: boolean;
}
FastAPI — Pydantic
from pydantic import BaseModel

class CreateTodo(BaseModel):
    title: str
    done: bool = False

NestJS는 타입 위에 @IsString() 같은 데코레이터를 일일이 붙이지만, Pydantic은 타입 힌트 자체가 곧 검증 규칙입니다. title: str 한 줄이 "문자열이어야 함"을 이미 강제합니다.

⚙️

Field — 세부 제약 걸기

"문자열인데 1~50자", "0보다 큰 정수" 같은 세부 규칙은 Field로 겁니다. NestJS의 @MinLength(1), @Max(...)에 대응합니다.

python
from pydantic import BaseModel, Field

class CreateTodo(BaseModel):
    title: str = Field(min_length=1, max_length=50)
    priority: int = Field(default=1, ge=1, le=5)   # 1 이상 5 이하
    done: bool = False
Field 옵션의미NestJS 대응
min_length / max_length문자열 길이@MinLength / @MaxLength
gt / ge초과 / 이상@Min
lt / le미만 / 이하@Max
default기본값DTO 기본값
pattern정규식(문자열이 정해진 형식에 맞는지 검사하는 패턴, 예: 이메일 모양)@Matches
Field도 Annotated로 쓸 수 있다. Week 2에서 배운 Annotated 기억하시죠? Field도 title: Annotated[str, Field(min_length=1)]처럼 쓸 수 있습니다. 이 스타일의 장점은 재사용입니다 — Title = Annotated[str, Field(min_length=1, max_length=50)]처럼 이름을 붙여 두면, CreateTodo·UpdateTodo 등 여러 모델에서 title: Title 한 줄로 같은 제약을 공유할 수 있습니다.
🪆

중첩 모델 — 모델 안의 모델

실무 데이터는 평평하지 않습니다. "할 일에 작성자 정보가 들어 있다"처럼 객체 안에 객체가 옵니다. Pydantic 모델을 필드 타입으로 그냥 쓰면 됩니다.

python
class Author(BaseModel):
    name: str
    email: str

class Todo(BaseModel):
    title: str
    author: Author              # 중첩!
    tags: list[str] = []     # 리스트 필드

들어온 JSON의 author도 자동으로 Author 규칙으로 검증됩니다. 중첩 깊이에 상관없이 전부 검사되죠.

중첩된 author도 자동으로 Author 모델 규칙에 따라 검증된다.

tags: list[str] = [] — 모델 안에서는 안전, 일반 함수에서는 함정

핵심은 딱 하나입니다. 파이썬은 함수의 기본값을 "함수를 정의할 때 한 번만" 만들고, 호출할 때마다 새로 만들지 않습니다.

비유 — 카운터에 놓인 공용 메모장. 카페를 하나 연다고 생각해 보세요. 가게를 오픈하는 순간(= def가 실행되는 순간) 카운터에 빈 메모장을 한 권 올려두고 규칙을 정합니다. "손님이 자기 메모장을 안 가져오면 카운터 메모장에 적으세요." 첫 손님이 "사과"라고 적고 갑니다. 두 번째 손님이 와서 자기 메모장이 없으니 카운터 메모장을 펼치는데… 이미 "사과"가 적혀 있죠. 메모장은 새로 갈리지 않았으니까요. 거기에 "바나나"를 덧붙입니다. 이게 바로 그 유명한 버그입니다.
python
def add_tag(tag, tags=[]):   # 이 []는 def가 실행될 때 딱 한 권 만들어짐
    tags.append(tag)
    return tags

print(add_tag("사과"))    # ['사과']
print(add_tag("바나나"))  # ['사과', '바나나']  ← 바나나만 있어야 하는데?

a = add_tag("사과")
b = add_tag("바나나")
print(a is b)             # True — 두 호출이 완전히 같은 리스트 하나를 돌려줌

고치는 법은 "메모장 없으면 새로 한 권 드릴게요"입니다. None은 "아무것도 안 받았다"는 표시일 뿐 내용을 적을 수 없는 값이라 기본값으로 써도 안전하고, 함수 안에서 새 리스트를 만들면 호출마다 새 메모장이 생깁니다. (list[str] | None의 |는 "둘 중 하나"라는 뜻입니다.)

python
def add_tag(tag, tags: list[str] | None = None):
    if tags is None:
        tags = []          # 호출할 때마다 실행되므로 매번 새 리스트
    tags.append(tag)
    return tags

print(add_tag("사과"))    # ['사과']
print(add_tag("바나나"))  # ['바나나']  ← 이제 정상

참고로 count=0이나 name="" 같은 숫자·문자열 기본값은 이 함정이 없습니다. 숫자나 문자열은 "내용을 고칠 수 없는" 값이라 여러 호출이 공유해도 서로 망가뜨릴 수가 없거든요. 문제는 append처럼 제자리에서 내용이 바뀌는 리스트·딕셔너리일 때만 생깁니다.

그런데 Pydantic 모델은 왜 괜찮을까요? 가게 운영 방식이 다릅니다. 카운터의 메모장은 견본일 뿐이고, 손님(인스턴스)이 올 때마다 견본을 복사해서 새 메모장을 건네줍니다. 그래서 = []라고 써도 인스턴스끼리 섞이지 않습니다.

python
from pydantic import BaseModel

class Post(BaseModel):
    tags: list[str] = []      # 견본. 인스턴스마다 복사됨

a = Post()
b = Post()
a.tags.append("사과")

print(a.tags)             # ['사과']
print(b.tags)             # []     ← b는 깨끗한 새 리스트
print(a.tags is b.tags)   # False — 서로 다른 리스트
한 줄 정리. 일반 함수의 = []는 "한 권을 모두가 돌려 쓰는 것"이고, Pydantic 필드의 = []는 "견본을 복사해서 한 권씩 나눠주는 것"입니다. 그래서 함수에서는 None + 안에서 새로 만들기가 정석이고, Pydantic 모델에서는 = []를 그대로 써도 됩니다.
🛠️

커스텀 validator — 규칙을 직접 쓰기

"비밀번호는 숫자를 포함해야 한다"처럼 타입이나 길이만으로는 표현할 수 없는, 우리 서비스만의 규칙(비즈니스 규칙)은 @field_validator로 직접 작성합니다.

python
from pydantic import BaseModel, field_validator

class SignUp(BaseModel):
    username: str
    password: str

    @field_validator("password")
    @classmethod                       # ← 인스턴스(self)가 아니라 클래스(cls)를 받는 메서드
    def check_password(cls, v: str) -> str:
        if not any(c.isdigit() for c in v):
            raise ValueError("비밀번호에 숫자가 1개 이상 필요합니다")
        return v

낯선 부분은 함수 위에 쌓인 데코레이터 두 개와 인자 (cls, v)일 겁니다. 하나씩 풀어 보죠. @field_validator("password")는 "password 필드를 검사할 땐 이 함수를 실행해줘"라고 Pydantic에 등록하는 역할입니다. 그러면 Pydantic은 SignUp(username=..., password="abc123")처럼 객체를 만들 때 사용자가 입력한 password 값 그 자체("abc123")를 두 번째 인자로 넘겨줍니다 — 그게 v입니다(value의 줄임말인 관례적 이름이라 다른 이름으로 바꿔도 됩니다).

그럼 첫 번째 인자가 왜 self가 아니라 cls일까요? 보통 클래스 안의 메서드는 이미 만들어진 인스턴스(self)를 받습니다. 그런데 검증이 실행되는 시점은 인스턴스가 완성되기 전입니다 — 입력값이 검사를 통과해야 비로소 회원 객체가 생기니까요. 아직 없는 것을 받을 수는 없으니, 대신 클래스 자체(cls, 즉 SignUp이라는 설계도)를 받는 메서드로 만들어야 하고, 그렇게 만들어 주는 게 @classmethod입니다.

비유 — 개인 신상 확인 vs 규정집 확인. self를 쓰는 일반 메서드는 "이 사람(인스턴스)의 정보를 보고 판단"하는 것이고, @classmethod는 "회사 규정집(클래스)만 보고 판단"하는 것입니다. 비밀번호 검증은 아직 회원이 만들어지기 전, 제출된 서류 한 장(v)이 규정집에 맞는지만 보면 되니 후자입니다.

데코레이터 순서도 정해져 있습니다 — @field_validator가 위, @classmethod가 아래. 데코레이터는 함수에 가까운 아래쪽부터 적용되므로, 먼저 @classmethod가 함수를 "클래스를 받는 메서드"로 바꾸고, 그 결과를 @field_validator가 검증기로 등록하는 순서입니다. 순서를 뒤집으면 Pydantic이 검증기를 알아보지 못해 에러 없이 조용히 무시되니(검증이 안 되는데 티가 안 납니다) 꼭 이 순서로 쓰세요. 검증에 실패하면 ValueError를 던지고, FastAPI가 이를 자동으로 422 응답으로 바꿔줍니다. NestJS의 커스텀 @Validate 데코레이터와 같은 역할입니다.

return v까지가 한 세트. 검사를 통과한 값은 return v로 돌려줘야(필요하면 가공해서) 그 값이 password 필드에 저장됩니다. return이 없으면 파이썬 함수는 None을 반환하고, Pydantic은 그 반환값을 그대로 필드 값으로 채택하므로 검증은 통과했는데 password가 None이 되는 이상한 버그가 생깁니다.
🔄

직렬화 — 모델 ↔ dict/JSON

직렬화(serialization)는 파이썬 안의 모델 객체를 네트워크로 보내거나 저장할 수 있는 dict/JSON 형태로 바꾸는 것이고, 역직렬화는 그 반대 — 밖에서 들어온 dict/JSON을 다시 모델로 되살리는 것입니다. 그러니까 먼저 "모델·dict·JSON"이 각각 뭔지부터 잡아야 합니다. 같은 데이터(회원 한 명의 정보)가 상황에 따라 세 가지 모습으로 존재하는데, 담긴 내용은 똑같고 겉모습(형식)만 다릅니다.

모습정체실제 생김새
모델
(Pydantic 객체)		파이썬이 다루는 검증된 객체. 점(.)으로 필드에 접근하고, 자동완성·타입 검사가 된다.user.username
user.password
dict
(딕셔너리)		파이썬 기본 자료형인 키-값 묶음. 대괄호([])로 값을 꺼낸다. 아직 파이썬 메모리 안에 있는 데이터.{"username": "민수",
 "password": "abc123"}
JSON
(문자열)		dict를 글자(문자열)로 납작하게 편 것. 네트워크로 보내거나 파일로 저장할 수 있는 형태. 사람이 보면 dict와 비슷하지만 따옴표로 감싼 한 덩어리의 텍스트다.'{"username":"민수",
"password":"abc123"}'
비유 — 같은 사람의 세 가지 모습. 모델은 내 앞에 서 있는 실제 사람입니다 — 말을 걸고(메서드 호출) 팔을 잡을(.필드) 수 있죠. dict는 그 사람의 신상 정보를 항목별로 적은 메모지입니다 — 칸이 나뉘어 있어 바로 꺼내 쓰기 좋지만, 아직 내 책상 위(파이썬 메모리)에만 있습니다. JSON은 그 메모지를 봉투에 넣어 부칠 수 있게 만든 편지입니다 — 글자로만 이뤄져 있어 우편(네트워크)으로 멀리 보낼 수 있습니다. 받는 쪽은 편지(JSON)를 열어 다시 메모지(dict)로, 필요하면 사람(모델)으로 되살립니다 — 이 "되살리기"가 역직렬화입니다.

아래 메서드들이 이 세 모습 사이를 오가는 변환기입니다. 이름의 규칙은 validate = 밖에서 들어온 데이터를 검증하며 모델로, dump = 모델을 밖으로 쏟아내기입니다.

메서드방향용도
model_validate(data)dict → 모델데이터를 검증하며 객체로
model_dump()모델 → dict저장·가공용 파이썬 dict
model_dump_json()모델 → JSON 문자열네트워크 전송용
python
raw = {"username": "민수", "password": "abc123"}   # ① 밖에서 들어온 dict

user = SignUp.model_validate(raw)   # ② dict → 모델 (검증까지 통과) = 역직렬화
user.username                       #   → "민수"

user.model_dump()                   # ③ 모델 → dict  {'username': '민수', ...}   = 직렬화
user.model_dump_json()              # ④ 모델 → JSON  '{"username":"민수",...}'

SignUp(**raw)                       # ②와 같은 일 — 생성자로 만들어도 똑같이 검증한다

마지막 줄처럼 SignUp(**raw)(dict를 풀어서 넘기기)나 SignUp(username="민수", password="abc123")처럼 생성자로 직접 만들어도 같은 검증을 거칩니다. 앞 섹션의 validator 예시에서 생성자 방식을 쓴 것도 그래서입니다. model_validate는 "dict를 통째로 넘기는 입구"가 하나 더 있는 것뿐이라, 둘 중 편한 쪽을 쓰면 됩니다.

Pydantic v1 → v2 메서드 이름. 예전 자료엔 .dict(), .parse_obj()가 나오는데, 이건 v1 표기입니다. v2에서는 .model_dump(), .model_validate()로 바뀌었습니다. FastAPI 최신 버전은 v2를 쓰니 새 이름을 익히세요.
✅

셀프 체크

Q NestJS의 DTO+class-validator와 Pydantic의 차이를 한마디로?

NestJS는 타입(DTO)과 검증 데코레이터를 따로 붙이지만, Pydantic은 타입 힌트 자체가 검증 규칙이라 한 클래스로 끝납니다.

Q 커스텀 validator에서 검증 실패를 어떻게 알리나요?

@field_validator 함수 안에서 ValueError를 raise하면 됩니다. FastAPI가 이를 422 응답으로 자동 변환하고, 어떤 필드가 왜 실패했는지 detail에 담아줍니다.

Q @classmethod를 @field_validator 위에 쓰면 어떻게 되나요?

검증기로 등록되지 않아 에러 없이 조용히 무시됩니다. 아래쪽 데코레이터부터 적용되므로 @field_validator가 위, @classmethod가 아래여야 합니다.

Q .dict()가 동작 안 한다고 나옵니다. 왜죠?

v1 시절 이름이라서요. v2에서는 .model_dump()(그리고 .parse_obj() 대신 .model_validate())를 씁니다.
