Pydantic 모델 & 검증 — FastAPI를 떠받치는 엔진

NestJS의 DTO + class-validator가 하던 일을, FastAPI에서는 Pydantic 모델 하나가 통째로 합니다. 선언과 검증이 한 곳에서 일어나죠.

한 줄 요약. Pydantic 모델은 요청 데이터의 입국 심사대다. 타입이 맞는지, 길이·범위 규칙을 지키는지 검사해서 통과시키거나(파싱) 돌려보낸다(422). 클래스에 타입만 적으면 검사기가 공짜로 생긴다.

학습 목표

  • BaseModel로 데이터 모델을 정의하고 자동 검증을 받는다
  • Field로 세부 제약(길이·범위·기본값)을 건다
  • 중첩 모델과 커스텀 validator를 작성한다
  • model_dump/model_validate로 직렬화·역직렬화한다
🔍

Pydantic이란 — 타입 힌트로 하는 검증

Pydantic은 "타입 힌트를 읽어 실제로 데이터를 검증·변환"해주는 라이브러리입니다. Week 1에서 "타입 힌트는 런타임에 살아남는다"고 했죠? Pydantic이 바로 그 힌트를 런타임에 읽어 일하는 주인공입니다.

비유 — 공항 입국 심사대. 해외에서 들어온 승객(요청 JSON)은 입국 심사대(Pydantic 모델)를 통과해야 합니다. 여권 형식이 맞는지(타입), 비자 기간이 유효한지(제약)를 검사해서, 통과하면 입국 도장(파싱된 객체)을 찍고, 문제가 있으면 정중히 돌려보냅니다(422). 심사대 덕분에 공항 안(=당신의 비즈니스 로직)은 늘 "검증된 데이터"만 돌아다닙니다.
📦

BaseModel 기초

BaseModel을 상속하고 필드에 타입 힌트를 적으면 끝입니다. NestJS DTO와 나란히 보죠.

NestJS — DTO + 데코레이터
import { IsString, IsBoolean }
  from 'class-validator';

class CreateTodoDto {
  @IsString()
  title: string;

  @IsBoolean()
  done: boolean;
}
FastAPI — Pydantic
from pydantic import BaseModel

class CreateTodo(BaseModel):
    title: str
    done: bool = False

NestJS는 타입 위에 @IsString() 같은 데코레이터를 일일이 붙이지만, Pydantic은 타입 힌트 자체가 곧 검증 규칙입니다. title: str 한 줄이 "문자열이어야 함"을 이미 강제합니다.

⚙️

Field — 세부 제약 걸기

"문자열인데 1~50자", "0보다 큰 정수" 같은 세부 규칙은 Field로 겁니다. NestJS의 @MinLength(1), @Max(...)에 대응합니다.

python
from pydantic import BaseModel, Field

class CreateTodo(BaseModel):
    title: str = Field(min_length=1, max_length=50)
    priority: int = Field(default=1, ge=1, le=5)   # 1 이상 5 이하
    done: bool = False
Field 옵션의미NestJS 대응
min_length / max_length문자열 길이@MinLength / @MaxLength
gt / ge초과 / 이상@Min
lt / le미만 / 이하@Max
default기본값DTO 기본값
pattern정규식@Matches
Field도 Annotated로 쓸 수 있다. Week 2에서 배운 Annotated 기억하시죠? Field도 title: Annotated[str, Field(min_length=1)]처럼 쓸 수 있고, 이게 모델 간 재사용에 유리한 최신 스타일입니다.
🪆

중첩 모델 — 모델 안의 모델

실무 데이터는 평평하지 않습니다. "할 일에 작성자 정보가 들어 있다"처럼 객체 안에 객체가 옵니다. Pydantic 모델을 필드 타입으로 그냥 쓰면 됩니다.

python
class Author(BaseModel):
    name: str
    email: str

class Todo(BaseModel):
    title: str
    author: Author              # 중첩!
    tags: list[str] = []     # 리스트 필드

들어온 JSON의 author도 자동으로 Author 규칙으로 검증됩니다. 중첩 깊이에 상관없이 전부 검사되죠.

중첩된 author도 자동으로 Author 모델 규칙에 따라 검증된다.
🛠️

커스텀 validator — 규칙을 직접 쓰기

"비밀번호는 숫자를 포함해야 한다" 같은 비즈니스 규칙은 @field_validator로 직접 작성합니다.

python
from pydantic import BaseModel, field_validator

class SignUp(BaseModel):
    username: str
    password: str

    @field_validator("password")
    @classmethod                       # ← 인스턴스(self)가 아니라 클래스(cls)를 받는 메서드
    def check_password(cls, v: str) -> str:
        if not any(c.isdigit() for c in v):
            raise ValueError("비밀번호에 숫자가 1개 이상 필요합니다")
        return v

@classmethod는 뭘까요? 보통 클래스 안의 메서드는 첫 번째 인자로 만들어진 인스턴스 자신(self)을 받습니다. 그런데 @classmethod를 붙이면 인스턴스 대신 클래스 자체(cls)를 첫 번째 인자로 받게 됩니다. 위 코드에서 check_password(cls, v)의 cls가 바로 그겁니다 — SignUp이라는 "설계도" 자체를 가리키지, 아직 만들어진 회원 한 명(인스턴스)을 가리키는 게 아닙니다.

그럼 두 번째 인자 v는 뭘까요? 바로 위에 붙은 @field_validator("password")가 "password 필드를 검사할 땐 이 함수를 실행해줘"라고 Pydantic에 등록해두는 역할을 합니다. 그러면 Pydantic은 SignUp(username=..., password="abc123")처럼 객체를 만들 때, 사용자가 입력한 password 값 그 자체("abc123")를 cls 다음 인자로 자동으로 넘겨줍니다 — 그게 v입니다. v는 value의 줄임말일 뿐인 관례적인 이름이라 password처럼 다른 이름으로 바꿔도 동일하게 동작합니다. 함수 안에서는 이 v를 검사하고, 문제가 없으면 return v로 그 값을 그대로(혹은 가공해서) 돌려줘야 최종적으로 password 필드에 저장됩니다.

비유 — 개인 신상 확인 vs 규정집 확인. self를 쓰는 일반 메서드는 "이 사람(인스턴스)의 정보를 보고 판단"하는 것이고, @classmethod는 "회사 규정집(클래스)만 보고 판단"하는 것에 가깝습니다. 비밀번호 검증은 아직 완성된 회원 객체가 없어도 — 즉 제출된 서류 한 장(v, 입력된 비밀번호 문자열)이 규칙에 맞는지만 보면 되므로, 특정 인스턴스가 아니라 클래스 차원의 규칙 검사인 셈입니다.

Pydantic이 @field_validator 검증을 실행하는 시점은 아직 유효한 인스턴스가 만들어지기 전(입력값을 검사해서 통과해야 비로소 객체가 완성되는 단계)입니다. 그래서 self를 받을 수 없고, @field_validator 바로 아래에 @classmethod를 붙이는 게 정해진 관례입니다. ValueError를 던지면 FastAPI가 자동으로 422 검증 에러로 바꿔줍니다. NestJS의 커스텀 @Validate 데코레이터와 같은 역할입니다.

return v를 빠뜨리면? 함수 끝에 return v가 없으면 파이썬 함수는 기본적으로 None을 반환합니다. Pydantic은 이 반환값을 그대로 필드 값으로 채택하므로, return v를 깜빡하면 검증은 통과했는데 password가 None으로 저장되는 이상한 버그가 생깁니다. "검사만 하고 끝"이 아니라 "검사하고 값을 돌려준다"까지가 한 세트라는 걸 기억하세요.
🔄

직렬화 — 모델 ↔ dict/JSON

표를 보기 전에, 여기 나오는 세 단어부터 확실히 잡고 가죠. 같은 데이터(회원 한 명의 정보)가 상황에 따라 세 가지 모습으로 존재합니다. 셋은 담긴 내용은 똑같고 겉모습(형식)만 다릅니다.

모습정체실제 생김새
모델
(Pydantic 객체)		파이썬이 다루는 검증된 객체. 점(.)으로 필드에 접근하고, 자동완성·타입 검사가 된다.user.username
user.password
dict
(딕셔너리)		파이썬 기본 자료형인 키-값 묶음. 대괄호([])로 값을 꺼낸다. 아직 파이썬 메모리 안에 있는 데이터.{"username": "민수",
 "password": "abc123"}
JSON
(문자열)		dict를 글자(문자열)로 납작하게 편 것. 네트워크로 보내거나 파일로 저장할 수 있는 형태. 사람이 보면 dict와 비슷하지만 따옴표로 감싼 한 덩어리의 텍스트다.'{"username":"민수",
"password":"abc123"}'
비유 — 같은 사람의 세 가지 모습. 모델은 내 앞에 서 있는 실제 사람입니다 — 말을 걸고(메서드 호출) 팔을 잡을(.필드) 수 있죠. dict는 그 사람의 신상 정보를 항목별로 적은 메모지입니다 — 이름·나이 칸이 나뉘어 있어 바로 꺼내 쓰기 좋지만, 아직 내 책상 위(파이썬 메모리)에만 있습니다. JSON은 그 메모지를 봉투에 넣어 부칠 수 있게 만든 편지입니다 — 글자로만 이뤄져 있어 우편(네트워크)으로 멀리 보낼 수 있습니다. 받는 쪽은 편지(JSON)를 열어 다시 메모지(dict)로, 필요하면 사람(모델)으로 되살립니다.

그래서 왜 서로 변환하냐면 — 파이썬 코드 안에서 다룰 땐 편리한 모델/dict가 좋지만, 그 데이터를 브라우저나 다른 서버로 보내는 순간엔 글자 형태인 JSON이어야만 하기 때문입니다. 아래 메서드들이 이 세 모습 사이를 오가는 변환기입니다. (이름의 규칙: validate = 밖에서 들어온 데이터를 검증하며 모델로, dump = 모델을 밖으로 쏟아내기.)

메서드방향용도
model_validate(data)dict → 모델데이터를 검증하며 객체로
model_dump()모델 → dict저장·가공용 파이썬 dict
model_dump_json()모델 → JSON 문자열네트워크 전송용
python
raw = {"username": "민수", "password": "abc123"}   # ① 밖에서 들어온 dict

user = SignUp.model_validate(raw)   # ② dict → 모델 (검증까지 통과)
user.username                       #   → "민수"   (점으로 접근 = 모델이라 가능)

user.model_dump()                   # ③ 모델 → dict  {'username': '민수', ...}
user.model_dump_json()              # ④ 모델 → JSON  '{"username":"민수",...}'  (글자 한 덩어리)
Pydantic v1 → v2 메서드 이름. 예전 자료엔 .dict(), .parse_obj()가 나오는데, 이건 v1 표기입니다. v2에서는 .model_dump(), .model_validate()로 바뀌었습니다. FastAPI 최신 버전은 v2를 쓰니 새 이름을 익히세요.
여기서 잠깐 — 가변 기본값(mutable default) 함정. 앞의 중첩 모델에서 tags: list[str] = []처럼 리스트를 필드 기본값으로 아무렇지 않게 썼죠? 그런데 똑같은 = []를 보통 파이썬 함수에 쓰면 악명 높은 버그가 됩니다. "모델에선 잘 됐는데 왜 함수에선 위험하다는 거지?"를 이해하려면 이 함정부터 짚어야 해서, 잠깐 순수 파이썬으로 넘어가 봅니다.

먼저 아래 함수를 보고, "이 함수를 두 번 부르면 뭐가 나올까?"를 예상해 보세요. "태그를 하나 받아서, 빈 목록에 넣고, 그 목록을 돌려주는 함수"처럼 보이죠.

python
# ❌ 이렇게 쓰면 안 됩니다
def add_tag(tag: str, tags: list[str] = []):   # tags를 안 주면 빈 목록으로 시작(할 줄 알았지만…)
    tags.append(tag)
    return tags

print(add_tag("사과"))   # 예상: ['사과']       / 실제: ['사과']        ✅
print(add_tag("바나나")) # 예상: ['바나나']     / 실제: ['사과', '바나나']  ❌ 사과가 왜 남아있지?!

두 번째 호출에서 '바나나'만 들어있어야 할 것 같은데, 지워진 줄 알았던 '사과'가 그대로 남아 있습니다. 왜 이럴까요?

핵심은 이겁니다 — tags=[]의 그 빈 목록은 함수를 부를 때마다 새로 생기는 게 아니라, 함수를 처음 정의할 때 딱 하나만 만들어집니다. 그리고 tags를 생략한 모든 호출은 그 하나뿐인 목록을 계속 돌려 씁니다. 그래서 첫 호출이 담은 '사과'가 그 목록에 남아 있고, 두 번째 호출은 그 위에 '바나나'를 얹는 겁니다.

비유 — 마트 입구의 공용 카트 하나. tags=[]는 마트가 문 열 때(=함수 정의될 때) 입구에 딱 하나 갖다 둔 카트예요. 손님이 자기 카트를 안 가져오면 다들 이 카트 하나를 씁니다. 첫 손님이 사과를 담고 비우지 않은 채 반납하면, 다음 손님은 텅 빈 카트가 아니라 사과가 든 카트를 그대로 받게 되죠. "매번 새 카트"라고 착각한 게 버그의 원인입니다.

고치는 방법은 간단합니다. 기본값을 빈 목록 대신 None으로 두고, 함수 안에서 매번 새 목록을 만드는 겁니다. 이러면 호출마다 진짜로 새 카트를 꺼내 오는 셈이라 이전 흔적이 남지 않습니다.

python
# ✅ 안전한 패턴
def add_tag(tag: str, tags: list[str] | None = None):
    if tags is None:
        tags = []          # 호출될 때마다 여기서 새 목록을 만든다 → 공유 안 됨
    tags.append(tag)
    return tags

print(add_tag("사과"))   # ['사과']
print(add_tag("바나나")) # ['바나나']   ✅ 이제 매번 깨끗하게 시작
그런데 왜 Pydantic 모델에선 tags: list[str] = []를 써도 괜찮았을까? 위 함정은 순수 파이썬 함수 얘기입니다. Pydantic은 이 문제를 알고 있어서, 모델 인스턴스를 만들 때마다 기본값을 새로 복사해 넣어줍니다 — 즉 카트를 손님마다 새로 꺼내 주는 걸 Pydantic이 알아서 해주는 거죠. 그래서 모델 필드 안에서는 안전하지만, 그 밖의 일반 함수·클래스에서는 여전히 위험합니다. "모델 안이면 [] OK, 그냥 함수면 None 패턴" 이렇게 기억하면 됩니다.
✅

Q NestJS의 DTO+class-validator와 Pydantic의 차이를 한마디로?

NestJS는 타입(DTO)과 검증 규칙(class-validator 데코레이터)을 따로 선언하지만, Pydantic은 타입 힌트 자체가 검증 규칙이 되어 한 클래스에서 선언·검증이 동시에 일어납니다. 세부 제약만 Field로 보탭니다.

Q 커스텀 validator에서 검증 실패를 어떻게 알리나요?

@field_validator 함수 안에서 ValueError(또는 AssertionError)를 raise하면 됩니다. FastAPI가 이를 422 응답으로 자동 변환하고, 어떤 필드가 왜 실패했는지 detail에 담아줍니다.

Q .dict()가 동작 안 한다고 나옵니다. 왜죠?

Pydantic v2부터 .dict()는 deprecated이고 .model_dump()로 바뀌었습니다. 마찬가지로 .parse_obj() → .model_validate()입니다. 구버전 튜토리얼을 보고 있을 가능성이 큽니다.
