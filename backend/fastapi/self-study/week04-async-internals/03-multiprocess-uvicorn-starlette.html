멀티프로세스 & 3층 구조 — Uvicorn · Starlette · FastAPI

지금까지는 직원 한 명이 요령 있게 일하는 법(비동기)을 배웠습니다. 이번엔 가게를 여러 개 여는 법(멀티프로세스), 그리고 우리 서버가 실은 세 개의 라이브러리가 층층이 쌓인 구조라는 이야기입니다.

한 줄 요약. 비동기는 한 가게 안에서 기다림을 겹쳐 처리하는 기술(동시성)이고, 멀티프로세스(--workers)는 가게를 여러 개 열어 진짜 동시에 일하게 하는 기술(병렬성)이다. 서로 다른 문제를 풀기 때문에 실무에선 둘을 같이 쓴다. 그리고 요청 한 건은 Uvicorn(접수) → Starlette(동선) → FastAPI(검수·메뉴판) 3층을 통과한다.

학습 목표

  • 코어 · 프로세스 · 스레드를 각각 한 문장으로 말하고, "프로세스는 담고, 스레드가 돌고, 코어가 실행한다"는 관계를 그린다
  • GIL이 뭔지, 그래서 한 프로세스가 왜 코어 하나만 쓰는지 설명한다
  • --workers로 워커를 늘리는 법과 개수를 정하는 감을 잡는다
  • 워커끼리 전역 변수를 공유하지 못하는 이유와 대안을 안다
  • Uvicorn·Starlette·FastAPI가 각각 무슨 일을 하는지 그린다
  • ASGI와 WSGI의 차이를 한 줄로 설명한다

먼저 단어부터 — 코어 · 프로세스 · 스레드

이번 장에는 비슷하게 생긴 단어가 셋 나옵니다. 코어, 프로세스, 스레드. 이 셋의 관계만 잡으면 나머지 이야기는 술술 풀립니다. Lesson 01에서 쓰던 카페 비유(지점·점원)를 그대로 이어서 봅시다.

단어컴퓨터에서는카페로 보면
코어 (core)CPU 안에서 실제로 계산을 하는 장치. "8코어 노트북"이면 계산 장치가 8개 들어 있다.커피를 뽑을 수 있는 커피 머신. 머신이 많으면 동시에 여러 잔을 뽑을 수 있다.
프로세스 (process)실행 중인 프로그램 한 벌. 자기만의 메모리 공간을 따로 갖는다.독립된 가게(지점). 재료 창고(메모리)를 각자 따로 갖고 있어 옆 가게 재료엔 손댈 수 없다.
스레드 (thread)프로세스 안에서 코드를 실행하는 흐름. 같은 프로세스의 스레드끼리는 메모리를 공유한다.한 가게 안의 직원. 같은 창고를 같이 쓰니 서로의 물건이 바로 보인다.

여기서 가장 헷갈리는 지점을 짚고 갑시다. "코어가 프로세스를 실행하고, 프로세스가 스레드를 실행하는 건가?" — 아닙니다. 둘의 역할은 이렇게 갈립니다.

📦
프로세스 = 담는 그릇 (실행하지 않는다)
메모리·열어 둔 파일·네트워크 연결 같은 자원을 담아 두는 울타리입니다. 그릇 자체가 코드를 실행하는 게 아니라, 안에 든 스레드가 실행하죠. 그래서 모든 프로세스는 스레드를 최소 한 개(메인 스레드) 갖습니다.
🏃
스레드 = 실행 흐름 (이게 코어에 올라간다)
코어에 올라가 실제로 명령어를 처리하는 단위입니다. 즉 코어가 실행하는 건 프로세스가 아니라 스레드예요.

그래서 서로 다른 두 개의 관계를 따로 기억해야 합니다 — 포함 관계(무엇이 무엇을 담고 있나)와 실행 관계(무엇이 어디서 돌아가나).

📦 포함 관계 : 프로세스 (그릇) ⊃ 스레드 (실행 흐름) ⊃ 코루틴 (양보하는 요령)
🏃 실행 관계 : 스레드 → OS 스케줄러가 배정 → 코어 (하드웨어)

여기서 OS 스케줄러란 운영체제 안에서 "지금 어느 스레드를 어느 코어에 올릴지"를 아주 짧은 시간 단위로 정해 주는 배정 담당입니다. 카페로 말하면 — 가게 문이 열려 있다고 커피가 나오는 게 아니라, 직원이 머신 앞에 서야 커피가 나옵니다. 그림으로 보면 이렇습니다.

프로세스는 담고, 스레드가 돌고, 코어가 실행한다. 스레드가 코어보다 많으면 OS 스케줄러가 번갈아 올려 준다.
실제 숫자로 느껴 보기. 어느 맥북에서 재 보니 코어 12개 · 프로세스 643개 · 스레드 6,744개였습니다. 코어보다 수백 배 많은데도 문제없이 돌아가죠 — OS가 번갈아 올려 주기 때문입니다. 즉 코어 수는 "몇 개를 띄울 수 있냐"가 아니라 "한 순간에 몇 개가 진짜 동시에 계산되냐"를 정하는 숫자입니다. (맥은 top -l 1 -n 0 | grep Processes, 리눅스는 ps -eLf | wc -l로 확인할 수 있습니다.)
🖥️

한 프로세스는 왜 코어 하나만 쓸까 — GIL

uvicorn main:app으로 서버를 띄우면 프로세스는 딱 한 개 생깁니다. 바로 앞에서 "스레드가 여러 개면 코어 여러 개에 나눠 올라간다"고 했으니, 이 프로세스도 8코어를 다 쓸 것 같죠. 그런데 파이썬만은 예외입니다. 8코어짜리 컴퓨터에서 돌려도 한 순간에 코어 하나 몫의 계산밖에 못 합니다. 그 예외를 만드는 규칙이 GIL입니다.

GIL = 가게에 하나뿐인 "커피 머신 열쇠". 카페(프로세스)에 직원(스레드)을 세 명 뽑았는데, 가게 규칙이 "머신을 쓰려면 열쇠를 쥐어야 하고, 열쇠는 딱 하나"입니다. 직원이 셋이든 서른이든 실제로 커피를 뽑는 사람은 늘 한 명이죠. GIL(Global Interpreter Lock)이 바로 그 열쇠 — "파이썬 코드를 실행하려면 이 열쇠를 쥐어야 한다"는 자물쇠입니다. 여러 스레드가 파이썬 내부 데이터를 동시에 건드리면 값이 깨지는데, 한 명만 들여보내는 게 가장 단순한 안전장치라서 이렇게 만들어졌습니다.
열쇠를 쥔 하나만 일한다. 나머지 둘은 코드를 실행하지 못하고 순서를 기다린다.

여기서 "코어 하나만 쓴다"는 말은 내 서버가 낼 수 있는 처리량이 1코어분이라는 뜻이지, 코어 하나를 통째로 예약해 둔다는 뜻이 아닙니다. 남은 코어는 브라우저·DB 같은 다른 프로그램이 계속 쓰고 있습니다.

그럼 스레드를 여러 개 만드는 건 헛수고일까요? 아닙니다. 열쇠를 계속 쥐고 있는 건 아니기 때문입니다. 직원이 추출 버튼을 누르고 커피가 내려오길 기다리는 동안(= DB·HTTP·파일 응답을 기다리는 시간)에는 열쇠를 내려놓습니다. 그 사이 다른 직원이 열쇠를 집어 자기 커피를 걸죠. 반대로 원두를 손으로 가는 일(= CPU 계산 — 이미지 변환, 암호화, 큰 반복문)은 열쇠를 쥔 채 끝까지 해야 합니다. 이 차이가 결과를 완전히 갈라 놓습니다 — 같은 스레드 3개인데도요.

같은 스레드 3개인데 결과가 다르다. 초록(실행)은 절대 겹치지 않지만, 파랑(기다림)은 얼마든지 겹친다.

이건 파이썬만의 사정입니다. Java·Go·C++에는 이런 열쇠가 없어 스레드만 늘려도 코어를 더 씁니다. 비동기도 답이 아니고요 — 이벤트 루프는 스레드를 한 개만 쓰니 CPU 병렬과는 더 멀죠. 열쇠가 프로세스마다 하나씩이니, 코어를 더 쓰는 방법은 결국 프로세스를 늘리는 것(다음 섹션의 --workers)뿐입니다. 참고로 Python 3.13부터 GIL을 끈 실험 빌드가 나왔지만, 기본 배포판과 대부분의 라이브러리는 아직 GIL을 전제합니다.

멀티프로세스 워커 — 가게를 여러 개 열기

해법은 생각보다 단순합니다. 같은 앱을 프로세스 여러 개로 띄우고 들어오는 요청을 나눠 주면 됩니다. 이렇게 띄운 프로세스 하나하나를 워커(worker)라고 부릅니다 — 카페로 치면 지점을 여러 개 여는 것이죠.

지점마다 자기 열쇠(GIL)·자기 이벤트 루프·자기 창고(메모리)를 따로 가집니다. 열쇠가 워커 수만큼 생기니 이제야 여러 코어에서 진짜 동시에 일할 수 있습니다. (Lesson 02의 "워커 스레드"와는 이름만 같습니다. 그건 한 가게 안의 보조 직원이고, 여기서 말하는 워커는 가게 자체예요.)

bashterminal
# 운영 — 워커 4개로 띄운다
uvicorn main:app --workers 4

# 개발 — --reload (워커는 1개). --reload 와 --workers 는 함께 못 씁니다.
uvicorn main:app --reload

# 운영에서 Gunicorn에게 프로세스 관리를 맡기기도 합니다 (죽은 워커를 되살리는 등)
# pip install uvicorn-worker 가 필요합니다
gunicorn main:app -k uvicorn_worker.UvicornWorker --workers 4

"그럼 요청은 누가 4개 워커에 나눠 주나요?" 개발자가 코드를 짤 필요는 없습니다. 워커들은 같은 포트를 함께 바라보고(소켓 — 연결이 들어오는 "문"이라고 생각하면 됩니다), 새 연결이 들어오면 OS가 노는 워커에게 넘겨 줍니다. 우리가 할 일은 개수를 정해 주는 것뿐이죠.

워커를 늘리면 그만큼 여러 코어 몫을 동시에 낼 수 있다. 요청 배분은 OS와 서버가 알아서 한다.

여기서 두 축을 절대 헷갈리지 마세요. 이 표 한 장이 Week 4의 핵심입니다.

해결책해결하는 문제단위카페로 보면
비동기 (async/await)기다리는 시간을 겹쳐 처리 (동시성)코루틴 / 이벤트 루프직원 한 명이 추출을 기다리는 동안 다음 주문을 받는다
멀티프로세스 (--workers)여러 코어에서 진짜 동시에 계산 (병렬성)프로세스(워커)지점을 4개 열어 손님을 나눠 받는다

둘은 다른 문제를 푸는 도구라 경쟁 관계가 아닙니다. 실무에선 async def로 쓴 앱을 --workers 4로 띄우는 식으로 함께 쓰죠. 그렇게 띄운 서버 속은 이렇게 생겼습니다.

워커(프로세스) 안에 이벤트 루프 1개(Lesson 01)와 threadpool 스레드들(Lesson 02)이 들어 있다.
워커 개수는 몇으로 둘까? CPU 코어 수에서 시작해 실제 부하로 재 보며 조정하세요. 무작정 늘리면 안 되는 이유가 둘 있습니다 — ① 워커마다 앱 전체가 메모리에 복사되므로 메모리가 워커 수만큼 들고(시작할 때 큰 모델·데이터를 올린다면 그것도 워커 수만큼입니다), ② 코어보다 워커가 많으면 서로 번갈아 실행되며 전환 비용만 늘어 이득이 없습니다. 컨테이너에서 돌린다면 머신 전체가 아니라 그 컨테이너에 할당된 CPU가 기준입니다.
가장 흔한 사고 — 워커는 메모리를 공유하지 않는다. 워커는 독립된 가게라 재료 창고가 따로입니다. 그래서 전역 변수에 캐시·카운터·세션을 담아 두면 워커마다 값이 따로 놀아 버그가 됩니다.
pythonbad.py — 워커가 여러 개면 깨지는 코드
counter = 0          # 😱 이 변수는 워커마다 "따로" 존재한다

@app.post("/hit")
async def hit():
    global counter
    counter += 1
    return {"count": counter}

워커 4개로 띄우고 이 API를 네 번 호출하면 1, 2, 3, 4가 아니라 뒤죽박죽으로 나옵니다. 왜 그런지는 그림으로 보면 바로 납득이 됩니다.

전역 변수는 "서버에 하나"가 아니라 "워커마다 하나". 요청이 흩어지는 순간 값도 흩어진다.

해결책은 값을 모든 워커가 함께 보는 바깥 저장소에 두는 것입니다.

pythongood.py — 공유 상태는 외부 저장소로
@app.post("/hit")
async def hit():
    # Redis · DB 처럼 워커 밖에 있는 공용 창고에 저장
    count = await redis.incr("hit_count")
    return {"count": count}
같은 이유로 조심할 것 하나 더 — 앱 안의 스케줄러. APScheduler 같은 걸 앱에 넣고 워커 4개로 띄우면 같은 작업이 4번 실행됩니다(메일 4통, 정산 4번). 스케줄러는 별도 프로세스로 빼거나, 공용 저장소에 "내가 하는 중" 표시를 남겨(lock) 한 워커만 실행하게 해야 합니다.

3층 구조 — Uvicorn · Starlette · FastAPI

여기서 이야기가 바뀝니다. 우리는 "FastAPI로 서버를 만든다"고 말하지만, 요청 한 건을 처리하는 데는 사실 세 개의 라이브러리가 층을 이뤄 협력합니다. 역할이 또렷하게 나뉘어 있으니 층별로 정리해 봅시다.

층정체하는 일카페로 보면
UvicornASGI 서버HTTP 바이트를 파이썬 객체로 해석하고, 이벤트 루프를 돌린다드라이브스루 인터폰 — 밖에서 들리는 말을 주문서로 옮겨 적는다
Starlette웹 마이크로프레임워크미들웨어, 라우팅, Request/Response, WebSocket매장 동선 — 입구에서 공통 검문하고, 주문서를 담당 파트로 보낸다
FastAPIStarlette 위의 확장타입 검증(Pydantic), 의존성 주입(Depends), 자동 문서주문 검수원 — 이상한 주문은 반려하고, 필요한 재료를 미리 챙겨 준다

세 층은 양파처럼 겹쳐 있습니다. 요청은 바깥에서 안으로 한 겹씩 뚫고 들어가 맨 안쪽의 내 함수에 닿고, 응답은 그 길을 그대로 되짚어 나옵니다. 이 그림이 이 섹션의 전부입니다.

안쪽으로 갈수록 더 고수준의 일을 한다. 어느 층에서 막히면 그 아래 층은 아예 실행되지 않는다.

이 그림을 외워 두면 에러 코드만 보고도 어느 층을 고쳐야 할지 바로 찍을 수 있습니다.

마지막으로 꽤 중요한 사실 하나. FastAPI는 Starlette를 상속합니다.

pythonfastapi/applications.py (개념)
from starlette.applications import Starlette

class FastAPI(Starlette):   # ← Starlette를 그대로 상속
    # 여기에 검증 · 의존성 주입 · 자동 문서 기능을 얹는다
    ...

즉 내 FastAPI 앱은 그 자체로 Starlette 앱이기도 합니다. app.add_middleware(...), Request, WebSocket, BackgroundTasks가 원래 Starlette의 기능이고, FastAPI 공식 문서가 종종 "자세한 내용은 Starlette 문서를 보라"고 하는 이유도 이것입니다.

그럼 Starlette만 쓰면 안 되나요? 됩니다. 라우팅·미들웨어만 필요한 얇은 서버라면 그것으로 충분하죠. FastAPI를 얹는 이유는 타입만 적으면 검증·문서·의존성 주입이 자동으로 따라오기 때문입니다. 반대로 Uvicorn 없이 FastAPI만 있으면 아무 요청도 받지 못합니다 — 소켓을 열고 HTTP를 읽는 층이 없으니까요.

ASGI? WSGI? — "규격"이라는 개념

앞에서 Uvicorn을 "ASGI 서버"라고 불렀습니다. 여기서 ASGI는 프로그램이 아니라 약속(규격)입니다. 이 한 가지만 잡으면 됩니다.

규격 = 콘센트 모양. 220V 콘센트 모양이 정해져 있으니 선풍기 만드는 회사와 발전소가 서로를 몰라도 그냥 꽂으면 돌아가죠. ASGI/WSGI가 바로 그 플러그 모양입니다 — 서버(Uvicorn·Hypercorn)와 프레임워크(FastAPI·Django)가 서로를 몰라도 꽂아 쓸 수 있게 파이썬 커뮤니티가 정한 약속이에요. 그래서 uvicorn을 hypercorn으로 바꿔도 내 앱 코드는 한 줄도 안 바뀝니다.

그럼 그 "모양"이 구체적으로 뭘까요? 서버가 내 앱을 어떤 함수 모양으로 부르고, 몇 번 주고받느냐입니다. 둘을 나란히 놓으면 차이가 한눈에 보입니다.

WSGI는 한 번에 끝나는 대화, ASGI는 계속 이어지는 대화. 그래서 ASGI만 WebSocket을 표현할 수 있다.
규격특징대표 서버
WSGI동기 전용 · WebSocket 불가Gunicorn(기본), uWSGI
ASGIasync/await · WebSocket · 장기 연결 지원Uvicorn, Hypercorn

FastAPI가 비동기와 WebSocket을 쓸 수 있는 건 결국 ASGI라는 콘센트 위에 서 있기 때문이고, Flask·Django가 오래 동기였던 것도 그들이 WSGI 위에 있었기 때문입니다.

셀프 체크

Q --workers 4로 띄우면 프로세스·이벤트 루프·스레드는 각각 몇 개일까요?

프로세스 4개, 각각에 이벤트 루프 1개(메인 스레드)와 threadpool 스레드 최대 ~40개. 스레드는 총 4 × (1 + 최대 40)개이고, async def는 각 워커의 루프에서, def는 그 워커의 threadpool에서 실행됩니다.

Q GIL이 뭔가요? 스레드를 늘려도 CPU 계산이 빨라지지 않는 이유는?

GIL은 "한 순간에 파이썬 코드를 실행할 스레드는 하나뿐"이라는 자물쇠입니다. CPU 계산은 실행 내내 그 자물쇠를 쥐고 있으므로 스레드가 10개라도 결국 한 명씩 순서대로 하는 것과 같고, I/O 대기 중에는 자물쇠를 내려놓기 때문에 I/O 작업에는 스레드가 효과가 있습니다.

Q 비동기를 쓰는데도 워커를 여러 개 띄우는 이유는?

비동기는 한 프로세스 안에서 기다리는 시간을 겹쳐 쓰는 기술(동시성)이라 손이 두 개가 되지는 않습니다. 직접 계산해야 하는 일이 몰리면 그대로 밀리죠. 워커는 프로세스를 늘려 여러 코어에서 진짜 동시에 계산하게 하는 기술(병렬성)입니다. 서로 대신할 수 없는 다른 종류의 개선이라 둘을 같이 씁니다.

Q Uvicorn·Starlette·FastAPI의 역할을 한마디씩 구분하고, Uvicorn이 "ASGI 서버"라는 말의 뜻을 설명해 보세요.

Uvicorn은 소켓·HTTP 파싱·이벤트 루프 구동을 맡는 서버, Starlette는 라우팅·미들웨어·Request/Response·WebSocket을 맡는 프레임워크, FastAPI는 그 위에 타입 검증·의존성 주입·자동 문서를 얹은 확장(Starlette를 상속)입니다. "ASGI 서버"란 앱을 async def app(scope, receive, send) 모양으로 호출하기로 한 규격(ASGI)을 따르는 서버라는 뜻이고, 이 규격이 메시지를 여러 번 주고받는 모양이라 비동기와 WebSocket이 가능합니다.
