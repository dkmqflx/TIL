멀티프로세스 & 3층 구조 — Uvicorn · Starlette · FastAPI

지금까지는 직원 한 명이 요령 있게 일하는 법(비동기)을 배웠습니다. 이번엔 가게를 여러 개 여는 법(멀티프로세스), 그리고 우리 서버가 실은 세 개의 라이브러리가 층층이 쌓인 구조라는 이야기입니다.

한 줄 요약. 비동기는 한 가게 안에서 기다림을 겹쳐 처리하는 기술(동시성)이고, 멀티프로세스(--workers)는 가게를 여러 개 열어 진짜 동시에 일하게 하는 기술(병렬성)이다. 서로 다른 문제를 풀기 때문에 실무에선 둘을 같이 쓴다. 그리고 요청 한 건은 Uvicorn(접수) → Starlette(동선) → FastAPI(검수·메뉴판) 3층을 통과한다.
이 문서를 읽는 순서. 이 장이 어렵게 느껴지는 가장 큰 이유는 프로세스·스레드·코어·GIL 같은 단어가 설명 없이 쏟아지기 때문입니다. 그래서 앞의 두 섹션에서 단어부터 정리하고, 그 다음에 워커와 3층 구조로 넘어갑니다. 급하지 않다면 순서대로 읽어 주세요.

학습 목표

  • 코어 · 프로세스 · 스레드를 각각 한 문장으로 말할 수 있다
  • "프로세스는 담고, 스레드가 돌고, 코어가 실행한다"는 관계를 그린다
  • GIL이 뭔지, 그래서 한 프로세스가 왜 코어 하나만 쓰는지 설명한다
  • --workers로 워커를 늘리는 법과 개수를 정하는 감을 잡는다
  • 워커끼리 전역 변수를 공유하지 못하는 이유와 대안을 안다
  • Uvicorn·Starlette·FastAPI가 각각 무슨 일을 하는지 그린다
  • ASGI와 WSGI의 차이를 한 줄로 설명한다
🧩

먼저 단어부터 — 코어 · 프로세스 · 스레드

이번 장에는 비슷하게 생긴 단어가 셋 나옵니다. 코어, 프로세스, 스레드. 이 셋의 관계만 잡으면 나머지 이야기는 술술 풀립니다. Week 2~3에서 쓰던 카페 비유를 그대로 이어서 봅시다.

단어컴퓨터에서는카페로 보면
코어 (core)CPU 안에서 실제로 계산을 하는 장치. "8코어 노트북"이면 계산 장치가 8개 들어 있다.커피를 뽑을 수 있는 커피 머신. 머신이 많으면 동시에 여러 잔을 뽑을 수 있다.
프로세스 (process)실행 중인 프로그램 한 벌. 자기만의 메모리 공간을 따로 갖는다.독립된 가게(지점). 재료 창고(메모리)를 각자 따로 갖고 있어 옆 가게 재료엔 손댈 수 없다.
스레드 (thread)프로세스 안에서 코드를 실행하는 흐름. 같은 프로세스의 스레드끼리는 메모리를 공유한다.한 가게 안의 직원. 같은 창고를 같이 쓰니 서로의 물건이 바로 보인다.

여기서 가장 헷갈리는 지점을 짚고 갑시다. "코어가 프로세스를 실행하고, 프로세스가 스레드를 실행하는 건가?" — 아닙니다. 둘의 역할은 이렇게 갈립니다.

📦
프로세스 = 담는 그릇 (실행하지 않는다)
메모리 공간·열어 둔 파일·네트워크 연결 같은 자원을 담아 두는 울타리입니다. 그릇 자체가 코드를 실행하는 게 아니에요. 대신 모든 프로세스는 스레드를 최소 한 개 갖습니다(메인 스레드). 스레드 없는 프로세스는 없습니다.
🏃
스레드 = 실행 흐름 (이게 코어에 올라간다)
코어에 올라가 실제로 명령어를 처리하는 단위입니다. 즉 코어가 실행하는 건 프로세스가 아니라 스레드예요. 프로세스는 그 스레드가 "어느 그릇 소속인지"를 말해 줄 뿐입니다.

그래서 서로 다른 두 개의 관계를 따로 기억해야 합니다 — 포함 관계(무엇이 무엇을 담고 있나)와 실행 관계(무엇이 어디서 돌아가나).

📦 포함 관계 : 프로세스 (그릇) ⊃ 스레드 (실행 흐름) ⊃ 코루틴 (양보하는 요령)
🏃 실행 관계 : 스레드 → OS 스케줄러가 배정 → 코어 (하드웨어)

카페로 말하면 — 가게 문이 열려 있다고 커피가 나오는 게 아니라, 직원이 머신 앞에 서야 커피가 나옵니다. 가게(프로세스)는 직원과 재료를 담아 두는 틀이고, 실제로 일하는 건 직원(스레드), 그 직원이 쓰는 장비가 머신(코어)이죠. 그림으로 보면 이렇습니다.

프로세스는 담고, 스레드가 돌고, 코어가 실행한다. 스레드가 코어보다 많으면 OS가 번갈아 올려 준다.
실제 숫자로 느껴 보기. 지금 쓰고 있는 컴퓨터도 정확히 이 구조입니다. 어느 맥북에서 재 보니 코어 12개 · 프로세스 643개 · 스레드 6,744개였습니다. 코어보다 스레드가 500배 이상 많은데도 아무 문제 없이 돌아가죠 — OS가 번갈아 올려 주기 때문입니다. 직접 확인해 보세요: 맥은 top -l 1 -n 0 | grep Processes, 리눅스는 ps -eLf | wc -l(스레드 수) 입니다.
Week 4에서 배운 것들을 이 비유에 얹어 보면. Lesson 01·02의 이벤트 루프는 "요령 좋은 직원 한 명"이었습니다. 주문을 받고, 커피가 추출되는 동안 멍하니 서 있지 않고 다음 주문을 받는 직원이죠. threadpool은 "가게 뒤편에 대기하는 보조 직원 ~40명"이었고요. 그리고 이번 장의 워커(멀티프로세스)는 가게 자체를 여러 개 여는 것입니다. 같은 층위의 이야기가 아니라는 게 이제 보이시죠?
🖥️

한 프로세스는 왜 코어 하나만 쓸까 — GIL

uvicorn main:app으로 서버를 띄우면 프로세스는 딱 한 개 생깁니다. 그런데 이 프로세스는 8코어 컴퓨터에서 돌려도, 한 순간에 코어 하나 몫의 일밖에 해내지 못합니다. 8코어짜리 컴퓨터를 사 놓고 내 서버의 처리량은 1코어분에 묶여 있는 셈이죠. 이유는 파이썬에 GIL이라는 규칙이 있기 때문입니다.

GIL = 가게에 하나뿐인 "커피 머신 열쇠". 어떤 가게(프로세스)에 직원(스레드)을 10명 뽑았다고 해봅시다. 그런데 이 가게 규칙은 "커피 머신을 쓰려면 열쇠를 쥐어야 하고, 열쇠는 딱 한 개"입니다. 직원이 10명이어도 실제로 커피를 뽑는 사람은 언제나 한 명이죠. GIL(Global Interpreter Lock)이 바로 이 열쇠입니다 — "파이썬 코드를 실행할 권리를 가진 스레드는 한 순간에 하나뿐"이라는 자물쇠요.
오해 주의 — "코어 하나만 쓴다"가 "코어 하나당 프로세스 하나"라는 뜻은 아닙니다. 헷갈리기 쉬운 지점이니 짚고 갑시다. ① 코어는 프로세스에 배정·예약되지 않습니다. 남은 코어가 내 서버 때문에 비어 있는 게 아니라, 그 코어들은 브라우저·DB·다른 프로그램이 계속 쓰고 있죠. "코어 하나 몫"은 내 서버가 낼 수 있는 처리량이 1코어분이라는 뜻일 뿐입니다. ② 띄울 수 있는 프로세스 개수도 코어 수와 무관합니다. 2코어에서 --workers 20도 잘 돌아갑니다. 실제로 지금 여러분 컴퓨터에는 코어 수의 수십 배쯤 되는 프로세스가 돌고 있어요(ps -A | wc -l로 확인해 보세요). OS가 짧은 시간 단위로 번갈아 코어에 올려 주기 때문입니다 — Lesson 01의 동시성이 프로세스 층에서 한 번 더 나오는 셈이죠. ③ 그래서 코어 수가 정하는 건 "몇 개를 띄울 수 있냐"가 아니라 "한 순간에 몇 개가 진짜 동시에 계산될 수 있냐"입니다.

그럼 스레드는 왜 있는 걸까요? 열쇠를 계속 쥐고 있는 건 아니기 때문입니다. 직원이 커피 머신을 켜 두고 추출을 기다리는 동안(= 네트워크·DB·파일 응답 대기)에는 열쇠를 내려놓습니다. 그 사이 다른 직원이 열쇠를 집어 자기 일을 하죠. 그래서 결과가 이렇게 갈립니다.

하는 일스레드를 늘리면?왜 그럴까
I/O 대기 (DB 응답, HTTP 호출, 파일 읽기)✅ 효과 있다기다리는 동안 열쇠(GIL)를 내려놓으니 다른 스레드가 그동안 진행한다
CPU 계산 (이미지 변환, 암호화, 큰 반복문)❌ 효과가 거의 없다계산하는 내내 열쇠를 쥐고 있어서, 결국 한 명씩 순서대로 하는 것과 같아진다

그리고 이건 파이썬 사정이라는 점도 알아 두면 좋습니다. 앞 섹션에서 봤듯 OS는 한 프로세스의 스레드 여러 개를 여러 코어에 동시에 올릴 준비가 되어 있습니다. 그 능력을 파이썬이 GIL로 스스로 포기하는 것이죠.

언어프로세스 하나로 여러 코어 활용그래서
Java · Go · C++ …✅ 가능 (GIL 같은 자물쇠가 없음)스레드를 늘리면 그만큼 코어를 더 쓴다
Python (GIL 있음)❌ 불가프로세스를 늘려야 코어를 더 쓴다 → 다음 섹션의 --workers

그래서 "멀티프로세스로 코어를 쓴다"는 이야기가 유독 파이썬 세계에서 강조됩니다. Java·Go 개발자는 스레드만 늘려도 되니 이 고민을 거의 하지 않죠.

비동기(async)로는 CPU 병렬이 안 되는 이유. 이벤트 루프는 스레드를 여러 개 쓰지도 않습니다. 아예 한 개죠(직원 한 명). await는 "내가 기다리는 동안 너 먼저 해"라고 순서를 양보하는 장치일 뿐, 두 계산을 동시에 돌리는 장치가 아닙니다. 그래서 비동기는 동시성은 주지만 병렬성은 주지 않습니다. 진짜로 두 코어에서 동시에 계산하려면 열쇠가 하나 더 필요하고, 열쇠는 프로세스마다 하나씩 있으니 → 결론은 프로세스를 늘리는 것입니다.
참고 — GIL은 영원하지 않습니다. Python 3.13부터 GIL을 끈 실험적 빌드(free-threaded build)가 제공되기 시작했습니다. 다만 기본 배포판과 대부분의 라이브러리는 아직 GIL이 있다고 전제하므로, 실무의 기본 가정은 여전히 "GIL 있음 → 멀티프로세스로 코어 활용"입니다. 지금은 이렇게만 알고 넘어가면 충분합니다.
⚙️

멀티프로세스 워커 — 가게를 여러 개 열기

해법은 생각보다 단순합니다. 같은 앱을 프로세스 여러 개로 띄우고, 들어오는 요청을 나눠 주는 것. 이렇게 띄운 각 프로세스를 워커(worker)라고 부릅니다. 워커는 각자 자기 GIL·자기 이벤트 루프·자기 메모리를 가진 완전히 독립된 가게라서, 서로 다른 코어에서 진짜 동시에 일합니다.

bashterminal
# 방법 1) Uvicorn이 직접 워커 4개를 띄운다 (가장 간단)
uvicorn main:app --workers 4

# 방법 2) Gunicorn이 프로세스를 관리하고, 각 워커는 Uvicorn으로 돌린다
#         (워커가 죽으면 되살리는 등 관리 기능이 더 많아 운영 환경에서 자주 쓰임)
gunicorn main:app -k uvicorn.workers.UvicornWorker --workers 4

# 개발 중엔 --reload 를 쓰죠. --reload 와 --workers 는 함께 쓸 수 없습니다.
# 개발 = --reload (워커 1개), 운영 = --workers N 으로 기억하세요.
uvicorn main:app --reload

"그럼 요청은 누가 4개 워커에 나눠 주나요?" 개발자가 코드를 짤 필요는 없습니다. 워커들은 같은 포트(소켓)를 함께 바라보고, 새 연결이 들어오면 OS가 노는 워커에게 넘겨 줍니다. 우리가 할 일은 개수를 정해 주는 것뿐이죠.

워커를 늘리면 그만큼 여러 코어 몫을 동시에 낼 수 있다. 요청 배분은 OS와 서버가 알아서 한다.

여기서 두 축을 절대 헷갈리지 마세요. 이 표 한 장이 Week 4의 핵심입니다.

해결책해결하는 문제단위카페로 보면
비동기 (async/await)기다리는 시간을 겹쳐 처리 (동시성)코루틴 / 이벤트 루프직원 한 명이 추출을 기다리는 동안 다음 주문을 받는다
멀티프로세스 (--workers)여러 코어에서 진짜 동시에 계산 (병렬성)프로세스(워커)지점을 4개 열어 손님을 나눠 받는다

둘은 다른 문제를 푸는 다른 층위의 도구라서 경쟁 관계가 아닙니다. 실무에선 거의 항상 함께 씁니다 — async def로 쓴 앱을 --workers 4로 띄우는 식이죠. 그렇게 띄운 서버의 진짜 내부 구조를 앞 섹션의 "프로세스 = 그릇, 스레드 = 실행 흐름"으로 그려 보면 이렇습니다. Week 4에서 배운 세 가지가 각각 어느 층에 있는지 한눈에 보이죠.

워커(프로세스) 안에 이벤트 루프 1개와 threadpool 스레드들이 들어 있다. Lesson 01·02·03이 각각 다른 층의 이야기였던 이유.
워커 개수는 몇으로 둘까? 출발점은 CPU 코어 수입니다. I/O 위주의 비동기 앱이면 "코어 수" 정도, CPU를 많이 쓰는 앱이면 "코어 수" 또는 "코어 수 + 1"에서 시작해 실제 부하로 측정하며 조정하세요. 무작정 늘리면 안 되는 이유가 둘 있습니다 — ① 워커마다 앱 전체가 메모리에 복사되므로 메모리 사용량이 워커 수만큼 늘고, ② 코어보다 워커가 많아도 띄우는 것 자체는 됩니다만, 서로 번갈아 실행되며 전환 비용만 늘어 이득이 없습니다. 컨테이너(Docker/K8s)에서 돌린다면 머신 전체 코어가 아니라 그 컨테이너에 할당된 CPU를 기준으로 잡아야 합니다.
가장 흔한 사고 — 워커는 메모리를 공유하지 않는다. 워커는 독립된 가게라 재료 창고(메모리)가 따로입니다. 그래서 전역 변수에 캐시·카운터·세션을 담아 두면 워커마다 값이 따로 놀아 버그가 됩니다.
pythonbad.py — 워커가 여러 개면 깨지는 코드
counter = 0          # 😱 이 변수는 워커마다 "따로" 존재한다

@app.post("/hit")
async def hit():
    global counter
    counter += 1
    return {"count": counter}

워커 4개로 띄우고 이 API를 네 번 호출하면 1, 2, 3, 4가 아니라 1, 1, 2, 1처럼 뒤죽박죽으로 나옵니다. 요청이 어느 워커로 갔는지에 따라 각자의 counter가 오르기 때문이죠. 해결책은 값을 모든 워커가 함께 보는 바깥 저장소에 두는 것입니다.

pythongood.py — 공유 상태는 외부 저장소로
@app.post("/hit")
async def hit():
    # Redis · DB 처럼 워커 밖에 있는 공용 창고에 저장
    count = await redis.incr("hit_count")
    return {"count": count}
같은 이유로 조심할 것 두 가지 더. ① 시작 시 캐시 로딩 — startup에서 큰 모델이나 데이터를 메모리에 올리면 워커 4개면 메모리도 4배로 듭니다. ② 앱 안의 스케줄러/배치 — APScheduler 같은 걸 앱에 넣고 워커 4개로 띄우면 같은 작업이 4번 실행됩니다(메일 4통, 정산 4번). 스케줄러는 별도 프로세스로 빼거나 잠금(lock)으로 한 워커만 실행하게 해야 합니다. NestJS를 PM2 cluster로 여러 인스턴스 띄울 때와 똑같은 주의사항입니다.

3층 구조 — Uvicorn · Starlette · FastAPI

여기서 이야기가 바뀝니다. 우리는 "FastAPI로 서버를 만든다"고 말하지만, 요청 한 건을 처리하는 데는 사실 세 개의 라이브러리가 층을 이뤄 협력합니다. 역할이 또렷하게 나뉘어 있어서, 한 번 정리해 두면 에러 메시지를 볼 때 "이건 어느 층 문제구나"가 바로 보입니다.

층정체하는 일카페로 보면
UvicornASGI 서버소켓에서 바이트를 받고 HTTP를 해석해 파이썬 객체로 만든다. 이벤트 루프를 돌리는 것도 이 층.드라이브스루 인터폰 — 밖에서 들리는 말(HTTP 바이트)을 매장용 주문서로 옮겨 적는다
Starlette웹 마이크로프레임워크라우팅, 미들웨어, Request/Response 객체, WebSocket, 백그라운드 태스크.매장 동선 — 주문서를 담당 파트로 보내고(라우팅), 입구에서 공통 검문(미들웨어)
FastAPIStarlette 위의 확장타입 기반 검증(Pydantic), 의존성 주입, 자동 OpenAPI 문서.주문 검수원 + 메뉴판 제작 — 이상한 주문은 반려하고, 필요한 재료를 미리 챙겨 준다

이제 요청 한 건의 여행을 순서대로 따라가 봅시다. 이게 이 섹션의 핵심입니다.

1
브라우저가 서버에 연결해 HTTP 요청을 바이트 뭉치로 보냅니다. (POST /items HTTP/1.1 ...)
2
Uvicorn이 그 바이트를 해석해 메서드·경로·헤더·본문을 정리한 파이썬 딕셔너리로 바꾸고, 이벤트 루프 위에서 앱을 호출합니다. ← 여기까지가 서버 층
3
Starlette 미들웨어를 차례로 통과합니다. (CORS 확인, 요청 로깅, 인증 헤더 검사 등 모든 요청에 공통인 일)
4
Starlette 라우터가 경로와 메서드를 보고 어느 함수를 부를지 찾습니다. 못 찾으면 여기서 404.
5
FastAPI가 의존성(Depends)을 실행하고, Path·Query·Body를 타입에 맞는지 검증합니다. 틀리면 422를 반환하고 내 함수는 호출조차 되지 않습니다.
6
내가 쓴 경로 함수가 실행됩니다. (async def면 이벤트 루프에서, def면 threadpool에서 — Lesson 02!)
7
반환값을 FastAPI가 response_model대로 다듬어 JSON으로 만들고, Starlette가 Response 객체로 감싸고, Uvicorn이 HTTP 바이트로 내보냅니다. 들어온 순서의 역순으로 나갑니다.
이 순서를 알면 디버깅이 쉬워집니다. 422가 떴다? → 5번, FastAPI 검증 층입니다(내 함수는 안 돌았음). 404? → 4번, 라우팅. CORS 에러? → 3번, 미들웨어. 요청이 아예 안 닿거나 포트 문제? → 2번, Uvicorn. 층을 알면 어디를 고쳐야 하는지 바로 보입니다.

그리고 꽤 중요한 사실 하나: FastAPI는 Starlette를 상속합니다. "상속"이란 Starlette가 가진 기능을 전부 물려받고 거기에 새 기능을 얹는다는 뜻이죠.

pythonfastapi/applications.py (개념)
from starlette.applications import Starlette

class FastAPI(Starlette):   # ← Starlette를 그대로 상속
    # 여기에 검증 · 의존성 주입 · 자동 문서 기능을 얹는다
    ...

즉 내 FastAPI 앱은 그 자체로 Starlette 앱이기도 합니다. 그래서 이런 일들이 자연스럽게 설명됩니다 — app.add_middleware(...), Request, WebSocket, BackgroundTasks는 원래 Starlette의 기능이고, FastAPI 공식 문서가 종종 "자세한 내용은 Starlette 문서를 보라"고 하거나 예제에서 from starlette...를 import하는 이유도 이것입니다.

Uvicorn 안에 Starlette, 그 안에 FastAPI가 중첩된다. 안쪽일수록 더 고수준의 일을 하고, 응답은 들어온 길을 되짚어 나간다.
그럼 Starlette만 쓰면 안 되나요? 됩니다. 라우팅·미들웨어만 필요한 아주 얇은 서버라면 Starlette만으로도 충분합니다. 우리가 FastAPI를 얹는 이유는 타입만 적으면 검증·문서·의존성 주입이 자동으로 따라오기 때문이죠. 반대로 Uvicorn 없이 FastAPI만 있으면 아무 요청도 받지 못합니다 — 소켓을 열고 HTTP를 읽는 층이 없으니까요.

ASGI? WSGI? — "규격"이라는 개념

앞에서 Uvicorn을 "ASGI 서버"라고 불렀습니다. 여기서 ASGI는 프로그램이 아니라 약속(규격)입니다. 이 한 가지만 잡으면 됩니다.

비유 — 규격은 콘센트 모양입니다. 220V 콘센트 모양이 정해져 있으니, 선풍기 만드는 회사와 발전소가 서로를 몰라도 그냥 꽂으면 돌아가죠. ASGI/WSGI가 바로 그 플러그 모양입니다. 서버(Uvicorn·Hypercorn)와 프레임워크(FastAPI·Django·Starlette)가 서로를 몰라도 꽂아 쓸 수 있게 파이썬 커뮤니티가 정한 약속이에요. 그래서 uvicorn을 hypercorn으로 바꿔도 내 앱 코드는 한 줄도 안 바뀝니다.

모양이 실제로 어떻게 다른지 보면 차이가 확 와닿습니다. 규격이란 결국 "서버가 앱을 어떤 모양의 함수로 호출할지"에 대한 약속입니다.

python규격의 정체 — 함수 모양 하나
# WSGI (옛 규격) — 그냥 함수. 한 번 호출하고 결과를 받으면 끝.
def app(environ, start_response):
    ...

# ASGI (새 규격) — async 함수. receive/send 로 메시지를 여러 번 주고받는다.
async def app(scope, receive, send):
    ...

차이가 보이시나요? WSGI는 "한 번 부르고 한 번 답하기"라서 요청 1건이 끝날 때까지 워커 하나가 붙잡혀 있고, 연결을 길게 유지하며 메시지를 주고받는 WebSocket은 아예 표현할 방법이 없습니다. ASGI는 async에 메시지를 여러 번 주고받는 구조라서 비동기 동시성과 장기 연결이 가능하죠.

규격특징대표 서버
WSGI동기 전용. 요청 1건 = 워커 1개가 끝까지 점유. WebSocket 불가.Gunicorn(기본), uWSGI
ASGIasync/await · WebSocket · 장기 연결 지원. 비동기 동시성 가능.Uvicorn, Hypercorn

한 줄로: ASGI는 WSGI에 비동기와 WebSocket을 더한 차세대 규격입니다. FastAPI가 비동기·WebSocket을 쓸 수 있는 건, 결국 ASGI라는 콘센트 위에 서 있기 때문이죠. (그래서 Flask·Django가 오래 동기였던 것도 그들이 WSGI 위에 있었기 때문입니다.)

Week 4 전체 정리 — 두 축과 3층. ① 동시성 축: async/await + 이벤트 루프로 한 워커 안에서 기다림을 겹쳐 처리한다(직원 한 명의 요령). ② 병렬성 축: --workers N으로 워커(가게)를 늘려 여러 코어를 쓴다. GIL은 워커마다 하나씩이라 이 방법밖에 없다. ③ 그리고 이 모든 게 Uvicorn → Starlette → FastAPI 3층 위에서 돌아간다. "두 축 + 3층" 이 그림이 머릿속에 있으면, 나중에 성능 문제를 만났을 때 어디를 손봐야 할지 판단할 수 있습니다.

셀프 체크

Q 프로세스와 스레드의 차이를 한 문장으로?

프로세스는 자기 메모리를 따로 가진 "그릇"(가게)이고, 스레드는 그 안에서 실제로 코드를 실행하는 흐름(직원)입니다. 핵심은 코어에 올라가 실행되는 건 프로세스가 아니라 스레드라는 점 — 프로세스 자체는 실행되지 않고 담기만 합니다(그래서 모든 프로세스는 스레드를 최소 1개 갖습니다). 또 같은 프로세스의 스레드끼리는 메모리를 공유하지만 프로세스끼리는 공유하지 않아서, 워커를 여러 개 띄우면 전역 변수가 서로 보이지 않습니다.

Q --workers 4로 띄우면 프로세스·이벤트 루프·스레드는 각각 몇 개일까요?

프로세스 4개, 그 각각에 이벤트 루프 1개(메인 스레드), 그리고 각 워커마다 threadpool 스레드 최대 ~40개가 붙습니다. 그래서 스레드는 총 4 × (1 + 최대 40)개가 되죠. async def는 각 워커의 이벤트 루프에서, def는 그 워커의 threadpool에서 실행됩니다. Lesson 01(이벤트 루프)·02(threadpool)·03(프로세스)이 서로 다른 층의 이야기였던 이유입니다.

Q GIL이 뭔가요? 스레드를 늘려도 CPU 계산이 빨라지지 않는 이유는?

GIL은 "한 순간에 파이썬 코드를 실행할 스레드는 하나뿐"이라는 자물쇠입니다(가게에 하나뿐인 커피 머신 열쇠). CPU 계산은 실행 내내 열쇠를 쥐고 있으므로, 스레드가 10개라도 결국 한 명씩 순서대로 하는 것과 같아집니다. 반면 I/O 대기 중에는 열쇠를 내려놓기 때문에 I/O 작업에는 스레드가 효과가 있습니다.

Q 코어가 8개면 프로세스(워커)도 8개까지만 띄울 수 있나요?

아니요. 코어 수는 개수 제한이 아닙니다. 2코어에서 --workers 20도 잘 돌아가고, 지금 여러분 컴퓨터에도 코어 수의 수십 배쯤 되는 프로세스가 실행 중입니다. OS가 프로세스들을 짧은 시간 단위로 번갈아 코어에 올려 주기 때문이죠. 코어 수가 정하는 건 "한 순간에 몇 개가 진짜 동시에 계산되는가"입니다. 그래서 "워커 ≈ 코어 수"는 규칙이 아니라 성능상 출발점이에요 — 코어보다 많이 띄워도 동작은 하지만 전환 비용과 메모리가 늘고, 반대로 I/O 대기가 대부분인 앱이라면 코어 수보다 많이 띄우는 게 이득일 수도 있습니다.

Q 비동기를 쓰는데도 워커를 여러 개 띄우는 이유는?

비동기는 직원 한 명을 요령 있게 일하게 만드는 기술입니다. 커피가 추출되는 동안(= DB 응답을 기다리는 동안) 멍하니 서 있지 않고 다음 주문을 받죠. 그런데 이 직원은 어쨌든 한 명입니다. 기다리는 일이 아니라 직접 손을 놀려야 하는 일(계산)이 몰리면 뒤에 줄이 그대로 밀립니다. 요령으로는 손이 두 개가 되지 않으니까요.

그래서 가게를 여러 개 엽니다. 워커 4개 = 가게 4채 = 요령 좋은 직원 4명이 각자의 커피 머신으로 일하는 것이니, 손이 4배가 됩니다. 8코어 컴퓨터를 사 놓고 1코어 몫만 쓰던 상황이 이렇게 풀리죠.

한 줄로: 비동기는 "한 명이 잘 일하게", 워커는 "일할 사람을 늘리게" 만듭니다. 서로 대신할 수 없는 다른 종류의 개선이라 둘을 같이 씁니다. (용어로 말하면 — 비동기는 한 프로세스 안의 I/O 동시성, 워커는 여러 코어를 쓰는 CPU 병렬성입니다.)

Q 워커 4개인데 전역 변수 카운터 값이 뒤죽박죽입니다. 왜죠?

워커는 독립된 프로세스라 메모리를 공유하지 않아서, counter가 워커마다 별개로 4개 존재합니다. 요청이 어느 워커로 갔는지에 따라 각자의 값이 오르니 1, 1, 2, 1처럼 보이죠. 해결책은 Redis·DB 같은 외부 저장소에 값을 두는 것입니다. 같은 이유로 앱 안의 스케줄러는 워커 수만큼 중복 실행되니 주의해야 합니다.

Q Uvicorn, Starlette, FastAPI의 역할을 한마디씩 구분하면?

Uvicorn은 ASGI 서버(소켓·HTTP 파싱·이벤트 루프 구동), Starlette는 웹 프레임워크(라우팅·미들웨어·Request/Response·WebSocket), FastAPI는 그 위의 확장(타입 검증·의존성 주입·자동 문서)입니다. FastAPI는 Starlette를 상속하므로 내 FastAPI 앱은 그 자체로 Starlette 앱이기도 합니다.

Q 422 응답은 3층 중 어디서 만들어질까요?

FastAPI 층입니다. 라우팅(Starlette)으로 함수를 찾은 뒤, FastAPI가 Path·Query·Body를 타입에 맞춰 검증하다가 실패하면 422를 돌려줍니다. 이때 내가 쓴 경로 함수는 호출조차 되지 않습니다. 참고로 404는 Starlette 라우팅 층, CORS 에러는 미들웨어 층에서 발생합니다.

Q ASGI가 WSGI와 다른 핵심 한 가지는?

ASGI는 async/await와 WebSocket·장기 연결을 지원합니다. WSGI는 "함수를 한 번 부르고 결과를 받는" 동기 전용 모양이라 비동기 동시성이나 WebSocket을 표현할 수 없고, ASGI는 async 함수에 receive/send로 메시지를 여러 번 주고받는 모양이라 가능합니다. FastAPI가 비동기로 동작하는 토대가 바로 ASGI(그 위의 Uvicorn)입니다.
