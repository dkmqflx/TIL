SQLAlchemy 2.0 ORM 모델링 클래스로 테이블을 그리기

파이썬 클래스 하나가 테이블 하나가 됩니다. NestJS의 TypeORM @Entity가 하던 일을, SQLAlchemy 2.0의 DeclarativeBase + Mapped[]로 합니다.

한 줄 요약. ORM은 객체 ↔ 테이블 번역기다. class Todo(Base)가 todos 테이블이 되고, Todo(...) 인스턴스 하나가 한 행(row)이 된다. SQL을 손으로 쓰지 않고 파이썬 객체로 데이터를 다룬다. 2.0 스타일은 Mapped[] 타입 힌트로 컬럼을 선언한다.

학습 목표

  • ORM이 객체와 테이블을 어떻게 매핑하는지 이해한다
  • SQLAlchemy 2.0 스타일(DeclarativeBase · Mapped · mapped_column)로 모델을 짠다
  • 타입·nullable·default·index 등 컬럼 옵션을 건다
  • create_all로 테이블을 생성(DDL)한다
🔁

ORM이란 — 객체와 테이블의 번역기

DB는 행과 열로 데이터를 저장하지만, 우리 코드는 객체로 생각합니다. 이 둘 사이의 간극(임피던스 불일치)을 메우는 게 ORM(Object-Relational Mapping)입니다.

비유 — 양식 작성 대행. raw SQL은 모든 서류를 손으로 직접 작성하는 것입니다. 빠르지만 오타(SQL 문법 오류)가 나기 쉽고, 양식이 바뀌면 전부 고쳐야 하죠. ORM은 "이름·완료여부만 알려주세요" 하고 양식을 대신 채워주는 대행 창구입니다. 당신은 파이썬 객체만 다루고, ORM이 INSERT INTO todos ... 같은 SQL로 번역합니다.
raw SQLORM
SQL 문자열을 직접 작성파이썬 객체로 표현
DB 종류 바뀌면 SQL 수정대부분 코드 그대로 이식
오타·인젝션 위험 직접 관리안전한 바인딩 자동(Lesson 3)
세밀한 튜닝에 유리생산성·가독성에 유리

2.0 스타일 — DeclarativeBase & Mapped

SQLAlchemy 2.0은 타입 힌트 기반으로 모델을 선언합니다. DeclarativeBase를 상속한 Base를 만들고, 컬럼은 Mapped[타입] + mapped_column(...)로 적습니다. 타입 힌트가 곧 컬럼 타입이 됩니다.

python
from datetime import datetime
from sqlalchemy import String, func
from sqlalchemy.orm import (
    DeclarativeBase, Mapped, mapped_column,
)

class Base(DeclarativeBase):
    pass                              # 모든 모델의 부모. metadata가 모인다.

class Todo(Base):
    __tablename__ = "todos"

    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str] = mapped_column(String(100), index=True)
    done: Mapped[bool] = mapped_column(default=False)
    created_at: Mapped[datetime] = mapped_column(
        server_default=func.now(),
    )
타입 힌트는 "장식"이 아니다. 위 코드에서 Mapped[str]의 str은 단순한 메모가 아니라, 실제로 만들어질 테이블 컬럼의 설계도입니다. 컬럼 타입은 물론이고 NOT NULL 제약까지 여기서 결정됩니다. 이게 2.0 스타일의 가장 큰 변화라, 바로 다음 섹션에서 하나씩 뜯어봅니다.
🕳️

Mapped[T] vs Mapped[T | None] — "이 칸, 비워도 되나요?"

2.0 스타일에서 처음 배울 때 가장 많이 막히는 지점입니다. 결론부터 말하면, 타입 힌트에 | None이 붙어 있느냐 없느냐가 테이블의 NOT NULL 제약을 결정합니다. 왜 그렇게 되는지 이해하려면 원래 상관없어 보이는 두 가지를 따로 짚어야 합니다. ① DB에서 말하는 NULL이 무엇인지, ② 파이썬에서 | None이 무엇인지. 그리고 ③ SQLAlchemy가 이 둘을 어떻게 이어 붙이는지가 이 섹션의 전부입니다.

① NULL은 0도, 빈 문자열도 아니다

DB에서 NULL은 "값이 아예 없음"이라는 뜻입니다. 숫자 0이나 빈 문자열 ''과는 전혀 다릅니다. 0과 ''은 값이 있는 상태고, NULL은 값 자체가 없는 상태입니다. 그리고 NOT NULL은 "이 칸은 절대 비어 있으면 안 된다"고 DB가 직접 거는 규칙입니다. 이 규칙을 어긴 저장 요청은 DB가 아예 거부합니다.

비유 — 종이 신청서의 별표(*). 회원가입 신청서를 떠올려 보세요. 이름 * 처럼 별표가 붙은 칸은 반드시 채워야 접수가 됩니다(NOT NULL). 반면 "별명" 칸은 비워둬도 접수가 되죠(NULL 허용). 여기서 중요한 건, 별명 칸에 "없음"이라고 적는 것과 아무것도 안 적고 비워두는 것이 다르다는 점입니다. 앞은 '없음'이라는 값이 적힌 것이고, 뒤가 바로 NULL입니다.

② | None은 파이썬의 "또는"

파이썬 타입 힌트에서 |는 "또는"이라는 뜻입니다. 그래서 str | None은 "여기엔 문자열이 들어오거나, None이 들어올 수 있다"는 선언이 됩니다. None은 파이썬이 "값이 없음"을 표현하는 방식이고요. 정리하면 str은 "문자열이 반드시 있다", str | None은 "없을 수도 있다"입니다. 여기까지는 DB와 아무 상관 없는, 순수한 파이썬 문법 이야기입니다.

Optional[str]이라고 쓴 코드도 자주 보실 텐데, str | None과 완전히 같은 뜻입니다. |는 파이썬 3.10부터 생긴 새 표기일 뿐이에요. 예전 코드·문서에선 Optional[...], 요즘 코드에선 | None을 주로 씁니다.

③ SQLAlchemy가 둘을 이어 붙인다

여기가 연결 고리입니다. SQLAlchemy 2.0은 모델 클래스를 읽을 때 타입 힌트를 그냥 읽고 넘어가지 않고, 그것을 스키마 설계도로 해석합니다. "파이썬에서 None이 될 수 있다 = DB에서도 비어 있을 수 있다"로 번역하는 것이죠. 그래서 nullable=True 같은 옵션을 따로 적을 필요가 없습니다.

Mapped[str]
→
"None은 못 들어오네"
→
VARCHAR NOT NULL
Mapped[str | None]
→
"None도 들어올 수 있네"
→
VARCHAR (비워도 됨)

실제 모델과, 그 모델로 만들어지는 테이블을 나란히 놓고 보면 확실해집니다. 기본키 id는 앞 예제와 같으니 접어두고, 필수인 title과 선택인 memo 두 컬럼만 봅니다.

파이썬 — 내가 쓰는 모델
class Todo(Base):
    __tablename__ = "todos"

    # | None 없음 → 필수
    title: Mapped[str] = \
      mapped_column(String(100))

    # | None 있음 → 선택
    memo: Mapped[str | None] = \
      mapped_column(String(500))
DB — 실제로 만들어지는 테이블
CREATE TABLE todos (
    ...

    -- 비우면 DB가 거부한다
    title VARCHAR(100) NOT NULL,

    -- 비워도 통과한다
    memo VARCHAR(500)
);

어기면 어떻게 되나 — 두 군데서 잡아준다

| None의 유무는 값을 넣을 때와 값을 꺼내 쓸 때 양쪽에서 효과를 냅니다. 이 두 가지를 한 줄로 동시에 얻는 게 2.0 스타일의 핵심 이득입니다.

넣을 때 — DB가 거부한다

python
session.add(Todo(title="장보기", memo=None))   # ✅ memo는 선택 → 통과
session.add(Todo(title="장보기"))              # ✅ memo 생략 → NULL로 저장

session.add(Todo(title=None, memo="메모"))     # ❌ title은 필수
session.commit()
# sqlalchemy.exc.IntegrityError:
#   null value in column "title" violates not-null constraint

이 에러는 파이썬이 만든 게 아니라 PostgreSQL이 직접 뱉은 것입니다. 앱 코드에 구멍이 생겨도 DB가 마지막 방어선 역할을 해 준다는 뜻이죠.

꺼내 쓸 때 — 에디터가 미리 경고한다

python
todo = session.get(Todo, 1)

todo.title.upper()      # ✅ str이 확실하니 그냥 호출 가능
todo.memo.upper()       # ⚠️ 경고: "None일 수도 있는데 .upper()를 부른다고?"

if todo.memo:           # ✅ None인지 확인하고 쓰면 안전
    print(todo.memo.upper())
실행 전에 잡힌다는 게 포인트. memo가 None인 줄 모르고 .upper()를 호출하면 실제 서비스에서 AttributeError로 터집니다. 그런데 Mapped[str | None]이라고 선언해 두면 코드를 돌려보기도 전에 에디터(VS Code·Pyright·mypy)가 빨간 줄을 그어 줍니다. 타입 힌트 한 번으로 DB 제약 + 파이썬 코드 안전성을 동시에 챙기는 셈입니다.

왜 이렇게 바꿨을까 — 1.x 스타일과 비교

예전 스타일에서는 "파이썬 타입"과 "DB 제약"을 서로 다른 곳에 적어야 했습니다. 게다가 옛 Column()의 기본값은 nullable=True라, 아무 옵션도 안 주면 모든 컬럼이 조용히 NULL 허용이 되어 버렸습니다.

1.x 스타일 — 두 군데를 손으로 맞춤
class Todo(Base):
    __tablename__ = "todos"

    # 기본이 nullable=True 라서
    # 필수는 직접 명시해야 한다
    title = Column(
        String, nullable=False
    )

    # 파이썬 타입 정보는 없다
    # → 에디터는 str인지 모른다
2.0 스타일 — 타입 힌트 한 곳으로 통일
class Todo(Base):
    __tablename__ = "todos"

    # 타입 힌트 한 줄이
    # NOT NULL 과 str 을 함께 선언
    title: Mapped[str]

    # 이 한 줄이면 NULL 허용
    memo: Mapped[str | None]

선언의 출처를 타입 힌트 한 곳으로 모았기 때문에, "타입은 str인데 스키마는 NULL 허용" 같은 어긋남이 생길 수가 없습니다. 고칠 때도 한 줄만 고치면 둘 다 따라옵니다.

NestJS를 해봤다면. TypeORM에서는 @Column({ nullable: true }) memo: string | null;처럼 데코레이터 옵션과 TS 타입을 각각 적어야 합니다. 둘이 어긋나도(옵션은 nullable: true인데 타입은 string) 아무도 알려주지 않죠. SQLAlchemy 2.0은 Mapped[str | None] 한 곳만 고치면 스키마와 타입이 함께 움직입니다.

헷갈리기 쉬운 세 가지

이렇게 쓰면실제 결과왜 그런가
primary_key=True를 준 컬럼 타입과 무관하게 언제나 NOT NULL 기본키는 행을 구분하는 열쇠라 비워둘 수 없습니다. | None을 붙여도 소용없습니다.
Mapped[str]에 default=None 여전히 NOT NULL → 저장 시 에러 default는 "안 적었을 때 파이썬이 채워 넣을 값", nullable은 "빈 값을 DB가 허용하는가". 서로 다른 문제입니다.
Mapped[str]에 nullable=True NULL 허용 (옵션이 이김) 명시한 옵션이 타입 힌트를 덮어씁니다. 하지만 타입과 스키마가 어긋나 에디터가 잘못된 안내를 하게 되니 피하는 게 좋습니다.
한 줄로 기억하기. 타입에 | None이 있으면 "비워도 되는 칸", 없으면 "반드시 채워야 하는 칸"입니다. 신청서로 치면 | None을 붙이는 행위가 곧 별표(*)를 떼는 것입니다.
🎛️

컬럼 옵션 — 타입 · nullable · default · index

옵션의미예
primary_key=True기본키(PK)id
Mapped[T] / Mapped[T | None]NOT NULL / NULL 허용title / 선택 필드
default=...파이썬 측 기본값done=False
server_default=func.now()DB가 채우는 기본값created_at
index=True조회용 인덱스title
String(100)VARCHAR 길이 제한title
created_at은 왜 server_default일까. 파이썬 쪽 default=datetime.utcnow는 3.12+에서 deprecated이고, 앱 서버 시계에 의존합니다. server_default=func.now()는 DB 서버가 직접 시각을 찍어 정확하고 일관됩니다. 여러 인스턴스가 떠 있어도 기준 시계가 하나(DB)라 안전합니다.

NestJS TypeORM과 나란히

같은 "할 일" 엔티티를 양쪽으로 그려 봅니다. 데코레이터(Nest) ↔ 타입 힌트(SQLAlchemy)의 대비가 핵심입니다.

NestJS — TypeORM Entity
@Entity('todos')
export class Todo {
  @PrimaryGeneratedColumn()
  id: number;

  @Column({ length: 100 })
  title: string;

  @Column({ default: false })
  done: boolean;

  @CreateDateColumn()
  createdAt: Date;
}
FastAPI — SQLAlchemy 2.0
class Todo(Base):
    __tablename__ = "todos"

    id: Mapped[int] = \
        mapped_column(primary_key=True)
    title: Mapped[str] = \
        mapped_column(String(100))
    done: Mapped[bool] = \
        mapped_column(default=False)
    created_at: Mapped[datetime] = \
        mapped_column(server_default=func.now())

@PrimaryGeneratedColumn ↔ primary_key=True, @Column ↔ mapped_column. 데코레이터 대신 타입 힌트가 일합니다.

클래스 = 테이블, 필드 = 컬럼, 인스턴스 = 행. ORM이 이 매핑을 자동으로 관리한다.
🏗️

create_all — 테이블 생성(DDL)

모델을 선언했다고 테이블이 생기진 않습니다. Base.metadata.create_all(engine)를 호출하면, 등록된 모든 모델을 보고 CREATE TABLE(DDL)을 실행합니다. 이미 있는 테이블은 건드리지 않습니다.

python
from database import engine
from models import Base

# 모델 → CREATE TABLE 변환 후 실행. 있으면 건너뜀.
Base.metadata.create_all(engine)
create_all은 "변경"을 못 한다. create_all은 없는 테이블을 만들 뿐, 이미 있는 테이블의 컬럼 추가·타입 변경은 하지 못합니다. 모델을 고쳐도 기존 테이블엔 반영되지 않죠. 그래서 데모·초기 개발에만 쓰고, 운영의 스키마 변경은 Week 10의 Alembic 마이그레이션으로 버전 관리합니다.
다음 단계 예고 — Alembic. 실무에선 "컬럼 하나 추가"도 기록(마이그레이션)으로 남겨 팀·운영 DB에 순서대로 적용합니다. NestJS의 typeorm migration:generate에 대응하는 게 Alembic의 alembic revision --autogenerate입니다. 지금은 create_all로 빠르게 시작하고, 구조가 안정되면 Alembic으로 갈아탑니다.

셀프 체크

Q SQLAlchemy 2.0 스타일에서 컬럼의 nullable 여부는 어떻게 정하나요?

타입 힌트로 정합니다. Mapped[str]는 NOT NULL, Mapped[str | None]은 NULL 허용입니다. 별도 옵션 없이 타입 자체가 nullable 여부를 선언합니다.

Q Mapped[str]에 default=None을 주면 빈 값으로 저장되나요?

아닙니다. default는 "값을 안 적었을 때 파이썬이 대신 채워 넣을 값"이고, nullable은 "빈 값을 DB가 허용하는가"라서 서로 다른 문제입니다. Mapped[str]인 채로 None이 들어가면 DB가 IntegrityError(not-null constraint 위반)로 거부합니다. 비워도 되게 하려면 타입을 Mapped[str | None]으로 바꿔야 합니다.

Q default와 server_default의 차이는?

default는 파이썬(앱) 쪽에서 값을 채우고, server_default는 DB 서버가 채웁니다. created_at처럼 정확한 시각·여러 인스턴스 일관성이 중요한 경우 server_default=func.now()로 DB가 찍게 하는 편이 안전합니다.

Q 모델 컬럼을 바꿨는데 create_all로 테이블이 안 바뀌어요.

create_all은 없는 테이블을 만들 뿐, 기존 테이블의 컬럼 변경은 하지 못합니다. 스키마 변경은 Alembic 마이그레이션(Week 10)으로 처리해야 합니다. 데모라면 테이블을 드롭 후 다시 만들 수도 있지만, 실데이터가 있으면 절대 그러면 안 됩니다.
