Connection Pool · Session 그리고 안전한 쿼리

DB에 말을 걸려면 먼저 연결이 필요하고, 그 연결은 비쌉니다. 그래서 미리 만들어 돌려 쓰는 Connection Pool, 작업을 묶는 Session, 그리고 값을 안전하게 넘기는 bind 변수까지 — DB를 실제로 다루는 마지막 조각들입니다. 마지막에 NestJS + TypeORM과 대응표로 비교합니다.

한 줄 요약. DB 연결은 맺는 데 비용이 커서 매번 새로 만들지 않는다. 미리 몇 개 만들어 두고(pool) 빌려 쓰고 반납한다. 그 연결 위에서 하는 작업 한 묶음이 Session(장바구니)이고, 결제 버튼이 commit이다. 값은 문자열로 잇지 말고 bind 변수로 따로 전달해 인젝션을 막는다.

학습 목표

  • "DB 연결"이 정확히 무엇이고 왜 비싼지 설명할 수 있다
  • Connection Pool이 왜 필요한지와 파라미터 4개의 의미를 안다
  • Session(장바구니)으로 작업을 묶고 commit / close 한다
  • select → execute → fetch의 3단계를 구분해 결과를 꺼낸다
  • bind 변수가 왜 SQL Injection을 막는지 원리로 설명한다
  • 각 개념을 NestJS + TypeORM의 무엇과 대응시킬 수 있다
🔄

Connection Pool — 연결을 재사용하기

① "연결(connection)"이 뭔가요, 왜 비싼가요

PostgreSQL은 내 파이썬 코드 안에 들어 있는 게 아닙니다. 완전히 별개의 프로그램이고, 보통 다른 컨테이너나 다른 서버에서 혼자 돌아갑니다. 즉 내 코드와 DB는 서로 남남인 두 프로그램이고, 남남끼리 대화하려면 먼저 말을 주고받을 통로를 하나 뚫어야 합니다. 그 통로 하나가 연결(connection)입니다. 통로를 뚫으려면 주소로 찾아가 접속하고, 서로 신호를 주고받아 통로를 열고, "나 todo 계정인데 비밀번호는 ○○" 하고 인증까지 받아야 비로소 본론(쿼리)을 말할 수 있습니다. 정확히 몇 ms인지는 네트워크와 서버 사정에 따라 다르지만, 방향은 분명합니다. 연결을 새로 맺는 일은 가벼운 조회 한 번보다 훨씬 비싼 작업입니다.

비용은 내 쪽 시간만이 아닙니다. PostgreSQL 공식 문서는 서버가 "연결마다 새 프로세스를 fork한다", 즉 그 연결만 전담할 일꾼 프로세스를 하나 새로 띄운다고 설명합니다. 연결 하나 = DB 서버의 프로세스 하나인 셈이라, 요청이 몰릴 때 연결을 마구 만들면 느려지는 정도가 아니라 DB 자체가 버티지 못합니다. 그래서 SQLAlchemy 문서도 커넥션 풀을 "연결을 효율적으로 재사용하기 위한 표준 기법"이라고 소개합니다.

② 해결책 — 미리 만들어 두고 돌려 쓴다

방법은 단순합니다. 연결을 몇 개 만들어 두고, 요청이 오면 그중 하나를 빌려주고, 일이 끝나면 끊지 말고 돌려받는 것입니다. 이 "만들어 둔 연결 보관함"이 Connection Pool입니다. 보관함은 create_engine()만 호출하면 SQLAlchemy가 알아서 만들고 관리하며, 실제 연결은 처음 쓸 때 하나씩 만들어져 보관함에 남습니다. 우리가 할 일은 빌린 걸 반드시 반납하는 것뿐입니다.

비유 — 콜택시 대기열. 손님(요청)이 올 때마다 새 택시를 사는 것은 미친 짓입니다. 대신 회사는 택시 몇 대를 대기열(pool)에 세워 둡니다. 손님이 오면 대기 중인 택시를 배차(빌림)하고, 목적지에 도착하면 택시는 다시 대기열로 복귀(반납)합니다. 손님이 몰리면 임시 차량을 더 부르고(max_overflow), 그래도 모자라면 손님은 줄을 서서 기다립니다. 중요한 건 택시를 폐차하지 않는다는 점이에요.
1
앱이 뜰 때 풀(보관함)이 만들어집니다. 연결은 첫 요청 때부터 필요한 만큼 채워집니다.
2
요청이 들어오면 풀에서 놀고 있는 연결 하나를 빌립니다(checkout). 이미 연결·인증이 끝난 상태라 기다림이 거의 0입니다.
3
그 연결로 쿼리를 주고받습니다. 이 연결은 그동안 나만 씁니다(다른 요청과 공유되지 않음).
4
작업이 끝나면 close()로 반납(checkin)합니다. 여기서 close()는 "연결을 끊는다"가 아니라 "다 썼으니 풀에 돌려놓는다"는 뜻입니다. 이 반납을 담당하는 게 다음 섹션의 Session.close()입니다.

③ 파라미터 네 개 뜯어보기

풀은 create_engine에 옵션으로 설정합니다. 이름만 보면 어렵지만, 전부 택시 회사 운영 규칙이라고 생각하면 쉽습니다.

python
engine = create_engine(
    DATABASE_URL,
    pool_size=5,        # 상시 대기 5대
    max_overflow=10,    # 피크 때 임시로 +10대까지
    pool_recycle=1800,  # 30분 넘게 산 연결은 폐차하고 새로
    pool_pre_ping=True, # 배차 전 시동 걸어보기
)
파라미터의미택시 회사로 치면
pool_size평상시 유지하는 연결 수 (기본 5)상시 대기 택시 대수
max_overflow몰릴 때 추가로 허용하는 한도 (기본 10)피크 때만 부르는 임시 콜 한도
pool_recycle지정한 초가 지난 연결은 버리고 새로 만듦오래된 차 교체 주기
pool_pre_ping빌려주기 직전에 "살아있니?" 한 번 확인배차 전 시동 확인

pool_size와 max_overflow는 짝입니다. 위 설정이면 동시에 열릴 수 있는 연결은 최대 5 + 10 = 15개입니다. 상시 5대는 계속 대기열에 남아 있지만, 임시로 부른 10대는 일이 끝나면 대기열에 남지 않고 해산합니다(진짜로 연결이 닫힙니다). 15개도 다 차면 새 요청은 에러가 나는 게 아니라 줄을 서서 기다리고, 기본값 30초(pool_timeout)를 넘겨도 자리가 안 나면 그때 TimeoutError가 납니다. 그래서 "API가 갑자기 30초씩 느려지다가 터진다"면 연결을 반납하지 않은 코드를 가장 먼저 의심해야 합니다.

pool_recycle이 필요한 이유는 조금 뜻밖입니다. 내 쪽에서는 연결을 잘 들고 있어도, DB 서버가 재시작되거나, 오래 조용한 연결을 스스로 끊어 버리는 일이 있기 때문입니다. PostgreSQL에도 유휴 세션을 끊는 idle_session_timeout 설정이 있고, 공식 문서는 여기에 "커넥션 풀 같은 계층은 예기치 않은 연결 종료에 잘 대응하지 못할 수 있으니 주의하라"는 경고를 달아 두었습니다. 바로 이 상황입니다 — 풀에는 겉보기엔 멀쩡하지만 실제로는 죽은 연결이 남고, 하필 그걸 빌려 간 요청이 에러를 뱉습니다. 그래서 "일정 시간 지난 연결은 어차피 버리고 새로 만들자"고 정해 두는 겁니다. pool_pre_ping=True는 여기에 안전장치를 하나 더 겁니다. 빌려주기 직전에 아주 가벼운 확인 쿼리를 날려 보고, 응답이 없으면 그 연결을 조용히 버리고 새 연결을 대신 내줍니다. 비용이 거의 없으니 켜 두는 걸 권장합니다.

요청은 풀에서 연결을 빌려 쓰고, 끝나면 반납한다. 매번 새로 맺지 않아 빠르다.

Session — 작업 단위(Unit of Work)

① Session은 "장바구니"다

풀에서 연결을 빌렸다고 바로 SQL을 쓰지는 않습니다. 그 연결 위에서 한 덩어리의 작업을 담아 두는 그릇이 Session입니다. 교과서에서는 Unit of Work(작업 단위)라고 부릅니다.

비유 — 쇼핑 장바구니. 상품을 장바구니에 담는다고 결제가 되지는 않습니다. 여러 개를 담고 빼고 하다가, 결제 버튼을 눌러야 비로소 주문이 확정되죠. Session도 똑같습니다. session.add(todo)는 장바구니에 담기일 뿐 DB에는 아직 아무 일도 없고, session.commit()이 결제 버튼입니다. 마음이 바뀌면 session.rollback()으로 장바구니를 통째로 비울 수도 있습니다.

② 왜 굳이 모았다가 한 번에 반영할까 — 트랜잭션

"그냥 하나씩 바로 저장하면 안 되나?" 싶지만, 계좌 이체에서 "A에서 1만 원 빼기"와 "B에 1만 원 넣기"는 반드시 둘 다 되거나, 둘 다 안 되어야 합니다. 빼기만 성공하면 돈이 공중분해되니까요. 이렇게 여러 작업을 "전부 성공 아니면 전부 취소"로 묶는 단위가 트랜잭션입니다. Session 자체가 트랜잭션인 건 아니고, 세션이 첫 작업을 시작하면 트랜잭션이 자동으로 열리고 commit()(확정) 또는 rollback()(전부 취소)으로 닫힙니다. 그래서 한 번의 commit()까지 쌓인 변경은 언제나 한 덩어리로 반영되거나 한 덩어리로 없던 일이 됩니다.

③ 코드 한 줄씩 — sessionmaker

Session은 요청마다 새로 만들어야 하니, 매번 옵션을 적는 대신 세션을 찍어내는 공장을 하나 만들어 둡니다. 그게 sessionmaker입니다.

python
from sqlalchemy.orm import Session, sessionmaker

SessionLocal = sessionmaker(       # ← 세션을 찍어내는 "공장"
    bind=engine,                   # 이 엔진의 풀에서 연결을 빌려라
    autoflush=False,               # 몰래 미리 내보내지 마라
    expire_on_commit=False,        # commit 후에도 객체 값을 그대로 두라
)

db = SessionLocal()                # ← 여기서 세션 하나가 만들어진다
flush와 commit은 다릅니다. flush는 "장바구니 목록을 계산대 직원에게 보여주는 것"입니다. INSERT/UPDATE 문이 DB로 나가 id 같은 값은 생기지만, 아직 확정이 아니라 rollback하면 사라집니다. commit이 "결제 완료"고, 이때부터 다른 사람 눈에도 보입니다. (commit()은 내부적으로 flush를 먼저 합니다.)
옵션무슨 뜻인가왜 이렇게 두나
bind=engine이 세션이 사용할 엔진(=연결 풀)을 지정세션은 스스로 DB에 연결하지 않고 엔진의 풀에서 빌려 쓴다
autoflush=False쿼리 직전에 장바구니 내용을 자동으로 flush하는 기능을 끔commit()도 안 불렀는데 INSERT가 나가면 흐름을 따라가기 어렵다. 다만 대가가 있다 — 아직 flush 안 된 내 변경을 쿼리가 못 본다. (공식 권장이 아니라 선택)
expire_on_commit=Falsecommit() 후에도 이미 읽어 둔 객체 값을 유효하게 유지기본값(True)이면 commit 직후 객체 값을 "낡았을지 모른다"고 표시(만료)해, todo.title만 읽어도 DB를 다시 조회한다. 세션이 이미 닫힌 뒤라면 에러

④ get_db — 세션은 여기서 닫힌다

FastAPI에서는 라우트마다 세션을 만들고 닫는 코드를 반복하지 않고, 의존성(Depends)으로 주입받습니다. 그 의존성 함수가 get_db입니다.

python
def get_db():
    db = SessionLocal()   # ① 세션 생성 (곧 풀에서 연결을 빌린다)
    try:
        yield db          # ② 라우트 함수에 넘겨주고 "여기서 잠깐 멈춤"
    finally:
        db.close()        # ③ 응답이 나간 뒤 실행 → 연결을 풀로 반납

왜 return이 아니라 yield인지, FastAPI가 응답을 보낸 뒤 finally를 어떻게 실행해 주는지는 Week 6·02 yield 의존성에서 자세히 다룹니다. 여기서 기억할 건 하나입니다 — 라우트가 정상 종료하든 에러가 나든 세션은 이 finally에서 닫히고, 그때 연결이 풀로 반납됩니다. close()가 빠지면 그 연결은 영원히 "사용 중"으로 남아 풀이 바닥나므로(연결 누수), 세션은 항상 Depends(get_db)나 with Session(engine) as s:처럼 닫힘이 보장되는 방식으로 씁니다.

메서드역할장바구니로 치면
session.add(obj)새 객체를 세션에 등록 (아직 DB 반영 X)장바구니에 담기
session.flush()SQL은 내보내되 확정하지는 않음계산대에 목록 보여주기
session.commit()모은 변경을 트랜잭션으로 확정결제 버튼
session.rollback()확정 전 변경을 전부 취소장바구니 비우기
session.refresh(obj)DB가 채워 준 값(id·created_at)을 다시 읽어옴. "생성 API가 id: null을 반환한다"면 대개 이걸 빠뜨린 경우영수증 받아 확인하기
session.close()세션 종료 + 연결을 풀로 반납매장에서 나가기
왜 commit()을 빠뜨리면 데이터가 사라질까. SQLAlchemy 문서에 답이 있습니다 — 연결이 풀로 반납될 때 트랜잭션 상태도 함께 롤백됩니다. 즉 add()만 하고 commit() 없이 요청이 끝나면, get_db의 close()가 연결을 반납하면서 내 변경을 조용히 되돌립니다. 에러도 안 나고 로그도 안 남으니 "분명 저장했는데 DB에 없다"는 상황이 됩니다. 초보가 가장 자주 만나는 함정입니다.

결과 꺼내기

select(Todo)를 쓴 순간에는 DB에 아무 일도 일어나지 않습니다. 이건 그냥 "할 일 목록 전부 주세요"라고 적은 주문서 한 장일 뿐이에요. 그래서 변수에 담아 두고 .where(), .order_by()를 계속 덧붙일 수 있습니다. 주문서를 실제로 창구에 내미는 순간이 execute()이고, 그때 비로소 SQL이 DB로 날아갑니다. 그리고 돌아온 결과 꾸러미에서 원하는 모양으로 꺼내는 것이 fetch입니다.

② Row vs 객체 — scalars()가 하는 일

execute()가 돌려주는 결과는 표입니다. 한 줄 한 줄이 Row이고, Row 안에는 칸(컬럼)이 여러 개 들어 있습니다. 그런데 select(Todo)처럼 엔티티 하나만 골랐다면 각 Row에는 칸이 딱 하나뿐이고, 그 안에 Todo 객체가 들어 있습니다. 이때 Row째로 받으면 row[0].title처럼 매번 첫 칸을 꺼내야 해서 번거롭죠. scalars()는 "각 줄의 첫 칸만 꺼내 줘"라는 뜻이라, 칸이 하나뿐인 표를 그냥 객체 리스트로 펴 줍니다. 그래서 곧바로 todo.title처럼 쓸 수 있습니다.

python
from sqlalchemy import select
from models import Todo

stmt = select(Todo).order_by(Todo.id)   # ① 주문서 (아직 DB에 안 감)

todos = db.scalars(stmt).all()          # ② + ③ 한 번에 — Todo 객체 리스트
for todo in todos:
    print(todo.title)                   # 바로 객체로 다룬다

# 같은 일을 풀어서 쓰면
result = db.execute(stmt)               # ② 실행 → 결과 꾸러미(Result)
todos = result.scalars().all()          # ③ 첫 칸만 꺼내 리스트로

# 여러 컬럼을 고르면 scalars() 없이 Row로 받는다
rows = db.execute(select(Todo.id, Todo.title)).all()
for todo_id, title in rows:             # Row는 튜플처럼 풀어 쓴다
    print(todo_id, title)

③ 몇 개를 꺼낼 것인가 — fetch 메서드

마지막 단계에서 붙이는 .all(), .first() 같은 메서드가 "결과를 어떤 모양으로 받을지"를 정합니다.

메서드결과없거나 여러 개면
.all()전부 리스트로없으면 빈 리스트 []
.first()맨 앞 하나만 (나머지 행은 버림)없으면 None (여러 개여도 조용히 첫 개)
.one()정확히 하나없거나 2개 이상이면 예외
.one_or_none()하나 또는 None2개 이상이면 예외
실무 감각. "이메일로 사용자 한 명 찾기"처럼 유일해야 마땅한 조회에는 .one_or_none()이 좋습니다. 데이터가 두 개 나오면 조용히 첫 개를 쓰는 대신 예외로 알려 주니, 중복 데이터 버그를 초기에 잡을 수 있습니다. 참고로 단순히 PK로 하나 찾기는 db.get(Todo, todo_id)가 가장 간단합니다.
🛡️

bind 변수 — 값을 "끼워 넣지" 말고 "바인딩"하라

① 사고가 나는 장면을 천천히 보기

검색 API를 만든다고 해 봅시다. 사용자가 입력한 검색어 q를 넣어 SQL을 만들어야 하니, 파이썬에서 가장 익숙한 f-string으로 문자열을 이어 붙였습니다.

python
q = "우유"
sql = f"SELECT * FROM todos WHERE title = '{q}'"
# → SELECT * FROM todos WHERE title = '우유'      ✅ 의도대로 동작

q = "' OR '1'='1"                    # 😈 공격자가 이렇게 입력하면
sql = f"SELECT * FROM todos WHERE title = '{q}'"
# → SELECT * FROM todos WHERE title = '' OR '1'='1'
#                                        ↑ 여기서 문자열이 끝나 버리고
#                                          뒤가 "조건문"으로 승격된다

공격자가 넣은 작은따옴표 하나가 문자열을 조기에 끝내 버렸고, 그 뒤의 OR '1'='1이 데이터가 아니라 SQL 문법으로 읽혔습니다. '1'='1'은 항상 참이니 모든 행이 조회됩니다. 같은 수법으로 로그인 조건을 우회하거나, 더 심하면 다른 테이블 내용까지 꺼낼 수 있습니다. 이것이 SQL Injection입니다.

핵심은 "값이 문법으로 승격됐다"는 것. 문자열을 이어 붙이는 순간, 사용자 입력과 SQL 문법이 구분 없이 한 덩어리 문장이 됩니다. DB는 그 문장을 통째로 받아 해석하므로, 어디까지가 내가 쓴 코드고 어디부터가 남이 넣은 값인지 구분할 방법이 없습니다.

② 그래서 바인딩이 왜 안전한가

해결책은 문장과 값을 아예 따로 보내는 것입니다. SQL에는 값을 넣을 자리에 :q 같은 빈칸 표시만 남기고, 실제 값은 따로 함께 보냅니다. 그러면 DB는 문장 구조를 먼저 확정한 다음 빈칸에 값을 순수한 데이터로 끼워 넣습니다. 구조가 이미 정해진 뒤에 값이 들어오므로, 값 안에 따옴표가 있든 OR 1=1이 있든 문법으로 승격될 기회 자체가 없습니다.

비유 — 빈칸 채우기 시험지. "제목이   ____   인 할 일을 찾아라"라는 문제 문장은 이미 인쇄되어 있습니다. 학생이 빈칸에 무엇을 적든 — 심지어 "그리고 전부 다 보여줘"라고 적더라도 — 그건 빈칸에 적힌 답일 뿐 문제 자체를 바꾸지는 못합니다. 반대로 f-string은 학생이 문제 문장까지 직접 쓰게 두는 것과 같습니다.

코드로 보면 이렇습니다. 아래의 text()는 raw SQL 문자열을 SQLAlchemy에 넘길 때 감싸는 포장지이고, 그 안의 :q가 빈칸 표시입니다. select(Todo).where(Todo.title == q) 같은 ORM 표현식은 SQLAlchemy가 알아서 바인딩하므로, 위험은 거의 항상 raw SQL을 f-string으로 직접 조립할 때 생깁니다.

위험 — 문자열 포매팅 (절대 금지)
# ❌ 사용자 입력을 그대로 이어붙임
q = request_query
sql = text(
  f"SELECT * FROM todos "
  f"WHERE title = '{q}'"
)
db.execute(sql)
# q = "' OR '1'='1"  →  전체 노출!
안전 — bind 변수 바인딩
from sqlalchemy import select
from sqlalchemy import text

# ✅ 값을 파라미터로 따로 전달
# 1) ORM 표현식은 자동 바인딩
select(Todo).where(
  Todo.title == q
)

# 2) raw SQL도 :param 으로
db.execute(
  text("SELECT * FROM todos "
       "WHERE title = :q"),
  {"q": q},   # 데이터로 취급
)
언어가 달라도 규칙은 같습니다. NestJS의 TypeORM도 .where('t.title = :q', { q })처럼 똑같은 :q 바인딩 문법을 쓰고, 반대로 .where(`t.title = '${q}'`)처럼 백틱 템플릿 리터럴로 조건문을 조립하면 그대로 뚫립니다. 파이썬의 f-string과 자바스크립트의 백틱은 완전히 같은 함정입니다 — 값은 문장에 붙이지 말고 따로 넘긴다.
바인딩할 수 있는 건 "값"뿐입니다. :q 자리에는 제목·숫자·날짜 같은 값만 들어갈 수 있고, 테이블명이나 컬럼명은 바인딩되지 않습니다(문장 구조에 해당하니까요). 정렬 컬럼을 사용자가 고르게 하고 싶다면, 입력을 그대로 SQL에 넣지 말고 미리 정해 둔 허용 목록에서 골라 쓰세요. 예: {"title": Todo.title, "id": Todo.id}[key]

전체 흐름 한눈에

지금까지의 조각을 하나의 엔드포인트로 모으면 이렇습니다. 코드는 세 줄이지만, 그 뒤에서 벌어지는 일은 아래 여섯 단계입니다.

python
from fastapi import Depends, FastAPI
from sqlalchemy import select
from sqlalchemy.orm import Session
from database import get_db
from models import Todo

app = FastAPI()

@app.get("/todos")
def list_todos(db: Session = Depends(get_db)):
    return db.scalars(select(Todo).order_by(Todo.id)).all()
1
GET /todos 요청 도착. FastAPI가 Depends(get_db)를 보고 get_db를 먼저 실행합니다.
2
SessionLocal()로 세션(장바구니)이 생성되고, yield db로 라우트 함수에 전달됩니다.
3
첫 쿼리가 실행되는 순간 세션이 풀에서 연결 하나를 빌립니다. (이미 연결·인증이 끝난 상태라 즉시)
4
select(Todo)가 SQL로 번역되어 실행되고, scalars().all()로 Todo 객체 리스트를 받습니다. 값은 모두 bind 변수로 안전하게 전달됩니다.
5
반환된 객체를 FastAPI가 JSON으로 직렬화해 응답합니다. 이 예시는 조회 전용이라 commit()이 없고, 세션도 아직 열려 있어 값을 그대로 읽습니다. (expire_on_commit=False가 실제로 필요해지는 곳은 commit한 뒤 그 객체를 반환하는 생성·수정 엔드포인트입니다.)
6
응답이 나간 뒤 get_db의 finally가 실행되어 db.close() → 연결이 풀로 반납되고 다음 요청이 재사용합니다.

NestJS로 치면 — 한눈에 대응표

NestJS를 하다 오면 여기서 가장 크게 당황합니다. NestJS에는 commit()도 close()도 안 보였기 때문입니다. 같은 "할 일 하나 만들기"를 양쪽으로 써 보면 차이가 분명해집니다.

NestJS — Repository 주입
constructor(
  @InjectRepository(Todo)
  private repo: Repository<Todo>,
) {}

async create(dto: CreateDto) {
  const todo =
    this.repo.create(dto);
  return this.repo.save(todo);
  // save가 곧 반영 + 반납
}
FastAPI — Session 주입
def create(
    dto,
    db: Session = Depends(get_db)
):
    data = dto.model_dump()
    todo = Todo(**data)
    db.add(todo)      # 장바구니
    db.commit()       # 결제
    db.refresh(todo)  # id 채우기
    return todo
    # close는 get_db가 책임

TypeORM은 "한 건씩 바로 처리"가 기본이라 save()가 곧 확정이고, 연결도 쿼리마다 자동으로 빌리고 돌려줍니다. SQLAlchemy는 "일단 다 모았다가 결제"가 기본이라 트랜잭션이 공짜로 딸려오는 대신 commit()과 close()를 내가 챙깁니다. NestJS에서 프레임워크가 숨겨 주던 연결·트랜잭션·반납이 여기서는 내 코드에 드러나 있을 뿐, 일어나는 일은 같습니다.

셀프 체크

Q Connection Pool은 왜 필요한가요?

연결을 맺는 준비(접속·인증)가 쿼리보다 훨씬 비싸고, PostgreSQL은 연결마다 서버 프로세스를 하나씩 띄우기 때문입니다. 그래서 연결을 만들어 두고 빌려 쓰고 반납합니다.

Q pool_size=5, max_overflow=10인데 동시 요청이 20개면?

최대 15개(5+10)까지만 연결이 열리고, 나머지 5개는 에러 없이 줄을 섭니다. 30초(pool_timeout) 안에 자리가 나면 정상 처리되고, 넘기면 TimeoutError입니다.

Q db.add(todo)만 하고 commit() 없이 요청이 끝나면 어떻게 되나요?

get_db의 close()가 연결을 반납하면서 트랜잭션이 롤백되어, 에러 없이 조용히 사라집니다. TypeORM의 save()에는 커밋이 숨어 있었지만 SQLAlchemy는 commit()이 곧 결제 버튼이라 내가 눌러야 합니다.

Q bind 변수는 왜 SQL Injection을 막나요?

문장과 값을 따로 보내서, DB가 문장 구조를 먼저 확정한 뒤 값을 순수 데이터로 끼워 넣기 때문입니다. 값 안에 따옴표나 OR 1=1이 있어도 문법으로 승격될 기회가 없습니다.
