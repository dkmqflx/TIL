Connection Pool · Session 그리고 안전한 쿼리

DB에 말을 걸려면 먼저 연결이 필요하고, 그 연결은 비쌉니다. 그래서 미리 만들어 돌려 쓰는 Connection Pool, 작업을 묶는 Session, 그리고 값을 안전하게 넘기는 bind 변수까지 — DB를 실제로 다루는 마지막 조각들입니다. 각 절 끝에서 NestJS + TypeORM과 나란히 비교합니다.

한 줄 요약. DB 연결은 전화를 거는 것과 같아서 매번 새로 걸기엔 비싸다. 그래서 미리 몇 개 걸어 두고(pool) 빌려 쓰고 반납한다. 그 연결 위에서 하는 작업 한 묶음이 Session(장바구니)이고, 결제 버튼이 commit이다. 값은 문자열로 잇지 말고 bind 변수로 따로 전달해 인젝션을 막는다.

학습 목표

  • "DB 연결"이 정확히 무엇이고 왜 비싼지 설명할 수 있다
  • Connection Pool이 왜 필요한지와 파라미터 4개의 의미를 안다
  • Session(장바구니)으로 작업을 묶고 commit / close 한다
  • select → execute → fetch의 3단계를 구분해 결과를 꺼낸다
  • bind 변수가 왜 SQL Injection을 막는지 원리로 설명한다
  • 각 개념을 NestJS + TypeORM의 무엇과 대응시킬 수 있다
🔄

Connection Pool — 연결을 재사용하기

① 그래서 "연결(connection)"이 뭔가요?

가장 먼저 짚고 갈 것이 있습니다. PostgreSQL은 내 파이썬 코드 안에 들어 있는 게 아닙니다. 완전히 별개의 프로그램이고, 보통 다른 컨테이너나 아예 다른 서버에서 혼자 돌아가고 있습니다. 즉 내 코드와 DB는 서로 남남인 두 프로그램이에요. 남남끼리 대화하려면 먼저 말을 주고받을 통로를 하나 뚫어야 합니다. 그 통로 하나가 바로 연결(connection)입니다.

비유 — 전화 걸기. 친구에게 용건을 말하려면 먼저 전화를 걸어야 합니다. 번호를 누르고(주소로 접속), 신호가 가고 상대가 받고(TCP 핸드셰이크), "저 도현인데요, 비밀번호는 ○○예요" 하고 신원을 확인받습니다(인증). 이 준비 과정이 다 끝나야 비로소 "어제 그 파일 좀" 이라는 본론(쿼리)을 말할 수 있죠. 문제는 준비가 본론보다 훨씬 오래 걸린다는 겁니다.

② 매번 새로 연결하면 무슨 일이 생기나

정확한 수치는 환경마다 다르지만 감을 잡아 보면, 연결을 새로 맺는 데는 보통 수 ms에서 수십 ms가 걸립니다. 반면 SELECT * FROM todos 같은 가벼운 쿼리는 1ms 안팎이면 끝납니다. 즉 준비에 30, 본론에 1을 쓰는 셈입니다. 전화를 걸고 인사만 나눈 뒤 바로 끊고, 다음 질문을 하려고 또 전화를 거는 것과 같습니다.

요청이 초당 수백 개씩 들어오는 서버라면 이 낭비가 그대로 누적됩니다. 게다가 PostgreSQL은 연결 하나마다 서버 쪽에서도 프로세스와 메모리를 하나씩 잡습니다. 연결을 마구 만들면 느려지는 정도가 아니라 DB 자체가 버티지 못합니다.

③ 해결책 — 미리 만들어 두고 돌려 쓴다

그래서 나온 방법이 단순합니다. 연결을 몇 개 미리 만들어 두고, 요청이 오면 그중 하나를 빌려주고, 일이 끝나면 끊지 말고 돌려받는 것입니다. 이 "미리 만들어 둔 연결 보관함"이 Connection Pool입니다. 전화 비유로 하면, 통화를 끊지 않고 수화기를 내려놓았다가 다음 사람이 그대로 이어 쓰는 셈이죠.

비유 — 콜택시 대기열. 손님(요청)이 올 때마다 새 택시를 사는 것은 미친 짓입니다. 대신 회사는 택시 몇 대를 대기열(pool)에 세워 둡니다. 손님이 오면 대기 중인 택시를 배차(빌림)하고, 목적지에 도착하면 택시는 다시 대기열로 복귀(반납)합니다. 손님이 몰리면 임시 차량을 더 부르고(max_overflow), 그래도 모자라면 손님은 줄을 서서 기다립니다. 중요한 건 택시를 폐차하지 않는다는 점이에요.
1
앱이 뜰 때 풀이 만들어집니다. (연결은 첫 요청 때부터 필요한 만큼 채워집니다.)
2
요청이 들어오면 풀에서 놀고 있는 연결 하나를 빌립니다(checkout). 이미 연결·인증이 끝난 상태라 기다림이 거의 0입니다.
3
그 연결로 쿼리를 주고받습니다. 이 연결은 그동안 나만 씁니다(다른 요청과 공유되지 않음).
4
작업이 끝나면 close()로 반납(checkin)합니다. 여기서 close()는 "연결을 끊는다"가 아니라 "다 썼으니 풀에 돌려놓는다"는 뜻입니다. ← 헷갈리기 쉬운 지점

④ 파라미터 네 개 뜯어보기

풀은 create_engine에 옵션으로 설정합니다. 이름만 보면 어렵지만, 전부 택시 회사 운영 규칙이라고 생각하면 쉽습니다.

python
engine = create_engine(
    DATABASE_URL,
    pool_size=5,        # 상시 대기 5대
    max_overflow=10,    # 피크 때 임시로 +10대까지
    pool_recycle=1800,  # 30분 넘게 산 연결은 폐차하고 새로
    pool_pre_ping=True, # 배차 전 시동 걸어보기
)
파라미터의미택시 회사로 치면
pool_size평상시 유지하는 연결 수 (기본 5)상시 대기 택시 대수
max_overflow몰릴 때 추가로 허용하는 한도 (기본 10)피크 때만 부르는 임시 콜 한도
pool_recycle지정한 초가 지난 연결은 버리고 새로 만듦오래된 차 교체 주기
pool_pre_ping빌려주기 직전에 "살아있니?" 한 번 확인배차 전 시동 확인

pool_size와 max_overflow는 짝입니다. 위 설정이면 동시에 열릴 수 있는 연결은 최대 5 + 10 = 15개입니다. 상시 5대는 계속 대기열에 남아 있지만, 임시로 부른 10대는 일이 끝나면 대기열에 남지 않고 해산합니다(진짜로 연결이 닫힙니다). 그래서 "평소엔 5개만 유지, 몰릴 때만 잠깐 15개까지"라는 뜻이 됩니다.

15개도 다 차면 어떻게 되나요? 새 요청은 에러가 나는 게 아니라 줄을 서서 기다립니다. 그리고 기본값 30초(pool_timeout)를 넘겨도 자리가 안 나면 그때 TimeoutError가 납니다. 그래서 "API가 갑자기 30초씩 느려지다가 터진다"면 연결을 반납하지 않은 코드를 가장 먼저 의심해야 합니다.

pool_recycle이 필요한 이유는 조금 뜻밖입니다. 내 쪽에서는 연결을 잘 들고 있어도, 중간의 방화벽·로드밸런서나 DB 서버가 "오래 조용한 연결"을 몰래 끊어 버리는 일이 흔합니다. 그러면 풀에는 겉보기엔 멀쩡하지만 실제로는 죽은 연결이 남고, 하필 그걸 빌려 간 요청이 에러를 뱉습니다. 그래서 "일정 시간 지난 연결은 어차피 버리고 새로 만들자"고 정해 두는 겁니다. pool_pre_ping=True는 여기에 안전장치를 하나 더 겁니다. 빌려주기 직전에 아주 가벼운 확인 쿼리를 날려 보고, 응답이 없으면 그 연결을 조용히 버리고 새 연결을 대신 내줍니다. 비용이 거의 없으니 켜 두는 걸 권장합니다.

요청은 풀에서 연결을 빌려 쓰고, 끝나면 반납한다. 매번 새로 맺지 않아 빠르다.
좋은 소식. 이 풀은 create_engine()만 호출하면 SQLAlchemy가 알아서 만들고 관리합니다. 우리가 할 일은 빌린 걸 반드시 반납하는 것뿐이고, 그 반납을 담당하는 게 바로 다음에 나오는 Session의 close()입니다.

⑤ NestJS와 나란히 — 사실 이미 쓰고 있었다

NestJS에서 TypeOrmModule.forRoot({...})를 적을 때도 똑같은 풀이 만들어지고 있었습니다. 다만 기본값에 가려져 신경 쓸 일이 없었을 뿐이에요.

NestJS — TypeOrmModule
TypeOrmModule.forRoot({
  type: 'postgres',
  url: process.env.DATABASE_URL,
  poolSize: 15,   // 최대 15개
  extra: {
    idleTimeoutMillis: 30000,
  },
})
FastAPI — create_engine
engine = create_engine(
    DATABASE_URL,
    pool_size=5,        # 상시 5
    max_overflow=10,    # +10까지
    pool_recycle=1800,
    pool_pre_ping=True,
)
차이 하나. TypeORM은 드라이버(node-postgres) 풀을 그대로 쓰기 때문에 poolSize로 상한 하나만 정합니다. 반면 SQLAlchemy는 상시(pool_size) + 임시(max_overflow)로 나눠 두고, pool_recycle·pool_pre_ping처럼 죽은 연결을 걸러내는 옵션까지 이름을 붙여 노출합니다. 개념이 다른 게 아니라 손잡이가 더 잘게 나뉘어 있는 것뿐입니다.

Session — 작업 단위(Unit of Work)

① Session은 "장바구니"다

풀에서 연결을 빌렸다고 바로 SQL을 쓰지는 않습니다. 그 연결 위에서 한 덩어리의 작업을 담아 두는 그릇이 필요한데, 그게 Session입니다. 교과서에서는 Unit of Work(작업 단위)라는 어려운 이름으로 부르지만, 온라인 쇼핑 장바구니라고 생각하면 한 번에 이해됩니다.

비유 — 쇼핑 장바구니. 상품을 장바구니에 담는다고 결제가 되지는 않습니다. 여러 개를 담고 빼고 하다가, 결제 버튼을 눌러야 비로소 주문이 확정되죠. Session도 똑같습니다. session.add(todo)는 장바구니에 담기일 뿐 DB에는 아직 아무 일도 없고, session.commit()이 결제 버튼입니다. 마음이 바뀌면 session.rollback()으로 장바구니를 통째로 비울 수도 있습니다.

② 왜 굳이 모았다가 한 번에 반영할까 — 트랜잭션

"그냥 하나씩 바로 저장하면 안 되나?" 싶지만, 모아서 처리해야만 하는 상황이 있습니다. 계좌 이체를 떠올려 보세요. "A에서 1만 원 빼기"와 "B에 1만 원 넣기"는 반드시 둘 다 되거나, 둘 다 안 되어야 합니다. 빼기만 성공하고 넣기가 실패하면 돈이 공중분해되니까요.

이렇게 여러 작업을 "전부 성공 아니면 전부 취소"로 묶는 단위를 트랜잭션이라고 합니다. Session은 한 번의 commit()까지 쌓인 변경들을 하나의 트랜잭션으로 처리합니다. 중간에 에러가 나면 rollback()으로 전부 없던 일이 되고요. 장바구니 비유로 하면 "결제는 전체 금액에 대해 한 번에 승인되거나 한 번에 거절된다"는 것과 같습니다.

③ 코드 한 줄씩 — sessionmaker

Session은 요청마다 새로 만들어야 하는데, 매번 옵션을 적기 번거롭습니다. 그래서 세션 찍어내는 틀(공장)을 하나 만들어 두고 씁니다. 그게 sessionmaker입니다. 붕어빵 틀을 한 번 만들어 두고 계속 찍어내는 것과 같아요.

python
from sqlalchemy.orm import Session, sessionmaker

SessionLocal = sessionmaker(       # ← 세션을 찍어내는 "틀"
    bind=engine,                   # 이 엔진의 풀에서 연결을 빌려라
    autoflush=False,               # 몰래 미리 내보내지 마라
    expire_on_commit=False,        # commit 후에도 객체 값을 그대로 두라
)

db = SessionLocal()                # ← 여기서 세션 하나가 만들어진다
옵션무슨 뜻인가왜 이렇게 두나
bind=engine이 세션이 사용할 엔진(=연결 풀)을 지정세션은 스스로 DB에 연결하지 않고, 엔진의 풀에서 빌려 쓴다
autoflush=False쿼리 직전에 장바구니 내용을 DB로 미리 밀어 보내는 기능을 끔내가 commit()을 부르지도 않았는데 INSERT가 나가면 흐름을 따라가기 어렵다. 초보일수록 꺼 두는 게 예측 가능하다
expire_on_commit=Falsecommit() 후에도 이미 읽어 둔 객체 값을 유효하게 유지기본값(True)이면 commit 직후 todo.title만 읽어도 DB를 다시 조회한다. 세션이 이미 닫힌 뒤라면 에러까지 난다
flush와 commit은 다릅니다. flush는 "장바구니 목록을 계산대 직원에게 보여주는 것"입니다. INSERT/UPDATE 문이 DB로 나가서 임시로 반영되고 id 같은 값도 생기지만, 아직 확정은 아니라 rollback하면 사라집니다. commit이 "결제 완료"고, 이때부터 다른 사람 눈에도 보입니다. (commit()은 내부적으로 flush를 먼저 하고 확정합니다.)

④ get_db — 왜 return이 아니라 yield인가

FastAPI에서는 라우트마다 세션을 만들고 닫는 코드를 반복하지 않고, 의존성(Depends)으로 주입받습니다. 그 의존성 함수가 get_db입니다.

python
def get_db():
    db = SessionLocal()   # ① 세션 생성 (곧 풀에서 연결을 빌린다)
    try:
        yield db          # ② 라우트 함수에 넘겨주고 "여기서 잠깐 멈춤"
    finally:
        db.close()        # ③ 응답이 나간 뒤 실행 → 연결을 풀로 반납

return db였다면 함수는 그 자리에서 완전히 끝나 버려서, 뒤에 close()를 붙일 자리가 없습니다. yield는 "값을 건네주고 일시정지"라는 뜻이라, FastAPI가 라우트 처리를 다 마치고 응답을 보낸 뒤에 멈춰 있던 지점으로 돌아와 나머지(finally)를 실행해 줍니다. 덕분에 라우트에서 에러가 터지든 정상 종료하든 세션은 반드시 닫힙니다.

비유 — 도서관 대출 창구. SessionLocal()은 책을 빌려주는 것, yield db는 "자, 읽으세요" 하고 기다리는 것, finally: db.close()는 반납 확인입니다. 창구 직원은 당신이 책을 다 읽을 때까지 자리를 뜨지 않고, 반납을 받아야 일과를 마칩니다. 반납이 없으면 서가(풀)의 책이 계속 줄어들죠.
반납을 잊으면 — 연결 누수(leak). close()가 빠지면 그 연결은 영원히 "사용 중"으로 남습니다. 요청이 쌓일수록 대기열이 비고, 결국 모든 요청이 30초씩 기다리다 타임아웃 납니다. 그래서 세션은 항상 Depends(get_db)나 with Session(engine) as s: 형태로 닫힘이 보장되는 방식으로 씁니다.
메서드역할장바구니로 치면
session.add(obj)새 객체를 세션에 등록 (아직 DB 반영 X)장바구니에 담기
session.flush()SQL은 내보내되 확정하지는 않음계산대에 목록 보여주기
session.commit()모은 변경을 트랜잭션으로 확정결제 버튼
session.rollback()확정 전 변경을 전부 취소장바구니 비우기
session.refresh(obj)DB가 채워 준 값(id·created_at)을 다시 읽어옴영수증 받아 확인하기
session.close()세션 종료 + 연결을 풀로 반납매장에서 나가기
refresh가 필요한 순간. id나 created_at처럼 DB가 직접 만들어 주는 값은 파이썬 객체에는 없습니다. commit() 뒤 session.refresh(todo)를 부르면 그 값들을 DB에서 다시 읽어와 객체에 채워 줍니다. "생성 API가 id: null을 반환한다"면 대개 이걸 빠뜨린 경우입니다.

⑤ NestJS와 나란히 — Repository와 Session

NestJS를 하다 오면 여기서 가장 크게 당황합니다. NestJS에는 commit()도 close()도 안 보였기 때문입니다. 같은 "할 일 하나 만들기"를 양쪽으로 써 보면 차이가 분명해집니다.

NestJS — Repository 주입
constructor(
  @InjectRepository(Todo)
  private repo: Repository<Todo>,
) {}

async create(dto: CreateDto) {
  const todo =
    this.repo.create(dto);
  return this.repo.save(todo);
  // save가 곧 반영 + 반납
}
FastAPI — Session 주입
def create(
    dto,
    db: Session = Depends(get_db)
):
    data = dto.model_dump()
    todo = Todo(**data)
    db.add(todo)      # 장바구니
    db.commit()       # 결제
    db.refresh(todo)  # id 채우기
    return todo
    # close는 get_db가 책임
질문NestJS + TypeORMFastAPI + SQLAlchemy
무엇을 주입받나Repository<Todo> — 엔티티별 창구Session — 요청 하나짜리 장바구니
저장은 언제 반영되나repo.save() 호출 즉시db.commit()을 불러야 확정
값을 바꾸면todo.title = 'x' 후 save()를 또 불러야 반영세션이 변경을 추적해 commit()만 해도 UPDATE
트랜잭션으로 묶으려면dataSource.transaction(...)을 따로 씀세션이 이미 트랜잭션 — commit / rollback
연결 반납은 누가쿼리마다 자동으로 빌리고 돌려줌get_db의 finally: close()
한 문장 정리. TypeORM은 "한 건씩 바로 처리"가 기본이라 편한 대신, 여러 작업을 묶으려면 트랜잭션을 따로 열어야 합니다. SQLAlchemy는 반대로 "일단 다 모았다가 결제"가 기본이라 트랜잭션이 공짜로 딸려오는 대신, commit()과 close()를 내가 챙겨야 합니다. NestJS에서 save()를 빠뜨린 경험이 있다면, 여기서는 그게 commit()이라고 생각하면 됩니다.

결과 꺼내기

select(Todo)를 쓴 순간에는 DB에 아무 일도 일어나지 않습니다. 이건 그냥 "할 일 목록 전부 주세요"라고 적은 주문서 한 장일 뿐이에요. 그래서 변수에 담아 두고 .where(), .order_by()를 계속 덧붙일 수 있습니다. 주문서를 실제로 창구에 내미는 순간이 execute()이고, 그때 비로소 SQL이 DB로 날아갑니다. 그리고 돌아온 결과 꾸러미에서 원하는 모양으로 꺼내는 것이 fetch입니다.

② Row vs 객체 — scalars()가 하는 일

execute()가 돌려주는 결과는 엑셀 표라고 생각하면 됩니다. 한 줄 한 줄이 Row이고, Row 안에는 칸(컬럼)이 여러 개 들어 있습니다. 그런데 select(Todo)처럼 엔티티 하나만 골랐다면, 각 Row에는 칸이 딱 하나뿐이고 그 안에 Todo 객체가 들어 있습니다.

이때 Row째로 받으면 row[0].title처럼 매번 첫 칸을 꺼내야 해서 번거롭습니다. scalars()는 "각 줄의 첫 칸만 꺼내 줘"라는 뜻이고, 그래서 곧바로 todo.title처럼 쓸 수 있게 됩니다. 칸이 하나뿐인 표를 그냥 리스트로 펴 주는 것이라고 보면 됩니다.

python
from sqlalchemy import select
from models import Todo

stmt = select(Todo).order_by(Todo.id)   # ① 주문서 (아직 DB에 안 감)

todos = db.scalars(stmt).all()          # ② + ③ 한 번에 — Todo 객체 리스트
for todo in todos:
    print(todo.title)                   # 바로 객체로 다룬다

# 같은 일을 풀어서 쓰면
result = db.execute(stmt)               # ② 실행 → 결과 꾸러미(Result)
todos = result.scalars().all()          # ③ 첫 칸만 꺼내 리스트로

# 여러 컬럼을 고르면 scalars() 없이 Row로 받는다
rows = db.execute(select(Todo.id, Todo.title)).all()
for todo_id, title in rows:             # Row는 튜플처럼 풀어 쓴다
    print(todo_id, title)

③ 몇 개를 꺼낼 것인가 — fetch 메서드

마지막 단계에서 붙이는 .all(), .first() 같은 메서드가 "결과를 어떤 모양으로 받을지"를 정합니다.

메서드결과없거나 여러 개면
.all()전부 리스트로없으면 빈 리스트 []
.first()맨 앞 하나만없으면 None (여러 개여도 조용히 첫 개)
.one()정확히 하나없거나 2개 이상이면 예외
.one_or_none()하나 또는 None2개 이상이면 예외
실무 감각. "이메일로 사용자 한 명 찾기"처럼 유일해야 마땅한 조회에는 .one_or_none()이 좋습니다. 데이터가 두 개 나오면 조용히 첫 개를 쓰는 대신 예외로 알려 주니, 중복 데이터 버그를 초기에 잡을 수 있습니다. 참고로 단순히 PK로 하나 찾기는 db.get(Todo, todo_id)가 가장 간단합니다.

④ NestJS와 나란히 — 이름만 바뀐 것들

TypeORM의 find 계열 메서드를 그대로 옮겨 놓으면 이렇게 대응됩니다. 하는 일은 거의 같고, 이름과 조립 방식만 다릅니다.

하고 싶은 일NestJS + TypeORMFastAPI + SQLAlchemy 2.0

왜 TypeORM엔 scalars() 같은 게 없을까? repo.find()는 애초에 Todo 엔티티만 돌려주기로 약속된 메서드라 꺼낼 게 없습니다. 반면 SQLAlchemy의 execute()는 SQL이라면 뭐든 실행하는 범용 창구여서 결과가 항상 표(Row) 모양입니다. 그래서 "엔티티 하나만 골랐으니 첫 칸을 펴 줘"라고 한 번 더 말해 주는 단계가 필요한 것이고, 그게 scalars()입니다. NestJS의 repo.query()가 엔티티가 아닌 raw 결과를 주는 것과 같은 결의 이야기입니다.
🛡️

bind 변수 — 값을 "끼워 넣지" 말고 "바인딩"하라

① 사고가 나는 장면을 천천히 보기

검색 API를 만든다고 해 봅시다. 사용자가 입력한 검색어 q를 넣어 SQL을 만들어야 하니, 파이썬에서 가장 익숙한 f-string으로 문자열을 이어 붙였습니다.

python
q = "우유"
sql = f"SELECT * FROM todos WHERE title = '{q}'"
# → SELECT * FROM todos WHERE title = '우유'      ✅ 의도대로 동작

q = "' OR '1'='1"                    # 😈 공격자가 이렇게 입력하면
sql = f"SELECT * FROM todos WHERE title = '{q}'"
# → SELECT * FROM todos WHERE title = '' OR '1'='1'
#                                        ↑ 여기서 문자열이 끝나 버리고
#                                          뒤가 "조건문"으로 승격된다

공격자가 넣은 작은따옴표 하나가 문자열을 조기에 끝내 버렸고, 그 뒤의 OR '1'='1이 데이터가 아니라 SQL 문법으로 읽혔습니다. '1'='1'은 항상 참이니 모든 행이 조회됩니다. 같은 수법으로 로그인 조건을 우회하거나, 더 심하면 다른 테이블 내용까지 꺼낼 수 있습니다. 이것이 SQL Injection입니다.

핵심은 "값이 문법으로 승격됐다"는 것. 문자열을 이어 붙이는 순간, 사용자 입력과 SQL 문법이 구분 없이 한 덩어리 문장이 됩니다. DB는 그 문장을 통째로 받아 해석하므로, 어디까지가 내가 쓴 코드고 어디부터가 남이 넣은 값인지 구분할 방법이 없습니다.

② 그래서 바인딩이 왜 안전한가

해결책은 문장과 값을 아예 따로 보내는 것입니다. SQL에는 값을 넣을 자리에 :q 같은 빈칸 표시만 남기고, 실제 값은 별도의 소포로 함께 보냅니다. 그러면 DB는 문장 구조를 먼저 확정한 다음 빈칸에 값을 순수한 데이터로 끼워 넣습니다. 구조가 이미 정해진 뒤에 값이 들어오므로, 값 안에 따옴표가 있든 OR 1=1이 있든 문법으로 승격될 기회 자체가 없습니다.

비유 — 빈칸 채우기 시험지. "제목이   ____   인 할 일을 찾아라"라는 문제 문장은 이미 인쇄되어 있습니다. 학생이 빈칸에 무엇을 적든 — 심지어 "그리고 전부 다 보여줘"라고 적더라도 — 그건 빈칸에 적힌 답일 뿐 문제 자체를 바꾸지는 못합니다. 반대로 f-string은 학생이 문제 문장까지 직접 쓰게 두는 것과 같습니다.
위험 — 문자열 포매팅 (절대 금지)
# ❌ 사용자 입력을 그대로 이어붙임
q = request_query
sql = text(
  f"SELECT * FROM todos "
  f"WHERE title = '{q}'"
)
db.execute(sql)
# q = "' OR '1'='1"  →  전체 노출!
안전 — bind 변수 바인딩
from sqlalchemy import select, text

# ✅ 값을 파라미터로 따로 전달
# 1) ORM은 기본이 바인딩
select(Todo).where(Todo.title == q)

# 2) raw SQL도 :param 으로
db.execute(
  text("SELECT * FROM todos "
       "WHERE title = :q"),
  {"q": q},   # 데이터로 취급
)
ORM을 쓰면 기본이 안전. select(Todo).where(Todo.title == q)처럼 ORM 표현식을 쓰면 SQLAlchemy가 자동으로 값을 바인딩합니다. 즉, 평소처럼 ORM으로 짜기만 해도 인젝션이 막힙니다. 위험은 거의 항상 raw SQL을 f-string으로 직접 조립할 때 생깁니다.

③ NestJS와 나란히 — :q 문법이 똑같다

반가운 소식이 있습니다. TypeORM의 QueryBuilder에서 쓰던 :q 이름 붙은 파라미터 문법이 SQLAlchemy에서도 그대로입니다. 개념도 같고 표기도 같으니, 사실상 새로 배울 게 없습니다.

NestJS — TypeORM
// ✅ QueryBuilder — :q 바인딩
this.repo
  .createQueryBuilder('t')
  .where('t.title = :q', { q })
  .getMany();

// ✅ raw는 $1 자리표시자
this.repo.query(
  'SELECT * FROM todos ' +
  'WHERE title = $1',
  [q],
);
FastAPI — SQLAlchemy
# ✅ ORM 표현식 — 자동 바인딩
select(Todo).where(
    Todo.title == q
)

# ✅ raw는 :q + 파라미터 dict
db.execute(
    text("SELECT * FROM todos "
         "WHERE title = :q"),
    {"q": q},
)
양쪽 다 똑같이 뚫립니다. QueryBuilder를 쓴다고 안전한 게 아닙니다. .where(`t.title = '${q}'`)처럼 템플릿 리터럴로 조건문을 조립하면 TypeORM에서도 그대로 인젝션이 됩니다. 파이썬의 f-string과 자바스크립트의 백틱은 여기서 완전히 같은 함정입니다. 규칙은 언어와 무관합니다 — 값은 문장에 붙이지 말고 따로 넘긴다.
바인딩할 수 있는 건 "값"뿐입니다. :q 자리에는 제목·숫자·날짜 같은 값만 들어갈 수 있고, 테이블명이나 컬럼명은 바인딩되지 않습니다(문장 구조에 해당하니까요). 정렬 컬럼을 사용자가 고르게 하고 싶다면, 입력을 그대로 SQL에 넣지 말고 미리 정해 둔 허용 목록에서 골라 쓰세요. 예: {"title": Todo.title, "id": Todo.id}[key]

전체 흐름 한눈에

지금까지의 조각을 하나의 엔드포인트로 모으면 이렇습니다. 코드는 세 줄이지만, 그 뒤에서 벌어지는 일은 아래 여섯 단계입니다.

python
from fastapi import Depends, FastAPI
from sqlalchemy import select
from sqlalchemy.orm import Session
from database import get_db
from models import Todo

app = FastAPI()

@app.get("/todos")
def list_todos(db: Session = Depends(get_db)):
    return db.scalars(select(Todo).order_by(Todo.id)).all()
1
GET /todos 요청 도착. FastAPI가 Depends(get_db)를 보고 get_db를 먼저 실행합니다.
2
SessionLocal()로 세션(장바구니)이 생성되고, yield db로 라우트 함수에 전달됩니다.
3
첫 쿼리가 실행되는 순간 세션이 풀에서 연결 하나를 빌립니다. (이미 연결·인증이 끝난 상태라 즉시)
4
select(Todo)가 SQL로 번역되어 실행되고, scalars().all()로 Todo 객체 리스트를 받습니다. 값은 모두 bind 변수로 안전하게 전달됩니다.
5
반환된 객체를 FastAPI가 JSON으로 직렬화해 응답합니다. (expire_on_commit=False 덕분에 이 시점에도 값을 안전하게 읽을 수 있습니다.)
6
응답이 나간 뒤 get_db의 finally가 실행되어 db.close() → 연결이 풀로 반납되고 다음 요청이 재사용합니다.

셀프 체크

Q Connection Pool은 왜 필요한가요?

DB는 내 코드와 별개인 프로그램이라, 말을 걸려면 먼저 연결(전화 걸기)을 맺어야 합니다. 그런데 이 준비 과정(접속 + 인증)이 정작 쿼리보다 훨씬 오래 걸리고, PostgreSQL은 연결 하나마다 서버 자원도 잡습니다. 그래서 연결을 미리 몇 개 만들어 두고 빌려 쓰고 반납합니다 — 택시를 매번 사지 않고 대기열에서 배차하는 것과 같습니다.

Q pool_size=5, max_overflow=10인데 동시 요청이 20개면?

동시에 열리는 연결은 최대 15개(5+10)이므로, 나머지 5개는 에러가 아니라 대기열에서 기다립니다. 기본 30초(pool_timeout) 안에 자리가 나면 정상 처리되고, 넘기면 TimeoutError가 납니다. 참고로 임시로 늘어난 10개는 일이 끝나면 대기열에 남지 않고 실제로 닫힙니다.

Q session.close()를 빠뜨리면 어떻게 되나요?

빌린 연결이 반납되지 않아 계속 "사용 중"으로 남습니다(연결 누수). 요청이 쌓일수록 풀이 비고, 결국 모든 요청이 30초씩 기다리다 타임아웃 납니다. 그래서 Depends(get_db)의 finally: db.close()나 with 문처럼 닫힘이 보장되는 방식으로만 세션을 씁니다.

Q flush와 commit은 뭐가 다른가요?

flush는 INSERT/UPDATE 문을 DB로 내보내기만 한 상태입니다. id 같은 값은 생기지만 아직 확정이 아니라 rollback하면 사라지고, 다른 트랜잭션에는 보이지 않습니다. commit이 결제 완료에 해당하는 확정이며, 이때부터 모두에게 보입니다. commit()은 내부적으로 flush를 먼저 수행합니다.

Q get_db는 왜 return이 아니라 yield를 쓰나요?

return이면 함수가 그 자리에서 끝나 뒷정리 코드를 넣을 자리가 없습니다. yield는 "값을 주고 일시정지"이므로, FastAPI가 응답을 보낸 뒤 멈춰 있던 지점으로 돌아와 finally: db.close()를 실행해 줍니다. 덕분에 라우트에서 예외가 나도 연결은 반드시 반납됩니다.

Q NestJS에서는 commit()을 안 썼는데 왜 여기선 필요한가요?

TypeORM의 repo.save()는 한 건을 그 자리에서 확정하는 방식이라 커밋이 안에 숨어 있습니다. 반면 SQLAlchemy의 Session은 변경을 모았다가 한 번에 확정하는 방식(장바구니)이라 commit()이 곧 결제 버튼입니다. 대신 SQLAlchemy는 트랜잭션이 공짜로 딸려오고(여러 작업을 묶으려고 dataSource.transaction()을 따로 열 필요가 없음), 객체 값만 바꿔도 commit 시 UPDATE가 나갑니다. TypeORM에서는 바꾼 뒤 save()를 또 불러야 하죠.

Q scalars()는 왜 쓰나요?

execute()의 결과는 칸이 여러 개인 Row(표의 한 줄)입니다. select(Todo)처럼 엔티티 하나만 골랐다면 각 Row의 칸은 하나뿐이니, scalars()로 그 첫 칸만 꺼내 Todo 객체 리스트로 폅니다. 그래야 row[0].title 대신 todo.title로 쓸 수 있습니다. 여러 컬럼을 골랐다면 scalars() 없이 Row로 받아 튜플처럼 풀어 씁니다.

Q bind 변수는 왜 SQL Injection을 막나요?

문장과 값을 따로 보내기 때문입니다. SQL에는 :q라는 빈칸만 두고 값은 별도로 전달하면, DB가 문장 구조를 먼저 확정한 뒤 빈칸에 값을 순수 데이터로 끼워 넣습니다. 값 안에 따옴표나 OR 1=1이 있어도 문법으로 승격될 기회가 없습니다 — 빈칸 채우기 시험지에서 답을 뭐라 적든 문제 문장은 바뀌지 않는 것과 같습니다. 반대로 f-string은 값과 문법이 한 덩어리가 되어 구분이 사라집니다. ORM 표현식(where(Todo.title == q))은 자동으로 바인딩하므로 기본이 안전합니다.
