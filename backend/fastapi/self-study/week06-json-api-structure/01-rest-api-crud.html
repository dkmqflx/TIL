REST API 명세 & CRUD ToDo API를 처음부터 끝까지

명세표 한 장 → 스키마 3개 → 라우터 함수 5개 순서로 할 일(ToDo) API를 완성합니다. NestJS를 써 본 분을 위해 대응표와 비교 설명을 곳곳에 두었지만, FastAPI 쪽 설명만 읽어도 이어집니다.

한 줄 요약. FastAPI에서 API의 규칙은 타입힌트로 말한다. payload: TodoCreate라고 적으면 검증·문서가 같이 따라오고, response_model=TodoPublic이라고 적으면 응답 모양이 고정된다. 직접 켜야 하는 스위치는 딱 하나, DB 객체를 응답으로 내보낼 때 필요한 from_attributes=True다.

학습 목표

  • REST API 명세를 먼저 표로 설계한다
  • 입력용·수정용·응답용 Pydantic 스키마 3종을 나누는 이유를 설명한다
  • response_model + from_attributes=True로 ORM 객체를 안전하게 응답한다
  • SQLAlchemy Session으로 CRUD 엔드포인트 5개를 구현한다
  • 없는 자원에 HTTPException(404)로 응답한다
⚖️

NestJS ↔ FastAPI 한눈에 보는 대응표

NestJS를 모르신다면 이 표와 각 섹션의 NestJS 언급은 건너뛰어도 됩니다. FastAPI 쪽 개념은 각 섹션 본문에서 따로 설명합니다. Nest를 아는 분은 "내가 알던 그거, 여기선 뭐라고 부르지?"를 이 표로 먼저 잡아 두세요.

하고 싶은 일NestJSFastAPI

요청 본문 받기@Body() dto: CreateTodoDtopayload: TodoCreate (인자에 타입만 적음)
입력 검증class-validator + ValidationPipe 등록Pydantic 모델 자체가 규칙 (항상 켜짐)

비유 — 포스트잇을 붙이는 나라 vs 양식지를 채우는 나라. NestJS는 클래스 위에 @Get(), @IsString() 같은 쪽지를 한 장씩 붙여 규칙을 알려 주는 포스트잇의 나라입니다. FastAPI는 양식지의 나라입니다. payload: TodoCreate라고 칸에 적으면 그 타입 선언 자체가 검증 규칙이자 문서가 됩니다. 그래서 Nest에서 따로 켜던 검증·문서가 FastAPI에서는 기본으로 돌아갑니다.

REST API 명세 — 먼저 표로 그린다

코드를 짜기 전에 "어떤 요청에 어떻게 응답할지"를 표로 정리합니다. 이게 곧 API의 계약서이고, 프런트엔드와 백엔드가 같이 보는 약속입니다.

메서드경로설명성공 상태코드
GET/todos할 일 전체 목록 조회200 OK
GET/todos/{id}할 일 단건 조회200 OK (없으면 404)
POST/todos새 할 일 생성201 Created
PATCH/todos/{id}일부 필드만 수정200 OK (없으면 404)
DELETE/todos/{id}할 일 삭제204 No Content (없으면 404)
비유 — 식당의 주문 규칙. REST는 손님과 주방 사이의 주문 규칙입니다. "메뉴(자원)는 메뉴판 번호(URL)로 가리키고, 하고 싶은 행동(조회·추가·변경·취소)은 정해진 손짓(HTTP 메서드)으로 한다." 손님이 규칙대로만 주문하면 어떤 주방이든 같은 방식으로 알아듣습니다. 상태코드는 주방이 돌려주는 "됐어요(201) / 없어요(404)" 같은 표준 답변이고요.

이 표를 코드로 옮기면 APIRouter(prefix="/todos", tags=["todos"]) 하나에 함수 5개를 붙이는 꼴이 됩니다. prefix는 공통 경로, tags는 /docs에서의 그룹 이름이고, HTTP 메서드는 함수마다 @router.get·@router.post 같은 데코레이터로 붙입니다. 전체 코드는 CRUD 라우터에서 봅니다. (NestJS라면 @Controller('todos') 클래스 안에 메서드 5개를 두는 자리입니다.)

스키마 3종 — 입력·수정·응답을 나눈다

"받을 때 필요한 필드"와 "돌려줄 때 보여줄 필드"는 다릅니다. 생성할 때는 id를 받으면 안 되고(DB가 정함), 수정할 때는 모든 필드가 선택이어야 하고, 응답에는 id·created_at이 들어가야 하죠. 모델 하나로 다 하면 "필수/선택"이 충돌하므로 용도별로 셋을 만듭니다(NestJS의 DTO 3종과 같은 이유).

Pydantic 스키마용도NestJS 대응
TodoCreatePOST 요청 본문 (title 필수, id 안 받음)CreateTodoDto
TodoUpdatePATCH 요청 본문 (모든 필드 선택)PartialType(CreateTodoDto)
TodoPublic응답 (response_model에 건다)TodoResponseDto
pythonschemas.py
from datetime import datetime
from pydantic import BaseModel, ConfigDict, Field

class TodoCreate(BaseModel):
    title: str = Field(min_length=1, max_length=100)   # 타입 + 길이 검증을 한 줄에
    done: bool = False

class TodoUpdate(BaseModel):                           # 전부 | None → "안 보내도 됨"
    title: str | None = Field(default=None, min_length=1, max_length=100)
    done: bool | None = None

class TodoPublic(BaseModel):
    model_config = ConfigDict(from_attributes=True)   # ← 핵심! (다음 섹션)
    id: int
    title: str
    done: bool
    created_at: datetime
검증은 자동, 실패하면 422. payload: TodoCreate라고 적는 순간 검증이 돌아가고, 틀리면 422 Unprocessable Entity로 응답합니다(Nest의 ValidationPipe는 400이라 프런트와 약속을 맞출 때 확인하세요). 모델에 없는 필드는 기본적으로 조용히 버려집니다 — 에러로 바꾸고 싶으면 ConfigDict(extra="forbid")를 켭니다(Nest의 forbidNonWhitelisted에 해당).
🔄

from_attributes — ORM 객체를 응답으로 내보내는 스위치

라우트 함수가 DB에서 꺼낸 Todo 객체를 그대로 return하면, FastAPI는 response_model=TodoPublic을 보고 그 객체를 TodoPublic 모양의 JSON으로 바꿉니다. 그런데 이때 ConfigDict(from_attributes=True)라는 스위치가 없으면 에러가 납니다. 왜 스위치가 필요할까요? 답은 파이썬에서 데이터를 꺼내는 문법이 두 가지라서입니다.

python
data = {"id": 1, "title": "밥 먹기"}   # 딕셔너리
data["id"]     # ✅ 1
data.id        # ❌ AttributeError

todo = db.get(Todo, 1)                # SQLAlchemy 객체
todo.id        # ✅ 1
todo["id"]     # ❌ TypeError: 'Todo' object is not subscriptable

Pydantic이 평소에 상대하는 데이터는 JSON 요청 본문이고, JSON을 파싱하면 딕셔너리가 나옵니다. 그래서 Pydantic의 기본 동작은 data["title"] 방식 하나뿐입니다. DB에서 꺼낸 Todo는 딕셔너리가 아니라 객체라서 이 기본 동작으로는 아무것도 읽을 수 없고, from_attributes=True가 "딕셔너리가 아니면 todo.title처럼 속성으로도 읽어 봐"라고 허락해 주는 스위치입니다. (자바스크립트는 평범한 객체든 클래스 인스턴스든 todo.id 한 가지로 읽으니 NestJS에는 이런 스위치가 없었습니다.)

비유 — 서랍장이냐, 사람이냐. Pydantic의 기본 상태는 서랍장에서 물건 꺼내기만 할 줄 압니다. title이라고 이름표가 붙은 서랍을 열면 값이 나오죠(딕셔너리). 그런데 DB에서 데려온 건 서랍장이 아니라 사람(객체)입니다. 사람 몸에는 서랍이 없으니 값을 알고 싶으면 "이름이 뭐예요?"라고 물어봐야 합니다(todo.title). from_attributes=True는 "서랍이 없는 상대면 말로 물어봐도 된다"는 허가증입니다.

그러면 response_model은 정확히 무엇을 할까요? "응답은 이 모델 모양으로 내보내라"는 선언입니다. TodoPublic에 적은 필드만 나가고, 안 적은 필드(예: owner_token)는 자동으로 빠집니다. NestJS에서 같은 일을 하던 ClassSerializerInterceptor는 반대로 숨길 필드에 @Exclude()를 일일이 표시하는 방식이었습니다.

이 방향 차이가 실무에서 제일 중요합니다. "숨길 것을 표시"하는 방식은 User에 @Exclude() 하나를 빠뜨리면 password 해시가 응답에 그대로 실려 나갑니다. FastAPI는 UserPublic에 적지 않은 필드는 절대 나가지 않으므로, 깜빡해서 새는 사고가 구조적으로 일어나지 않습니다.
스위치를 안 켜면 이런 에러를 만납니다. TodoPublic에서 model_config 줄을 지우고 ORM 객체를 반환하면, FastAPI가 응답을 만들다가 이렇게 터집니다. 
pydantic_core._pydantic_core.ValidationError: 1 validation error for TodoPublic
  Input should be a valid dictionary or instance of TodoPublic
  [type=model_type, input_value=<models.Todo object at 0x10a...>, input_type=Todo]
"딕셔너리를 달라고 했는데 Todo 객체가 왔다"는 뜻입니다. 이 메시지 = from_attributes를 안 켰다는 신호입니다.

SQLAlchemy 모델 & DB 세션 — Week 5 것을 그대로

테이블 모델은 Week 5에서 만든 models.py를 그대로 씁니다. 세션을 건네주는 get_db도 Week 5·03의 것을 그대로 import합니다. Mapped·mapped_column이 낯설다면 Week 5·02를 다시 보세요(TypeORM 엔티티와의 대응표도 거기 있습니다).

pythonmodels.py
from datetime import datetime
from sqlalchemy import func
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column

class Base(DeclarativeBase): ...

class Todo(Base):
    __tablename__ = "todos"
    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str] = mapped_column(index=True)
    done: Mapped[bool] = mapped_column(default=False)
    created_at: Mapped[datetime] = mapped_column(server_default=func.now())  # DB가 채움

CRUD 라우터 — 5개 엔드포인트

이제 명세표의 5줄을 실제 코드로 옮깁니다. 흐름을 한눈에 보기 위해 DB 코드까지 라우터에 직접 적습니다(다음 레슨에서 서비스 계층으로 분리합니다). 조회 두 개부터 봅니다.

pythonrouters/todos.py — 조회
from fastapi import APIRouter, Depends, HTTPException, status
from sqlalchemy import select
from sqlalchemy.orm import Session
from database import get_db
from models import Todo
from schemas import TodoCreate, TodoUpdate, TodoPublic

router = APIRouter(prefix="/todos", tags=["todos"])

@router.get("", response_model=list[TodoPublic])
def list_todos(db: Session = Depends(get_db)):
    return db.scalars(select(Todo).order_by(Todo.id)).all()   # Todo 객체 리스트

@router.get("/{todo_id}", response_model=TodoPublic)
def get_todo(todo_id: int, db: Session = Depends(get_db)):
    todo = db.get(Todo, todo_id)          # 기본키로 한 건 조회 (없으면 None)
    if todo is None:
        raise HTTPException(status.HTTP_404_NOT_FOUND, "Todo not found")
    return todo                           # ORM 객체 그대로 → from_attributes가 처리

db: Session = Depends(get_db)는 "이 함수에 DB 세션 하나 넣어 달라"는 선언입니다(원리는 다음 레슨). select(Todo)는 "todos 전부 주세요"라는 주문서이고 scalars().all()이 결과를 Todo 객체 리스트로 꺼냅니다 — Week 5·03에서 본 그대로입니다. status.HTTP_404_NOT_FOUND는 숫자 404에 이름을 붙인 상수라 그냥 404라고 써도 같습니다.

pythonrouters/todos.py — 생성·수정·삭제
@router.post("", response_model=TodoPublic,
             status_code=status.HTTP_201_CREATED)
def create_todo(payload: TodoCreate, db: Session = Depends(get_db)):
    todo = Todo(title=payload.title, done=payload.done)
    db.add(todo)                  # 세션에 올려 두기 (아직 SQL 안 나감)
    db.commit()                   # 여기서 INSERT
    db.refresh(todo)              # DB가 채운 id·created_at 다시 읽기
    return todo

@router.patch("/{todo_id}", response_model=TodoPublic)
def update_todo(todo_id: int, payload: TodoUpdate,
                db: Session = Depends(get_db)):
    todo = db.get(Todo, todo_id)
    if todo is None:
        raise HTTPException(status.HTTP_404_NOT_FOUND, "Todo not found")
    # exclude_unset=True → 요청에 실제로 보낸 필드만 수정
    for field, value in payload.model_dump(exclude_unset=True).items():
        setattr(todo, field, value)
    db.commit()
    db.refresh(todo)
    return todo

@router.delete("/{todo_id}", status_code=status.HTTP_204_NO_CONTENT)
def delete_todo(todo_id: int, db: Session = Depends(get_db)):
    todo = db.get(Todo, todo_id)
    if todo is None:
        raise HTTPException(status.HTTP_404_NOT_FOUND, "Todo not found")
    db.delete(todo)
    db.commit()                   # 아무것도 return 안 함 → 본문 없이 204
저장은 add → commit → refresh 세 줄입니다. add()는 세션에 올려 두기만 하고 실제 INSERT는 commit()에서 나갑니다(Week 5·03의 "세션 = 작업 단위"). 그런데 created_at처럼 DB가 채우는 값은 커밋했다고 객체에 저절로 들어오지 않고, 커밋 직후 객체 속성은 "만료" 상태라 다시 조회해야 합니다. refresh(todo)가 이 둘을 한 번에 해결합니다. (TypeORM save()는 반환값에 채워져 와서 한 줄이었습니다.)
PATCH는 exclude_unset이 핵심입니다. PUT은 자원 전체를 교체하지만 PATCH는 보낸 필드만 고칩니다. Pydantic 모델은 "어떤 필드가 실제로 요청에 들어왔는지"를 기억하고 있어서 model_dump(exclude_unset=True)가 그것만 골라냅니다. 이 옵션이 없으면 안 보낸 필드까지 기본값 None으로 들어와 멀쩡한 값을 덮어씁니다. "null을 일부러 보낸 경우"와 "아예 안 보낸 경우"도 구분됩니다(JS의 null vs undefined).
404 응답의 모양. raise HTTPException(404, "Todo not found")는 {"detail":"Todo not found"}를 돌려줍니다(Nest의 NotFoundException은 {"statusCode":404,"message":...}라 프런트 에러 처리 코드를 그대로 옮기면 안 됩니다). 에러 응답 모양을 앱 전체에서 통일하는 방법은 03 전역 예외 핸들러에서 다룹니다.

전체 흐름 — 요청부터 응답까지

요청 하나가 들어와서 응답이 나가기까지 FastAPI는 위에서 아래 순서로 처리합니다. 이번 레슨에서 쓴 건 검증·경로 함수·response_model뿐이고, 나머지 칸은 앞으로 하나씩 채웁니다. (NestJS의 Middleware → Guard → Interceptor → Pipe → Handler → Filter 라이프사이클을 아시면 가운데 열과 비교해 보세요 — 부품 수가 확 줄어듭니다.)

셀프 체크

Q ORM 객체를 그냥 return하는데 왜 from_attributes=True가 필요한가?

Pydantic은 기본적으로 딕셔너리(data["id"])만 읽을 줄 아는데, ORM 객체는 속성(todo.id)으로 읽어야 하기 때문입니다. 이 스위치가 "객체면 속성으로 읽어도 된다"는 허락입니다.

Q 스키마를 Create/Update/Public 셋으로 나누는 이유는?

생성 때는 id를 받지 않고, 수정 때는 모든 필드가 선택이며, 응답에는 id·created_at이 들어가야 해서 하나의 모델로는 "필수/선택"이 충돌합니다. 용도별로 나누면 각자 딱 맞는 규칙을 가질 수 있습니다.

Q PATCH에서 model_dump(exclude_unset=True)를 빼면 무슨 일이 생기나?

요청에 안 보낸 필드까지 기본값 None으로 dump되어, 고치려 하지 않은 값(예: title)을 None으로 덮어써 버립니다. 이 옵션이 "실제로 보낸 필드만" 골라 줍니다.
