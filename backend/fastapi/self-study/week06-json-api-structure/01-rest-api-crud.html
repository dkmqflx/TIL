REST API 명세 & CRUD NestJS로 하던 일을 FastAPI로

이번 레슨은 NestJS를 이미 아는 사람을 위한 번역기입니다. @Controller·DTO·Repository로 만들던 ToDo API를, FastAPI의 APIRouter·Pydantic·Session으로 한 줄씩 옮겨 가며 만듭니다.

한 줄 요약. 두 프레임워크가 하는 일은 똑같다. 차이는 "규칙을 어떻게 말하느냐"다. NestJS는 클래스 위에 데코레이터를 붙여서(@Get(), @IsString(), @Expose()), FastAPI는 함수에 타입힌트를 적어서(payload: TodoCreate, response_model=TodoPublic) 말한다. 그리고 NestJS에서 따로 켜던 것(ValidationPipe, Swagger)은 FastAPI에서 기본 ON이고, 대신 FastAPI에서 딱 하나 직접 켜야 하는 스위치가 from_attributes=True다.

학습 목표

  • NestJS 컨트롤러 ↔ FastAPI 라우터의 대응 관계를 표로 외운다
  • Create/Update/Response DTO ↔ Pydantic 스키마 3종을 옮겨 쓴다
  • ClassSerializerInterceptor ↔ response_model + from_attributes의 차이를 설명한다
  • TypeORM Entity/Repository ↔ SQLAlchemy 모델/Session으로 CRUD를 구현한다
  • NotFoundException ↔ HTTPException(404)로 없는 자원을 일관되게 응답한다
⚖️

NestJS ↔ FastAPI 한눈에 보는 대응표

새 프레임워크를 배울 때 가장 빠른 길은 "내가 알던 그거, 여기선 뭐라고 부르지?"를 먼저 정리하는 것입니다. 아래 표만 손에 쥐고 있으면 이번 레슨의 코드는 거의 다 읽힙니다.

비유 — 포스트잇을 붙이는 나라 vs 양식지를 채우는 나라. NestJS는 포스트잇의 나라입니다. 클래스와 메서드 위에 @Get(), @IsString(), @Expose() 같은 쪽지를 한 장씩 붙여서 "이건 이렇게 처리해 줘"라고 알려 줍니다. FastAPI는 양식지의 나라입니다. payload: TodoCreate라고 칸에 적어 넣으면, 그 타입 선언 자체가 검증 규칙이자 문서이자 편집기 자동완성이 됩니다. 결과물은 같은 API지만, 한쪽은 규칙을 덧붙이고 다른 쪽은 규칙을 타입으로 말합니다.
"켜야 하는 것"의 방향이 반대다. NestJS에서는 검증(ValidationPipe), 응답 변환(ClassSerializerInterceptor), 문서(SwaggerModule)를 직접 등록해야 동작합니다. FastAPI는 이 셋이 기본으로 돌아갑니다. 대신 FastAPI에서 딱 하나 직접 켜야 하는 스위치가 있는데, 그게 이번 레슨의 주인공 from_attributes=True입니다. 왜 이것만 수동인지는 아래 섹션에서 풀어 봅니다.
📋

REST API 명세 — 먼저 표로 그린다

코드를 짜기 전에 "어떤 요청에 어떻게 응답할지"를 표로 정리합니다. 이게 곧 API의 계약서입니다. NestJS에서 컨트롤러 메서드 목록을 먼저 설계하던 것과 정확히 같은 단계죠.

메서드경로설명성공 상태코드
GET/todos할 일 전체 목록 조회200 OK
GET/todos/{id}할 일 단건 조회200 OK (없으면 404)
POST/todos새 할 일 생성201 Created
PATCH/todos/{id}일부 필드만 수정200 OK (없으면 404)
DELETE/todos/{id}할 일 삭제204 No Content (없으면 404)

같은 명세를 두 프레임워크의 뼈대 코드로 옮기면 이렇게 됩니다. NestJS는 클래스 하나에 메서드를 모으고, FastAPI는 router 객체에 함수를 붙입니다.

NestJS — 클래스 + 데코레이터
@Controller('todos')
export class TodosController {
  @Get()      // GET /todos
  findAll() {}

  @Post()     // POST /todos
  @HttpCode(201)
  create() {}
}

클래스가 prefix를, 메서드 데코레이터가 HTTP 메서드를 담당.

FastAPI — 라우터 + 함수
router = APIRouter(
    prefix="/todos",
    tags=["todos"])

@router.get("")  # GET /todos
def list_todos(): ...

@router.post("",
    status_code=201)  # POST
def create_todo(): ...

APIRouter가 prefix를, 데코레이터가 HTTP 메서드를 담당. 클래스가 없을 뿐.

tags는 NestJS의 @ApiTags()다. NestJS에서 Swagger 문서에 그룹을 만들려면 @ApiTags('todos')를 따로 붙여야 했죠. FastAPI에서는 APIRouter(tags=["todos"]) 한 줄이면 /docs에 "todos" 섹션이 생깁니다. 문서 도구가 프레임워크에 내장되어 있어서 그렇습니다.
비유 — 식당의 주문 규칙. REST는 손님과 주방 사이의 주문 규칙입니다. "메뉴(자원)는 메뉴판 번호(URL)로 가리키고, 하고 싶은 행동(조회·추가·변경·취소)은 정해진 손짓(HTTP 메서드)으로 한다." 손님이 규칙대로만 주문하면 어떤 주방이든 같은 방식으로 알아듣습니다 — 주방이 NestJS든 FastAPI든요. 상태코드는 주방이 돌려주는 "됐어요(201)/없어요(404)" 같은 표준 답변이고요.
🗂️

스키마 3종 — NestJS의 DTO 3종과 같다

"받을 때 필요한 필드"와 "돌려줄 때 보여줄 필드"는 다릅니다. 그래서 NestJS에서 CreateTodoDto·UpdateTodoDto·TodoResponseDto를 나눠 쓰셨죠. FastAPI에서도 똑같은 이유로 똑같이 셋을 만듭니다. 이름만 Pydantic 모델일 뿐입니다.

Pydantic 스키마용도NestJS 대응
TodoCreatePOST 요청 본문 (title 필수, id 안 받음)CreateTodoDto
TodoUpdatePATCH 요청 본문 (모든 필드 선택)UpdateTodoDto extends PartialType(...)
TodoPublic응답 (response_model)TodoResponseDto + ClassSerializerInterceptor
NestJS — 데코레이터로 규칙 붙이기
export class CreateTodoDto {
  @IsString()
  @MinLength(1)
  @MaxLength(100)
  title: string;

  @IsBoolean() @IsOptional()
  done = false;
}

export class UpdateTodoDto
  extends PartialType(
    CreateTodoDto) {}

타입(string)과 검증(@IsString)을 따로 적어야 함.

FastAPI — 타입이 곧 규칙
class TodoCreate(BaseModel):
    title: str = Field(
        min_length=1,
        max_length=100)
    done: bool = False

# PartialType 대신 | None
class TodoUpdate(BaseModel):
    title: str | None = None
    done: bool | None = None

title: str 한 번이면 타입 + 검증 + 문서까지 동시에 해결.

실제로 쓸 세 모델을 한 파일에 모으면 이렇습니다. TodoPublic의 model_config 한 줄이 다음 섹션의 주인공입니다.

pythonschemas.py
from datetime import datetime
from pydantic import BaseModel, ConfigDict, Field

class TodoCreate(BaseModel):                      # ← CreateTodoDto
    title: str = Field(min_length=1, max_length=100)
    done: bool = False

class TodoUpdate(BaseModel):                      # ← UpdateTodoDto (PartialType)
    title: str | None = Field(default=None, min_length=1, max_length=100)
    done: bool | None = None

class TodoPublic(BaseModel):                      # ← TodoResponseDto
    model_config = ConfigDict(from_attributes=True)   # ← 핵심! (다음 섹션)
    id: int
    title: str
    done: bool
    created_at: datetime
NestJS에서 자주 겪던 함정 하나가 사라진다. Nest에서는 DTO에 @IsString()을 아무리 잘 붙여도, main.ts에 app.useGlobalPipes(new ValidationPipe())를 안 적으면 검증이 아예 안 돕니다. 데코레이터는 "메모"일 뿐이고 그 메모를 읽어 주는 파이프를 등록해야 하니까요. FastAPI에는 이 단계가 없습니다. payload: TodoCreate라고 적는 순간 검증이 돌아갑니다. 단, 실패했을 때 상태코드가 다릅니다 — Nest는 400 Bad Request, FastAPI는 422 Unprocessable Entity. 프런트엔드와 약속을 맞출 때 꼭 확인하세요.
whitelist: true에 해당하는 건? Nest의 new ValidationPipe({ whitelist: true })는 DTO에 없는 필드를 버리고, forbidNonWhitelisted: true는 아예 에러를 냅니다. Pydantic에서는 ConfigDict(extra=...)가 같은 역할을 합니다. 기본값 "ignore"가 Nest의 whitelist: true에, "forbid"가 forbidNonWhitelisted: true에 해당합니다. 즉 FastAPI는 "모르는 필드는 버린다"가 기본입니다.
🔄

from_attributes — NestJS엔 왜 이런 게 없었을까

NestJS에서는 컨트롤러가 TypeORM 엔티티를 그냥 return해도 아무 문제가 없었습니다. 그런데 FastAPI에서는 ConfigDict(from_attributes=True)라는 스위치를 켜 줘야 한다고 합니다. 왜 한쪽만 스위치가 필요할까요? 답은 프레임워크가 아니라 언어의 차이에 있습니다.

자바스크립트에는 꺼내는 방법이 하나뿐이다

TypeScript에서 { id: 1, title: "밥" }이라는 평범한 객체든, new Todo()로 만든 엔티티 인스턴스든, 값을 꺼내는 방법은 오직 하나입니다 — todo.id. (todo['id']도 되지만 이건 같은 프로퍼티 접근의 다른 표기일 뿐, 완전히 동일한 동작입니다.) 그래서 class-transformer는 상대가 무엇이든 고민 없이 todo.id로 읽으면 됩니다. 선택지가 없으니 스위치도 필요 없었던 것이죠.

파이썬에는 꺼내는 방법이 두 가지다

파이썬은 다릅니다. 데이터를 꺼내는 문법이 서로 통하지 않는 두 종류로 나뉩니다.

python
data = {"id": 1, "title": "밥 먹기"}   # 딕셔너리
data["id"]     # ✅ 1
data.id        # ❌ AttributeError

todo = db.get(Todo, 1)                # SQLAlchemy 객체
todo.id        # ✅ 1
todo["id"]     # ❌ TypeError: 'Todo' object is not subscriptable

Pydantic이 평소에 상대하는 데이터는 JSON 요청 본문입니다. JSON을 파싱하면 딕셔너리가 나오죠. 그래서 Pydantic의 기본 동작은 data["title"] 방식 하나만입니다. 그런데 DB에서 꺼낸 Todo는 딕셔너리가 아니라 객체라서, 이 기본 동작으로는 아무것도 읽을 수가 없습니다. ConfigDict(from_attributes=True)는 딱 한 줄로 "딕셔너리가 아니면 todo.title처럼 속성으로도 읽어 봐"라고 허락해 주는 스위치입니다.

비유 — 서랍장이냐, 사람이냐. Pydantic의 기본 상태는 서랍장에서 물건 꺼내기만 할 줄 압니다. title이라고 이름표가 붙은 서랍을 열면 값이 나오죠(딕셔너리). 그런데 DB에서 데려온 건 서랍장이 아니라 사람(객체)입니다. 사람 몸에는 서랍이 없으니, 값을 알고 싶으면 "이름이 뭐예요?"라고 물어봐야 합니다(todo.title). from_attributes=True는 "서랍이 없는 상대면 그냥 말로 물어봐도 된다"는 허가증이에요. 자바스크립트 세계에는 애초에 서랍장이라는 개념이 없고 전부 "물어보기" 하나라서, NestJS에서는 이 허가증을 발급받을 필요가 없었던 겁니다.

그래서 두 프레임워크의 코드는 이렇게 대응한다

NestJS에서 "엔티티를 응답 모양으로 다듬는" 일은 ClassSerializerInterceptor가 맡았습니다. FastAPI에서는 response_model이 그 자리를 대신하고, from_attributes는 그 인터셉터가 ORM 객체를 읽을 수 있게 해 주는 부품입니다.

NestJS — 인터셉터를 등록
// 1) 엔티티/DTO에 표시
export class Todo {
  @Expose() id: number;
  @Expose() title: string;
  @Exclude() ownerToken: string;
}

// 2) 인터셉터를 켠다
@UseInterceptors(
  ClassSerializerInterceptor)
@Get(':id')
findOne() {
  return this.repo.findOne(id);
}

숨길 필드에 @Exclude()를 일일이 붙여야 함.

FastAPI — 모델을 응답에 건다
# 1) 모델에 스위치를 켠다
class TodoPublic(BaseModel):
    model_config = ConfigDict(
        from_attributes=True)
    id: int
    title: str
    # owner_token 은 안 적음
    #  → 응답에서 자동 제외

# 2) 라우트에 모양을 건다
@router.get("/{todo_id}",
    response_model=TodoPublic)
def get_todo(todo_id: int):
    return todo  # ORM 그대로

모델에 적은 것만 나감. 안 적으면 그게 곧 숨김.

차이를 항목별로 뜯어보면

질문NestJSFastAPI
응답 변환은 누가?ClassSerializerInterceptorresponse_model=
언제 동작하나?인터셉터를 등록한 곳에서만response_model을 적은 라우트에서
무엇이 규칙인가?DTO/엔티티의 @Expose·@ExcludePydantic 모델의 필드 목록 그 자체

필드가 비어 있으면?조용히 undefined → JSON에서 사라짐ValidationError → 서버 에러로 즉시 드러남

마지막 줄이 실무에서 제일 중요합니다. NestJS에서 User 엔티티에 @Exclude()를 빠뜨려 password 해시가 응답에 그대로 실려 나가는 사고, 한 번쯤 들어 보셨을 겁니다. FastAPI는 방향이 반대입니다 — UserPublic 모델에 적지 않은 필드는 절대 나가지 않습니다. "숨길 것을 표시"하는 게 아니라 "보여줄 것만 나열"하는 방식이라, 깜빡해서 새는 사고가 구조적으로 일어나지 않습니다.
스위치를 안 켜면 이런 에러를 만납니다. TodoPublic에서 model_config 줄을 지우고 ORM 객체를 반환하면, FastAPI가 응답을 만들다가 이렇게 터집니다. 
pydantic_core._pydantic_core.ValidationError: 1 validation error for TodoPublic
  Input should be a valid dictionary or instance of TodoPublic
  [type=model_type, input_value=<models.Todo object at 0x10a...>, input_type=Todo]
"딕셔너리를 달라고 했는데 Todo 객체가 왔다"는 뜻입니다. 이 메시지를 보면 "아, from_attributes를 안 켰구나"라고 바로 알아채면 됩니다.
수동 변환도 대응이 있습니다. Nest에서 인터셉터 없이 직접 변환할 땐 plainToInstance(TodoDto, todo, { excludeExtraneousValues: true })를 썼죠. Pydantic의 대응은 TodoPublic.model_validate(todo)입니다. 재미있는 건 둘 다 "옵션 하나를 빠뜨리면 조용히 이상하게 동작하는" 자리라는 점 — 다만 하는 일은 다릅니다. excludeExtraneousValues는 "표시 안 된 필드를 버려라"이고, from_attributes는 "속성으로 읽어라"입니다.
NestJS의 엔티티 → ClassSerializerInterceptor → JSON 과 같은 흐름. 가운데 화살표에 붙은 from_attributes가 "속성으로 읽어도 된다"는 허가증이다.

Repository 하나 vs Session 하나 — 여기서 감각이 갈린다

구조가 눈에 띄게 다른 지점이 하나 있습니다. TypeORM은 엔티티마다 리포지토리를 주입받지만, SQLAlchemy는 세션 하나로 모든 엔티티를 다룹니다.

NestJS — 엔티티별 Repository
// 엔티티마다 하나씩 주입
constructor(
  @InjectRepository(Todo)
  private repo: Repository<Todo>,
) {}

// 저장 = save() 한 방
await this.repo.save(todo);

User도 쓰려면 @InjectRepository(User)를 또 주입.

FastAPI — 세션 하나로 전부
# 세션 하나로 모든 엔티티
db: Session = Depends(get_db)

db.get(Todo, id)
db.get(User, id)   # 같은 세션

# 저장 = add → commit
db.add(todo)
db.commit()

모델 클래스를 인자로 넘기므로 세션 하나면 충분.

비유 — 즉시 결제 vs 장바구니. TypeORM의 save()는 "이거 지금 계산해 주세요"입니다. 부를 때마다 SQL이 나가죠. SQLAlchemy의 add()는 "일단 장바구니에 담아 둬"에 가깝습니다. 실제 SQL은 commit()을 부르는 순간 한꺼번에 나갑니다. 그래서 객체 열 개를 고쳐도 커밋 한 번이면 되고, 중간에 문제가 생기면 장바구니를 통째로 비울 수 있습니다(롤백). 이 방식을 Unit of Work라고 부르고, SQLAlchemy를 배울 때 가장 먼저 익숙해져야 하는 감각입니다.

CRUD 라우터 — Controller + Service를 함수로

이제 명세표의 5줄을 실제 코드로 옮깁니다. NestJS라면 TodosController와 TodosService 두 파일로 나눴을 텐데, 여기서는 흐름을 한눈에 보기 위해 라우터에 직접 적습니다. (다음 레슨에서 서비스 계층으로 분리합니다.)

pythonrouters/todos.py — 조회
from fastapi import APIRouter, Depends, HTTPException, status
from sqlalchemy import select
from sqlalchemy.orm import Session
from database import get_db
from models import Todo
from schemas import TodoCreate, TodoUpdate, TodoPublic

router = APIRouter(prefix="/todos", tags=["todos"])   # ← @Controller('todos')

@router.get("", response_model=list[TodoPublic])      # ← @Get()
def list_todos(db: Session = Depends(get_db)):
    return db.scalars(select(Todo).order_by(Todo.id)).all()

@router.get("/{todo_id}", response_model=TodoPublic)  # ← @Get(':id')
def get_todo(todo_id: int, db: Session = Depends(get_db)):
    todo = db.get(Todo, todo_id)
    if todo is None:
        # ← throw new NotFoundException('Todo not found')
        raise HTTPException(status.HTTP_404_NOT_FOUND, "Todo not found")
    return todo                       # ORM 객체 그대로 반환 → from_attributes가 처리

생성(POST)을 두 프레임워크로 나란히 놓으면 이렇습니다. 순서와 역할이 거의 똑같다는 게 보일 겁니다.

NestJS — @Post + save()
@Post()
@HttpCode(201)
async create(
  @Body() dto: CreateTodoDto,
) {
  const todo =
    this.repo.create(dto);
  return this.repo.save(todo);
}

save()가 반환값으로 id가 채워진 객체를 돌려줌.

FastAPI — add · commit · refresh
@router.post(
    "", status_code=201,
    response_model=TodoPublic)
def create_todo(
    payload: TodoCreate,
    db: Session = Depends(get_db)
):
    todo = Todo(
        **payload.model_dump())
    db.add(todo)
    db.commit()
    db.refresh(todo)
    return todo

커밋 후 refresh()로 DB가 채운 값을 다시 읽어 옴.

pythonrouters/todos.py — 생성·수정·삭제
@router.post("", response_model=TodoPublic,
             status_code=status.HTTP_201_CREATED)   # ← @HttpCode(201)
def create_todo(payload: TodoCreate, db: Session = Depends(get_db)):
    todo = Todo(title=payload.title, done=payload.done)
    db.add(todo)
    db.commit()
    db.refresh(todo)              # DB가 채운 id·created_at 다시 읽기
    return todo

@router.patch("/{todo_id}", response_model=TodoPublic)   # ← @Patch(':id')
def update_todo(todo_id: int, payload: TodoUpdate,
                db: Session = Depends(get_db)):
    todo = db.get(Todo, todo_id)
    if todo is None:
        raise HTTPException(status.HTTP_404_NOT_FOUND, "Todo not found")
    # exclude_unset=True → 요청에 실제로 보낸 필드만 수정
    for field, value in payload.model_dump(exclude_unset=True).items():
        setattr(todo, field, value)
    db.commit(); db.refresh(todo)
    return todo

@router.delete("/{todo_id}",
              status_code=status.HTTP_204_NO_CONTENT)   # ← @HttpCode(204)
def delete_todo(todo_id: int, db: Session = Depends(get_db)):
    todo = db.get(Todo, todo_id)
    if todo is None:
        raise HTTPException(status.HTTP_404_NOT_FOUND, "Todo not found")
    db.delete(todo); db.commit()       # 아무것도 return 안 함 → 본문 없이 204
404 에러의 모양이 다릅니다. Nest의 throw new NotFoundException('Todo not found')는 {"statusCode":404,"message":"Todo not found","error":"Not Found"}를 돌려줍니다. FastAPI의 raise HTTPException(404, "Todo not found")는 {"detail":"Todo not found"}입니다. 던지는 방식(throw ↔ raise)과 프레임워크가 알아서 응답으로 바꿔 준다는 점은 같지만, 본문 형식이 다르니 프런트엔드 에러 처리 코드를 그대로 옮기면 안 됩니다. 응답 모양을 통일하고 싶다면 다음다음 레슨의 전역 예외 핸들러에서 다룹니다.
PATCH와 PUT은 다르고, exclude_unset이 그 핵심입니다. PUT은 자원 전체를 통째로 교체(모든 필드 필수), PATCH는 일부만 수정입니다. NestJS에서는 PartialType으로 만든 DTO의 안 보낸 필드가 undefined가 되고, TypeORM이 undefined를 알아서 건너뛰어 주는 데 기대곤 했죠. Pydantic은 더 명시적입니다 — 모델이 "어떤 필드가 실제로 요청에 들어왔는지"를 기억하고 있어서, model_dump(exclude_unset=True) 한 줄이면 보낸 것만 정확히 골라냅니다. 덕분에 null을 명시적으로 보낸 경우와 아예 안 보낸 경우를 구분할 수 있습니다. JS의 null vs undefined 구분을 언어 차원에서 안전하게 해 주는 셈입니다.
🔀

전체 흐름 — Nest의 요청 라이프사이클과 비교

NestJS를 쓰면서 외웠던 그 순서 — Middleware → Guard → Interceptor → Pipe → Handler → Interceptor → ExceptionFilter — 를 FastAPI에 옮겨 놓으면 부품 수가 확 줄어듭니다.

Guard·Interceptor·Pipe가 전부 Depends 하나로 합쳐졌다고 보면 됩니다. 종류가 적어 배우기는 쉽지만, Nest처럼 "전역에 한 번 등록해서 모든 라우트에 적용"하고 싶을 땐 방법이 다릅니다. APIRouter(dependencies=[Depends(auth)])처럼 라우터나 앱 레벨에 달아 줘야 하죠. app.useGlobalGuards()가 FastAPI(dependencies=[...])에 해당한다고 기억하세요.

하나의 요청이 라우터를 거쳐 DB를 만나고 다시 JSON으로 돌아오는 길입니다.

요청 → 라우터(검증·세션) → DB(커밋) → response_model 직렬화 → JSON 응답.
commit 뒤엔 refresh를 잊지 말 것 — Nest에는 없던 습관입니다. TypeORM에서는 const saved = await this.repo.save(todo)처럼 반환값에 id가 채워져 왔습니다. SQLAlchemy는 다릅니다. id와 created_at은 INSERT 시점에 DB가 채워 주는 값이고, db.commit() 직후 객체는 "만료(expired)" 상태가 됩니다. db.refresh(todo)로 DB가 채운 최신 값을 다시 읽어 와야 응답에 제대로 담깁니다.

셀프 체크

Q NestJS에선 엔티티를 그냥 return해도 됐는데, FastAPI는 왜 from_attributes가 필요한가?

언어의 차이입니다. 자바스크립트에는 값을 꺼내는 방법이 todo.id 하나뿐이라, class-transformer는 상대가 평범한 객체든 엔티티든 고민 없이 읽습니다. 파이썬은 data["id"](딕셔너리)와 todo.id(객체)가 서로 통하지 않는 두 문법입니다. Pydantic은 JSON 요청 본문(=딕셔너리)을 주로 다루므로 기본값이 딕셔너리 방식이고, ConfigDict(from_attributes=True)가 "객체면 속성으로도 읽어 봐"라고 켜 주는 스위치입니다.

Q response_model=TodoPublic은 NestJS의 무엇에 해당하고, 보안상 어떤 이점이 있나?

ClassSerializerInterceptor에 해당합니다. 다만 방향이 반대예요. Nest는 엔티티에 @Exclude()를 붙여 "숨길 것을 표시"하는 방식이라, 깜빡하면 password 같은 필드가 그대로 새어 나갑니다. FastAPI는 응답 모델에 "보여줄 것만 나열"하는 방식이라, 적지 않은 필드는 아예 나가지 않습니다. 실수로 유출되는 사고가 구조적으로 막힙니다.

Q 스키마를 Create/Update/Public 셋으로 나누는 이유는?

NestJS에서 DTO를 셋으로 나누던 이유와 똑같습니다. 생성 때는 id를 받지 않고, 수정 때는 모든 필드가 선택적이며, 응답에는 id·created_at이 들어갑니다. 하나로 다 처리하려 하면 "선택적이어야 할 곳이 필수가 되는" 모순이 생기죠. Nest의 PartialType(CreateTodoDto)에 해당하는 게 FastAPI에서는 모든 필드를 | None = None으로 두는 것입니다.

Q 검증 실패 응답이 Nest는 400, FastAPI는 422다. 왜 신경 써야 하나?

프런트엔드가 상태코드로 분기하기 때문입니다. Nest의 ValidationPipe는 400 Bad Request를, FastAPI는 422 Unprocessable Entity를 돌려줍니다. 에러 본문 형식도 달라서({"message":[...]} vs {"detail":[...]}), Nest 프런트 코드를 그대로 옮기면 에러 메시지가 화면에 안 뜹니다. 팀 규약이 400이라면 전역 예외 핸들러로 바꿔 주면 됩니다.

Q TypeORM save() 한 줄이 SQLAlchemy에서는 왜 세 줄(add·commit·refresh)인가?

SQLAlchemy는 Unit of Work 방식이기 때문입니다. add()는 "장바구니에 담기"라 SQL이 나가지 않고, commit()에서 담아 둔 변경이 한꺼번에 나갑니다. 여러 객체를 고쳐도 커밋 한 번이면 되고 롤백도 통째로 되는 게 장점이죠. 다만 커밋 직후 객체가 "만료" 상태가 되므로, DB가 채운 id·created_at을 응답에 담으려면 refresh()로 다시 읽어 와야 합니다. TypeORM은 save()의 반환값이 이 역할을 대신했습니다.

Q PATCH에서 model_dump(exclude_unset=True)를 쓰는 이유는?

요청 본문에 실제로 보낸 필드만 추려 수정하기 위해서입니다. 이 옵션 없이 dump하면 보내지 않은 필드도 기본값(None)으로 들어와 멀쩡한 값을 덮어써 버립니다. Pydantic 모델은 "어떤 필드가 요청에 들어왔는지"를 기억하고 있어서, null을 명시적으로 보낸 경우와 아예 안 보낸 경우까지 구분할 수 있습니다. JS의 undefined vs null 구분을 안전하게 처리해 주는 셈입니다.
