Dependency Injection 서비스 계층으로 리팩터링

FastAPI의 Depends는 NestJS의 DI 컨테이너에 대응합니다. 공통 의존성(DB 세션)을 주입받고, 라우터에 뭉쳐 있던 로직을 서비스 계층(MVC)으로 분리합니다.

한 줄 요약. DI는 "필요한 걸 직접 만들지 말고 받아 쓰라"는 원칙이다. FastAPI에서는 함수 인자에 Depends(get_db)를 적기만 하면 세션이 자동으로 주입된다. 그리고 라우터(컨트롤러)는 요청/응답만, 서비스는 비즈니스 로직만 — 이렇게 계층을 나누면 테스트와 유지보수가 쉬워진다.

학습 목표

  • Depends로 공통 의존성(DB 세션)을 함수에 주입한다
  • yield 의존성으로 세션을 열고 닫는 생명주기를 관리한다
  • Annotated[Session, Depends(get_db)] 스타일을 익힌다
  • 라우터·서비스·리포지토리로 계층을 분리한다(MVC)
  • 라우터에 뭉친 코드를 서비스 함수로 리팩터링한다
💉

Depends — 의존성을 주입받기

지난 레슨에서 모든 라우트가 db: Session = Depends(get_db)를 적었죠. 이게 바로 의존성 주입(DI)입니다. "의존성"은 함수가 일을 하려면 꼭 필요한 것(여기서는 DB 세션)이고, "주입"은 그걸 함수가 직접 만들지 않고 밖에서 넣어 준다는 뜻입니다. 함수는 "세션 주세요"라고 선언만 하고, FastAPI가 get_db를 호출해 결과를 넣어 줍니다.

비유 — 주방 보조가 도마를 건네준다. 요리사(라우트 함수)가 요리할 때마다 직접 도마를 찾아오고 씻는다면 요리에 집중할 수 없습니다. 대신 "도마 하나 주세요"라고 선언만 하면(db: Session = Depends(get_db)), 주방 보조(FastAPI)가 주문이 들어올 때마다 깨끗한 도마를 꺼내 손에 쥐여 주고, 요리가 끝나면 알아서 치웁니다. 요리사는 도마가 어디서 오는지 몰라도 됩니다. 덕분에 테스트할 땐 보조에게 "이번엔 가짜 도마를 줘"라고 바꿔치기만 하면 되는데, 이 방법(dependency_overrides)은 Week 10에서 배웁니다.
🔁

yield 의존성 — 열고, 쓰고, 닫기

그 get_db는 Week 5·03에서 만든 함수입니다. 평범한 return 대신 yield를 쓰는데, 이런 함수를 생성기(generator)라고 부릅니다. 생성기는 yield에서 값을 내놓고 잠시 멈췄다가, 나중에 그 자리부터 이어서 실행되는 함수입니다. FastAPI는 이 성질을 이용해 yield 위쪽은 요청 전(열기), 아래쪽은 응답 후(닫기)로 돌립니다.

pythondatabase.py
from collections.abc import Generator
from sqlalchemy.orm import Session

# Generator[Session, None, None] = "Session을 yield하고, 받는 값·return 값은 없다"
def get_db() -> Generator[Session, None, None]:
    db = SessionLocal()       # ① 열기 — 요청이 오면 여기부터 실행
    try:
        yield db              # ② 쓰기 — 라우트에 db를 건네고 여기서 멈춤
    finally:
        db.close()            # ③ 닫기 — 응답이 나간 뒤 이어서 실행 (예외가 나도)

GET /todos/1 한 번에 실제로 벌어지는 일을 순서대로 늘어놓으면 이렇습니다.

GET /todos/1 → 함수 인자 확인 → Depends(get_db) 발견 → get_db() 호출 · yield까지 실행 → db 인자에 주입 → 라우트 실행 → 응답 후 finally: db.close()
try/finally가 핵심. finally 안에서 close()를 하므로 라우트에서 예외가 터져도 세션은 반드시 닫히고, 빌려 쓴 커넥션이 풀(Week 5)로 돌아갑니다. return으로 세션을 넘기면 "끝난 뒤 닫기"를 끼워 넣을 자리가 없습니다 — 그래서 yield입니다. (NestJS의 요청 스코프 프로바이더 — 요청마다 만들고 요청이 끝나면 버리는 객체 — 와 같은 생명주기입니다.)
🏷️

Annotated 스타일 — 재사용 가능한 의존성

모든 라우트마다 db: Session = Depends(get_db)를 반복하면 지저분합니다. Annotated로 별칭 타입을 하나 만들어 두면 깔끔하게 재사용할 수 있습니다 — FastAPI가 권장하는 최신 스타일입니다.

python
from typing import Annotated
from fastapi import Depends
from sqlalchemy.orm import Session
from database import get_db

# ① 지금까지 쓰던 방식 — 기본값 자리에 Depends
def get_todo(todo_id: int, db: Session = Depends(get_db)):
    return services.get_todo(db, todo_id)

# ② Annotated 방식 — 별칭을 한 번 만들어 두고, 모든 라우트에서 재사용
DbSession = Annotated[Session, Depends(get_db)]

def get_todo(todo_id: int, db: DbSession):   # ①과 완전히 같은 코드
    return services.get_todo(db, todo_id)

Annotated[A, B]는 "이 값의 타입은 A인데, 옆에 B라는 메모를 붙여 둔다"는 파이썬 표기입니다. 그래서 DbSession은 겉보기엔 그냥 Session이지만 Depends(get_db)라는 쪽지가 붙어 있는 Session입니다. 요청이 오면 FastAPI는 함수 인자를 하나씩 보면서 "Depends 쪽지가 붙어 있나?"만 확인하므로, 기본값에 적었든 타입 안에 접어 넣었든 똑같이 get_db()를 호출해 db를 채웁니다. todo_id는 URL에서 오지만 db는 클라이언트가 보내는 값이 아니라서, 자동 생성되는 API 문서에도 db 파라미터는 보이지 않습니다.

세션은 요청 하나당 하나. get_db()는 요청마다 새로 호출되어 새 세션을 만듭니다. 같은 요청 안에서 여러 곳(라우트 + 다른 의존성 등)이 DbSession을 요구하면 FastAPI가 get_db()를 한 번만 호출하고 그 결과를 돌려 씁니다(DB 캐시가 아니라 "같은 요청 안에서 의존성 결과 재사용"입니다). 라우트끼리, 요청끼리 세션을 공유하는 일은 없습니다.
별칭은 한 곳에 모아 두자. DbSession = Annotated[...]은 쓰기 전에 정의(또는 import)돼 있어야 하는 평범한 변수입니다. get_db가 있는 database.py 아래쪽에 한 번만 정의해 두고, 각 라우터에서 from database import DbSession으로 가져다 쓰세요.
⚖️

NestJS Provider/DI와 나란히

두 프레임워크 모두 "의존성을 컨테이너가 주입"한다는 발상은 같습니다. 표현 방식만 다릅니다.

NestJS — @Injectable + 생성자 주입
@Injectable()
export class TodosService { ... }

@Controller('todos')
export class TodosController {
  // 생성자에서 주입받음
  constructor(
    private todos: TodosService,
  ) {}
}
FastAPI — Depends
# 함수 인자에서 주입받음
@router.get("/{todo_id}")
def get_todo(
    todo_id: int,
    db: DbSession): ...

생성자 주입 ↔ 함수 인자 주입. 클래스 없이 함수 단위로 더 가볍게.

계층 분리(MVC) — 왜 나누나

지난 레슨의 라우터는 "요청 받기 + 비즈니스 판단 + DB 쿼리"를 한 함수에 다 했습니다. 작을 땐 괜찮지만, 로직이 커지면 라우터가 비대해지고 재사용·테스트가 어려워집니다. 그래서 책임을 계층으로 나눕니다. 흔히 MVC(Model·View·Controller)라고 부르는 구조인데, JSON API에서는 화면(View)이 없고 응답 JSON이 그 자리를 대신하므로 실제로는 라우터 · 서비스 · 모델(리포지토리) 세 층으로 나눕니다.

계층역할NestJS 대응
라우터(컨트롤러)요청 받기 · 응답 보내기 · 검증Controller
서비스비즈니스 로직 (무엇을·어떻게)Service
리포지토리/모델DB 접근 (쿼리·저장)Repository / Entity
Router → Service → Repository/Model → DB. 책임이 한 방향으로 흐른다.
♻️

리팩터링 — 라우터의 로직을 서비스로

이제 라우터에 박혀 있던 DB 코드를 services.py로 옮깁니다. 라우터는 "받아서 서비스에 넘기고 결과를 돌려주는" 얇은 껍데기가 됩니다. 먼저 서비스가 던질 우리만의 예외를 하나 만듭니다. 파이썬에서 Exception을 상속한 클래스는 raise로 던질 수 있는 예외가 되고, super().__init__(...)은 부모 Exception에 에러 메시지를 넘겨 주는 줄입니다.

pythonexceptions.py
class TodoNotFoundError(Exception):
    def __init__(self, todo_id: int) -> None:
        self.todo_id = todo_id                       # 핸들러가 꺼내 쓸 수 있게 보관
        super().__init__(f"Todo {todo_id} not found")

이 예외는 상태코드도 JSON도 모르는 "할 일이 없다"는 사실 그 자체입니다. 이걸 404 HTTP 응답으로 바꾸는 일은 03의 전역 예외 핸들러가 맡습니다. 이제 서비스 함수들입니다.

pythonservices.py
from sqlalchemy.orm import Session
from models import Todo
from schemas import TodoCreate, TodoUpdate
from exceptions import TodoNotFoundError   # 도메인 예외(HTTP 모름)

def get_todo(db: Session, todo_id: int) -> Todo:
    todo = db.get(Todo, todo_id)
    if todo is None:
        raise TodoNotFoundError(todo_id)   # HTTPException 아님!
    return todo

def create_todo(db: Session, data: TodoCreate) -> Todo:
    todo = Todo(title=data.title, done=data.done)
    db.add(todo)
    db.commit()
    db.refresh(todo)
    return todo

def update_todo(db: Session, todo_id: int, data: TodoUpdate) -> Todo:
    todo = get_todo(db, todo_id)            # 없으면 위의 예외가 그대로 올라감
    for field, value in data.model_dump(exclude_unset=True).items():
        setattr(todo, field, value)
    db.commit()
    db.refresh(todo)
    return todo
pythonrouters/todos.py
import services
from fastapi import APIRouter, status
from schemas import TodoCreate, TodoUpdate, TodoPublic
from database import DbSession   # ← Annotated[Session, Depends(get_db)] 별칭

router = APIRouter(prefix="/todos", tags=["todos"])

@router.get("/{todo_id}", response_model=TodoPublic)
def get_todo(todo_id: int, db: DbSession):
    return services.get_todo(db, todo_id)   # 위임만 한다

@router.post("", response_model=TodoPublic,
             status_code=status.HTTP_201_CREATED)
def create_todo(payload: TodoCreate, db: DbSession):
    return services.create_todo(db, payload)
서비스는 HTTP를 몰라야 한다. 서비스 계층에서 HTTPException(상태코드, 헤더)을 던지면, 그 로직은 "웹 요청 안에서만" 쓸 수 있게 묶여 버립니다. 대신 TodoNotFoundError 같은 도메인 예외를 던지고, HTTP 변환은 다음 레슨의 전역 예외 핸들러에 맡기세요. 그래야 서비스를 배치 작업·CLI·테스트 어디서든 재사용할 수 있습니다.
commit은 누가 하나. 이 예제는 단순함을 위해 서비스 함수 안에서 commit()합니다. 지금은 "한 요청 = 한 작업 = 한 커밋"으로 익히면 충분합니다. 한 요청에서 서비스 함수 여러 개를 부르며 하나의 트랜잭션으로 묶어야 하는 경우는 나중 주차에서 다룹니다.

셀프 체크

Q FastAPI의 Depends는 NestJS의 무엇에 대응하나요?

NestJS의 DI 컨테이너(@Injectable + 생성자 주입)에 대응합니다. 차이는 주입 자리뿐 — Nest는 생성자, FastAPI는 함수 인자입니다.

Q def get_todo(todo_id: int, db: DbSession)에서 db는 누가 넣어 주나요?

FastAPI가 넣어 줍니다. DbSession 안에 Depends(get_db) 쪽지가 붙어 있어서, 요청마다 FastAPI가 get_db()를 호출해 나온 세션을 db 자리에 꽂습니다. 클라이언트가 보내는 값이 아닙니다.

Q get_db가 일반 return이 아니라 yield를 쓰는 이유는?

요청 처리가 끝난 뒤 정리(세션 닫기)를 보장하기 위해서입니다. yield 위쪽에서 세션을 열고, 라우트에 넘긴 뒤, 응답이 끝나면 yield 아래쪽(finally: db.close())이 실행됩니다. 예외가 나도 세션이 누수되지 않습니다.

Q 라우터의 로직을 서비스로 빼면 뭐가 좋아지나요?

책임이 분리됩니다. 라우터는 요청/응답만 담당하고, 비즈니스 로직은 서비스에 모입니다. 그 결과 ① 같은 로직을 여러 라우트나 배치 작업에서 재사용할 수 있고, ② 서비스 함수를 HTTP 없이 단위 테스트할 수 있으며, ③ 라우터가 얇아져 읽기 쉬워집니다.
