외부 API 호출 — 이번엔 우리가 클라이언트다

백엔드는 혼자 일하지 않습니다. 결제·알림·다른 마이크로서비스를 HTTP로 호출하죠. 그 순간 우리 서버가 또 다른 서버의 클라이언트가 됩니다. 비동기 환경의 표준 도구 httpx.AsyncClient를 익힙니다.

한 줄 요약. 비동기 엔드포인트에서 외부 API를 부를 땐 반드시 httpx.AsyncClient를 쓴다. requests는 동기라 이벤트 루프를 막는다. 클라이언트는 async with로 열고, await client.get(...)으로 호출하고, 타임아웃과 상태코드 검사를 빼먹지 않는다.

학습 목표

  • 백엔드가 다른 서비스를 호출하는 상황(MSA·결제·알림)을 이해한다
  • httpx.AsyncClient로 비동기 HTTP 요청을 보낸다
  • requests를 async 엔드포인트에서 쓰면 안 되는 이유를 안다
  • Lifespan + app.state로 클라이언트 하나를 만들어 재사용한다
  • 타임아웃·상태코드 확인·예외 처리로 외부 호출을 안전하게 만든다
🔁

백엔드가 클라이언트가 되는 순간

지금까지 우리 서버는 프론트엔드의 요청을 받기만 했습니다. 하지만 결제 게이트웨이를 부르거나, 카카오·슬랙으로 알림을 보내거나, 주문 서비스가 재고 서비스를 호출할 때는 우리가 직접 다른 서버에 요청을 보내는 쪽이 됩니다. Week 1에서 본 대로 클라이언트와 서버는 고정된 역할이 아니라 "요청을 보내는 쪽 / 받는 쪽"일 뿐이라, 같은 서버가 상황에 따라 둘 다 될 수 있습니다.

프론트 → 우리 서버 → 외부 API → 응답 가공 → 프론트. 가운데에서 우리는 클라이언트가 된다.
🔌

httpx.AsyncClient — 기본 사용법

httpx는 requests와 거의 같은 API를 제공하면서, 비동기(async/await)를 정식 지원합니다. 핵심은 AsyncClient를 async with로 열고, 메서드 앞에 await를 붙이는 것입니다.

python
import httpx
from fastapi import APIRouter

router = APIRouter()

@router.get("/weather/{city}")
async def get_weather(city: str):
    url = f"https://api.example.com/weather?q={city}"
    async with httpx.AsyncClient() as client:
        r = await client.get(url)
    data = r.json()
    return {"city": city, "temp": data["temp"]}

async with로 열면 블록을 벗어날 때 연결이 자동으로 정리됩니다. POST·헤더·바디도 requests와 똑같습니다: await client.post(url, json={...}, headers={...}).

⚠️

함정 — requests는 async에서 금물

가장 흔한 실수입니다. 익숙하다고 requests를 async def 안에서 쓰면 이렇게 됩니다.

python
import requests

@router.get("/bad")
async def bad():
    url = "https://api.example.com/ping"
    r = requests.get(url)     # ❌ await를 걸 수 없는 동기 호출 — 응답 올 때까지 루프가 멈춘다
    return r.json()
Lesson 01의 동기 DB와 같은 문제입니다 (Week 4 함정). requests.get()은 await가 없는 동기 호출이라, async def 안에 있어도 외부 응답을 기다리는 동안 이벤트 루프가 통째로 막힙니다. 고치는 법은 위 기본 사용법 코드 그대로입니다 — 비동기 엔드포인트에서는 HTTP도 httpx.
정 requests를 써야 한다면. 레거시 코드 등 불가피하게 동기 라이브러리를 호출해야 하면 from fastapi.concurrency import run_in_threadpool 뒤에 r = await run_in_threadpool(requests.get, url)로 별도 스레드에 떠넘깁니다. 기다리는 건 그 스레드이고 루프 스레드는 자유로워지므로 막히지 않습니다 — Week 4에서 def 엔드포인트가 스레드풀로 가던 것과 같은 원리입니다. 새 코드라면 그냥 httpx를 쓰는 게 훨씬 깔끔합니다.
⏱️

타임아웃 & 클라이언트 재사용

외부 호출에서 가장 무서운 건 상대가 응답을 안 주는 경우입니다. 타임아웃을 안 걸면 우리 요청 처리도 무한정 매달리므로 timeout=5.0처럼 항상 상한을 둡니다. 두 번째 문제는 비용입니다. 서버와 연결을 새로 맺는 데는 시간이 듭니다 — TCP 연결을 열고, https라면 암호화 방식까지 협상해야 하죠(이 왕복을 핸드셰이크라고 부릅니다). 위 기본 코드처럼 매 요청 async with httpx.AsyncClient()로 새로 열면 이 비용을 요청마다 다시 냅니다. 클라이언트 하나를 만들어 두고 계속 쓰면 한 번 맺은 연결을 끊지 않고 다음 요청에 재사용(keep-alive)하므로 훨씬 빠릅니다.

그래서 Lesson 01의 DB 엔진과 똑같은 패턴을 씁니다 — lifespan 시작에서 하나 만들고, 종료에서 닫기. 만든 클라이언트는 app.state에 넣어 둡니다. app.state는 FastAPI 앱 객체에 달린 빈 주머니 같은 속성이라, 아무 값이나 붙여 두면 라우트에서 request.app.state로 꺼낼 수 있습니다.

python
from contextlib import asynccontextmanager
import httpx
from fastapi import FastAPI

@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.http = httpx.AsyncClient(timeout=5.0)   # 🟢 startup — 한 번만 만든다 (초 단위)
    yield
    await app.state.http.aclose()                     # 🔴 shutdown — 열린 연결 정리

app = FastAPI(lifespan=lifespan)

라우트에서는 request: Request 매개변수를 받아 client = request.app.state.http로 꺼내 쓰면 됩니다. 바로 아래 에러 처리 코드가 이 방식을 그대로 씁니다.

🚨

에러 처리 — 상태코드 & 예외

외부 API는 4xx·5xx를 줄 수도, 아예 응답을 안 줄 수도 있습니다. 이 실패를 우리 API의 적절한 응답으로 번역해야 합니다. Week 6의 HTTPException과 자연스럽게 이어집니다.

python
import httpx
from fastapi import APIRouter, HTTPException, Request

@router.get("/weather/{city}")
async def get_weather(city: str, request: Request):
    client = request.app.state.http            # lifespan에서 만들어 둔 클라이언트
    url = f"https://api.example.com/weather?q={city}"
    try:
        r = await client.get(url)
        r.raise_for_status()                   # 4xx·5xx 면 여기서 예외 발생
    except httpx.TimeoutException:
        raise HTTPException(504, "외부 API 응답 시간 초과")
    except httpx.ConnectError:
        raise HTTPException(503, "외부 API에 연결할 수 없음")
    except httpx.HTTPStatusError as e:
        raise HTTPException(502, f"외부 API 오류: {e.response.status_code}")
    return r.json()
httpx는 404를 받아도 예외를 던지지 않습니다. 외부가 에러 상태코드를 줘도 await client.get()은 조용히 Response 객체를 돌려줍니다. 그래서 r.raise_for_status()를 빼먹으면 에러 페이지 HTML을 정상 데이터로 착각해 그대로 진행합니다. 응답을 받은 직후 한 줄을 습관처럼 붙이세요.

번역할 때 쓰는 상태코드는 5xx 중에서도 "관문(gateway) 너머가 문제"라는 뜻을 가진 것들입니다. 프론트 입장에서 우리 서버는 외부 API로 가는 관문이니까요.

httpx 예외의미권장 응답
TimeoutException타임아웃 초과504 Gateway Timeout — 관문 너머가 제때 응답하지 않음
ConnectError연결 자체 실패503 Service Unavailable — 의존하는 서비스를 쓸 수 없음
HTTPStatusError외부가 에러 상태코드 반환502 Bad Gateway — 관문 너머에서 잘못된 응답이 옴
외부 실패를 500으로 흘려보내지 마라. 외부 API가 죽었는데 우리가 그냥 500 Internal Server Error를 내면, 프론트는 "우리 서버 버그"로 오해합니다. "외부 의존성 문제"라는 의미를 담은 502/503/504로 번역해 주는 게 디버깅과 모니터링에 훨씬 유리합니다.

NestJS와 비교 — HttpService(axios) vs httpx

NestJS에서 외부 API를 부를 땐 HttpModule을 import하고 HttpService를 주입받았죠. HttpService는 axios를 감싸면서 결과를 Observable(RxJS 스트림)로 돌려주기 때문에 firstValueFrom()으로 Promise로 바꾸는 한 단계가 끼었습니다. httpx는 그 단계가 없습니다 — 그냥 await. 대신 axios가 알아서 해 주던 에러 throw는 우리 몫입니다(위 에러 처리 참고).

NestJS — HttpService
constructor(
  private http: HttpService,
) {}

async getUser(url: string) {
  const src = this.http.get(url);
  const res = await
    firstValueFrom(src);
  return res.data; // 4xx→throw
}

Observable → Promise 변환이 한 겹 낀다.

FastAPI — httpx
async def get_user(url: str):
    r = await client.get(url)
    r.raise_for_status()  # 필수
    return r.json()

바로 await. 대신 에러 검사는 내 몫.

NestJS (HttpModule)FastAPI (httpx)
HttpService (axios 래퍼)httpx.AsyncClient
Observable → firstValueFrom()그냥 await client.get(...)
4xx·5xx → 자동으로 throwraise_for_status() 를 직접 호출
HttpModule.register({ timeout: 5000 })AsyncClient(timeout=5.0)
DI가 axios 인스턴스를 싱글턴 보관lifespan + app.state.http 로 직접 보관
타임아웃 단위를 헷갈리지 마세요. axios·NestJS는 밀리초(timeout: 5000 = 5초), httpx는 초(timeout=5.0 = 5초)입니다. 습관대로 timeout=5000이라고 쓰면 5000초(약 83분)가 되어 사실상 타임아웃이 없는 것과 같아집니다. 조용히 장애로 번지는 종류의 실수라 특히 조심하세요.

셀프 체크

Q async 엔드포인트에서 requests를 쓰면 왜 안 되나요?

requests.get()에는 await를 붙일 수 없어서, 외부 응답을 기다리는 동안 루프가 양보를 못 하기 때문입니다. await가 되는 httpx.AsyncClient를 써야 그 시간에 다른 요청을 처리합니다.

Q 클라이언트를 매 요청마다 새로 만들지 말라는 이유는?

만들 때마다 연결을 새로 맺는 비용(핸드셰이크)을 내기 때문입니다. lifespan에서 하나 만들어 app.state.http에 두면 맺어 둔 연결을 다음 요청에 재사용합니다.

Q 외부 API가 타임아웃 나면 클라이언트엔 몇 번 코드를 줘야 하나요?

504 Gateway Timeout입니다. "우리 버그"가 아니라 "관문 너머(외부)가 문제"라는 뜻을 담아야 프론트와 모니터링이 오해하지 않습니다.
