OTP & Background Tasks — 일회용 코드와 후처리

문자로 받는 일회용 인증번호(OTP)를 Redis로 구현하고, 그 코드를 문자·메일로 발송하는 느린 작업을 응답과 분리하는 법을 배웁니다.

한 줄 요약. OTP는 Redis에 짧은 TTL로 저장하고 한 번 쓰면 지운다. 발송처럼 느린 일은 BackgroundTasks로 응답 뒤에 처리하되, 무겁거나 반드시 끝나야 하는 일은 별도 워커(Celery 등)에 맡긴다.

학습 목표

  • OTP를 생성해 Redis에 TTL과 함께 저장하고, 검증 후 삭제한다
  • BackgroundTasks로 응답을 먼저 보내고 후처리를 뒤에 실행한다
  • OTP 요청·검증 API의 전체 흐름을 그린다
  • BackgroundTasks의 한계와 워커(Celery)가 필요한 지점을 안다
🔢

OTP — 한 번 쓰고 버리는 코드

OTP(One-Time Password)는 “문자로 온 6자리 인증번호”처럼 딱 한 번, 짧은 시간만 유효한 코드입니다. 본인 확인, 2단계 인증 등에 쓰이죠. 두 가지 성질이 핵심입니다 — 짧은 수명과 1회 소비. 이 둘은 Lesson 2에서 본 Redis의 TTL과 delete로 그대로 구현됩니다. 몇 분 뒤 버릴 값을 굳이 PostgreSQL 테이블에 넣고 지우는 일을 반복할 이유가 없으니, “잠깐 쓰고 버리는” 데이터는 책상 위(Redis)에 두는 것입니다.

비유 — 3분 안에 쓰는 보관함 번호. OTP는 무인 택배함의 임시 비밀번호와 같습니다. 발급되면 3분만 유효하고, 한 번 문을 열면 그 번호는 폐기됩니다. 시간이 지나면 저절로 사라져 따로 청소할 필요도 없죠 — Redis가 TTL로 알아서 지워줍니다.
python
import secrets
import redis.asyncio as redis

r = redis.from_url("redis://localhost:6379", decode_responses=True)
OTP_TTL = 180  # 3분

async def issue_otp(phone: str) -> str:
    # 0~999999 난수를 6자리로, 앞을 0으로 채움 (:06d) → "004213"
    code = f"{secrets.randbelow(1000000):06d}"
    await r.set(f"otp:{phone}", code, ex=OTP_TTL)   # 3분 뒤 자동 삭제
    return code

async def verify_otp(phone: str, code: str) -> bool:
    saved = await r.get(f"otp:{phone}")   # 만료됐으면 None
    if saved is None or saved != code:
        return False
    await r.delete(f"otp:{phone}")        # 맞췄으면 즉시 폐기
    return True
OTP 보안 기본기. ① 코드는 random이 아니라 secrets로 만듭니다. random은 시뮬레이션용이라 앞의 출력 몇 개를 보면 다음 값을 계산해 낼 수 있지만, secrets는 예측이 불가능하도록 운영체제의 난수원을 씁니다. ② 6자리는 경우의 수가 100만뿐이라 다 찔러보는 무차별 대입이 가능하니, 시도 횟수 제한을 둡니다 — 예를 들어 r.incr(f"otp_try:{phone}")로 실패 횟수를 세고(같은 키에 expire로 TTL), 5회가 넘으면 검증을 거부하는 식입니다.

이 두 함수를 라우트로 감싸면 API가 됩니다. 그런데 발급 뒤에는 문자를 보내는 느린 일이 끼어 있죠. 그걸 어떻게 다룰지가 다음 섹션입니다.

BackgroundTasks — 응답 먼저, 일은 나중에

OTP 문자 발송, 가입 환영 메일, 알림 푸시 — 이런 작업은 사용자가 결과를 기다릴 필요가 없습니다. 그런데 발송이 2초 걸린다고 응답을 2초 늦추면 손해죠. FastAPI의 BackgroundTasks는 응답을 먼저 돌려주고, 등록한 작업을 그 뒤에 실행합니다. 라우트 파라미터에 bg: BackgroundTasks를 선언하면 FastAPI가 할 일 목록을 하나 넣어 주고, 거기에 bg.add_task(함수, 인자...)로 적어 두기만 하면 됩니다.

비유 — 손님 보내고 나서 설거지. 식당에서 손님이 식사를 마치면 먼저 보내드리고(응답 반환), 설거지는 그 다음에 합니다(백그라운드 작업). 손님을 설거지 끝날 때까지 붙잡아두지 않죠.
python
from fastapi import APIRouter, BackgroundTasks, HTTPException

router = APIRouter()

def send_sms(phone: str, code: str):
    ...  # 느린 I/O — 문자 발송 업체 API 호출

@router.post("/otp/request")
async def request_otp(phone: str, bg: BackgroundTasks):
    code = await issue_otp(phone)
    bg.add_task(send_sms, phone, code)   # 등록만 — 지금 실행 X
    return {"message": "인증번호를 발송했습니다"}  # code 는 응답에 넣지 않음

@router.post("/otp/verify")
async def check_otp(phone: str, code: str):
    if not await verify_otp(phone, code):
        raise HTTPException(400, "인증번호가 틀렸거나 만료되었습니다")
    return {"verified": True}

phone: str 같은 단순 타입은 Week 2 규칙대로 쿼리 파라미터로 들어옵니다(POST /otp/request?phone=010...). 예제를 짧게 하려고 그런 것이고, 실제 서비스라면 Pydantic 모델로 body에 담으세요.

위 두 라우트를 한 장면으로. ③은 응답이 나간 뒤에 돈다.

BackgroundTasks의 한계 — 워커가 필요할 때

BackgroundTasks는 가볍고 편하지만, 등록한 작업이 같은 서버 프로세스 안에서, 그것도 메모리에만 적혀 있다가 실행됩니다. 그래서 한계가 분명합니다. 서버가 죽거나 재배포로 재시작되면 그 순간 처리 중이던(또는 아직 시작 못 한) 작업은 흔적 없이 사라지고, 실패해도 다시 시도해 주지 않습니다. 영상 인코딩이나 대량 배치처럼 오래 걸리는 일을 올리면 요청을 받아야 할 서버의 자원을 그 일이 잠식합니다.

이럴 때 쓰는 것이 작업 큐 + 워커입니다. 서버는 “할 일”을 Redis 같은 저장소의 큐(줄)에 적어 두기만 하고, 서버와 별도로 떠 있는 워커(일만 하는 프로세스)가 그 줄에서 하나씩 꺼내 처리합니다. 할 일이 서버 메모리가 아니라 저장소에 남아 있으니 서버가 죽어도 사라지지 않고, 실패하면 다시 시도하고, 결과도 추적할 수 있습니다(이런 성질을 내구성이라 합니다). 파이썬에선 Celery(+ Redis/RabbitMQ)나 더 가벼운 ARQ가 이 역할을 합니다.

기준은 하나. 메일 한 통, 문자 한 통처럼 짧고 가볍고 “한 번쯤 못 가도 괜찮은” 후처리는 BackgroundTasks. 무겁거나, 오래 걸리거나, 반드시 완료돼야 하는(예: 결제 확정, 리포트 생성) 작업은 Celery/ARQ 워커.
📊

NestJS와 비교 — BackgroundTasks의 자리는 어디였나

재미있는 점 하나. NestJS에는 BackgroundTasks에 정확히 대응하는 기능이 없습니다. “응답을 먼저 보내고 그다음에 이 함수를 실행해줘”를 프레임워크가 대신 관리해 주지 않거든요. Nest에서 같은 일을 하려면 보통 셋 중 하나를 골랐습니다.

  • await 없이 그냥 호출(fire-and-forget — 쏘고 잊기) — 가장 흔하지만 가장 위험. 예외가 나면 아무도 모르고, 앱이 죽을 수도 있습니다.
  • @nestjs/event-emitter로 이벤트를 쏘고 @OnEvent 리스너가 처리 — 프로세스 안에서 도는 건 같지만 “응답 이후”가 보장되지는 않습니다.
  • @nestjs/bullmq로 Redis 큐에 넣고 별도 워커 프로세스가 처리 — 제대로 된 방법이지만 인프라가 하나 늘어납니다.

FastAPI의 BackgroundTasks는 그 중 첫 번째의 안전한 버전이고, 세 번째(BullMQ)의 자리는 파이썬에서 Celery/ARQ가 맡습니다. BullMQ에 익숙하다면 특히 주의하세요 — BullMQ가 기본으로 해 주던 재시도·재시작 복구를 BackgroundTasks는 해 주지 않습니다.

NestJS — BullMQ (큐 + 워커)
// ① 큐에 넣고 즉시 응답
await this.queue.add(
  'otp', { phone },
);

// ② 워커 — 별도 프로세스
@Processor('otp')
class W extends WorkerHost {
  async process(job: Job) {
    await sendSms(job.data);
  }
}

재시도·백오프(실패 시 간격을 늘려 재시도)·대시보드가 기본 제공.

FastAPI — Celery (같은 자리)
# ② 워커 — 별도 프로세스
@celery.task
def send_sms(phone, code): ...

# ① 라우트: 큐에 넣고 즉시 응답
send_sms.delay(phone, code)

짧은 후처리만이면 위의 bg.add_task 한 줄로 충분 — 인프라 0개.

셀프 체크

Q OTP를 Redis가 아니라 PostgreSQL 테이블에 저장하면 안 되나요?

되긴 하지만 손해입니다. 3분 뒤 버릴 값을 디스크에 쓰고, 만료된 행을 지우는 청소 작업까지 직접 돌려야 하니까요. Redis는 TTL 한 번으로 저장과 청소가 끝나고 속도도 훨씬 빠릅니다.

Q BackgroundTasks는 언제 쓰고, 언제 피해야 하나요?

“못 가도 괜찮은 메일 한 통”이면 쓰고, “꼭 끝나야 하는 결제 처리”나 몇 분씩 걸리는 일이면 피합니다. 후자는 할 일이 서버 메모리 밖(큐)에 남아야 하니 워커로 보냅니다.

Q OTP 발송 응답에 생성한 코드를 같이 내려주면 편하지 않나요?

절대 안 됩니다. 코드를 응답으로 내려주면 통신을 가로채는 누구나 인증을 통과할 수 있어 OTP의 의미가 사라집니다. 코드는 오직 본인 채널(문자·메일)로만 보내고, 서버 응답엔 “발송했습니다” 정도만 담습니다.
