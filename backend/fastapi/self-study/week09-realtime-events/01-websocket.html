WebSocket 서버가 먼저 말을 거는 채널

지금까지의 HTTP는 클라이언트가 물어봐야만 서버가 답했습니다. WebSocket은 한 번 연결해두면 양쪽이 아무 때나 메시지를 던질 수 있는 지속 회선입니다. 채팅·알림·실시간 대시보드의 토대죠.

한 줄 요약. WebSocket은 한 번 연결하면 끊을 때까지 유지되는 양방향 회선이다. 클라이언트가 묻지 않아도 서버가 먼저 메시지를 보낼 수 있다는 게 핵심이다.

학습 목표

  • HTTP와 WebSocket의 통신 모델 차이를 설명한다
  • @app.websocket으로 엔드포인트를 만들고, 브라우저에서 접속해 수신/송신 루프를 확인한다
  • WebSocketDisconnect로 연결 종료를 안전하게 처리한다
  • ConnectionManager로 다중 접속을 관리하고 broadcast로 채팅을 구현한다
📞

HTTP vs WebSocket — 편지 vs 전화

HTTP는 요청-응답 모델입니다. 클라이언트가 요청을 보내면 서버가 한 번 답하고 연결이 끝납니다. 서버에 새 소식이 생겨도 클라이언트가 다시 물어보기 전까지는 전해줄 방법이 없죠. 그래서 "새 알림 있나요?"를 1초마다 물어보는 폴링(polling)이 등장했지만, 대부분의 요청이 빈손으로 돌아와 낭비가 큽니다.

WebSocket은 시작만 HTTP로 합니다. 클라이언트가 "이 연결을 WebSocket으로 바꾸자"고 HTTP 요청을 보내고 서버가 동의하는 첫 한 번의 악수를 핸드셰이크라고 부릅니다. 그 뒤로는 연결을 끊지 않고 그대로 유지하며, 양쪽이 동시에, 아무 때나 메시지를 보낼 수 있습니다(이걸 full-duplex라고 합니다). 서버에 새 데이터가 생기면 서버가 먼저 밀어줄 수 있고(push), 이것이 실시간의 본질입니다.

비유 — 편지 vs 전화 통화. HTTP는 편지입니다. 할 말이 생길 때마다 봉투를 새로 붙여(연결을 새로 맺어) 보내고, 답장이 오면 끝입니다. WebSocket은 전화 통화입니다. 한 번 연결되면 끊기 전까지 양쪽이 자유롭게 말하고, 상대가 먼저 "여보세요, 새 소식!" 하고 말을 걸 수도 있습니다.
항목HTTPWebSocket
방향단방향 (요청→응답)양방향 (full-duplex)
연결요청마다 맺고 끊음한 번 맺고 유지
서버가 먼저 보내기불가 (폴링으로 흉내)가능 (push)
오버헤드매 요청 헤더 반복최초 1회 핸드셰이크 후 가벼움
주소 스킴http:// / https://ws:// / wss:// (wss는 https처럼 암호화된 쪽)
HTTP는 빈손 요청을 반복하지만, WebSocket은 한 회선으로 양방향 push가 가능하다.
🤔

언제 WebSocket을 쓰는가

모든 API를 WebSocket으로 바꿀 필요는 없습니다. 서버가 먼저, 자주, 작은 메시지를 밀어줘야 하는 상황에 쓰세요. 일반 CRUD는 HTTP가 더 단순하고 캐싱·로깅·인증 생태계도 잘 갖춰져 있습니다.

상황예시
실시간 채팅메신저, 고객 상담, 협업 댓글
알림 push"새 주문이 들어왔습니다" 즉시 표시
실시간 대시보드주가·트래픽·센서 값이 끊임없이 갱신
협업 편집여러 명이 같은 문서를 동시에 수정

가장 작은 WebSocket 엔드포인트

FastAPI는 @app.websocket 데코레이터로 WebSocket 라우트를 만듭니다. 함수 안에서 먼저 await websocket.accept()로 핸드셰이크를 수락하고, 그다음 수신/송신 루프를 돕니다. WebSocket 핸들러는 거의 항상 async def입니다.

pythonmain.py
from fastapi import FastAPI, WebSocket, WebSocketDisconnect

app = FastAPI()

@app.websocket("/ws")
async def echo(websocket: WebSocket):
    await websocket.accept()          # 핸드셰이크 수락 (필수!)
    try:
        while True:
            text = await websocket.receive_text()   # 클라이언트 메시지 대기
            await websocket.send_text(f"echo: {text}")  # 되돌려 보냄
    except WebSocketDisconnect:
        print("클라이언트 연결 종료")        # 정상적인 종료 신호

만들었으면 바로 붙어 봅시다. uvicorn main:app --reload로 서버를 띄운 뒤, 브라우저 개발자 도구의 콘솔에 아래 네 줄을 붙여 넣으면 됩니다. 브라우저에는 WebSocket 클라이언트가 내장되어 있어 따로 설치할 게 없습니다.

javascript브라우저 콘솔 — 접속해 보기
const ws = new WebSocket("ws://localhost:8000/ws");  // http 대신 ws
ws.onopen = () => ws.send("안녕");                       // 연결되면 한 마디
ws.onmessage = (e) => console.log("서버:", e.data);     // → "서버: echo: 안녕"
// 끝낼 때: ws.close()  → 서버 터미널에 "클라이언트 연결 종료"가 찍힌다

터미널이 편하다면 websocat ws://localhost:8000/ws(설치: brew install websocat)로 접속해 줄을 입력하는 방식으로도 똑같이 확인할 수 있습니다.

accept()를 빠뜨리면 연결이 안 된다. HTTP 라우트와 달리 WebSocket은 await websocket.accept()를 호출해야 비로소 연결이 성립합니다. 빠뜨리면 클라이언트 쪽에서 연결이 거부됩니다. 인증이 필요하면 accept() 전에 확인합니다. WebSocket에는 HTTP의 Authorization 헤더를 붙이기 어려워 보통 ws://.../ws?token=...처럼 쿼리 파라미터로 토큰을 받고(websocket.query_params["token"]), 통과하면 accept(), 아니면 await websocket.close(code=1008)로 거절합니다. 1008은 "정책 위반"을 뜻하는 표준 종료 코드로, 클라이언트가 "내가 뭔가 자격이 안 됐구나"를 알 수 있게 해 줍니다.
🔌

WebSocketDisconnect — 끊김을 다루기

사용자가 탭을 닫거나, 네트워크가 끊기거나, 새로고침하면 연결이 종료되고, 그 순간 대기 중이던 receive_text()가 WebSocketDisconnect 예외를 던집니다. 위 에코 코드에서 try / except WebSocketDisconnect로 루프를 감싼 이유가 이것입니다. 접속자가 한 명일 땐 예외를 잡고 로그만 남기면 되지만, 여러 명을 관리하기 시작하면 끊긴 연결을 목록에서 빼는 정리(cleanup)가 이 자리에서 일어나야 합니다. 그 일을 다음 절의 ConnectionManager가 맡습니다.

👥

ConnectionManager — 다중 접속 관리

채팅방에는 여러 명이 들어옵니다. "한 명이 보낸 메시지를 접속한 모두에게 뿌린다(broadcast)"를 하려면, 현재 살아있는 연결들을 어딘가 모아둬야 합니다. 그 역할을 하는 작은 클래스가 ConnectionManager입니다. 활성 연결 리스트를 들고, 연결/해제/방송 세 가지만 합니다.

pythonmain.py
class ConnectionManager:
    def __init__(self):
        self.active: list[WebSocket] = []   # 살아있는 연결들

    async def connect(self, ws: WebSocket):
        await ws.accept()
        self.active.append(ws)

    def disconnect(self, ws: WebSocket):
        self.active.remove(ws)        # 목록에서 제거 (정리)

    async def broadcast(self, message: str):
        for connection in self.active:
            await connection.send_text(message)  # 모두에게 전송

manager = ConnectionManager()

한 가지만 미리 짚어 둡니다. 위 broadcast는 흐름을 보기 쉽게 단순화한 버전이라, 보내는 도중 끊긴 소켓을 만나면 거기서 예외가 나 뒤에 남은 사람들이 메시지를 못 받습니다. 실전에서는 send_text를 try / except로 감싸 실패한 소켓을 목록에서 빼는 한 줄을 더 넣습니다.

broadcast는 왜 async인가. send_text는 네트워크로 데이터를 내보내는 I/O 작업이라 await로 기다려야 하고, await를 쓰는 함수는 async def여야 합니다. Week 4에서 배운 "I/O는 await로 양보한다"가 그대로 적용되는 자리입니다.
한 명이 보낸 메시지를 ConnectionManager가 받아 활성 연결 전체에 send_text로 뿌린다.
💬

간단 채팅 예제 — 다 합치기

이제 라우트 하나로 채팅방이 완성됩니다. 접속하면 manager에 등록하고, 메시지를 받을 때마다 모두에게 방송하고, 끊기면 목록에서 빼고 퇴장을 알립니다. 에코 서버에 있던 accept()가 사라진 게 아니라 manager.connect() 안으로 들어갔다는 점만 눈여겨보세요. 브라우저 탭 두 개에서 각각 ws://localhost:8000/ws/chat/민수, .../chat/영희로 접속해 보면 서로의 메시지가 보입니다.

pythonmain.py
@app.websocket("/ws/chat/{name}")
async def chat(websocket: WebSocket, name: str):
    await manager.connect(websocket)            # 안에서 accept()까지 해 준다
    await manager.broadcast(f"🟢 {name} 님 입장")
    try:
        while True:
            text = await websocket.receive_text()
            await manager.broadcast(f"{name}: {text}")  # 모두에게
    except WebSocketDisconnect:
        manager.disconnect(websocket)         # 정리
        await manager.broadcast(f"🔴 {name} 님 퇴장")
메모리 안의 리스트는 한 프로세스에만 산다. manager.active는 그 서버 프로세스의 메모리에 있는 리스트입니다. 서버를 여러 대(워커 여러 개)로 띄우면, A 서버에 붙은 사용자와 B 서버에 붙은 사용자는 서로의 메시지를 못 받습니다. 이 스케일아웃 문제를 푸는 것이 다음 강의의 메시지 브로커(Redis Pub/Sub)입니다.

NestJS와 비교 — Gateway가 대신 해주던 일들

"ConnectionManager를 왜 직접 만들었지?" 싶었다면, NestJS에서는 그 일을 Socket.IO라는 라이브러리가 대신 해 줬기 때문입니다. NestJS의 WebSocket Gateway는 기본적으로 Socket.IO 위에서 돌고, Socket.IO는 접속자 목록·전체 방송·방(room, 채팅방처럼 묶어서 보내기)을 이미 구현해 둔 상태라 this.server.emit() 한 줄이면 방송이 끝났습니다. FastAPI의 @app.websocket은 그보다 한 층 아래인 순수 WebSocket이라 아무도 접속자를 기억해 주지 않고, 그래서 그 명단(manager.active)을 우리가 직접 들고 있는 것입니다. 대신 무슨 일이 일어나는지 전부 내 코드 안에 보입니다.

NestJS — Gateway (선언형)
@WebSocketGateway()
export class ChatGw {
  @WebSocketServer()
  server: Server;

  @SubscribeMessage('chat')
  onChat(@MessageBody() t: any) {
    this.server.emit('chat', t);
  }
}

접속 목록·브로드캐스트를 Socket.IO가 관리.

FastAPI — 직접 루프
@app.websocket("/ws/chat")
async def chat(ws: WebSocket):
  await mgr.connect(ws)
  try:
    ...  # receive → broadcast
  except WebSocketDisconnect:
    mgr.disconnect(ws)

목록·방송·정리를 내가 관리(4~5절 코드).

NestJS (Socket.IO 기반)FastAPI (순수 WebSocket)
@WebSocketGateway() 클래스@app.websocket("/ws/...") 함수
@SubscribeMessage('chat') — 이벤트 이름별 분기while True: 루프 안에서 직접 파싱
handleConnection() / handleDisconnect()await ws.accept() / except WebSocketDisconnect
server.emit() — 전체 방송 (내장)manager.broadcast() — 직접 구현
client.join('room') · server.to('room').emit()방 개념 없음 → dict[room, list[WebSocket]] 직접
Socket.IO는 "그냥 WebSocket"이 아니다. Socket.IO는 WebSocket 위에 자기만의 규칙을 한 겹 더 얹은 별개 규격이라, 브라우저의 new WebSocket("ws://...")으로는 NestJS Gateway에 붙을 수 없고, 반대로 socket.io-client로는 FastAPI의 @app.websocket에 붙을 수 없습니다. 양쪽이 같은 규격을 써야 합니다. 프론트가 이미 socket.io-client를 쓰고 있다면 서버에 python-socketio를 얹어 맞추면 됩니다.

셀프 체크

Q HTTP 폴링 대신 WebSocket을 쓰면 뭐가 좋아지나요?

물어볼 필요가 없어집니다. 연결을 유지해 두면 서버가 데이터가 생긴 순간 바로 밀어주니, 빈손 요청이 사라지고 지연도 줄어듭니다.

Q WebSocketDisconnect를 처리하지 않으면 어떻게 되나요?

끊긴 연결이 manager 목록에 그대로 남아, 다음 broadcast 때 죽은 소켓에 보내다가 예외가 납니다. 예외를 잡는 자리에서 disconnect()로 목록에서 빼 줘야 합니다.

Q broadcast 함수는 왜 async로 만들어야 하나요?

안에서 호출하는 send_text가 네트워크 I/O라 await가 붙고, await를 쓰는 함수는 async def여야 하기 때문입니다.
