메시지 브로커 발행하면, 듣는 쪽이 받는다

서비스끼리 직접 함수를 호출하면 단단히 묶입니다(결합). 이벤트를 발행하고 관심 있는 쪽이 구독하게 만들면, 서로를 몰라도 협력할 수 있습니다. 그 중계소가 메시지 브로커입니다.

한 줄 요약. 브로커는 발행자(publisher)와 구독자(subscriber) 사이의 중계소다. 발행자는 채널에 메시지를 던지고, 구독자는 관심 채널만 골라 받는다. 둘이 서로를 직접 호출하지 않으니 결합이 풀리고(디커플링) 비동기로 흘러간다.

학습 목표

  • 동기 직접 호출과 이벤트 발행의 차이, 그리고 디커플링의 의미를 안다
  • 메시지 브로커가 왜 비동기·버퍼링·결합도 측면에서 유리한지 설명한다
  • Redis를 띄우고 Redis Pub/Sub의 publish / subscribe 기본 흐름을 작성한다
  • WebSocket과 결합해 여러 서버 인스턴스 간 broadcast(스케일아웃)를 구현하고, 구독 루프를 lifespan에서 띄운다
🧩

이벤트 기반 아키텍처 — 결합도를 낮추기

주문이 들어오면 ①재고 차감, ②알림 발송, ③통계 집계를 해야 한다고 합시다. 동기 직접 호출 방식은 주문 서비스가 이 세 서비스를 차례로 호출합니다.

pythonorder_service.py — 직접 호출 (강결합)
def create_order(order):
    save(order)
    inventory.decrease(order)   # 재고 서비스를 직접 안다
    notifier.send(order)        # 알림 서비스를 직접 안다
    stats.record(order)        # 통계 서비스를 직접 안다
    # 알림 서비스가 느리거나 죽으면? 주문 전체가 막힌다.

문제는 두 가지입니다. 주문 서비스가 세 서비스를 전부 알아야 하고(강결합), 하나라도 느리거나 죽으면 주문 응답이 통째로 지연/실패합니다. 새 구독자(예: "배송 예측")를 추가하려면 주문 코드를 또 고쳐야 하죠.

이벤트 발행 방식은 주문 서비스가 그냥 "order.created" 이벤트 하나만 브로커에 던집니다. 누가 듣는지는 모르고, 알 필요도 없습니다. 재고·알림·통계는 각자 그 이벤트를 구독해 알아서 처리합니다. 아래 broker는 설명용 가상 객체이고, 실제 Redis에서는 3절의 r.publish가 그 자리에 들어갑니다.

pythonorder_service.py — 이벤트 발행 (느슨한 결합, 개념 코드)
def create_order(order):
    save(order)
    broker.publish("order.created", order)  # 던지고 끝
    # 구독자가 몇이든, 추가/제거돼도 이 코드는 안 바뀐다.
비유 — 방송국. 브로커는 방송국입니다. DJ(발행자)는 청취자가 몇 명인지 모른 채 자기 채널로 방송하고, 청취자(구독자)는 관심 있는 주파수(채널)만 맞춰 듣습니다. DJ와 청취자는 서로를 직접 알 필요가 없고, 청취자가 한 명 늘거나 줄어도 방송은 그대로입니다.

왜 메시지 브로커인가 — 3가지 이득

이득의미
비동기발행자는 처리 완료를 기다리지 않는다. 주문 응답이 알림 발송 속도에 묶이지 않음
버퍼링트래픽이 몰려도 브로커가 메시지를 쌓아 두었다가 구독자 속도에 맞춰 흘려보낸다(완충). 단, 이건 큐 계열 브로커(RabbitMQ 등)의 이득이고, 이번에 쓸 Redis Pub/Sub은 쌓아 두지 않는다(5절)
디커플링발행자 코드를 건드리지 않고 구독자를 자유롭게 추가/제거
하나의 발행이 채널을 거쳐 구독한 모든 서비스로 퍼진다.
📡

Redis Pub/Sub — 가장 쉬운 시작

Redis는 Week 8에서 토큰 저장에 썼던 그 인메모리 저장소인데, 가벼운 메시지 브로커 기능도 함께 들어 있습니다. publish(channel, msg)로 채널에 메시지를 던지고, subscribe(channel)로 채널을 구독합니다. 아직 Redis가 안 떠 있다면 Week 5·01의 compose에 서비스 하나를 보태거나, 일회용으로 docker run 한 줄이면 됩니다.

yamldocker-compose.yml — redis 서비스 추가 (또는 terminal 한 줄)
services:
  redis:
    image: redis:7
    ports: ["6379:6379"]
# compose 없이 바로: docker run -d -p 6379:6379 redis:7

FastAPI는 비동기이므로 비동기 클라이언트인 redis.asyncio를 씁니다(설치: uv add redis). 예전 튜토리얼에 보이는 aioredis는 지금은 redis-py 안으로 흡수된 구버전 이름입니다. redis.from_url("redis://호스트:포트")로 연결 객체를 만들고, 구독할 때는 r.pubsub()로 구독 전용 객체를 하나 꺼내 씁니다. 구독은 연결 하나를 계속 점유하는 동작이라 일반 명령과 분리해 두는 구조입니다.

pythonpublisher — 발행
import redis.asyncio as redis

r = redis.from_url("redis://localhost:6379")

async def publish_message(text: str):
    await r.publish("chat", text)   # "chat" 채널로 발행
pythonsubscriber — 구독 루프
async def subscribe_loop():
    pubsub = r.pubsub()
    await pubsub.subscribe("chat")          # "chat" 채널 구독
    async for message in pubsub.listen():
        if message["type"] == "message":    # 실제 메시지만
            data = message["data"].decode()
            print("받음:", data)
listen()은 메시지 외 신호도 흘려보낸다. pubsub.listen()이 처음 내보내는 항목은 "구독 성공(subscribe)" 같은 제어 메시지입니다. 그래서 message["type"] == "message"인 것만 골라 처리해야 합니다. 이 가드를 빠뜨리면 엉뚱한 신호를 데이터로 착각합니다.

WebSocket × Redis — 여러 서버로 스케일아웃

지난 강의 끝에서 본 문제, 즉 manager.active가 한 서버 프로세스의 메모리에만 있어 서버를 여러 대 띄우면 서로의 메시지를 못 받는 문제를 Redis Pub/Sub이 풉니다.

핵심 아이디어: 채팅 메시지를 직접 broadcast하지 말고, Redis 채널에 publish한다. 모든 서버 인스턴스는 같은 Redis 채널을 구독하고 있다가, 메시지가 오면 자기에게 붙은 WebSocket들에게만 뿌린다. 그러면 어느 서버에 붙었든 모두가 같은 메시지를 받습니다. 코드는 세 토막입니다. 지난 강의의 ConnectionManager(manager)와 위에서 만든 r을 그대로 씁니다.

pythonmain.py — 다중 서버 채팅
import asyncio
from contextlib import asynccontextmanager

# 1) Redis 구독 → 받은 메시지를 "이 서버"에 붙은 소켓들에게 broadcast
async def redis_to_clients():
    pubsub = r.pubsub()
    await pubsub.subscribe("chat")
    async for msg in pubsub.listen():
        if msg["type"] == "message":
            await manager.broadcast(msg["data"].decode())

# 2) 서버가 뜰 때 구독 루프를 백그라운드 태스크로 띄운다
@asynccontextmanager
async def lifespan(app: FastAPI):
    task = asyncio.create_task(redis_to_clients())  # 옆에서 계속 돌게
    yield                                           # ← 서버가 요청을 받는 구간
    task.cancel()                                   # 종료 시 정리

app = FastAPI(lifespan=lifespan)

# 3) 클라이언트 메시지 → 직접 broadcast 대신 Redis 채널로 발행
@app.websocket("/ws/chat")
async def chat(ws: WebSocket):
    await manager.connect(ws)
    try:
        while True:
            text = await ws.receive_text()
            await r.publish("chat", text)   # Redis로!
    except WebSocketDisconnect:
        manager.disconnect(ws)

②가 초보자에게 가장 낯선 부분입니다. redis_to_clients()는 async for로 영원히 끝나지 않는 루프라서, 그냥 await하면 서버 시작이 거기서 멈춰 버립니다. 그래서 asyncio.create_task()로 "이벤트 루프 옆에서 알아서 돌아라" 하고 띄워 두고 바로 다음 줄로 넘어갑니다. 이 일을 서버 시작 시 딱 한 번 하라고 Week 7·01에서 본 lifespan 안에 넣는 것입니다.

각 서버는 자기 소켓만 관리하고, 서버 간 전파는 Redis 채널이 책임진다 — 수평 확장의 핵심.

Pub/Sub vs 큐 — 그리고 더 강력한 브로커

한 줄로 짚고 갑니다. Redis Pub/Sub은 메시지를 보존하지 않습니다. 발행하는 순간 듣고 있던 구독자에게만 전달되고, 그때 끊겨 있던 구독자는 그 메시지를 영영 못 받습니다(fire-and-forget). 반면 큐(queue)는 소비될 때까지 메시지를 쌓아두므로, 잠깐 죽었던 워커도 나중에 처리할 수 있습니다.

도구특징적합한 곳
Redis Pub/Sub가볍고 빠름 · 보존 안 함실시간 알림·채팅처럼 한 메시지를 여럿에게 퍼뜨리기(fan-out)
RabbitMQ큐 · ACK(구독자가 "잘 받았다"고 답해야 큐에서 지움) · 재시도 · 라우팅(조건에 따라 다른 큐로 배달)작업 처리 보장이 중요한 비동기 작업
Kafka메시지를 로그처럼 오래 남겨 둠 · 대용량 · 옛 메시지부터 다시 읽기(재처리) 가능이벤트 스트리밍·데이터 파이프라인
도구 선택의 첫 질문은 "잃어도 되는가". 알림이 한 번쯤 빠져도 괜찮다면 Pub/Sub으로 충분하고, 결제 이벤트처럼 절대 잃으면 안 된다면 보존·ACK·재시도가 있는 RabbitMQ·Kafka, 또는 Redis Streams(메시지를 로그처럼 남겨 두는 Redis의 다른 기능)를 고릅니다.

NestJS와 비교 — Microservices 트랜스포트

NestJS에서는 이 이야기가 @nestjs/microservices라는 이름으로 있었습니다. client.emit('order.created', order)로 던지고, 받는 쪽은 @EventPattern('order.created')만 붙이면 끝이라 구독 루프나 message["type"] 검사는 한 줄도 쓰지 않았죠. Nest가 트랜스포트(transport)라는 얇은 껍데기로 그 루프를 감싸 준 것이고, 그 덕에 설정의 Transport.REDIS를 KAFKA로 바꾸는 것만으로 브로커를 갈아끼울 수 있었습니다. 이번 강의에서 손으로 쓴 코드가 바로 그 껍데기 안쪽입니다.

NestJS — @EventPattern
// 발행
this.client.emit(
  'order.created', order,
);

// 구독 — 루프가 없다
@EventPattern('order.created')
handle(@Payload() order: any) {
  this.stock.decrease(order);
}

직렬화·구독 루프를 프레임워크가 숨긴다.

FastAPI — redis.asyncio
# 발행
await r.publish(
    "order.created",
    json.dumps(order))

# 구독 — 루프를 직접 돈다
async for m in ps.listen():
    if m["type"] == "message":
        o = json.loads(m["data"])
        await decrease(o)

브로커 API가 그대로 드러난다(그래서 다 보인다).

NestJSFastAPI (이번 강의)
ClientProxy.emit() — 이벤트 발행await r.publish(channel, msg)
@EventPattern('x') — 구독 핸들러pubsub.listen() 루프 + type == "message" 검사
페이로드 JSON 직렬화 자동json.dumps / json.loads 직접
Transport.REDIS ↔ RMQ ↔ KAFKA 옵션 교체브로커별 라이브러리로 교체
Transport.REDIS의 내부이번 강의와 똑같은 Redis Pub/Sub — 유실 특성도 같다. 데코레이터가 메시지를 지켜 주진 않는다
@nestjs/event-emitter (프로세스 내부 이벤트)그냥 함수 호출 또는 BackgroundTasks
WebSocket 다중 서버 = @socket.io/redis-adapter4절의 redis_to_clients() — 같은 원리를 직접
파이썬에도 그 껍데기가 있다 — FastStream. 매번 listen() 루프를 쓰는 게 번거로워지면 FastStream이 @nestjs/microservices와 거의 같은 자리를 채웁니다. @broker.subscriber("order.created") 데코레이터 하나로 Redis·RabbitMQ·Kafka를 같은 방식으로 다루고 Pydantic 검증까지 붙습니다. 다만 원리를 먼저 손으로 겪어 본 뒤에 쓰는 것이 순서입니다.

셀프 체크

Q 직접 호출 대신 이벤트를 발행하면 결합도가 왜 낮아지나요?

발행자 코드에 구독자 이름이 한 줄도 안 들어가기 때문입니다. 구독자를 늘리거나 빼도, 구독자가 느려도 발행자는 영향을 받지 않습니다.

Q WebSocket 채팅에 Redis Pub/Sub을 왜 끼워 넣나요?

서버 여러 대가 하나의 채팅방처럼 보이게 하려고요. 각 서버는 자기 소켓만 알지만, 메시지를 Redis 채널로 돌리면 모든 서버가 같은 메시지를 받아 자기 소켓들에 뿌릴 수 있습니다.

Q Redis Pub/Sub과 메시지 큐의 결정적 차이는?

쌓아 두느냐입니다. Pub/Sub은 그 순간 듣고 있던 쪽에만 주고 끝이라 자리를 비운 구독자는 놓치고, 큐는 누군가 가져갈 때까지 보관합니다.
