10 Week 10 · 테스트 심화 & 배포

성능, 추측하지 말고 측정하라

"느린 것 같다"는 느낌이 아니라 숫자로 말해야 합니다. 부하 테스트로 RPS와 지연을 재고, I/O 바운드 작업에서 async가 처리량을 어떻게 끌어올리는지 확인한 뒤, 흔한 병목을 하나씩 걷어냅니다.

한 줄 요약. 성능은 측정이 먼저다. 부하를 걸어 RPS(처리량)와 p95 지연을 보고, 병목이 어디인지 숫자로 짚는다. I/O 바운드라면 async 전환이 같은 서버로 훨씬 많은 동시 요청을 처리하게 해준다.

학습 목표

  • 부하 테스트 도구(locust·wrk·ab)를 설치·실행하고, 출력에서 RPS와 지연(p50/p95/p99)을 읽는다
  • def · async def 안 블로킹 · async def + await 세 갈래가 부하 테스트 수치에 어떻게 나타나는지 안다
  • I/O 바운드에서 async 전환의 처리량 효과를 수치로 이해한다
  • 흔한 병목(동기 라이브러리·N+1·캐싱·커넥션 풀·워커 수)을 개선한다
📏

왜 측정하는가 — 감이 아니라 숫자

"이 엔드포인트가 느린 것 같아"는 디버깅의 출발점이 못 됩니다. 어디가, 얼마나, 어떤 부하에서 느린지 모르면 엉뚱한 곳을 고치게 되죠. 그래서 부하 테스트(load test)로 동시 요청을 쏟아붓고 다음 지표를 봅니다.

지표의미
RPS (requests/sec)초당 처리한 요청 수 = 처리량(throughput). 높을수록 좋다
p50 지연요청의 절반이 이 시간 안에 끝남 (중앙값)
p95 / p99 지연95% / 99%가 이 시간 안에 끝남. 꼬리 지연(tail latency) — 사용자 체감에 중요
평균이 아니라 p95·p99를 보라. 평균 지연은 소수의 느린 요청을 가립니다. 평균 50ms라도 p99가 2초면, 100명 중 1명은 2초를 기다린다는 뜻이죠. 사용자 경험은 꼬리(p95/p99)가 결정합니다. 그래서 성능 리포트는 백분위수로 읽습니다.
🛠️

부하 테스트 도구 — locust · wrk · ab

도구특징언제
ab (ApacheBench)설치 간단 · 단일 URL 빠른 측정"이 엔드포인트 RPS 대충 보자"
wrk가볍고 매우 고성능 · 멀티스레드높은 부하로 한계 RPS 측정
locust파이썬으로 시나리오 작성 · 웹 UI로그인→조회→주문 같은 흐름 재현

셋 다 하는 일은 같습니다. "가짜 사용자 N명이 동시에 이 주소를 계속 두드리면 서버가 초당 몇 개를 처리하고, 한 요청이 얼마나 걸리는가"를 재 줍니다. ab는 macOS에 기본으로 들어 있고, wrk는 brew install wrk, locust는 uv add --dev locust로 설치합니다. 먼저 uvicorn main:app으로 서버를 띄워 두고(--reload는 측정 땐 빼세요) 다른 터미널에서 돌립니다.

bashterminal — ab · wrk 빠른 측정
# ApacheBench: 총 1000 요청을, 동시에 50명이 두드리는 상태로
ab -n 1000 -c 50 http://localhost:8000/async

# wrk: 동시 연결 100개로 10초 동안 (-t4 는 wrk 자신이 쓸 스레드 수, 서버와 무관)
wrk -t4 -c100 -d10s --latency http://localhost:8000/async

출력은 길지만 볼 줄은 두 군데뿐입니다. 처리량은 Requests per second(ab) 또는 Requests/sec(wrk) 줄, 꼬리 지연은 백분위 표에서 95%·99% 줄입니다. wrk는 --latency를 붙여야 이 표가 나옵니다.

bashab 출력 — 볼 줄만 발췌
Requests per second:    412.30 [#/sec] (mean)   # ← RPS (처리량)
Time per request:       121.27 [ms] (mean)      #    요청 하나의 평균 (참고만)
Percentage of the requests served within a certain time (ms)
  50%    118                                    # ← p50
  95%    140                                    # ← p95
  99%    190                                    # ← p99
 100%    212  (longest request)
pythonlocustfile.py — 시나리오 부하
from locust import HttpUser, task

class ApiUser(HttpUser):
    @task
    def hit_async(self):
        self.client.get("/async")

# 실행 ① 웹 UI: locust -f locustfile.py --host http://localhost:8000
#        → http://localhost:8089 에서 사용자 수·증가 속도를 넣고 Start
# 실행 ② 터미널만: locust -f locustfile.py --host http://localhost:8000 \
#            --headless -u 50 -r 10 -t 30s     # 50명, 초당 10명씩 늘려, 30초
#        → 표의 req/s 열이 RPS, 아래 "Response time percentiles" 표의 95%·99% 열이 꼬리 지연

sync def vs async def — 처리량에 어떻게 나타나나

엔드포인트를 어떻게 쓰느냐에 따라 FastAPI의 동작이 세 갈래로 나뉜다는 것은 Week 4·02에서 배웠습니다. 여기서는 그 세 갈래가 부하 테스트 숫자에 어떻게 나타나는지만 봅니다. 각 요청이 100ms짜리 I/O 대기를 한다고 가정합니다.

작성 방식실제 동작부하를 걸면 보이는 모습
def (sync) 엔드포인트스레드풀에서 실행 (한 프로세스당 기본 약 40개 스레드)RPS가 약 40 × 10 = 400 근처에서 천장. 동시 접속이 그보다 많으면 p95가 계단처럼 늘어남
async def 안에서 블로킹 호출
(time.sleep, 동기 DB)		이벤트 루프 전체가 멈춤RPS 약 10. 동시 50명을 보내면 p95가 수 초. 세 갈래 중 최악
async def + await (async 드라이버)대기 중 루프가 다른 요청 처리RPS가 수백~수천까지 올라가고, 동시 접속을 늘려도 p95가 거의 그대로

숫자 하나만 구분해 두세요. 첫 행의 "40개"는 한 프로세스 안에서 def 엔드포인트를 돌리는 스레드 수(AnyIO 기본값)이고, 5절에 나오는 --workers 4는 프로세스 수입니다. 둘을 곱한 만큼이 동시에 처리되는 def 요청의 상한이 됩니다.

데모 — I/O 바운드에서 async의 효과

외부 API 호출이나 DB 조회처럼 기다리는 시간이 대부분인 I/O 바운드 작업을 가정합시다. 각 요청이 100ms를 "그냥 대기"한다고 할 때, 두 방식을 비교합니다. (아래는 code/main.py의 데모 엔드포인트 쌍입니다.)

pythonmain.py — 블로킹 vs 비동기
import asyncio, time

# ❌ async 함수 안에서 블로킹 → 이벤트 루프가 멈춘다
@app.get("/blocking")
async def blocking():
    time.sleep(0.1)        # 루프 전체를 막는 100ms
    return {"ok": True}

# ✅ await로 양보 → 대기 중 다른 요청 처리
@app.get("/async")
async def good_async():
    await asyncio.sleep(0.1)  # 100ms 동안 루프를 양보
    return {"ok": True}

같은 100ms 대기지만 결과는 극과 극입니다. /blocking은 요청을 사실상 한 줄로 세워 처리하므로 워커 1개 기준 RPS가 ~10에 머뭅니다(1초 ÷ 0.1초). /async는 대기 중 다른 요청을 받아 수백 개를 겹쳐 처리하므로 RPS가 수백~수천으로 치솟습니다. Week 4에서 배운 "I/O는 await로 양보"가 처리량으로 직결되는 장면입니다. 직접 보려면 2절의 ab -n 200 -c 50 http://localhost:8000/blocking과 같은 명령을 /async에도 돌려 Requests per second 줄을 나란히 놓아 보세요.

아래 숫자는 측정값이 아니라 설명용 예시. 다음 그래프의 RPS 값은 원리를 보여주기 위한 예시 수치입니다. 실제 값은 하드웨어·워커 수·작업 성격에 따라 달라지니 꼭 여러분 환경에서 재 보세요. 핵심은 절대값이 아니라 경향입니다.
I/O 바운드에서 await 기반 async는 대기 시간을 겹쳐 처리량을 크게 끌어올린다 (예시 수치).
async가 항상 이기는 건 아니다 — CPU 바운드. 위 효과는 대기가 많은 I/O 바운드에서의 이야기입니다. 이미지 처리·암호 해싱 같은 CPU 바운드는 양보할 대기 시간이 없어 async로 바꿔도 처리량이 늘지 않습니다. 오히려 단일 이벤트 루프를 점유해 해롭죠. CPU 작업은 run_in_executor(프로세스/스레드)나 별도 워커·작업 큐로 빼야 합니다.

흔한 병목 & 개선

측정으로 느린 지점을 찾았다면, 다음 순서로 의심해보세요.

병목증상개선
동기 라이브러리async 앱인데 처리량이 안 오름async 드라이버로 전환 (httpx, async DB), 불가피하면 def 엔드포인트나 run_in_executor(Week 4·02)
N+1 쿼리게시글 20개를 목록 조회 1번으로 가져온 뒤, 작성자를 글마다 1번씩 20번 더 조회하는 식으로 쿼리 수가 항목 수만큼 불어남JOIN이나 selectinload(연관 객체를 한 번에 미리 불러오는 SQLAlchemy 옵션)로 한두 번에 로드
반복 계산/조회같은 결과를 매번 다시 계산캐싱 — 결과를 Redis에 잠시 저장해 재사용
커넥션 풀 부족부하 시 DB 연결 차례를 기다리느라 지연 급증풀 크기 튜닝(pool_size, max_overflow)
워커 수CPU 코어를 못 쓰거나, 너무 많아 메모리 압박--workers를 코어 수에 맞춤. 시작점은 "코어 수와 같게", 더 올려도 재 보고 결정(Week 4·03)
bashterminal — 워커 늘려 띄우기
# 프로세스 4개 → CPU 코어 4개 활용 (CPU 바운드·전체 처리량에 유효)
uvicorn main:app --workers 4
# 운영에선 죽은 프로세스를 다시 띄워 주는 관리자(gunicorn)에 uvicorn 워커를 얹는 조합이 흔하다
개선 후엔 다시 측정하라. "고쳤으니 빨라졌겠지"도 추측입니다. 변경 전후로 같은 부하 테스트를 돌려 RPS·p95를 비교해야 정말 나아졌는지, 아니면 병목이 다른 곳으로 옮겨갔을 뿐인지 알 수 있습니다.
성능 작업은 한 번으로 끝나지 않는다 — 측정·병목·개선·재측정의 순환이다.

셀프 체크

Q ab 출력에서 처리량과 꼬리 지연은 각각 어느 줄에서 읽나요?

처리량은 Requests per second 줄, 꼬리 지연은 맨 아래 백분위 표의 95%·99% 줄입니다. Time per request의 평균은 참고만 합니다.

Q I/O 바운드에서 async가 처리량을 올리는 원리는?

한 요청이 응답을 기다리는 동안 await로 루프를 비워 주니, 그 빈 시간에 다른 요청들이 끼어들어 대기가 겹쳐 처리되기 때문입니다.

Q 3절의 "스레드 약 40개"와 5절의 --workers 4는 뭐가 다른가요?

40개는 한 프로세스 안에서 def 엔드포인트를 돌리는 스레드 수이고, --workers 4는 프로세스를 4개 띄우라는 뜻입니다. 둘을 곱한 만큼이 동시에 처리되는 def 요청의 상한입니다.

Q 성능 리포트에서 평균보다 p95·p99를 보는 이유는?

평균은 소수의 아주 느린 요청을 묻어 버리는데, 사용자가 불편을 느끼는 건 바로 그 느린 쪽이기 때문입니다.
