Alembic 마이그레이션 · DB 스키마의 버전 관리

개발 초기엔 create_all()로 충분했지만, 운영 중 "컬럼 하나 추가"가 필요한 순간 그 한계가 드러납니다. 스키마 변경을 안전하게 이력으로 남기는 도구 — Alembic을 익힙니다.

한 줄 요약. Alembic은 DB 스키마의 변경을 버전 파일(rev)로 기록해 두고 upgrade/downgrade로 앞뒤로 옮기는 도구 — 한마디로 DB 스키마용 git이다.

학습 목표

  • create_all()의 한계와 마이그레이션이 필요한 이유를 안다
  • alembic init → env.py에 target_metadata·DB 주소 연결 → revision → upgrade 흐름을 익힌다
  • 마이그레이션 파일의 upgrade/downgrade 구조를 읽는다
  • autogenerate의 한계를 알고 생성 결과를 검토한다
🤔

왜 마이그레이션인가

Week 5·02에서 Base.metadata.create_all(engine)로 테이블을 만들었습니다. 그런데 이 함수는 "존재하지 않는 테이블만 새로 만들" 뿐, 이미 있는 테이블에 컬럼을 더하거나 타입을 바꾸지는 못합니다. 운영 DB에 데이터가 쌓인 상태에서 "할 일에 우선순위 컬럼 추가"가 필요해지면, create_all()은 아무 일도 하지 않습니다. 그렇다고 테이블을 지우고 다시 만들 수도 없죠 — 데이터가 날아가니까요. 필요한 건 "지금 있는 테이블을 이렇게 고쳐라"를 순서대로 적어 두고 실행하는 도구, 즉 마이그레이션입니다.

비유 — Alembic은 DB 스키마용 git. 코드는 git으로 커밋·이력 관리하고, 문제가 생기면 이전 커밋으로 되돌립니다. DB 스키마도 똑같이 다뤄야 합니다. Alembic의 각 마이그레이션 파일은 하나의 커밋이고, upgrade는 앞으로 가는 변경, downgrade는 되돌리는 변경입니다. git의 HEAD처럼 head는 "가장 최신 버전"을 가리키는 이름이라, alembic upgrade head는 "최신 커밋까지 따라잡기"인 셈이죠.
⚙️

시작하기 — init과 env.py 연결

alembic init으로 마이그레이션 작업 폴더를 만들면 그 안에 env.py가 생깁니다. 이 파일에 우리 모델의 metadata(Week 5에서 만든 Base가 들고 있는 "테이블 설계도 모음")를 연결해야, autogenerate가 "모델 ↔ 실제 DB"의 차이를 감지할 수 있습니다. 손댈 곳은 딱 두 군데 — target_metadata와 DB 주소(sqlalchemy.url)입니다.

bash
# 프로젝트 루트에서 실행 → alembic/ 폴더 + alembic.ini 생성
$ alembic init alembic
#   alembic.ini          ← 설정 파일 (DB 주소 등)
#   alembic/env.py       ← 여기를 고친다
#   alembic/versions/    ← 마이그레이션 파일이 쌓이는 곳
python
# alembic/env.py — 자동 생성된 파일 윗부분에 이미 있는 줄들 사이를 고친다
import os
from alembic import context

config = context.config          # (자동 생성) alembic.ini 를 읽은 설정 객체

# ① DB 주소: alembic.ini 의 sqlalchemy.url 을 직접 써도 되지만,
#    비밀번호를 파일에 남기지 않으려면 환경 변수로 덮어쓴다
config.set_main_option("sqlalchemy.url", os.environ["DATABASE_URL"])

# ② 우리 모델의 Base 를 가져와 metadata 를 연결한다
from app.database import Base
from app import models           # 모든 모델이 Base 에 등록되도록 import

target_metadata = Base.metadata  # (자동 생성) 원래 None 이던 줄을 이렇게 바꾼다
모델 import를 빠뜨리지 말 것. autogenerate는 target_metadata에 등록된 모델만 봅니다. 모델은 models.py가 import될 때 비로소 Base에 등록되므로, env.py에서 이 import를 빼먹으면 그 테이블이 metadata에 없습니다. 그러면 Alembic은 "DB에는 있는데 모델에는 없네 → 모델에서 삭제된 테이블이구나"라고 오판해 drop_table을 만들어 버립니다.
⬆️

변경 만들기 — revision & upgrade

모델을 수정한 뒤 --autogenerate로 마이그레이션을 생성하면, Alembic이 "모델과 현재 DB의 차이"를 읽어 변경 스크립트 초안을 만들어 줍니다. 그다음 upgrade head로 적용합니다.

bash
# 1) 모델 변경 후, 차이를 읽어 마이그레이션 파일 생성
$ alembic revision --autogenerate -m "add priority to todos"

# 2) 최신 버전까지 적용 (DB 에 실제 반영)
$ alembic upgrade head

# 되돌리기: 직전 버전으로 한 칸
$ alembic downgrade -1

# 현재 버전 / 이력 확인
$ alembic current
$ alembic history

생성된 마이그레이션 파일(alembic/versions/ 안)은 upgrade()와 downgrade() 두 함수로 이뤄집니다. down_revision이 부모(이전) 버전을 가리켜 사슬처럼 연결되고, 그 사슬의 맨 끝이 head입니다.

python
from alembic import op        # op: ALTER TABLE 같은 DDL 을 실행하는 도구
import sqlalchemy as sa       # sa: 컬럼·타입 정의

revision = "3f9a1c"
down_revision = "a1b2c3"      # 이전 버전 = 부모 (사슬 연결)

def upgrade():
    op.add_column("todos",
        sa.Column("priority", sa.Integer(),
                  server_default="1"))   # 이미 있는 행들에 채워 줄 값

def downgrade():
    op.drop_column("todos", "priority")   # upgrade 의 정확한 역연산

server_default="1"이 붙은 이유는 테이블에 이미 데이터가 있기 때문입니다. 새 컬럼을 추가하면 기존 행에도 그 칸이 생기는데, 채울 값을 정해 주지 않으면 DB가 거부하거나 빈 값(NULL)으로 남습니다.

rev1 → rev2 → rev3. 사슬의 맨 끝(최신)이 head.

NestJS TypeORM 마이그레이션과 나란히

TypeORM 마이그레이션을 써 봤다면 새로 배울 개념은 없습니다. 명령 이름만 바뀝니다.

NestJS — TypeORM
# 엔티티 변경 후 생성
$ typeorm migration:generate \
    src/migrations/AddPriority
$ typeorm migration:run
$ typeorm migration:revert

// 1700000000-AddPriority.ts
async up(q): { /* ALTER … */ }
async down(q): { /* 되돌리기 */ }
FastAPI — Alembic
$ alembic revision --autogenerate
$ alembic upgrade head
$ alembic downgrade -1

# versions/..._add_priority.py
def upgrade(): ...
def downgrade(): ...

migration:generate ↔ revision --autogenerate, run/revert ↔ upgrade/downgrade, up/down ↔ upgrade()/downgrade().

⚠️

autogenerate의 한계 — 반드시 검토

autogenerate는 강력하지만 만능이 아닙니다. 테이블·컬럼 추가/삭제 같은 굵직한 변경은 잘 잡지만, 일부 변경은 놓치거나 위험하게 생성합니다.

생성된 마이그레이션은 사람이 꼭 검토. autogenerate가 못 잡거나 부정확한 대표 사례: 컬럼 타입 변경(구버전 Alembic은 env.py에 compare_type=True를 켜야 감지), 컬럼/테이블 이름 변경(Alembic 눈에는 "옛 컬럼 삭제 + 새 컬럼 추가"로 보여 drop+add를 만듦 → 데이터 유실!), 일부 제약·인덱스, 위에서 본 server_default 같은 서버 기본값. 운영 데이터가 걸린 변경일수록 생성된 upgrade()/downgrade()를 눈으로 확인하고 수정한 뒤 적용하세요. "git diff 없이 머지"하지 않듯이요.
create_all과 Alembic은 함께 쓰지 않는다. Alembic을 도입했다면 앱 시작 시의 Base.metadata.create_all()은 제거하세요. 둘이 동시에 스키마를 만들면 "이미 테이블이 있는데 Alembic은 처음부터 만들려 한다"는 충돌이 납니다. 스키마의 단일 진실 공급원(SSOT, "진짜 기준은 여기 하나"라는 뜻)은 마이그레이션 이력이어야 합니다.
✅

셀프 체크

Q create_all()로는 왜 컬럼 추가가 안 되나요?

테이블 단위로 "없으면 만든다"만 할 뿐, 이미 있는 테이블은 쳐다보지도 않기 때문입니다. 있는 테이블을 고치는 건 마이그레이션의 일입니다.

Q autogenerate가 만든 마이그레이션을 그대로 믿어도 되나요?

아니요. 초안일 뿐입니다. 특히 이름 변경이 drop+add로 나오면 데이터가 사라지니, 적용 전에 파일을 열어 읽고 고쳐야 합니다.

Q 배포한 변경에 문제가 생겼습니다. 어떻게 되돌리나요?

alembic downgrade -1(한 칸 뒤로) 또는 alembic downgrade <revision>(특정 버전까지). 이게 통하려면 각 파일의 downgrade()를 미리 제대로 써 두었어야 합니다.
