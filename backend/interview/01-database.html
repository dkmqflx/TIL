Q1. DB에서 B-Tree 인덱스를 사용하는 이유는 무엇인가요?

검색, 정렬 성능을 높이기 위해 B-Tree 구조를 사용합니다. 균형 잡힌 트리 구조로 빠른 탐색이 가능하고, 삽입/삭제 시에도 성능을 유지할 수 있기 때문입니다. B-Tree는 O(log n) 시간 복잡도로 데이터를 찾을 수 있어 대용량 데이터에서도 효율적입니다. 또한 인덱스 구조가 항상 정렬된 상태를 유지하기 때문에 범위 검색에 특히 유리합니다.

📖 상세 설명

이 질문이 묻는 핵심은 "인덱스가 없으면 뭐가 문제이고, 왜 하필 B-Tree라는 구조냐"입니다. 신입 면접에서 "빨라서요"라고만 답하면 꼬리 질문에서 무너집니다. 왜 빠른지를 구조로 설명할 수 있어야 합니다.

비유 — 책 뒤의 '찾아보기(색인)'. 500쪽짜리 책에서 "트랜잭션"이라는 단어를 찾는다고 해봅시다. 색인이 없으면 1쪽부터 500쪽까지 한 장씩 넘겨야 합니다(이게 풀 스캔 / Full Scan). 하지만 책 뒤에 가나다순으로 정렬된 색인이 있으면 "ㅌ" 근처만 펼쳐 순식간에 페이지 번호를 찾죠. B-Tree 인덱스가 바로 이 정렬된 색인입니다.

B-Tree가 빠른 진짜 이유는 매번 후보를 절반씩 잘라내기 때문입니다. 정렬돼 있으니 가운데 값과 한 번 비교하면 "찾는 값은 왼쪽 절반에 있다"가 확정되고, 나머지 절반은 통째로 버립니다. 100만 건이라도 이 "절반 버리기"를 20번 정도만 반복하면 원하는 값에 도달합니다(2²⁰ ≈ 100만). 풀 스캔이라면 최악의 경우 100만 번을 봐야 하죠. 이 "몇 번 만에 찾느냐"가 바로 O(log n)의 의미입니다.

"균형(Balanced) 트리"라는 말도 중요합니다. B-Tree는 어떤 데이터를 넣고 빼도 모든 잎(실제 데이터가 있는 맨 아래층)까지의 거리를 항상 똑같이 유지합니다. 한쪽만 길게 늘어진 트리라면 어떤 값은 3번, 어떤 값은 100번 만에 찾게 되어 성능이 들쭉날쭉해집니다. B-Tree는 삽입/삭제 때 스스로 균형을 맞춰, 어떤 값을 찾든 비슷한 속도를 보장합니다.

범위 검색에 강한 이유. 인덱스가 정렬돼 있고, 잎 노드끼리 옆으로 연결(링크)돼 있기 때문입니다. WHERE age BETWEEN 20 AND 30이면 20의 위치만 찾은 뒤 옆으로 죽 훑어 30까지 읽으면 끝입니다. ORDER BY 정렬도 이미 정렬돼 있으니 공짜로 됩니다. Hash 인덱스는 이게 안 됩니다(바로 아래 꼬리 질문에서).

Q. B-Tree와 Hash 인덱스의 차이점은 무엇인가요?

A. B-Tree는 범위 검색과 정렬이 가능한 반면, Hash 인덱스는 정확한 키 검색에만 최적화되어 있습니다. 따라서 WHERE 절에 = 조건이 아닌 연산이 있을 때는 B-Tree가 적합합니다. Hash 인덱스는 '=' 연산에 O(1) 시간 복잡도로 매우 빠르지만, '>', '<', 'BETWEEN', 'LIKE' 등의 연산에는 사용할 수 없고 인덱스를 이용한 정렬도 불가능합니다. 또한 B-Tree는 부분 검색도 가능하지만 Hash는 전체 키에 대해서만 동작합니다.

📖 상세 설명
비유 — 사물함 vs 정렬된 책장. Hash는 "학번을 넣으면 사물함 번호가 딱 나오는" 방식입니다. 이름표를 해시 함수에 넣으면 곧장 그 물건이 든 사물함으로 갑니다 — 한 방에 찾으니 O(1). 대신 사물함 번호는 이름과 아무 순서 관계가 없어서, "번호가 100~200 사이인 사물함 전부"를 달라고 하면 손쓸 방법이 없습니다. B-Tree는 반대로 가나다순으로 꽂힌 책장이라, 하나 찾는 건 사물함보다 살짝 느려도(O(log n)) "ㄱ부터 ㄷ까지 전부"처럼 범위로 훑는 건 자유롭게 됩니다.

정리하면, Hash가 순서를 뭉개버리는 대신 얻은 게 "한 방 접근"이고, B-Tree가 살짝 느린 대신 지킨 게 "정렬 상태"입니다. 그래서 조건에 따라 유불리가 갈립니다.

쿼리 조건HashB-Tree
WHERE id = 42 (정확히 일치)✅ 최고로 빠름✅ 빠름
WHERE age > 30, BETWEEN (범위)❌ 불가✅ 적합
ORDER BY name (정렬)❌ 불가✅ 공짜
LIKE 'abc%' (앞부분 부분검색)❌ 불가✅ 가능

이래서 대부분의 RDBMS가 기본 인덱스를 B-Tree로 잡습니다. 범위·정렬·부분검색까지 두루 커버되기 때문이죠. Hash 인덱스는 "무조건 =로만 조회하고 속도가 극단적으로 중요한" 특수한 경우(예: 세션 저장소)에나 선택합니다.

Q2. Repeatable Read 격리 수준에서 팬텀 리드가 발생하지 않는 이유는?

InnoDB의 Repeatable Read에서는 두 가지 메커니즘이 함께 작동합니다. 첫째, 일반 SELECT(잠금 없는 읽기)는 MVCC 스냅샷을 통해 트랜잭션 시작 시점의 일관된 데이터를 읽으므로 팬텀 리드가 보이지 않습니다. 둘째, SELECT ... FOR UPDATE/SHARE 같은 잠금 읽기나 쓰기에서는 Next-Key Lock(레코드 락 + 갭 락)으로 해당 범위에 새 레코드가 끼어드는 것을 막습니다. 표준 SQL에서는 Repeatable Read가 팬텀 리드를 막지 못하지만, InnoDB는 이 두 메커니즘으로 팬텀을 방지합니다. 다만 스냅샷 읽기와 잠금 읽기를 섞어 쓸 때는 write skew 같은 이상 현상이 남을 수 있으므로, 완전한 직렬화가 필요하면 Serializable을 써야 합니다.

📖 상세 설명

먼저 용어부터. 팬텀 리드(Phantom Read)는 "같은 조건으로 두 번 조회했는데, 처음엔 없던 유령 같은 행이 두 번째엔 나타나는" 현상입니다. 그리고 격리 수준(Isolation Level)은 "동시에 도는 트랜잭션들이 서로의 작업을 얼마나 못 보게 막을지"를 정하는 단계입니다.

비유 — 창고 재고를 세는 두 사람. 내가 "20~30번 선반의 상자 개수"를 세는 중인데, 옆 사람이 그새 25번 자리에 새 상자를 슬쩍 넣습니다. 내가 확인차 다시 세면 개수가 늘어나 있죠. 분명 아까 셀 땐 없던 "유령 상자"입니다. 이게 팬텀 리드입니다. Repeatable Read는 이 유령이 나타나지 않도록 두 가지 장치로 막습니다.

① MVCC 스냅샷 — "시작하는 순간 사진을 찍는다". 잠금 없는 평범한 SELECT는 트랜잭션이 시작된 시점의 스냅샷(사진)을 기준으로 데이터를 읽습니다. 내가 사진을 찍어둔 뒤에는 남들이 상자를 넣든 빼든 내 사진에는 안 보입니다. 그래서 몇 번을 다시 읽어도 결과가 똑같습니다 — 이름 그대로 "반복 읽어도 같음(Repeatable Read)".

② Next-Key Lock — "범위에 울타리를 친다". 사진만으로는 부족한 경우가 있습니다. SELECT ... FOR UPDATE처럼 "이 행들을 내가 바꿀 거니 건들지 마"라고 잠그는 읽기(잠금 읽기)죠. 이때 InnoDB는 조회한 행뿐 아니라 행과 행 사이의 빈 공간(gap)까지 잠급니다. 그러면 그 범위에 새 상자를 끼워 넣는 것 자체가 막혀, 유령이 애초에 생기지 않습니다. (구조는 바로 아래 꼬리 질문에서.)

주의 — "완벽한 격리"는 아닙니다. InnoDB의 RR은 팬텀을 막지만, 스냅샷 읽기와 잠금 읽기를 섞으면 Write Skew 같은 미묘한 이상 현상이 남을 수 있습니다(예: 두 트랜잭션이 각자 "당직 최소 1명"을 확인하고 동시에 퇴근 처리 → 결국 0명). 정말로 한 줄로 세운 것처럼 완벽한 순서 보장이 필요하면 한 단계 위인 Serializable을 씁니다. 대신 Serializable은 동시성이 크게 떨어집니다.

Q. Next-Key Lock이란 무엇인가요? 어떻게 동작하나요?

A. Next-Key Lock은 인덱스 레코드와 그 사이 구간까지 잠그는 방식으로, 새로운 레코드가 들어오는 것을 방지하여 팬텀 리드를 막습니다. 이는 Record Lock(인덱스 레코드 자체를 잠금)과 Gap Lock(인덱스 레코드 사이의 간격을 잠금)을 조합한 형태입니다. 예를 들어, 인덱스 값이 10, 20, 30인 테이블에서 WHERE id BETWEEN 10 AND 30 쿼리 실행 시, Next-Key Lock은 10 이상 30 이하 범위를 모두 잠가 해당 범위에 새 데이터가 삽입되는 것을 방지합니다.

📖 상세 설명

Next-Key Lock은 이름 그대로 레코드(Record) + 그 앞의 틈(Gap)을 한 세트로 잠그는 방식입니다. 두 종류의 락이 합쳐진 것입니다.

  • Record Lock — 실제 존재하는 행(예: id=20) 자체를 잠금.
  • Gap Lock — 행과 행 사이의 빈 구간(예: 10과 20 사이)을 잠금. 여기엔 아직 데이터가 없지만, "누가 15를 새로 넣는 것"을 막습니다.
비유 — 주차장에 라바콘 세우기. Record Lock이 "이미 주차된 차(10·20·30번 칸)를 못 빼게 막는" 거라면, Gap Lock은 차와 차 사이 빈 칸에 라바콘을 세워 새 차가 끼어들지 못하게 하는 겁니다. Next-Key Lock은 이 둘을 합쳐 "차 + 그 앞 빈 칸"을 통째로 봉쇄합니다. BETWEEN 10 AND 30이면 10~30 구간 전체에 라바콘이 서니, 15든 25든 새 값을 절대 못 넣습니다 → 유령 상자 원천 봉쇄.

그래서 표준 SQL 정의상으론 "RR은 팬텀을 못 막는다"인데도, InnoDB는 이 Gap Lock 덕분에 잠금 읽기에서까지 팬텀을 막아냅니다. InnoDB의 RR이 다른 DB의 RR보다 한 단계 더 강하게 느껴지는 이유가 바로 이것입니다.

Q7. 왜 MySQL InnoDB는 기본 격리 수준으로 Repeatable Read를 채택했을까요?

MVCC 기반으로 성능과 정합성의 균형을 유지할 수 있기 때문입니다. Oracle이나 PostgreSQL과 같은 다른 DBMS가 Read Committed를 기본값으로 사용하는 것과 달리, MySQL은 Repeatable Read를 선택했습니다. 이는 다음과 같은 이유가 있습니다.

  • 바이너리 로그 기반 복제 시 소스와 레플리카 간 일관성 보장
  • MVCC 구현 방식의 특성상 Read Committed보다 오버헤드가 크지 않음
  • 높은 격리 수준으로 데이터 일관성을 더 중요시하는 설계 철학
  • 잠금 읽기·쓰기 시 Next-Key Lock으로 팬텀 리드를 방지(일반 SELECT는 MVCC 스냅샷으로 처리) — 다만 완전한 직렬화는 아니므로 Serializable과 동일하지는 않음
📖 상세 설명

이 질문의 함정은 "다른 DB는 Read Committed가 기본인데 MySQL만 왜 유별나게 Repeatable Read냐"입니다. 정답의 핵심은 과거의 복제(Replication) 방식에 있습니다.

비유 — 레시피를 그대로 따라 하는 복제 요리사. 옛날 MySQL의 복제는 원본 서버가 실행한 SQL 문장(레시피)을 그대로 복제 서버에 넘겨 다시 실행시키는 방식이었습니다(statement-based). 그런데 원본에서 트랜잭션들이 뒤섞여 실행된 순서와 복제본에서 재현되는 순서가 어긋나면, 같은 레시피인데 다른 요리가 나옵니다(데이터 불일치). Read Committed는 이 순서가 흔들릴 여지가 컸고, Repeatable Read는 스냅샷과 Gap Lock으로 순서를 단단히 붙잡아 원본과 복제본이 똑같은 결과가 되도록 보장했습니다.

즉 "일관성에 더 신경 쓰는 철학"이라기보다는, 복제를 안전하게 만들기 위한 현실적 선택이 크게 작용했습니다. 게다가 InnoDB는 MVCC(다중 버전) 방식이라, 격리 수준을 한 단계 높여도 읽기가 쓰기를 막지 않기 때문에 Read Committed 대비 성능 손해가 거의 없었습니다. "안전은 더 챙기는데 비용은 거의 안 든다"면 높은 쪽을 기본값으로 둘 이유가 충분했던 것이죠.

실무 팁. 요즘은 로우 단위로 복제하는 Row-based replication이 기본이라 위 문제는 사실상 사라졌습니다. 그래서 실무에선 락 경합을 줄이려고 일부러 Read Committed로 낮춰 쓰는 서비스도 많습니다. "MySQL 기본값이 RR이니 무조건 RR" 이 아니라, 서비스 특성에 맞게 고를 수 있다는 점까지 말하면 좋은 인상을 줍니다.

Q. MVCC에서 Undo Log는 어떤 역할을 하나요?

A. Undo Log는 다음과 같은 중요한 역할을 합니다.

  • 트랜잭션 롤백 시 이전 데이터로 복원하는 데 사용
  • MVCC에서 다른 트랜잭션이 변경한 레코드의 이전 버전을 조회할 수 있게 함
  • 트랜잭션 격리 수준에 따라 적절한 버전의 데이터를 읽을 수 있도록 지원
  • 롤백 세그먼트에 저장되며, 트랜잭션의 ID와 함께 레코드 변경 이력 관리

예를 들어, 트랜잭션 A가 레코드를 수정 중일 때 트랜잭션 B가 같은 레코드를 읽으면, 트랜잭션 B는 Undo Log에서 트랜잭션 A 시작 전의 버전을 읽게 됩니다.

📖 상세 설명

MVCC(Multi-Version Concurrency Control)는 "하나의 행에 대해 여러 버전을 동시에 유지"하는 기법입니다. 그리고 그 옛날 버전들을 보관하는 창고가 바로 Undo Log입니다.

비유 — 문서의 '실행 취소(Ctrl+Z)' 기록. 워드로 문서를 고칠 때, 편집기는 "고치기 직전 상태"를 몰래 저장해 둡니다. 그래서 마음이 바뀌면 Ctrl+Z로 되돌릴 수 있죠. Undo Log가 바로 이 되돌리기용 백업입니다. 트랜잭션이 실패해 ROLLBACK 하면 이 기록을 꺼내 원상복구합니다.

그런데 이 백업이 롤백에만 쓰이는 게 아닙니다. MVCC의 "과거 버전 읽기"에도 그대로 재활용됩니다. 트랜잭션 A가 어떤 행을 수정 중일 때, 다른 트랜잭션 B가 그 행을 읽으면 B는 A가 바꾼 최신값 대신 Undo Log에 남아 있는 "A가 손대기 전 버전"을 봅니다. 덕분에 읽는 쪽은 쓰는 쪽을 기다릴 필요가 없어 동시성이 크게 올라갑니다. 이것이 "MySQL은 격리 수준을 높여도 성능 손해가 적다"의 실제 원리입니다.

참고 — 오래된 버전은 언제 지워지나. 아무도 그 과거 버전을 볼 필요가 없어지면(관련 트랜잭션이 다 끝나면) 백그라운드의 Purge 작업이 Undo Log를 정리합니다. 그래서 아주 긴 트랜잭션을 열어두면 과거 버전이 안 지워져 Undo 영역이 부풀어 오르는 문제가 생길 수 있습니다.

Q9. 커버링 인덱스란 무엇이고, 어떤 상황에서 사용되나요?

인덱스에 포함된 컬럼만으로 쿼리를 처리할 수 있을 때, 테이블 접근 없이 인덱스만으로 결과를 반환하는 인덱스입니다. 조회 성능이 극대화됩니다. 구체적으로는 다음과 같습니다.

  • SELECT 절에 있는 모든 컬럼이 인덱스에 포함되어 있어야 함
  • WHERE, ORDER BY, GROUP BY 등에 사용되는 컬럼도 인덱스에 포함되어야 함
  • InnoDB의 경우 PK가 인덱스에 자동으로 포함되므로 활용 가능

예를 들어 (name, age)로 복합 인덱스가 있을 때:

sql
SELECT name, age FROM user WHERE name = 'Dingco'

쿼리는 테이블에 접근하지 않고 인덱스만으로 처리 가능합니다.

📖 상세 설명

보통의 인덱스 조회는 2단계입니다. ① 인덱스에서 "어디 있는지" 위치(PK)를 찾고, ② 그 위치로 테이블 본체를 다시 찾아가 나머지 컬럼을 읽습니다. 이 두 번째 단계를 "테이블로 되돌아가기"(back to table)라고 부르는데, 디스크를 한 번 더 뒤지는 비싼 작업입니다. 커버링 인덱스는 이 2단계를 1단계로 줄입니다 — 필요한 컬럼이 인덱스 안에 전부 있으면, 굳이 테이블 본체까지 안 가고 인덱스만 읽고 끝내는 것이죠.

비유 — 책 '찾아보기'에 답까지 적혀 있는 경우. 보통은 색인에서 페이지 번호를 확인하고(1단계) 그 페이지를 펴서 내용을 읽습니다(2단계). 그런데 만약 색인에 "트랜잭션 … 340쪽"이 아니라 "트랜잭션 = 작업의 최소 단위"라고 뜻풀이까지 적혀 있다면? 색인만 보고 덮으면 됩니다 — 본문(테이블)을 펼 필요가 없죠. 이게 커버링 인덱스입니다. 필요한 정보가 색인 안에서 모두 커버(cover)되니까요.

위 예시에서 (name, age) 인덱스는 name과 age 값을 이미 자기 안에 정렬해 들고 있습니다. 그래서 SELECT name, age ... WHERE name = 'Dingco'는 인덱스만으로 조건 판별과 결과 반환이 모두 끝납니다. 반면 SELECT name, age, email ...이었다면 email은 인덱스에 없으니 테이블로 되돌아가야 해서 커버링이 깨집니다. 실행계획(EXPLAIN)에서 Using index라고 뜨면 "커버링이 적용됐다"는 신호입니다.

🔁 꼬리 질문

Q. 커버링 인덱스를 적용했던 경험이 있나요?

A. 커버링 인덱스를 통해 대량의 데이터를 처리하고자 했을 때 사용했습니다.

구현 사례

  • 사용자 목록 페이징 처리 시 (user_id, name, created_at) 복합 인덱스로 테이블 접근 없이 처리
  • 주문 목록에서 주문일, 상태별 조회 시 (order_date, status, order_id) 인덱스 활용
  • 통계 집계 쿼리에서 GROUP BY, COUNT() 연산을 인덱스만으로 처리

성능 개선 효과

  • 테이블 접근 I/O가 제거되어 디스크 읽기 감소
  • 대용량 테이블에서 수백 배 성능 차이 발생
  • 특히 조인 쿼리에서 효과적 (인덱스는 크기가 작아 메모리에 적재 가능성 높음)

고려사항

  • 인덱스 크기 증가에 따른 트레이드오프 관리
  • 복합 인덱스 컬럼 순서 최적화 (선택도 높은 컬럼 우선)
  • INSERT/UPDATE 성능에 미치는 영향 고려
📖 상세 설명

이 꼬리 질문은 "이론만 아는지, 실제로 써봤는지"를 확인하려는 것입니다. 경험이 없더라도, 왜 그 상황에서 효과적인지를 설명하면 충분히 좋은 답이 됩니다. 위 사례들을 관통하는 공통점은 "많은 행을 훑지만, 정작 필요한 컬럼은 몇 개 안 되는" 조회라는 점입니다.

비유 — 페이징은 '수백 명의 명단만' 필요한 일. 게시판 목록 페이지는 한 번에 20명씩 보여주려고 수천 개의 행을 순서대로 훑습니다. 그런데 화면에 실제로 뿌리는 건 이름과 작성일 정도죠. 이럴 때 매 행마다 테이블 본체까지 다녀오면(수천 번의 왕복) 느립니다. (name, created_at)이 인덱스에 있으면 왕복 없이 인덱스만 죽 훑어 끝나니, 대용량일수록 수십~수백 배 차이가 납니다.
공짜가 아니다 — 트레이드오프. 커버링을 노리고 컬럼을 자꾸 인덱스에 욱여넣으면 인덱스가 뚱뚱해집니다. 인덱스도 결국 저장 공간을 먹고, 데이터를 넣고 고칠 때(INSERT/UPDATE)마다 인덱스도 같이 갱신해야 하므로 쓰기가 느려집니다. 그래서 "조회가 압도적으로 많은, 성능이 중요한 쿼리"에만 선별적으로 적용하는 게 정석입니다.

Q10. 낙관적 락과 비관적 락의 차이를 설명해보세요.

낙관적 락은 충돌 가능성이 낮은 경우 버전 체크로 처리하고, 비관적 락은 충돌 가능성이 높아 미리 락을 거는 방식입니다. 각 방식의 구체적인 특징은 다음과 같습니다.

낙관적 락

  • 데이터에 버전 정보(@VersionColumn)를 두고 수정 시 버전 증가
  • 수정 시점에 버전이 변경되었으면 충돌로 판단하고 예외 발생
  • 트랜잭션 충돌이 적은 환경에 적합
  • 락을 획득하지 않아 동시성은 높지만 충돌 시 재시도 로직 필요

비관적 락

  • SELECT ... FOR UPDATE(TypeORM은 setLock('pessimistic_write'))로 데이터에 실제 락 획득
  • 동시 접근을 원천 차단하여 데이터 일관성 보장
  • 충돌이 빈번한 환경에 적합
  • 락 획득에 따른 대기 시간으로 동시성 저하 가능성
📖 상세 설명

이름이 곧 성격입니다. 낙관적(Optimistic)은 "충돌은 거의 안 날 거야, 낙관적으로 보자"라는 태도이고, 비관적(Pessimistic)은 "충돌이 날 게 뻔하니 미리 막자"라는 태도입니다. 이 태도 차이가 락을 언제 거느냐를 가릅니다.

비유 — 화장실 문 vs 구글 문서. 비관적 락은 공중화장실 문을 잠그는 것입니다. 내가 들어가는 순간 문을 잠가버리니, 뒷사람은 내가 나올 때까지 무조건 기다립니다 — 충돌은 100% 없지만 줄이 생기죠. 낙관적 락은 구글 문서를 여럿이 동시에 여는 것입니다. 일단 다 같이 편집하다가, 저장하는 순간 "그새 다른 사람이 이 부분을 바꿨어요"라고 알려주면 그때 다시 시도합니다. 평소엔 아무도 안 기다려 빠르지만, 정말 겹쳤을 때만 재작업이 필요합니다.

낙관적 락의 동작은 version이라는 번호표로 이뤄집니다. 데이터를 읽을 때 버전이 3이었다면, 수정 시 UPDATE ... WHERE id = ? AND version = 3처럼 "내가 읽었을 때의 버전이 그대로면 반영해"라고 조건을 겁니다. 그새 누가 먼저 고쳐 버전이 4가 됐다면 이 UPDATE는 0건 처리되고, 애플리케이션은 "충돌!"로 감지해 예외를 던지거나 재시도합니다. DB 락을 아예 안 걸어 동시성이 높은 대신, 충돌 시 재시도 로직은 내가 짜야 합니다.

비관적 락은 읽는 순간 SELECT ... FOR UPDATE로 진짜 DB 락을 걸어, 다른 트랜잭션이 그 행을 아예 못 건드리게 합니다. 충돌 자체가 원천 차단되지만, 남들은 락이 풀릴 때까지 대기해야 하므로 처리량이 떨어지고 데드락 위험도 생깁니다.

고르는 기준 — "얼마나 자주 겹치나". 프로필 수정처럼 같은 데이터를 동시에 고칠 일이 거의 없으면 낙관적 락(빠르고 가벼움). 재고 차감·좌석 예매처럼 수많은 사람이 같은 행에 몰리면 비관적 락(재시도 폭주를 피함). "충돌 빈도"가 판단의 핵심 축입니다.
🔁 꼬리 질문

Q. 당신의 프로젝트에서는 어떤 락 방식을 선택했고, 왜 그렇게 결정했나요?

A. 프로젝트의 특성에 따라 락 전략을 선택했습니다.

낙관적 락 적용 사례

  • 사용자 프로필 정보 수정 같이 동시 수정 확률이 낮은 경우
  • 데이터 조회가 많고 수정이 적은 시스템
  • 가용성과 응답 속도가 중요한 사용자 대면 기능
  • TypeORM의 @VersionColumn 활용으로 구현 간소화

비관적 락 적용 사례

  • 재고 관리처럼 동시 수정 충돌이 자주 발생하는 경우
  • 결제 처리나 예약 시스템처럼 데이터 정합성이 매우 중요한 경우
  • 배치 작업에서 데이터 무결성이 필요한 경우

하이브리드 접근법

  • 기본적으로 낙관적 락을 사용하되, 특정 중요 트랜잭션에만 비관적 락 적용
  • 실시간 모니터링으로 충돌 빈도에 따라 전략 동적 변경
📖 상세 설명

면접관은 여기서 "상황에 맞게 트레이드오프를 판단할 수 있는가"를 봅니다. 정답은 "무엇을 썼다"가 아니라 "왜 그 선택이 그 상황에 맞았는가"입니다. 핵심 판단 기준을 한 문장으로 정리하면: "이 데이터를, 얼마나 많은 사람이, 동시에 고치려 드는가?"

비유 — 한정판 티켓 예매 vs 내 프로필 사진 변경. 인기 콘서트 티켓 1장에 수천 명이 동시에 달려들면, 낙관적 락으로 처리했다간 거의 모두가 "충돌! 재시도!"가 되어 서버가 재시도 폭탄을 맞습니다 → 이럴 땐 비관적 락으로 줄을 세우는 게 낫습니다. 반대로 내 프로필 사진은 나 말고 아무도 안 바꾸니, 있지도 않을 충돌을 대비해 락을 거는 건 낭비죠 → 낙관적 락이 정답입니다.

하이브리드는 "평소엔 가벼운 낙관적 락으로 처리량을 챙기다가, 결제·정산처럼 틀리면 큰일 나는 소수의 트랜잭션에만 비관적 락으로 확실히 잠근다"는 실전 전략입니다. 여기에 "충돌이 잦은 재고 차감은 Redis 원자 연산이나 큐로 직렬화하는 방법도 고려했다"까지 덧붙이면, DB 락 너머의 시야를 보여줄 수 있습니다.

Q11. 정규화를 왜 하나요? 그리고 비정규화는 언제 필요한가요?

데이터 중복 제거와 일관성을 위해 정규화를 하며, 조회 성능이나 JOIN이 과도할 경우 비정규화를 적용하기도 합니다. 정규화의 구체적인 장점은 다음과 같습니다.

  • 데이터 중복 최소화로 저장 공간 절약
  • 데이터 변경 시 한 곳만 수정하여 일관성 유지
  • 데이터 무결성 강화 및 이상 현상(Anomaly) 방지
  • 스키마 변경 유연성 증가

비정규화가 필요한 상황은 다음과 같습니다.

  • 읽기 비중이 쓰기보다 매우 높은 시스템
  • 복잡한 JOIN으로 인한 성능 저하 발생 시
  • 통계/분석용 데이터 처리에 최적화가 필요할 때
  • 특정 조회 패턴이 매우 빈번하게 발생할 때
📖 상세 설명

정규화(Normalization)는 "같은 정보를 여러 군데 중복해서 적지 않도록, 테이블을 주제별로 쪼개 관계로 연결하는" 설계 원칙입니다. 목표는 딱 하나 — "한 사실은 한 곳에만 저장"입니다.

비유 — 주소록에 회사명을 매번 적는 경우. 직원 100명이 모두 "ABC컴퍼니" 소속이라고 각자 칸에 회사명을 적어뒀다고 합시다. 회사명이 "ABC코퍼레이션"으로 바뀌면? 100칸을 전부 고쳐야 하고, 하나라도 빠뜨리면 데이터가 어긋납니다(이상 현상). 정규화는 회사 테이블을 따로 만들어 회사명을 딱 한 줄만 두고, 직원은 그 회사의 번호만 참조하게 합니다. 그러면 이름이 바뀌어도 한 곳만 고치면 끝이죠. 이게 "중복 제거 → 일관성"의 정체입니다.

반대로 비정규화(Denormalization)는 이 원칙을 일부러 어기는 것입니다. 왜냐면 정규화의 대가가 JOIN이거든요. 정보를 잘게 쪼갤수록, 화면 하나 그리는 데 5개, 10개 테이블을 이어 붙여야 합니다. 조회가 폭발적으로 많은 화면이라면 이 JOIN 비용이 병목이 됩니다.

비정규화 = "자주 같이 보는 정보를 미리 한 장에 붙여두기". 예를 들어 주문 목록 화면에 항상 상품명이 같이 뜬다면, 매번 상품 테이블과 JOIN하는 대신 주문 상세에 상품명을 복사해 저장합니다. 읽기는 빨라지지만, 상품명이 바뀌면 여러 곳을 동기화해야 하는 부담(중복의 대가)이 생깁니다. 그래서 비정규화는 "읽기가 압도적으로 많고, 그 값이 잘 안 바뀌는" 경우에 의도적으로, 최소한만 적용합니다.

정리하면 둘은 대립이 아니라 저울입니다. 한쪽엔 일관성·정확성(정규화), 다른 쪽엔 조회 속도(비정규화)가 놓여 있고, 서비스의 읽기/쓰기 비중에 따라 균형점을 정하는 것입니다. "일단 정규화로 바르게 설계하고, 측정된 병목에 한해 비정규화한다"가 안전한 순서입니다.

🔁 꼬리 질문

Q. 정규화를 적용하다 성능 문제가 생겼던 경험이 있나요?

A. 정규화와 성능 사이의 균형을 맞추는 실제 경험은 다음과 같았습니다.

문제 상황

  • 전자상거래 주문 내역 조회 시 고객, 상품, 배송 정보 등 여러 테이블 JOIN 발생
  • 대시보드에서 실시간 주문 현황 표시 시 5개 이상 테이블 JOIN으로 응답 시간 증가
  • 특히 주문량이 많은 시간대에 쿼리 지연 현상 심화

해결 방법

  • 주문 조회용 비정규화 테이블 생성 (주문 정보 + 고객명 + 상품명 + 배송상태 등 통합)
  • 원본 정규화 테이블은 유지하되, 주문 생성/변경 시 이벤트 기반으로 조회용 테이블 동기화
  • 자주 조회되는 집계 데이터는 별도 통계 테이블로 미리 계산하여 저장
  • 일부 컬럼에 대해 선택적 중복 허용 (예: 상품명을 주문상세에 중복 저장)

결과

  • 조회 성능 5~10배 개선
  • 데이터 일관성은 이벤트 기반 동기화로 유지
  • 쓰기 작업에 약간의 오버헤드 발생했으나 읽기 비중이 높아 전체적으로 성능 향상
📖 상세 설명

이 답변의 좋은 점은 "비정규화로 도망친 게 아니라, 원본은 정규화된 채 두고 조회 전용 사본을 따로 만들었다"는 부분입니다. 면접관이 듣고 싶은 건 바로 이 균형 감각입니다.

비유 — 원본 장부와 '오늘의 요약본'. 회계의 원본 장부는 정확성을 위해 항목별로 잘게 나눠 적습니다(정규화). 하지만 사장님이 매일 아침 보는 건 항목이 다 합쳐진 "오늘의 매출 요약본" 한 장이죠. 매번 원본을 뒤져 합산하면 느리니, 거래가 생길 때마다 요약본을 갱신해 둡니다. 원본(정규화)은 진실의 원천으로 남기고, 요약본(비정규화)은 빠른 조회용으로 파생시킨 겁니다. 위 답변의 "조회용 테이블 + 이벤트 기반 동기화"가 정확히 이 구조입니다.
이 방식의 대가 — 동기화 지연. 원본이 바뀐 순간과 사본이 갱신되는 순간 사이에는 아주 짧게 값이 어긋나는 구간이 생깁니다(최종 일관성, Eventual Consistency). 그래서 돈·재고처럼 1원도 틀리면 안 되는 값은 이렇게 복제하기보다 원본을 직접 읽는 게 안전합니다. "어디까지 살짝 어긋나도 되는가"를 구분하는 것이 실무 감각입니다.
