Q3. 트래픽이 몰릴 때 서버 병목을 진단하는 방법은?

CPU, Memory, Disk, Network 사용률 확인 → 이벤트 루프 지연(event loop lag), 힙 사용량, DB 커넥션 풀 확인. Prometheus + Grafana, 또는 자체 로깅 사용. Node.js는 싱글 스레드 이벤트 루프 기반이라 CPU 바운드 작업이 루프를 막으면 전체 지연으로 이어지므로, 이벤트 루프 지연 모니터링이 특히 중요합니다. APM 도구(예: Datadog, Sentry, clinic.js)를 활용하면 트랜잭션 레벨의 병목 지점도 식별할 수 있습니다.

📖 상세 설명

이 질문은 사실 "장애가 났을 때 무작정 서버부터 늘리는 사람인가, 아니면 어디가 막혔는지 측정해서 찾는 사람인가"를 봅니다. 병목은 대체로 CPU · 메모리 · 디스크 · 네트워크 · 이벤트 루프 · DB 커넥션 풀 중 하나에서 생기는데, 범인을 특정하지 않고 스케일 아웃부터 하면 돈만 쓰고 문제는 그대로일 수 있습니다.

비유 — 고속도로 정체의 원인 찾기. 차가 막힌다고 무조건 차선을 늘린다고 뚫리는 게 아닙니다. 원인이 톨게이트가 느린 것(DB 응답 지연)일 수도, 사고 차량 한 대(무거운 코드 한 줄)가 전 차선을 막은 것일 수도 있죠. 병목 진단은 "어느 구간에서 차가 멈춰 서는지" CCTV(모니터링 지표)로 확인하는 일입니다.

특히 Node.js는 웨이터가 딱 한 명인 식당과 같습니다(싱글 스레드 이벤트 루프). 이 웨이터가 무거운 계산 한 건에 붙잡히면 나머지 모든 손님(요청)이 통째로 멈춥니다. 그래서 다른 언어에선 잘 안 보는 이벤트 루프 지연(event loop lag)이 Node 진단의 핵심 지표가 됩니다. 실무에선 Prometheus+Grafana로 지표를 그래프로 쌓아두고, Datadog·clinic.js 같은 APM으로 "어떤 API·어떤 쿼리가 느린지" 트랜잭션 단위까지 파고듭니다.

Q. 이벤트 루프 지연이 심하거나 메모리가 계속 늘어난다면 어떻게 조치할 수 있나요?

A. 이벤트 루프가 막힌다면 동기(sync) 블로킹 연산이나 무거운 CPU 작업이 루프를 점유하고 있을 가능성이 높고, 메모리가 계속 늘어난다면 참조가 해제되지 않는 누수를 의심해야 합니다. 구체적인 조치로는 다음과 같은 고민을 할 수 있습니다.

  • 동기 블로킹 API(예: fs.readFileSync, 무거운 JSON.parse)를 비동기/스트리밍으로 전환
  • CPU 바운드 작업(암호화, 이미지 처리 등)은 Worker Threads나 별도 큐(BullMQ)로 오프로드
  • 대용량 응답은 한 번에 메모리에 올리지 말고 스트림으로 처리
  • 불필요하게 큰 객체를 전역/모듈 스코프에 캐싱하지 않기 (클로저·이벤트 리스너 참조 정리)
  • 힙 스냅샷(--inspect, clinic.js, heapdump) 분석으로 메모리 누수 추적
  • 필요 시 --max-old-space-size로 힙 상한을 조정하되, 근본 원인(누수) 해결이 우선
📖 상세 설명

두 증상은 원인이 다릅니다. 이벤트 루프 지연은 "웨이터가 한 곳에 붙잡힌" 문제(동기 블로킹·무거운 CPU 작업), 메모리 증가는 "다 쓴 물건을 안 버리고 계속 쌓는" 문제(누수)입니다. 조치도 그래서 갈립니다.

비유 — 웨이터 한 명 vs 주방 보조. 이벤트 루프(웨이터)가 이미지 리사이징 같은 무거운 요리를 직접 하면, 그 몇 초 동안 다른 손님 주문을 아예 못 받습니다. 해법은 무거운 요리를 주방 보조(Worker Threads·BullMQ 큐)에게 넘겨 웨이터는 계속 홀을 돌게 하는 것입니다. readFileSync 같은 동기 API도 웨이터를 붙잡으니 비동기/스트림으로 바꿉니다.

메모리 누수는 다 먹은 접시(더 이상 안 쓰는 객체)를 계속 치우지 않아 식탁이 접시로 가득 차는 상황입니다. 흔한 범인은 전역 배열·맵에 계속 쌓기, 해제 안 한 이벤트 리스너/타이머, 클로저가 붙잡은 큰 객체입니다. 힙 스냅샷을 두 번 찍어 비교하면(시간이 지나도 안 사라지고 계속 늘어나는 객체) 범인을 추적할 수 있습니다. --max-old-space-size로 상한을 늘리는 건 임시방편일 뿐, 새는 구멍을 막는 것이 우선입니다.

Q4. Redis를 캐시로 사용할 때 주의해야 할 점은?

캐시 일관성 문제(Cache-Aside 패턴), TTL 관리, 캐시 무효화 전략이 필요합니다. 또한 Redis는 인메모리 데이터 저장소이므로 메모리 사용량 모니터링이 중요합니다. 메모리가 부족해지면 maxmemory-policy 설정에 따라 데이터 제거가 일어날 수 있습니다. 또한 Redis는 기본적으로 싱글 스레드로 동작하므로, 시간 복잡도가 O(N) 이상인 명령어 사용 시 전체 성능에 영향을 줄 수 있어 주의해야 합니다. 분산 환경에서는 Sentinel이나 Cluster 구성도 고려해야 합니다.

📖 상세 설명

이 질문의 의도는 "Redis를 '빠르니까 그냥 쓴다'가 아니라, 그 대가와 함정을 아는가"입니다. 캐시는 공짜 속도가 아니라 세 가지 숙제를 함께 떠안습니다 — ① 원본과의 일관성, ② TTL·무효화 관리, ③ 메모리 한계.

비유 — 책상 위 포스트잇 메모. 매번 서류함(DB)까지 가지 않으려고 자주 쓰는 정보를 포스트잇(캐시)에 적어 책상에 붙여둡니다. 빠르지만 문제는 서류함 원본이 바뀌었을 때죠. 포스트잇을 안 고치면 옛날 정보를 보게 됩니다(일관성 문제). 게다가 책상 공간(메모리)은 유한해서, 꽉 차면 오래된 메모부터 떼어냅니다(maxmemory-policy에 따른 eviction).
싱글 스레드 + O(N) 명령의 함정. Redis도 일꾼이 한 명입니다. KEYS *처럼 전체 키를 훑는 O(N) 명령을 큰 데이터에 실행하면, 그동안 다른 모든 요청이 줄 서서 대기합니다. 화장실이 한 칸인데 한 사람이 오래 점유하는 것과 같죠. 그래서 운영 중엔 KEYS 대신 SCAN을 쓰고, 큰 컬렉션을 한 번에 순회하는 명령을 피합니다.

Q. Redis에 저장된 캐시와 DB의 일관성이 깨졌을 때 대응 방법은?

A. DB와의 정합성 유지를 위해 다음과 같은 전략을 사용할 수 있습니다.

  • Cache-Aside 패턴: 데이터 갱신 시 캐시를 먼저 무효화하고 DB를 업데이트
  • Write-Through 패턴: DB 업데이트와 캐시 업데이트를 동시에 수행
  • Write-Behind 패턴: 캐시를 먼저 업데이트하고 비동기적으로 DB 업데이트
  • 이벤트 기반 캐시 무효화: DB 변경 이벤트를 구독하여 캐시 업데이트
  • 적절한 TTL 설정으로 오래된 데이터 자동 제거
  • 배치 작업으로 주기적 캐시-DB 동기화

일관성이 깨진 것이 감지되면 해당 키만 선택적으로 무효화하고, 심각한 불일치 시 전체 캐시를 리프레시 할 수 있습니다.

📖 상세 설명

핵심은 "원본(DB)과 사본(캐시)을 언제, 어떤 순서로 맞출 것인가"입니다. 세 패턴의 차이는 갱신 타이밍에 있습니다.

  • Cache-Aside — 가장 흔한 방식. 읽을 땐 캐시 먼저 보고 없으면 DB에서 가져와 캐시에 채움. 쓸 땐 DB를 고치고 캐시는 지워버림(무효화) → 다음 조회 때 새로 채워짐.
  • Write-Through — DB와 캐시를 동시에 갱신. 항상 최신이지만 쓰기가 조금 느림.
  • Write-Behind — 캐시 먼저 갱신하고 DB는 나중에 비동기로. 빠르지만 그 사이 장애 나면 유실 위험.
비유 — 지하철 전광판과 실제 열차. 캐시(전광판)와 DB(실제 열차 위치)가 어긋나면 승객이 헷갈립니다. Cache-Aside는 "열차가 바뀌면 전광판을 일단 끄고, 다음에 누가 볼 때 실제 위치로 다시 켜는" 방식이죠.
왜 캐시를 '갱신'이 아니라 '삭제'할까? 두 요청이 거의 동시에 값을 바꾸면, 캐시에 덮어쓰는 순서가 꼬여 오래된 값이 최종적으로 남을 수 있습니다. 그래서 실무에선 "DB 갱신 후 캐시는 지우기만 하고, 다음 조회 때 최신값으로 다시 채우는" Cache-Aside가 안전하다고 봅니다.

Q6. 1000개의 티켓에 대해 수십만 요청이 동시에 들어오는 상황을 어떻게 처리할 수 있을까요?

Skip Locked, Redis 분산락, 메모리 큐 사용 등으로 RDB 부하를 줄이거나 처리 순서를 제어합니다. 구체적인 아키텍처는 다음과 같습니다.

  • 초기 요청은 API Gateway에서 Rate Limiting으로 서버 보호
  • 모든 요청을 Kafka나 RabbitMQ 같은 메시지 큐에 넣어 비동기 처리
  • Redis Sorted Set으로 요청 순서 보장 및 선착순 처리
  • 작업자(Worker)를 여러 개 두어 병렬 처리하되 분산락으로 동시성 제어
  • DB 업데이트는 배타적 락(FOR UPDATE)이나 낙관적 락으로 처리
  • 처리 결과는 웹소켓이나 이벤트 스트림으로 클라이언트에 실시간 전달
📖 상세 설명

이건 전형적인 선착순 한정 수량(티켓팅·수강신청·한정판) 문제입니다. 질문의 핵심은 "수십만 요청을 DB에 그대로 다 때리면 죽는다 — 그 앞에서 어떻게 완충하고, 재고를 어떻게 정확히 지킬 것인가"입니다. 두 가지를 동시에 풀어야 합니다: ① 몰려드는 양을 줄이기, ② 1000개를 초과 판매하지 않기.

비유 — 콘서트 티켓 창구. 창구(DB) 하나에 수만 명이 한꺼번에 달려들면 창구가 마비됩니다. 그래서 ① 입구에서 인원 제한(Rate Limiting)으로 한꺼번에 못 들어오게 막고, ② 들어온 사람은 번호표를 뽑아 줄을 세우며(메시지 큐 · Redis Sorted Set), ③ 창구를 여러 개 열어(Worker) 차례대로 처리합니다. 이때 두 직원이 같은 좌석을 동시에 파는 것만 막으면(락) 초과 판매가 없습니다.

여기서 메시지 큐가 "번호표 뽑고 줄 서기"의 역할을 합니다. 순간적으로 수십만 요청이 와도 큐가 버퍼(완충 저수지)가 되어 받아두고, 워커들은 뒤에서 감당 가능한 속도로 하나씩 꺼내 처리합니다. 폭발적인 유입과 실제 처리 속도를 분리(디커플링)하는 것이죠. 마지막 재고 차감만 FOR UPDATE(비관적 락)나 낙관적 락, 혹은 Redis 원자 연산으로 딱 잠그면, 1000개를 넘겨 파는 일이 생기지 않습니다.

🔁 꼬리 질문

Q. SKIP LOCKED는 MySQL 8.0부터 제공되는데, 그 이전(5.7 등) 환경이라면 어떤 대안이 있을까요?

A. SKIP LOCKED·NOWAIT는 MySQL 8.0부터 표준 지원되므로(5.7은 2023-10 EOL, 8.0이 현재 기준) 8.0 이상이라면 SKIP LOCKED를 쓰는 게 가장 깔끔합니다. 5.7 이하 레거시 환경이라면 다음 대안을 사용할 수 있습니다.

  • FOR UPDATE로 레코드 락을 걸되, 트랜잭션 타임아웃 설정으로 데드락 방지
  • Redis를 활용한 분산락 구현 (SETNX + TTL 활용)
  • 애플리케이션 레벨에서 p-limit이나 큐(BullMQ)의 concurrency 옵션으로 동시 처리 수 제한
  • 처리 상태 컬럼을 추가하여 낙관적 락 기반 처리 (예: 대기→처리중→완료)
  • 샤딩 기법으로 테이블을 분할하여 락 경합 감소
  • 배치 프로세싱으로 일정 간격마다 처리하여 부하 분산
📖 상세 설명

먼저 SKIP LOCKED가 왜 좋은지부터. 여러 워커가 같은 대기열 테이블에서 "다음 처리할 작업"을 집으려 할 때, 보통의 FOR UPDATE는 이미 남이 잠근 행이 풀릴 때까지 기다립니다. 반면 SKIP LOCKED는 잠긴 행은 건너뛰고 그 다음 자유로운 행을 집습니다. 그래서 워커들이 서로 부딪히지 않고 각자 다른 작업을 병렬로 가져갑니다.

비유 — 물류창고에서 상자 집는 알바들. 여러 알바가 컨베이어에서 상자를 집는데, 남이 이미 손댄 상자 앞에서 멀뚱히 기다리면(FOR UPDATE) 비효율입니다. SKIP LOCKED는 "집힌 상자는 건너뛰고 다음 빈 상자를 잡아라"라서 모두가 쉬지 않고 일합니다.

MySQL 8.0 미만이라 이 기능이 없다면, "같은 작업을 두 워커가 동시에 집지 못하게" 다른 방법으로 막아야 합니다. Redis 분산락(SETNX로 "이 작업은 내가 맡음" 표시 + TTL로 워커 죽어도 자동 해제)이 대표적이고, 애플리케이션에서 p-limit·BullMQ concurrency로 동시 처리 수를 제한하거나, 상태 컬럼(대기→처리중→완료)을 두고 UPDATE ... WHERE status='대기'가 1건 성공하는 워커만 처리하게 하는 낙관적 방식도 흔합니다.

⚡

Q14. 캐시 Avalanche란 무엇이며, 어떻게 방지할 수 있을까요?

캐시 Avalanche는 다수의 캐시 항목이 동시에 만료되어 데이터베이스나 백엔드 시스템에 갑작스러운 부하가 몰리는 현상입니다. 이는 서비스 장애로 이어질 수 있습니다. 방지 방법은 다음과 같습니다.

  • TTL 분산: 캐시 항목마다 만료 시간에 랜덤 지연 추가
  • 백그라운드 갱신: 캐시 만료 전 비동기적으로 데이터 갱신
  • 계층형 캐시 구조: 로컬 캐시와 분산 캐시 함께 사용
  • 캐시 웜업: 시스템 재시작이나 배포 전 주요 항목 미리 로딩
📖 상세 설명

"Avalanche(눈사태)"라는 이름 그대로, 수많은 캐시 키가 거의 같은 순간에 한꺼번에 만료되면서 그 요청이 전부 DB로 쏟아져 DB가 무너지는 현상입니다. 이 질문은 "캐시가 오히려 장애의 방아쇠가 될 수 있음을 아는가"를 봅니다. 캐시가 있을 땐 DB가 편했는데, 캐시가 동시에 비는 순간 DB가 평소의 수백 배 부하를 그대로 맞는 것이죠.

비유 — 모두가 정각 6시에 우산을 반납한다면. 공유 우산을 다들 "대여 후 정확히 6시간"으로 맞춰 빌렸다고 합시다. 그러면 오후 6시 정각에 모든 우산이 동시에 반납되고, 동시에 다시 대여 요청이 몰려 대여소가 마비됩니다. 만료 시각을 5시 55분~6시 5분처럼 조금씩 흩뿌리면 이 쏠림이 사라집니다. 이게 TTL 분산(지터)입니다.

그래서 방지책의 1순위는 TTL에 랜덤을 섞는 것(예: 기본 10분 ± 랜덤 1분)이라 만료가 시간축에 퍼집니다. 여기에 백그라운드 갱신(만료 직전 미리 새 값으로 교체), 다층 캐시(로컬+Redis로 한쪽이 비어도 다른 쪽이 방어), 웜업(배포·재시작 직후 주요 키를 미리 채워 첫 순간의 빈 캐시를 방지)을 더합니다.

사촌 개념 구분. Penetration(관통)은 존재하지 않는 키를 계속 조회해 매번 DB까지 뚫리는 것(→ 빈 값도 캐싱하거나 Bloom Filter), Breakdown/Hotkey(핫키)는 인기 있는 단 하나의 키가 만료되는 순간 그 키로만 요청이 폭주하는 것(→ 뮤텍스/단일 갱신 락)입니다. Avalanche는 "여러 키가 동시에"라는 점이 다릅니다.
🔁 꼬리 질문

Q. TTL 분산 전략을 적용했던 경험이 있나요?

A. TTL을 고정값이 아니라 기본값에 ±10% 정도의 랜덤 지연을 추가하여 동시 만료를 방지하거나, 서비스 시작 시 미리 Warm-up 캐시를 준비하면 캐시 어밸런치(Avalanche)를 효과적으로 완화할 수 있습니다.

📖 상세 설명

경험이 없더라도 "왜 ±10%가 효과가 있는지"를 설명할 수 있으면 충분히 좋은 답입니다. 원리는 단순합니다 — 같은 순간에 몰린 만료를 시간축으로 얇게 펴는 것입니다.

비유 — 알람 시간 흩뿌리기. 기숙사생 100명이 알람을 정확히 7시로 맞추면 7시에 샤워실이 마비됩니다. 각자 6시 55분~7시 5분으로 살짝 다르게 맞추면 붐빔이 자연스럽게 분산되죠. TTL 600초 → 540~660초처럼 랜덤을 주면 캐시 만료도 똑같이 퍼집니다.

구현은 ttl = base + random(-base*0.1, +base*0.1) 한 줄이면 됩니다. 여기에 배포 직후엔 캐시가 텅 비어 첫 요청들이 전부 DB로 가니, 웜업으로 인기 데이터를 미리 채워두면 "배포 직후 순간 폭주"까지 함께 막을 수 있습니다. 두 기법을 같이 쓰는 게 정석입니다.

⚡

Q23. API 요청량이 급증할 때 어떻게 대응할 수 있나요?

서버 스케일 아웃, 로드 밸런서 도입, 캐싱 적용, DB 인덱싱 최적화, 비동기 처리 적용, CDN 활용 등 다양한 기법을 사용할 수 있습니다.

📖 상세 설명

이 질문은 "트래픽 급증에 쓸 수 있는 도구상자를 계층별로 정리해 아는가"를 봅니다. 답변이 나열식이라 밋밋해 보이지만, 실제로는 요청이 지나가는 길목마다 방어선이 있다는 그림으로 묶으면 훨씬 좋은 답이 됩니다.

비유 — 갑자기 손님이 몰린 식당. ① 직원을 더 투입(스케일 아웃)하고, ② 입구에 안내원을 둬 빈 자리로 손님을 고르게 배분(로드 밸런서)합니다. ③ 자주 나가는 반찬은 미리 만들어(캐시) 조리 시간을 줄이고, ④ 배달은 가까운 지점에서 나가게(CDN) 합니다. ⑤ 주문은 일단 받아두고 조리는 순서대로(비동기 큐) 처리하죠.

정리하면 방어선은 세 층입니다. 앞단 — CDN·캐시로 아예 서버까지 안 오게 걸러내기. 애플리케이션 — 서버를 여러 대로 늘리고(스케일 아웃) 로드 밸런서로 고르게 분산. 뒷단 — 느린 쿼리는 인덱싱으로 잡고, 무거운 작업은 비동기 큐로 미뤄 응답을 먼저 돌려주기. 그리고 아무리 늘려도 한계가 있으니, 마지막엔 Rate Limiting으로 "받을 만큼만 받고 나머지는 정중히 거절"해 시스템 전체가 무너지는 것을 막습니다.

🔁 꼬리 질문

Q. Rate Limiting을 구현하는 방법에는 어떤 것들이 있나요?

A. Redis를 활용한 counting, token bucket, leaky bucket 알고리즘을 구현하거나, API Gateway의 rate limiting 기능을 활용할 수 있습니다. 또한 NestJS의 경우 @nestjs/throttler나 rate-limiter-flexible 같은 라이브러리를 활용할 수 있습니다.

📖 상세 설명

Rate Limiting은 "단위 시간당 허용 요청 수를 정해, 그걸 넘으면 막는" 기법입니다. 핵심은 어떤 알고리즘으로 "얼마나 왔는지"를 셀 것인가인데, 대표 두 가지를 비유로 기억하면 쉽습니다.

비유 — 토큰 버킷 vs 새는 양동이. Token Bucket은 놀이공원 자유이용권 토큰통입니다. 토큰이 일정 속도로 채워지고, 요청이 올 때마다 하나씩 꺼내 씁니다. 토큰이 남아 있으면 순간적으로 몰려도(버스트) 허용, 다 떨어지면 거절. Leaky Bucket은 바닥에 구멍 뚫린 양동이로, 물(요청)이 아무리 쏟아져도 구멍으로 일정 속도로만 빠져나가 처리 속도를 매끈하게 고릅니다.

가장 간단한 구현은 Redis에 사용자ID:분 키를 두고 요청마다 INCR로 세다가 임계치를 넘으면 거절하는 고정 윈도우 카운팅입니다(원자적이라 분산 서버에서도 안전). 직접 짜기보다 실무에선 @nestjs/throttler·rate-limiter-flexible 같은 검증된 라이브러리나 API Gateway·Nginx의 내장 기능을 쓰는 게 안전합니다.
