Q5. 서비스 규모가 커지면서 OrderService가 300줄이 넘어갔습니다. 어떻게 리팩토링 하면 좋을까요?

먼저 단일 책임 원칙(SRP)에 따라 책임별로 서비스 클래스를 나누고, 도메인 중심으로 로직을 분산시켰습니다. 구체적으로는:

  • 단일 책임 원칙(SRP)에 따라 주문 생성, 조회, 변경, 취소 등 책임별로 서비스 클래스 분리
  • 복잡한 비즈니스 로직은 도메인 모델로 이동시켜 객체지향적 설계 강화
  • (읽기/쓰기 모델이 실제로 크게 갈릴 때에 한해) 명령과 조회를 분리(CQRS)하는 것도 고려 — 보통 이 규모에서는 1~2번 분리로 충분하고 CQRS는 과한 설계가 되기 쉬움
  • CommandOrderService, QueryOrderService 등으로 역할 구분
  • UseCase 클래스를 도입하여 특정 비즈니스 시나리오 캡슐화
📖 상세 설명

이 질문이 진짜 확인하려는 건 "클래스가 왜 커지면 안 되는지, 그리고 어떤 기준으로 쪼갤지"입니다. "300줄"이라는 숫자 자체가 문제가 아니라, 한 클래스가 너무 많은 이유로 바뀌게 된 상태가 문제입니다. 답의 핵심은 단일 책임 원칙(SRP) — "하나의 클래스는 바뀌어야 할 이유가 하나여야 한다"입니다.

비유 — 혼자 다 하는 1인 식당. 한 사람이 요리도 하고, 서빙도 하고, 계산도 하고, 재고 주문까지 다 하면, 손님이 몰릴 때 어디 하나만 삐끗해도 가게 전체가 멈춥니다. 게다가 "계산 방식"만 바꾸려 해도 그 사람의 하루 전체를 건드려야 하죠. OrderService가 300줄이 됐다는 건 이 1인 식당과 같습니다. 주문 생성·조회·변경·취소라는 서로 다른 일을 한 클래스가 떠안고 있는 것 — 그래서 각각을 담당하는 직원(클래스)으로 나누는 게 SRP 리팩토링입니다.

구체적 순서는 이렇습니다. ① 먼저 책임별로 서비스를 분리합니다(생성/조회/변경/취소). ② 그다음 흩어져 있던 복잡한 계산·판단 규칙은 도메인 모델(엔티티) 안으로 옮깁니다 — 예를 들어 "주문 총액 계산", "취소 가능 여부 판단"은 Order 엔티티 스스로 알고 있는 게 자연스럽습니다. ③ "쿠폰 적용 후 결제까지"처럼 여러 단계를 묶은 시나리오는 UseCase 클래스로 캡슐화합니다.

과한 설계 주의 — CQRS는 함부로 꺼내지 말 것. 명령(쓰기)과 조회(읽기)를 아예 다른 모델로 나누는 CQRS는 "읽기와 쓰기의 요구가 정말로 크게 다를 때"만 값어치를 합니다. 300줄짜리를 정리하는 수준이라면 대개 책임별 1~2번 분리로 충분합니다. 신입 면접에서 "CQRS 도입하겠다"를 남발하면 오히려 오버엔지니어링으로 비칩니다. "필요해질 때 도입한다"는 절제가 더 좋은 인상을 줍니다.

Q. 그럴 경우 트랜잭션은 어디에 걸어야 할까요?

A. 트랜잭션은 한 서비스 계층에서 묶어서 처리하는 것이 일반적입니다. 구체적으로 다음과 같이 구현할 수 있습니다.

  • Facade 패턴을 적용하여 상위 서비스에서 트랜잭션 경계 관리
  • 분리된 서비스들을 호출하는 조정자(Coordinator) 역할의 서비스에 트랜잭션 적용
  • TypeORM의 dataSource.transaction()이나 QueryRunner로 상위 서비스에서 트랜잭션 경계 관리 (데코레이터 방식이 필요하면 typeorm-transactional 라이브러리 활용)
  • 마이크로서비스처럼 분산된 경우 Saga 패턴을 적용하여 보상 트랜잭션 구현

가능하면 트랜잭션 범위는 최소화하되, 비즈니스적으로 원자성이 필요한 작업은 반드시 하나의 트랜잭션 내에서 처리해야 합니다.

📖 상세 설명

서비스를 여러 개로 쪼개고 나면 새로운 고민이 생깁니다. "주문 하나를 처리하는 일"이 이제 여러 서비스 호출로 흩어졌는데, 중간에 실패하면 어떻게 되지? 이 질문은 바로 그 지점을 찌릅니다. 핵심 답은 "트랜잭션 경계는 흐름을 조정하는 상위 계층에 하나로 건다"입니다.

비유 — 계좌 이체는 '전부 아니면 전무'. A에서 돈을 빼고(출금) B에 넣는(입금) 이체를 생각해 보세요. 출금은 됐는데 입금 직전에 서버가 죽으면? 돈이 허공에서 증발합니다. 그래서 이 둘은 반드시 한 묶음으로, "둘 다 성공하거나 둘 다 취소"돼야 합니다. 주문 처리도 마찬가지 — 재고 차감·주문 저장·결제 기록이 각각 다른 서비스로 나뉘어 있어도, 이들을 호출하는 상위(Facade/조정자) 서비스가 전체를 하나의 트랜잭션으로 감싸야 중간 실패 시 통째로 롤백됩니다.

만약 반대로 쪼개진 하위 서비스마다 각자 트랜잭션을 커밋해 버리면, 앞 단계는 이미 저장됐는데 뒤 단계만 실패하는 부분 커밋(어중간하게 반만 처리된 데이터)이 생깁니다. 그래서 트랜잭션은 "가장 바깥에서 한 번"이 원칙입니다. 한편 마이크로서비스처럼 DB가 물리적으로 분리돼 하나의 트랜잭션으로 못 묶는 경우엔, 각 단계가 실패하면 앞 단계를 되돌리는 보상 트랜잭션(Saga 패턴)으로 "논리적 원자성"을 흉내 냅니다.

Q13. 도메인 서비스와 애플리케이션 서비스의 차이를 설명해주세요.

도메인 서비스는 도메인 규칙과 비즈니스 로직을 캡슐화하는 서비스입니다. 특정 도메인의 개념과 규칙을 다루며, 여러 도메인 객체 간 상호작용이 필요한 비즈니스 로직을 구현합니다.

애플리케이션 서비스는 사용자 요청을 처리하고 전체 흐름을 조정하며 트랜잭션 경계를 관리합니다. 여러 도메인 서비스를 조합하고 보안, 로깅과 같은 기술적 관심사를 처리합니다.

📖 상세 설명

둘 다 이름이 "서비스"라 헷갈리는데, 맡은 역할이 완전히 다릅니다. 한 줄로 구분하면: 도메인 서비스 = "실제 규칙(무엇이 맞는가)", 애플리케이션 서비스 = "흐름 조정(언제 무엇을 시키는가)"입니다.

비유 — 식당의 요리사와 홀 매니저. 요리사(도메인 서비스)는 "이 재료로 어떻게 요리하는지", "이 조합이 되는지 안 되는지"라는 진짜 요리 규칙을 압니다. 홀 매니저(애플리케이션 서비스)는 요리를 직접 하진 않지만, 주문을 받고 → 주방에 넘기고 → 결제를 처리하고 → 영수증을 기록하는 전체 진행을 지휘합니다. 매니저는 "요리법"을 몰라도 되고, 요리사는 "결제·로깅" 같은 걸 신경 쓸 필요가 없죠. 이렇게 규칙과 흐름을 분리하는 게 두 서비스를 나누는 이유입니다.

조금 더 구체적으로, 도메인 서비스는 "여러 엔티티에 걸쳐 있어서 어느 한 엔티티에 넣기 애매한 비즈니스 규칙"을 담습니다(예: 계좌 A·B를 함께 봐야 하는 이체 규칙). 순수 비즈니스 판단만 하고, DB·HTTP 같은 기술은 모릅니다. 반면 애플리케이션 서비스는 유스케이스 한 건의 흐름을 조율하면서 트랜잭션 경계, 인증/권한, 로깅 같은 기술적 관심사를 처리합니다. 그래서 애플리케이션 서비스는 얇게, 도메인 서비스·엔티티는 규칙으로 두껍게 두는 게 좋은 설계입니다.

🔁 꼬리 질문

Q. 당신은 어디에 비즈니스 로직을 주로 배치했나요?

A. 비즈니스 로직은 도메인 서비스에 배치하고, 애플리케이션 서비스에서는 흐름 제어와 트랜잭션 처리에 집중합니다. 단일 엔티티 관련 로직은 해당 엔티티 내부에, 여러 엔티티를 다루는 복잡한 로직은 도메인 서비스에 구현하는 것이 좋습니다.

📖 상세 설명

이 꼬리 질문은 "로직을 어느 계층에 두는지 스스로 기준이 있는가"를 봅니다. 좋은 답의 뼈대는 간단한 3단계 규칙입니다 — ① 한 엔티티로 판단되는 로직은 그 엔티티 안에, ② 여러 엔티티가 얽히면 도메인 서비스에, ③ 흐름·트랜잭션·기술은 애플리케이션 서비스에.

비유 — 계산 규칙은 계산기 안에. "할인율을 적용한 최종 금액"을 구하는 규칙은 계산기(Order 엔티티) 스스로 갖고 있는 게 자연스럽습니다. 사용자는 그저 버튼을 누르는 순서(흐름)만 정하면 되죠. 만약 계산 규칙까지 사용자(서비스)가 매번 직접 해야 한다면, 규칙이 여기저기 흩어져 하나 바뀔 때마다 전부 찾아 고쳐야 합니다.
피해야 할 안티패턴 — 빈혈 도메인 모델(Anemic Domain Model). 엔티티는 get/set만 있는 빈 껍데기가 되고 모든 로직이 서비스에 몰리는 구조입니다. 당장은 편하지만 규칙이 흩어져 유지보수가 어려워집니다. "데이터를 가진 객체가 그 데이터에 대한 규칙도 갖는다"는 객체지향의 기본을 지키는 편이 좋습니다.

Q16. REST API 설계에서 응답에 꼭 포함시켜야 하는 항목은 무엇인가요?

REST API 응답에 꼭 포함시켜야 하는 항목은 다음과 같습니다.

  • 상태 코드: HTTP 표준 상태 코드(200, 400, 404, 500 등)
  • 메시지: 사용자 친화적인 메시지, 오류 원인 설명
  • 데이터(payload): 요청 결과 데이터
  • 메타데이터: 요청 ID, 타임스탬프, 페이지네이션 정보 등
📖 상세 설명

이 질문의 의도는 "응답을 받는 프론트엔드(클라이언트) 입장을 상상할 수 있는가"입니다. 데이터만 덜렁 던지면, 클라이언트는 "이게 성공인가 실패인가?", "실패면 왜?", "다음 페이지는 있나?"를 알 방법이 없습니다. 좋은 응답은 데이터뿐 아니라 그 데이터를 해석할 단서까지 함께 담습니다.

비유 — 택배 송장. 택배 상자만 오고 아무 정보가 없다면 곤란하죠. 송장에는 배송 상태(배송중/완료 = 상태 코드), 안내 문구("부재 시 경비실" = 메시지), 실제 물건(= 데이터), 그리고 운송장 번호·발송 시각(= 메타데이터)이 적혀 있습니다. API 응답도 똑같습니다. 이 네 가지가 있어야 받는 쪽이 "무슨 일이 일어났고, 문제가 생기면 어디로 문의할지"를 알 수 있습니다.

특히 상태 코드는 "기계(클라이언트 코드)가 성공/실패를 판단하는 신호"이고, 메시지는 "사람이 읽는 설명"이라 역할이 다릅니다 — 둘 다 필요합니다. 또 요청 ID 같은 메타데이터는 장애가 났을 때 "이 요청 로그를 찾아줘"라며 서버 로그와 응답을 연결하는 추적 열쇠가 됩니다. 실패 응답에서는 성공과 같은 구조로 에러 코드·메시지를 담아, 클라이언트가 한 가지 방식으로 처리할 수 있게 하는 것이 중요합니다.

🔁 꼬리 질문

Q. 당신의 API는 상태 코드와 에러 메시지를 어떻게 일관성 있게 관리하나요?

A. 요청 ID, 상태 코드, 메시지, 에러 코드 등을 일관된 구조로 반환하고, 공통 Response 객체를 통해 관리합니다. 이를 통해 클라이언트가 응답을 일관되게 처리할 수 있고, API 문서화도 용이해집니다.

📖 상세 설명

이 꼬리 질문은 "일관성을 어떻게 강제하느냐"를 봅니다. 각 개발자가 API마다 응답 모양을 제각각 만들면, 어떤 곳은 { "msg": ... }, 어떤 곳은 { "error": ... }가 되어 클라이언트가 매번 다르게 분기해야 합니다. 핵심은 "규칙을 사람의 성실함에 맡기지 말고 한 곳에서 자동으로 감싸라"입니다.

비유 — 회사 공문 양식. 부서마다 자기 맘대로 문서를 쓰면 받는 사람이 매번 헤맵니다. 그래서 회사는 표준 공문 양식(머리글·본문·발신번호)을 정해두고, 누가 쓰든 같은 서식으로 나가게 합니다. API도 마찬가지 — 공통 Response 래퍼와, 예외를 가로채 표준 에러 형식으로 바꿔주는 중앙 장치(NestJS라면 Exception Filter·Interceptor)를 두면, 개별 코드가 신경 쓰지 않아도 모든 응답이 같은 모양으로 통일됩니다.

여기에 에러 코드 체계(예: ORDER_NOT_FOUND)를 더하면, 클라이언트가 사람이 읽는 메시지 대신 코드로 분기할 수 있어 다국어·문구 변경에도 안전합니다. 그리고 모든 응답에 요청 ID를 실어 서버 로그와 이어두면, 장애 문의가 왔을 때 그 ID로 로그를 바로 추적할 수 있습니다. 이렇게 하면 클라이언트 처리도 단순해지고 API 문서화도 자동으로 정돈됩니다.

🏗️

Q21. MSA(Microservice Architecture)의 장단점을 설명해주세요.

장점: 서비스별 독립적 배포와 확장 가능, 장애 격리, 기술 스택 다양화 가능

단점: 분산 시스템 복잡성 증가, 통합 테스트 어려움, 트랜잭션 관리 복잡

📖 상세 설명

MSA는 하나의 큰 애플리케이션(모놀리식)을 기능별로 잘게 쪼개, 각각을 독립적으로 배포·운영하는 구조입니다. 이 질문의 함정은 "MSA = 무조건 좋은 것"이라고 답하는 것입니다. MSA는 장점만큼 큰 비용을 치르는 트레이드오프라는 점을 이해하고 있는지가 핵심입니다.

비유 — 원룸 하나 vs 여러 채로 나뉜 단지. 모놀리식은 모든 방이 붙어 있는 큰 원룸입니다. 관리는 단순하지만, 부엌 하나 리모델링하려 해도 집 전체 공사를 세워야 하고, 한 곳에 불이 나면 전체가 위험합니다. MSA는 여러 채로 나뉜 단지입니다. 각 집을 따로 수리·증축할 수 있고(독립 배포·확장), 한 집에 불이 나도 옆집은 멀쩡합니다(장애 격리). 대신 집과 집 사이 도로·배관(네트워크 통신)을 새로 깔고 관리해야 하죠. 이 "집 사이의 복잡함"이 바로 MSA의 대가입니다.

정리하면 장점은 ① 서비스별 독립 배포·확장(주문 트래픽만 몰리면 주문 서비스만 늘림), ② 장애 격리, ③ 서비스마다 다른 기술 스택 선택 가능. 단점은 ① 네트워크를 넘나드는 분산 시스템의 복잡성(지연·장애 전파), ② 여러 서비스에 걸친 트랜잭션 관리가 까다로움(앞서 본 Saga), ③ 통합 테스트·운영·모니터링 부담 증가입니다.

신입이 빠지기 쉬운 함정. "요즘 다 MSA니까 MSA가 정답"이 아닙니다. 팀이 작고 서비스가 단순하다면 잘 만든 모놀리식이 훨씬 빠르고 안전합니다. 실제로 많은 서비스가 "모놀리식으로 시작해, 정말 필요한 부분만 점진적으로 분리"하는 길을 택합니다. 면접에서 이 절제된 판단을 보여주면 가산점이 됩니다.
🔁 꼬리 질문

Q. MSA에서 서비스 간 통신 방식은 어떤 것들이 있나요?

A. 동기식 통신으로는 REST API, gRPC 등이 있고, 비동기식 통신으로는 메시지 큐(Kafka, RabbitMQ)를 활용한 이벤트 기반 통신이 있습니다. 각 통신 방식은 요구사항과 시스템 특성에 따라 선택됩니다.

📖 상세 설명

서비스를 쪼갰으니 이제 서로 대화해야 합니다. 대화 방식은 크게 동기(즉시 응답을 기다림)와 비동기(던져놓고 각자 진행) 둘로 나뉩니다. 이 둘의 성격 차이를 이해하는 게 핵심입니다.

비유 — 전화 vs 문자. 동기 통신(REST·gRPC)은 전화입니다. 상대가 받아 답할 때까지 수화기를 들고 기다리죠 — 즉시 결과를 얻지만, 상대가 안 받으면(장애·지연) 나도 발이 묶입니다. 비동기 통신(Kafka·RabbitMQ)은 문자·우편함입니다. 메시지를 던져두면 상대가 편할 때 꺼내 처리합니다 — 서로 기다리지 않아 느슨하게 연결되고 한쪽이 잠깐 죽어도 메시지가 큐에 남아 안전합니다. 대신 "언제 처리될지 모르는" 특성상 결과가 바로바로 일치하진 않습니다(최종 일관성).

그래서 즉시 답이 꼭 필요한 조회(예: 결제 전 재고 확인)는 동기(REST/gRPC)가 맞고, "주문 완료됨" 같은 사건을 여러 서비스에 알리는 경우는 비동기 이벤트가 적합합니다. 동기는 단순하지만 서비스들이 서로 강하게 묶여 한 곳의 지연이 줄줄이 전파될 위험이 있고, 비동기는 결합이 느슨하고 장애에 강한 대신 흐름 추적과 일관성 관리가 어렵습니다. "정답은 하나가 아니라, 요구사항에 따라 섞어 쓴다"가 좋은 마무리입니다.
