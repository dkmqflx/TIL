Q19. NestJS의 IoC와 DI에 대해 설명해주세요.

IoC(Inversion of Control)는 객체의 생성과 생명주기 관리를 개발자가 아닌 프레임워크(NestJS의 DI 컨테이너)가 담당하는 것이고, DI(Dependency Injection)는 객체가 필요로 하는 의존성을 외부에서 주입하는 방식입니다. NestJS에서는 @Injectable()로 등록한 프로바이더를 컨테이너가 생성·관리하고, 생성자(constructor)를 통해 주입합니다. 이를 통해 결합도를 낮추고 테스트 용이성을 높일 수 있습니다(테스트 시 Test.createTestingModule()로 실제 구현 대신 Mock 프로바이더를 손쉽게 교체).

Q. NestJS 프로바이더의 생명주기(생명주기 훅)에 대해 설명해주세요.

A. 프로바이더는 생성 → 의존성 주입 → 초기화 훅 → 사용 → 종료 훅 → 소멸 순으로 진행됩니다. NestJS는 인터페이스 형태의 생명주기 훅을 제공하는데, 초기화 시점에는 OnModuleInit(모듈 의존성 준비 완료) → OnApplicationBootstrap(모든 모듈 초기화 완료)이 호출되고, 종료 시점에는 OnModuleDestroy → beforeApplicationShutdown → OnApplicationShutdown이 호출됩니다. 종료 훅은 app.enableShutdownHooks()를 켜야 동작하며, DB 커넥션 정리나 진행 중인 작업 마무리(graceful shutdown)에 활용합니다.

Q20. NestJS(TypeORM)에서 트랜잭션 처리 방식에 대해 설명해주세요.

TypeORM에서는 주로 세 가지 방식을 씁니다. ① dataSource.transaction(async (manager) => { ... }) 콜백 방식 — 콜백이 정상 종료되면 커밋, 예외가 던져지면 자동 롤백. ② QueryRunner를 직접 생성해 startTransaction / commitTransaction / rollbackTransaction을 명시적으로 제어하는 방식(세밀한 제어가 필요할 때, finally에서 release() 필수). ③ 선언적(@Transactional 데코레이터) 방식이 필요하면 typeorm-transactional 라이브러리를 도입합니다. 격리 수준은 transaction(isolationLevel, cb)이나 QueryRunner의 startTransaction('SERIALIZABLE')로 지정할 수 있습니다.

Q. 여러 리포지토리에 걸친 작업을 하나의 트랜잭션으로 묶으려면 어떻게 해야 하나요?

A. 각 Repository를 그냥 주입해서 쓰면 서로 다른 커넥션을 사용해 하나의 트랜잭션으로 묶이지 않는 것이 흔한 함정입니다. 트랜잭션 콜백(또는 QueryRunner)이 제공하는 동일한 EntityManager로 manager.getRepository(Entity)를 얻어 모든 쓰기 작업을 수행해야 같은 트랜잭션에 묶입니다. 선언적으로 처리하고 싶다면 typeorm-transactional이 AsyncLocalStorage로 컨텍스트를 전파해 주며, 이때 Propagation.REQUIRED(기존 트랜잭션에 참여, 없으면 생성)·REQUIRES_NEW(항상 새 트랜잭션 생성) 같은 전파 옵션도 지원합니다.

Q22. TypeORM의 N+1 문제란 무엇이며, 어떻게 해결할 수 있나요?

N+1 문제는 연관된 엔티티를 조회할 때 최초 쿼리 1번과 연관 엔티티 조회를 위한 N번의 추가 쿼리가 발생하는 문제입니다. TypeORM에서는 find({ relations }) 옵션이나 QueryBuilder의 leftJoinAndSelect로 한 번의 JOIN 쿼리로 연관 엔티티까지 함께 조회해 해결합니다. 또한 relationLoadStrategy: 'query'로 연관 데이터를 IN 쿼리 한 번에 모아 조회하거나, 엔티티에 eager: true를 설정하는 방법도 있습니다.

Q. leftJoinAndSelect(조인 조회)와 지연 로딩(lazy relations)의 차이점은 무엇인가요?

A. lazy relations(Promise 타입 관계)는 연관 엔티티를 실제 접근하는 시점에 별도 쿼리로 로딩하는 방식이라 반복문 안에서 접근하면 N+1 문제가 발생할 수 있습니다. 반면 leftJoinAndSelect는 QueryBuilder에서 한 번의 JOIN 쿼리로 연관 엔티티까지 함께 조회하므로 N+1을 방지합니다. TypeORM은 기본적으로 관계를 lazy로 두지 않기 때문에, relations 옵션이나 eager: true를 지정하지 않으면 관계가 아예 로딩되지 않는다는 점도 함께 짚으면 좋습니다.
