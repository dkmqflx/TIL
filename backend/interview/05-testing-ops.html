Q8. 당신이 작성한 테스트 코드는 어떤 기준으로 구분되어 있나요?

Controller는 블랙박스 테스트, Service는 통합 테스트, 도메인은 단위 테스트로 분리하여 테스트했습니다. 각 계층별 상세 테스트 전략은 다음과 같습니다.

도메인 레이어

  • 순수 단위 테스트로 외부 의존성 없이 테스트
  • 비즈니스 규칙 검증에 집중
  • Jest의 mock(jest.fn, jest.mock)으로 외부 의존성 대체

서비스 레이어

  • 통합 테스트로 여러 컴포넌트 간 상호작용 검증
  • @nestjs/testing의 Test.createTestingModule()로 필요한 프로바이더만 로드해 구성
  • 실제 DB 연동 테스트 또는 테스트용 인메모리 DB 사용

컨트롤러 레이어

  • supertest로 app.getHttpServer()에 HTTP 요청/응답 검증
  • 입력 유효성 검사, 응답 형식, 상태 코드 확인
  • 서비스 레이어는 Mock으로 대체

통합/E2E 테스트

  • 모든 계층을 통합한 전체 흐름 테스트
  • 실제 환경과 유사한 설정으로 테스트
📖 상세 설명

이 질문의 의도는 "테스트를 그냥 짜는 게 아니라, 계층마다 왜 다른 전략을 쓰는지 이해하고 있는가"입니다. 핵심 개념은 테스트 피라미드 — 아래로 갈수록 빠르고 싸고 많이, 위로 갈수록 느리고 비싸고 적게 쌓는 구조입니다.

비유 — 자동차 공장의 3단계 검사. ① 나사·엔진 같은 부품 하나하나를 따로 검사하고(→ 단위 테스트: 도메인 로직), ② 엔진+변속기를 조립해서 함께 돌려보고(→ 통합 테스트: 서비스 계층), ③ 완성차를 실제 도로에서 시운전합니다(→ E2E: 컨트롤러부터 DB까지 전체 흐름). 부품 검사는 수천 번 빠르게 돌리지만, 시운전은 비싸고 느리니 몇 번만 하죠. 테스트도 똑같습니다.

계층별로 전략이 갈리는 이유는 "그 계층이 무엇에 의존하느냐" 때문입니다. 도메인은 순수한 계산·규칙이라 DB나 네트워크가 필요 없으니 외부를 Mock으로 끊고 단위 테스트로 촘촘히 덮습니다. 서비스는 여러 객체와 DB가 맞물리는 지점이라, 진짜로 잘 연동되는지 통합 테스트로 확인합니다. 컨트롤러는 "HTTP 요청이 들어와 올바른 상태 코드·형식으로 나가는가"가 관심사라, 내부는 Mock으로 두고 supertest로 입구·출구만 블랙박스처럼 검증합니다.

면접 포인트. "전부 E2E로 하면 안 되나요?"라는 꼬리 질문에 대비하세요. E2E만 잔뜩 짜면 느려서 자주 못 돌리고, 깨져도 어디가 문제인지 찾기 어렵습니다. 그래서 단위로 넓게 덮고, 통합·E2E는 핵심 경로에만 얹는 게 정석이라고 답하면 좋습니다.

Q. 통합 테스트와 단위 테스트의 차이점은?

A. 통합 테스트는 실제 연동과 환경을 포함하여 테스트하지만, 단위 테스트는 하나의 로직 단위만 검증합니다. 두 테스트 유형의 주요 차이점은 다음과 같습니다.

테스트 범위

  • 단위 테스트: 하나의 메서드/클래스/컴포넌트만 테스트
  • 통합 테스트: 여러 컴포넌트 간 상호작용을 포함한 테스트

의존성 처리

  • 단위 테스트: 외부 의존성을 Mock/Stub으로 대체
  • 통합 테스트: 실제 의존성을 사용하거나 테스트용 구현체 활용

실행 속도와 안정성

  • 단위 테스트: 빠르고 안정적으로 실행됨
  • 통합 테스트: 상대적으로 느리고 환경에 따라 결과가 달라질 수 있음

문제 발견

  • 단위 테스트: 구체적인 문제 지점 파악 용이
  • 통합 테스트: 컴포넌트 간 상호작용 문제 발견에 효과적
📖 상세 설명
비유 — 레고 블록 하나 vs 조립품. 단위 테스트는 레고 블록 하나가 규격대로 잘 만들어졌는지 보는 것이고, 통합 테스트는 여러 블록을 실제로 끼워 맞춰 흔들어보는 것입니다. 블록 하나하나가 완벽해도, 끼우는 부분(연결부)이 안 맞으면 무너지죠. 그 "연결부"에서 나는 버그는 오직 통합 테스트만 잡아냅니다.

두 테스트는 잡아내는 버그의 종류가 다릅니다. 단위 테스트는 "이 함수의 계산이 틀렸다" 같은 로직 버그를, 통합 테스트는 "쿼리 컬럼명이 실제 테이블과 안 맞는다", "트랜잭션이 안 걸렸다" 같은 연동 버그를 잡습니다. 그래서 둘은 경쟁 관계가 아니라 역할 분담입니다.

기준단위 테스트통합 테스트
대상함수·클래스 하나여러 컴포넌트 + 실제 인프라
외부 의존성Mock/Stub으로 대체실제 DB·구현체 사용
속도매우 빠름 (ms)느림 (DB 기동 등)
실패 시 원인 추적쉬움 (범위 좁음)어려움 (범위 넓음)

Q12. 단위 테스트와 통합 테스트의 차이는?

단위 테스트는 하나의 메서드·클래스를 격리해 검증하는 테스트로, 외부 의존성은 Jest mock 등으로 대체해 빠르고 결정적으로 돌아갑니다(도메인 로직 검증에 적합). 통합 테스트는 여러 컴포넌트·실제 인프라(DB 등)의 연동을 함께 검증합니다. NestJS에서는 목적에 따라 테스트 범위를 나눠 구성합니다.

  • 컨트롤러 계층은 Test.createTestingModule()로 컨트롤러 + Mock 서비스만 주입하고, supertest로 요청/응답·검증·상태코드만 확인
  • 레포지토리·쿼리는 실제 테스트 DB(또는 Testcontainers)에 TypeORM DataSource를 연결해 실제 SQL 동작을 확인
  • 전체 흐름은 앱 모듈 전체를 createNestApplication()으로 띄우고, 실제 DB에 가깝게 검증하려면 Testcontainers로 진짜 DB를 컨테이너로 띄워 e2e 테스트

단위 테스트로 로직을 촘촘히 덮고, 통합 테스트는 계층이 맞물리는 핵심 경로에 집중하는 식으로 역할을 나눴습니다.

📖 상세 설명

Q8과 겹치지만, 이 질문은 특히 "격리(isolation)"라는 단어에 방점이 있습니다. 단위 테스트의 본질은 "테스트하려는 한 조각만 진짜로 실행하고, 나머지는 전부 가짜로 끊어내는 것"입니다.

비유 — 방음실 vs 오케스트라 합주. 단위 테스트는 바이올린 하나만 방음실에 넣고 음이 정확한지 보는 것입니다. 다른 소리가 섞이지 않으니, 삑사리가 나면 범인은 100% 이 바이올린이죠. 통합 테스트는 합주입니다 — 실제로 다 같이 연주해야만 "바이올린과 첼로의 박자가 안 맞는" 문제가 드러납니다. 방음실에선 절대 안 보이는 문제죠.

여기서 왜 Testcontainers 같은 걸 언급하면 좋은지도 알아둡시다. 통합 테스트를 "진짜 같지 않은 가짜 DB(예: SQLite 인메모리)"로 하면, 정작 운영에서 쓰는 PostgreSQL/MySQL 고유 문법이나 동작 차이 때문에 테스트는 통과하는데 운영에서 터지는 일이 생깁니다. Testcontainers는 테스트 시작 시 진짜 DB를 도커 컨테이너로 잠깐 띄웠다가 끝나면 버리는 방식이라, "운영과 똑같은 DB"로 검증하면서도 뒷정리가 깔끔합니다.

Q. Mock 객체는 어떤 경우에 사용했나요?

A. Mock 객체는 의존 객체의 동작을 시뮬레이션하여 테스트 범위를 제한하고 속도를 높이기 위해 사용합니다. 데이터베이스, 외부 API 호출 등을 대체하거나 특정 시나리오(예: 에러 상황)를 쉽게 재현할 때 활용됩니다.

📖 상세 설명
비유 — 영화 촬영의 스턴트 대역·더미. 자동차가 절벽으로 떨어지는 장면을 진짜 주연 배우로 찍을 순 없죠. 더미 인형(Mock)을 대신 태웁니다. Mock을 쓰는 이유도 똑같습니다 — 실제로 부르면 위험하거나(결제 실제 청구), 느리거나(외부 API), 통제할 수 없는(현재 시각·랜덤값) 것들을 내가 조종 가능한 가짜로 바꿔 끼우는 겁니다.

대표적으로 이런 상황에 씁니다:

  • 느리거나 외부에 있는 것 — DB, 결제·이메일 같은 외부 API. 매 테스트마다 진짜로 부르면 느리고 불안정합니다.
  • 재현하기 어려운 상황 — "결제 서버가 타임아웃 났을 때"처럼 일부러 만들기 힘든 에러 케이스를, Mock이 "에러를 던지도록" 시켜 쉽게 테스트합니다.
  • 매번 값이 바뀌는 것 — Date.now(), 랜덤값. 고정된 가짜값을 주입해 결정적(deterministic) 테스트로 만듭니다.
과유불급 — Mock을 너무 많이 쓰면. 모든 걸 가짜로 바꾸면 결국 "내가 짠 가짜가 내 예상대로 동작하는지"만 확인하게 되어, 정작 진짜 코드의 버그를 못 잡습니다. 또 실제 구현이 바뀌면 Mock도 같이 고쳐야 해 깨지기 쉬운 테스트가 됩니다. "끊어야 할 외부 경계에만 Mock, 검증 대상 로직은 진짜로"가 원칙입니다.

Q15. Node.js에서 메모리 누수나 이벤트 루프 지연을 어떻게 감지하나요?

Node.js/V8 환경에서는 다음과 같은 지표로 감지할 수 있습니다.

  • 높은 CPU 사용률과 응답 시간 증가 (특히 이벤트 루프가 막히는 구간)
  • 이벤트 루프 지연(event loop lag) 증가 — perf_hooks.monitorEventLoopDelay로 측정
  • process.memoryUsage()의 heapUsed·RSS가 요청 처리 후에도 계속 우상향
  • V8 GC pause가 잦아지고 길어짐 (--trace-gc 로그로 확인)
  • 재시작 전까지 메모리가 회복되지 않는 지속적 증가 패턴(누수 의심)
📖 상세 설명

이 질문을 이해하려면 먼저 Node.js의 특징 하나를 알아야 합니다 — 메인 작업을 처리하는 스레드가 딱 하나(이벤트 루프)라는 점입니다. 그래서 두 종류의 문제가 특히 치명적입니다.

비유 — 창구가 하나뿐인 은행. 이벤트 루프 지연은 한 손님이 창구에서 복잡한 서류를 한참 작성하는 바람에, 뒤에 줄 선 손님 전부가 멈춰 기다리는 상황입니다(무거운 동기 연산이 루프를 점유). 메모리 누수는 창구 뒤 창고에 서류를 쌓기만 하고 안 버려서, 결국 창고가 꽉 차 은행이 마비되는(OOM으로 프로세스 종료) 상황이고요. 둘 다 "느려지다 결국 멈춘다"로 나타나 헷갈리지만, 원인과 처방이 다릅니다.

이벤트 루프 지연은 perf_hooks.monitorEventLoopDelay()로 수치화합니다. 이건 "루프가 한 바퀴 도는 데 원래보다 얼마나 늦었는지"를 재는 도구입니다. 평소 1ms 근처여야 할 지연이 수십~수백 ms로 튀면, 어딘가에서 동기 블로킹 작업이 루프를 잡고 있다는 신호입니다.

메모리 누수는 process.memoryUsage()의 heapUsed·RSS가 요청 처리가 끝난 뒤에도 계속 우상향하는 패턴으로 의심합니다. 여기서 한 발 더 들어가려면 힙 스냅샷(heap snapshot)을 씁니다.

힙 스냅샷 비교법 — "before / after 사진 찍기". node --inspect로 실행한 뒤 Chrome DevTools에 연결해, ① 부하를 주기 전 스냅샷을 찍고, ② 같은 요청을 수천 번 돌린 후 다시 찍어, ③ 두 스냅샷을 비교합니다. 정상이라면 늘었다가 GC로 회수돼야 할 객체가, 계속 살아남아 쌓여 있으면 그게 누수의 범인입니다. 이 흐름을 자동화해 주는 clinic.js(clinic doctor/heapprofiler) 같은 도구도 있습니다.
🔁 꼬리 질문

Q. 메모리·이벤트 루프 병목을 줄이기 위해 어떤 리팩토링을 했나요?

A. 대용량 데이터를 한 번에 메모리에 올리던 부분을 스트림·페이지네이션으로 바꾸고, 무거운 CPU 작업은 Worker Threads나 BullMQ 큐로 오프로드했습니다. 또한 해제되지 않던 이벤트 리스너·타이머·전역 캐시 참조를 정리하고, 동기 블로킹 호출을 비동기로 전환해 이벤트 루프 점유 시간을 줄이는 리팩토링으로 지연과 메모리 부하를 낮출 수 있습니다.

📖 상세 설명

처방은 "무엇이 문제였나"에 따라 갈립니다. 위 답변은 두 병목(이벤트 루프 점유와 메모리 폭증)에 대한 대표 처방을 잘 담고 있습니다. 비유로 묶어보면 이해가 쉽습니다.

비유 — 창구 하나뿐인 은행, 다시. 오래 걸리는 손님(무거운 CPU 작업)은 창구를 막지 않게 별도 상담실(Worker Threads)이나 대기표 시스템(BullMQ 큐)으로 보냅니다. 그리고 서류 100만 장을 한꺼번에 창고에 쌓는 대신(메모리 폭증), 한 뭉치씩 처리하고 흘려보냅니다(스트림·페이지네이션). 이러면 창구(이벤트 루프)도 안 막히고 창고(메모리)도 안 넘칩니다.
  • 스트림 / 페이지네이션 — 수십만 건을 find()로 한 번에 배열에 담으면 메모리가 터집니다. DB 커서·스트림이나 페이지 단위로 조금씩 읽어 흘려보냅니다.
  • Worker Threads / 큐(BullMQ) — 이미지 변환·암호화 같은 CPU 집약 작업을 메인 루프에서 떼어내, 별도 스레드나 백그라운드 워커가 처리하게 합니다.
  • 참조 정리 — 안 지워진 setInterval 타이머, 계속 붙는 이벤트 리스너, 무한정 커지는 전역 캐시(Map)는 대표적 누수원입니다. 해제 시점을 명확히 하거나 크기 제한(LRU)을 둡니다.
  • 동기 → 비동기 — fs.readFileSync처럼 루프를 멈추는 동기 호출을 비동기 버전으로 바꿔 점유 시간을 없앱니다.

Q17. CI와 CD의 차이를 설명해주세요.

CI(Continuous Integration)는 코드 통합과 테스트를 자동화하는 과정입니다. 개발자가 변경한 코드를 중앙 저장소에 자주 통합하고, 빌드와 테스트를 자동으로 수행하여 문제를 조기에 발견합니다.

CD(Continuous Delivery/Deployment)는 배포 자동화를 의미합니다. Continuous Delivery는 자동으로 테스트 환경까지 배포하되 프로덕션 배포는 수동 승인을 거치고, Continuous Deployment는 프로덕션 환경까지 완전 자동화된 배포를 의미합니다.

📖 상세 설명

CI의 핵심 단어는 "자주(Continuous)"입니다. 옛날처럼 각자 몇 주씩 따로 개발하다 한 번에 합치면, 충돌이 산더미처럼 쌓여 "머지 지옥"이 옵니다. CI는 매일, 매 커밋마다 합치고 자동으로 빌드·테스트해서, 문제를 작을 때 바로 잡자는 개념입니다.

비유 — 여러 요리사의 주방. CI는 각 요리사가 만든 재료를 자주 한 냄비에 합쳐 맛보는 것입니다. 매번 간을 보니(자동 테스트) 누가 소금을 쏟았는지 바로 압니다. CD는 그렇게 완성된 요리를 손님상까지 자동으로 내보내는 단계입니다. 여기서 Delivery는 "서빙 직전 지배인의 최종 승인(수동 버튼)"을 거치는 것이고, Deployment는 그 승인마저 없애 주방에서 손님상까지 완전 자동으로 나가는 것입니다.

즉 CI와 CD는 하나의 컨베이어 벨트로 이어집니다: git push → [CI] 빌드 + 테스트 + 코드 검사 → [CD] 스테이징 배포 → (Delivery면 사람이 승인 버튼, Deployment면 자동) → 프로덕션 배포. CI가 "합쳐도 안 깨지는지"를 보장하고, CD가 "그걸 안전하게 내보내는" 일을 맡습니다.

🔁 꼬리 질문

Q. 당신의 프로젝트에서 CI/CD 파이프라인은 어떻게 구성되어 있나요?

A. CI는 코드 체크아웃, 의존성 설치, 테스트 실행, 빌드 생성, 코드 품질 검사 등을 자동화하고, CD는 여기에 테스트 환경 배포, 통합/성능 테스트, 스테이징 환경 배포, 사용자 수용 테스트, 프로덕션 환경 배포까지 이어지는 파이프라인을 구성합니다.

📖 상세 설명

이 꼬리 질문은 "교과서 정의 말고, 실제 파이프라인을 순서대로 그려낼 수 있는가"를 봅니다. 대답은 "어떤 이벤트에서 시작해, 어떤 단계를 거쳐, 어디에 배포되는가"를 흐름으로 말하면 됩니다.

비유 — 공장 컨베이어 벨트. 원재료(코드)가 벨트에 올라가면, 검수대(테스트)를 지나 포장(빌드)되고, 창고(스테이징)를 거쳐 매장(프로덕션)에 진열됩니다. 어느 검수대에서든 불량이 나오면 벨트가 멈추고 뒤 공정으로 안 넘어갑니다 — 테스트가 실패하면 배포가 중단되는 것과 같죠.

예를 들어 GitHub Actions 기준으로 이렇게 말할 수 있습니다:

flow
PR 생성/푸시
  └─[CI] 체크아웃 → 의존성 설치 → lint → 단위·통합 테스트 → 빌드
main 머지
  └─[CD] 이미지 빌드/푸시 → 스테이징 배포 → 스모크 테스트
        → (수동 승인) → 프로덕션 배포 → 헬스체크

여기에 "테스트 실패 시 배포 차단", "실패하면 이전 버전으로 자동 롤백", "무중단 배포(블루-그린/롤링)" 같은 안전장치를 덧붙이면 실무 감각이 잘 드러납니다.

Q18. 서비스에서 장애가 발생했을 때 우선적으로 해야 할 일은?

서비스 장애가 발생했을 때는 신속하고 체계적인 대응이 중요합니다. 우선적으로 취해야 할 조치들은 다음과 같습니다. 첫째, 장애의 영향 범위를 파악해야 합니다. 영향받는 서비스와 사용자 수를 확인하고, 장애의 심각도를 평가하여 적절한 대응 수준을 결정합니다.

📖 상세 설명

이 질문에서 신입이 흔히 하는 실수는 "원인부터 찾겠습니다"라고 답하는 것입니다. 하지만 실무의 1순위는 원인 규명이 아니라 피해를 멈추는 것(지혈)입니다. 원인 분석은 서비스를 살려낸 다음에 합니다.

비유 — 응급실의 원칙. 출혈이 심한 환자가 실려 오면 의사가 "왜 다쳤는지"부터 조사하지 않습니다. 먼저 지혈해서 생명을 살리고, 사고 경위(부검·원인 분석)는 안정된 뒤에 따집니다. 장애 대응도 똑같습니다 — 복구가 먼저, 원인 규명은 나중. 이 순서를 뒤집으면 분석하는 동안 피해가 계속 커집니다.

그래서 대응은 대략 이런 순서로 흐릅니다:

  • ① 감지·영향 파악 — 무엇이, 얼마나 많은 사용자에게, 얼마나 심각하게 영향을 주는지 확인하고 심각도를 정합니다.
  • ② 전파·공유 — 관련 팀과 이해관계자에게 알리고, 대응 담당(인시던트 커맨더)을 정해 혼선을 막습니다.
  • ③ 완화(지혈) — 이전 버전으로 롤백, 문제 부분 격리, 트래픽 우회 등 가장 빠르게 피해를 멈추는 조치를 먼저 합니다.
  • ④ 복구 확인 — 지표가 정상으로 돌아왔는지 모니터링으로 검증합니다.
  • ⑤ 사후 분석(포스트모템) — 안정된 뒤 근본 원인을 찾고, 사람을 비난하지 않고 재발 방지책을 문서로 남깁니다.
면접에서 좋은 인상. "완벽한 원인을 찾을 때까지 기다리기보다, 롤백 등으로 우선 서비스를 정상화하고 원인은 그 뒤에 분석하겠다"는 우선순위 감각과, "책임 추궁이 아니라 재발 방지 중심의 포스트모템"을 언급하면 실무 이해도가 높아 보입니다.
🔁 꼬리 질문

Q. 실제 장애 대응 경험이 있다면 어떻게 처리하셨나요?

A. 장애 발생 시 가장 먼저 사용자 영향도 파악과 서비스 격리, 이후 빠른 복구 및 로그 분석, 원인 재현을 수행해야 합니다. 임시 조치를 적용하여 서비스 영향을 최소화해야 합니다. 트래픽을 우회시키거나, 문제가 되는 서비스를 격리하거나, 이전 버전으로 롤백하는 등의 방법을 사용할 수 있습니다. 또한 회로 차단기(Circuit Breaker) 패턴을 활용하여 장애가 전파되는 것을 방지할 수 있습니다.

📖 상세 설명

여기서 핵심 키워드는 "격리"와 "장애 전파 차단"입니다. 큰 시스템에서는 작은 고장 하나가 연쇄적으로 전체를 무너뜨리는 것이 가장 무섭습니다. 그래서 "고장을 한 칸에 가두는" 설계가 중요합니다.

비유 — 배의 방수 격벽 & 집의 두꺼비집. 큰 배는 한 구획에 물이 새도 격벽으로 막아 배 전체가 가라앉지 않게 합니다(서비스 격리·Bulkhead). 서킷 브레이커(Circuit Breaker)는 집의 두꺼비집(누전 차단기)과 같습니다 — 특정 회로에 과부하가 걸리면 스스로 차단해, 그 불이 집 전체로 번지지 않게 합니다. 장애 난 외부 API를 계속 호출하다 우리 서버까지 같이 죽는 상황을, 서킷 브레이커가 "잠깐 호출을 끊어" 막아줍니다.

서킷 브레이커를 조금 더 풀면: 어떤 의존 서비스(예: 결제 API)가 계속 실패하면, 차단기가 "열려서" 한동안 아예 호출을 시도하지 않고 즉시 실패 처리합니다. 덕분에 응답 없는 서비스를 무한정 기다리다 우리 쪽 스레드·자원까지 고갈되는 연쇄 장애를 막습니다. 일정 시간 뒤 조심스레 "반쯤 열어" 회복됐는지 떠보고, 정상이면 다시 닫습니다. 여기에 롤백·트래픽 우회·재현을 위한 로그 확보까지 함께 말하면 완성도 높은 답이 됩니다.
