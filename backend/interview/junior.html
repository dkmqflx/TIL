Q1. DB에서 B-Tree 인덱스를 사용하는 이유는 무엇인가요?

검색, 정렬 성능을 높이기 위해 B-Tree 구조를 사용합니다. 균형 잡힌 트리 구조로 빠른 탐색이 가능하고, 삽입/삭제 시에도 성능을 유지할 수 있기 때문입니다. B-Tree는 O(log n) 시간 복잡도로 데이터를 찾을 수 있어 대용량 데이터에서도 효율적입니다. 또한 인덱스 구조가 항상 정렬된 상태를 유지하기 때문에 범위 검색에 특히 유리합니다.

🔁 꼬리 질문

Q. B-Tree와 Hash 인덱스의 차이점은 무엇인가요?

A. B-Tree는 범위 검색과 정렬이 가능한 반면, Hash 인덱스는 정확한 키 검색에만 최적화되어 있습니다. 따라서 WHERE 절에 = 조건이 아닌 연산이 있을 때는 B-Tree가 적합합니다. Hash 인덱스는 '=' 연산에 O(1) 시간 복잡도로 매우 빠르지만, '>', '<', 'BETWEEN', 'LIKE' 등의 연산에는 사용할 수 없고 인덱스를 이용한 정렬도 불가능합니다. 또한 B-Tree는 부분 검색도 가능하지만 Hash는 전체 키에 대해서만 동작합니다.

Q2. Repeatable Read 격리 수준에서 팬텀 리드가 발생하지 않는 이유는?

InnoDB의 Repeatable Read에서는 두 가지 메커니즘이 함께 작동합니다. 첫째, 일반 SELECT(잠금 없는 읽기)는 MVCC 스냅샷을 통해 트랜잭션 시작 시점의 일관된 데이터를 읽으므로 팬텀 리드가 보이지 않습니다. 둘째, SELECT ... FOR UPDATE/SHARE 같은 잠금 읽기나 쓰기에서는 Next-Key Lock(레코드 락 + 갭 락)으로 해당 범위에 새 레코드가 끼어드는 것을 막습니다. 표준 SQL에서는 Repeatable Read가 팬텀 리드를 막지 못하지만, InnoDB는 이 두 메커니즘으로 팬텀을 방지합니다. 다만 스냅샷 읽기와 잠금 읽기를 섞어 쓸 때는 write skew 같은 이상 현상이 남을 수 있으므로, 완전한 직렬화가 필요하면 Serializable을 써야 합니다.

🔁 꼬리 질문

Q. Next-Key Lock이란 무엇인가요? 어떻게 동작하나요?

A. Next-Key Lock은 인덱스 레코드와 그 사이 구간까지 잠그는 방식으로, 새로운 레코드가 들어오는 것을 방지하여 팬텀 리드를 막습니다. 이는 Record Lock(인덱스 레코드 자체를 잠금)과 Gap Lock(인덱스 레코드 사이의 간격을 잠금)을 조합한 형태입니다. 예를 들어, 인덱스 값이 10, 20, 30인 테이블에서 WHERE id BETWEEN 10 AND 30 쿼리 실행 시, Next-Key Lock은 10 이상 30 이하 범위를 모두 잠가 해당 범위에 새 데이터가 삽입되는 것을 방지합니다.

Q7. 왜 MySQL InnoDB는 기본 격리 수준으로 Repeatable Read를 채택했을까요?

MVCC 기반으로 성능과 정합성의 균형을 유지할 수 있기 때문입니다. Oracle이나 PostgreSQL과 같은 다른 DBMS가 Read Committed를 기본값으로 사용하는 것과 달리, MySQL은 Repeatable Read를 선택했습니다. 이는 다음과 같은 이유가 있습니다.

  • 바이너리 로그 기반 복제 시 소스와 레플리카 간 일관성 보장
  • MVCC 구현 방식의 특성상 Read Committed보다 오버헤드가 크지 않음
  • 높은 격리 수준으로 데이터 일관성을 더 중요시하는 설계 철학
  • 잠금 읽기·쓰기 시 Next-Key Lock으로 팬텀 리드를 방지(일반 SELECT는 MVCC 스냅샷으로 처리) — 다만 완전한 직렬화는 아니므로 Serializable과 동일하지는 않음

Q. MVCC에서 Undo Log는 어떤 역할을 하나요?

A. Undo Log는 다음과 같은 중요한 역할을 합니다.

  • 트랜잭션 롤백 시 이전 데이터로 복원하는 데 사용
  • MVCC에서 다른 트랜잭션이 변경한 레코드의 이전 버전을 조회할 수 있게 함
  • 트랜잭션 격리 수준에 따라 적절한 버전의 데이터를 읽을 수 있도록 지원
  • 롤백 세그먼트에 저장되며, 트랜잭션의 ID와 함께 레코드 변경 이력 관리

예를 들어, 트랜잭션 A가 레코드를 수정 중일 때 트랜잭션 B가 같은 레코드를 읽으면, 트랜잭션 B는 Undo Log에서 트랜잭션 A 시작 전의 버전을 읽게 됩니다.

Q9. 커버링 인덱스란 무엇이고, 어떤 상황에서 사용되나요?

인덱스에 포함된 컬럼만으로 쿼리를 처리할 수 있을 때, 테이블 접근 없이 인덱스만으로 결과를 반환하는 인덱스입니다. 조회 성능이 극대화됩니다. 구체적으로는 다음과 같습니다.

  • SELECT 절에 있는 모든 컬럼이 인덱스에 포함되어 있어야 함
  • WHERE, ORDER BY, GROUP BY 등에 사용되는 컬럼도 인덱스에 포함되어야 함
  • InnoDB의 경우 PK가 인덱스에 자동으로 포함되므로 활용 가능

예를 들어 (name, age)로 복합 인덱스가 있을 때:

sql
SELECT name, age FROM user WHERE name = 'Dingco'

쿼리는 테이블에 접근하지 않고 인덱스만으로 처리 가능합니다.

Q. 커버링 인덱스를 적용했던 경험이 있나요?

A. 커버링 인덱스를 통해 대량의 데이터를 처리하고자 했을 때 사용했습니다.

구현 사례

  • 사용자 목록 페이징 처리 시 (user_id, name, created_at) 복합 인덱스로 테이블 접근 없이 처리
  • 주문 목록에서 주문일, 상태별 조회 시 (order_date, status, order_id) 인덱스 활용
  • 통계 집계 쿼리에서 GROUP BY, COUNT() 연산을 인덱스만으로 처리

성능 개선 효과

  • 테이블 접근 I/O가 제거되어 디스크 읽기 감소
  • 대용량 테이블에서 수백 배 성능 차이 발생
  • 특히 조인 쿼리에서 효과적 (인덱스는 크기가 작아 메모리에 적재 가능성 높음)

고려사항

  • 인덱스 크기 증가에 따른 트레이드오프 관리
  • 복합 인덱스 컬럼 순서 최적화 (선택도 높은 컬럼 우선)
  • INSERT/UPDATE 성능에 미치는 영향 고려

Q10. 낙관적 락과 비관적 락의 차이를 설명해보세요.

낙관적 락은 충돌 가능성이 낮은 경우 버전 체크로 처리하고, 비관적 락은 충돌 가능성이 높아 미리 락을 거는 방식입니다. 각 방식의 구체적인 특징은 다음과 같습니다.

낙관적 락

  • 데이터에 버전 정보(@Version)를 두고 수정 시 버전 증가
  • 수정 시점에 버전이 변경되었으면 충돌로 판단하고 예외 발생
  • 트랜잭션 충돌이 적은 환경에 적합
  • 락을 획득하지 않아 동시성은 높지만 충돌 시 재시도 로직 필요

비관적 락

  • SELECT FOR UPDATE 등으로 데이터에 실제 락 획득
  • 동시 접근을 원천 차단하여 데이터 일관성 보장
  • 충돌이 빈번한 환경에 적합
  • 락 획득에 따른 대기 시간으로 동시성 저하 가능성
🔁 꼬리 질문

Q. 당신의 프로젝트에서는 어떤 락 방식을 선택했고, 왜 그렇게 결정했나요?

A. 프로젝트의 특성에 따라 락 전략을 선택했습니다.

낙관적 락 적용 사례

  • 사용자 프로필 정보 수정 같이 동시 수정 확률이 낮은 경우
  • 데이터 조회가 많고 수정이 적은 시스템
  • 가용성과 응답 속도가 중요한 사용자 대면 기능
  • JPA의 @Version 어노테이션 활용으로 구현 간소화

비관적 락 적용 사례

  • 재고 관리처럼 동시 수정 충돌이 자주 발생하는 경우
  • 결제 처리나 예약 시스템처럼 데이터 정합성이 매우 중요한 경우
  • 배치 작업에서 데이터 무결성이 필요한 경우

하이브리드 접근법

  • 기본적으로 낙관적 락을 사용하되, 특정 중요 트랜잭션에만 비관적 락 적용
  • 실시간 모니터링으로 충돌 빈도에 따라 전략 동적 변경

Q11. 정규화를 왜 하나요? 그리고 비정규화는 언제 필요한가요?

데이터 중복 제거와 일관성을 위해 정규화를 하며, 조회 성능이나 JOIN이 과도할 경우 비정규화를 적용하기도 합니다. 정규화의 구체적인 장점은 다음과 같습니다.

  • 데이터 중복 최소화로 저장 공간 절약
  • 데이터 변경 시 한 곳만 수정하여 일관성 유지
  • 데이터 무결성 강화 및 이상 현상(Anomaly) 방지
  • 스키마 변경 유연성 증가

비정규화가 필요한 상황은 다음과 같습니다.

  • 읽기 비중이 쓰기보다 매우 높은 시스템
  • 복잡한 JOIN으로 인한 성능 저하 발생 시
  • 통계/분석용 데이터 처리에 최적화가 필요할 때
  • 특정 조회 패턴이 매우 빈번하게 발생할 때

Q. 정규화를 적용하다 성능 문제가 생겼던 경험이 있나요?

A. 정규화와 성능 사이의 균형을 맞추는 실제 경험은 다음과 같았습니다.

문제 상황

  • 전자상거래 주문 내역 조회 시 고객, 상품, 배송 정보 등 여러 테이블 JOIN 발생
  • 대시보드에서 실시간 주문 현황 표시 시 5개 이상 테이블 JOIN으로 응답 시간 증가
  • 특히 주문량이 많은 시간대에 쿼리 지연 현상 심화

해결 방법

  • 주문 조회용 비정규화 테이블 생성 (주문 정보 + 고객명 + 상품명 + 배송상태 등 통합)
  • 원본 정규화 테이블은 유지하되, 주문 생성/변경 시 이벤트 기반으로 조회용 테이블 동기화
  • 자주 조회되는 집계 데이터는 별도 통계 테이블로 미리 계산하여 저장
  • 일부 컬럼에 대해 선택적 중복 허용 (예: 상품명을 주문상세에 중복 저장)

결과

  • 조회 성능 5~10배 개선
  • 데이터 일관성은 이벤트 기반 동기화로 유지
  • 쓰기 작업에 약간의 오버헤드 발생했으나 읽기 비중이 높아 전체적으로 성능 향상

Q3. 트래픽이 몰릴 때 서버 병목을 진단하는 방법은?

CPU, Memory, Disk, Network 사용률 확인 → GC Time, 스레드 수, DB 커넥션 풀 확인. Prometheus + Grafana, 또는 자체 로깅 사용. 각 단계별로 구체적인 명령어나 도구를 활용할 수 있습니다. APM 도구를 활용하면 트랜잭션 레벨의 병목 지점도 식별할 수 있습니다.

🔁 꼬리 질문

Q. GC Time이 길어진다면 어떻게 조치할 수 있나요?

A. GC Time이 길다면, 객체 생성이 과도하거나 Old 영역이 포화된 상태일 수 있습니다. 이럴 경우 GC 정책을 G1GC로 변경하거나 객체 생명주기를 조절해야 합니다. 구체적인 조치로는 다음과 같은 고민을 할 수 있습니다.

  • 힙 메모리 크기 조정 (-Xms, -Xmx 옵션)
  • G1GC나 ZGC 같은 최신 GC 알고리즘 적용
  • 불필요한 객체 생성 줄이기 (특히 루프 내부)
  • String 연산 최적화 (StringBuilder 사용)
  • 컬렉션 사용 패턴 검토 (불필요한 복사 연산 제거)
  • 힙 덤프 분석으로 메모리 누수 찾기
⚡

Q4. Redis를 캐시로 사용할 때 주의해야 할 점은?

캐시 일관성 문제(Cache-Aside 패턴), TTL 관리, 캐시 무효화 전략이 필요합니다. 또한 Redis는 인메모리 데이터 저장소이므로 메모리 사용량 모니터링이 중요합니다. 메모리가 부족해지면 maxmemory-policy 설정에 따라 데이터 제거가 일어날 수 있습니다. 또한 Redis는 기본적으로 싱글 스레드로 동작하므로, 시간 복잡도가 O(N) 이상인 명령어 사용 시 전체 성능에 영향을 줄 수 있어 주의해야 합니다. 분산 환경에서는 Sentinel이나 Cluster 구성도 고려해야 합니다.

🔁 꼬리 질문

Q. Redis에 저장된 캐시와 DB의 일관성이 깨졌을 때 대응 방법은?

A. DB와의 정합성 유지를 위해 다음과 같은 전략을 사용할 수 있습니다.

  • Cache-Aside 패턴: 데이터 갱신 시 캐시를 먼저 무효화하고 DB를 업데이트
  • Write-Through 패턴: DB 업데이트와 캐시 업데이트를 동시에 수행
  • Write-Behind 패턴: 캐시를 먼저 업데이트하고 비동기적으로 DB 업데이트
  • 이벤트 기반 캐시 무효화: DB 변경 이벤트를 구독하여 캐시 업데이트
  • 적절한 TTL 설정으로 오래된 데이터 자동 제거
  • 배치 작업으로 주기적 캐시-DB 동기화

일관성이 깨진 것이 감지되면 해당 키만 선택적으로 무효화하고, 심각한 불일치 시 전체 캐시를 리프레시 할 수 있습니다.

Q6. 1000개의 티켓에 대해 수십만 요청이 동시에 들어오는 상황을 어떻게 처리할 수 있을까요?

Skip Locked, Redis 분산락, 메모리 큐 사용 등으로 RDB 부하를 줄이거나 처리 순서를 제어합니다. 구체적인 아키텍처는 다음과 같습니다.

  • 초기 요청은 API Gateway에서 Rate Limiting으로 서버 보호
  • 모든 요청을 Kafka나 RabbitMQ 같은 메시지 큐에 넣어 비동기 처리
  • Redis Sorted Set으로 요청 순서 보장 및 선착순 처리
  • 작업자(Worker)를 여러 개 두어 병렬 처리하되 분산락으로 동시성 제어
  • DB 업데이트는 배타적 락(FOR UPDATE)이나 낙관적 락으로 처리
  • 처리 결과는 웹소켓이나 이벤트 스트림으로 클라이언트에 실시간 전달
🔁 꼬리 질문

Q. SKIP LOCKED는 MySQL 8.0부터 제공되는데, 그 이전(5.7 등) 환경이라면 어떤 대안이 있을까요?

A. SKIP LOCKED·NOWAIT는 MySQL 8.0부터 표준 지원되므로(5.7은 2023-10 EOL, 8.0이 현재 기준) 8.0 이상이라면 SKIP LOCKED를 쓰는 게 가장 깔끔합니다. 5.7 이하 레거시 환경이라면 다음 대안을 사용할 수 있습니다.

  • FOR UPDATE로 레코드 락을 걸되, 트랜잭션 타임아웃 설정으로 데드락 방지
  • Redis를 활용한 분산락 구현 (SETNX + TTL 활용)
  • 애플리케이션 레벨에서 Semaphore나 ThreadPoolExecutor로 동시 요청 제한
  • 처리 상태 컬럼을 추가하여 낙관적 락 기반 처리 (예: 대기→처리중→완료)
  • 샤딩 기법으로 테이블을 분할하여 락 경합 감소
  • 배치 프로세싱으로 일정 간격마다 처리하여 부하 분산

Q14. 캐시 Avalanche란 무엇이며, 어떻게 방지할 수 있을까요?

캐시 Avalanche는 다수의 캐시 항목이 동시에 만료되어 데이터베이스나 백엔드 시스템에 갑작스러운 부하가 몰리는 현상입니다. 이는 서비스 장애로 이어질 수 있습니다. 방지 방법은 다음과 같습니다.

  • TTL 분산: 캐시 항목마다 만료 시간에 랜덤 지연 추가
  • 백그라운드 갱신: 캐시 만료 전 비동기적으로 데이터 갱신
  • 계층형 캐시 구조: 로컬 캐시와 분산 캐시 함께 사용
  • 캐시 웜업: 시스템 재시작이나 배포 전 주요 항목 미리 로딩
🔁 꼬리 질문

Q. TTL 분산 전략을 적용했던 경험이 있나요?

A. TTL을 고정값이 아니라 기본값에 ±10% 정도의 랜덤 지연을 추가하여 동시 만료를 방지하거나, 서비스 시작 시 미리 Warm-up 캐시를 준비하면 캐시 어밸런치(Avalanche)를 효과적으로 완화할 수 있습니다.

Q5. 서비스 규모가 커지면서 OrderService가 300줄이 넘어갔습니다. 어떻게 리팩토링 하면 좋을까요?

먼저 단일 책임 원칙(SRP)에 따라 책임별로 서비스 클래스를 나누고, 도메인 중심으로 로직을 분산시켰습니다. 구체적으로는:

  • 단일 책임 원칙(SRP)에 따라 주문 생성, 조회, 변경, 취소 등 책임별로 서비스 클래스 분리
  • 복잡한 비즈니스 로직은 도메인 모델로 이동시켜 객체지향적 설계 강화
  • (읽기/쓰기 모델이 실제로 크게 갈릴 때에 한해) 명령과 조회를 분리(CQRS)하는 것도 고려 — 보통 이 규모에서는 1~2번 분리로 충분하고 CQRS는 과한 설계가 되기 쉬움
  • CommandOrderService, QueryOrderService 등으로 역할 구분
  • UseCase 클래스를 도입하여 특정 비즈니스 시나리오 캡슐화
🔁 꼬리 질문

Q. 그럴 경우 트랜잭션은 어디에 걸어야 할까요?

A. 트랜잭션은 한 서비스 계층에서 묶어서 처리하는 것이 일반적입니다. 구체적으로 다음과 같이 구현할 수 있습니다.

  • Facade 패턴을 적용하여 상위 서비스에서 트랜잭션 경계 관리
  • 분리된 서비스들을 호출하는 조정자(Coordinator) 역할의 서비스에 트랜잭션 적용
  • Spring의 @Transactional 어노테이션을 활용하여 AOP 기반 트랜잭션 관리
  • 마이크로서비스처럼 분산된 경우 Saga 패턴을 적용하여 보상 트랜잭션 구현

가능하면 트랜잭션 범위는 최소화하되, 비즈니스적으로 원자성이 필요한 작업은 반드시 하나의 트랜잭션 내에서 처리해야 합니다.

Q13. 도메인 서비스와 애플리케이션 서비스의 차이를 설명해주세요.

도메인 서비스는 도메인 규칙과 비즈니스 로직을 캡슐화하는 서비스입니다. 특정 도메인의 개념과 규칙을 다루며, 여러 도메인 객체 간 상호작용이 필요한 비즈니스 로직을 구현합니다.

애플리케이션 서비스는 사용자 요청을 처리하고 전체 흐름을 조정하며 트랜잭션 경계를 관리합니다. 여러 도메인 서비스를 조합하고 보안, 로깅과 같은 기술적 관심사를 처리합니다.

🔁 꼬리 질문

Q. 당신은 어디에 비즈니스 로직을 주로 배치했나요?

A. 비즈니스 로직은 도메인 서비스에 배치하고, 애플리케이션 서비스에서는 흐름 제어와 트랜잭션 처리에 집중합니다. 단일 엔티티 관련 로직은 해당 엔티티 내부에, 여러 엔티티를 다루는 복잡한 로직은 도메인 서비스에 구현하는 것이 좋습니다.

Q19. Spring의 IoC와 DI에 대해 설명해주세요.

IoC(Inversion of Control)는 객체의 생성과 생명주기 관리를 개발자가 아닌 프레임워크가 담당하는 것이고, DI(Dependency Injection)는 객체가 필요로 하는 의존성을 외부에서 주입하는 방식입니다. 이를 통해 결합도를 낮추고 테스트 용이성을 높일 수 있습니다.

🔁 꼬리 질문

Q. Spring의 Bean 생명주기에 대해 설명해주세요.

A. Bean 생명주기는 생성 → 의존성 주입 → 초기화 메서드 실행(@PostConstruct) → 사용 → 소멸 메서드 실행(@PreDestroy) → 소멸 순으로 진행됩니다. 추가로 BeanPostProcessor를 구현하여 생명주기에 개입할 수도 있습니다.

Q20. Spring에서 트랜잭션 처리 방식에 대해 설명해주세요.

Spring은 @Transactional 어노테이션과 AOP를 활용해 선언적 트랜잭션 관리를 지원합니다. 트랜잭션 경계 설정, 전파 속성, 격리 수준, 롤백 규칙 등을 설정할 수 있습니다.

🔁 꼬리 질문

Q. @Transactional의 propagation 속성 중 REQUIRED와 REQUIRES_NEW의 차이는 무엇인가요?

A. REQUIRED는 기존 트랜잭션이 있으면 참여하고 없으면 새로 생성하는 반면, REQUIRES_NEW는 항상 새로운 트랜잭션을 생성하고 기존 트랜잭션은 일시 중단됩니다. 독립적인 트랜잭션이 필요할 때 REQUIRES_NEW를 사용합니다.

Q22. JPA의 N+1 문제란 무엇이며, 어떻게 해결할 수 있나요?

N+1 문제는 연관된 엔티티를 조회할 때 최초 쿼리 1번과 연관 엔티티 조회를 위한 N번의 추가 쿼리가 발생하는 문제입니다. 해결 방법으로는 fetch join, EntityGraph, batch size 설정 등이 있습니다.

🔁 꼬리 질문

Q. fetch join과 지연 로딩(lazy loading)의 차이점은 무엇인가요?

A. 지연 로딩은 연관 엔티티를 실제 사용할 때 로딩하는 방식으로 N+1 문제가 발생할 수 있습니다. fetch join은 JPQL의 JOIN FETCH 구문으로 한 번의 쿼리로 연관 엔티티까지 함께 조회하여 N+1 문제를 해결합니다.

Q8. 당신이 작성한 테스트 코드는 어떤 기준으로 구분되어 있나요?

Controller는 블랙박스 테스트, Service는 통합 테스트, 도메인은 단위 테스트로 분리하여 테스트했습니다. 각 계층별 상세 테스트 전략은 다음과 같습니다.

도메인 레이어

  • 순수 단위 테스트로 외부 의존성 없이 테스트
  • 비즈니스 규칙 검증에 집중
  • Mockito 등으로 외부 의존성 대체

서비스 레이어

  • 통합 테스트로 여러 컴포넌트 간 상호작용 검증
  • @SpringBootTest 또는 필요한 컴포넌트만 로드하는 슬라이스 테스트
  • 실제 DB 연동 테스트 또는 테스트용 인메모리 DB 사용

컨트롤러 레이어

  • MockMvc로 HTTP 요청/응답 검증
  • 입력 유효성 검사, 응답 형식, 상태 코드 확인
  • 서비스 레이어는 Mock으로 대체

통합/E2E 테스트

  • 모든 계층을 통합한 전체 흐름 테스트
  • 실제 환경과 유사한 설정으로 테스트
🔁 꼬리 질문

Q. 통합 테스트와 단위 테스트의 차이점은?

A. 통합 테스트는 실제 연동과 환경을 포함하여 테스트하지만, 단위 테스트는 하나의 로직 단위만 검증합니다. 두 테스트 유형의 주요 차이점은 다음과 같습니다.

테스트 범위

  • 단위 테스트: 하나의 메서드/클래스/컴포넌트만 테스트
  • 통합 테스트: 여러 컴포넌트 간 상호작용을 포함한 테스트

의존성 처리

  • 단위 테스트: 외부 의존성을 Mock/Stub으로 대체
  • 통합 테스트: 실제 의존성을 사용하거나 테스트용 구현체 활용

실행 속도와 안정성

  • 단위 테스트: 빠르고 안정적으로 실행됨
  • 통합 테스트: 상대적으로 느리고 환경에 따라 결과가 달라질 수 있음

문제 발견

  • 단위 테스트: 구체적인 문제 지점 파악 용이
  • 통합 테스트: 컴포넌트 간 상호작용 문제 발견에 효과적
🧪

Q12. 단위 테스트와 통합 테스트의 차이는?

단위 테스트는 하나의 메서드·클래스를 격리해 검증하는 테스트로, 외부 의존성은 Mockito 등으로 대체해 빠르고 결정적으로 돌아갑니다(도메인 로직 검증에 적합). 통합 테스트는 여러 컴포넌트·실제 인프라(DB 등)의 연동을 함께 검증합니다. 스프링에서는 목적에 따라 슬라이스를 골라 씁니다.

  • 컨트롤러 계층은 @WebMvcTest + MockMvc로 요청/응답·검증·상태코드만 확인(서비스는 Mock)
  • 레포지토리·쿼리는 @DataJpaTest로 JPA 슬라이스만 띄워 실제 SQL 동작을 확인
  • 전체 흐름은 @SpringBootTest로 컨텍스트를 띄우고, 실제 DB에 가깝게 검증하려면 Testcontainers로 진짜 DB를 컨테이너로 띄워 테스트

단위 테스트로 로직을 촘촘히 덮고, 통합 테스트는 계층이 맞물리는 핵심 경로에 집중하는 식으로 역할을 나눴습니다.

🔁 꼬리 질문

Q. Mock 객체는 어떤 경우에 사용했나요?

A. Mock 객체는 의존 객체의 동작을 시뮬레이션하여 테스트 범위를 제한하고 속도를 높이기 위해 사용합니다. 데이터베이스, 외부 API 호출 등을 대체하거나 특정 시나리오(예: 에러 상황)를 쉽게 재현할 때 활용됩니다.

🧪

Q15. GC 튜닝이 필요한 상황을 어떻게 감지하나요?

GC 튜닝이 필요한 상황은 다음과 같은 지표로 감지할 수 있습니다.

  • 높은 CPU 사용률 (특히 GC 스레드)
  • 응답 시간 증가 및 지연 현상
  • Full GC 빈도 증가
  • GC 로그에서 긴 일시 중지(pause) 시간 확인
  • 메모리 사용량의 지속적 증가
🔁 꼬리 질문

Q. GC 튜닝 외에 병목을 줄이기 위해 어떤 리팩토링을 했나요?

A. Full GC가 자주 발생할 때는 Minor GC 비율을 조정하거나, 불필요한 객체 생성을 줄이는 방식으로 최적화할 수 있습니다. 또한 메모리 누수 해결, String 연산 최적화(StringBuilder 사용), 불필요한 Boxing/Unboxing 제거 등의 코드 리팩토링을 통해 GC 부하를 줄일 수 있습니다.

🧪

Q17. CI와 CD의 차이를 설명해주세요.

CI(Continuous Integration)는 코드 통합과 테스트를 자동화하는 과정입니다. 개발자가 변경한 코드를 중앙 저장소에 자주 통합하고, 빌드와 테스트를 자동으로 수행하여 문제를 조기에 발견합니다.

CD(Continuous Delivery/Deployment)는 배포 자동화를 의미합니다. Continuous Delivery는 자동으로 테스트 환경까지 배포하되 프로덕션 배포는 수동 승인을 거치고, Continuous Deployment는 프로덕션 환경까지 완전 자동화된 배포를 의미합니다.

🔁 꼬리 질문

Q. 당신의 프로젝트에서 CI/CD 파이프라인은 어떻게 구성되어 있나요?

A. CI는 코드 체크아웃, 의존성 설치, 테스트 실행, 빌드 생성, 코드 품질 검사 등을 자동화하고, CD는 여기에 테스트 환경 배포, 통합/성능 테스트, 스테이징 환경 배포, 사용자 수용 테스트, 프로덕션 환경 배포까지 이어지는 파이프라인을 구성합니다.

🧪

Q18. 서비스에서 장애가 발생했을 때 우선적으로 해야 할 일은?

서비스 장애가 발생했을 때는 신속하고 체계적인 대응이 중요합니다. 우선적으로 취해야 할 조치들은 다음과 같습니다. 첫째, 장애의 영향 범위를 파악해야 합니다. 영향받는 서비스와 사용자 수를 확인하고, 장애의 심각도를 평가하여 적절한 대응 수준을 결정합니다.

🔁 꼬리 질문

Q. 실제 장애 대응 경험이 있다면 어떻게 처리하셨나요?

A. 장애 발생 시 가장 먼저 사용자 영향도 파악과 서비스 격리, 이후 빠른 복구 및 로그 분석, 원인 재현을 수행해야 합니다. 임시 조치를 적용하여 서비스 영향을 최소화해야 합니다. 트래픽을 우회시키거나, 문제가 되는 서비스를 격리하거나, 이전 버전으로 롤백하는 등의 방법을 사용할 수 있습니다. 또한 회로 차단기(Circuit Breaker) 패턴을 활용하여 장애가 전파되는 것을 방지할 수 있습니다.
