기본 개념

웹 애플리케이션을 만들다 보면 우리는 늘 서로 말이 통하지 않는 두 세계를 오가게 됩니다. 하나는 우리가 TypeScript로 짠 객체(object)의 세계이고, 다른 하나는 PostgreSQL 같은 데이터베이스가 사는 표(table)와 SQL의 세계입니다. TypeScript 객체에게 "너 자신을 DB에 저장해"라고 말해도 객체는 SQL을 할 줄 모르고, 반대로 DB는 우리가 만든 클래스가 무엇인지 알지 못합니다. 그래서 예전에는 개발자가 이 둘 사이에서 매번 직접 번역을 해줘야 했습니다.

비유 — 손님과 외국인 점원 사이의 통역사 여러분(TypeScript 객체)은 한국어만 할 줄 알고, 데이터베이스(점원)는 영어(SQL)만 알아듣는다고 상상해 보세요. 둘이 직접 마주 앉아도 주문 하나 제대로 못 합니다. ORM은 그 사이에 서 있는 통역사예요. 여러분이 "이 사용자를 저장해 주세요"라고 한국어로 부탁하면, 통역사가 알아서 INSERT INTO ...라는 영어(SQL)로 바꿔 점원에게 전하고, 점원의 대답도 다시 한국어(객체)로 돌려줍니다. TypeORM이 바로 이 통역사입니다.

그래서 TypeORM에서 데이터는 Entity라는 클래스로 정의하고, 실제 DB와의 대화는 Repository라는 창구를 통해 주고받습니다. 이 두 단어는 지금 당장 외울 필요 없이, 뒤에서 하나씩 천천히 짚어 볼 거예요. 핵심은 이것입니다 — Spring JDBC처럼 SQL을 한 줄 한 줄 손으로 쓰지 않아도, 저장·조회·수정·삭제(CRUD) 같은 기본 작업은 TypeORM이 알아서 SQL로 번역해 처리해 준다는 것. 덕분에 우리는 SQL 문법이 아니라 "어떤 데이터를 다루고 싶은가"라는 의도에만 집중할 수 있습니다.

예를 들어 아래처럼 생긴 users 테이블이 있다고 해봅시다. TypeORM에서는 이런 표 하나를 그대로 하나의 Entity 클래스로 옮겨 표현하게 됩니다.

Raw SQL vs TypeORM

ORM(Object-Relational Mapping)이라는 이름은 말 그대로 객체(Object)와 관계형 DB(Relational)를 서로 이어 매핑(Mapping)한다는 뜻입니다. 앞서 통역사 비유에서 봤듯이, SQL을 직접 쓰지 않고 TypeScript 객체를 다루듯 DB를 다룰 수 있게 해주는 것이죠. 아래 두 코드를 나란히 놓고 보면 그 차이가 확 와닿습니다. 왼쪽은 SQL 문자열을 직접 조립하고 그 결과에서 id를 손으로 꺼내야 하는 번거로운 방식이고, 오른쪽은 그저 객체를 save()에 넘기기만 하면 되는 방식입니다.

❌ Raw SQL (직접 작성)
// 반복적인 코드, SQL 의존적
const result = await dataSource.query(
  `INSERT INTO categories (name) VALUES ($1)
   RETURNING id`,
  [category.name]
);
const id = result[0].id;
✅ TypeORM (객체 중심)
// 간결하고 객체 지향적
const saved = await this.categoryRepository
  .save(category);
const id = saved.id;

핵심 개념 4가지

TypeORM을 이루는 큰 기둥은 네 가지입니다. 이름이 낯설어도 괜찮아요. 아래 비유로 각자의 역할을 먼저 그림으로 잡아 두면, 이어지는 코드들이 훨씬 편하게 읽힙니다.

비유 — 붕어빵 틀, 창고 관리인, 그리고 창고 열쇠 Entity는 붕어빵을 찍어내는 틀(설계도)입니다. "사용자 한 명은 이름·이메일·나이를 가진다"처럼 데이터의 모양을 미리 정해 두죠. Repository는 그렇게 찍어낸 붕어빵들을 보관한 창고를 지키는 관리인이에요. 우리가 직접 창고(DB)에 들어가는 게 아니라, 관리인에게 "이런 붕어빵 찾아줘", "이거 새로 넣어줘"라고 부탁하면 관리인이 대신 처리합니다. DataSource는 그 창고로 들어가는 열쇠이자 정문이고요. 이 셋의 관계만 잡아 두면 나머지는 세부 사용법일 뿐입니다.
🗂️
Entity
DB 테이블과 매핑되는 TypeScript 클래스. @Entity() 데코레이터로 선언.
🔌
Repository
Entity에 대한 CRUD 작업을 담당. Repository<T> 타입으로 주입.
💾
DataSource
DB 연결 설정의 중심. 트랜잭션·마이그레이션 실행의 진입점.
⚡
주의: save() 필수
엔티티를 변경해도 save()를 호출해야 DB에 반영됩니다. 변경 사항이 자동으로 저장되지 않습니다.

TypeORM vs 다른 ORM

ORM은 TypeORM 하나만 있는 게 아닙니다. Node.js 진영에는 여러 선택지가 있는데, 그중 NestJS와 가장 궁합이 좋고 공식적으로 지원되는 것이 TypeORM입니다. 참고삼아 대표적인 세 가지를 비교해 두었으니, 지금은 "아, TypeORM 말고도 이런 것들이 있구나" 정도만 알고 넘어가면 충분합니다.

의존성 설정

이제 통역사(TypeORM)를 우리 프로젝트에 실제로 데려오는 단계입니다. 크게 두 가지를 합니다. 먼저 필요한 패키지를 설치하고, 그다음 "우리 데이터베이스는 여기 있고, 접속 정보는 이거야"라고 연결 설정을 알려주는 것이죠. 순서대로 따라가 봅시다.

bash
npm install @nestjs/typeorm typeorm pg
# pg = PostgreSQL 드라이버 (MySQL이면 mysql2)

app.module.ts

설치가 끝났으면, 앱이 시작될 때 TypeOrmModule.forRoot(...)로 DB 연결 정보를 한 번 등록해 둡니다. host·port·username·password 같은 값은 마치 전화를 걸기 위한 상대방 번호와 비밀번호와 같아요. 이 정보만 정확히 적어 두면, 이후 앱 어디에서든 DB에 연결된 상태로 일할 수 있습니다. 실제 값을 코드에 직접 쓰지 않고 process.env(환경 변수)에서 꺼내 오는 점도 눈여겨보세요 — 비밀번호를 소스코드에 박아 두지 않기 위한 습관입니다.

typescript
import { TypeOrmModule } from '@nestjs/typeorm';

@Module({
  imports: [
    TypeOrmModule.forRoot({
      type: 'postgres',
      host: process.env.DB_HOST,
      port: Number(process.env.DB_PORT) || 5432,
      username: process.env.DB_USERNAME,
      password: process.env.DB_PASSWORD,
      database: process.env.DB_NAME,
      entities: [__dirname + '/**/*.entity{.ts,.js}'],
      synchronize: true,  // 개발 환경에서만 사용 (프로덕션은 false)
    }),
  ],
})
export class AppModule {}

설정값 중에 synchronize: true 하나는 특히 주의해서 이해해야 합니다. 이건 "Entity 클래스를 고치면 DB 테이블 구조도 자동으로 똑같이 맞춰줘"라는 아주 편리한 옵션입니다. 개발 초기에는 테이블을 손수 만들 필요가 없어 편하지만, 바로 그 자동성이 운영 환경에서는 위험합니다.

비유 — 방을 멋대로 정리하는 청소 로봇 synchronize: true는 내 설계도(Entity)에 맞춰 방(DB 테이블)을 자동으로 재배치해 주는 청소 로봇과 같습니다. 방이 텅 빈 개발 초기에는 알아서 척척 정리해 주니 편하죠. 하지만 이미 소중한 짐(실제 사용자 데이터)이 가득한 운영 서버에서 이 로봇을 돌리면, 설계도가 조금 바뀌었다는 이유로 멀쩡한 데이터를 지워 버릴 수도 있습니다. 그래서 운영 환경에서는 로봇을 꺼두고(false), 사람이 직접 검토하는 마이그레이션 방식으로 바꿔야 합니다.
synchronize: true는 Entity 변경 시 DB 스키마를 자동으로 업데이트합니다. 프로덕션에서는 반드시 false로 설정하고 마이그레이션을 사용하세요.
🗂️

Entity 정의

앞에서 Entity를 "붕어빵 틀"에 비유했었죠. 이제 그 틀을 실제로 어떻게 그리는지 볼 차례입니다. Entity 클래스 하나가 곧 DB 테이블 하나에 대응하고, 클래스 안의 각 속성(property)이 테이블의 컬럼(column) 하나하나가 됩니다. 클래스 위와 속성 위에 붙는 @Entity(), @Column() 같은 데코레이터가 "이건 테이블이야", "이건 컬럼이야"라고 TypeORM에게 알려주는 표식 역할을 합니다.

비유 — 빈칸이 그려진 서류 양식 Entity 클래스는 관공서의 서류 양식과 같습니다. 양식에는 "이름 칸", "이메일 칸", "나이 칸"이 미리 그려져 있죠. @Column()은 바로 그 빈칸을 하나 그리는 행위이고, @Column({ length: 50 })처럼 옵션을 주는 건 "이 칸은 50자까지만"이라는 기입 규칙을 정해 두는 것입니다. 이렇게 양식을 한 번 잘 만들어 두면, 실제 데이터(김철수, 이영희 …)는 이 양식의 빈칸을 채운 낱장의 서류들이 되는 셈입니다.
typescript
// user.entity.ts
import {
  Entity,
  PrimaryGeneratedColumn,
  Column,
  CreateDateColumn,
  UpdateDateColumn,
} from 'typeorm';

@Entity('users')
export class User {
  @PrimaryGeneratedColumn()
  id: number;

  @Column({ length: 50 })
  name: string;

  @Column({ unique: true })
  email: string;

  @Column()
  age: number;

  @CreateDateColumn({ name: 'created_at' })
  createdAt: Date;

  @UpdateDateColumn({ name: 'updated_at' })
  updatedAt: Date;
}

자주 쓰는 컬럼 데코레이터

위 코드에서 @PrimaryGeneratedColumn()은 자동으로 1, 2, 3… 늘어나는 기본 키(PK)를 만들고, @Column({ unique: true })는 이메일이 겹치지 않도록 막습니다. @CreateDateColumn()과 @UpdateDateColumn()은 우리가 신경 쓰지 않아도 만든 시각과 수정한 시각을 알아서 기록해 주는 편리한 컬럼이고요. 자주 쓰는 데코레이터를 아래 표에 모아 두었으니, 필요할 때마다 사전처럼 찾아 쓰면 됩니다.

데코레이터설명
@PrimaryGeneratedColumn()AUTO_INCREMENT PK
@PrimaryGeneratedColumn('uuid')UUID PK
@Column()일반 컬럼
@Column({ nullable: true })NULL 허용
@Column({ unique: true })UNIQUE 제약
@Column({ default: 0 })기본값 설정
@CreateDateColumn()INSERT 시 자동 설정
@UpdateDateColumn()UPDATE 시 자동 갱신
@VersionColumn()낙관적 락 버전 관리 (Part 5)

AUTO_INCREMENT vs UUID — 어떤 PK를 써야 할까?

모든 데이터에는 그것을 콕 집어 가리킬 고유한 번호(기본 키, PK)가 필요합니다. 그런데 이 번호를 매기는 방식이 크게 두 가지예요. 하나는 1, 2, 3처럼 순서대로 번호를 붙이는 AUTO_INCREMENT이고, 다른 하나는 550e8400-e29b-...처럼 겹칠 일 없는 무작위 문자열을 쓰는 UUID입니다. 즉 두 방식은 PK를 어떤 값으로, 누가 만드느냐가 다릅니다.

비유 — 식당 대기표 vs 콘서트 예매번호 AUTO_INCREMENT는 식당 앞에서 뽑는 대기표와 같습니다. 1번, 2번, 3번… 순서대로 나오니 깔끔하지만, 누군가 /users/1000이라는 번호를 보면 "아, 이 서비스 가입자가 최소 1000명이구나"라고 규모를 짐작할 수 있죠. 반면 UUID는 무작위로 발급되는 긴 예매번호와 같아서, 번호만 봐서는 몇 번째 손님인지 전혀 알 수 없습니다. 대신 길고 복잡해서 서로 비교할 때 살짝 더 느립니다. 그래서 "빠르고 단순하지만 예측 가능한" 대기표와 "느리지만 안전하고 겹치지 않는" 예매번호 중, 상황에 맞게 고르는 것입니다.
@PrimaryGeneratedColumn() — AUTO_INCREMENT
@Entity()
export class User {
  @PrimaryGeneratedColumn()
  id: number;  // 1, 2, 3, ...

  @Column()
  name: string;
}

내부 JOIN 성능은 AUTO_INCREMENT로, 외부 노출 URL은 UUID로 분리하면 두 장점을 모두 얻을 수 있습니다. 
@Entity()
export class User {
  @PrimaryGeneratedColumn()
  id: number;          // 내부 JOIN용 — 빠른 int 비교

  @Column({ unique: true, default: () => 'gen_random_uuid()' })
  publicId: string;    // 외부 노출용 — URL에 사용 (/users/550e8400-...)
}

Setter 대신 메서드 사용

Entity를 만들다 보면, 어떤 값을 바꾸기 위해 setTitle() 같은 단순한 setter를 습관적으로 만들게 됩니다. 값을 그냥 넣기만 하는 setter는 편해 보이지만, 사실은 아무런 검사 없이 아무 값이나 집어넣을 수 있는 통로가 됩니다. 빈 제목, null, 100자가 넘는 제목… 이런 잘못된 값이 스르륵 들어와도 아무도 막지 못하죠. 그 결과 데이터 무결성이 조금씩 무너집니다. 그래서 값을 바꿀 때는 그냥 setter가 아니라, 규칙을 품은 의미 있는 메서드를 쓰는 편이 좋습니다.

비유 — 은행 잔고를 직접 고칠 수는 없다 여러분의 은행 계좌 잔고가 balance = 5000000처럼 아무나 직접 숫자를 덮어쓸 수 있게 열려 있다면 어떨까요? 생각만 해도 아찔합니다. 그래서 은행은 잔고를 직접 만지게 두지 않고, 오직 입금(deposit)·출금(withdraw)이라는 정해진 절차로만 바꾸게 합니다. 출금할 때는 "잔고가 충분한가?"를 반드시 확인하죠. Entity의 updateTitle() 같은 메서드가 바로 이 입출금 창구입니다. 값을 바꾸기 전에 규칙(빈 값 아님, 길이 제한)을 먼저 검사하기 때문에, 잘못된 데이터가 애초에 들어올 수 없습니다.

아래 두 코드를 비교해 봅시다. 왼쪽은 아무 값이나 통과시키는 열린 setter, 오른쪽은 규칙을 먼저 확인한 뒤에야 값을 바꾸는 메서드입니다.

❌ 나쁜 예 — public setter
@Entity()
export class Post {
  @Column()
  title: string;

  // 어디서든 마음대로 변경 가능
  setTitle(title: string) {
    this.title = title; // 빈 문자열? null?
  }
}

// 호출부
post.setTitle('');    // 빈 제목?
post.setTitle(null);  // null?
✅ 좋은 예 — 의미 있는 메서드
@Entity()
export class Post {
  @Column({ nullable: false })
  title: string;

  // 비즈니스 로직이 명확
  updateTitle(newTitle: string): void {
    if (!newTitle?.trim()) {
      throw new BadRequestException(
        '제목은 필수입니다.'
      );
    }
    if (newTitle.length > 100) {
      throw new BadRequestException(
        '제목은 100자를 초과할 수 없습니다.'
      );
    }
    this.title = newTitle;
  }
}
장점: 유효성 검증이 Entity 안에 모임 → 어디서 호출해도 일관된 규칙이 적용됩니다. Controller/Service에서 중복 검증이 필요 없어집니다.

Repository - 기본 사용법

이제 마지막 조각입니다. Entity로 데이터의 모양을 정했으니, 실제로 그 데이터를 저장하고 꺼내 오는 일을 할 차례입니다. 그 일을 담당하는 것이 바로 Repository예요. 우리는 DB에 직접 손을 대지 않고, 언제나 Repository에게 "찾아줘(find)", "저장해줘(save)", "지워줘(delete)"라고 부탁만 합니다.

비유 — 도서관 사서 도서관에서 책을 찾을 때, 우리가 직접 서고에 들어가 수십만 권을 뒤지지는 않죠. 대신 사서에게 "이런 책 있어요?"라고 물으면 사서가 알아서 찾아다 줍니다. Repository가 바로 이 사서입니다. 방대한 서고(데이터베이스)의 구조를 우리가 몰라도, 사서에게 부탁하기만 하면 책(데이터)을 찾고, 새로 등록하고, 폐기하는 일을 대신 처리해 줍니다. 우리는 사서와 대화하는 법(find, save, delete …)만 익히면 됩니다.

그런데 이 사서를 쓰려면 두 단계의 준비가 필요합니다. 먼저 "이 모듈에서는 User라는 책을 다룰 거야"라고 등록하고, 그다음 서비스 안으로 사서를 배정(주입)받는 것이죠.

모듈에 등록

typescript
// users.module.ts
@Module({
  imports: [TypeOrmModule.forFeature([User])],
  providers: [UsersService],
  controllers: [UsersController],
})
export class UsersModule {}

Repository 주입

TypeOrmModule.forFeature([User])로 등록을 마쳤다면, 이제 서비스에서 @InjectRepository(User)를 통해 사서를 배정받습니다. 이렇게 생성자에서 주입받은 userRepository가 앞으로 우리가 대화할 User 전담 사서입니다. NestJS가 알아서 이 사서를 만들어 넣어 주기 때문에, 우리는 받아서 쓰기만 하면 됩니다.

typescript
@Injectable()
export class UsersService {
  constructor(
    @InjectRepository(User)
    private readonly userRepository: Repository<User>,
  ) {}
}
