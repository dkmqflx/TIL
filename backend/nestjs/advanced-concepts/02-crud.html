find - 데이터 조회 GET

애플리케이션 화면의 대부분은 사실 "이미 저장된 데이터를 꺼내 보여주는 일"입니다. 목록 페이지, 상세 페이지, 검색 결과까지 — 전부 DB에서 조건에 맞는 행을 골라 오는 조회(find)에서 시작합니다. Part 1에서 만든 Repository에는 이 조회를 위한 메서드가 이미 준비되어 있어서, SQL을 손으로 쓰지 않고도 원하는 데이터를 가져올 수 있습니다.

비유 — 도서관 사서에게 부탁하기 Repository는 서가를 대신 뒤져 주는 도서관 사서라고 생각하면 편합니다. "20세 이상 회원을 전부 데려와 주세요"처럼 조건을 말하면, 사서가 알아서 서가(테이블)를 훑어 해당하는 책들을 가져다줍니다. 여러 권을 다 가져오는 find()와 딱 한 권만 집어 오는 findOne()의 차이는, 사서에게 "해당하는 책 전부"를 부탁하느냐 "그중 한 권만"을 부탁하느냐의 차이일 뿐입니다.

전체 조회

가장 기본은 조건 없이 테이블의 모든 행을 가져오는 것입니다. find()를 인자 없이 부르면 SELECT * FROM users와 똑같은 결과를 엔티티 객체 배열로 돌려받습니다.

typescript
// SELECT * FROM users
const users = await this.userRepository.find();

조건 조회

모든 행이 아니라 특정 조건에 맞는 데이터만 필요할 때는 where 옵션을 넘깁니다. 딱 하나만 필요하면 findOne(), 조건에 맞는 여러 건이 필요하면 find()에 where를 붙이면 됩니다. 아래 MoreThanOrEqual(30)처럼 단순 일치뿐 아니라 "30 이상" 같은 범위 조건도 표현할 수 있습니다.

typescript
// SELECT * FROM users WHERE id = 1 LIMIT 1
const user = await this.userRepository.findOne({ where: { id: 1 } });

// SELECT * FROM users WHERE age >= 30
const users = await this.userRepository.find({
  where: { age: MoreThanOrEqual(30) },
});
프론트 관점에서: GET /users/1 요청이 내부적으로 findOne({ where: { id: 1 } })처럼 동작합니다.

TypeORM 비교 연산자

SQL의 WHERE 절에서 쓰던 <, LIKE, IN, IS NULL 같은 조건들은 TypeORM에서 각각 LessThan, Like, In, IsNull 같은 함수로 바뀝니다. 즉 문자열로 SQL을 조합하는 대신, 이 함수들을 where 값 자리에 넣어 조건을 표현하는 것이죠. 오른쪽 주석에 각 함수가 어떤 SQL로 번역되는지 적어 두었으니 나란히 비교해 보세요.

typescript
import { Equal, Not, LessThan, MoreThanOrEqual, Like, In, IsNull } from 'typeorm';

find({ where: { age: LessThan(20) } })           // WHERE age < 20
find({ where: { name: Like('김%') } })            // WHERE name LIKE '김%'
find({ where: { id: In([1, 2, 3]) } })           // WHERE id IN (1, 2, 3)
find({ where: { email: IsNull() } })             // WHERE email IS NULL
find({ where: { email: Not(IsNull()) } })        // WHERE email IS NOT NULL

정렬 / 특정 컬럼 선택

조회한 데이터의 순서를 정하고 싶으면 order를, 필요한 컬럼만 골라 가져오고 싶으면 select를 씁니다. 예를 들어 비밀번호 같은 민감한 컬럼을 응답에서 빼거나, 목록 화면에 필요한 몇 개 컬럼만 가져와 쿼리를 가볍게 만들 때 유용합니다. where·order·select는 아래처럼 한 객체 안에서 자유롭게 조합할 수 있습니다.

typescript
// ORDER BY age DESC
find({ order: { age: 'DESC' } })

// SELECT name, email FROM users
find({ select: { name: true, email: true } })

// ORDER BY + WHERE 조합
find({
  where: { age: MoreThanOrEqual(20) },
  order: { createdAt: 'DESC' },
  select: { id: true, name: true, email: true },
})
➕

save - 데이터 삽입 POST

이번엔 반대로 새 데이터를 DB에 새로 집어넣는 작업입니다. 회원가입, 글쓰기, 주문 생성 — 사용자가 무언가를 "만드는" 모든 순간이 여기에 해당합니다. TypeORM에서는 이 과정을 create()와 save() 두 단계로 나눠서 다루는데, 처음 보면 "왜 굳이 두 번 부르지?" 싶을 수 있습니다. 그 이유를 비유로 먼저 잡고 가겠습니다.

비유 — 택배 상자 포장(create)과 발송(save) create()는 보낼 물건을 상자에 담아 포장까지 끝낸 상태입니다. 아직 우체국에 넘기지 않았으니 책상 위에 있을 뿐, 언제든 내용물을 바꿀 수 있죠(메모리에만 있는 엔티티 객체). 반면 save()는 그 상자를 실제로 발송하는 행동입니다. 이 순간에야 DB에 INSERT가 일어나고, 발송 후 받은 운송장 번호처럼 자동으로 생성된 PK(id)가 객체에 채워집니다.

단건 삽입

아래 코드에서 create()는 아직 DB를 건드리지 않고 메모리에 User 인스턴스만 만듭니다. 그 인스턴스를 save()에 넘겨야 비로소 INSERT 쿼리가 실행되고, 반환된 saved 객체에는 DB가 매겨 준 id가 들어 있습니다.

typescript
// INSERT INTO users (name, email, age) VALUES ('홍길동', 'hong@example.com', 27)
const user = this.userRepository.create({
  name: '홍길동',
  email: 'hong@example.com',
  age: 27,
});

const saved = await this.userRepository.save(user);
console.log(saved.id); // 자동 생성된 PK
create()는 Entity 인스턴스를 생성(메모리)하고, save()가 실제 DB에 저장합니다. Spring JDBC의 KeyHolder와 달리 saved.id로 바로 접근 가능합니다.

DTO와 함께 사용 (실무 패턴)

실무에서는 클라이언트가 보낸 요청 본문을 그대로 저장하지 않고, DTO(Data Transfer Object)라는 "입력 전용 형태"로 한 번 받아서 넘깁니다. create(dto)에 DTO를 그대로 넘기면 TypeORM이 알아서 엔티티로 변환해 주기 때문에, 필드를 하나하나 옮겨 담을 필요가 없습니다. 아래처럼 create() → save()를 이어 쓰는 것이 가장 흔한 삽입 패턴입니다.

typescript
// create-user.dto.ts
export class CreateUserDto {
  name: string;
  email: string;
  age: number;
}

// service
async create(dto: CreateUserDto): Promise<User> {
  const user = this.userRepository.create(dto);
  return this.userRepository.save(user);
}
✏️

update / save - 데이터 수정 PATCH

이미 저장된 데이터의 일부를 바꾸는 작업입니다. 프로필 수정, 주문 상태 변경처럼 아주 흔한 일이죠. TypeORM에서 수정하는 길은 크게 두 갈래입니다. 하나는 조회를 건너뛰고 곧바로 UPDATE를 날리는 update(), 다른 하나는 먼저 데이터를 꺼내 손질한 뒤 다시 저장하는 findOne() + save()입니다. 둘 다 결과적으로 데이터를 바꾸지만, 그 과정과 얻는 것이 다릅니다.

비유 — 수정테이프 vs 서류를 꺼내 와서 고치기 update()는 서류함을 열지 않고 바깥에서 손을 넣어 한 줄만 수정테이프로 고치는 것과 같습니다. 빠르지만, 그 서류가 실제로 있었는지·원래 뭐라 적혀 있었는지는 보지 못합니다. 반면 findOne() + save()는 서류를 통째로 책상에 꺼내 와서 내용을 눈으로 확인하고, 필요한 부분을 고친 뒤 다시 제자리에 넣는 방식입니다. 손이 한 번 더 가지만, 서류가 없으면 바로 알아채고 수정 전후를 자유롭게 다룰 수 있습니다.
방법 1: update() — 부분 수정
엔티티를 조회하지 않고 바로 수정. 빠르지만 affected 확인 필요.
방법 2: save() — 전체 수정
findOne() 후 수정. 존재 여부를 자동 확인할 수 있음.

방법 1: update()

가장 빠른 길입니다. 아래 코드는 조회 없이 곧장 UPDATE ... WHERE id = 1을 실행합니다. 다만 대상 행이 실제로 있었는지는 쿼리 결과의 affected(영향받은 행 수)로만 알 수 있어서, 존재하지 않는 id를 수정하려 하면 조용히 아무 일도 일어나지 않습니다. 그래서 affected === 0일 때 직접 예외를 던져 "수정할 게 없었다"는 사실을 알려 주는 코드가 필요합니다.

typescript
// UPDATE users SET email = 'new@example.com' WHERE id = 1
const result = await this.userRepository.update(1, { email: 'new@example.com' });

if (result.affected === 0) {
  throw new NotFoundException('수정할 데이터가 없습니다.');
}

방법 2: save() (findOne 후 수정)

이쪽은 먼저 findOne()으로 엔티티를 꺼내 옵니다. 이때 대상이 없으면 곧바로 예외를 던질 수 있어 존재 확인이 자연스럽고, 꺼내 온 객체의 값을 코드에서 자유롭게 바꾼 뒤 save()로 저장합니다. 객체를 손에 쥐고 있으니 "이 사용자가 수정 권한이 있는가" 같은 비즈니스 로직을 중간에 끼워 넣기도 쉽습니다.

typescript
const user = await this.userRepository.findOne({ where: { id: 1 } });
if (!user) throw new NotFoundException('사용자를 찾을 수 없습니다.');

user.name = '김철수';
user.email = 'kim@example.com';
user.age = 29;

await this.userRepository.save(user);

두 방법을 나란히 두고 보면 트레이드오프가 분명해집니다. update()는 쿼리 한 번으로 끝나 빠른 대신 엔티티 객체가 없어 훅이나 검증을 걸기 어렵고, save()는 조회가 한 번 더 들지만 그만큼 객체를 온전히 다룰 수 있습니다. 아래 표는 이 차이를 한눈에 정리한 것입니다.

update()save() — findOne 후
DB 쿼리 수1번 (UPDATE만)2번 (SELECT → UPDATE)
존재 여부 확인result.affected로 간접 확인findOne()에서 직접 확인
라이프사이클 훅❌ @BeforeUpdate 등 발동 안 됨✅ 발동됨
비즈니스 로직 적용어려움 (엔티티 객체 없음)용이 (객체를 직접 다룰 수 있음)
적합한 상황단순 필드 패치, 관리자 일괄 수정서비스 계층의 일반적인 수정 로직
실무에선 어떻게 고를까
상황을 떠올려 보면 선택은 의외로 단순합니다. 관리자 페이지에서 "이 사용자들 상태를 한꺼번에 비활성으로" 같은 단순 필드 변경이고 중간에 검증이나 훅이 필요 없다면, 굳이 조회할 이유가 없으니 update(id, { field }) 한 방이 깔끔합니다. 반대로 "수정하기 전에 이 값이 정말 바뀌어도 되는지 확인해야 한다"거나 "수정된 결과를 그대로 응답으로 돌려줘야 한다"면, 객체를 손에 쥐어야 하니 findOne()으로 꺼내 온 뒤 save()하는 편이 자연스럽습니다.
그래서 실제 서비스 계층 코드의 대부분은 save() 방식으로 기웁니다. findOne()에서 "없으면 404" 예외 처리와 존재 확인을 한 번에 끝낼 수 있어, 읽는 사람 입장에서 흐름이 훨씬 분명하기 때문입니다.
🗑️

delete / remove - 데이터 삭제 DELETE

이제 데이터를 지우는 작업입니다. 수정과 마찬가지로 TypeORM에는 삭제 방법이 두 가지 있고, 가장 큰 갈림길은 "지우기 전에 DB에서 먼저 조회하느냐"입니다. delete()는 조회 없이 조건만으로 바로 지우고, remove()는 엔티티를 꺼내 온 뒤 그 객체를 넘겨서 지웁니다.

비유 — 주소만 보고 폐기 vs 물건을 꺼내 확인하고 폐기 delete(1)은 창고 관리인에게 "1번 칸 물건 버려 주세요"라고 위치만 말하는 것과 같습니다. 관리인은 그 칸을 열어 보지도 않고 바로 비웁니다 — 빠르지만, 원래 뭐가 있었는지·정말 있긴 했는지는 알 수 없죠. remove()는 물건을 직접 꺼내 손에 든 다음 버리는 방식입니다. 버리기 전에 "이거 정말 버려도 되나", "버린 기록을 남기자" 같은 확인을 할 수 있는 대신, 꺼내 오는 수고(조회 쿼리)가 한 번 더 듭니다.
delete()remove()
DB 조회 필요 여부❌ 없음 (빠름)✅ 먼저 findOne() 필요
존재 여부 확인result.affected로 확인findOne()에서 직접 확인
cascade 이벤트 발동❌ 발동 안 됨✅ @BeforeRemove 등 발동
언제 사용단순 삭제 (ID로 바로 삭제)삭제 전 엔티티 검증·가공이 필요할 때

방법 1: delete() — ID(조건)로 바로 삭제

DB에서 먼저 조회하지 않고 조건만으로 DELETE를 실행합니다. DB 요청이 1번이라 빠릅니다.

typescript
// DB 요청: 1번
// DELETE FROM users WHERE id = 1
const result = await this.userRepository.delete(1);
// ※ id 대신 조건 객체도 가능: delete({ email: 'test@test.com' })

// affected: 실제로 삭제된 행 수
// 삭제할 데이터가 애초에 없었다면 affected === 0
if (result.affected === 0) {
  throw new NotFoundException('삭제할 데이터가 없습니다.');
}

// delete()는 삭제된 엔티티 객체를 반환하지 않음
// → 삭제 후 해당 데이터가 필요하면 remove()를 써야 함

방법 2: remove() — 엔티티 객체를 받아 삭제

먼저 엔티티를 조회한 뒤, 그 객체를 넘겨서 삭제합니다. DB 요청이 2번(조회 + 삭제)입니다.

typescript
// DB 요청: 2번 (SELECT → DELETE)

// 1) 먼저 조회 — 없으면 여기서 예외를 던짐
const user = await this.userRepository.findOne({ where: { id: 1 } });
if (!user) throw new NotFoundException();

// 2) 조회한 엔티티 객체를 넘겨서 삭제
// DELETE FROM users WHERE id = 1
await this.userRepository.remove(user);

// remove()의 장점: 삭제 전 user 객체를 코드에서 활용 가능
// 예) 삭제 전에 user.name을 로그로 남기거나, 응답으로 반환하거나
실무에선 어떻게 고를까
판단 기준은 수정 때와 똑같습니다. "이 ID 그냥 지워" 이상도 이하도 아니라면 조회는 낭비이니 delete(id)가 빠르고 간결합니다. 하지만 삭제 직전에 "이 사람이 지울 권한이 있나"를 확인하거나, 지운 내용을 로그로 남기거나, 삭제된 데이터를 응답으로 돌려줘야 한다면 — 객체가 손에 있어야 하니 findOne()으로 꺼내 온 뒤 remove()를 씁니다.
조건 없이 delete({})를 호출하면 테이블 전체가 삭제됩니다. WHERE 조건을 반드시 확인하세요.

softDelete — 실무에서 가장 많이 쓰는 삭제 패턴 DELETE

여기까지의 delete()·remove()는 데이터를 DB에서 정말로 지워 버립니다. 그런데 실무에서는 "지웠지만 실제로는 남겨 두고 싶은" 경우가 훨씬 많습니다. 탈퇴한 회원, 취소된 주문, 삭제한 게시글 — 화면에서는 사라져야 하지만, 나중에 복구하거나 "누가 언제 지웠는지" 따져야 할 수 있기 때문이죠. 그래서 실제로 지우는 대신 "삭제된 시각"만 기록해 두고 조회할 때 자동으로 걸러내는 Soft Delete 패턴을 씁니다.

비유 — 휴지통(softDelete) vs 영구 삭제(delete/remove) delete()·remove()는 파일을 고른 뒤 Shift+Delete로 완전히 없애는 것과 같습니다. 디스크에서 사라졌으니 되돌릴 수 없죠. 반면 softDelete()는 파일을 휴지통에 넣는 것입니다. 탐색기(일반 조회)에는 더 이상 보이지 않지만 파일 자체는 디스크에 그대로 있어서, 마음이 바뀌면 복원(restore())으로 되살릴 수 있고 "언제 버렸는지"도 남습니다. 핵심 데이터일수록 곧바로 없애기보다 일단 휴지통에 넣어 두는 편이 안전합니다.

1단계 — 엔티티에 @DeleteDateColumn 추가

@DeleteDateColumn을 선언하면 TypeORM이 softDelete() 호출 시 자동으로 해당 컬럼에 시각을 기록하고, 이후 find() 쿼리에서 자동으로 제외합니다.

typescript
@Entity()
export class User {
  @PrimaryGeneratedColumn()
  id: number;

  @Column()
  name: string;

  @CreateDateColumn({ name: 'created_at' })
  createdAt: Date;

  // 이 컬럼 하나로 Soft Delete 활성화
  @DeleteDateColumn({ name: 'deleted_at', nullable: true })
  deletedAt: Date | null;  // 삭제 전: null / 삭제 후: 삭제된 시각
}

2단계 — softDelete / restore 사용

컬럼 하나만 준비되면 나머지는 TypeORM이 알아서 처리합니다. softDelete()를 부르면 실제 DELETE가 아니라 deleted_at에 현재 시각을 적는 UPDATE가 나가고, restore()는 그 값을 다시 null로 되돌려 복구합니다. 그리고 평범한 find()는 자동으로 deleted_at IS NULL 조건을 붙여 삭제된 행을 걸러 주며, 삭제된 것까지 보고 싶을 때만 withDeleted: true를 넘기면 됩니다.

typescript
// ── 삭제 (deleted_at에 현재 시각 기록, 행은 남아 있음) ──
// UPDATE users SET deleted_at = NOW() WHERE id = 1
await this.userRepository.softDelete(1);

// ── 복구 (deleted_at을 다시 null로) ──
// UPDATE users SET deleted_at = NULL WHERE id = 1
await this.userRepository.restore(1);

// ── 일반 조회 — 소프트 삭제된 행은 자동으로 제외됨 ──
// SELECT * FROM users WHERE deleted_at IS NULL
const users = await this.userRepository.find();

// ── 소프트 삭제된 항목까지 포함해서 조회 ──
const allUsers = await this.userRepository.find({ withDeleted: true });

실무에서의 전체 흐름 예시

실제 서비스에서는 앞서 배운 "존재 확인 → 처리" 흐름과 Soft Delete를 합쳐 씁니다. 아래 remove() 메서드는 먼저 findOne()으로 대상을 확인해 없으면 404를 던지고, 있으면 softDelete()로 deleted_at만 기록합니다. 복구용 restore()는 affected로 실제로 되살릴 행이 있었는지 확인합니다.

typescript
// user.service.ts
async remove(id: number): Promise {
  // 1) 존재 확인 (없으면 404)
  const user = await this.userRepository.findOne({ where: { id } });
  if (!user) throw new NotFoundException('사용자를 찾을 수 없습니다.');

  // 2) Soft Delete — DB에서 지우지 않고 deleted_at만 기록
  await this.userRepository.softDelete(id);
}

async restore(id: number): Promise {
  const result = await this.userRepository.restore(id);
  if (result.affected === 0) {
    throw new NotFoundException('복구할 데이터가 없습니다.');
  }
}
update / delete / remove / softDelete — 실무 의사결정 이야기

막상 코드를 짤 때는 이렇게 자문하면 길이 보입니다. "지우는 게 아니라 고치는 것"이면 수정 쪽이고, 값만 빠르게 바꾸면 되면 update(), 객체를 확인·가공해야 하면 findOne() + save()입니다(대부분 이쪽). "정말 지우는 것"이라면 이 데이터가 사라져도 되는 하찮은 것인지부터 봅니다. 임시·캐시·로그처럼 없어져도 그만이면 물리 삭제(delete(), 삭제 전 객체가 필요하면 remove())로 깔끔히 비우고, 회원·주문·게시글처럼 복구나 이력이 걸린 핵심 데이터라면 주저 없이 softDelete()로 휴지통에 넣습니다. 실무에서 "삭제"라고 하면 사실상 이 softDelete()가 기본값에 가깝습니다.
