연관관계가 필요한 이유

지금까지는 users 한 테이블만 다뤘습니다. 실제 서비스는 여러 테이블이 서로 연결됩니다 (게시글 → 카테고리, 주문 → 회원). TypeORM은 이 관계를 객체 그래프로 표현해, FK를 직접 조회·연결하는 수고를 없애줍니다.

❌ Raw 쿼리 방식
// Post 조회 후 Category 따로 조회
async findPost(id: number) {
  const post = await dataSource.query(
    'SELECT * FROM posts WHERE id = $1', [id]
  );
  // Category를 따로 조회해서 수동으로 연결
  const category = await dataSource.query(
    'SELECT * FROM categories WHERE id = $1',
    [post[0].category_id]
  );
  post[0].category = category[0];
  return post[0];
}
✅ TypeORM 연관관계
// 객체 그래프 탐색으로 바로 접근
async findPost(id: number) {
  const post = await this.postRepository
    .findOne({
      where: { id },
      relations: { category: true },
    });

  // 바로 접근 가능
  const categoryName = post.category.name;
  return post;
}

@ManyToOne — 가장 많이 쓰는 연관관계

① "N:1 관계"가 뭔가요?

쉽게 말하면 "여러 개(N)가 하나(1)를 가리키는 관계"입니다.

예시로 이해하기
유튜브 영상(N) → 채널(1)
댓글(N) → 게시글(1)
게시글(N) → 카테고리(1)

공통점: "여러 개"쪽이 "하나"의 ID를 가짐
DB 테이블로 보면
posts 테이블이 category_id라는 컬럼을 가집니다.
categories 테이블에는 아무 변화 없음.

즉, "여러 개(N)"쪽 테이블에 FK 컬럼이 생깁니다.
posts 테이블 (category_id = FK 컬럼)
idtitlecategory_id
1NestJS 시작하기1 → "백엔드"
2TypeORM 연관관계1 → "백엔드"
3React 기초2 → "프론트엔드"

② 연관 데이터를 가져오는 3가지 전략

Post를 조회할 때 Category 정보를 언제, 어떻게 가져올지 결정하는 방식이 3가지 있습니다.

전략동작 방식실무 사용 여부
EAGER엔티티에 eager: true 설정 → 항상 자동 JOIN⚠️ 제한적
LAZY처음엔 Post만 가져오고, await post.category 시점에 추가 쿼리 실행❌ 비권장
relations 명시find() 호출마다 필요할 때만 relations: { category: true } 지정✅ 실무 표준

각 전략이 실제로 어떻게 동작하는가

EAGER — 항상 같이 가져옴
// 엔티티 설정
@ManyToOne(() => Category, {
  eager: true,  // ← 항상 자동 JOIN
})
category: Category;

// 조회 — relations 안 써도 category 포함됨
const post = await repo.findOne(
  { where: { id: 1 } }
);
// SQL: SELECT ... JOIN categories
//      category가 필요 없어도 항상 JOIN
⚠️ 필요 없을 때도 매번 JOIN → 불필요한 부하
LAZY — 접근 시점에 추가 쿼리
// 엔티티 설정
@ManyToOne(() => Category)
category: Promise<Category>;
// ← 타입이 Promise여야 함 (특이한 구조)

// 조회
const post = await repo.findOne(
  { where: { id: 1 } }
);
// SQL 1: SELECT * FROM posts WHERE id=1
// (category는 아직 안 가져옴)

// category에 접근하는 순간 추가 쿼리 실행
const cat = await post.category;
// SQL 2: SELECT * FROM categories WHERE id=?
❌ Promise 타입 강제, 실수 시 N+1 문제 디버깅 어려움
relations 명시 — 필요할 때만 (권장)
// 엔티티 설정 — 아무 옵션 없음
@ManyToOne(() => Category)
category: Category;

// category 필요 없을 때
const post = await repo.findOne(
  { where: { id: 1 } }
);
// SQL: SELECT * FROM posts WHERE id=1

// category 필요할 때 → 명시적으로 추가
const post = await repo.findOne({
  where: { id: 1 },
  relations: { category: true },
});
// SQL: SELECT ... JOIN categories
✅ 필요한 것만 가져옴, 코드만 봐도 동작 예측 가능
LAZY를 실무에서 쓰지 않는 이유
TypeORM의 LAZY는 "연관 필드 타입을 Promise<Category>로 바꿔야 한다"는 특이한 제약이 있습니다. 그래서 일반 Category 타입처럼 쓰다가 await를 빠뜨리면 조용히 Promise 객체가 반환되어 버그가 생기고, 어느 시점에 쿼리가 몇 번 나가는지 추적하기도 어렵습니다.

relations 옵션은 코드만 봐도 "이 호출은 JOIN이 발생한다"는 게 바로 보여서 훨씬 안전합니다.

③ 실제 코드 — 실무 권장 패턴

typescriptpost.entity.ts
@Entity('posts')
export class Post {
  @PrimaryGeneratedColumn()
  id: number;

  @Column()
  title: string;

  // @ManyToOne: "Post가 N, Category가 1"
  // () => Category : 연결할 대상 엔티티
  // (category) => category.posts : 반대쪽(Category)에서 이 관계를 뭐라 부르는지
  @ManyToOne(() => Category, (category) => category.posts, {
    nullable: false,  // category 없는 post는 존재 불가 (NOT NULL)
  })
  @JoinColumn({ name: 'category_id' })  // DB 컬럼명을 category_id로 지정
  category: Category;

  @Column({ name: 'category_id' })
  categoryId: number;  // ID만 필요할 때 편하게 꺼내 쓸 수 있음
}

@JoinColumn — FK 컬럼 이름 지정

@JoinColumn은 FK(외래 키) 컬럼이 DB에 어떤 이름으로 생성될지 지정하는 데코레이터입니다. 생략하면 TypeORM이 categoryId(camelCase)로 자동 생성합니다. { name: 'category_id' }를 넘기면 snake_case 컬럼명으로 만들어집니다.

관계@JoinColumn이유
@ManyToOne선택 — 컬럼명 커스텀할 때만FK가 "N"쪽 테이블에 생기는 건 TypeORM이 이미 앎
@OneToOne필수FK가 어느 쪽 테이블에 생길지 직접 지정해야 함
@OneToMany불필요FK는 반대쪽(@ManyToOne)에 생김
위 코드에서 @JoinColumn({ name: 'category_id' })를 쓴 이유는 딱 하나 — 컬럼명을 category_id(snake_case)로 맞추기 위해서입니다. 생략해도 FK는 생기지만 컬럼명이 categoryId(camelCase)가 됩니다.
typescriptpost.service.ts
// category 정보가 필요 없을 때 → 그냥 조회
const post = await this.postRepository.findOne({
  where: { id: 1 },
  // category 정보 없음 → post.category = undefined
});

// category 정보가 필요할 때 → relations 명시
const postWithCategory = await this.postRepository.findOne({
  where: { id: 1 },
  relations: { category: true },  // SELECT ... JOIN categories
  // 이제 post.category.name 접근 가능
});

console.log(postWithCategory.category.name);  // "백엔드"

④ eager 옵션 — 항상 자동으로 같이 가져오기

엔티티에 eager: true를 설정하면 relations를 쓰지 않아도 매번 자동으로 JOIN합니다.

eager: true 설정
// post.entity.ts
@ManyToOne(() => Category, (category) => category.posts, {
  eager: true,  // 항상 category를 같이 가져옴
})
category: Category;
서비스에서 사용
// post.service.ts
// relations 없어도 category가 자동 포함됨
const post = await this.postRepository.findOne({
  where: { id: 1 },
});

// eager: true 덕분에 바로 접근 가능
console.log(post.category.name);  // "백엔드"
방식동작언제 쓰나주의점
eager: true 항상 자동 JOIN 이 관계가 항상 필요한 경우 불필요한 조회도 항상 JOIN → 성능 주의
relations 명시 해당 쿼리에서만 JOIN 필요할 때만 가져오고 싶을 때 가장 일반적인 실무 패턴 ✅
아무것도 없음 category 미포함 ID만 필요한 경우 (categoryId) post.category는 undefined
실무 팁: eager: true는 "이 엔티티를 조회하면 항상 이 관계가 필요하다"는 확신이 있을 때만 씁니다. 대부분의 경우는 relations로 명시하는 게 더 유연합니다.
↙️

@OneToMany — 양방향 관계

Category 입장에서 여러 Post를 가지는 관계. @OneToMany는 반드시 @ManyToOne의 역방향으로만 존재합니다.

typescriptcategory.entity.ts
@Entity('categories')
export class Category {
  @PrimaryGeneratedColumn()
  id: number;

  @Column({ unique: true })
  name: string;

  // mappedBy 역할: Post.category 필드와 연결
  @OneToMany(() => Post, (post) => post.category)
  posts: Post[];   // 조회 시 자동 로딩 안 됨 (relations 명시 필요)
}

// Post.category와 반드시 짝을 맞춤
@Entity('posts')
export class Post {
  @ManyToOne(() => Category, (category) => category.posts)
  @JoinColumn({ name: 'category_id' })
  category: Category;
}

Cascade — 부모에게 한 작업이 자식에게 자동으로 전파

cascade가 없으면 Post와 Comment를 각각 따로 save() 해야 합니다. cascade가 있으면 Post만 save()해도 Comment까지 자동으로 처리됩니다.

❌ cascade 없을 때 — 각각 따로 저장해야 함
// Comment를 먼저 직접 save()
const comment1 = new Comment();
comment1.content = '좋아요!';
await this.commentRepository.save(comment1);  // ← 따로 저장

const comment2 = new Comment();
comment2.content = '유익해요';
await this.commentRepository.save(comment2);  // ← 따로 저장

// 그 다음 Post를 저장
const post = new Post();
post.title = 'NestJS 강의';
post.comments = [comment1, comment2];
await this.postRepository.save(post);

// SQL: INSERT INTO comments ... (2번)
// SQL: INSERT INTO posts ...
✅ cascade: true 있을 때 — Post만 save()하면 Comment도 자동 저장
// 엔티티 설정
@Entity('posts')
export class Post {
  @OneToMany(() => Comment, (comment) => comment.post, {
    cascade: true,  // 저장·삭제 모두 전파
  })
  comments: Comment[];
}

// 서비스 코드 — commentRepository.save() 없이 postRepository.save() 한 번으로 끝
const post = new Post();
post.title = 'NestJS 강의';
post.comments = [
  Object.assign(new Comment(), { content: '좋아요!' }),
  Object.assign(new Comment(), { content: '유익해요' }),
];

await this.postRepository.save(post);  // ← 이것만으로 Comment도 자동 INSERT
// SQL 1: INSERT INTO posts ...
// SQL 2: INSERT INTO comments ...  ← 자동 실행

cascade: ['insert'] — 저장만 전파, 삭제는 각자

생성할 때는 Post 하나로 묶어서 편하게 만들고 싶지만, 삭제할 때는 댓글이 자동으로 지워지는 게 위험해서 따로 관리하고 싶을 때 씁니다.

cascade: ['insert'] 설정
@OneToMany(() => Comment, (comment) => comment.post, {
  cascade: ['insert'],  // 저장만 전파, 삭제는 전파 안 함
})
comments: Comment[];

// ✅ 저장 — Post save() 시 Comment도 자동 INSERT
const post = new Post();
post.comments = [Object.assign(new Comment(), { content: '안녕' })];
await this.postRepository.save(post);  // Comment도 자동 저장됨

// ❌ 삭제 — Post remove()해도 Comment는 자동 삭제 안 됨
// → 먼저 Comment를 직접 삭제해야 Post를 지울 수 있음
await this.commentRepository.delete({ post: { id: 1 } });  // 직접 삭제
await this.postRepository.remove(post);
cascade: ['insert']를 쓰는 실제 이유
게시글 삭제 시 댓글도 자동으로 지워지면 실수로 중요한 데이터를 날릴 수 있습니다. 삭제는 별도 확인 후 직접 처리하고, 생성만 편하게 묶고 싶을 때 cascade: ['insert']를 선택합니다.
옵션저장 전파삭제 전파언제 쓰나
cascade: true✅✅부모와 자식을 항상 함께 관리할 때
cascade: ['insert']✅❌생성은 묶어서 편하게, 삭제는 직접 관리할 때
cascade: ['remove']❌✅생성은 각자, 부모 삭제 시 자식도 지울 때

orphanedRowAction — 배열에서 빠진 자식을 DB에서도 지우기

cascade와 헷갈리기 쉬운 옵션입니다. 핵심 차이는 "부모를 삭제할 때"가 아니라, "자식이 부모 배열에서 빠질 때" 동작한다는 점입니다.

❌ orphanedRowAction 없을 때 — 고아 행 발생
// 댓글이 3개 있는 Post 조회
const post = await this.postRepository.findOne({
  where: { id: 1 },
  relations: { comments: true },
});
// post.comments = [댓글1(id:1), 댓글2(id:2), 댓글3(id:3)]

// 댓글3을 배열에서 제거하고 저장
post.comments = post.comments.filter(c => c.id !== 3);
await this.postRepository.save(post);

// DB 결과: 댓글3이 DB에 그대로 남아있음 → "고아(orphan) 행"
// comments 테이블: id=1, id=2, id=3 모두 존재
✅ orphanedRowAction: 'delete' 있을 때
@Entity('posts')
export class Post {
  @OneToMany(() => Comment, (comment) => comment.post, {
    cascade: true,
    orphanedRowAction: 'delete',  // 배열에서 빠지면 DB에서도 삭제
  })
  comments: Comment[];
}

// 댓글3을 배열에서 제거하고 저장
post.comments = post.comments.filter(c => c.id !== 3);
await this.postRepository.save(post);

// DB 결과: 댓글3이 DB에서도 자동 삭제됨
// comments 테이블: id=1, id=2만 존재
// SQL: DELETE FROM comments WHERE id = 3  ← 자동 실행
cascade vs orphanedRowAction 한 줄 요약
• cascade — 부모를 통째로 삭제할 때 자식도 함께 삭제
• orphanedRowAction: 'delete' — 부모 배열에서 자식을 제거했을 때 DB에서도 삭제

① 좋아요 기능을 DB에 저장하려면?

③ 코드로 보기 — 딱 3개 파일

중간 테이블을 직접 Entity로 만들고, 양쪽에 @ManyToOne을 하나씩 답니다.

typescriptpost-like.entity.ts — 중간 테이블
@Entity('post_likes')
export class PostLike {
  @PrimaryGeneratedColumn()
  id: number;

  // "이 좋아요는 어떤 멤버가 눌렀나?"
  // → member_id 컬럼이 생기고, members 테이블과 연결됨
  @ManyToOne(() => Member, { nullable: false })
  @JoinColumn({ name: 'member_id' })
  member: Member;

  // "이 좋아요는 어떤 게시글에 눌렸나?"
  // → post_id 컬럼이 생기고, posts 테이블과 연결됨
  @ManyToOne(() => Post, { nullable: false })
  @JoinColumn({ name: 'post_id' })
  post: Post;

  // 이 컬럼이 있기 때문에 중간 Entity를 직접 만든 것!
  // TypeORM @ManyToMany 자동 생성 방식으로는 이 컬럼을 추가할 수 없음
  @CreateDateColumn()
  createdAt: Date;
}
typescriptmember.entity.ts — 멤버 쪽
@Entity('members')
export class Member {
  @PrimaryGeneratedColumn()
  id: number;

  @Column()
  name: string;

  // "이 멤버가 누른 좋아요 목록"
  // Member(1) : PostLike(N) — 1:N 관계
  @OneToMany(() => PostLike, (like) => like.member)
  postLikes: PostLike[];
}
typescriptlike.service.ts — 실제 사용
// 좋아요 누르기
async like(memberId: number, postId: number) {
  const like = this.postLikeRepository.create({
    member: { id: memberId },  // member_id = 1
    post:   { id: postId },    // post_id = 10
  });
  await this.postLikeRepository.save(like);
  // INSERT INTO post_likes (member_id, post_id) VALUES (1, 10)
}

// "이 게시글 좋아요 누른 사람 목록" 조회
async whoLiked(postId: number) {
  return this.postLikeRepository.find({
    where: { post: { id: postId } },  // post_id = 10 조건
    relations: { member: true },       // member 정보도 같이
  });
  // → [{ member: { name: '김철수' }, createdAt: ... }, ...]
}

// "이 멤버가 좋아요 누른 게시글 목록" 조회
async whatILiked(memberId: number) {
  return this.postLikeRepository.find({
    where: { member: { id: memberId } },
    relations: { post: true },
  });
}
