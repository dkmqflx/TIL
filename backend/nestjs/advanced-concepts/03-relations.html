연관관계가 필요한 이유

Part 1과 Part 2에서는 줄곧 users 한 테이블만 다뤘습니다. 하지만 현실의 서비스는 그렇게 단순하지 않습니다. 게시글은 어떤 카테고리에 속하고, 주문은 어떤 회원이 넣은 것이며, 댓글은 어떤 게시글에 달립니다. 이렇게 여러 테이블이 서로를 가리키며 얽혀 있는 것이 실제 데이터의 모습입니다. 이번 Part에서는 이 "얽힘"을 TypeORM에서 어떻게 표현하는지를 배웁니다.

비유 — 학생 명부에 학교 정보를 통째로 베껴 적으면? 학생 1,000명의 명부를 만드는데, 학생마다 다니는 학교의 이름·주소·전화번호를 전부 베껴 적었다고 해봅시다. 그런데 학교가 이사를 가면? 1,000명의 기록을 하나하나 고쳐야 합니다. 대신 학생 기록에는 "학교 번호"만 적어두고, 학교 상세 정보는 학교 명단에서 한 번만 관리하면, 학교가 이사해도 한 곳만 고치면 끝입니다. 데이터베이스에서 테이블을 나누고 서로 연결(연관관계)하는 이유가 바로 이것입니다.

이렇게 정보를 나눠 저장하면 관리가 깔끔해지는 대신, 조회할 때 두 테이블을 도로 이어 붙이는 수고가 생깁니다. 게시글을 가져온 뒤 그 안의 category_id를 보고 카테고리 테이블을 또 조회해서 손으로 연결해야 하죠. 이 반복 작업을 TypeORM이 대신 해줍니다. 우리가 "게시글과 카테고리는 이런 관계"라고 엔티티에 한 번 선언해두면, 그다음부터는 post.category.name처럼 객체를 점(.)으로 타고 들어가듯 자연스럽게 접근할 수 있습니다. 이것을 객체 그래프 탐색이라고 부릅니다.

아래는 같은 작업을 손으로 FK를 이어 붙이는 방식과 TypeORM 연관관계로 맡기는 방식으로 나란히 비교한 것입니다. 왼쪽은 카테고리를 별도 쿼리로 조회해 직접 post.category = ...로 꽂아 넣지만, 오른쪽은 relations: { category: true } 한 줄이면 TypeORM이 알아서 JOIN해 채워줍니다.

❌ Raw 쿼리 방식
// Post 조회 후 Category 따로 조회
async findPost(id: number) {
  const post = await dataSource.query(
    'SELECT * FROM posts WHERE id = $1', [id]
  );
  // Category를 따로 조회해서 수동으로 연결
  const category = await dataSource.query(
    'SELECT * FROM categories WHERE id = $1',
    [post[0].category_id]
  );
  post[0].category = category[0];
  return post[0];
}
✅ TypeORM 연관관계
// 객체 그래프 탐색으로 바로 접근
async findPost(id: number) {
  const post = await this.postRepository
    .findOne({
      where: { id },
      relations: { category: true },
    });

  // 바로 접근 가능
  const categoryName = post.category.name;
  return post;
}

@ManyToOne — 가장 많이 쓰는 연관관계

① "N:1 관계"가 뭔가요?

@ManyToOne은 이름 그대로 "여러 개(Many)가 하나(One)를 가리키는 관계"입니다. 실무에서 가장 자주 등장하는 관계라서, 이것 하나만 확실히 익혀도 연관관계의 절반은 이해한 셈입니다. 말로만 들으면 추상적이니, 익숙한 장면으로 먼저 감을 잡아봅시다.

비유 — 한 반에 여러 학생 한 학급(1)에는 여러 학생(N)이 속합니다. 그런데 "누가 어느 반인지"를 어디에 적을까요? 학생 각자의 학생증에 "3반"이라고 적습니다. 반대로 교실 벽에 30명의 이름을 다 적어두지는 않죠. 즉 "여러 개(N)"쪽인 학생이 자기가 속한 "하나(1)"의 번호를 들고 있습니다. 데이터베이스도 똑같아서, 여러 게시글(N)이 한 카테고리(1)에 속할 때 게시글 쪽에 category_id가 생깁니다.

이 "N쪽이 1의 ID를 가진다"는 규칙은 @ManyToOne을 이해하는 핵심 열쇠입니다. 아래 두 카드로 여러 예시와 실제 테이블 모습을 확인해봅시다.

예시로 이해하기
유튜브 영상(N) → 채널(1)
댓글(N) → 게시글(1)
게시글(N) → 카테고리(1)

공통점: "여러 개"쪽이 "하나"의 ID를 가짐
DB 테이블로 보면
posts 테이블이 category_id라는 컬럼을 가집니다.
categories 테이블에는 아무 변화 없음.

즉, "여러 개(N)"쪽 테이블에 FK 컬럼이 생깁니다.

② 연관 데이터를 가져오는 3가지 전략

게시글과 카테고리가 연결됐다고 해서, 게시글을 조회할 때마다 카테고리까지 항상 딸려 와야 하는 건 아닙니다. 목록 화면에서는 제목만 필요하고, 상세 화면에서는 카테고리 이름도 필요할 수 있죠. 그래서 "연관된 데이터를 언제, 어떻게 가져올지"를 정하는 세 가지 전략이 있습니다. 이름은 낯설지만, 식당에서 곁들임(사이드 메뉴)을 주문하는 방식에 그대로 대응됩니다.

비유 — 햄버거에 감자튀김을 곁들이는 세 가지 방법 게시글을 햄버거, 카테고리를 감자튀김이라고 합시다. ① EAGER는 세트 메뉴입니다. 버거를 시키면 필요하든 아니든 감자튀김이 항상 따라옵니다. ② LAZY는 일단 버거만 받고, 나중에 "감자튀김도 주세요"라고 말하는 순간 주방이 그때 다시 튀겨 옵니다(추가 대기). ③ relations 명시는 주문할 때 그때그때 "이번엔 감자튀김도요"라고 직접 고르는 방식입니다. 실무에서는 이 세 번째 방식이 표준입니다 — 매번 필요한 것만 정확히 고를 수 있으니까요.

세 전략을 표로 정리하면 다음과 같습니다. 뒤에서 각각의 실제 코드와 SQL을 하나씩 뜯어봅니다.

전략동작 방식실무 사용 여부
EAGER엔티티에 eager: true 설정 → 항상 자동 JOIN⚠️ 제한적
LAZY처음엔 Post만 가져오고, await post.category 시점에 추가 쿼리 실행❌ 비권장
relations 명시find() 호출마다 필요할 때만 relations: { category: true } 지정✅ 실무 표준

각 전략이 실제로 어떻게 동작하는가

이제 세 방식이 실제로 어떤 SQL을 만들어내는지 코드로 확인해봅시다. 특히 쿼리가 몇 번 나가는지를 눈여겨보세요. EAGER는 필요 없어도 매번 JOIN이 붙고, LAZY는 쿼리가 두 번으로 쪼개지며, relations 명시만이 "필요할 때 한 번, 필요 없을 때 안 나감"을 정확히 지킵니다.

EAGER — 항상 같이 가져옴
// 엔티티 설정
@ManyToOne(() => Category, {
  eager: true,  // ← 항상 자동 JOIN
})
category: Category;

// 조회 — relations 안 써도 category 포함됨
const post = await repo.findOne(
  { where: { id: 1 } }
);
// SQL: SELECT ... JOIN categories
//      category가 필요 없어도 항상 JOIN
⚠️ 필요 없을 때도 매번 JOIN → 불필요한 부하
LAZY — 접근 시점에 추가 쿼리
// 엔티티 설정
@ManyToOne(() => Category)
category: Promise<Category>;
// ← 타입이 Promise여야 함 (특이한 구조)

// 조회
const post = await repo.findOne(
  { where: { id: 1 } }
);
// SQL 1: SELECT * FROM posts WHERE id=1
// (category는 아직 안 가져옴)

// category에 접근하는 순간 추가 쿼리 실행
const cat = await post.category;
// SQL 2: SELECT * FROM categories WHERE id=?
❌ Promise 타입 강제, 실수 시 N+1 문제 디버깅 어려움
relations 명시 — 필요할 때만 (권장)
// 엔티티 설정 — 아무 옵션 없음
@ManyToOne(() => Category)
category: Category;

// category 필요 없을 때
const post = await repo.findOne(
  { where: { id: 1 } }
);
// SQL: SELECT * FROM posts WHERE id=1

// category 필요할 때 → 명시적으로 추가
const post = await repo.findOne({
  where: { id: 1 },
  relations: { category: true },
});
// SQL: SELECT ... JOIN categories
✅ 필요한 것만 가져옴, 코드만 봐도 동작 예측 가능
LAZY를 실무에서 쓰지 않는 이유
TypeORM의 LAZY는 "연관 필드 타입을 Promise<Category>로 바꿔야 한다"는 특이한 제약이 있습니다. 그래서 일반 Category 타입처럼 쓰다가 await를 빠뜨리면 조용히 Promise 객체가 반환되어 버그가 생기고, 어느 시점에 쿼리가 몇 번 나가는지 추적하기도 어렵습니다.

relations 옵션은 코드만 봐도 "이 호출은 JOIN이 발생한다"는 게 바로 보여서 훨씬 안전합니다.

③ 실제 코드 — 실무 권장 패턴

전략을 정했으니 이제 엔티티에 관계를 실제로 선언해봅니다. 아래 코드에서 @ManyToOne(() => Category, (category) => category.posts) 부분을 천천히 뜯어보면, 첫 번째 인자 () => Category는 "내가 연결될 상대 엔티티"를, 두 번째 인자 (category) => category.posts는 "그 상대 쪽에서 이 관계를 뭐라고 부르는지"를 알려주는 이정표입니다. 이 두 번째 인자 덕분에 나중에 Category에서 거꾸로 게시글 목록을 찾아 들어갈 수 있게 됩니다(뒤의 @OneToMany에서 이어집니다).

typescriptpost.entity.ts
@Entity('posts')
export class Post {
  @PrimaryGeneratedColumn()
  id: number;

  @Column()
  title: string;

  // @ManyToOne: "Post가 N, Category가 1"
  // () => Category : 연결할 대상 엔티티
  // (category) => category.posts : 반대쪽(Category)에서 이 관계를 뭐라 부르는지
  @ManyToOne(() => Category, (category) => category.posts, {
    nullable: false,  // category 없는 post는 존재 불가 (NOT NULL)
  })
  @JoinColumn({ name: 'category_id' })  // DB 컬럼명을 category_id로 지정
  category: Category;

  @Column({ name: 'category_id' })
  categoryId: number;  // ID만 필요할 때 편하게 꺼내 쓸 수 있음
}

@JoinColumn — FK 컬럼 이름 지정

@JoinColumn은 FK(외래 키) 컬럼이 DB에 어떤 이름으로 생성될지 지정하는 데코레이터입니다. 생략하면 TypeORM이 categoryId(camelCase)로 자동 생성하고, { name: 'category_id' }를 넘기면 category_id(snake_case) 컬럼명으로 만들어집니다.

비유 — FK는 "연결 고리", 그 고리를 어느 쪽 문에 달까? 두 방을 잇는 연결 통로(FK)를 만들 때, 그 통로 문을 어느 방 벽에 뚫을지 정해야 합니다. @ManyToOne에서는 TypeORM이 "여러 개(N)쪽 벽에 문을 단다"는 걸 이미 알고 있어서 @JoinColumn 없이도 잘 동작합니다. 다만 문에 붙일 이름표(컬럼명)를 바꾸고 싶을 때만 @JoinColumn({ name: 'category_id' })로 지정하는 것이죠. 반면 @OneToOne은 방 둘의 크기가 같아 어느 쪽에 문을 달지 TypeORM이 스스로 못 정하기 때문에, @JoinColumn으로 반드시 짚어줘야 합니다.

아래 표는 관계별로 @JoinColumn이 필요한지 여부와 그 이유를 정리한 것입니다.

관계@JoinColumn이유
@ManyToOne선택 — 컬럼명 커스텀할 때만FK가 "N"쪽 테이블에 생기는 건 TypeORM이 이미 앎
@OneToOne필수FK가 어느 쪽 테이블에 생길지 직접 지정해야 함
@OneToMany불필요FK는 반대쪽(@ManyToOne)에 생김
위 코드에서 @JoinColumn({ name: 'category_id' })를 쓴 이유는 딱 하나 — 컬럼명을 category_id(snake_case)로 맞추기 위해서입니다. 생략해도 FK는 생기지만 컬럼명이 categoryId(camelCase)가 됩니다.
typescriptpost.service.ts
// category 정보가 필요 없을 때 → 그냥 조회
const post = await this.postRepository.findOne({
  where: { id: 1 },
  // category 정보 없음 → post.category = undefined
});

// category 정보가 필요할 때 → relations 명시
const postWithCategory = await this.postRepository.findOne({
  where: { id: 1 },
  relations: { category: true },  // SELECT ... JOIN categories
  // 이제 post.category.name 접근 가능
});

console.log(postWithCategory.category.name);  // "백엔드"

④ eager 옵션 — 항상 자동으로 같이 가져오기

앞서 비유에서 "세트 메뉴"에 해당했던 방식이 바로 이 eager: true입니다. 엔티티에 이 옵션을 달아두면 조회할 때 relations를 쓰지 않아도 매번 자동으로 JOIN됩니다. 편해 보이지만, 정말로 "이 관계는 조회할 때 항상 함께 필요하다"는 확신이 있을 때만 써야 합니다. 그렇지 않으면 카테고리가 필요 없는 목록 조회에서도 매번 불필요한 JOIN이 따라붙어 성능을 갉아먹기 때문입니다. 아래에서 설정과 사용 모습을 나란히 봅시다.

eager: true 설정
// post.entity.ts
@ManyToOne(() => Category, (category) => category.posts, {
  eager: true,  // 항상 category를 같이 가져옴
})
category: Category;
서비스에서 사용
// post.service.ts
// relations 없어도 category가 자동 포함됨
const post = await this.postRepository.findOne({
  where: { id: 1 },
});

// eager: true 덕분에 바로 접근 가능
console.log(post.category.name);  // "백엔드"
방식동작언제 쓰나주의점
eager: true 항상 자동 JOIN 이 관계가 항상 필요한 경우 불필요한 조회도 항상 JOIN → 성능 주의
relations 명시 해당 쿼리에서만 JOIN 필요할 때만 가져오고 싶을 때 가장 일반적인 실무 패턴 ✅
아무것도 없음 category 미포함 ID만 필요한 경우 (categoryId) post.category는 undefined
실무 팁: eager: true는 "이 엔티티를 조회하면 항상 이 관계가 필요하다"는 확신이 있을 때만 씁니다. 대부분의 경우는 relations로 명시하는 게 더 유연합니다.
↙️

@OneToMany — 양방향 관계

바로 앞에서 배운 @ManyToOne이 "게시글(N) → 카테고리(1)"를 게시글 입장에서 바라본 것이라면, @OneToMany는 똑같은 관계를 카테고리 입장에서 거꾸로 바라본 것입니다. 카테고리 하나에는 여러 게시글이 딸려 있으니 "하나(One) → 여럿(Many)"이 되는 것이죠. 여기서 꼭 기억할 점 하나 — @OneToMany는 혼자서는 존재할 수 없고, 반드시 짝이 되는 @ManyToOne이 반대편에 있어야 성립합니다.

비유 — 부모와 자녀, 동전의 양면 "부모와 자녀"는 하나의 관계지만 부르는 방향이 둘입니다. 부모 입장에서 보면 "나에게는 자녀가 여럿 있다"(@OneToMany)이고, 자녀 입장에서 보면 "나에게는 부모가 하나 있다"(@ManyToOne)입니다. 둘은 별개의 관계가 아니라 같은 관계를 양쪽에서 부르는 이름일 뿐이죠. 그래서 실제 연결 고리(FK)는 한 군데, 즉 자녀(=N쪽) 테이블에만 있습니다. 부모 쪽의 @OneToMany는 새 컬럼을 만들지 않고, 그저 "이 관계를 반대편에서 이렇게 부른다"고 이름표를 붙이는 역할입니다.

아래 코드에서 @OneToMany(() => Post, (post) => post.category)의 두 번째 인자 (post) => post.category가 바로 "반대편(Post)의 어느 필드와 짝인지"를 알려주는 부분입니다. 이렇게 양쪽이 서로를 가리켜야 비로소 양방향 관계가 완성됩니다.

typescriptcategory.entity.ts
@Entity('categories')
export class Category {
  @PrimaryGeneratedColumn()
  id: number;

  @Column({ unique: true })
  name: string;

  // mappedBy 역할: Post.category 필드와 연결
  @OneToMany(() => Post, (post) => post.category)
  posts: Post[];   // 조회 시 자동 로딩 안 됨 (relations 명시 필요)
}

// Post.category와 반드시 짝을 맞춤
@Entity('posts')
export class Post {
  @ManyToOne(() => Category, (category) => category.posts)
  @JoinColumn({ name: 'category_id' })
  category: Category;
}

Cascade — 부모에게 한 작업이 자식에게 자동으로 전파

게시글(부모) 하나를 새로 만들면서 그 안의 댓글(자식) 여러 개를 함께 저장하고 싶을 때가 있습니다. 이때 cascade 옵션이 없으면 댓글을 하나하나 따로 save()한 뒤 게시글을 저장해야 해서 번거롭습니다. cascade를 켜두면 게시글만 save()해도 딸린 댓글까지 TypeORM이 알아서 함께 저장해줍니다.

비유 — 앨범을 저장하면 안의 사진도 함께 사진 앨범(부모)에 사진 여러 장(자식)을 끼워 넣고 "이 앨범 저장!"이라고 말했다고 합시다. cascade는 앨범을 저장하는 순간 안에 끼워진 사진들도 한꺼번에 저장되게 하는 옵션입니다. 이게 없으면 사진을 한 장씩 따로 보관 처리한 뒤 앨범을 저장해야 하니 손이 많이 가죠. 부모에게 내린 명령(저장·삭제)이 안에 담긴 자식에게로 흘러 전파된다고 해서 "cascade(폭포처럼 흘러내림)"라는 이름이 붙었습니다.
❌ cascade 없을 때 — 각각 따로 저장해야 함
// Comment를 먼저 직접 save()
const comment1 = new Comment();
comment1.content = '좋아요!';
await this.commentRepository.save(comment1);  // ← 따로 저장

const comment2 = new Comment();
comment2.content = '유익해요';
await this.commentRepository.save(comment2);  // ← 따로 저장

// 그 다음 Post를 저장
const post = new Post();
post.title = 'NestJS 강의';
post.comments = [comment1, comment2];
await this.postRepository.save(post);

// SQL: INSERT INTO comments ... (2번)
// SQL: INSERT INTO posts ...
✅ cascade: true 있을 때 — Post만 save()하면 Comment도 자동 저장
// 엔티티 설정
@Entity('posts')
export class Post {
  @OneToMany(() => Comment, (comment) => comment.post, {
    cascade: true,  // 저장·삭제 모두 전파
  })
  comments: Comment[];
}

// 서비스 코드 — commentRepository.save() 없이 postRepository.save() 한 번으로 끝
const post = new Post();
post.title = 'NestJS 강의';
post.comments = [
  Object.assign(new Comment(), { content: '좋아요!' }),
  Object.assign(new Comment(), { content: '유익해요' }),
];

await this.postRepository.save(post);  // ← 이것만으로 Comment도 자동 INSERT
// SQL 1: INSERT INTO posts ...
// SQL 2: INSERT INTO comments ...  ← 자동 실행

cascade: ['insert'] — 저장만 전파, 삭제는 각자

생성할 때는 Post 하나로 묶어서 편하게 만들고 싶지만, 삭제할 때는 댓글이 자동으로 지워지는 게 위험해서 따로 관리하고 싶을 때 씁니다.

cascade: ['insert'] 설정
@OneToMany(() => Comment, (comment) => comment.post, {
  cascade: ['insert'],  // 저장만 전파, 삭제는 전파 안 함
})
comments: Comment[];

// ✅ 저장 — Post save() 시 Comment도 자동 INSERT
const post = new Post();
post.comments = [Object.assign(new Comment(), { content: '안녕' })];
await this.postRepository.save(post);  // Comment도 자동 저장됨

// ❌ 삭제 — Post remove()해도 Comment는 자동 삭제 안 됨
// → 먼저 Comment를 직접 삭제해야 Post를 지울 수 있음
await this.commentRepository.delete({ post: { id: 1 } });  // 직접 삭제
await this.postRepository.remove(post);
cascade: ['insert']를 쓰는 실제 이유
게시글 삭제 시 댓글도 자동으로 지워지면 실수로 중요한 데이터를 날릴 수 있습니다. 삭제는 별도 확인 후 직접 처리하고, 생성만 편하게 묶고 싶을 때 cascade: ['insert']를 선택합니다.
옵션저장 전파삭제 전파언제 쓰나
cascade: true✅✅부모와 자식을 항상 함께 관리할 때
cascade: ['insert']✅❌생성은 묶어서 편하게, 삭제는 직접 관리할 때
cascade: ['remove']❌✅생성은 각자, 부모 삭제 시 자식도 지울 때

orphanedRowAction — 배열에서 빠진 자식을 DB에서도 지우기

cascade와 이름도 비슷하고 역할도 헷갈리기 쉬운 옵션입니다. 하지만 동작하는 순간이 완전히 다릅니다. cascade가 "부모를 통째로 삭제할 때" 자식을 함께 지운다면, orphanedRowAction은 "부모는 그대로 있는데, 자식이 부모의 목록(배열)에서 빠졌을 때" 그 빠진 자식을 DB에서 지웁니다.

비유 — 플레이리스트에서 곡을 빼면 라이브러리에서도 사라지게 어떤 음악 앱에 "플레이리스트에서 곡을 제거하면 그 곡을 내 라이브러리에서도 완전히 삭제한다"는 설정이 있다고 합시다. 플레이리스트(부모)는 멀쩡히 남아 있는데, 목록에서 곡 하나(자식)를 빼는 순간 그 곡은 갈 곳이 없어진 "고아(orphan)"가 되어 라이브러리에서 통째로 사라집니다. orphanedRowAction: 'delete'가 바로 이 설정입니다. 반면 cascade에 의한 삭제는 플레이리스트 자체를 삭제할 때 안의 곡이 함께 지워지는 것이라, 작동하는 시점이 서로 다릅니다.
❌ orphanedRowAction 없을 때 — 고아 행 발생
// 댓글이 3개 있는 Post 조회
const post = await this.postRepository.findOne({
  where: { id: 1 },
  relations: { comments: true },
});
// post.comments = [댓글1(id:1), 댓글2(id:2), 댓글3(id:3)]

// 댓글3을 배열에서 제거하고 저장
post.comments = post.comments.filter(c => c.id !== 3);
await this.postRepository.save(post);

// DB 결과: 댓글3이 DB에 그대로 남아있음 → "고아(orphan) 행"
// comments 테이블: id=1, id=2, id=3 모두 존재
✅ orphanedRowAction: 'delete' 있을 때
@Entity('posts')
export class Post {
  @OneToMany(() => Comment, (comment) => comment.post, {
    cascade: true,
    orphanedRowAction: 'delete',  // 배열에서 빠지면 DB에서도 삭제
  })
  comments: Comment[];
}

// 댓글3을 배열에서 제거하고 저장
post.comments = post.comments.filter(c => c.id !== 3);
await this.postRepository.save(post);

// DB 결과: 댓글3이 DB에서도 자동 삭제됨
// comments 테이블: id=1, id=2만 존재
// SQL: DELETE FROM comments WHERE id = 3  ← 자동 실행
cascade vs orphanedRowAction 한 줄 요약
• cascade — 부모를 통째로 삭제할 때 자식도 함께 삭제
• orphanedRowAction: 'delete' — 부모 배열에서 자식을 제거했을 때 DB에서도 삭제

@ManyToMany — 중간 Entity 사용 권장

지금까지 본 @ManyToOne/@OneToMany는 한쪽은 반드시 "하나"였습니다(게시글은 카테고리 하나에만 속함). 그런데 세상에는 양쪽 모두 "여러 개"인 관계도 많습니다. 이것이 @ManyToMany, 즉 N:M 관계입니다.

비유 — 학생과 수강 과목 한 학생은 여러 과목을 수강하고, 한 과목은 여러 학생이 듣습니다. 양쪽 다 "여러 개"를 가리키죠. 이걸 어떻게 기록할까요? 학생 명부에 "수강 과목: 수학, 영어, 과학…"을 적자니 칸이 부족하고, 과목 명단에 "수강생: 김철수, 이영희…"를 적자니 마찬가지입니다. 그래서 현실에서는 "수강신청 내역"이라는 별도의 명단을 만들어, 한 줄에 "누가 + 무슨 과목"을 적습니다. 이 중간 명단이 바로 데이터베이스의 중간 테이블(join table)입니다.

아래에서는 이 개념을 인스타그램 좋아요 기능으로 구체화해봅니다. "누가 어떤 글에 좋아요를 눌렀나"는 회원(N)과 게시글(M) 양쪽이 서로 여럿을 가리키는 전형적인 N:M 관계이기 때문입니다.

③ 코드로 보기 — 딱 3개 파일

구조는 생각보다 단순합니다. 중간 테이블(PostLike)을 직접 Entity로 만들고, 그 안에서 회원 쪽과 게시글 쪽으로 각각 @ManyToOne을 하나씩 답니다. 잘 보면 새로운 문법이 아니라, 앞에서 배운 @ManyToOne을 두 번 쓰는 것일 뿐입니다. 수강신청 내역 한 줄이 "학생 한 명"과 "과목 하나"를 가리키듯, PostLike 한 줄이 "회원 한 명(@ManyToOne → Member)"과 "게시글 하나(@ManyToOne → Post)"를 가리키는 것이죠.

typescriptpost-like.entity.ts — 중간 테이블
@Entity('post_likes')
export class PostLike {
  @PrimaryGeneratedColumn()
  id: number;

  // "이 좋아요는 어떤 멤버가 눌렀나?"
  // → member_id 컬럼이 생기고, members 테이블과 연결됨
  @ManyToOne(() => Member, { nullable: false })
  @JoinColumn({ name: 'member_id' })
  member: Member;

  // "이 좋아요는 어떤 게시글에 눌렸나?"
  // → post_id 컬럼이 생기고, posts 테이블과 연결됨
  @ManyToOne(() => Post, { nullable: false })
  @JoinColumn({ name: 'post_id' })
  post: Post;

  // 이 컬럼이 있기 때문에 중간 Entity를 직접 만든 것!
  // TypeORM @ManyToMany 자동 생성 방식으로는 이 컬럼을 추가할 수 없음
  @CreateDateColumn()
  createdAt: Date;
}
typescriptmember.entity.ts — 멤버 쪽
@Entity('members')
export class Member {
  @PrimaryGeneratedColumn()
  id: number;

  @Column()
  name: string;

  // "이 멤버가 누른 좋아요 목록"
  // Member(1) : PostLike(N) — 1:N 관계
  @OneToMany(() => PostLike, (like) => like.member)
  postLikes: PostLike[];
}
typescriptlike.service.ts — 실제 사용
// 좋아요 누르기
async like(memberId: number, postId: number) {
  const like = this.postLikeRepository.create({
    member: { id: memberId },  // member_id = 1
    post:   { id: postId },    // post_id = 10
  });
  await this.postLikeRepository.save(like);
  // INSERT INTO post_likes (member_id, post_id) VALUES (1, 10)
}

// "이 게시글 좋아요 누른 사람 목록" 조회
async whoLiked(postId: number) {
  return this.postLikeRepository.find({
    where: { post: { id: postId } },  // post_id = 10 조건
    relations: { member: true },       // member 정보도 같이
  });
  // → [{ member: { name: '김철수' }, createdAt: ... }, ...]
}

// "이 멤버가 좋아요 누른 게시글 목록" 조회
async whatILiked(memberId: number) {
  return this.postLikeRepository.find({
    where: { member: { id: memberId } },
    relations: { post: true },
  });
}

④ 왜 @ManyToMany 데코레이터를 직접 안 쓰나요?

사실 TypeORM에는 @ManyToMany라는 데코레이터가 따로 있어서, 중간 테이블을 자동으로 만들어주기도 합니다. 편해 보이는데 왜 실무에서는 굳이 중간 Entity를 손수 만들까요? 이유는 그 자동 테이블의 구조가 "두 개의 ID"로 고정되어 있어서, 나중에 정보를 덧붙일 수 없기 때문입니다.

비유 — 빈칸 두 개짜리 자동 양식 vs 내가 설계한 신청서 @ManyToMany 자동 방식은 "학생 번호 __ / 과목 번호 __" 딱 두 칸만 있는 고정 양식과 같습니다. 처음엔 충분해 보이지만, 나중에 "신청한 날짜"나 "취소 여부", "성적" 칸을 추가하려는 순간 이 고정 양식으로는 불가능합니다. 반면 중간 Entity(PostLike)를 직접 만들면, 이건 그냥 평범한 테이블이라 createdAt·status 같은 칸을 원하는 만큼 붙일 수 있습니다. 좋아요·팔로우·수강신청처럼 "언제 눌렀나", "취소됐나" 같은 부가 정보가 거의 항상 따라붙는 실무에서는, 처음부터 직접 만드는 편이 훨씬 안전합니다.

아래 표로 두 방식의 차이를 정리하면, 왜 중간 Entity 방식이 실무 표준이 됐는지 한눈에 보입니다.
