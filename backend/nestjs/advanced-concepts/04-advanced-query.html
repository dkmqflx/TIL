QueryBuilder - 복잡한 쿼리

Part 2에서 우리는 find() 하나로 대부분의 조회를 처리했습니다. 그런데 실무에 들어가면 "주문을 한 번이라도 한 사용자만", "이름이 김씨이거나 이씨인 사람", "사용자별 총 결제액" 처럼 find()의 옵션만으로는 표현하기 벅찬 요구가 쏟아집니다. 이럴 때 한 단계 아래로 내려가 쿼리를 직접 조립하는 도구가 바로 QueryBuilder입니다. 여러 테이블을 엮는 JOIN, 복잡한 WHERE, 집계(합계·개수) 같은 것들이 모두 여기서 다뤄집니다.

비유 — 레고 완제품 세트 vs 낱개 부품으로 직접 조립 Part 2에서 배운 find()는 레고 완제품 세트와 같습니다. 상자를 열면 필요한 부품과 설명서가 딱 맞게 들어 있어서, 정해진 순서대로 끼우기만 하면 근사한 결과물이 뚝딱 나옵니다. 빠르고 편하지만, 설명서에 없는 모양(여러 테이블을 엮은 JOIN, 복잡한 조건, 합계 계산)을 만들려 하면 금방 한계에 부딪히죠. QueryBuilder는 레고 부품을 낱개로 사서 직접 쌓는 것입니다. 블록 하나하나(.where(), .leftJoin(), .select())를 원하는 순서로 이어 붙여 세상에 없던 모양도 자유롭게 만들 수 있습니다. 대신 어떤 블록을 어떤 순서로 쌓을지는 우리가 정해야 합니다.

JOIN — 흩어진 두 테이블을 하나로 엮기

실무 쿼리의 절반은 "따로 저장된 두 테이블을 하나로 붙여 보는" 일입니다. 위 예시에서도 사람 정보는 users에, 그 사람이 주문한 내역은 orders에 나뉘어 있습니다(Part 3에서 배운 연관관계가 바로 이 구조입니다). "누가 무엇을 주문했는지"를 한 줄로 보려면 두 테이블을 이어 붙여야 하는데, 이 연결이 JOIN입니다. 그런데 한쪽에만 있는 데이터(주문이 없는 사용자처럼)를 어떻게 처리할지에 따라 JOIN은 INNER · LEFT · RIGHT 세 종류로 갈립니다.

비유 — 동창회 회원 명부와 회비 장부 대조하기 users를 전체 동창 명부, orders를 회비를 낸 사람들의 장부라고 상상해 봅시다. 두 종이를 나란히 놓고 이름을 대조할 때, 회비를 낸 사람만 추리면 INNER JOIN입니다. 반대로 명부에 적힌 전원을 그대로 두되 회비를 안 낸 사람 옆에는 "납부액: 없음(null)"이라고 적으면 LEFT JOIN이고요. 기준을 뒤집어 장부(주문)를 한 줄씩 훑으면 RIGHT JOIN입니다. 같은 두 명단이라도 "누구를 기준으로 훑느냐"에 따라 결과가 달라진다는 것이 JOIN의 핵심입니다.

INNER JOIN — 교집합만 반환

가장 먼저 살펴볼 INNER JOIN은 양쪽 테이블에 모두 데이터가 있는 행만 남깁니다. 위 비유에서 "회비를 낸 사람만" 추리는 것과 같아서, 주문이 하나도 없는 박민준·최준호는 결과에서 통째로 빠집니다. 아래 코드는 처음 보면 메서드가 줄줄이 이어져 낯설 수 있는데, "어느 테이블에서 시작해(createQueryBuilder) → 무엇과 연결하고(innerJoinAndSelect) → 어떤 컬럼을 꺼내(select) → 실행한다(getMany)"는 흐름 하나만 잡고 읽으면 됩니다. 각 줄의 상세 설명은 주석에 달아 두었습니다.

typescript
// 실행되는 SQL:
// SELECT u.name, u.email, o.product, o.price
// FROM users u INNER JOIN orders o ON o.user_id = u.id

const result = await this.userRepository
  // users 테이블을 기준으로 쿼리 시작, 'u'는 별칭(alias)
  // → 이후 u.name, u.email처럼 짧게 참조 가능
  .createQueryBuilder('u')

  // 'u.orders' → User 엔티티에 선언된 orders 프로퍼티를 가리킴
  //
  // user.entity.ts:
  //   @OneToMany(() => Order, (order) => order.user)
  //   orders: Order[];  ← 여기서 'u.orders'가 이 프로퍼티를 참조
  //
  // TypeORM은 이 데코레이터를 읽어서
  //   1) 대상 테이블: Order 엔티티 → orders 테이블
  //   2) FK 컬럼: Order의 @ManyToOne 쪽에서 user_id를 찾아 ON 조건 자동 생성
  //
  // 두 번째 인자 'o'는 이 joined 테이블에 붙이는 별칭
  // → 이후 select에서 o.product, o.price처럼 참조 가능
  //
  // AndSelect: JOIN한 데이터를 결과에 포함 (없으면 필터링에만 쓰고 결과 미포함)
  .innerJoinAndSelect('u.orders', 'o')

  // 반환할 컬럼 지정 — u.는 users, o.는 orders 테이블
  // 생략하면 SELECT * (모든 컬럼)
  .select(['u.name', 'u.email', 'o.product', 'o.price'])

  // 쿼리 실행 → User[] 배열로 반환
  // getOne()이면 단건(User | null), getRawMany()면 집계용 원시 데이터
  .getMany();

LEFT JOIN — 왼쪽 테이블 기준

이번에는 LEFT JOIN입니다. 비유에서 "명부에 적힌 전원을 그대로 두는" 방식이 여기에 해당합니다. 왼쪽(users) 테이블의 모든 행을 빠짐없이 반환하고, 오른쪽(orders)에 짝이 없으면 그 자리를 null로 채웁니다. 그래서 주문이 없는 박민준·최준호도 목록에 남되 product·price가 null로 나옵니다. "주문 여부와 상관없이 전체 회원 목록을 보여줘야 하는" 화면에서 자주 쓰입니다. 코드에서 바뀌는 부분은 innerJoinAndSelect가 leftJoinAndSelect로 딱 한 단어 바뀐 것뿐입니다.

typescript
// SELECT u.name, u.email, o.product, o.price
// FROM users u LEFT JOIN orders o ON o.user_id = u.id
const users = await this.userRepository
  .createQueryBuilder('u')
  .leftJoinAndSelect('u.orders', 'o')
  .select(['u.name', 'u.email', 'o.product', 'o.price'])
  .getMany();
// orders가 없는 사용자는 orders: [] 로 반환

박민준, 최준호도 포함되지만 product/price는 null. 주문 없는 사용자도 목록에 나타내야 할 때 사용합니다.

leftJoin vs leftJoinAndSelect

이름이 비슷해서 헷갈리는 두 메서드입니다. 둘 다 SQL의 LEFT JOIN을 똑같이 만들어 내지만, 결정적인 차이는 JOIN한 테이블의 컬럼을 결과에 담느냐 마느냐입니다. 뒤에 AndSelect가 붙으면 "연결도 하고, 그 데이터도 결과에 넣어줘"라는 뜻이고, 붙지 않으면 "연결만 해 둘 테니 무엇을 꺼낼지는 내가 addSelect()로 직접 정할게"라는 뜻입니다. 왜 이런 구분이 필요한지 비유로 먼저 감을 잡아 보겠습니다.

비유 — 옆자리에 앉혀 물어보기 vs 서류까지 받아 적기 leftJoin은 옆 부서(orders) 담당자를 내 옆자리로 불러 앉히는 것과 같습니다. 궁금한 걸 바로 물어보며(COUNT(o.id) 세기, WHERE o.price > ... 로 거르기) 함께 일할 수 있죠. 다만 그 사람이 가진 서류를 내 결과 보고서에 그대로 옮겨 적지는 않습니다. leftJoinAndSelect는 여기에 더해 그 서류(주문 컬럼)를 통째로 복사해 보고서에 첨부하는 것입니다. 그래서 결과에서 user.orders로 주문 목록을 바로 꺼내 쓸 수 있게 되죠. 연결(JOIN)과 가져오기(SELECT)는 별개라는 점이 이 절 전체의 핵심입니다.
leftJoinleftJoinAndSelect
LEFT JOIN 생성OO
JOIN 대상 컬럼 자동 SELECTXO
엔티티 관계 객체 자동 채움XO
주 용도집계·필터링관계 객체 로드
typescript
// leftJoinAndSelect: JOIN + o.* 자동 SELECT
// → getMany() 결과에서 user.orders 로 바로 접근 가능
const users = await this.userRepository
  .createQueryBuilder('u')
  .leftJoinAndSelect('u.orders', 'o')  // SELECT u.*, o.* 모두 포함
  .getMany();
// users[0].orders → Order[] 배열로 채워짐

// leftJoin: JOIN만 생성, SELECT는 addSelect()로 직접 지정
// → 집계 함수처럼 o.* 전체가 아닌 특정 표현식만 필요할 때 사용
const result = await this.userRepository
  .createQueryBuilder('u')
  .leftJoin('u.orders', 'o')           // o.* 은 SELECT 되지 않음
  .select('u.name', 'name')
  .addSelect('COUNT(o.id)', 'orderCount')
  .addSelect('SUM(o.price)', 'totalPrice')
  .groupBy('u.id')
  .getRawMany();
// result[0] → { name: '김철수', orderCount: '2', totalPrice: '1550000' }
정리: 관계 객체(user.orders)를 그대로 쓰려면 leftJoinAndSelect, 집계나 필터링 목적으로 JOIN만 필요하면 leftJoin + addSelect()를 사용합니다. leftJoin에 AndSelect가 없는 이유는 "어떤 컬럼을 SELECT할지 직접 결정하겠다"는 의도입니다.

JOIN은 "참조 허용", SELECT는 "결과에 포함"

leftJoin만 해도 o.id, o.price 같은 컬럼을 쿼리 안에서 참조할 수 있습니다. JOIN이 실행되는 순간 SQL 엔진 내부에서 u와 o가 합쳐진 가상의 행이 만들어지기 때문입니다.

sql
-- leftJoin('u.orders', 'o') 가 만드는 SQL
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
--                    ↑ 이 시점부터 o.* 컬럼을 쿼리 안에서 참조 가능

-- 집계 표현식에서 o.id, o.price를 참조 (o.* 전체를 SELECT하지 않아도 됨)
SELECT u.name, COUNT(o.id) AS orderCount, SUM(o.price) AS totalPrice
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id

이 구조 덕분에 o. 참조가 필요한 상황을 세 가지로 나눌 수 있습니다.

상황JOIN 필요?AndSelect 필요?
COUNT(o.id) 집계 계산O (o 참조용)X (o.* 전체 불필요)
user.orders 객체 접근OO
WHERE o.price > 1000 필터O (o 참조용)X
핵심: o. 참조는 JOIN만 있으면 가능합니다. AndSelect는 "o의 컬럼을 결과 객체에 담겠다"는 추가 명령입니다. JOIN = 연결, SELECT = 꺼내기는 별개의 개념입니다.

RIGHT JOIN — 오른쪽 테이블 기준

마지막은 RIGHT JOIN입니다. 앞선 동창회 비유에서 "장부(주문)를 한 줄씩 훑는" 방식이 여기에 해당합니다. 오른쪽(orders) 테이블의 모든 행을 기준으로 삼고, 왼쪽(users)에 짝이 없으면 null로 채웁니다. 그런데 TypeORM에는 rightJoinAndSelect가 따로 없습니다. 그럴 필요가 없기 때문인데, 기준 테이블을 orders로 바꿔서 leftJoinAndSelect를 쓰면 똑같은 결과가 나오기 때문입니다. 즉 "왼쪽 기준 LEFT JOIN"의 방향만 뒤집으면 RIGHT JOIN이 됩니다.

typescript
// SELECT u.name, u.email, o.product, o.price
// FROM users u RIGHT JOIN orders o ON o.user_id = u.id
//
// TypeORM에는 rightJoinAndSelect가 없으므로
// 기준 테이블을 orders로 바꿔서 leftJoin으로 표현
const result = await this.orderRepository
  .createQueryBuilder('o')
  .leftJoinAndSelect('o.user', 'u')
  .select(['u.name', 'u.email', 'o.product', 'o.price'])
  .getMany();
샘플 데이터에서는 모든 주문이 존재하는 사용자와 연결되어 있어 INNER JOIN 결과와 동일합니다. 만약 user_id가 없는 주문이 있다면 그 행도 포함됩니다.

JOIN 종류 비교 요약

JOIN 종류반환 기준없을 때사용 상황
INNER JOIN 양쪽 모두 있는 행 제외됨 주문한 사용자만 조회
LEFT JOIN 왼쪽 테이블 전체 오른쪽 → null 모든 사용자 + 주문(없으면 null)
RIGHT JOIN 오른쪽 테이블 전체 왼쪽 → null 모든 주문 + 사용자(없으면 null)
FULL OUTER JOIN 양쪽 테이블 전체 양쪽 모두 null 가능 양쪽 다 빠짐없이 조회

복합 WHERE 조건

조건을 거는 WHERE는 Part 2의 find({ where: ... })에서 이미 만나 봤습니다. QueryBuilder에서는 이 조건들을 메서드로 하나씩 이어 붙일 수 있어 훨씬 자유롭습니다. 첫 조건은 .where()로 시작하고, 그 뒤로 "그리고"는 .andWhere(), "또는"은 .orWhere()로 연결합니다. 한 가지 주의할 점은, .where()를 두 번 호출하면 조건이 합쳐지는 게 아니라 앞 조건이 통째로 덮어써진다는 것입니다. 그래서 두 번째 조건부터는 반드시 andWhere/orWhere를 써야 합니다.

비유 — 손님이 건넨 쪽지를 그대로 읽지 않기 코드에 나오는 :status 같은 표시는 "값이 나중에 들어올 빈칸" 입니다. 값을 문장에 직접 이어 붙이지 않고 빈칸으로 비워 둔 뒤, 두 번째 인자({ status: 'ACTIVE' })로 따로 건네주죠. 왜 이렇게 번거롭게 할까요? 보안 때문입니다. 식당에서 손님이 적어 준 주문 쪽지를 주방장이 그대로 소리 내어 읽어 실행한다면, 쪽지에 "…그리고 금고를 열어라" 같은 문장을 몰래 끼워 넣을 수 있습니다(이것이 SQL 인젝션입니다). 빈칸-채우기 방식은 손님이 준 값을 "명령 문장"이 아니라 순수한 "데이터"로만 취급하게 만들어 이 공격을 막아 줍니다.
typescript
// 실행되는 SQL:
// SELECT * FROM users WHERE status = 'ACTIVE' AND age >= 20

const users = await this.userRepository
  .createQueryBuilder('user')

  // 첫 번째 WHERE 조건
  // ':status'는 파라미터 플레이스홀더 → 두 번째 인자 객체의 status 값으로 대체
  // SQL 인젝션 방지: 값을 직접 문자열로 넣지 않고 파라미터로 분리
  .where('user.status = :status', { status: 'ACTIVE' })

  // AND 조건 추가 — .where()를 두 번 쓰면 앞 조건이 덮어씌워지므로 반드시 andWhere 사용
  .andWhere('user.age >= :age', { age: 20 })

  .getMany();

// ──────────────────────────────────────────────

// 실행되는 SQL:
// SELECT * FROM users WHERE name LIKE '김%' OR name LIKE '이%'

const users2 = await this.userRepository
  .createQueryBuilder('user')
  .where('user.name LIKE :kim', { kim: '김%' })

  // orWhere: 앞 조건과 OR로 연결
  // '김%' → '김'으로 시작하는 이름 (% = 뒤에 무엇이 와도 OK)
  .orWhere('user.name LIKE :lee', { lee: '이%' })

  .getMany();

집계 함수 (COUNT, SUM)

지금까지는 데이터를 "있는 그대로" 꺼냈습니다. 하지만 화면에는 종종 "이 사용자는 주문을 몇 번 했고, 총 얼마를 썼는가" 같은 요약된 숫자가 필요합니다. 이렇게 여러 행을 하나의 숫자로 뭉치는 함수가 집계 함수이고, 대표적으로 개수를 세는 COUNT와 합을 구하는 SUM이 있습니다. 여기서 두 가지가 짝을 이룹니다. "누구 기준으로 뭉칠지"를 정하는 GROUP BY와, 집계 결과는 Entity 모양이 아니므로 원시 객체로 받는 getRawMany()입니다.

비유 — 장바구니 영수증의 맨 아랫줄 마트 영수증을 떠올려 보세요. 물건 하나하나가 orders의 개별 주문 행이라면, 맨 아래 "총 2개 품목 · 합계 1,550,000원" 줄이 바로 COUNT(개수)와 SUM(합계)입니다. 그리고 GROUP BY u.id는 "사람별로 영수증을 따로 끊어라"는 지시예요. 그래서 김철수의 주문들은 김철수 영수증 한 장으로, 이영희의 주문들은 이영희 영수증 한 장으로 각각 요약됩니다. 만약 GROUP BY가 없다면 온 매장의 주문이 영수증 딱 한 장에 몽땅 합산돼 버립니다.
typescript
// 실행되는 SQL:
// SELECT u.name AS name, COUNT(o.id) AS orderCount, SUM(o.price) AS totalPrice
// FROM users u LEFT JOIN orders o ON o.user_id = u.id
// GROUP BY u.id

const result = await this.userRepository
  .createQueryBuilder('u')

  // leftJoin: 주문 없는 사용자도 포함 (주문 컬럼은 null)
  // leftJoinAndSelect와 달리 AndSelect가 없음
  // → 집계 함수 결과를 addSelect로 직접 지정하므로 AndSelect 불필요
  .leftJoin('u.orders', 'o')

  // select(): 첫 번째 인자 = SQL 표현식, 두 번째 인자 = 결과 객체의 키 이름(alias)
  // → 결과: { name: '김철수', ... }
  .select('u.name', 'name')

  // addSelect(): select()에 컬럼을 추가 (select()를 또 쓰면 앞 것이 덮어씌워짐)
  // COUNT(o.id): o.id가 null이 아닌 행의 수 → 주문 없는 사용자는 0
  .addSelect('COUNT(o.id)', 'orderCount')

  // SUM(o.price): price 합계 → 주문 없는 사용자는 null
  .addSelect('SUM(o.price)', 'totalPrice')

  // GROUP BY: u.id 기준으로 묶음
  // → 같은 사용자의 여러 주문 행을 하나로 집계
  .groupBy('u.id')

  // getRawMany(): 집계 결과는 User 엔티티 구조와 맞지 않으므로 원시 객체 배열로 반환
  // getMany()를 쓰면 TypeORM이 Entity에 매핑 시도 → orderCount 같은 컬럼이 없어서 누락됨
  .getRawMany();

// 결과: [{ name: '김철수', orderCount: '2', totalPrice: '1550000' }, ...]

서브쿼리

서브쿼리(Subquery)란 쿼리 안에 또 다른 쿼리를 중첩하는 것입니다.
메인 쿼리가 실행되기 전에 서브쿼리가 먼저 실행되고, 그 결과를 메인 쿼리의 조건으로 사용합니다.

비유 — 먼저 명단을 뽑고, 그 명단으로 다시 찾기 서브쿼리는 "심부름 안의 심부름" 입니다. 예를 들어 "주문한 적 있는 사람에게만 쿠폰을 보내라"는 일을 한다고 해봅시다. 무작정 전체 회원을 한 명씩 뒤지는 대신, 먼저 주문 장부에서 주문자 명단만 쏙 뽑아 두고(서브쿼리), 그 명단을 손에 쥔 채 회원 목록에서 그 사람들만 골라내는(메인 쿼리) 2단계로 나눠 처리하는 거죠. 안쪽 심부름(명단 뽑기)이 먼저 끝나야 바깥쪽 심부름(쿠폰 보내기)을 시작할 수 있다는 순서가 포인트입니다.
① 서브쿼리 실행
주문한 user_id 목록 추출
→
② 결과를 조건으로 전달

→
③ 메인 쿼리 실행
해당 user_id의 사용자만 조회
단계실행 SQL결과
① 서브쿼리 SELECT DISTINCT user_id FROM orders user_id: [1, 2]
② 메인 쿼리 SELECT * FROM users WHERE id IN (1, 2) 김철수, 이영희
INNER JOIN과 서브쿼리의 차이
둘 다 "주문한 사용자만 조회"라는 같은 결과를 냅니다.
INNER JOIN은 orders 컬럼까지 함께 반환하고, 서브쿼리는 users 컬럼만 반환합니다.
→ users 정보만 필요하면 서브쿼리가 더 깔끔합니다.
typescript
// 실행되는 SQL:
// SELECT * FROM users u
// WHERE u.id IN (SELECT DISTINCT o.user_id FROM orders o)

// ── 1단계: 서브쿼리 정의 ──
const subQuery = this.orderRepository
  .createQueryBuilder('o')

  // orders 테이블에서 user_id만 선택
  .select('o.user_id')

  // DISTINCT: 같은 user_id가 여러 번 나와도 중복 제거
  // → 주문을 1건 이상 한 사용자 id 목록
  .distinct(true);

// ── 2단계: 서브쿼리를 메인 쿼리의 IN 조건에 삽입 ──
const users = await this.userRepository
  .createQueryBuilder('u')

  // subQuery.getQuery(): 서브쿼리를 SQL 문자열로 변환 (실행하지는 않음)
  // → WHERE u.id IN (SELECT DISTINCT o.user_id FROM orders o)
  // INNER JOIN으로도 같은 결과를 낼 수 있지만,
  // 서브쿼리는 JOIN 없이 users 테이블 컬럼만 반환하고 싶을 때 더 명확
  .where(`u.id IN (${subQuery.getQuery()})`)

  .getMany();
프론트 관점에서: JOIN은 서버에서 여러 API를 호출해 데이터를 합치는 과정을 DB 레벨에서 한 번에 처리하는 것과 같습니다. getRawMany()는 집계/서브쿼리처럼 Entity 형태로 매핑이 불가능한 경우에 사용합니다.

DTO 프로젝션 — 필요한 컬럼만 골라서 조회

보통 find()나 getMany()는 Entity의 모든 컬럼을 가져옵니다. 그런데 목록 화면에는 id, name, price 세 개만 필요한데 불필요한 컬럼까지 전부 가져오면 낭비입니다. 필요한 컬럼만 골라 가져오는 것이 DTO 프로젝션입니다. 여기서 DTO는 "Data Transfer Object", 즉 화면에 넘겨줄 데이터만 담은 가벼운 상자라고 생각하면 됩니다.

비유 — 뷔페에서 접시에 담기 getMany()로 Entity 전체를 가져오는 것은 뷔페 음식을 종류별로 죄다 퍼 오는 것과 같습니다. 정작 먹을 건 세 가지뿐인데 접시가 무겁고 자리도 차지하죠. DTO 프로젝션은 먹을 것만 골라 담는 것입니다. 목록 화면에 id·이름·가격만 필요하다면 그 세 컬럼만 select()로 집어 옵니다. 접시(네트워크로 오가는 데이터)가 가벼워지니 서버도 DB도 덜 일하고, 화면도 더 빨리 뜹니다.
getMany() — 전체 컬럼 조회
const products = await this.productRepository
  .createQueryBuilder('p')
  .getMany();

// SELECT p.id, p.name, p.price,
//        p.description,   ← 안 쓰는데도 가져옴
//        p.stock,         ← 안 쓰는데도 가져옴
//        p.created_at,    ← 안 쓰는데도 가져옴
//        ...
// FROM products p
getRawMany() — 필요한 컬럼만
const products = await this.productRepository
  .createQueryBuilder('p')
  .select(['p.id', 'p.name', 'p.price'])
  .getRawMany();

// SELECT p.id, p.name, p.price
// FROM products p

JOIN한 다른 테이블 컬럼도 함께 가져올 수 있습니다. AS로 원하는 이름을 붙입니다.

typescript
// 상품 목록에 판매자 이름과 카테고리 이름도 같이 보여주고 싶을 때
const list = await this.productRepository
  .createQueryBuilder('p')
  .innerJoin('p.seller', 'seller')      // seller 테이블 JOIN
  .innerJoin('p.category', 'category')  // category 테이블 JOIN
  .select([
    'p.id        AS id',
    'p.name      AS name',
    'p.price     AS price',
    'seller.name   AS "sellerName"',    // AS로 원하는 키 이름 지정
    'category.name AS "categoryName"',
  ])
  .getRawMany();

// 결과:
// [
//   { id: 1, name: '노트북', price: 1500000, sellerName: '김철수', categoryName: '전자기기' },
//   { id: 2, name: '마우스', price: 50000,   sellerName: '이영희', categoryName: '전자기기' },
// ]
getMany() vs getRawMany() 차이
getMany() → Entity 객체 배열로 반환. TypeORM이 컬럼을 자동 매핑.
getRawMany() → 날 것의 객체 배열로 반환. AS로 붙인 이름 그대로 키가 됨.

JOIN이 들어가거나 특정 컬럼만 고를 때는 getRawMany()가 더 다루기 쉽습니다.

LIMIT / OFFSET - 페이지네이션

DB에 데이터가 10,000건 쌓여 있는데 이걸 한 번에 다 가져오면 어떻게 될까요? 쿼리도 느려지고, 네트워크로 실어 나르는 양도 어마어마하고, 브라우저도 버벅입니다. 게다가 사용자는 첫 화면에서 보통 앞의 10~20건만 봅니다. 그래서 필요한 만큼만 잘라서 가져오는 것이 페이지네이션이고, 그 가장 기본적인 방법이 LIMIT(몇 개)과 OFFSET(앞에서 몇 개 건너뛰기)입니다.

비유 — 두꺼운 책을 페이지 번호로 펼치기 1만 쪽짜리 백과사전을 통째로 들고 다닐 순 없습니다. 그래서 우리는 "몇 쪽부터 몇 쪽까지"만 펼쳐 봅니다. 이때 "앞에서 20쪽을 세어 넘긴 뒤, 그다음 10쪽을 보여줘" 라고 페이지 번호로 위치를 세는 방식이 바로 OFFSET 방식입니다. LIMIT은 "한 번에 펼쳐 볼 쪽수", OFFSET은 "앞에서 건너뛸 쪽수"예요. 우리가 게시판 아래에서 흔히 보는 1 · 2 · 3 … 페이지 번호 UI가 대부분 이 방식으로 동작합니다.
LIMIT (take)
한 번에 가져올 행의 수.
프론트에서 보내는 size 값과 동일.
OFFSET (skip)
앞에서 몇 개를 건너뛸지.
"2페이지면 10개를 넘기고 그 다음부터 가져와"

전체 데이터가 30건이고 한 페이지에 10건씩 보여준다면:

findAndCount() — 목록 + 전체 개수 한 번에

프론트에서 "전체 몇 페이지인지" 계산하려면 전체 데이터 수(total)가 필요합니다.
findAndCount()는 목록과 전체 개수를 쿼리 2번으로 한 번에 가져옵니다.

typescript
async findAll(page: number, size: number) {
  // findAndCount(): [data, total] 튜플로 반환
  // 내부적으로 SELECT ... LIMIT/OFFSET 과 SELECT COUNT(*) 두 쿼리를 실행
  const [data, total] = await this.userRepository.findAndCount({
    order: { createdAt: 'DESC' },
    take: size,                  // LIMIT: 한 페이지에 가져올 수
    skip: (page - 1) * size,     // OFFSET: 건너뛸 수
  });

  return {
    data,                              // 현재 페이지 목록
    total,                             // 전체 데이터 수 (예: 30)
    page,                              // 현재 페이지 번호
    totalPages: Math.ceil(total / size), // 전체 페이지 수 (예: 3)
    // Math.ceil: 소수점 올림 → 31건이면 ceil(31/10) = 4페이지
  };
}

// 프론트에서 받는 응답 예시 (page=2, size=10):
// {
//   data: [...],      // 11번~20번 데이터 10건
//   total: 30,        // 전체 30건
//   page: 2,
//   totalPages: 3,    // 총 3페이지
// }

OFFSET의 한계, 그리고 커서(Cursor) 방식

OFFSET 방식은 직관적이고 만들기 쉽지만, 데이터가 아주 많아지면 뒤 페이지로 갈수록 느려진다는 약점이 있습니다. 왜냐하면 DB는 OFFSET 9860을 만나면 그 9,860개의 행을 실제로 읽은 뒤 그냥 버리고 나서야 다음 10개를 돌려주기 때문입니다. 건너뛰는 게 공짜가 아니라 "세면서 버리는" 작업인 셈이죠. 게다가 사용자가 페이지를 넘기는 사이에 앞쪽 데이터가 추가·삭제되면 경계가 밀려서 같은 글이 두 번 보이거나 빠지는 문제도 생깁니다. 이 두 문제를 풀어 주는 것이 커서(Cursor) 방식입니다.

비유 — 페이지 번호로 세어 찾기 vs 책갈피 꽂아 두기 OFFSET 방식은 원하는 곳을 펼칠 때마다 1쪽부터 다시 세어서 찾아갑니다. 987페이지를 펼치려면 앞의 수천 줄을 일일이 세어 넘긴 뒤 버려야 하니, 뒤로 갈수록 점점 느려지죠. 커서 방식은 마지막으로 읽은 문장에 책갈피를 꽂아 두는 것입니다. 다음에 읽을 때는 처음부터 세지 않고 "책갈피 바로 다음 문장부터 10줄"만 펼치면 되니, 몇 페이지째든 속도가 한결같습니다. 여기서 책갈피에 적어 두는 위치 기준값(보통 마지막으로 본 행의 id나 createdAt)이 바로 "커서"입니다.
typescript
// 커서 = "마지막으로 본 행의 기준값" (여기서는 id를 사용)
// 첫 페이지: 커서 없이 최신 10건
// 다음 페이지: 이전 페이지의 마지막 id보다 '더 이전' 것 10건
async findByCursor(cursorId?: number, size = 10) {
  const qb = this.userRepository
    .createQueryBuilder('u')
    .orderBy('u.id', 'DESC')
    .take(size + 1); // 다음 페이지 존재 여부를 알려고 1개 더 요청

  if (cursorId) {
    // OFFSET처럼 '앞에서 N개 건너뛰기'가 아니라
    // '기준값보다 작은 것부터' → 인덱스를 타고 바로 점프 (세며 버리지 않음)
    qb.where('u.id < :cursorId', { cursorId });
  }

  const rows = await qb.getMany();
  const hasNext = rows.length > size;              // size+1개면 다음 페이지 있음
  const data = hasNext ? rows.slice(0, size) : rows; // 여분 1개는 잘라냄
  const nextCursor = hasNext ? data[data.length - 1].id : null;

  // 프론트는 nextCursor를 다음 요청에 그대로 실어 보냄
  // GET /users?cursor=42  →  findByCursor(42)
  return { data, nextCursor };
}

OFFSET과 커서는 어느 쪽이 더 좋다기보다, 화면 성격에 따라 갈라 쓰는 도구입니다. 아래 표로 성격을 비교해 두었습니다.

구분OFFSET 방식커서(Cursor) 방식
위치를 찾는 법앞에서 N개를 세어 건너뜀기준값(커서)보다 이전/이후를 바로 조회
뒤 페이지 속도뒤로 갈수록 느려짐몇 페이지든 거의 일정
데이터가 중간에 바뀌면경계가 밀려 중복·누락 가능기준값이 고정이라 안정적
특정 페이지로 점프가능 (page=5로 바로)불가 (앞뒤 순차 이동만)
전체 페이지 수 표시쉬움 (COUNT로 계산)어려움
잘 맞는 화면게시판식 번호 페이징무한 스크롤 · 피드 타임라인
커서 방식은 "5페이지로 바로 이동" 같은 임의 점프가 안 됩니다. 오직 "다음으로 · 이전으로"만 가능하죠. 그래서 페이지 번호 UI가 꼭 필요한 게시판에는 OFFSET이, 아래로 계속 당겨 보는 SNS 피드·무한 스크롤에는 커서가 잘 맞습니다. 처음에는 만들기 쉬운 OFFSET으로 시작하고, 데이터가 크게 늘어 뒤 페이지가 느려질 때 커서 방식을 고민하면 충분합니다.
