INNER JOIN — 교집합만 반환

양쪽 테이블 모두 데이터가 있는 행만 반환합니다. 주문이 없는 사용자는 제외됩니다.

typescript
// 실행되는 SQL:
// SELECT u.name, u.email, o.product, o.price
// FROM users u INNER JOIN orders o ON o.user_id = u.id

const result = await this.userRepository
  // users 테이블을 기준으로 쿼리 시작, 'u'는 별칭(alias)
  // → 이후 u.name, u.email처럼 짧게 참조 가능
  .createQueryBuilder('u')

  // 'u.orders' → User 엔티티에 선언된 orders 프로퍼티를 가리킴
  //
  // user.entity.ts:
  //   @OneToMany(() => Order, (order) => order.user)
  //   orders: Order[];  ← 여기서 'u.orders'가 이 프로퍼티를 참조
  //
  // TypeORM은 이 데코레이터를 읽어서
  //   1) 대상 테이블: Order 엔티티 → orders 테이블
  //   2) FK 컬럼: Order의 @ManyToOne 쪽에서 user_id를 찾아 ON 조건 자동 생성
  //
  // 두 번째 인자 'o'는 이 joined 테이블에 붙이는 별칭
  // → 이후 select에서 o.product, o.price처럼 참조 가능
  //
  // AndSelect: JOIN한 데이터를 결과에 포함 (없으면 필터링에만 쓰고 결과 미포함)
  .innerJoinAndSelect('u.orders', 'o')

  // 반환할 컬럼 지정 — u.는 users, o.는 orders 테이블
  // 생략하면 SELECT * (모든 컬럼)
  .select(['u.name', 'u.email', 'o.product', 'o.price'])

  // 쿼리 실행 → User[] 배열로 반환
  // getOne()이면 단건(User | null), getRawMany()면 집계용 원시 데이터
  .getMany();

LEFT JOIN — 왼쪽 테이블 기준

왼쪽(users) 테이블의 모든 행을 반환하고, 오른쪽(orders)에 데이터가 없으면 null로 채웁니다.

typescript
// SELECT u.name, u.email, o.product, o.price
// FROM users u LEFT JOIN orders o ON o.user_id = u.id
const users = await this.userRepository
  .createQueryBuilder('u')
  .leftJoinAndSelect('u.orders', 'o')
  .select(['u.name', 'u.email', 'o.product', 'o.price'])
  .getMany();
// orders가 없는 사용자는 orders: [] 로 반환

leftJoin vs leftJoinAndSelect

두 메서드 모두 SQL의 LEFT JOIN을 생성하지만, 결과 SELECT 절에 포함되는지 여부가 다릅니다.

leftJoinleftJoinAndSelect
LEFT JOIN 생성OO
JOIN 대상 컬럼 자동 SELECTXO
엔티티 관계 객체 자동 채움XO
주 용도집계·필터링관계 객체 로드
typescript
// leftJoinAndSelect: JOIN + o.* 자동 SELECT
// → getMany() 결과에서 user.orders 로 바로 접근 가능
const users = await this.userRepository
  .createQueryBuilder('u')
  .leftJoinAndSelect('u.orders', 'o')  // SELECT u.*, o.* 모두 포함
  .getMany();
// users[0].orders → Order[] 배열로 채워짐

// leftJoin: JOIN만 생성, SELECT는 addSelect()로 직접 지정
// → 집계 함수처럼 o.* 전체가 아닌 특정 표현식만 필요할 때 사용
const result = await this.userRepository
  .createQueryBuilder('u')
  .leftJoin('u.orders', 'o')           // o.* 은 SELECT 되지 않음
  .select('u.name', 'name')
  .addSelect('COUNT(o.id)', 'orderCount')
  .addSelect('SUM(o.price)', 'totalPrice')
  .groupBy('u.id')
  .getRawMany();
// result[0] → { name: '김철수', orderCount: '2', totalPrice: '1550000' }
정리: 관계 객체(user.orders)를 그대로 쓰려면 leftJoinAndSelect, 집계나 필터링 목적으로 JOIN만 필요하면 leftJoin + addSelect()를 사용합니다. leftJoin에 AndSelect가 없는 이유는 "어떤 컬럼을 SELECT할지 직접 결정하겠다"는 의도입니다.

JOIN은 "참조 허용", SELECT는 "결과에 포함"

leftJoin만 해도 o.id, o.price 같은 컬럼을 쿼리 안에서 참조할 수 있습니다. JOIN이 실행되는 순간 SQL 엔진 내부에서 u와 o가 합쳐진 가상의 행이 만들어지기 때문입니다.

sql
-- leftJoin('u.orders', 'o') 가 만드는 SQL
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
--                    ↑ 이 시점부터 o.* 컬럼을 쿼리 안에서 참조 가능

-- 집계 표현식에서 o.id, o.price를 참조 (o.* 전체를 SELECT하지 않아도 됨)
SELECT u.name, COUNT(o.id) AS orderCount, SUM(o.price) AS totalPrice
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id

이 구조 덕분에 o. 참조가 필요한 상황을 세 가지로 나눌 수 있습니다.

상황JOIN 필요?AndSelect 필요?
COUNT(o.id) 집계 계산O (o 참조용)X (o.* 전체 불필요)
user.orders 객체 접근OO
WHERE o.price > 1000 필터O (o 참조용)X
핵심: o. 참조는 JOIN만 있으면 가능합니다. AndSelect는 "o의 컬럼을 결과 객체에 담겠다"는 추가 명령입니다. JOIN = 연결, SELECT = 꺼내기는 별개의 개념입니다.

RIGHT JOIN — 오른쪽 테이블 기준

오른쪽(orders) 테이블의 모든 행을 반환하고, 왼쪽(users)에 데이터가 없으면 null로 채웁니다. TypeORM에서는 leftJoinAndSelect의 반대 방향으로 생각하면 됩니다.

typescript
// SELECT u.name, u.email, o.product, o.price
// FROM users u RIGHT JOIN orders o ON o.user_id = u.id
//
// TypeORM에는 rightJoinAndSelect가 없으므로
// 기준 테이블을 orders로 바꿔서 leftJoin으로 표현
const result = await this.orderRepository
  .createQueryBuilder('o')
  .leftJoinAndSelect('o.user', 'u')
  .select(['u.name', 'u.email', 'o.product', 'o.price'])
  .getMany();
샘플 데이터에서는 모든 주문이 존재하는 사용자와 연결되어 있어 INNER JOIN 결과와 동일합니다. 만약 user_id가 없는 주문이 있다면 그 행도 포함됩니다.

JOIN 종류 비교 요약

JOIN 종류반환 기준없을 때사용 상황
INNER JOIN 양쪽 모두 있는 행 제외됨 주문한 사용자만 조회
LEFT JOIN 왼쪽 테이블 전체 오른쪽 → null 모든 사용자 + 주문(없으면 null)
RIGHT JOIN 오른쪽 테이블 전체 왼쪽 → null 모든 주문 + 사용자(없으면 null)
FULL OUTER JOIN 양쪽 테이블 전체 양쪽 모두 null 가능 양쪽 다 빠짐없이 조회

복합 WHERE 조건

typescript
// 실행되는 SQL:
// SELECT * FROM users WHERE status = 'ACTIVE' AND age >= 20

const users = await this.userRepository
  .createQueryBuilder('user')

  // 첫 번째 WHERE 조건
  // ':status'는 파라미터 플레이스홀더 → 두 번째 인자 객체의 status 값으로 대체
  // SQL 인젝션 방지: 값을 직접 문자열로 넣지 않고 파라미터로 분리
  .where('user.status = :status', { status: 'ACTIVE' })

  // AND 조건 추가 — .where()를 두 번 쓰면 앞 조건이 덮어씌워지므로 반드시 andWhere 사용
  .andWhere('user.age >= :age', { age: 20 })

  .getMany();

// ──────────────────────────────────────────────

// 실행되는 SQL:
// SELECT * FROM users WHERE name LIKE '김%' OR name LIKE '이%'

const users2 = await this.userRepository
  .createQueryBuilder('user')
  .where('user.name LIKE :kim', { kim: '김%' })

  // orWhere: 앞 조건과 OR로 연결
  // '김%' → '김'으로 시작하는 이름 (% = 뒤에 무엇이 와도 OK)
  .orWhere('user.name LIKE :lee', { lee: '이%' })

  .getMany();

집계 함수 (COUNT, SUM)

typescript
// 실행되는 SQL:
// SELECT u.name AS name, COUNT(o.id) AS orderCount, SUM(o.price) AS totalPrice
// FROM users u LEFT JOIN orders o ON o.user_id = u.id
// GROUP BY u.id

const result = await this.userRepository
  .createQueryBuilder('u')

  // leftJoin: 주문 없는 사용자도 포함 (주문 컬럼은 null)
  // leftJoinAndSelect와 달리 AndSelect가 없음
  // → 집계 함수 결과를 addSelect로 직접 지정하므로 AndSelect 불필요
  .leftJoin('u.orders', 'o')

  // select(): 첫 번째 인자 = SQL 표현식, 두 번째 인자 = 결과 객체의 키 이름(alias)
  // → 결과: { name: '김철수', ... }
  .select('u.name', 'name')

  // addSelect(): select()에 컬럼을 추가 (select()를 또 쓰면 앞 것이 덮어씌워짐)
  // COUNT(o.id): o.id가 null이 아닌 행의 수 → 주문 없는 사용자는 0
  .addSelect('COUNT(o.id)', 'orderCount')

  // SUM(o.price): price 합계 → 주문 없는 사용자는 null
  .addSelect('SUM(o.price)', 'totalPrice')

  // GROUP BY: u.id 기준으로 묶음
  // → 같은 사용자의 여러 주문 행을 하나로 집계
  .groupBy('u.id')

  // getRawMany(): 집계 결과는 User 엔티티 구조와 맞지 않으므로 원시 객체 배열로 반환
  // getMany()를 쓰면 TypeORM이 Entity에 매핑 시도 → orderCount 같은 컬럼이 없어서 누락됨
  .getRawMany();

// 결과: [{ name: '김철수', orderCount: '2', totalPrice: '1550000' }, ...]

서브쿼리

서브쿼리(Subquery)란 쿼리 안에 또 다른 쿼리를 중첩하는 것입니다.
메인 쿼리가 실행되기 전에 서브쿼리가 먼저 실행되고, 그 결과를 메인 쿼리의 조건으로 사용합니다.

① 서브쿼리 실행
주문한 user_id 목록 추출
→
② 결과를 조건으로 전달
IN (1, 2)
→
③ 메인 쿼리 실행
해당 user_id의 사용자만 조회
단계실행 SQL결과
① 서브쿼리 SELECT DISTINCT user_id FROM orders user_id: [1, 2]
② 메인 쿼리 SELECT * FROM users WHERE id IN (1, 2) 김철수, 이영희
INNER JOIN과 서브쿼리의 차이
둘 다 "주문한 사용자만 조회"라는 같은 결과를 냅니다.
INNER JOIN은 orders 컬럼까지 함께 반환하고, 서브쿼리는 users 컬럼만 반환합니다.
→ users 정보만 필요하면 서브쿼리가 더 깔끔합니다.
typescript
// 실행되는 SQL:
// SELECT * FROM users u
// WHERE u.id IN (SELECT DISTINCT o.user_id FROM orders o)

// ── 1단계: 서브쿼리 정의 ──
const subQuery = this.orderRepository
  .createQueryBuilder('o')

  // orders 테이블에서 user_id만 선택
  .select('o.user_id')

  // DISTINCT: 같은 user_id가 여러 번 나와도 중복 제거
  // → 주문을 1건 이상 한 사용자 id 목록
  .distinct(true);

// ── 2단계: 서브쿼리를 메인 쿼리의 IN 조건에 삽입 ──
const users = await this.userRepository
  .createQueryBuilder('u')

  // subQuery.getQuery(): 서브쿼리를 SQL 문자열로 변환 (실행하지는 않음)
  // → WHERE u.id IN (SELECT DISTINCT o.user_id FROM orders o)
  // INNER JOIN으로도 같은 결과를 낼 수 있지만,
  // 서브쿼리는 JOIN 없이 users 테이블 컬럼만 반환하고 싶을 때 더 명확
  .where(`u.id IN (${subQuery.getQuery()})`)

  .getMany();
프론트 관점에서: JOIN은 서버에서 여러 API를 호출해 데이터를 합치는 과정을 DB 레벨에서 한 번에 처리하는 것과 같습니다. getRawMany()는 집계/서브쿼리처럼 Entity 형태로 매핑이 불가능한 경우에 사용합니다.

DTO 프로젝션 — 필요한 컬럼만 골라서 조회

보통 find()나 getMany()는 Entity의 모든 컬럼을 가져옵니다. 그런데 목록 화면에는 id, name, price 세 개만 필요한데 불필요한 컬럼까지 전부 가져오면 낭비입니다. 필요한 컬럼만 골라 가져오는 것이 DTO 프로젝션입니다.

getMany() — 전체 컬럼 조회
const products = await this.productRepository
  .createQueryBuilder('p')
  .getMany();

// SELECT p.id, p.name, p.price,
//        p.description,   ← 안 쓰는데도 가져옴
//        p.stock,         ← 안 쓰는데도 가져옴
//        p.created_at,    ← 안 쓰는데도 가져옴
//        ...
// FROM products p
getRawMany() — 필요한 컬럼만
const products = await this.productRepository
  .createQueryBuilder('p')
  .select(['p.id', 'p.name', 'p.price'])
  .getRawMany();

// SELECT p.id, p.name, p.price
// FROM products p
//
// → 딱 3개만 가져옴

JOIN한 다른 테이블 컬럼도 함께 가져올 수 있습니다. AS로 원하는 이름을 붙입니다.

typescript
// 상품 목록에 판매자 이름과 카테고리 이름도 같이 보여주고 싶을 때
const list = await this.productRepository
  .createQueryBuilder('p')
  .innerJoin('p.seller', 'seller')      // seller 테이블 JOIN
  .innerJoin('p.category', 'category')  // category 테이블 JOIN
  .select([
    'p.id        AS id',
    'p.name      AS name',
    'p.price     AS price',
    'seller.name   AS "sellerName"',    // AS로 원하는 키 이름 지정
    'category.name AS "categoryName"',
  ])
  .getRawMany();

// 결과:
// [
//   { id: 1, name: '노트북', price: 1500000, sellerName: '김철수', categoryName: '전자기기' },
//   { id: 2, name: '마우스', price: 50000,   sellerName: '이영희', categoryName: '전자기기' },
// ]
getMany() vs getRawMany() 차이
getMany() → Entity 객체 배열로 반환. TypeORM이 컬럼을 자동 매핑.
getRawMany() → 날 것의 객체 배열로 반환. AS로 붙인 이름 그대로 키가 됨.

JOIN이 들어가거나 특정 컬럼만 고를 때는 getRawMany()가 더 다루기 쉽습니다.

LIMIT / OFFSET - 페이지네이션

DB에 데이터가 10,000건 있을 때 전부 한 번에 가져오면 느리고 낭비입니다. LIMIT과 OFFSET으로 잘라서 가져오는 것이 페이지네이션입니다.

LIMIT (take)
한 번에 가져올 행의 수.
프론트에서 보내는 size 값과 동일.
OFFSET (skip)
앞에서 몇 개를 건너뛸지.
"2페이지면 10개를 넘기고 그 다음부터 가져와"

findAndCount() — 목록 + 전체 개수 한 번에

프론트에서 "전체 몇 페이지인지" 계산하려면 전체 데이터 수(total)가 필요합니다.
findAndCount()는 목록과 전체 개수를 쿼리 2번으로 한 번에 가져옵니다.

typescript
async findAll(page: number, size: number) {
  // findAndCount(): [data, total] 튜플로 반환
  // 내부적으로 SELECT ... LIMIT/OFFSET 과 SELECT COUNT(*) 두 쿼리를 실행
  const [data, total] = await this.userRepository.findAndCount({
    order: { createdAt: 'DESC' },
    take: size,                  // LIMIT: 한 페이지에 가져올 수
    skip: (page - 1) * size,     // OFFSET: 건너뛸 수
  });

  return {
    data,                              // 현재 페이지 목록
    total,                             // 전체 데이터 수 (예: 30)
    page,                              // 현재 페이지 번호
    totalPages: Math.ceil(total / size), // 전체 페이지 수 (예: 3)
    // Math.ceil: 소수점 올림 → 31건이면 ceil(31/10) = 4페이지
  };
}

// 프론트에서 받는 응답 예시 (page=2, size=10):

//   total: 30,        // 전체 30건
//   page: 2,
