Column 옵션 · Enum · Embedding

@Column()에 숨겨진 옵션들 — type, nullable, default, unique, length — 을 완전히 정리하고, Enum 컬럼과 Entity Embedding으로 공통 필드를 묶는 법을 배운다.

한 줄 요약. @Column()은 단순한 표시가 아니다 — 옵션을 얼마나 정확히 선언하느냐가 DB 스키마 품질을 결정한다. 빈 @Column()과 @Column({ type: 'varchar', length: 100, nullable: false, default: '' })은 완전히 다른 테이블을 만든다.

학습 목표

  • @Column()의 주요 옵션(type, nullable, default, unique, length, select, update)을 설명할 수 있다
  • Enum 컬럼을 만들고, TypeScript enum과 연결하는 방법을 안다
  • Entity Embedding으로 여러 Entity에 걸친 공통 필드를 하나의 클래스로 묶을 수 있다
⚙️

@Column 옵션 완전 정리

@Column()은 그저 "이 필드는 컬럼입니다"라고 표시하는 도장이 아닙니다. 괄호 안에 옵션 객체를 채워 넣는 순간, 그 컬럼이 DB에서 어떤 모습으로 태어날지 — 어떤 타입인지, 비워둬도 되는지, 값이 없을 때 무엇으로 채울지 — 를 직접 설계하게 됩니다. 옵션을 아예 안 쓰면 TypeORM이 TypeScript 타입을 보고 "아마 이런 뜻이겠지" 하고 추측해서 컬럼을 만들어 주긴 합니다. 하지만 이건 마치 이사할 집의 설계도를 인테리어 업자의 감에만 맡기는 것과 비슷합니다 — 대충은 맞겠지만 나중에 "왜 벽이 여기 있지?" 같은 문제가 튀어나올 수 있죠. 그래서 실무에서는 옵션을 명시적으로 선언해서 컬럼의 모양을 직접 결정하는 편이 훨씬 안전합니다.

비유 — 입력 칸의 규칙. 온라인 가입 폼을 생각해 보세요. 각 입력 칸에는 규칙이 있습니다 — "이 칸은 필수입니다(nullable: false)", "이 칸은 비워두면 '게스트'가 자동으로 들어갑니다(default: 'guest')", "이 칸은 중복 이메일을 허용하지 않습니다(unique: true)", "이 칸은 최대 50자까지만 됩니다(length: 50)". @Column()의 옵션이 바로 DB 수준에서 그 칸의 규칙을 정의하는 것입니다. 폼을 만드는 사람이 규칙을 안 정하면 사용자가 아무렇게나 입력해도 다 통과되듯, @Column()에 옵션을 안 주면 DB도 별다른 규칙 없이 값을 받아줍니다.
옵션타입설명예시
typestringDB 컬럼 타입 명시'varchar', 'int', 'text', 'boolean'
nullablebooleanNULL 허용 여부 (기본 false)nullable: true
defaultanyDB 수준 기본값default: 0, default: 'guest'
uniquebooleanUNIQUE 제약 추가unique: true
lengthnumbervarchar 최대 길이length: 100
selectbooleanfalse면 기본 조회에서 제외select: false
updatebooleanfalse면 최초 INSERT 이후 수정 불가update: false
namestringDB 컬럼 이름 직접 지정name: 'created_at'
commentstringDB 컬럼 주석comment: '이메일 주소'
typescriptuser.entity.ts — @Column 옵션 예시
import { Entity, PrimaryGeneratedColumn, Column } from 'typeorm';

@Entity()
export class User {
  @PrimaryGeneratedColumn()
  id: number;

  // 최대 100자 varchar, NULL 불가, UNIQUE
  @Column({ type: 'varchar', length: 100, nullable: false, unique: true })
  email: string;

  // 기본 SELECT에서 제외 (비밀번호 해시 등 민감 정보)
  @Column({ select: false })
  password: string;

  // 기본값 0, 한 번 저장되면 update 불가
  @Column({ type: 'int', default: 0, update: false })
  loginCount: number;

  // NULL 허용, DB 이름은 'nick_name'으로
  @Column({ type: 'varchar', length: 50, nullable: true, name: 'nick_name' })
  nickname: string | null;
}
select: false와 update: false의 동작을 정확히 이해하세요. select: false인 컬럼은 find() 등 일반 조회에서 자동으로 빠집니다. 예를 들어 비밀번호 해시 컬럼에 이 옵션을 걸어두면, 개발자가 실수로 user 객체를 통째로 API 응답에 실어 보내도 비밀번호 해시는 애초에 그 안에 들어있지 않습니다 — 복사기로 서류를 복사할 때 특정 페이지만 자동으로 빼놓는 것과 비슷하죠. 정말 그 값이 필요할 때는 QueryBuilder에서 .addSelect('user.password')를 명시해야 다시 보입니다. update: false는 조금 다릅니다 — TypeORM ORM 레이어를 통해 저장할 때만 보호되는 규칙이라서, 직접 SQL을 실행하거나 QueryBuilder로 UPDATE를 날리면 여전히 값이 바뀔 수 있습니다. 즉 "금고에 넣고 잠근 것"이 아니라 "손대지 말라고 붙여둔 안내문"에 가깝다는 걸 기억하세요.

Enum 컬럼 — @Column({ type: 'enum', enum: ... })

자유 텍스트로 status 컬럼을 만들면 어떤 일이 생길까요? 누군가는 'published'라고 소문자로 쓰고, 누군가는 'Published'라고 쓰고, 오타로 'publised'라고 쓸 수도 있습니다. DB 입장에서는 셋 다 그냥 문자열이라 아무 문제 없이 저장됩니다. Enum 컬럼은 이런 혼란을 애초에 차단합니다 — 컬럼에 들어올 수 있는 값의 목록을 미리 못박아 두고, 그 목록에 없는 값은 DB가 거부합니다. TypeScript의 enum과 연결하면 코드를 작성하는 단계에서부터 자동완성과 타입 체크까지 받을 수 있고, PostgreSQL에서는 이 제약이 실제로 ENUM 타입으로 만들어집니다.

비유 — 신호등이 켤 수 있는 세 가지 색. 신호등은 빨강, 노랑, 초록 세 가지 색만 켤 수 있습니다. "연두색"이나 "주황색"은 애초에 존재하지 않습니다 — 그런 전구 자체가 없으니까요. Enum 컬럼도 마찬가지입니다. PostStatus를 DRAFT, PUBLISHED, ARCHIVED 세 값으로 정의하면, DB는 그 외의 값이 들어오려는 시도 자체를 막아버립니다. "혹시 몰라서" 문자열 컬럼을 쓰고 애플리케이션 코드에서만 값을 검증하는 것과, DB 스스로가 "이 신호는 세 가지 색만 가능해"라고 강제하는 것은 안정성의 차원이 다릅니다.
typescriptpost.entity.ts — Enum 컬럼
import { Entity, PrimaryGeneratedColumn, Column } from 'typeorm';

// TypeScript enum 정의
export enum PostStatus {
  DRAFT     = 'DRAFT',
  PUBLISHED = 'PUBLISHED',
  ARCHIVED  = 'ARCHIVED',
}

@Entity()
export class Post {
  @PrimaryGeneratedColumn()
  id: number;

  @Column()
  title: string;

  // type: 'enum' + enum: 열거형 클래스 지정
  @Column({
    type: 'enum',
    enum: PostStatus,
    default: PostStatus.DRAFT,
  })
  status: PostStatus;
}
Enum 컬럼이 유용한 이유. 상태값처럼 "정해진 값 중 하나만 허용"되는 필드에 Enum을 쓰면 세 가지 이점이 있습니다. ① DB 수준에서 유효하지 않은 값이 들어오는 것을 막아줍니다. ② TypeScript 타입으로 자동완성과 오류 감지가 됩니다. ③ 코드 전체에서 'PUBLISHED' 같은 문자열 리터럴 대신 PostStatus.PUBLISHED를 써서 오타를 방지합니다. 단, PostgreSQL Enum은 이미 존재하는 값을 삭제하거나 이름을 바꾸면 마이그레이션이 복잡해질 수 있으므로 주의하세요.

Entity Embedding — 공통 필드를 묶어 재사용

User에도 배송지 주소가 필요하고, Store에도 사업장 주소가 필요하다고 해봅시다. 두 Entity에 city, street 컬럼을 매번 따로 선언하면, 나중에 "우편번호(zipCode)도 추가하자"는 요구사항이 왔을 때 두 곳을 똑같이 고쳐야 합니다. Entity Embedding은 이런 반복을 없애줍니다 — 주소 관련 필드를 Address라는 하나의 클래스로 따로 떼어 놓고, 그 클래스가 필요한 Entity에 @Column(() => Address)로 끼워 넣기만 하면 됩니다. 신기한 점은 DB에는 별도 테이블이 생기는 게 아니라, Address의 필드들이 접두사를 붙인 채 원래 테이블 안에 그대로 펼쳐진다는 것입니다.

typescriptaddress.embedded.ts + user.entity.ts — Embedding 예시
// --- 공통 필드를 담은 임베딩 클래스 ---
import { Column } from 'typeorm';

export class Address {
  @Column({ type: 'varchar', length: 100, nullable: true })
  city: string;

  @Column({ type: 'varchar', length: 200, nullable: true })
  street: string;
}

// --- Address를 포함하는 Entity ---
import { Entity, PrimaryGeneratedColumn, Column } from 'typeorm';
import { Address } from './address.embedded';

@Entity()
export class User {
  @PrimaryGeneratedColumn()
  id: number;

  @Column()
  name: string;

  // () => Address: 이 프로퍼티 아래로 Address의 컬럼들이 펼쳐짐
  @Column(() => Address)
  address: Address;
}
// 결과 DB 컬럼: id, name, address_city, address_street
비유 — 여러 서류에 찍는 같은 도장. 회사에 "주소 기입란" 도장이 하나 있다고 생각해 보세요. 계약서에도 찍고, 배송 요청서에도 찍습니다. 도장의 모양(도시, 도로명 칸)은 완전히 똑같지만, 계약서와 배송 요청서는 서로 다른 서류일 뿐 하나가 다른 하나를 상속받는 관계는 아닙니다. Entity Embedding이 바로 이 도장 역할을 합니다. Address 클래스를 한 번 정의해 두고, 필요한 Entity마다 그 모양 그대로 "찍어서" 컬럼을 채워 넣는 것이죠. 그래서 다음 레슨에서 배울 상속(extends BaseModel)과는 성격이 다릅니다 — 상속은 "부모 자식 관계"이고, Embedding은 "같은 서식을 여러 곳에 붙여 쓰는 것"에 가깝습니다.
일반 컬럼(파랑), Enum 컬럼(빨강), Embedded 묶음(노랑 점선)이 하나의 테이블로 합쳐진다.
Embedding vs 상속의 차이. Entity Embedding은 공통 필드를 같은 테이블에 펼쳐 합치는 방식입니다. 상속(다음 레슨)은 기본 클래스를 extends해서 코드를 재사용합니다. Embedding은 "주소"처럼 논리적 묶음이 있는 필드에, 상속은 createdAt/updatedAt처럼 모든 Entity에 공통으로 들어가는 메타 필드에 어울립니다.

셀프 체크 — 면접관처럼 물어보기

Q nullable: false와 default: ''를 동시에 주면 어떻게 되나요?

nullable: false는 컬럼이 NULL을 허용하지 않는다는 뜻입니다. default: ''는 값을 주지 않을 때 빈 문자열을 기본값으로 씁니다. 둘을 함께 쓰면, 값을 명시하지 않아도 빈 문자열이 자동으로 채워져 NOT NULL 제약을 지킵니다. 반면 nullable: true에 default가 없으면 값을 생략할 경우 NULL이 저장됩니다. "필수 필드이지만 빈 값은 허용"이라면 nullable: false + default: '' 조합이 적합합니다.

Q Enum 컬럼을 쓸 때의 장점과 주의점을 설명하세요.

장점: ① DB에서 허용 값을 제한해 데이터 무결성을 보장합니다. ② TypeScript enum 타입으로 자동완성과 컴파일 오류 감지가 됩니다. ③ 'PUBLISHED' 같은 문자열 리터럴 오타를 막습니다. 주의점: PostgreSQL ENUM은 값을 이미 생성한 후 삭제하거나 이름을 바꾸는 마이그레이션이 복잡합니다. 가능하면 Enum 값은 추가만 하고 수정·삭제는 신중하게 해야 합니다. 또한 synchronize: true로 자동 동기화할 때 Enum 변경이 예상대로 반영되지 않는 경우가 있으니 마이그레이션으로 직접 관리하는 것이 안전합니다.

Q select: false인 컬럼을 조회하는 방법은?

select: false로 선언된 컬럼은 find()와 같은 일반 조회에서 결과에 포함되지 않습니다. 그 값이 꼭 필요할 때는 QueryBuilder를 사용해서 .select(['user.id', 'user.email']).addSelect('user.password')처럼 해당 컬럼을 명시적으로 추가해야 합니다. 비밀번호 해시 같은 민감한 필드를 기본 조회에서 자동으로 제외시키는 데 주로 활용합니다.
