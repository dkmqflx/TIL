관계 이론 — SQL Relations

Foreign Key로 테이블이 서로를 참조하는 방법, JOIN으로 흩어진 데이터를 합치는 법, 그리고 1:1 · 1:N · N:M 세 가지 관계 모델을 직관으로 이해한다.

한 줄 요약. 한 테이블에 모든 것을 몰아넣으면 중복이 폭발한다. 관계형 DB의 핵심 아이디어는 단순하다 — 데이터는 나눠서 저장하고, 필요할 때 JOIN으로 다시 연결한다. FK(Foreign Key)가 그 연결 고리다.

학습 목표

  • Foreign Key(FK)가 무엇이고, 참조 무결성을 어떻게 보장하는지 설명할 수 있다
  • INNER JOIN · LEFT JOIN SQL을 작성하고 결과 행을 예측할 수 있다
  • 1:1 · 1:N · N:M 관계가 각각 어떤 상황에서 쓰이는지 설명할 수 있다
  • N:M 관계에 왜 중간(조인) 테이블이 필요한지 이해한다
🔗

Foreign Key — 테이블 간의 연결 고리

Foreign Key(외래 키, FK)는 한 테이블의 컬럼이 다른 테이블의 PK(기본 키)를 참조하도록 선언하는 제약입니다. 이를 통해 DB가 참조 무결성(Referential Integrity)을 강제합니다 — 존재하지 않는 행을 가리키는 FK를 삽입하려 하면 오류가 발생합니다.

비유 — 명함첩의 참조. 명함첩에는 각 사람의 카드(users 테이블)가 있고, 게시판엔 각 글의 쪽지(posts 테이블)가 있습니다. 쪽지에는 작성자 칸에 "카드 번호"만 적혀 있죠. 실제로 글을 누가 썼는지 알고 싶으면 그 번호로 명함첩을 찾아봅니다. 이 "카드 번호"가 FK입니다. FK가 보장하는 것은 단 하나 — 카드 번호에 해당하는 카드가 반드시 명함첩에 존재한다는 것입니다.
posts.authorId가 users.id를 참조하는 FK. 화살표 방향 = "이 테이블이 저 테이블을 참조한다."
sqlSQL — FK 제약 선언
-- posts 테이블에 author_id 컬럼과 FK 제약 추가
ALTER TABLE posts
  ADD COLUMN author_id INT,
  ADD CONSTRAINT fk_posts_author
    FOREIGN KEY (author_id)
    REFERENCES users(id)
    ON DELETE CASCADE;

-- 존재하지 않는 user(id=999)를 참조하려 하면 오류 발생
INSERT INTO posts (title, author_id) VALUES ('Test', 999);
-- ERROR: insert or update on table "posts" violates foreign key constraint
FK가 보장하는 것 — 참조 무결성. FK 제약이 선언되면 DB는 두 가지를 강제합니다. ① posts.authorId에 삽입하는 값은 users.id에 반드시 존재해야 합니다. ② ON DELETE CASCADE처럼 연쇄 동작을 선언하면, 참조 대상 행이 삭제될 때 자동으로 처리(연쇄 삭제·NULL 처리)됩니다. 이 보장을 참조 무결성이라고 합니다.
🔀

JOIN — 흩어진 데이터를 연결하기

FK로 나눠 저장한 데이터를 다시 합칠 때 JOIN을 사용합니다. 가장 자주 쓰는 두 가지는 INNER JOIN(양쪽 모두 존재하는 행만)과 LEFT JOIN(왼쪽 행은 모두, 오른쪽은 없으면 NULL)입니다.

sqlSQL — JOIN 예시
-- INNER JOIN: 작성자가 있는 게시글만 (author_id IS NOT NULL)
SELECT
  p.id        AS post_id,
  p.title,
  u.nickname  AS author_name
FROM  posts p
INNER JOIN users u ON p.author_id = u.id;

-- LEFT JOIN: 작성자 없는 게시글도 포함 (author_name = NULL)
SELECT
  p.id        AS post_id,
  p.title,
  u.nickname  AS author_name
FROM  posts p
LEFT JOIN users u ON p.author_id = u.id;
INNER JOIN은 매칭되는 행만, LEFT JOIN은 왼쪽 테이블 전체를 보존한다. TypeORM의 relations 옵션은 내부적으로 LEFT JOIN을 실행한다.
🧩

관계 종류 모델링 — 1:1 · 1:N · N:M

테이블 간 관계는 카디널리티(한쪽이 몇 개와 연결될 수 있는가)에 따라 세 가지로 분류합니다. 상황에 맞는 관계 모델을 선택하는 것이 설계의 핵심입니다.

관계 카디널리티 한눈에. FK는 항상 "N쪽" 혹은 "소유쪽" 테이블에 생긴다.
관계예시FK 위치N:M 특이사항
1:1User ↔ ProfileFK 소유 쪽(보통 두 번째)—
1:NUser → PostN쪽(posts.authorId)—
N:MPost ↔ Tag중간 테이블 양쪽 FK중간(조인) 테이블 필수
N:M에 중간 테이블이 필요한 이유. 한 컬럼에 여러 값(배열)을 저장할 수 없는 관계형 DB의 특성상, "Post의 tag_ids = [1, 2, 3]" 같은 형태는 불가능합니다. 대신 조인 테이블을 두어 (postId, tagId) 쌍을 행 하나씩으로 저장합니다. 이렇게 하면 N:M이 두 개의 1:N 관계로 분해되어 FK 제약을 유지할 수 있습니다.

그런데 왜 굳이 별도 테이블이어야 할까요? 배열이 안 된다면, 중간 테이블 없이 기존 posts 테이블 안에서 해결할 수는 없을까요? 두 가지를 시도해보면 이유가 드러납니다.

시도 1 — Post 행을 태그 개수만큼 반복. posts에 tag_id 컬럼 하나만 추가하고, 태그가 여러 개면 행을 여러 번 반복하면 어떨까요?
idtitlecontentauthor_idtag_id
1NestJS 강좌본문 내용...53
1NestJS 강좌본문 내용...57

title·content·author_id가 태그 개수만큼 통째로 중복됩니다. 제목을 바꾸면 두 행을 다 고쳐야 하고(수정 이상), 태그가 아직 없는 새 글은 tag_id가 없어 행 자체를 만들 수 없고(삽입 이상), 마지막 태그 하나를 떼어내면 게시글 정보 전체가 사라집니다(삭제 이상).

시도 2 — 컬럼을 여러 개 만들기 (tag_id_1, tag_id_2, …). 배열 대신 tag_id_1, tag_id_2, tag_id_3처럼 고정된 컬럼을 늘어놓는 방법도 있습니다. 하지만 태그가 4개인 글이 나오면 컬럼이 모자라고, "태그 3이 붙은 글 찾기"는 WHERE tag_id_1=3 OR tag_id_2=3 OR tag_id_3=3 ...처럼 쿼리가 끔찍해지며, 태그가 하나뿐인 글은 나머지 컬럼이 전부 NULL로 낭비됩니다.
모양이 다른 데이터는 다른 테이블에. posts의 속성(title, content, author)은 게시글당 정확히 한 벌이어야 정상이지만, "이 게시글에 이 태그가 붙어있다"는 사실은 게시글당 여러 벌일 수 있습니다. 이 둘은 행의 모양 자체가 다른 데이터라 같은 테이블에 우겨넣을 수 없습니다. posts_tags 중간 테이블은 그래서 우회용 트릭이 아니라 "연결"이라는 별개의 사실을 위한 정직한 자기 자리입니다 — 게시글 속성과 연결 정보를 분리해야 데이터 중복 없이 N:M 관계를 표현할 수 있습니다.

그럼 세 테이블에 실제로 데이터를 채워서, 최종적으로 어떤 모양이 되는지 확인해봅시다.

정리하면: Post 1("NestJS 강좌")은 backend·nodejs 두 태그와 연결되고, Post 2("Docker 입문")는 backend 하나와만 연결됩니다. frontend 태그는 아직 어떤 글에도 안 붙어서 posts_tags에는 등장하지 않지만, tags 테이블에는 독립적으로 존재합니다 — Post 속성과 연결 정보를 분리했기 때문에 가능한 일입니다.

sqlSQL — 중간 테이블 생성
-- 두 FK를 합쳐 복합 PK로 쓴다 → "같은 조합"의 중복 삽입을 DB가 막아준다
CREATE TABLE posts_tags (
  post_id INT NOT NULL REFERENCES posts(id) ON DELETE CASCADE,
  tag_id  INT NOT NULL REFERENCES tags(id)  ON DELETE CASCADE,
  PRIMARY KEY (post_id, tag_id)
);
sqlSQL — 중간 테이블을 거쳐 조회하기
-- Post 1에 달린 태그 이름 전부
SELECT t.name
FROM   posts_tags pt
JOIN   tags t ON pt.tag_id = t.id
WHERE  pt.post_id = 1;
-- → backend, nodejs

-- backend 태그(id=3)가 붙은 게시글 전부
SELECT p.title
FROM   posts_tags pt
JOIN   posts p ON pt.post_id = p.id
WHERE  pt.tag_id = 3;
-- → NestJS 강좌, Docker 입문
복합 PK가 하는 일. PRIMARY KEY (post_id, tag_id)는 같은 게시글에 같은 태그를 두 번 붙이는 것을 DB 레벨에서 막아줍니다. 두 FK를 합쳐 하나의 기본 키로 쓰는 것 자체가, 이 테이블의 각 행이 "게시글 하나와 태그 하나의 연결, 그 자체"임을 보여주는 설계입니다.

셀프 체크 — 면접관처럼 물어보기

Q Foreign Key가 보장하는 것은 무엇인가요?

참조 무결성(Referential Integrity)입니다. FK가 선언된 컬럼에 삽입하는 값은 참조 대상 테이블의 해당 컬럼에 반드시 존재해야 합니다. 예를 들어 posts.authorId = 999를 삽입하려 할 때, users.id = 999가 없으면 DB가 오류를 반환합니다. 이로써 "존재하지 않는 사용자가 쓴 게시글" 같은 불일치 데이터가 생기는 것을 방지합니다.

Q N:M 관계에서 왜 중간(조인) 테이블이 필요한가요?

관계형 DB는 한 컬럼에 배열 형태로 여러 외래 키를 저장하는 것을 지원하지 않습니다. posts.tagIds = [1, 2, 3] 같은 형태는 FK 제약을 걸 수 없고 정규화도 되지 않습니다. 중간 테이블 없이 posts 행을 태그 개수만큼 복제하는 방법도 있지만, 그러면 title·content 같은 게시글 속성까지 함께 중복되어 수정·삽입·삭제 이상(anomaly)이 발생합니다. 대신 중간 테이블에 (postId, tagId) 쌍을 행 하나씩으로 저장합니다. 이렇게 하면 N:M이 사실상 두 개의 1:N 관계로 분해되어 FK 제약을 그대로 유지하면서, 게시글 속성 데이터의 중복 없이 연결 정보를 표현할 수 있습니다.

Q INNER JOIN과 LEFT JOIN의 차이는 무엇인가요?

INNER JOIN은 두 테이블 모두에 매칭 행이 있을 때만 결과를 반환합니다. 매칭되지 않는 왼쪽 행은 제외됩니다. LEFT JOIN은 왼쪽 테이블의 모든 행을 보존하되, 오른쪽에 매칭 행이 없으면 오른쪽 컬럼값을 NULL로 채웁니다. TypeORM에서 relations: { author: true } 옵션을 사용하면 내부적으로 LEFT JOIN이 실행됩니다 — 작성자가 없는 게시글도 조회 결과에 포함되기 때문입니다.
