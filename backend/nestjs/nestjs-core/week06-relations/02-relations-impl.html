관계 TypeORM 구현

@OneToOne · @ManyToOne / @OneToMany 데코레이터를 사용해 엔티티 관계를 선언하고, FK가 어느 쪽에 생성되는지, N:M은 중간 엔티티로 어떻게 분해하는지 정확히 이해한다.

한 줄 요약. TypeORM에서 관계는 데코레이터 하나로 선언된다. 그러나 어느 쪽 엔티티에 어떤 데코레이터를 붙이느냐가 FK 컬럼의 위치를 결정한다 — 이 규칙을 틀리면 테이블 구조 자체가 잘못된다.

학습 목표

  • @OneToOne + @JoinColumn을 쌍으로 선언하고 FK 소유 쪽을 정확히 지정할 수 있다
  • @ManyToOne / @OneToMany가 짝임을 이해하고, FK가 ManyToOne 쪽에만 생긴다는 것을 안다
  • N:M 관계를 중간 테이블을 Entity로 선언하고 양쪽에 @ManyToOne을 붙여 구현할 수 있다
  • 각 관계 데코레이터의 두 인수(타입 함수, 역방향 함수)가 하는 역할을 설명할 수 있다
🔐

@OneToOne + @JoinColumn — 1:1 관계와 FK 소유

1:1 관계는 두 엔티티 모두에 @OneToOne을 선언합니다. 단, FK 컬럼을 실제로 갖는 쪽(소유쪽)에만 @JoinColumn을 추가합니다. @JoinColumn 없이 @OneToOne만 있는 반대쪽은 FK 없이 관계만 참조합니다.

비유 — 여권과 사람. 한 사람은 여권 하나만 가질 수 있고, 여권도 주인 한 명뿐입니다. 여권(Profile) 서류에는 "소지인 번호"(FK)가 인쇄되어 있지만, 사람(User) 그 자체에는 여권 번호가 새겨져 있지 않습니다. TypeORM에서 @JoinColumn은 "이 서류가 FK를 보관한다"는 선언입니다.
typescriptuser.entity.ts + profile.entity.ts — @OneToOne
// user.entity.ts
import { Entity, PrimaryGeneratedColumn, Column, OneToOne } from 'typeorm';
import { Profile } from './profile.entity';

@Entity()
export class User {
  @PrimaryGeneratedColumn()
  id: number;

  @Column()
  email: string;

  // 반대쪽: @JoinColumn 없음 → FK 컬럼이 생기지 않는다
  @OneToOne(() => Profile, (profile) => profile.user)
  profile: Profile;
}

// profile.entity.ts
import { Entity, PrimaryGeneratedColumn, Column, OneToOne, JoinColumn } from 'typeorm';
import { User } from './user.entity';

@Entity()
export class Profile {
  @PrimaryGeneratedColumn()
  id: number;

  @Column()
  bio: string;

  // FK 소유쪽: @JoinColumn → profiles 테이블에 userId 컬럼 생성
  @OneToOne(() => User, (user) => user.profile)
  @JoinColumn()
  user: User;
}
@JoinColumn이 선언된 Profile 쪽 테이블에만 userId FK 컬럼이 생긴다.
🔀

@ManyToOne / @OneToMany — 1:N 관계와 FK는 항상 ManyToOne

1:N 관계에서 TypeORM은 두 개의 데코레이터를 쌍으로 씁니다. N쪽(자식) 엔티티에는 @ManyToOne, 1쪽(부모) 엔티티에는 @OneToMany입니다. FK 컬럼은 언제나 @ManyToOne이 있는 쪽 테이블에만 생성됩니다 — @OneToMany만 있는 쪽에는 어떤 FK 컬럼도 생기지 않습니다.

typescriptuser.entity.ts + post.entity.ts — @ManyToOne / @OneToMany
// user.entity.ts — 1쪽 (부모)
import { Entity, PrimaryGeneratedColumn, Column, OneToMany } from 'typeorm';
import { Post } from './post.entity';

@Entity()
export class User {
  @PrimaryGeneratedColumn()
  id: number;

  @Column()
  email: string;

  // @OneToMany: users 테이블에 FK 컬럼이 생기지 않는다
  @OneToMany(() => Post, (post) => post.author)
  posts: Post[];
}

// post.entity.ts — N쪽 (자식), FK가 생기는 쪽
import { Entity, PrimaryGeneratedColumn, Column, ManyToOne } from 'typeorm';
import { User } from './user.entity';

@Entity()
export class Post {
  @PrimaryGeneratedColumn()
  id: number;

  @Column()
  title: string;

  // @ManyToOne: posts 테이블에 authorId(FK) 컬럼이 생성된다
  @ManyToOne(() => User, (user) => user.posts, { onDelete: 'CASCADE' })
  author: User;
}
FK(authorId)는 @ManyToOne이 선언된 Post 테이블에만 생긴다. User 테이블에는 어떤 FK 컬럼도 추가되지 않는다.
@OneToMany만 단독으로 선언할 수 없다. @OneToMany는 반드시 반대쪽 엔티티에 @ManyToOne이 정의되어 있어야 작동합니다. TypeORM은 @OneToMany의 두 번째 인수(역방향 함수)로 반대쪽 @ManyToOne 필드를 참조하기 때문입니다. @ManyToOne 없이 @OneToMany만 선언하면 런타임 오류가 발생합니다.
🧩

N:M 관계 구현 — 명시적 중간 엔티티 (실무 권장)

N:M 관계는 중간 테이블을 그대로 Entity로 선언하고, 양쪽에 @ManyToOne을 붙여서 구현합니다. 사실상 N:M을 두 개의 1:N 관계로 분해하는 것이므로, 앞서 배운 @ManyToOne / @OneToMany 규칙이 그대로 적용됩니다.

typescriptpost-tag.entity.ts + post.entity.ts + tag.entity.ts — 명시적 중간 엔티티
// post-tag.entity.ts — 중간 테이블을 그대로 Entity로 선언
import { Entity, PrimaryGeneratedColumn, ManyToOne, CreateDateColumn } from 'typeorm';
import { Post } from './post.entity';
import { Tag } from './tag.entity';

@Entity()
export class PostTag {
  @PrimaryGeneratedColumn()
  id: number;

  // 일반 @ManyToOne과 동일 — postId(FK)가 생성된다
  @ManyToOne(() => Post, (post) => post.postTags, { onDelete: 'CASCADE' })
  post: Post;

  // tagId(FK)가 생성된다
  @ManyToOne(() => Tag, (tag) => tag.postTags, { onDelete: 'CASCADE' })
  tag: Tag;

  // 중간 엔티티이기 때문에 "관계 자체"에 속성을 자유롭게 추가할 수 있다
  @CreateDateColumn()
  createdAt: Date;
}

// post.entity.ts
import { Entity, PrimaryGeneratedColumn, Column, OneToMany } from 'typeorm';
import { PostTag } from './post-tag.entity';

@Entity()
export class Post {
  @PrimaryGeneratedColumn()
  id: number;

  @Column()
  title: string;

  @OneToMany(() => PostTag, (postTag) => postTag.post)
  postTags: PostTag[];
}

// tag.entity.ts
import { Entity, PrimaryGeneratedColumn, Column, OneToMany } from 'typeorm';
import { PostTag } from './post-tag.entity';

@Entity()
export class Tag {
  @PrimaryGeneratedColumn()
  id: number;

  @Column()
  name: string;

  @OneToMany(() => PostTag, (postTag) => postTag.tag)
  postTags: PostTag[];
}
PostTag가 postId·tagId 두 FK를 직접 소유한 일반 엔티티다. createdAt처럼 관계 자체의 속성도 자유롭게 추가할 수 있다.
명시적 중간 엔티티를 쓰는 이유. ① 확장성 — createdAt, addedBy처럼 관계 자체에 속성이 필요해지면 중간 엔티티에 컬럼을 자유롭게 추가할 수 있습니다. ② 저장 동작의 투명성 — repository.save() / delete()를 직접 호출하므로 어떤 SQL이 나가는지 명확합니다. ③ 중간 테이블 직접 조회 — PostTag가 일반 Entity이므로 "최근 추가된 순서로", "특정 조건으로 필터링" 같은 쿼리를 Repository로 자유롭게 날릴 수 있습니다.
데코레이터붙이는 위치DB에 생기는 것짝 데코레이터
@OneToOne양쪽 모두FK 없음 (JoinColumn 쪽에 FK)@JoinColumn (소유쪽)
@JoinColumnFK 소유쪽만FK 컬럼@OneToOne
@ManyToOneN쪽(자식) — N:M의 중간 엔티티에서는 양쪽 모두FK 컬럼@OneToMany
@OneToMany1쪽(부모)없음@ManyToOne
두 인수의 역할 — 타입 함수 · 역방향 함수. 모든 관계 데코레이터의 두 인수를 이해하면 오타로 인한 오류를 예방할 수 있습니다. 첫 번째 () => Post는 관계 대상 타입을 지정합니다(순환 참조를 피하기 위해 함수로 감쌈). 두 번째 (post) => post.author는 반대쪽 엔티티에서 이 관계를 가리키는 필드를 지정합니다. TypeORM은 이 정보로 양방향 JOIN을 수행합니다.

셀프 체크 — 면접관처럼 물어보기

Q @JoinColumn은 관계의 어느 쪽에 붙이나요?

@JoinColumn은 FK 컬럼을 실제로 소유하는 쪽에만 붙입니다. 1:1 관계에서는 두 엔티티 중 FK를 갖기로 결정한 한쪽에만 선언합니다(보통 "종속적인" 쪽 — 예: User ↔ Profile에서 Profile). @JoinColumn이 없는 반대쪽에는 FK 컬럼이 생기지 않습니다. ManyToOne에서는 @ManyToOne 자체가 암묵적으로 @JoinColumn 역할을 합니다 — 별도로 선언하지 않아도 N쪽 테이블에 FK 컬럼이 생깁니다.

Q @OneToMany가 선언된 쪽에 FK 컬럼이 생기나요?

아니요. FK는 항상 @ManyToOne이 선언된 N쪽 테이블에만 생깁니다. @OneToMany가 선언된 1쪽(부모) 테이블에는 어떤 FK 컬럼도 추가되지 않습니다. @OneToMany는 오직 "반대쪽에 @ManyToOne으로 연결된 컬렉션 필드"를 노출하기 위한 매핑일 뿐입니다. TypeORM이 내부적으로 JOIN을 수행할 때 N쪽의 FK를 참조합니다.

Q N:M 관계를 명시적 중간 엔티티로 구현하면 어떤 점이 좋나요?

세 가지입니다. ① 확장성 — createdAt처럼 관계 자체에 속성이 필요해져도 중간 엔티티에 컬럼만 추가하면 됩니다. ② 저장 동작의 투명성 — repository.save() / delete()를 직접 호출하므로 어떤 SQL이 나가는지 명확합니다. ③ 중간 테이블 직접 조회 — PostTag가 일반 Entity이므로 Repository로 자유롭게 조회·필터링할 수 있습니다.
