Custom Decorator — @User 파라미터 데코레이터

매 핸들러마다 req.user.email처럼 직접 꺼내 쓰는 반복을 없애기 위해, createParamDecorator로 request.user를 파라미터에 바로 주입하는 @User() 데코레이터를 만든다. data 인자로 특정 필드만 골라 받는 패턴도 함께.

한 줄 요약. 이 챕터는 딱 하나만 다룬다 — 반복되는 req.user 접근 코드를 데코레이터 뒤에 숨기기. Guard가 request.user를 채워두면, @User()가 그걸 꺼내 핸들러에 바로 꽂아준다. Guard는 인증만, Custom Decorator는 추출만 — 분업 구조다.

학습 목표

  • Custom Decorator 없이 @Req()로 직접 값을 꺼낼 때 어떤 문제가 생기는지 설명할 수 있다
  • createParamDecorator((data, ctx) => ...) 기본 구조를 작성할 수 있다
  • @User() 파라미터 데코레이터로 request.user 전체를 핸들러에 주입할 수 있다
  • @User('email')처럼 data 인자로 특정 필드만 추출하는 패턴을 구현할 수 있다
  • Guard → request.user 세팅 → Custom Decorator 추출 흐름을 그릴 수 있다
왜 이 챕터를 배우나요? 사실 Week 2부터 @Body(), @Param(), @Query()를 계속 써왔습니다 — 이것들도 전부 NestJS 내부에서 createParamDecorator로 만들어진 파라미터 데코레이터입니다. 이번 챕터는 그 원리를 그대로 가져와 "인증된 사용자 정보를 꺼내는" 나만의 데코레이터를 만들어 봅니다. Guard(인증) · Pipe(검증) · Custom Decorator(추출)가 모이면, 핸들러는 이미 검증되고 정리된 값만 파라미터로 받는 깨끗한 상태가 됩니다.
🤔

왜 필요한가 — createParamDecorator 기본

Guard가 인증에 성공하면 request.user에 사용자 정보를 저장해 둡니다. 이 값을 쓰려면 원래 @Req() req: Request로 요청 객체 전체를 받은 뒤 req.user, req.user.email처럼 매번 직접 꺼내야 합니다. 이렇게 하면 어떤 문제가 생기는지 먼저 보겠습니다.

typescriptposts.controller.ts — Custom Decorator 없이 매번 직접 꺼내는 경우
import { Controller, Get, Post, Req, UseGuards } from '@nestjs/common';
import { Request } from 'express';

@UseGuards(AccessTokenGuard)
@Controller('posts')
export class PostsController {

  @Post()
  createPost(@Req() req: Request) {
    const user = req.user; // 매번 req에서 꺼내야 함, req.user는 보통 any 타입
    return { authorId: user.id };
  }

  @Get('my')
  getMyPosts(@Req() req: Request) {
    const email = req.user.email; // 여기서도 또 꺼내야 함, 필드명 오타가 나도 컴파일 에러가 안 남
    return { email };
  }
}

핸들러가 늘어날수록 req.user를 꺼내는 코드가 계속 반복되고, 나중에 "인증된 사용자 정보를 어디서 어떻게 꺼내는지"가 바뀌면 이 코드를 쓴 모든 핸들러를 다 고쳐야 합니다. createParamDecorator는 이 반복을 한 곳에 모아둡니다. @Body(), @Param()처럼 핸들러 파라미터에 값을 바로 주입하는 데코레이터를 직접 만드는 함수이고, 콜백을 하나 작성해서 넘기면 그 콜백이 반환하는 값이 곧 파라미터로 주입되는 값이 됩니다.

비유 — 택배 상자에서 필요한 것만 꺼내기. request.user는 Guard가 배달해 놓은 택배 상자입니다. 상자 안에는 이메일, 닉네임, 역할 등 여러 정보가 들어 있습니다. @User()는 "상자 전체를 꺼내라"이고, @User('email')는 "상자 안에서 이메일만 꺼내라"입니다. 상자를 여는 방법(택배 기사가 어디에 놓는지)은 데코레이터 안에 딱 한 번만 정의해두고, 핸들러는 원하는 항목을 콕 집어 파라미터로 받기만 하면 됩니다.
typescriptuser.decorator.ts — createParamDecorator 기본
import { createParamDecorator, ExecutionContext } from '@nestjs/common';

// data: @User('email') 처럼 전달한 인자 ('email' 또는 undefined)
// ctx: ExecutionContext — request 객체 접근에 사용
export const User = createParamDecorator(
  (data: string | undefined, ctx: ExecutionContext) => {
    const req = ctx.switchToHttp().getRequest();
    return req.user; // request.user 전체 반환
  },
);

ctx는 Guard 챕터에서 다룬 ExecutionContext와 동일합니다 — switchToHttp().getRequest()로 요청 객체를 꺼내는 방법도 그대로입니다. 콜백이 하는 일은 딱 두 줄, "요청 객체를 꺼내고" "원하는 값을 반환하는" 것뿐입니다.

@User() 데코레이터 구현 — request.user 추출

Guard가 request.user에 인증된 사용자 정보를 저장해 두었다면, @User()는 그 객체를 꺼내 핸들러 파라미터로 바로 주입합니다. 실제 코드는 code/user.decorator.ts에서 확인하세요.

typescriptposts.controller.ts — @User() 사용
import { Controller, Get, Post, UseGuards } from '@nestjs/common';
import { AccessTokenGuard } from './auth/guard/access-token.guard';
import { User } from './auth/decorator/user.decorator';
import { UserModel } from './users/entity/users.entity';

@UseGuards(AccessTokenGuard)
@Controller('posts')
export class PostsController {

  @Post()
  createPost(
    @User() user: UserModel,        // request.user 전체
  ) {
    return { authorId: user.id };
  }

  @Get('my')
  getMyPosts(
    @User('email') email: string,   // request.user.email 만
  ) {
    return { email };
  }
}

1절 예제와 비교해 보면, @Req() req를 받아 req.user · req.user.email을 꺼내던 두 줄이 각각 @User(), @User('email') 한 줄로 줄었습니다. 요청 객체를 어떻게 다루는지는 데코레이터 안으로 숨고, 핸들러는 필요한 값만 파라미터로 받습니다.

Guard(파랑)가 request.user를 채우고, @User 데코레이터(노랑)가 꺼내 핸들러 파라미터에 바로 주입한다.
🎛️

data 인자로 특정 필드만 뽑기

데코레이터에 인자를 전달하면 data 파라미터로 받을 수 있습니다. @User('email')처럼 필드 이름을 넘기면 user[data]를 반환하고, 인자 없이 @User()만 쓰면 user 전체를 반환하는 패턴이 가장 흔합니다.

typescriptuser.decorator.ts — data 인자로 필드 선택 (전체 구현)
import { createParamDecorator, ExecutionContext } from '@nestjs/common';
import { UserModel } from '../users/entity/users.entity';

export const User = createParamDecorator(
  (data: keyof UserModel | undefined, ctx: ExecutionContext) => {
    const req = ctx.switchToHttp().getRequest();
    const user = req.user as UserModel;

    // data가 있으면 해당 필드만, 없으면 user 전체 반환
    return data ? user?.[data] : user;
  },
);

// 사용 예시
// @User()            → UserModel 전체 객체
// @User('id')        → user.id (number)
// @User('email')     → user.email (string)
// @User('nickname')  → user.nickname (string)
Guard와 Custom Decorator는 한 팀. Custom Decorator 혼자서는 request.user가 비어 있으면 아무것도 꺼낼 수 없습니다. Guard가 JWT를 검증하고 request.user를 채워두는 것이 선행되어야 합니다. 이 두 개의 분업이 NestJS 인증 흐름의 핵심 패턴입니다 — Guard: "누구인지 확인해서 기록", Custom Decorator: "기록된 걸 꺼내서 전달".

셀프 체크 — 면접관처럼 물어보기

Q 파라미터 데코레이터가 핸들러에 무엇을 넣어주나요?

createParamDecorator의 콜백 함수가 반환하는 값이 핸들러 파라미터로 주입됩니다. @User()의 경우 콜백이 req.user를 반환하므로, 핸들러는 user: UserModel 파라미터로 인증된 사용자 객체를 바로 받습니다. 콜백에서 undefined를 반환하면 파라미터가 undefined가 됩니다. 이 메커니즘은 NestJS 내장 @Body(), @Query(), @Param()도 동일하게 동작합니다.

Q data 인자는 어디에 쓰나요?

data는 데코레이터를 사용할 때 전달하는 인자입니다. @User('email')이라고 쓰면 data === 'email'이 됩니다. @User()처럼 인자 없이 쓰면 data === undefined입니다. 이를 활용해 return data ? user?.[data] : user처럼 조건 분기를 만들면, 하나의 데코레이터로 전체 객체 또는 특정 필드를 선택적으로 꺼낼 수 있습니다. TypeScript에서 keyof UserModel 타입을 data에 지정하면 자동완성과 타입 안전성을 함께 얻을 수 있습니다.

Q Guard 없이 @User()를 사용하면 어떻게 되나요?

request.user가 undefined이므로 @User()의 반환값도 undefined가 됩니다. Guard는 JWT를 검증한 뒤 req.user = payload처럼 요청 객체에 사용자 정보를 직접 저장합니다. 이 선행 작업 없이 데코레이터만 쓰면 핸들러가 undefined를 받아 TypeError가 발생하거나 잘못된 동작을 할 수 있습니다. 따라서 @User()를 쓰는 라우트에는 반드시 @UseGuards(AccessTokenGuard) 등 Guard가 함께 있어야 합니다.
