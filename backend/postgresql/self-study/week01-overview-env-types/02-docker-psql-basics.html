Docker로 PostgreSQL 띄우기 — 그리고 psql로 속을 들여다보기

DB를 내 컴퓨터에 직접 설치하지 않고 postgres:18 컨테이너로 빌려 씁니다. 그리고 psql의 백슬래시 명령으로 DB 안을 직접 열어봅니다.

한 줄 요약. DB는 설치하는 게 아니라 컨테이너로 빌려 쓰는 것이고, DB 속은 \d 패밀리(백슬래시 명령)로 들여다보는 것입니다. 그리고 Postgres에는 MySQL에 없는 스키마라는 한 층이 더 있습니다.

학습 목표

  • Docker로 PostgreSQL 18을 띄우고 끄고, 데이터를 안전하게 보존한다
  • psql로 접속해 \l \dt \d \du \dn 핵심 명령을 쓴다
  • 데이터베이스 · 스키마 · search_path가 각각 무엇인지 구분한다
  • PG18의 볼륨 마운트 경로 변경 함정을 피한다
📦

왜 DB를 Docker로 띄우나

"PostgreSQL을 내 맥에 그냥 설치하면 안 되나요?" 됩니다. 다만 몇 주만 지나면 이런 일이 생깁니다. A 프로젝트는 PG 15를 쓰는데 B 프로젝트는 PG 18이 필요하고, 둘 다 5432 포트를 쓰겠다고 다투고, 팀원 중 한 명은 윈도우라 설치 절차가 완전히 다르고, 결국 "제 컴퓨터에선 되는데요?"가 등장합니다.

Docker는 이 문제를 두 단어로 해결합니다. 격리(isolation)와 재현성(reproducibility). DB가 컨테이너라는 상자 안에 갇혀 내 컴퓨터와 섞이지 않고, 같은 설계도(이미지)만 받으면 누구든 바이트 단위로 똑같은 DB를 띄울 수 있습니다.

비유 — 콘크리트 창고 vs 조립식 창고. DB를 직접 설치하는 건 마당에 콘크리트로 창고를 짓는 일입니다. 한 번 지으면 옮기기 힘들고, 헐어낼 때도 바닥에 자국이 남습니다(설정 파일, 시스템 서비스, 남은 데이터 폴더…). Docker 컨테이너는 레고처럼 가져다 놓는 조립식 창고입니다. up 한 줄로 세우고 down 한 줄로 흔적 없이 치웁니다. 게다가 설계도(compose 파일)를 그대로 복사해 주면 팀원의 마당에도 똑같은 창고가 생깁니다.

docker-compose.yml — 그리고 PG18의 볼륨 함정

컨테이너 한 채를 띄우는 설계도입니다. 어떤 이미지를 쓸지, 계정은 뭘로 할지, 포트는 어디에 연결할지, 데이터는 어디에 보관할지를 선언합니다. 이번 코스의 실습 환경은 아래 파일 하나로 끝납니다.

yamldocker-compose.yml
services:
  db:
    image: postgres:18          # PostgreSQL 18 공식 이미지
    container_name: pg-study
    environment:
      POSTGRES_USER: study
      POSTGRES_PASSWORD: study_pw
      POSTGRES_DB: study_db
    ports:
      - "5432:5432"             # 호스트 5432 → 컨테이너 5432
    volumes:
      - pgdata:/var/lib/postgresql   # ⚠ 뒤에 /data 붙이지 말 것 (아래 설명)

volumes:
  pgdata:

대부분의 줄은 이름만 봐도 뜻이 짐작되는데, volumes 한 줄이 가장 헷갈리고 가장 자주 사고가 납니다. 잠깐만 짚고 가겠습니다.

컨테이너는 원래 일회용입니다. down하면 통째로 사라지죠. 그러면 그 안에 쌓아둔 DB 데이터도 같이 증발합니다. 그래서 데이터만 컨테이너 밖(내 컴퓨터)에 따로 보관하는데, 이 보관함을 볼륨(volume)이라 부르고, "컨테이너 안 어느 폴더를 이 보관함에 연결할지" 정하는 일을 마운트(mount)라고 합니다.

비유 — 외장 하드를 어느 폴더에 꽂을까. 컨테이너는 전원을 끄면 내용이 날아가는 노트북이고, 볼륨은 그 옆의 외장 하드입니다. 마운트는 "노트북의 어느 폴더를 외장 하드에 연결할까?"를 정하는 일이죠. 여기서 꽂는 위치가 결정적입니다. 엉뚱한 빈 폴더에 외장 하드를 연결해 두면, 정작 데이터가 쌓이는 진짜 폴더는 연결 밖에 있어 전원을 끄는 순간 사라집니다.

그런데 PG18에서 바로 그 "진짜 폴더"의 위치가 바뀌었습니다. 데이터가 실제로 쌓이는 곳이 버전 폴더 안으로 한 단계 들어갔기 때문입니다.

버전데이터가 실제로 쌓이는 곳볼륨을 연결할 폴더
PG17 이하/var/lib/postgresql/data/var/lib/postgresql/data
PG18/var/lib/postgresql/18/docker/var/lib/postgresql (한 단계 위)

PG18 볼륨은 /var/lib/postgresql(상위)에 마운트하고, 뒤에 /data를 붙이지 마세요. 데이터가 이제 버전 폴더(/var/lib/postgresql/18/docker) 안에 쌓이므로, 그 상위를 통째로 연결해야 보관됩니다.

옛 습관대로 .../data를 붙이면 어떻게 될까요? 다행히 조용히 데이터를 잃지는 않습니다. 그 폴더가 비어 있는 걸 감지해 unused mount/volume 경고와 함께 컨테이너가 exit 1로 즉시 종료됩니다. 즉 "엉뚱한 데 꽂았어요"라고 알려주는 안전장치가 작동하는 것이죠. 인터넷의 옛 블로그와 예제에는 아직 /data가 흔하니, 복사해 쓸 때 꼭 확인하세요.

설계도가 준비됐으니 실행입니다. compose 파일이 있는 폴더에서 아래 명령만 알면 됩니다.

bashterminal
# 백그라운드(-d, detached)로 DB 컨테이너 시작
docker compose up -d

# 잘 떴는지 확인
docker compose ps

# 종료 — 컨테이너만 지우고 데이터(볼륨)는 보존
docker compose down

# 데이터까지 완전 삭제 — 실습을 처음부터 다시 하고 싶을 때만
docker compose down -v
down -v의 -v는 데이터를 증발시킵니다. 그냥 docker compose down은 컨테이너만 지우고 named volume(pgdata)은 남겨 데이터가 살아남습니다. 하지만 -v를 붙이면 볼륨까지 삭제돼 그 안에 쌓인 모든 데이터가 사라집니다. 실습을 깨끗이 초기화하고 싶을 때만 의식적으로 쓰세요 — 습관처럼 붙이는 순간 사고가 됩니다.
🔌

psql로 접속하기

컨테이너가 떴으면 이제 그 안의 PostgreSQL에 말을 걸 차례입니다. psql은 PostgreSQL이 공식으로 제공하는 커맨드라인 클라이언트입니다. 별도 설치가 필요 없습니다 — 이미 컨테이너 이미지 안에 들어 있으니, 컨테이너 안에서 바로 실행하면 됩니다.

bashterminal — 컨테이너 안의 psql로 접속
docker compose exec db psql -U study -d study_db
# exec db   : 'db' 서비스 컨테이너 안에서 명령을 실행하라
# -U study  : 접속할 역할(role)
# -d study_db : 접속할 데이터베이스
# 접속되면 프롬프트가 study_db=# 로 바뀐다

접속에 성공했는지 가장 확실하게 확인하는 방법은 DB에게 "나는 지금 어느 DB에 누구로 붙어 있니?"라고 직접 물어보는 것입니다.

sqlstudy_db=# — 연결 확인
SELECT current_database(), current_user, version();
--  current_database | current_user |              version
-- ------------------+--------------+----------------------------------
--  study_db         | study        | PostgreSQL 18.4 (Debian ...) ...
-- (1 row)
psql 첫 사용자를 위한 생존 팁 3개. ① SQL 문 끝에 세미콜론(;)을 안 붙이면 프롬프트가 study_db-#로 바뀌며 "아직 안 끝났는데?" 하고 기다립니다 — 당황하지 말고 ; 치고 엔터. ② 결과가 길어 : 표시에서 멈추면 스페이스로 넘기고 q로 빠져나옵니다. ③ 나가려면 \q입니다(exit도 됩니다).
⌨️

psql의 진짜 무기 — 백슬래시 명령(\d 패밀리)

psql이 단순한 SQL 입력창이 아닌 이유는 백슬래시(\)로 시작하는 메타 명령 때문입니다. "이 DB에 테이블이 뭐가 있지?", "이 테이블 구조가 어떻게 되지?" 같은 질문을 긴 SQL 없이 한두 글자로 물어볼 수 있습니다.

명령무엇을 보나외우는 힌트
\l데이터베이스 목록list databases
\dt현재 스키마의 테이블 목록describe tables
\d <table>특정 테이블의 구조(컬럼·타입·인덱스·제약)describe
\du역할(role) 목록describe users
\dn스키마 목록describe namespaces
\di인덱스 목록describe indexes
\?메타 명령 전체 도움말막히면 이것부터
\qpsql 종료quit
메타 명령은 SQL이 아닙니다. \dt 같은 명령은 psql이라는 프로그램이 해석하는 명령이지 표준 SQL이 아닙니다. 그래서 애플리케이션 드라이버(psycopg, JDBC 등)로 \dt를 보내면 에러가 납니다. 내부적으로 psql은 이걸 pg_catalog(DB가 자기 자신에 대해 기록해 두는 시스템 테이블)를 조회하는 긴 SQL로 바꿔 실행합니다. 즉 \d는 긴 카탈로그 쿼리의 별명인 셈입니다. 궁금하면 \set ECHO_HIDDEN on을 켜고 \dt를 쳐 보세요 — 실제로 나가는 SQL이 그대로 보입니다.

말로만 들으면 감이 안 오니 직접 해봅시다. 테이블 하나를 만들고 \dt와 \d로 확인해 보겠습니다. 아래는 실제로 실행한 결과 그대로입니다.

sqlstudy_db=# — \dt 와 \d 체험
CREATE TABLE ping (id int PRIMARY KEY, msg text);

\dt
--         List of tables
--  Schema | Name | Type  | Owner
-- --------+------+-------+-------
--  public | ping | table | study

\d ping
--                 Table "public.ping"
--  Column |  Type   | Collation | Nullable | Default
-- --------+---------+-----------+----------+---------
--  id     | integer |           | not null |
--  msg    | text    |           |          |
-- Indexes:
--     "ping_pkey" PRIMARY KEY, btree (id)

\d ping의 마지막 줄을 보세요. 우리는 인덱스를 만든 적이 없는데 ping_pkey라는 인덱스가 자동으로 생겼습니다. PRIMARY KEY를 선언하면 Postgres가 그 뒤에서 자동으로 B-tree 인덱스를 만들어 줍니다. "중복이 없는지 매번 빠르게 확인"하려면 인덱스가 필요하기 때문이죠. 인덱스 이야기는 Week 4에서 본격적으로 다룹니다.

데이터베이스 · 스키마 · search_path — 입문자 최대 난관

MySQL을 쓰던 사람이 Postgres에 와서 가장 크게 당황하는 지점이 여기입니다. MySQL에는 "데이터베이스"라는 한 층만 있는데, Postgres에는 그 안에 "스키마"라는 층이 하나 더 있기 때문입니다. 세 개념을 한 번에 정리하겠습니다.

비유 — 서랍장 · 서랍 · 물건. 데이터베이스 = 서랍장 한 채, 스키마 = 그 안의 서랍, 테이블 = 서랍 속 물건입니다. 서랍장 하나에 여러 서랍이 들어 있고, 기본으로 열려 있는 서랍의 이름은 public입니다. 그리고 물건을 찾을 때 어느 서랍부터 열어볼지의 순서가 바로 search_path입니다.
database (서랍장) ⊃ schema (서랍) ⊃ table (물건)

그럼 search_path가 정확히 뭘까요? 우리가 SELECT * FROM ping이라고 쓸 때, 사실 "어느 스키마의 ping이냐"를 말하지 않았습니다. Postgres는 이때 search_path에 적힌 순서대로 스키마를 훑으며 ping을 찾습니다. 지금 설정을 확인해 봅시다.

sqlstudy_db=# — 기본 search_path
SHOW search_path;
--    search_path
-- -----------------
--  "$user", public
-- (1 row)

기본값 "$user", public은 "먼저 내 이름($user)과 같은 이름의 스키마를 찾아보고, 없으면 public을 찾아라"는 뜻입니다. 우리 실습 계정은 study인데 study라는 스키마는 만든 적이 없으니, 결국 항상 public에서 찾게 됩니다. 그래서 지금까지 스키마를 의식하지 않고도 아무 문제가 없었던 것이죠.

물론 순서에 의존하지 않고 주소를 완전히 적어줄 수도 있습니다. SELECT * FROM public.ping처럼요. 애플리케이션 코드나 함수 안에서는 이렇게 명시하는 편이 안전합니다.

MySQL — 익숙한 방식

database ≈ schema가 사실상 동의어입니다. 목록은 SHOW DATABASES;, 전환은 USE db;. 통(database) 하나 안에 테이블이 바로 들어 있는 "한 단계" 구조라고 보면 됩니다.

PostgreSQL — 이렇게 다르다

한 database 안에 여러 schema가 있는 "두 단계" 구조입니다(기본 스키마는 public). database 목록은 \l, 전환은 \c db. 같은 database 안의 스키마 목록은 \dn으로 봅니다.

\c로 database를 바꾸면 연결이 새로 맺어집니다. Postgres에서 한 연결(connection)은 하나의 database에만 붙습니다. 그래서 psql에서 \c other_db를 치면, 기존 연결을 끊고 새 연결을 다시 맺습니다(진행 중이던 트랜잭션도 사라집니다). MySQL의 USE db;가 같은 연결 안에서 대상만 갈아타는 것과 결정적으로 다릅니다.

반면 같은 database 안의 스키마는 연결을 끊지 않고 자유롭게 넘나들 수 있습니다 — search_path를 바꾸거나 schema.table처럼 접두사를 붙이면 됩니다. 그래서 "테넌트별로 스키마 분리" 같은 설계가 Postgres에서 자연스럽게 나옵니다.

이 구조가 처음엔 번거롭게 느껴지지만, 실제로는 한 DB 안에서 논리적으로 영역을 나눌 수 있는 무기입니다. 예를 들어 app 스키마엔 서비스 테이블을, audit 스키마엔 감사 로그를, staging 스키마엔 임시 적재 테이블을 두면 — 연결을 갈아타지 않고도 깔끔하게 분리됩니다.

셀프 체크

Q Postgres에서 database와 schema의 관계는?

하나의 database 안에 여러 schema가 들어 있는 두 단계 구조이고, 기본 스키마 이름은 public입니다. 반면 MySQL은 database와 schema가 사실상 동의어입니다. 서랍장(database) 안에 서랍(schema)이 있고 그 안에 물건(table)이 있다고 기억하세요.

Q 테이블 목록과 테이블 구조를 보는 명령은 각각?

목록은 \dt, 구조는 \d <table>입니다(예: \d ping). \d는 컬럼·타입·제약·인덱스까지 한 번에 보여줍니다. 단, 이 명령들은 psql 전용이라 애플리케이션 드라이버에서는 동작하지 않습니다.

Q search_path는 무엇을 결정하나요?

스키마를 명시하지 않았을 때 객체(테이블·함수 등)를 어느 스키마에서 어떤 순서로 찾을지를 결정합니다. 기본값 "$user", public은 "내 이름과 같은 스키마를 먼저, 없으면 public"이라는 뜻입니다.

Q PG18에서 볼륨을 /var/lib/postgresql/data에 마운트하면?

컨테이너가 unused mount/volume 경고와 함께 exit 1로 즉시 종료됩니다. PG18은 데이터를 /var/lib/postgresql/18/docker에 쌓기 때문에, 볼륨은 한 단계 위인 /var/lib/postgresql에 마운트해야 합니다. 데이터를 조용히 잃는 게 아니라 시작 자체를 막아주는 안전장치입니다.
