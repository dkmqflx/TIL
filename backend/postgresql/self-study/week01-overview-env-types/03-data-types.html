데이터 타입 총정리 — IDENTITY · uuidv7() · timestamptz

Postgres에는 타입이 수십 가지 있지만, 앱 개발자가 매일 쓰는 것은 몇 개뿐입니다. 그중에서도 잘못 고르면 나중에 크게 아픈 세 가지에 집중합니다.

한 줄 요약. 자동증가 키는 IDENTITY, UUID 키는 PG18 내장 uuidv7(), 시간은 무조건 timestamptz, 돈은 무조건 numeric. 이 네 줄만 지켜도 흔한 사고의 절반은 예방됩니다.

학습 목표

  • SERIAL과 IDENTITY의 차이를 알고, 왜 IDENTITY가 권장인지 설명한다
  • PG18 내장 uuidv7()로 정렬 가능한 UUID 키를 만든다
  • timestamp와 timestamptz의 함정을 실제 결과로 확인하고 피한다
  • 금액을 float으로 다루면 왜 안 되는지 눈으로 본다
🎫

자동증가 키 — SERIAL vs IDENTITY

"새 행이 들어올 때마다 1, 2, 3… 자동으로 번호가 붙는 기본 키"는 거의 모든 테이블에 필요합니다. MySQL이라면 AUTO_INCREMENT 한 단어로 끝나지만, Postgres에는 방법이 두 가지가 있습니다. 오래된 SERIAL과, SQL 표준인 GENERATED ALWAYS AS IDENTITY입니다.

sqlstudy_db=# — 같은 의도, 두 가지 표현
-- 구식: SERIAL (뒤에서 시퀀스를 몰래 만들어 연결)
CREATE TABLE old_way (id serial PRIMARY KEY, name text);

-- 권장: SQL 표준 IDENTITY
CREATE TABLE std_way (id int GENERATED ALWAYS AS IDENTITY PRIMARY KEY, name text);

겉보기엔 둘 다 잘 동작합니다. 그런데 왜 하나를 권장할까요? 번호를 누가, 어떻게 뽑는지가 다르기 때문입니다.

비유 — 알바생이 붙여주는 번호표 vs 자동 발권기.

SERIAL은 알바생이 손으로 번호표를 뽑아 붙여주는 방식입니다. 내부적으로 세 가지를 조합합니다: int 컬럼 + 번호를 세는 별도 객체(시퀀스) + "기본값은 시퀀스에서 뽑아라"는 DEFAULT 설정. 문제는 이 시퀀스가 눈에 보이는 독립 개체라는 점입니다. ① 권한을 따로(GRANT … ON SEQUENCE) 챙겨줘야 하고, ② 클라이언트가 "내가 직접 5번 넣을게"라고 우기면 막을 방법이 없어 시퀀스 카운터와 실제 값이 어긋납니다. 나중에 시퀀스가 5번을 뽑는 순간 중복 키 에러가 터집니다.

GENERATED ALWAYS AS IDENTITY는 자동 발권기입니다. ALWAYS라는 단어 덕분에 클라이언트가 id를 직접 넣으려 하면 Postgres가 아예 거부합니다. 정말 필요한 경우(데이터 마이그레이션 등)에만 OVERRIDING SYSTEM VALUE를 명시적으로 붙여 덮어쓸 수 있습니다. 권한도 컬럼에만 주면 되어 별도 시퀀스를 챙길 필요가 없습니다.

정리하면 SERIAL은 진짜 타입이 아니라 "int 컬럼 + 시퀀스 + DEFAULT nextval(...)"의 축약 표기입니다. 시퀀스는 컬럼에 OWNED BY로 묶여 있어서 컬럼이나 테이블을 지우면 같이 사라지긴 합니다. 하지만 "실수로 직접 값을 넣을 수 있다"는 구멍은 그대로 남죠. 새로 만드는 테이블이라면 고민할 것 없이 IDENTITY를 쓰세요.

MySQL — 익숙한 방식

컬럼에 AUTO_INCREMENT를 붙입니다. 테이블당 하나만 가능하고 보통 PK에 답니다. 별도의 시퀀스 객체라는 개념 자체가 없어 단순합니다.

PostgreSQL — 이렇게 다르다

SQL 표준 GENERATED ALWAYS AS IDENTITY가 권장입니다(내부적으로 시퀀스를 쓰지만 컬럼이 소유). SERIAL은 같은 일을 하는 레거시 축약이라 신규 코드에선 피합니다. 시퀀스가 독립 객체라 여러 테이블이 번호를 공유하는 것도 가능합니다.

ALWAYS와 BY DEFAULT의 차이. GENERATED ALWAYS AS IDENTITY는 사용자가 값을 직접 넣는 걸 거부합니다. GENERATED BY DEFAULT AS IDENTITY는 허용합니다(사용자가 안 넣으면 자동 생성). 기존 데이터를 그대로 옮겨야 하는 마이그레이션 상황이라면 BY DEFAULT가 편하지만, 평소엔 ALWAYS로 잠가두는 편이 사고를 막습니다.
🧬

UUIDv7 — 정렬되는 UUID (PG18 내장) ⭐

정수 키는 편하지만 한계가 있습니다. 여러 서버가 각자 ID를 만들어야 하거나, ID를 URL에 노출해야 해서 "1, 2, 3…"으로 남의 데이터를 추측당하면 곤란한 경우죠. 이럴 때 UUID를 키로 씁니다. 그런데 어떤 UUID를 쓰느냐가 성능을 크게 가릅니다.

비유 — 책을 아무 데나 꽂기 vs 항상 맨 끝에 꽂기.

인덱스(B-tree)는 값을 정렬된 상태로 유지하는 자료구조입니다. 도서관 책장이라고 생각하세요.

UUIDv4는 완전 무작위입니다. 새 책이 들어올 때마다 책장 한가운데 아무 데나 꽂아야 하고, 그 칸이 꽉 차 있으면 책들을 밀어내며 칸을 쪼개야 합니다(페이지 분할). 매번 다른 위치를 건드리니 캐시도 잘 안 맞습니다.

UUIDv7은 앞부분에 생성 시각이 박혀 있습니다. 그래서 "나중에 만든 값은 항상 더 큼"이 보장되고, 새 책은 언제나 책장 맨 끝에 꽂힙니다. 밀어낼 일도, 쪼갤 일도 거의 없습니다. 같은 UUID인데 인덱스 입장에서는 완전히 다른 손님인 셈이죠.

PG18부터는 함수 하나면 v7 UUID를 얻을 수 있습니다. 아래는 실제 실행 결과입니다. 같은 시각에 만든 세 행의 id가 생성 순서 그대로 정렬되는 데 주목하세요 — 앞부분 019eac0e-3cef라는 시각 접두사를 공유하고, 그 뒤가 순서대로 커집니다.

sqlstudy_db=# — uuidv7() (PG18 내장)
SELECT uuidv7();
--                 uuidv7
-- --------------------------------------
--  019eac0e-3ce8-7ebd-b830-32e512124867

-- 기본값으로 박아 두면 INSERT마다 자동 생성
CREATE TABLE evt (
  id uuid PRIMARY KEY DEFAULT uuidv7(),
  payload text
);
INSERT INTO evt (payload) VALUES ('a'), ('b'), ('c');
SELECT id FROM evt ORDER BY id;     -- 생성 순서대로!
--                   id
-- --------------------------------------
--  019eac0e-3cef-75b9-9412-5d0a03f0c78a
--  019eac0e-3cef-772c-bd86-5ed97c96eb05
--  019eac0e-3cef-773e-8599-ae7d598cefe1
--  ^^^^^^^^^^^^^ 시각 접두사 공유 → 시간순 정렬

이건 단순히 "보기 좋다"의 문제가 아닙니다. ORDER BY id가 사실상 ORDER BY 생성시각이 되므로, 별도의 created_at 인덱스 없이도 최신순 정렬·페이지네이션이 가능해집니다. 무작위 UUID를 쓸 때는 절대 얻을 수 없는 이득입니다.

PG18 이름이 비슷한 함정을 조심하세요. Postgres 코어에 오래전부터 있던 gen_random_uuid()는 v4(완전 무작위)를 만듭니다. 정렬 이득이 전혀 없습니다. 정렬 가능한 키가 필요하면 반드시 uuidv7()를 써야 합니다. uuidv7()는 PG18부터 코어에 내장됐고, 그 이전 버전에서는 확장(pg_uuidv7 등)이나 애플리케이션 코드로 만들어야 했습니다.
그래서 정수 키와 UUID 키, 뭘 골라야 하나? 단일 DB에 평범한 서비스라면 IDENTITY 정수 키가 여전히 가장 가볍고 빠릅니다(4~8바이트 vs 16바이트). "여러 시스템이 각자 ID를 만들어야 한다", "ID를 외부에 노출해도 추측이 불가능해야 한다" 중 하나라도 해당되면 uuidv7()를 쓰세요. 기준은 취향이 아니라 요구사항입니다.

timestamptz 함정 — 가장 자주 터지는 지뢰

시간 컬럼을 만들 때 무심코 timestamp라고 적기 쉽습니다. 이름도 자연스럽고, 넣고 빼는 데 아무 문제가 없어 보이니까요. 그런데 이건 타임존을 전혀 모르는 타입입니다. 서비스가 국내에만 있어도 사고가 납니다 — 서버는 UTC로 돌고 개발자는 KST로 보는 순간부터요.

timestamp는 "벽시계 사진"일 뿐입니다. 2026-06-09 11:04라는 값만 덜렁 저장할 뿐, 그게 어느 나라의 11시인지는 기록하지 않습니다. 서버와 클라이언트의 타임존이 다르면 같은 값이 서로 다른 순간을 가리키게 되고, 시간이 소리 없이 어긋납니다.

timestamptz는 "절대 시각"을 저장합니다. 입력을 받으면 내부적으로 UTC로 변환해 저장하고, 조회할 때 보는 사람의 세션 타임존으로 환산해 보여줍니다. (헷갈리기 쉬운 점: 이름과 달리 타임존 자체를 "저장"하지는 않습니다. UTC로 정규화해 두고 표시할 때 변환하는 방식입니다.)

말로는 감이 잘 안 오니 직접 보여드리겠습니다. 같은 순간을 두 타입에 각각 넣어두고, 세션 타임존만 바꿔서 조회한 실제 결과입니다.

sqlstudy_db=# — timestamp vs timestamptz (타임존 전환)
CREATE TABLE log (
  at_wrong timestamp,      -- 타임존 정보 없음 (지뢰)
  at_right timestamptz     -- UTC로 저장, 세션 타임존으로 표시
);
INSERT INTO log VALUES (now(), now());

-- (1) 기본 세션 타임존 (컨테이너 기본값 Etc/UTC)
SELECT * FROM log;
--           at_wrong          |           at_right
-- ----------------------------+-------------------------------
--  2026-06-09 11:12:20.558484 | 2026-06-09 11:12:20.558484+00
--  ↑ 여기까진 둘이 똑같아 보인다

-- (2) 세션 타임존을 한국으로 바꾸면 — 함정이 드러난다
SET timezone TO 'Asia/Seoul';
SELECT * FROM log;
--           at_wrong          |           at_right
-- ----------------------------+-------------------------------
--  2026-06-09 11:12:20.558484 | 2026-06-09 20:12:20.558484+09
--              ↑ 그대로(타임존 무시)         ↑ +09로 환산 표시

차이가 보이시나요? at_right는 "이건 세계시로 11시 12분이고, 한국에서 보면 저녁 8시 12분이야"라고 정확히 같은 순간을 상황에 맞게 보여줍니다. 반면 at_wrong은 누가 보든 무조건 11시 12분이라고 우깁니다. 만약 이 값이 "주문 시각"이었다면? 한국 사용자에게는 9시간 전에 주문한 것처럼 표시됩니다.

MySQL — 익숙한 방식

DATETIME(타임존 변환 없이 넣은 값 그대로)과 TIMESTAMP(저장 시 UTC로 변환·조회 시 세션 타임존으로)가 있습니다. 둘 중 무엇을 썼는지가 동작을 가릅니다.

PostgreSQL — 이렇게 다르다

timestamp(타임존 모름)와 timestamptz(UTC 저장 · 세션 타임존 표시)로 나뉩니다. 앱에서는 거의 항상 timestamptz가 정답입니다. 의미상 MySQL의 TIMESTAMP에 가깝습니다.

실무 규칙 한 줄. "그 시각이 지구상의 특정 순간을 가리키는가?"라고 물어보세요. 주문 시각, 로그인 시각, 결제 시각 — 전부 예 → timestamptz. 예외는 타임존과 무관한 벽시계 값뿐입니다. 예를 들어 "매장 오픈 시각 09:00"은 서울 매장이든 뉴욕 매장이든 그 지역의 9시를 뜻하므로 timestamp(또는 time)가 맞습니다. 이런 경우는 생각보다 드뭅니다.

numeric vs float — 돈은 절대 float으로 다루지 않는다

마지막 함정은 소수입니다. float8이나 real은 이진 부동소수점 방식이라, 우리 눈에는 딱 떨어지는 값도 컴퓨터 내부에서는 근사값으로만 표현됩니다. 프로그래밍 언어에서 한 번쯤 겪어봤을 그 유명한 0.1 + 0.2를 Postgres에서 두 타입으로 각각 더해봤습니다.

sqlstudy_db=# — float의 오차 vs numeric의 정확성
SELECT 0.1::float8 + 0.2::float8 AS float_bad,
       0.1::numeric + 0.2::numeric AS numeric_ok;
--       float_bad      | numeric_ok
-- ---------------------+------------
--  0.30000000000000004 |        0.3

float_bad가 0.30000000000000004입니다. 뒤에 붙은 4가 바로 근사 오차죠. 한 번이면 무시할 만하지만, 결제 금액을 수만 건 합산하면 이 오차가 쌓여 실제 장부와 맞지 않게 됩니다. 회계 대사(對査)가 안 맞는 사고의 단골 원인입니다.

비유 — 눈금 자 vs 계산기. float은 눈금이 촘촘한 자입니다. 아주 넓은 범위를 빠르게 재지만, 결국 "가장 가까운 눈금"으로 읽으므로 미세한 오차가 생깁니다. numeric은 자릿수를 하나하나 적어가며 계산하는 계산기입니다. 느리지만 정확히 우리가 쓴 그대로 계산합니다. 그래서 넓은 범위와 속도가 필요한 과학 계산엔 float, 한 원도 틀리면 안 되는 금액엔 numeric입니다.
금액·수량·정밀 계산은 반드시 numeric. numeric(12, 2)처럼 전체 자릿수와 소수 자릿수를 명시하면 의도도 문서화되고 입력 검증까지 됩니다. float8은 측정값(온도·좌표·센서 값)처럼 애초에 오차가 전제된 데이터에만 쓰세요.

자주 쓰는 타입 매핑 (MySQL ↔ PostgreSQL)

MySQL을 쓰던 사람이 Postgres로 넘어올 때 손에 익은 타입 이름을 그대로 쓰려다 헷갈리는 지점들을 모았습니다.

MySQLPostgreSQL메모
INT / BIGINTint / bigint사실상 동일
VARCHAR(n)text 선호Postgres에서는 길이 제한이 성능 이득이 없습니다. 길이 제약이 진짜 비즈니스 규칙일 때만 varchar(n)
TINYINT(1)boolean흉내가 아니라 진짜 불리언 타입 (true/false)
DATETIMEtimestamptz 권장의미상으로는 timestamp에 대응하지만, 앱에서는 타임존 안전을 위해 timestamptz
JSONjsonb인덱싱 가능한 이진 JSON (Week 3)
ENUMenum 타입컬럼 정의가 아니라 CREATE TYPE … AS ENUM으로 타입을 먼저 만듭니다 (Week 3)

왜 Postgres에서는 text를 그냥 써도 되나? MySQL과 달리 Postgres는 varchar(n), varchar, text를 내부적으로 동일한 방식으로 저장합니다. 길이를 제한한다고 공간을 아끼거나 빨라지지 않습니다. 오히려 나중에 길이를 늘리려면 스키마 변경이 필요하죠. 그래서 Postgres 커뮤니티의 기본 권장은 "특별한 이유가 없으면 text"입니다.

셀프 체크

Q 새 테이블의 자동증가 PK, SERIAL과 IDENTITY 중 무엇을?

GENERATED ALWAYS AS IDENTITY입니다. SQL 표준이고, 시퀀스를 컬럼이 소유해 권한 관리가 깔끔하며, 클라이언트가 값을 직접 넣어 시퀀스와 어긋나게 만드는 사고를 구조적으로 차단합니다. SERIAL은 같은 일을 하는 레거시 축약이라 신규 코드에선 피합니다.

Q UUIDv4 대신 UUIDv7을 PK로 쓰면 좋은 이유는?

v7은 앞부분에 생성 시각이 박혀 있어 시간순으로 정렬됩니다. 그래서 인덱스에 항상 맨 끝에 순차적으로 삽입되어 페이지 분할이 줄고 캐시 지역성이 좋아집니다. 덤으로 ORDER BY id가 곧 최신순 정렬이 됩니다. PG18은 uuidv7()가 내장이며, gen_random_uuid()는 v4(무작위)라 이 이득이 없다는 점을 꼭 기억하세요.

Q timestamp와 timestamptz 중 기본 선택은?

timestamptz입니다. 입력을 UTC로 정규화해 저장하고 조회 시 세션 타임존으로 환산해 보여주므로, 서버와 사용자의 타임존이 달라도 같은 순간을 정확히 가리킵니다. timestamp는 타임존을 모르는 "벽시계 사진"이라 어긋납니다. 예외는 "매장 오픈 09:00"처럼 지역마다 다르게 해석돼야 하는 값뿐입니다.

Q 결제 금액 컬럼의 타입은?

numeric(예: numeric(12, 2))입니다. float8은 이진 부동소수점 근사라 0.1 + 0.2 = 0.30000000000000004 같은 오차가 생기고, 이게 대량으로 쌓이면 장부가 맞지 않습니다. float은 오차가 애초에 허용되는 측정값에만 씁니다.
