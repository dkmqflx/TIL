DDL · 제약 · 기본키 전략 — 무결성을 DB에게 맡기기

CREATE TABLE은 누구나 씁니다. 실력 차이는 제약(constraint)에서 갈립니다 — 데이터를 지키는 일을 앱이 아니라 DB에게 맡기는 것이죠.

한 줄 요약. 앱 코드는 버그가 나고 동시 요청에 뚫립니다. 하지만 DB에 걸어둔 제약은 어떤 경로로 들어와도 절대 뚫리지 않습니다. 그래서 무결성 규칙은 데이터 옆(DB)에 두는 것이 원칙입니다.

학습 목표

  • NOT NULL·UNIQUE·CHECK·FK·DEFAULT로 무결성을 DB에 맡긴다
  • IDENTITY와 uuidv7() 중 어느 기본키를 고를지 판단 기준을 갖는다
  • 시퀀스가 왜 번호를 건너뛰는지(gap) 이해하고 불안해하지 않는다
  • (PG18) EXCLUDE·WITHOUT OVERLAPS로 "기간 겹침"을 DB가 막게 한다
🛡️

무결성(Integrity)이란 무엇인가

용어가 거창하지만 뜻은 단순합니다. 무결성이란 "데이터가 정해진 규칙을 항상 지키고 있는 상태" — 쉽게 말해 데이터를 믿을 수 있는 상태를 말합니다.

비유 — 택배 주소록. 주소록에 전화번호 칸이 있다고 해봅시다. 누군가 전화번호 칸에 "안녕하세요"라고 적어놓거나, 같은 사람이 두 번 등록돼 있거나, 이미 탈퇴한 회원 앞으로 주문이 남아 있다면 — 이 주소록은 무결성이 깨진 상태입니다. 데이터가 있긴 한데 믿을 수가 없죠. 반대로 모든 칸이 규칙대로 채워져 있다면 무결성이 지켜진 상태입니다.

이 규칙들을 DB에 선언해 둔 것이 제약(constraint)입니다. 우리가 일상적으로 말하는 요구사항이 제약으로 그대로 번역됩니다.

말로 하면제약으로 쓰면
이메일은 중복될 수 없다UNIQUE
이메일은 반드시 입력해야 한다NOT NULL
나이는 0 이상 150 미만이어야 한다CHECK (age >= 0 AND age < 150)
주문의 고객 ID는 실제로 존재하는 고객이어야 한다FOREIGN KEY … REFERENCES
안 적으면 'active'로 시작한다DEFAULT 'active'

이런 제약을 걸어두면, 규칙을 어기는 데이터가 들어오려 할 때 DB가 자동으로 거부합니다. 애플리케이션이 무엇을 하든, 어떤 도구로 접속했든 상관없이요. 이제 하나씩 직접 만들어 봅시다.

CREATE TABLE과 컬럼 제약

테이블을 만들 때 컬럼 이름과 타입만 적고 넘어가기 쉽지만, 진짜 중요한 건 그 뒤에 붙는 제약입니다. 아래 users 테이블에는 다섯 가지 제약이 모두 들어 있습니다.

sqlstudy_db=# — 제약이 붙은 users 테이블
CREATE TABLE users (
  id          int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email       text NOT NULL UNIQUE,                 -- 비어 있을 수 없고 중복 불가
  age         int CHECK (age >= 0 AND age < 150),   -- 값의 범위를 DB가 강제
  status      text NOT NULL DEFAULT 'active',       -- 미지정 시 기본값
  created_at  timestamptz NOT NULL DEFAULT now()
);

INSERT INTO users (email, age) VALUES ('a@ex.com', 30), ('b@ex.com', 25);
SELECT id, email, age, status FROM users ORDER BY id;
--  id |  email   | age | status
-- ----+----------+-----+--------
--   1 | a@ex.com |  30 | active
--   2 | b@ex.com |  25 | active

우리는 status를 넣은 적이 없는데 active가 채워졌습니다. DEFAULT가 한 일이죠. 그럼 이번엔 일부러 규칙을 어겨보겠습니다. DB가 어떻게 막는지 보세요.

sqlstudy_db=# — 제약 위반은 DB가 막는다 (의도적 에러)
INSERT INTO users (email, age) VALUES ('a@ex.com', 40);
-- ERROR:  duplicate key value violates unique constraint "users_email_key"
--         ↑ 이미 있는 이메일이라 거부

INSERT INTO users (email, age) VALUES ('c@ex.com', -5);
-- ERROR:  new row for relation "users" violates check constraint "users_age_check"
--         ↑ 나이가 음수라 거부

주목할 점은 에러 메시지가 어떤 제약을 위반했는지 이름까지 알려준다는 것입니다(users_email_key, users_age_check). 애플리케이션에서 이 이름을 잡아 "이미 사용 중인 이메일입니다" 같은 친절한 메시지로 바꿔줄 수 있습니다.

"중복 체크는 앱에서 하면 되지 않나요?" — 안 됩니다. 앱에서 하는 검사에는 두 가지 구멍이 있습니다.

① 버그. 검사 코드를 넣는 걸 깜빡한 경로가 하나만 있어도 뚫립니다. 관리자 페이지, 배치 스크립트, 급하게 짠 마이그레이션 코드…

② 동시성. 이게 더 무섭습니다. 두 사람이 같은 순간에 같은 이메일로 가입한다고 해봅시다. 요청 A가 "중복 없음" 확인 → 요청 B도 "중복 없음" 확인 → A가 INSERT → B가 INSERT. 두 코드 모두 검사를 통과했는데 중복이 들어갔습니다. 이걸 경쟁 상태(race condition)라고 하고, 앱 코드만으로는 원천적으로 막을 수 없습니다.

DB에 UNIQUE를 걸어두면 이 두 경우 모두 DB가 마지막 방어선으로 막아줍니다. 앱 검사는 "사용자에게 친절한 메시지를 주기 위해" 하고, 진짜 방어는 DB가 — 이게 실무의 정석입니다.

🔗

외래키(FK)와 참조 무결성

orders 테이블의 user_id가 실제로 존재하는 users.id만 가리키도록 강제하는 것이 외래키(FOREIGN KEY)입니다. 이걸 걸어두면 "없는 회원의 주문"이라는 유령 데이터가 애초에 만들어지지 않습니다.

여기서 한 가지 더 정해야 할 게 있습니다. 부모(회원)가 삭제되면 자식(주문)은 어떻게 할까? 이걸 ON DELETE로 지정합니다.

ON DELETE 옵션부모가 삭제되면…어울리는 상황
CASCADE자식 행도 함께 삭제회원 탈퇴 시 그 회원의 장바구니·알림 등 부모 없이 의미가 없는 데이터
SET NULL자식의 FK 컬럼을 NULL로담당자가 퇴사해도 업무는 남아야 하는 경우
RESTRICT (기본)자식이 있으면 삭제 자체를 거부주문 이력이 있는 회원은 함부로 못 지우게 막고 싶을 때

CASCADE가 실제로 어떻게 작동하는지 눈으로 봅시다.

sqlstudy_db=# — FK + ON DELETE CASCADE 시연
CREATE TABLE orders (
  id        int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id   int NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  amount    numeric(10,2) NOT NULL CHECK (amount > 0)
);
INSERT INTO orders (user_id, amount) VALUES (1, 9.99), (1, 5.00), (2, 12.50);

-- user 1을 지우면 그 주문도 함께 사라진다
DELETE FROM users WHERE id = 1;
SELECT * FROM orders ORDER BY id;
--  id | user_id | amount
-- ----+---------+--------
--   3 |       2 |  12.50
-- (1 row)   ↑ user_id=1의 주문 두 건이 CASCADE로 함께 삭제됨
CASCADE는 편하지만 위험하기도 합니다. 회원 한 명을 지웠는데 그 회원의 주문·결제·리뷰가 연쇄적으로 전부 사라질 수 있습니다. 게다가 자식의 자식까지 타고 내려가므로, 실제로 무엇이 지워질지 예측하기 어려워지죠. 그래서 회계·결제처럼 지워지면 안 되는 데이터가 걸려 있다면 RESTRICT(기본)로 막아두고, 삭제 대신 deleted_at 컬럼을 채우는 소프트 삭제를 쓰는 경우가 많습니다.
MySQL — 익숙한 방식

InnoDB 엔진에서 FK를 지원합니다(REFERENCES … ON DELETE CASCADE). 문법은 거의 같습니다. 다만 과거 MyISAM 엔진은 FK 문법을 받아들이기만 하고 실제로 강제하지 않는 함정이 있었습니다.

PostgreSQL — 이렇게 다르다

엔진 구분 자체가 없으므로 항상 FK를 강제합니다. "걸어뒀는데 안 지켜지는" 상황이 존재하지 않습니다. 문법은 표준 SQL을 따르므로 InnoDB와 거의 동일합니다.

기본키 전략 — IDENTITY vs uuidv7()

기본키(Primary Key)는 각 행을 구별하는 고유한 번호표입니다. 선택지는 크게 두 가지고, 이건 취향 문제가 아니라 요구사항으로 결정되는 문제입니다.

상황권장 기본키이유
대부분의 경우 — 기본 선택IDENTITY4~8바이트로 작고 빠르며, 인덱스에도 순차적으로 쌓임
ID가 외부에 노출될 때
URL(/posts/5), API 응답 JSON		uuidv7()숫자면 "다음은 6번이겠네" 추측이 가능 — 긴 UUID는 추측 불가
여러 서버·기기가 각자 ID를 만들 때uuidv7()DB에 물어보지 않고 만들어도 겹치지 않음

두 번째 이유가 왜 중요한지는 실제 사고 사례로 보면 바로 이해됩니다.

왜 외부에 노출되는 숫자 ID가 위험한가. URL이든 API 응답이든, 클라이언트에 ID가 전달되는 순간 문제가 생깁니다.

/posts/5를 본 사람은 "그럼 /posts/6도 있겠네"를 즉시 압니다. 권한 검사가 한 군데라도 허술하면, 1부터 하나씩 올려가며 남의 데이터를 전부 긁어갈 수 있습니다(이걸 IDOR 취약점이라고 부릅니다). 심지어 취약점이 없어도, 오늘 가입한 회원 ID가 10230이고 한 달 뒤 10450이라면 "이 서비스 한 달 신규 가입자는 220명"이라는 영업 정보가 그냥 새어나갑니다.

uuidv7()로 바꾸면 { "id": "019eac43-d675-7f08-…" }처럼 보여 다음 ID를 예측할 방법이 없습니다.

ID가 어디까지 나가나uuidv7()이 필요한가
내부 조인·집계에만 사용, 밖으로 안 나감❌ IDENTITY면 충분
URL 파라미터 (/posts/5)✅ 필요
API 응답 JSON에 포함✅ 필요
비유 — 여러 지점이 각자 사번을 발급하면. 서울 지점과 부산 지점이 각자 직원 번호를 매기면 둘 다 "1번, 2번, 3번…"을 만들어 번호가 겹칩니다. 숫자 IDENTITY는 이걸 피하려고 반드시 DB 한 곳에 "지금 몇 번까지 나갔어?"를 물어봐야 합니다. 서버가 여러 대면 그 문의가 병목이 되죠. 반면 uuidv7()은 "현재 시각 + 무작위 값"으로 만들기 때문에, 각자 독립적으로 만들어도 현실적으로 겹칠 확률이 없습니다.

그리고 uuidv7()은 무작위처럼 보이지만 앞부분에 생성 시각이 박혀 있어 만들어진 순서대로 정렬됩니다. 아래 결과에서 두 행의 앞부분 019eac43이 같은 것이 그 증거입니다.

sqlstudy_db=# — uuidv7() 기본키
CREATE TABLE membership (
  id      uuid PRIMARY KEY DEFAULT uuidv7(),
  label   text NOT NULL
);
INSERT INTO membership (label) VALUES ('gold'), ('silver');
SELECT id, label FROM membership ORDER BY id;
--                   id                  | label
-- --------------------------------------+--------
--  019eac43-d675-7f08-b52c-2df0e1d35a48 | gold
--  019eac43-d676-71fa-92bf-695880d95451 | silver
--  ^^^^^^^^ 같은 시각 접두사 → 생성 순서대로 정렬됨
🎰

시퀀스 — 그리고 번호가 건너뛰는 이유

IDENTITY 컬럼 뒤에는 사실 시퀀스(SEQUENCE)라는 객체가 숨어서 "다음 번호"를 발급하고 있습니다. 시퀀스는 번호표 뽑는 기계라고 생각하면 정확합니다 — nextval을 호출할 때마다 100, 101, 102…를 순서대로 내어줍니다.

sqlstudy_db=# — IDENTITY 뒤의 시퀀스 확인 + 직접 만들기
-- IDENTITY 컬럼이 소유한 시퀀스 이름 확인
SELECT pg_get_serial_sequence('users', 'id');
--     pg_get_serial_sequence
-- ---------------------------
--  public.users_id_seq

-- 시퀀스를 직접 만들어 번호 뽑기
CREATE SEQUENCE ticket_seq START 100 INCREMENT 1;
SELECT nextval('ticket_seq');   -- 100 (다음 값 발급)
SELECT nextval('ticket_seq');   -- 101
SELECT currval('ticket_seq');   -- 101 (이 세션이 마지막으로 받은 값)

여기서 초보자가 반드시 한 번은 놀라는 현상이 있습니다. id가 1, 2, 3이 아니라 1, 2, 5, 9처럼 뛰어 있는 것입니다. 버그가 아닙니다. 의도된 설계입니다.

비유 — 은행 대기표는 회수하지 않는다. A·B·C가 창구 번호표를 뽑아 101·102·103번을 받았습니다. 그런데 A가 "아, 서류를 안 가져왔네" 하고 그냥 나가버렸습니다(= 트랜잭션 롤백). 기계가 101번을 회수해서 다음 사람에게 다시 줄까요? 아닙니다. 다음 사람은 104번을 받고 101번은 그냥 빈 자리로 남습니다.

왜 이렇게 만들었을까요? 만약 "롤백되면 번호를 회수한다"고 설계하면, 동시에 100명이 번호를 뽑을 때 기계가 매번 잠기며 순서를 맞춰야 합니다. 그러면 시퀀스가 전체 시스템의 병목이 되죠. 그래서 일부러 "뽑으면 그걸로 끝"으로 만들었습니다. 속도를 얻고 연속성을 포기한 트레이드오프입니다.

gap이 생겨도 괜찮은 이유. 자동차 번호판이 12가 1234, 12가 1236으로 1235가 빠져 있어도 차를 구별하는 데 아무 문제가 없습니다. ID의 역할은 "각 행을 유일하게 식별하는 것"이지 연속된 번호를 매기는 게 아닙니다. 만약 "1번부터 빠짐없이 연속된 번호"가 정말 필요하다면(예: 세금계산서 일련번호), 그건 기본키가 아니라 별도의 비즈니스 컬럼으로 따로 관리해야 합니다.
⛔

제외 제약(EXCLUDE)과 temporal — "겹치면 안 돼"를 DB에게

지금까지 배운 UNIQUE는 "값이 완전히 같으면 안 됨"을 막습니다. 그런데 현실에는 UNIQUE로는 표현할 수 없는 규칙이 있습니다. 대표적인 게 예약 시스템입니다.

비유 — 회의실 예약 충돌. 팀장 A가 회의실 A를 10:00~11:00으로 예약했습니다. 이제 팀원 B가 회의실 A를 10:30~11:30으로 예약하려 합니다. 막아야겠죠.

그런데 이걸 UNIQUE로 어떻게 표현할까요? 방 이름에 UNIQUE를 걸면 그 방은 평생 한 번밖에 예약 못 합니다. 시간에 걸어도 소용없고요. 필요한 건 "방이 같고(=) 그리고 시간대가 겹치면(&&)"이라는 두 조건의 조합입니다. 이걸 표현하는 게 EXCLUDE입니다.

참고로 B가 11:00~12:00으로 예약하면? 딱 붙어 있지만 겹치지는 않으므로 허용됩니다.

본격적인 코드로 들어가기 전에, 낯선 부품 세 개를 먼저 풀어두겠습니다.

부품 ① tsrange — 시작과 끝을 하나로 묶은 타입

tsrange는 timestamp range의 줄임말로, 시작 시각과 끝 시각을 컬럼 두 개로 나누는 대신 하나의 값으로 묶은 타입입니다.

왜 묶을까요? started_at과 ended_at으로 나눠 두면 "두 예약이 겹치는가?"를 검사하는 SQL이 (a.start < b.end AND b.start < a.end)처럼 지저분해집니다. tsrange로 묶으면 && 연산자 하나로 끝납니다.

괄호의 의미가 중요합니다. [10:00, 11:00)에서 [는 10시를 포함, )는 11시를 미포함한다는 뜻입니다(수학의 반열린 구간). 11시 정각에 다음 예약이 시작할 수 있는 이유가 바로 이것 — 앞 예약이 11시를 포함하지 않으니 겹치지 않습니다.
비교결과이유
[10:00, 11:00) && [10:30, 11:30)true 겹침10:30~11:00 구간이 공유됨
[10:00, 11:00) && [11:00, 12:00)false 안 겹침딱 붙어 있지만 공유하는 시각이 없음

부품 ② USING gist — 왜 기본 인덱스로는 안 되나

Postgres의 기본 인덱스인 B-tree는 전화번호부와 같습니다. 값을 한 줄로 정렬해 두니 =, <, > 같은 크기 비교에 강합니다. 그런데 "두 범위가 겹치는가?"는 시작값과 끝값을 동시에 봐야 판단할 수 있어서, 한 줄 정렬로는 답이 안 나옵니다.

GiST는 지도에 가깝습니다. 데이터를 다차원 공간에 배치해 색인하므로 "겹치는 영역 찾기"를 빠르게 할 수 있습니다.

인덱스비유잘하는 연산
B-tree (기본)전화번호부 (가나다 정렬)= < > — 값 크기 비교
GiST지도 (공간 색인)&& — 범위·도형 겹침 검사

부품 ③ btree_gist 확장 — GiST에게 =도 가르치기

CREATE EXTENSION은 PostgreSQL에 플러그인을 설치하는 명령입니다(Node의 npm install, Python의 pip install과 같은 개념). IF NOT EXISTS는 "이미 있으면 에러 내지 말고 넘어가"라는 뜻입니다.

왜 필요할까요? 우리 조건은 하나의 GiST 인덱스가 =와 &&를 동시에 처리해야 합니다. GiST는 범위 겹침(&&)은 원래 잘하지만 텍스트의 동등 비교(=)는 못 합니다. btree_gist가 그걸 가르쳐주는 플러그인입니다.

연산btree_gist 없을 때btree_gist 있을 때
&& (범위 겹침)GiST 가능 ✅GiST 가능 ✅
= (텍스트 같음)GiST 불가 ❌GiST 가능 ✅

이제 조립해 봅시다

핵심 줄인 EXCLUDE USING gist (room WITH =, during WITH &&)는 이렇게 읽습니다. "GiST 인덱스를 써서, room이 같고(=) 그리고 during이 겹치는(&&) 행이 이미 있으면 거부하라." 두 조건이 동시에 참일 때만 막습니다 — 방만 같고 시간이 다르면 OK, 시간이 겹쳐도 다른 방이면 OK입니다.

sqlstudy_db=# — EXCLUDE USING gist (시간대 겹침 방지)
CREATE EXTENSION IF NOT EXISTS btree_gist;  -- 범위와 = 를 같이 쓰려면 필요

CREATE TABLE room_booking (
  id      int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  room    text NOT NULL,
  during  tsrange NOT NULL,                         -- 시작~끝 범위
  EXCLUDE USING gist (room WITH =, during WITH &&)  -- 방이 같고 시간이 겹치면 거부
);

INSERT INTO room_booking (room, during)
  VALUES ('A', '[2026-06-09 10:00, 2026-06-09 11:00)');   -- OK

INSERT INTO room_booking (room, during)
  VALUES ('A', '[2026-06-09 11:00, 2026-06-09 12:00)');   -- 딱 붙음, 안 겹침 → OK

-- 10:30~11:30은 기존 10:00~11:00과 겹침 → 거부
INSERT INTO room_booking (room, during)
  VALUES ('A', '[2026-06-09 10:30, 2026-06-09 11:30)');
-- ERROR:  conflicting key value violates exclusion constraint

이 제약의 가치는 어떤 경로로 들어와도 막힌다는 데 있습니다. 앱에서 "빈 시간인지" 확인하고 저장하는 방식은, 두 요청이 동시에 들어오면 둘 다 "빈 시간이네"라고 판단해 이중 예약이 만들어집니다. DB 제약은 그 틈을 원천 차단합니다.

PG18의 WITHOUT OVERLAPS — 같은 개념을 기본키에

PG18 비유 — 상품 가격 이력. 상품 1번의 가격이 1~6월엔 10,000원, 6~12월엔 12,000원이라고 합시다. 두 행 모두 product_id = 1이지만 기간이 다르니 정상입니다. 그런데 누군가 실수로 "3~9월에 11,000원"을 추가하면? 기존 두 기간과 모두 겹쳐 "6월의 가격은 얼마인가?"에 답이 두 개가 됩니다. WITHOUT OVERLAPS를 기본키에 붙이면 이런 겹침을 DB가 자동으로 막습니다.
sqlstudy_db=# — (PG18) temporal PK · WITHOUT OVERLAPS
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE price_history (
  product_id  int,
  valid_at    daterange,                                 -- 유효 기간
  price       numeric(10,2) NOT NULL,
  PRIMARY KEY (product_id, valid_at WITHOUT OVERLAPS)    -- 같은 상품끼리 기간 겹침 금지
);
INSERT INTO price_history VALUES (1, '[2026-01-01, 2026-06-01)', 10.00);  -- 1~6월 OK
INSERT INTO price_history VALUES (1, '[2026-06-01, 2026-12-01)', 12.00);  -- 6~12월 인접 OK

SELECT * FROM price_history ORDER BY valid_at;
--  product_id |        valid_at         | price
-- ------------+-------------------------+-------
--           1 | [2026-01-01,2026-06-01) | 10.00
--           1 | [2026-06-01,2026-12-01) | 12.00

-- 3~9월은 기존 두 기간과 모두 겹침 → 거부
INSERT INTO price_history VALUES (1, '[2026-03-01, 2026-09-01)', 11.00);
-- ERROR:  conflicting key value violates exclusion constraint "price_history_pkey"
✅

셀프 체크

Q 무결성 제약을 앱이 아니라 DB에 두는 이유는?

앱에는 버그와 경쟁 상태가 있기 때문입니다. 특히 두 요청이 동시에 "중복 없음"을 확인한 뒤 둘 다 INSERT하면, 앱 코드가 아무리 완벽해도 중복이 들어갑니다. UNIQUE·CHECK·FK를 DB에 두면 어떤 경로로 들어와도 DB가 마지막 방어선으로 막아줍니다.

Q IDENTITY와 uuidv7() 중 무엇을 기본키로?

기본은 작고 빠른 GENERATED ALWAYS AS IDENTITY입니다. ID가 URL이나 API 응답으로 외부에 노출되거나(순번 추측·정보 유출 방지), 여러 서버·기기가 각자 ID를 생성해야 하면 uuidv7()를 씁니다. v7은 시간순 정렬이라 인덱스에도 친화적입니다.

Q id가 1, 2, 5, 9처럼 건너뛰는데 버그인가요?

아니요, 정상입니다. 시퀀스는 트랜잭션을 따르지 않아서 롤백돼도 뽑은 번호를 회수하지 않습니다(은행 대기표와 같음). 회수하도록 만들면 동시 요청마다 잠금이 걸려 심각한 병목이 되기 때문에 의도적으로 이렇게 설계됐습니다. ID의 역할은 식별이지 연속 번호 매기기가 아닙니다.

Q UNIQUE로 예약 시간 겹침을 막을 수 있나요?

없습니다. UNIQUE는 "값이 완전히 같으면 안 됨"만 표현할 수 있는데, 예약 충돌은 "방이 같고(=) 그리고 시간이 겹치면(&&)"이라는 두 조건의 조합이기 때문입니다. 이럴 때 EXCLUDE USING gist (room WITH =, during WITH &&)를 씁니다. PG18에서는 WITHOUT OVERLAPS로 기본키에 직접 붙일 수도 있습니다.
