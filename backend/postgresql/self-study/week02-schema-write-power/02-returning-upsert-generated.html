RETURNING · UPSERT · MERGE — 쓰기 측 강력 기능

쓰기 한 번에 결과까지 받아오고(RETURNING), "있으면 수정 없으면 삽입"을 한 문장으로 끝내는(ON CONFLICT) — MySQL에서 넘어오면 가장 반가운 Postgres의 무기들입니다.

한 줄 요약. 이 레슨의 기능들은 전부 "여러 번 왕복하던 걸 한 문장으로 줄이는" 도구입니다. 왕복이 줄면 빨라지기도 하지만, 더 중요한 건 그 사이에 끼어드는 경쟁 상태가 사라진다는 점입니다.

학습 목표

  • RETURNING으로 왕복을 줄이고, (PG18) OLD/NEW로 변경 전후를 한 번에 받는다
  • UPSERT(ON CONFLICT)로 "있으면 수정, 없으면 삽입"을 원자적으로 처리한다
  • MERGE와 ON CONFLICT를 언제 각각 쓸지 판단한다
  • 생성 컬럼의 STORED와 (PG18 기본) virtual 차이를 안다
↩️

RETURNING — 쓰기와 결과를 한 번에

흔한 상황입니다. 새 상품을 등록한 뒤 "방금 만들어진 id가 뭐지?"를 알아야 합니다. 보통은 INSERT를 날리고, 그 다음 SELECT를 한 번 더 날려서 찾아옵니다. Postgres에서는 그럴 필요가 없습니다.

비유 — 주문하자마자 번호표를 받는 것. 음식점에서 주문한 뒤 "저기요, 제 주문번호가 몇 번이에요?"라고 다시 물어봐야 한다면 — 그게 보통의 INSERT + SELECT 패턴입니다(왕복 2번). RETURNING은 주문하는 순간 직원이 바로 "주문번호 A-123입니다"라고 알려주는 것과 같습니다. 왕복이 1번으로 줄고, 그 사이에 다른 요청이 값을 바꿔버릴 위험도 사라집니다.
sqlstudy_db=# — INSERT / DELETE ... RETURNING
INSERT INTO products (sku, price) VALUES ('A-1', 100.00)
  RETURNING id, created_at;          -- 재조회 없이 즉시 받는다
--  id |          created_at
-- ----+-------------------------------
--   1 | 2026-06-09 12:03:07.599352+00

-- DELETE도 "무엇을 지웠는지" 돌려받을 수 있다
DELETE FROM products WHERE sku = 'TMP' RETURNING id, sku;
--  id | sku
-- ----+-----
--   2 | TMP

DELETE … RETURNING이 특히 유용합니다. 지우기 전에 SELECT로 확인하고 DELETE하는 두 단계 대신, 지우면서 동시에 무엇이 지워졌는지 기록할 수 있으니까요.

PG18 — 변경 전후를 한 번에

PG18에서는 한 걸음 더 나갔습니다. UPDATE의 변경 전 값(OLD)과 변경 후 값(NEW)을 동시에 돌려받을 수 있습니다.

비유 — 은행 이체 확인서. 이체하면 "이전 잔액 1,000,000원 → 이후 잔액 900,000원"이 한 장에 찍혀 나오죠. PG18 이전에는 이걸 얻으려면 UPDATE 전에 미리 SELECT해서 이전 값을 챙겨둬야 했습니다. 그런데 그 사이에 다른 트랜잭션이 값을 바꾸면 확인서가 거짓말이 됩니다. RETURNING old.price, new.price는 한 문장 안에서 둘 다 가져오므로 그런 틈이 없습니다.
sqlstudy_db=# — (PG18) RETURNING OLD / NEW
UPDATE products SET price = price * 1.10 WHERE sku = 'A-1'
  RETURNING old.price AS old_price, new.price AS new_price;
--  old_price | new_price
-- -----------+-----------
--     100.00 |    110.00
PG18 RETURNING old.*, new.*처럼 그대로 쓰면 컬럼명이 겹칩니다(price가 둘). 결과를 읽는 쪽에서 혼란스러우니 위 예처럼 AS old_price, AS new_price로 별칭을 주는 편이 좋습니다.
MySQL — 익숙한 방식

INSERT 후 SELECT LAST_INSERT_ID();로 id만 받고, 다른 컬럼이 더 필요하면 SELECT … WHERE id = ?로 한 번 더 조회합니다. UPDATE 전후 값은 별도 SELECT로 직접 챙겨야 합니다. 표준 RETURNING은 없습니다.

PostgreSQL — 이렇게 다르다

INSERT … RETURNING id, created_at처럼 한 문장으로 받습니다. 왕복과 경쟁 상태를 동시에 없앱니다. PG18은 UPDATE에서 old.*/new.*까지 즉시 돌려줍니다.

🔀

UPSERT — INSERT ... ON CONFLICT

"있으면 수정, 없으면 삽입"은 워낙 자주 나오는 요구라 UPSERT(UPDATE + INSERT)라는 별명까지 붙었습니다. Postgres는 이걸 INSERT … ON CONFLICT로 한 문장, 원자적으로 처리합니다.

비유 — 소셜 로그인. 카카오 로그인을 처리한다고 해봅시다. "이 이메일로 가입한 회원이 이미 있으면 마지막 로그인 시각만 갱신, 없으면 새 회원으로 등록." 코드로 짜면 SELECT → 있으면 UPDATE, 없으면 INSERT로 분기해야 하고, 동시에 두 번 로그인 요청이 오면 둘 다 "없네"라고 판단해 회원이 두 개 만들어집니다. ON CONFLICT는 이걸 DB가 원자적으로 처리해 줍니다.

먼저 "무엇을 충돌로 볼지"를 정해야 합니다

ON CONFLICT는 어떤 조건에서 충돌인지를 먼저 지정해야 합니다. 두 가지 방식이 있습니다.

방식언제 쓰나
ON CONFLICT (sku)특정 컬럼의 UNIQUE 제약 기준. 가장 흔한 형태
ON CONFLICT ON CONSTRAINT 제약이름복합 UNIQUE(컬럼 2개 이상)처럼 컬럼 하나로 특정할 수 없을 때

충돌이 없으면 ON CONFLICT 절은 그냥 무시되고 평범한 INSERT가 됩니다. 충돌이 있을 때만 DO UPDATE나 DO NOTHING이 발동합니다.

EXCLUDED — 문 앞에서 거절당한 행

EXCLUDED는 "삽입하려다 충돌로 거절당한 그 행"을 가리키는 가상 테이블입니다. 이름이 헷갈리는데, "제외된(excluded) 행" = "못 들어간 행"이라고 읽으면 됩니다. 그래서 DO UPDATE SET qty = inventory.qty + EXCLUDED.qty는 "기존 행의 수량에, 들어오려던 행의 수량을 더하라"가 됩니다. 기존 값과 새 값을 자유롭게 조합할 수 있다는 게 핵심입니다.
sqlstudy_db=# — ON CONFLICT DO UPDATE / DO NOTHING
INSERT INTO inventory (sku, qty) VALUES ('A-1', 10)
  ON CONFLICT (sku) DO UPDATE SET qty = inventory.qty + EXCLUDED.qty;
-- sku='A-1'이 아직 없었으므로 그냥 삽입 (qty=10)

INSERT INTO inventory (sku, qty) VALUES ('A-1', 5)
  ON CONFLICT (sku) DO UPDATE SET qty = inventory.qty + EXCLUDED.qty;
-- 이번엔 충돌 → 10 + 5 = 15 로 갱신
SELECT * FROM inventory;
--  sku | qty
-- -----+-----
--  A-1 |  15

-- DO NOTHING: 충돌하면 조용히 무시(중복 삽입 방지)
INSERT INTO inventory (sku, qty) VALUES ('A-1', 999)
  ON CONFLICT (sku) DO NOTHING;
--  sku | qty
-- -----+-----
--  A-1 |  15      ← 999는 무시됨

DO NOTHING은 "이미 있으면 그냥 넘어가"라는 뜻입니다. 좋아요 버튼을 두 번 눌러도 한 번만 반영되어야 하는 경우, 혹은 여러 번 실행해도 결과가 같아야 하는(멱등한) 배치 작업에 잘 맞습니다.

실무에서 자주 쓰는 EXCLUDED 패턴을 정리하면 이렇습니다.

sqlstudy_db=# — EXCLUDED 활용 패턴 5가지
-- 1. 새 값으로 덮어쓰기 (가장 단순)
ON CONFLICT (sku) DO UPDATE SET qty = EXCLUDED.qty;

-- 2. 누적하기 (기존 + 새 값) — 재고 입고 등
ON CONFLICT (sku) DO UPDATE SET qty = inventory.qty + EXCLUDED.qty;

-- 3. 더 큰 값만 유지 — 최고 점수 갱신 등
ON CONFLICT (sku) DO UPDATE SET qty = GREATEST(inventory.qty, EXCLUDED.qty);

-- 4. 조건부 업데이트 (새 값이 더 클 때만 반영)
ON CONFLICT (sku) DO UPDATE SET qty = EXCLUDED.qty
  WHERE EXCLUDED.qty > inventory.qty;

-- 5. 복합 UNIQUE 제약 기준으로 충돌 감지
ON CONFLICT ON CONSTRAINT user_product_unique DO UPDATE SET qty = EXCLUDED.qty;
MySQL — 익숙한 방식

INSERT … ON DUPLICATE KEY UPDATE를 씁니다. 새 값은 VALUES(col)(최신 문법은 별칭)로 참조합니다. 어떤 키든 충돌하면 발동하므로, 의도치 않은 제약에서 걸려도 그대로 UPDATE가 실행됩니다.

PostgreSQL — 이렇게 다르다

INSERT … ON CONFLICT (col) DO UPDATE로 어떤 제약에서의 충돌인지 명시해야 합니다. 조금 번거롭지만 의도치 않은 발동을 막아주는 안전장치입니다. 새 값은 EXCLUDED.col로 참조합니다.

🔃

MERGE — 목록 전체를 대조해 병합하기

ON CONFLICT가 "지금 삽입하려는 이 한 행"에 대한 처리라면, MERGE는 "소스 목록 전체를 대상 테이블과 대조"해서 행마다 다르게 처리하는 SQL 표준 명령입니다.

비유 — 새 폰에 연락처 옮기기. 구글에서 내보낸 연락처 파일을 새 폰에 반영한다고 해봅시다. 사람마다 상황이 다릅니다.

  • 이미 저장돼 있는 사람(매칭) → 최신 번호로 덮어씁니다 (WHEN MATCHED → UPDATE)
  • 파일에만 있는 새 사람(미매칭) → 새로 등록합니다 (WHEN NOT MATCHED → INSERT)

코드로 짜면 "파일을 한 줄씩 읽어서 있으면 UPDATE, 없으면 INSERT" 하는 반복문이 됩니다. MERGE는 그 반복문 전체를 SQL 한 문장으로 대체합니다.

문법이 길어 보이지만 키워드 네 개만 알면 읽힙니다.

키워드의미연락처 비유
MERGE INTO 대상실제로 바뀔 테이블내 폰의 연락처
USING 소스 ON 조건비교 기준 데이터와 매칭 조건내보낸 파일, "이름이 같으면 같은 사람"
WHEN MATCHED THEN일치하는 행이 있을 때 → 보통 UPDATE이미 저장된 사람
WHEN NOT MATCHED THEN일치하는 행이 없을 때 → 보통 INSERT새로 추가된 사람
sqlstudy_db=# — MERGE (소스 테이블과 병합)
-- stock_feed(소스): 본사에서 받은 재고 데이터 (A-1=100, B-2=7)
-- inventory(대상): 현재 진열대 데이터 (A-1=15만 있음)

MERGE INTO inventory AS tgt         -- 바꿀 대상 테이블
USING stock_feed AS src             -- 비교할 소스 데이터
  ON tgt.sku = src.sku              -- 매칭 조건: sku가 같으면 같은 상품
WHEN MATCHED THEN                   -- 양쪽 모두 있을 때(A-1)
  UPDATE SET qty = src.qty          --   → 본사 수량으로 덮어쓰기
WHEN NOT MATCHED THEN               -- 소스에만 있고 대상엔 없을 때(B-2)
  INSERT (sku, qty) VALUES (src.sku, src.qty);   -- → 새로 삽입

SELECT * FROM inventory ORDER BY sku;
--  sku | qty
-- -----+-----
--  A-1 | 100      ← MATCHED → 15에서 100으로 갱신
--  B-2 |   7      ← NOT MATCHED → 새로 삽입됨
둘 중 뭘 쓸지 한 문장으로 판단하기. "지금 INSERT하는 이 한 행"의 충돌을 처리하는 거라면 → ON CONFLICT가 훨씬 간결합니다. "외부에서 받은 목록 전체"를 대상 테이블과 대조해 매칭/비매칭별로 다르게 처리해야 한다면 → MERGE가 맞습니다. 단순 upsert 한 건에 MERGE를 쓰면 코드만 길어지고 읽기 어려워집니다.

생성 컬럼 — DB가 알아서 계산해 주는 칸

생성 컬럼(Generated Column)은 DB가 자동으로 계산해 채워주는 컬럼입니다. 예를 들어 "부가세 포함 금액은 항상 price × 1.10"이라면, 앱 코드에서 매번 곱셈을 해서 넣을 필요가 없습니다. 계산식을 한 번 선언해 두면 끝입니다.

비유 — 엑셀의 수식 셀. 엑셀 B열에 =A1*1.10을 넣어두면, A열 값을 바꿀 때마다 B열이 자동으로 따라옵니다. 생성 컬럼이 정확히 이 개념입니다. 앱은 price만 넣고, price_tax는 DB가 채웁니다. 덕분에 계산식이 앱 곳곳에 흩어지지 않고, 실수로 다른 값이 들어갈 수도 없습니다(직접 넣으려 하면 에러입니다 — 항상(ALWAYS) DB가 계산하는 컬럼이니까요).

STORED vs virtual — 계산 결과를 저장하느냐

생성 컬럼에는 두 가지 동작 방식이 있고, 이 차이가 실무에서 꽤 중요합니다.

모드언제 계산디스크인덱스어울리는 용도
STORED쓸 때 (INSERT/UPDATE)저장함 — 조회 빠름가능 ✅검색·정렬 조건으로 쓸 컬럼
virtual PG18 기본읽을 때 (SELECT)저장 안 함 — 공간 절약불가 ❌단순 표시용 계산값

정리하면 이렇게 고르면 됩니다. 이 컬럼으로 WHERE나 ORDER BY를 할 건가? → 인덱스가 필요하니 STORED. 그냥 화면에 보여주기만 할 건가? → virtual로 충분합니다.

sqlstudy_db=# — STORED vs virtual
CREATE TABLE line_item (
  name        text,
  price       numeric(10,2),

  -- STORED: INSERT/UPDATE 시점에 계산해서 디스크에 저장
  price_tax   numeric(10,2) GENERATED ALWAYS AS (price * 1.10) STORED,

  -- virtual(PG18 기본): 키워드 생략 → SELECT할 때마다 계산
  search_name text GENERATED ALWAYS AS (lower(name))
);

-- name, price만 넣으면 나머지 두 컬럼은 DB가 채워줌
INSERT INTO line_item (name, price) VALUES ('Coffee', 100.00);

SELECT * FROM line_item;
--   name  | price  | price_tax | search_name
-- --------+--------+-----------+-------------
--  Coffee | 100.00 |    110.00 | coffee      ← 앱이 넣은 건 name, price뿐

-- 카탈로그로 확인: 's'=stored, 'v'=virtual
SELECT attname, attgenerated FROM pg_attribute
  WHERE attrelid = 'line_item'::regclass AND attgenerated <> '';
--    attname   | attgenerated
-- -------------+--------------
--  price_tax   | s             ← STORED
--  search_name | v             ← virtual (PG18 기본)
PG18 마이그레이션 시 주의. PG18 이전에는 생성 컬럼이 STORED만 지원됐고, 그래서 STORED를 반드시 명시해야 했습니다. PG18부터는 virtual도 가능해졌고 키워드를 생략하면 기본이 virtual입니다. 옛 코드를 옮길 때 STORED를 빠뜨리면 동작이 조용히 달라집니다(인덱스를 못 걸게 되죠). 마이그레이션 시 꼭 확인하세요.

셀프 체크

Q RETURNING이 절약하는 건 무엇인가요?

INSERT 후 "방금 만든 id·created_at"을 알려면 보통 SELECT를 한 번 더 던져야 하는데, RETURNING은 영향받은 행의 컬럼을 그 자리에서 돌려줍니다. 네트워크 왕복이 줄어드는 것도 이득이지만, 더 중요한 건 두 쿼리 사이에 다른 트랜잭션이 끼어들 틈이 없어진다는 점입니다. MySQL은 LAST_INSERT_ID() + 재조회 패턴이 필요합니다.

Q ON CONFLICT의 EXCLUDED는 무엇을 가리키나요?

충돌 때문에 삽입되지 못한 "들어오려던 행"을 가리키는 가상 테이블입니다. DO UPDATE SET qty = inventory.qty + EXCLUDED.qty처럼 기존 행 값과 새 값을 조합할 때 씁니다. DO NOTHING을 쓰면 충돌 시 조용히 넘어갑니다.

Q ON CONFLICT (sku)와 ON CONFLICT ON CONSTRAINT의 차이는?

전자는 컬럼 이름으로 충돌 대상을 지정합니다(그 컬럼에 UNIQUE 제약이 있어야 함). 후자는 제약 이름을 직접 지정하며, 컬럼 2개 이상의 복합 UNIQUE처럼 컬럼 하나로 특정할 수 없을 때 씁니다. 충돌이 없으면 ON CONFLICT 절 자체가 무시되고 평범한 INSERT가 됩니다.

Q 생성 컬럼의 STORED와 virtual, 어떻게 고르나요?

그 컬럼으로 WHERE·ORDER BY를 할 계획이면 STORED입니다(인덱스를 걸 수 있음). 단순히 화면에 보여주기만 한다면 virtual이 공간을 아낍니다. PG18부터는 키워드를 생략하면 기본이 virtual이므로, 인덱스가 필요하면 STORED를 반드시 명시해야 합니다.
