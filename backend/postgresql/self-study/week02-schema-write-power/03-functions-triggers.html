PL/pgSQL 함수 · 트리거 — updated_at과 감사 로그 자동화

updated_at을 앱이 매번 챙기지 말고 DB에게 맡기세요. 그리고 "누가 무엇을 바꿨나"를 기록하는 감사 로그도 DB가 자동으로 남기게 만듭니다.

한 줄 요약. 트리거는 "이 테이블에 이런 일이 생기면 자동으로 이 함수를 실행해"라고 DB에 심어두는 장치입니다. 앱 코드가 한 줄도 없어도 작동하는 게 장점이자 동시에 위험이기도 합니다 — 마지막 섹션에서 그 선을 짚습니다.

학습 목표

  • PL/pgSQL이 SQL과 무엇이 다른지 설명하고, 함수의 기본 구조를 읽는다
  • BEFORE/AFTER와 NEW/OLD의 역할을 구분한다
  • 트리거로 updated_at을 자동 갱신한다
  • 감사 로그 트리거로 변경 이력을 자동 기록한다
  • 트리거를 어디까지 쓰고 어디부터 쓰지 않을지 판단한다
🧰

PL/pgSQL — DB 안에서 도는 작은 프로그래밍 언어

먼저 이름부터 풀어봅시다. PL은 Procedural Language(절차형 언어)의 약자입니다. 즉 "절차를 쓸 수 있게 확장한 pgSQL"이라는 뜻이죠.

왜 확장이 필요했을까요? SQL은 원래 명령만 할 수 있는 언어이기 때문입니다. "이 데이터 가져와", "이 데이터 바꿔"는 되지만, 변수·조건문·반복문 같은 건 없습니다.

할 수 있는 것
SQLSELECT / INSERT / UPDATE / DELETE — 단순 명령
PL/pgSQLSQL + 변수 선언 + IF/ELSE + 반복문 + 예외 처리
비유 — 여러 팀이 공유하는 공용 계산기. "할인가 계산 로직"을 앱 코드에 넣으면, 서버·관리자 도구·배치 스크립트 등 여러 곳에 같은 계산식이 흩어집니다. 정책이 바뀌면 전부 찾아 고쳐야 하고, 하나라도 놓치면 값이 어긋나죠. PL/pgSQL 함수로 DB에 한 번 정의해 두면 모든 곳이 같은 함수를 공유합니다. 계산식을 바꿀 때 DB 함수 하나만 고치면 끝입니다.
솔직한 이야기 — 실무에서 PL/pgSQL을 직접 쓰는 일은 드뭅니다. 대부분의 비즈니스 로직은 앱에 두는 편이 테스트하고 배포하기 쉽거든요. 그래도 이걸 배우는 이유는 트리거 함수를 만들려면 반드시 필요하기 때문입니다. 이 레슨의 나머지가 전부 그 이야기입니다.

함수 구조 뜯어보기

처음 보면 낯선 기호가 많지만, 부품은 여섯 개뿐입니다.

부품역할
CREATE OR REPLACE FUNCTION 이름(인자) RETURNS 타입함수 이름·입력·출력 선언. OR REPLACE는 "이미 있으면 덮어써"
LANGUAGE plpgsql"이 함수는 PL/pgSQL로 썼어"라는 표시
AS $$ … $$본문을 감싸는 달러 인용. 본문 안에 작은따옴표가 아무리 많아도 충돌하지 않게 해준다
DECLARE … ;지역 변수 선언 블록. 변수가 없으면 통째로 생략 가능
BEGIN … END;실제로 실행할 코드
RAISE EXCEPTION '…'오류를 내고 트랜잭션을 롤백시킴
sqlstudy_db=# — PL/pgSQL 함수 기본 구조
CREATE OR REPLACE FUNCTION discounted_price(price numeric, pct numeric)
RETURNS numeric
LANGUAGE plpgsql
AS $$
DECLARE
  result numeric;            -- 지역 변수 선언
BEGIN
  IF pct < 0 OR pct > 100 THEN
    RAISE EXCEPTION '할인율은 0~100 사이여야 합니다: %', pct;  -- 오류 발생
  END IF;
  result := price * (1 - pct / 100);   -- := 는 PL/pgSQL의 대입 연산자
  RETURN round(result, 2);             -- 소수점 둘째 자리까지 반환
END;
$$;

SELECT discounted_price(10000, 30) AS sale_price;
--  sale_price
-- ------------
--     7000.00     ← 10000 × (1 - 30/100) = 7000
=가 아니라 :=입니다. PL/pgSQL에서 =는 비교, :=는 대입입니다. 다른 언어에 익숙하면 자주 틀리는 부분이니 기억해 두세요. 그리고 RAISE EXCEPTION의 %는 뒤에 오는 값이 들어갈 자리입니다(printf의 %s와 같은 역할).

트리거 기본 — BEFORE/AFTER · NEW/OLD

트리거(trigger)는 INSERT/UPDATE/DELETE가 일어날 때 DB가 자동으로 함수를 실행시키는 장치입니다. 앱이 아무것도 하지 않아도, 이벤트가 발생하는 순간 미리 정해둔 함수가 돌아갑니다.

비유 — 편의점 문에 달린 센서. 손님이 문을 통과하면(이벤트) 자동으로 "딩동" 소리가 납니다(함수 실행). 점원이 매번 버튼을 누를 필요가 없죠. 트리거도 똑같습니다. "article 테이블에 UPDATE가 생기면 → set_updated_at() 실행"이라고 심어두면, 앱이 어떤 경로로 수정하든 항상 실행됩니다.
앱이 UPDATE 실행 → DB가 트리거 감지 → 연결된 함수 자동 실행 → 저장

① 타이밍 — BEFORE vs AFTER

트리거를 만들 때 언제 실행할지를 정해야 합니다. 이 선택이 트리거의 성격을 결정합니다.

⏳
BEFORE — 저장되기 직전
행이 디스크에 저장되기 직전에 실행됩니다. 여기서 NEW를 수정하면 수정된 값이 실제로 저장됩니다. "저장될 값을 손보는" 작업(updated_at 채우기 등)에 씁니다.
✅
AFTER — 저장된 이후
행이 저장된 이후에 실행됩니다. 이미 끝났으니 값을 바꿀 수 없고, 대신 "저장됐다는 사실"에 반응하는 부수 작업(감사 로그 기록 등)에 씁니다.

② 데이터 — NEW와 OLD

트리거 함수 안에서는 두 개의 특수 변수로 행에 접근합니다. NEW는 새로 저장될 행, OLD는 변경 전 행입니다. 중요한 건 이벤트에 따라 둘 중 하나가 없을 수 있다는 점입니다.

이벤트OLD (변경 전)NEW (변경 후)왜?
INSERT없음 ❌삽입될 행 ✅새로 생기는 것이라 "이전"이 없음
UPDATE기존 행 ✅수정될 행 ✅둘 다 존재
DELETE삭제될 행 ✅없음 ❌없애는 것이라 "이후"가 없음
없는 쪽을 참조하면 에러가 납니다. INSERT 트리거에서 OLD.title을 읽으려 하면 실패하죠. 그래서 세 이벤트를 한 함수로 처리할 때는 TG_OP(어떤 작업인지)로 분기해야 합니다 — 감사 로그 섹션에서 실제로 그렇게 합니다.
MySQL — 익숙한 방식

CREATE TRIGGER … BEGIN … END 본문에 로직을 직접 적습니다. 구조가 단순한 대신, 같은 로직을 여러 테이블에서 재사용하려면 복사·붙여넣기해야 합니다.

PostgreSQL — 이렇게 다르다

함수와 트리거를 분리합니다. RETURNS trigger 함수를 먼저 만들고, CREATE TRIGGER … EXECUTE FUNCTION f()로 연결합니다. 두 단계라 번거롭지만 하나의 함수를 여러 테이블이 공유할 수 있습니다.

🕰️

updated_at 자동 갱신 트리거 ⭐

실무에서 가장 자주 쓰는 트리거입니다. updated_at은 "이 행이 마지막으로 언제 바뀌었나"를 적어두는 칸인데, 이걸 앱이 챙기려면 UPDATE를 날리는 모든 경로에서 빠짐없이 updated_at = now()를 넣어야 합니다. 경로가 10개면 10곳 모두요. 하나만 빠져도 거짓 시각이 남습니다.

비유 — 자동 날짜 도장 기계. 서류를 고칠 때마다 손으로 날짜 도장을 찍는 대신, 서류함 입구에 자동 도장 기계를 설치하는 겁니다. 어떤 경로로 들어온 서류든 무조건 오늘 날짜가 찍힙니다.

만드는 건 두 부분입니다. ① 도장 기계 자체 = 함수 set_updated_at()("시각을 찍는다"는 동작), ② 기계를 설치할 위치와 타이밍 = 트리거 trg_set_updated_at("article이 수정되기 직전에 돌려라"). 함수만 만들면 아무 일도 일어나지 않습니다 — 트리거로 연결해야 비로소 작동합니다.

sqlstudy_db=# — set_updated_at 함수 + 트리거
-- 1단계: 트리거가 호출할 함수 (RETURNS trigger 필수)
CREATE OR REPLACE FUNCTION set_updated_at()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
  NEW.updated_at := now();   -- 저장 직전에 NEW의 updated_at을 현재 시각으로 교체
  RETURN NEW;                -- 수정된 NEW를 반환해야 이 값이 실제로 저장됨
END;
$$;

-- 2단계: 어떤 테이블의 어떤 이벤트에 연결할지 지정
CREATE TRIGGER trg_set_updated_at
  BEFORE UPDATE ON article   -- article 테이블에 UPDATE 직전
  FOR EACH ROW               -- 영향받은 행마다 한 번씩 실행
  EXECUTE FUNCTION set_updated_at();
RETURN NEW를 빠뜨리면 데이터가 사라집니다. BEFORE 트리거의 반환값은 "실제로 저장될 행"을 뜻합니다. RETURN NEW면 수정된 행이 저장되고, 실수로 RETURN NULL을 반환하면 그 행의 INSERT/UPDATE가 통째로 취소됩니다. 에러도 안 나고 조용히 저장이 안 되므로 찾기 어려운 버그가 됩니다.

이제 행을 수정해 봅시다. updated_at은 전혀 건드리지 않았는데도 값이 바뀝니다. 아래는 INSERT 후 2초 뒤 UPDATE한 실제 결과입니다.

sqlstudy_db=# — updated_at이 자동으로 갱신됨
INSERT INTO article (title, body) VALUES ('첫 글', '초안');
SELECT id, updated_at AS before_update FROM article;
--  id |         before_update
-- ----+-------------------------------
--   1 | 2026-06-09 12:03:22.597622+00

UPDATE article SET body = '수정본' WHERE id = 1;   -- updated_at은 안 건드림
SELECT id, updated_at AS after_update FROM article;
--  id |         after_update
-- ----+-------------------------------
--   1 | 2026-06-09 12:03:24.604974+00   ← 트리거가 자동 갱신

감사 로그(audit) 트리거

"누가 무엇을 어떻게 바꿨나"를 자동으로 기록하는 것이 감사 로그입니다. AFTER INSERT/UPDATE/DELETE 트리거를 달아두면, 어떤 경로로 데이터가 바뀌든 변경 전후 값이 별도 테이블에 자동으로 쌓입니다. 앱 코드에는 로그 관련 코드가 한 줄도 없어도 됩니다.

비유 — 블랙박스 카메라. 운전자가 아무것도 하지 않아도 사고 전후를 자동으로 촬영해 두는 블랙박스처럼, 감사 로그 트리거는 데이터 변경 전·후를 자동 스냅샷해 별도 테이블에 보관합니다. 나중에 "이 값이 언제, 누구에 의해, 어떻게 바뀌었지?"를 추적할 때 꺼내 봅니다.
왜 BEFORE가 아니라 AFTER일까요? 앞의 updated_at 트리거는 저장될 값을 바꾸는 게 목적이라 BEFORE였습니다. 감사 로그는 정반대입니다 — "데이터가 실제로 저장됐다"는 사실을 기록하는 게 목적이므로, 저장이 완료된 뒤에 실행되는 AFTER가 맞습니다. 아직 저장될지 모르는 시점에 로그부터 남기면 거짓 기록이 될 수 있으니까요.

DB가 자동으로 알려주는 정보들

트리거 함수가 실행될 때, DB는 "지금 어떤 상황인지"를 자동으로 알려줍니다. 개발자가 넘겨주지 않아도 함수 안에서 바로 쓸 수 있습니다.

변수 / 함수담고 있는 것
TG_OP지금 어떤 작업인지: 'INSERT' / 'UPDATE' / 'DELETE'
TG_TABLE_NAME어떤 테이블에서 발생했는지. 함수 하나를 여러 테이블에 연결해도 각자 자기 이름이 자동으로 찍힘
to_jsonb(OLD) / to_jsonb(NEW)행 전체를 JSON으로 변환. 나중에 컬럼이 추가돼도 자동으로 포함되어 관리가 편함

여기서 to_jsonb()가 특히 영리한 선택입니다. 컬럼을 하나하나 나열해 로그를 남기면 나중에 컬럼이 추가될 때마다 트리거 함수를 고쳐야 하지만, 행 전체를 통째로 JSON으로 밀어 넣으면 스키마가 바뀌어도 트리거는 그대로 둬도 됩니다.

sqlstudy_db=# — audit_changes 함수 (jsonb로 old/new 기록)
CREATE OR REPLACE FUNCTION audit_changes()
RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  INSERT INTO audit_log (table_name, action, old_row, new_row)
  VALUES (
    TG_TABLE_NAME,           -- 자동 제공: 이 트리거가 발생한 테이블 이름
    TG_OP,                   -- 자동 제공: 'INSERT' / 'UPDATE' / 'DELETE'
    -- INSERT에는 OLD가 없으므로 CASE로 분기
    CASE WHEN TG_OP <> 'INSERT' THEN to_jsonb(OLD) END,
    -- DELETE에는 NEW가 없으므로 CASE로 분기
    CASE WHEN TG_OP <> 'DELETE' THEN to_jsonb(NEW) END
  );
  RETURN NULL;   -- AFTER 트리거는 이미 저장이 끝난 뒤라 반환값이 무시됨
END;
$$;

CREATE TRIGGER trg_audit
  AFTER INSERT OR UPDATE OR DELETE ON article
  FOR EACH ROW EXECUTE FUNCTION audit_changes();
여기서는 RETURN NULL이 괜찮습니다. 앞에서 "BEFORE 트리거에서 RETURN NULL하면 저장이 취소된다"고 경고했는데, AFTER 트리거는 이미 저장이 끝난 뒤라 반환값이 무시됩니다. 그래서 관례적으로 NULL을 반환합니다. 타이밍(BEFORE/AFTER)에 따라 같은 코드의 의미가 정반대가 되는 대표적인 예입니다.

이제 article에 INSERT · UPDATE · DELETE를 차례로 실행해 보면, 아무것도 안 했는데 audit_log에 이력이 쌓여 있습니다.

sqlstudy_db=# — audit_log에 자동으로 쌓인 이력
INSERT INTO article (title, body) VALUES ('둘째 글', 'hello');
UPDATE article SET title = '둘째 글(수정)' WHERE title = '둘째 글';
DELETE FROM article WHERE title = '둘째 글(수정)';

SELECT action, old_row->>'title' AS old_title,
       new_row->>'title' AS new_title
  FROM audit_log ORDER BY id;
--  action |   old_title   |   new_title
-- --------+---------------+---------------
--  INSERT |               | 둘째 글          ← OLD 없음
--  UPDATE | 둘째 글       | 둘째 글(수정)     ← 둘 다 있음
--  DELETE | 둘째 글(수정) |                  ← NEW 없음

결과 표의 빈칸이 정확히 앞에서 본 OLD/NEW 표와 일치하는 걸 확인하세요. CASE WHEN 분기가 왜 필요했는지 이 결과가 보여줍니다.

트리거 남용 주의 — 강력함의 이면. 트리거의 장점은 "앱이 몰라도 작동한다"인데, 이건 그대로 단점이기도 합니다. 코드 어디에도 안 보이는데 값이 바뀌니, 새로 합류한 개발자는 "왜 이 컬럼이 저절로 바뀌지?"를 한참 헤매게 됩니다. 디버깅도, 테스트도 까다로워집니다.

그래서 선을 그어두는 게 좋습니다. updated_at·감사 로그처럼 가볍고 정형화된 부수 작업에는 훌륭합니다. 반면 결제 처리·주문 상태 전이 같은 비즈니스 핵심 로직은 트리거가 아니라 앱/서비스 계층에 두세요. 추적 가능하고 테스트할 수 있는 곳에 있어야 합니다.

✅

셀프 체크

Q updated_at을 트리거로 처리하면 좋은 점은?

앱의 모든 UPDATE 경로마다 updated_at = now()를 챙길 필요가 없어집니다. 어떤 코드·도구·수동 SQL로 수정하든 DB가 항상 자동으로 갱신하므로, 한 곳이라도 빠뜨려 거짓 시각이 남는 사고가 사라집니다. BEFORE UPDATE 트리거에서 NEW.updated_at := now()로 교체하고 RETURN NEW로 반환합니다.

Q BEFORE와 AFTER는 어떻게 나눠 쓰나요?

저장될 값을 바꿔야 하면 BEFORE입니다(NEW를 수정하고 RETURN NEW). 저장됐다는 사실에 반응만 하면 AFTER입니다(감사 로그 등). AFTER는 이미 저장이 끝난 뒤라 값을 바꿀 수 없고 반환값도 무시됩니다.

Q BEFORE 트리거에서 RETURN NULL을 반환하면?

그 행의 INSERT/UPDATE가 통째로 취소됩니다. 에러도 나지 않고 조용히 저장이 안 되므로 매우 찾기 어려운 버그가 됩니다. 값만 손보는 BEFORE 트리거는 반드시 RETURN NEW로 끝내세요. 반대로 AFTER 트리거에서는 RETURN NULL이 관례이며 아무 영향이 없습니다.

Q 감사 로그 함수에서 CASE WHEN 분기가 필요한 이유는?

이벤트마다 존재하는 값이 다르기 때문입니다. INSERT에는 OLD가 없고 DELETE에는 NEW가 없는데, 없는 쪽을 참조하면 에러가 납니다. 그래서 CASE WHEN TG_OP <> 'INSERT' THEN to_jsonb(OLD) END처럼 분기해 안전하게 NULL을 넣습니다.

Q 트리거에 넣으면 안 되는 로직은?

결제·주문 상태 전이 같은 비즈니스 핵심 로직입니다. 트리거는 코드에 드러나지 않는 숨은 로직이라 추적·디버깅·테스트가 어렵습니다. updated_at·감사 로그처럼 가볍고 정형화된 부수 작업에만 쓰고, 핵심 로직은 앱/서비스 계층에 두는 것이 원칙입니다.
