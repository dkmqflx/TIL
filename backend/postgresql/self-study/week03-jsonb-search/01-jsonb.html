JSON vs JSONB — 연산자와 GIN 인덱스

Postgres는 "형식이 제각각인 데이터"를 일급 시민으로 다룹니다. 규칙은 단순합니다 — 앱에서는 거의 항상 jsonb를 쓰고, @>로 검색하고, GIN으로 인덱싱합니다.

한 줄 요약. JSONB는 "관계형을 포기하지 않고 유연함을 얻는" 방법입니다. NoSQL을 따로 붙일 필요 없이, 트랜잭션·조인·제약을 그대로 쓰면서 자유로운 형태의 데이터를 한 컬럼에 담고 인덱스까지 걸 수 있습니다.

학습 목표

  • json과 jsonb의 차이를 알고, 왜 앱은 jsonb를 쓰는지 설명한다
  • 핵심 연산자(-> ->> #> @> ?)를 헷갈리지 않고 쓴다
  • jsonb_set·||로 부분 갱신하고, GIN 인덱스로 검색을 가속한다
  • 무엇을 jsonb에 넣고 무엇을 일반 컬럼으로 뺄지 판단한다
🅱️

json vs jsonb — 이름 하나 차이, 완전히 다른 성격

Postgres에는 JSON을 담는 타입이 둘 있습니다. 이름이 한 글자 차이라 헷갈리지만, 내부 동작은 완전히 다릅니다.

비유 — 접힌 편지 vs 정리된 서류철.

json은 받은 편지를 접힌 그대로 서랍에 넣는 것입니다. 글씨체, 줄 간격, 심지어 같은 말을 두 번 쓴 것까지 원본 그대로 보존됩니다. 대신 내용을 확인하려면 매번 펼쳐서 읽어야 합니다.

jsonb는 받자마자 내용을 읽어 항목별로 정리해 서류철에 꽂아두는 것입니다. 순서를 정리하고 중복은 하나로 합칩니다. 원본 모양은 사라지지만, 나중에 "brand 항목만 뽑아줘"가 즉시 가능하고 색인까지 붙일 수 있습니다.

jsonjsonb
저장 형태원문 텍스트 그대로파싱된 바이너리
키 순서·공백그대로 보존정규화(정렬·압축)
중복 키유지마지막 값만 남김
연산 속도느림 (매번 파싱)빠름 (이미 파싱됨)
GIN 인덱스불가 ❌가능 ✅
결론원문 보존이 진짜로 필요할 때만앱의 기본 선택

말로만 들으면 추상적이니 같은 값을 두 타입에 넣어 봅시다. 차이가 한눈에 보입니다.

sqlstudy_db=# — 같은 값, 다른 타입
SELECT
  '{"b":1, "a":2, "a":3}'::json  AS as_json,    -- 원문 그대로(중복 a 유지)
  '{"b":1, "a":2, "a":3}'::jsonb AS as_jsonb;   -- 정규화(키 정렬, 중복 제거)
--         as_json        |     as_jsonb
-- -----------------------+------------------
--  {"b":1, "a":2, "a":3} | {"a": 3, "b": 1}
--                          ↑ 키가 정렬되고, 중복 a는 마지막 값(3)만 남음
실무 규칙: 고민하지 말고 jsonb. json이 필요한 경우는 "외부에서 받은 원문을 글자 하나 틀리지 않고 보관해야 하는" 상황(예: 서명 검증용 원본 페이로드) 정도입니다. 그 외 99%는 jsonb가 정답입니다. 특히 인덱스를 걸 수 있느냐가 결정적입니다 — 검색이 필요한 순간 json은 방법이 없습니다.
🔧

핵심 연산자 — -> · ->> · #> · @> · ?

JSONB를 배울 때 가장 처음 부딪히는 벽이 기호가 많다는 점입니다. 하지만 실제로 매일 쓰는 건 다섯 개뿐이고, 그중에서도 ->와 ->>의 차이만 확실히 잡으면 절반은 끝납니다.

둘 다 키로 값을 꺼내지만 돌려주는 타입이 다릅니다. ->는 jsonb를(따옴표가 붙은 채로), ->>는 text를(따옴표 없는 순수 문자열) 돌려줍니다. 화살표가 하나 더 길면 껍질(따옴표)이 벗겨진다고 외우면 편합니다.

sqlstudy_db=# — 실습 테이블 + -> (jsonb) vs ->> (text)
CREATE TABLE products (
  id    int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name  text NOT NULL,
  data  jsonb NOT NULL
);
INSERT INTO products (name, data) VALUES
  ('키보드', '{"brand":"Keychron","price":129,"tags":["mech","wireless"],"spec":{"switch":"brown"}}'),
  ('마우스', '{"brand":"Logitech","price":59,"tags":["wireless"],"spec":{"dpi":8000}}'),
  ('모니터', '{"brand":"LG","price":299,"tags":["4k","ips"],"spec":{"size":27}}');

SELECT
  name,
  data -> 'brand'         AS brand_jsonb,   -- "Keychron" (따옴표 포함 jsonb)
  data ->> 'brand'        AS brand_text,    -- Keychron   (순수 text)
  (data ->> 'price')::int AS price_int      -- text를 int로 캐스팅
FROM products ORDER BY id;
--   name  | brand_jsonb | brand_text | price_int
-- --------+-------------+------------+-----------
--  키보드 | "Keychron"  | Keychron   |       129
--  마우스 | "Logitech"  | Logitech   |        59
--  모니터 | "LG"        | LG         |       299

이 실수는 거의 모두가 한 번은 합니다.

WHERE data -> 'brand' = 'LG' — 얼핏 맞아 보이지만 매칭되지 않습니다. 왼쪽은 jsonb "LG"(따옴표 포함), 오른쪽은 text LG이기 때문입니다.

규칙은 이렇습니다. 비교·조인·캐스팅에는 ->>(text를 주는 쪽), 결과를 다시 키로 파고들 때는 ->(jsonb를 주는 쪽). 그래서 중첩된 값을 꺼낼 때는 data -> 'spec' ->> 'switch'처럼 중간엔 ->, 마지막만 ->>가 됩니다.

이제 나머지 셋입니다. #>/#>>는 깊은 경로를 배열로 한 번에 지정하는 축약형이고, @>는 이 레슨의 주인공, ?는 키 존재 확인입니다.

연산자묻는 것예시
#> / #>>경로로 깊이 들어간 값 (jsonb / text)data #>> '{spec,switch}'
@>왼쪽이 오른쪽을 통째로 포함하는가data @> '{"tags":["wireless"]}'
?이 최상위 키가 있는가data ? 'brand'
?| / ?&키 중 하나라도 / 전부 있는가data ?& array['brand','price']
@>를 이해하는 비유 — 장바구니 확인. @>는 "이 장바구니 안에 이 물건들이 다 들어 있니?"를 묻습니다. 장바구니에 다른 게 더 들어 있어도 상관없습니다 — 요청한 것만 들어 있으면 참입니다. 그래서 data @> '{"tags":["wireless"]}'는 "tags 배열에 wireless가 포함되어 있는가"를 묻고, tags에 다른 태그가 더 있어도 매칭됩니다. 이 "부분만 명시해도 되는" 성질 덕분에 검색 조건을 짜기가 아주 편합니다.
sqlstudy_db=# — #>> 경로 · @> 포함 · ?& 키 존재
-- #>> : 경로로 깊이 들어가 text 반환 (없으면 NULL)
SELECT name, data #>> '{spec,switch}' AS switch_text FROM products ORDER BY id;
--   name  | switch_text
-- --------+-------------
--  키보드 | brown
--  마우스 |              ← spec.switch가 없으면 NULL
--  모니터 |

-- @> : 포함(containment). 배열 원소 포함도 판정한다
SELECT name FROM products WHERE data @> '{"tags":["wireless"]}';
--   name
-- --------
--  키보드     ← tags에 mech도 있지만 wireless를 포함하므로 매칭
--  마우스

-- ?& : 나열한 키가 모두 존재하는가
SELECT name FROM products WHERE data ?& array['brand','price'];   -- 세 행 모두
MySQL — 익숙한 방식

단일 JSON 타입 하나뿐입니다(내부는 바이너리). 값 추출은 주로 함수로 합니다 — JSON_EXTRACT(data, '$.brand'), 단축형은 data->'$.brand'. 경로는 $.a.b 같은 JSONPath 문자열입니다.

PostgreSQL — 이렇게 다르다

json/jsonb 두 타입에 전용 연산자가 풍부합니다. 결정적인 차이는 @> 포함 검색을 GIN 인덱스로 가속할 수 있다는 점 — MySQL의 일반 JSON 컬럼에는 없는 능력입니다.

✏️

jsonb 부분 갱신 — jsonb_set · || · - · #-

jsonb는 읽기 전용이 아닙니다. 전체를 다시 쓰지 않고 일부만 고칠 수 있습니다. 도구는 네 개입니다.

도구하는 일비유
jsonb_set(data, 경로, 값)특정 경로의 값을 교체서류의 한 칸만 지우고 다시 쓰기
||두 jsonb를 병합(같은 키는 덮어쓰고, 없는 키는 추가)새 항목이 적힌 쪽지를 덧붙이기
-최상위 키 삭제맨 위 항목 하나 지우기
#-깊은 경로의 값 삭제안쪽 항목 하나 지우기
sqlstudy_db=# — jsonb 부분 갱신 네 가지
UPDATE products SET data = jsonb_set(data, '{price}', '139') WHERE name = '키보드';
UPDATE products SET data = data || '{"in_stock": true}'::jsonb WHERE name = '마우스';
UPDATE products SET data = data - 'tags' WHERE name = '모니터';        -- 최상위 키 삭제
UPDATE products SET data = data #- '{spec,dpi}' WHERE name = '마우스';  -- 경로 삭제

SELECT name, data FROM products ORDER BY id;
--   name  |                                    data
-- --------+----------------------------------------------------------------------------
--  키보드 | {"spec": {"switch": "brown"}, "tags": [...], "brand": "Keychron", "price": 139}
--  마우스 | {"spec": {}, "tags": ["wireless"], "brand": "Logitech", "price": 59, "in_stock": true}
--  모니터 | {"spec": {"size": 27}, "brand": "LG", "price": 299}

가장 중요한 경고 — 아무거나 jsonb에 쑤셔 넣지 마세요.

jsonb가 편하다고 정형 데이터까지 한 컬럼에 몰아넣으면, 관계형 DB의 강점을 전부 잃습니다. 컬럼 타입 검사도, CHECK 제약도, 외래키도, 효율적인 조인도 없어집니다. "가격을 문자열로 넣어버린" 행을 아무도 막지 못하게 되죠.

기준은 명확합니다. 자주 조회·조인·검증하는 값(가격, 상태, 사용자 id, 생성일…) → 일반 컬럼. 진짜로 가변적이거나 드문드문한 속성(제품마다 다른 스펙, 외부 API 원본 페이로드, 자유로운 설정값) → jsonb. 이 둘을 섞어 쓰는 것이 Postgres를 제대로 쓰는 법입니다.

⚡

GIN 인덱스 — @> 검색을 진짜로 빠르게

지금까지 배운 @> 검색은 인덱스가 없으면 모든 행을 하나씩 열어보며 확인합니다. 행이 100개면 괜찮지만 100만 개면 재앙이죠. 이때 필요한 것이 GIN(Generalized Inverted Index)입니다.

비유 — 책 뒤의 "찾아보기". GIN의 정식 이름에 들어 있는 Inverted(역)가 핵심입니다. 보통 책은 "3페이지 → 이런 내용"이지만, 찾아보기는 반대로 "이 단어 → 15, 42, 77페이지"로 정리돼 있죠. GIN도 똑같습니다. jsonb 안의 모든 키와 값을 뽑아내 "이 값이 들어 있는 행 번호 목록"을 미리 만들어 둡니다. 그래서 @> 검색이 곧바로 답에 닿습니다.

GIN을 만들 때 선택지가 둘 있는데, 차이를 알고 고르면 됩니다.

인덱스 종류지원 연산자특징
gin (data) — 기본@> · ? · ?| · ?&키 존재 검색까지 지원하지만 인덱스가 큼
gin (data jsonb_path_ops)@> 만더 작고 빠름 (키 존재 ?는 불가)

실무에서 @> 포함 검색만 쓴다면 jsonb_path_ops가 낫습니다. 인덱스가 작으면 메모리에 더 잘 올라가고 유지 비용도 줄기 때문이죠. 실제로 인덱스를 타는지 확인해 봅시다.

sqlstudy_db=# — jsonb_path_ops GIN이 @> 검색에 실제로 쓰인다
-- 인덱스가 실제로 쓰이려면 행이 충분해야 한다 → events 1,500행 생성
CREATE TABLE events (id int GENERATED ALWAYS AS IDENTITY PRIMARY KEY, payload jsonb NOT NULL);
INSERT INTO events (payload)
  SELECT jsonb_build_object('type', t, 'level', (i % 3))
  FROM generate_series(1, 500) i, (VALUES ('login'),('logout'),('error')) AS v(t);

CREATE INDEX idx_events_payload ON events USING gin (payload jsonb_path_ops);

EXPLAIN (COSTS OFF)
SELECT * FROM events WHERE payload @> '{"type":"error"}';
--                          QUERY PLAN
-- -------------------------------------------------------------
--  Bitmap Heap Scan on events
--    Recheck Cond: (payload @> '{"type": "error"}'::jsonb)
--    ->  Bitmap Index Scan on idx_events_payload      ← 인덱스를 탔다!
--          Index Cond: (payload @> '{"type": "error"}'::jsonb)
행이 적으면 인덱스를 안 탈 수도 있습니다. 위 예제에서 굳이 1,500행을 만든 이유가 있습니다. 행이 몇 개뿐이면 Postgres의 플래너가 "인덱스를 여는 것보다 그냥 다 읽는 게 빠르다"고 판단해 Seq Scan을 고릅니다. 버그가 아니라 똑똑한 판단입니다. 그래서 인덱스 실험을 할 때는 항상 데이터를 충분히 넣어야 합니다. 플래너의 이런 판단 과정은 Week 4.02에서 자세히 다룹니다.
한 걸음 더 — SQL/JSON 경로 질의. 조건이 복잡해지면 jsonb_path_query가 강력합니다. 예를 들어 jsonb_path_query(data, '$.items[*].q ? (@ > 4)')는 items 배열을 순회하며 q > 4인 값만 골라냅니다. PG17+에서는 JSON_TABLE(...)로 한발 더 나아가, jsonb를 관계형 행·열로 펼쳐 일반 테이블처럼 조인할 수도 있습니다.

셀프 체크

Q json과 jsonb 중 무엇을 골라야 하나요?

앱 개발에서는 거의 항상 jsonb입니다. 파싱된 바이너리로 저장돼 연산이 빠르고, 무엇보다 GIN 인덱스로 @> 검색을 가속할 수 있습니다. json은 키 순서·중복 키·공백까지 입력 원문을 글자 그대로 보존해야 하는 특수한 경우에만 씁니다.

Q ->와 ->>는 어떻게 구분하나요?

둘 다 키로 값을 꺼내지만 반환 타입이 다릅니다. ->는 jsonb("LG" — 따옴표 포함), ->>는 text(LG)를 돌려줍니다. 비교·조인·캐스팅엔 ->>, 결과를 다시 키로 파고들 땐 ->입니다. 중첩 값은 data -> 'spec' ->> 'switch'처럼 마지막만 ->>가 됩니다.

Q @>와 GIN 인덱스는 어떤 관계인가요?

@>는 "포함" 검색 연산자이고, GIN 인덱스가 이 검색을 가속합니다. 인덱스가 없으면 모든 행을 열어보는 풀스캔이지만, gin (data) 또는 @> 전용의 더 작은 gin (data jsonb_path_ops)를 만들면 EXPLAIN에서 Bitmap Index Scan을 확인할 수 있습니다.

Q 어떤 데이터를 jsonb에 넣고 어떤 걸 일반 컬럼으로 빼야 하나요?

자주 조회·조인·검증하는 값(가격, 상태, 사용자 id 등)은 일반 컬럼으로 빼야 타입 검사·제약·외래키·효율적인 조인을 얻습니다. 진짜로 가변적이거나 드문드문한 속성(제품마다 다른 스펙, 외부 API 원본 페이로드)만 jsonb에 담습니다. 전부 jsonb에 몰아넣으면 관계형의 강점을 통째로 잃습니다.
