배열 · enum · range — 표현력 높은 타입을 알맞게

관계형 안에서도 배열·열거형·범위 같은 타입을 쓸 수 있습니다. 남용하면 독이지만, 알맞게 쓰면 스키마가 훨씬 또렷해집니다.

한 줄 요약. 이 세 타입의 공통점은 "원래 여러 칸이나 여러 행이 필요하던 것을 한 값으로 표현"한다는 점입니다. 그래서 편해지는 만큼 잃는 것도 있습니다 — 각 섹션의 "언제 쓰지 말아야 하나"를 특히 눈여겨보세요.

학습 목표

  • 배열 타입과 연산(ANY·@>·&&·unnest)을 쓰고, 언제 정규화할지 판단한다
  • enum 타입을 만들고, 정렬 순서와 값 추가의 함정을 안다
  • range 타입으로 포함(@>)·겹침(&&)을 표현한다
📚

배열(array) — 한 칸에 여러 값

Postgres는 거의 모든 타입을 배열로 쓸 수 있습니다. 컬럼 타입 뒤에 []를 붙이기만 하면 됩니다(text[], int[]…). 태그처럼 단순한 다중 값에 특히 잘 맞습니다.

배열 인덱스는 1부터 시작합니다. 대부분의 프로그래밍 언어와 달리 Postgres 배열은 1-based입니다. 첫 원소는 tags[1]이지 tags[0]이 아닙니다. tags[0]은 에러가 아니라 조용히 NULL을 돌려주기 때문에 버그를 알아채기가 어렵습니다. 꼭 기억하세요.
sqlstudy_db=# — 배열 컬럼과 기본 함수
CREATE TABLE articles (
  id    int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title text NOT NULL,
  tags  text[] NOT NULL DEFAULT '{}'     -- 빈 배열을 기본값으로
);
INSERT INTO articles (title, tags) VALUES
  ('Postgres 입문', '{db,sql,postgres}'),          -- 리터럴 방식
  ('JSONB 검색',    ARRAY['db','postgres','jsonb']), -- ARRAY 생성자 방식
  ('CSS 그리드',    '{css,frontend}');

SELECT title, tags[1] AS first_tag, array_length(tags, 1) AS n_tags
  FROM articles ORDER BY id;
--      title     | first_tag | n_tags
-- ---------------+-----------+--------
--  Postgres 입문 | db        |      3
--  JSONB 검색    | db        |      3
--  CSS 그리드    | css       |      2

배열 검색의 핵심은 세 연산자입니다. 헷갈리기 쉬우니 한 표로 정리합니다.

연산묻는 것일상어로
'x' = ANY(tags)배열 안에 이 값이 있는가"postgres 태그 달린 글"
tags @> ARRAY['a','b']이 값들을 모두 포함하는가"db와 sql 둘 다 달린 글"
tags && ARRAY['a','b']겹치는 원소가 하나라도 있는가"css 또는 jsonb 달린 글"

그리고 unnest는 배열을 행으로 펼치는 함수입니다. 태그별 개수 집계 같은 작업에 필수죠.

sqlstudy_db=# — ANY · @> · && · unnest
-- ANY: 배열 안에 특정 값이 있는가
SELECT title FROM articles WHERE 'postgres' = ANY(tags);

-- @>: 모두 포함 (AND) / &&: 하나라도 겹침 (OR)
SELECT title FROM articles WHERE tags @> ARRAY['db','sql'];     -- 둘 다 포함
SELECT title FROM articles WHERE tags && ARRAY['css','jsonb'];  -- 하나라도 겹침

-- unnest: 배열을 행으로 펼쳐 집계
SELECT tag, count(*) AS n
  FROM articles, unnest(tags) AS tag
  GROUP BY tag ORDER BY n DESC, tag;
--    tag    | n
-- ----------+---
--  db       | 2
--  postgres | 2
--  css      | 1
--  ...

-- 배열도 GIN 인덱스로 @>, &&, = ANY 검색을 가속할 수 있다
CREATE INDEX idx_articles_tags ON articles USING gin (tags);

마지막 줄을 주목하세요. 배열에도 GIN 인덱스를 걸 수 있습니다. 앞 레슨의 jsonb와 같은 원리입니다 — GIN은 "여러 값이 든 하나의 칸"을 잘게 쪼개 역색인으로 만드는 데 특화돼 있습니다.

배열 vs 별도 테이블 — 갈림길은 하나입니다.

스스로에게 물어보세요. "이 값에 조인이나 추가 속성이 필요한가?"

아니오 → 배열이 훨씬 편합니다. 블로그 태그처럼 값 자체로 의미가 닫혀 있고, 그냥 문자열로 붙였다 뗐다 하면 되는 경우죠.

예 → 별도 테이블 + 외래키로 정규화해야 합니다. 예를 들어 태그마다 "누가 언제 달았는지", "설명 문구", "대표 색상"이 필요해지거나, 태그 이름을 한 번에 바꿔야 한다면 — 배열로는 감당이 안 됩니다. 배열 안의 문자열은 독립된 존재가 아니라 그냥 글자이기 때문입니다.

🏷️

enum — 재사용 가능한 열거형 "타입"

"주문 상태는 pending, paid, shipped 중 하나여야 한다"처럼 정해진 몇 개의 값만 허용하고 싶을 때 enum을 씁니다.

Postgres의 enum에서 가장 중요한 특징은 정렬이 알파벳순이 아니라 정의한 순서를 따른다는 점입니다. 이게 생각보다 유용합니다.

비유 — 등급에는 자연스러운 순서가 있다. low, mid, high를 알파벳순으로 정렬하면 high → low → mid라는 엉뚱한 순서가 나옵니다. 하지만 우리가 원하는 건 low → mid → high죠. enum은 "정의한 순서 = 크기 순서"로 취급하므로 ORDER BY level 한 줄로 우리가 의도한 순서가 나옵니다. WHERE level > 'mid' 같은 비교도 자연스럽게 됩니다.
sqlstudy_db=# — enum 정의 · 정렬 · 값 추가
CREATE TYPE mood AS ENUM ('low', 'mid', 'high');
ALTER TYPE mood ADD VALUE IF NOT EXISTS 'peak';   -- 맨 끝에 값 추가

INSERT INTO mood_log (note, level) VALUES
  ('피곤', 'low'), ('보통', 'mid'), ('최고', 'peak'), ('좋음', 'high');

-- 정렬은 '정의 순서': low < mid < high < peak (알파벳이 아님!)
SELECT note, level FROM mood_log ORDER BY level;
--  note | level
-- ------+-------
--  피곤 | low
--  보통 | mid
--  좋음 | high
--  최고 | peak

enum의 두 가지 함정.

① 같은 트랜잭션 안에서 바로 못 씁니다. ALTER TYPE ... ADD VALUE로 추가한 값은 커밋 전까지 사용할 수 없습니다. "값을 추가하고 곧바로 그 값으로 INSERT"하는 마이그레이션 스크립트를 짜면 실패합니다 — 두 트랜잭션으로 나눠야 합니다.

② 중간 삽입·삭제가 번거롭습니다. low와 mid 사이에 새 값을 끼우려면 BEFORE/AFTER 절이 필요하고, 값을 삭제하는 건 사실상 불가능합니다(타입을 새로 만들어 갈아타야 합니다).

그래서 값이 자주 바뀌고 추가·삭제가 잦다면 enum보다 참조(lookup) 테이블 + 외래키가 훨씬 유연합니다. 값이 거의 고정된 상태 코드에는 enum이 좋고, 관리자가 화면에서 추가할 수 있는 카테고리 같은 건 테이블이 맞습니다.

MySQL — 익숙한 방식

ENUM('low','mid','high')를 컬럼 정의에 직접 씁니다. 즉 컬럼에 종속된 정의라, 같은 열거형을 다른 테이블에서 쓰려면 매번 다시 적어야 하고 정의가 흩어지기 쉽습니다.

PostgreSQL — 이렇게 다르다

CREATE TYPE mood AS ENUM (...)로 독립된 타입을 먼저 만듭니다. 한 번 정의하면 여러 테이블·함수가 재사용하고, 정렬 순서도 타입 정의에 함께 담깁니다.

📏

range — 범위를 하나의 값으로

"1부터 10까지", "오전 10시~11시" 같은 범위는 보통 컬럼 두 개(start, end)로 표현합니다. Postgres의 range 타입은 이걸 하나의 값으로 다룹니다.

종류는 담는 값에 따라 int4range(정수), numrange(실수), daterange(날짜), tstzrange(타임존 포함 시각) 등이 있습니다. 경계 표기는 [)(시작 포함, 끝 미포함)가 기본이자 권장입니다.

sqlstudy_db=# — range 포함(@>) · 겹침(&&)
SELECT
  int4range(1, 10)                    AS r1,           -- [1,10)
  numrange(0, 100) @> 50::numeric     AS contains_50,  -- 이 범위가 50을 포함하는가?
  int4range(1,10) && int4range(5,20)  AS overlaps;     -- 두 범위가 겹치는가?
--    r1   | contains_50 | overlaps
-- --------+-------------+----------
--  [1,10) | t           | t

여기서 두 연산자의 의미를 확실히 구분해 두세요. @>는 "포함"(이 범위 안에 저 값/범위가 들어가는가), &&는 "겹침"(두 범위가 조금이라도 만나는가)입니다.

range의 진가 — 겹침 방지

range 타입이 진짜 빛나는 순간은 Week 2·01의 EXCLUDE와 결합할 때입니다. "같은 회의실에 시간이 겹치는 예약 금지"를 DB가 직접 보장하게 만들 수 있습니다.

비유 — 시간표에 색칠하기. 예약 시간을 start/end 두 컬럼으로 두면, 겹침을 확인할 때마다 (a.start < b.end AND b.start < a.end) 같은 조건을 손으로 조립해야 합니다. 한 번만 잘못 써도 이중 예약이 뚫리죠. during tstzrange 한 컬럼으로 두면 그 조건이 && 한 글자가 됩니다. 시간표 위에 색을 칠해 놓고 "겹치는 색이 있나?"를 보는 것과 같습니다.
sqlstudy_db=# — range + EXCLUDE로 예약 겹침 방지
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE room_booking (
  id     int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  room   text NOT NULL,
  during tstzrange NOT NULL,
  EXCLUDE USING gist (room WITH =, during WITH &&)
);
INSERT INTO room_booking (room, during) VALUES
  ('A', '[2026-06-09 10:00+09, 2026-06-09 11:00+09)'),   -- OK
  ('A', '[2026-06-09 11:00+09, 2026-06-09 12:00+09)');   -- 인접, 안 겹침 → OK

-- 같은 방 A의 겹치는 시간대는 막힌다 (의도적 에러)
INSERT INTO room_booking (room, during)
  VALUES ('A', '[2026-06-09 10:30+09, 2026-06-09 11:30+09)');
-- ERROR:  conflicting key value violates exclusion constraint
왜 [)가 기본이자 권장일까요? 시간·날짜 범위를 이어 붙일 때 딱 맞아떨어지기 때문입니다. 10~11시 예약이 11시를 포함하지 않으니 11~12시 예약이 바로 이어질 수 있습니다. 만약 양쪽 다 포함하는 []를 쓰면 11시가 두 예약에 겹쳐 1초짜리 충돌이 생깁니다. 그래서 "시작은 포함, 끝은 제외"가 범위 표현의 표준 관례입니다.

셀프 체크

Q 배열을 쓸 때와 별도 테이블로 정규화할 때는?

판단 기준은 "이 값에 조인이나 추가 속성이 필요한가?"입니다. 블로그 태그처럼 값 자체로 닫혀 있고 붙였다 떼기만 하면 되면 배열이 편합니다. 원소마다 속성(작성자·생성일·설명)이 필요하거나 다른 테이블과 조인해야 하면 별도 테이블 + 외래키로 정규화해야 합니다.

Q Postgres 배열의 첫 원소를 꺼내려면?

tags[1]입니다. Postgres 배열은 1부터 시작합니다. tags[0]은 에러 없이 조용히 NULL을 돌려주기 때문에 버그를 알아채기 어렵습니다.

Q enum에 값을 추가할 때 주의할 점은?

ALTER TYPE ... ADD VALUE로 추가한 값은 같은 트랜잭션 안에서는 곧바로 사용할 수 없습니다(커밋 후 가능). 또 중간 삽입은 번거롭고 삭제는 사실상 불가능합니다. 값이 자주 바뀐다면 enum보다 참조 테이블 + 외래키가 유연합니다. 정렬이 알파벳이 아니라 정의 순서를 따른다는 점도 함께 기억하세요.

Q range의 @>와 &&는 각각 무엇을 판별하나요?

@>는 포함(이 범위 안에 저 값/범위가 들어가는가), &&는 겹침(두 범위가 조금이라도 만나는가)입니다. EXCLUDE USING gist (room WITH =, during WITH &&)처럼 쓰면 "같은 방의 시간이 겹치는 예약"을 DB가 거부합니다.
