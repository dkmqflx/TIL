전문검색 — tsvector/tsquery와 pg_trgm

"검색 기능 붙여주세요"를 LIKE '%...%'로 해결하면 처음엔 잘 돌아가다가 데이터가 쌓이는 순간 무너집니다. Postgres에는 진짜 검색 엔진이 내장돼 있습니다.

한 줄 요약. Postgres는 검색을 두 갈래로 제공합니다. 단어 단위 정식 검색은 tsvector, 오타 허용·부분일치는 pg_trgm. 한국어라면 후자가 훨씬 실용적일 때가 많습니다.

학습 목표

  • LIKE '%x%'가 왜 느린지 원리로 설명한다
  • tsvector/tsquery로 전문검색을 하고 ts_rank로 관련도를 매긴다
  • 전문검색이 인덱스를 못 타는 대표적 함정을 피한다
  • pg_trgm으로 오타 허용·부분일치 검색을 가속한다
🐌

왜 LIKE '%word%'로는 부족한가

검색 기능을 처음 만들 때 거의 모두가 이렇게 씁니다. WHERE body LIKE '%검색어%'. 개발 중에는 완벽하게 동작하죠. 문제는 데이터가 쌓인 뒤에 터집니다. 이유는 두 가지입니다.

비유 — 색인 없는 책에서 단어 찾기.

B-tree 인덱스는 사전과 같습니다. 단어가 앞 글자부터 정렬돼 있으니 "post"로 시작하는 단어는 즉시 찾을 수 있죠. 그래서 LIKE 'post%'는 인덱스를 탈 수 있습니다.

그런데 LIKE '%post%'는 "중간에 post가 들어간 모든 단어"를 찾으라는 요청입니다. 사전의 정렬 순서가 아무 도움이 안 되죠. 결국 첫 장부터 끝까지 전부 읽는 수밖에 없습니다. 이게 선두 와일드카드 문제입니다.

두 번째 문제는 검색의 품질입니다. LIKE는 글자를 그대로 비교할 뿐이라:

  • running을 검색하면 run이 든 문서를 못 찾습니다 (어간 분석 없음)
  • 결과에 순위가 없습니다 — 제목에 나온 문서나 본문 끝에 한 번 나온 문서나 똑같이 취급됩니다
  • the, a 같은 불용어도 그대로 매칭돼 쓸모없는 결과가 쏟아집니다

Postgres는 이 두 문제를 각각 다른 도구로 해결합니다. 품질 문제는 tsvector, 속도(부분일치) 문제는 pg_trgm입니다.

📖

tsvector / tsquery — 내장 전문검색

전문검색의 구조는 단순합니다. 문서를 검색용으로 가공한 것이 tsvector, 사용자가 입력한 질의를 가공한 것이 tsquery, 그리고 둘을 맞춰보는 연산자가 @@입니다.

문서 text → to_tsvector() → tsvector @@ tsquery ← to_tsquery() ← 질의 text

to_tsvector가 하는 일은 문장을 검색하기 좋은 형태로 분해하는 것입니다. 공백으로 자르고, 소문자로 통일하고, the 같은 불용어를 버리고, running을 run으로 어간 분석합니다. 덕분에 run으로 검색해도 running이 든 문서가 걸립니다.

질의를 만드는 세 가지 함수. to_tsquery('english', 'a & b')는 &(AND)·|(OR)·!(NOT)를 직접 쓰는 방식입니다. 사용자 입력을 그대로 넣으면 문법 오류가 나므로 위험합니다. 그래서 실무에서는 평문을 알아서 AND로 묶어주는 plainto_tsquery나, 구글처럼 따옴표·or·-를 이해하는 websearch_to_tsquery를 씁니다. 검색창에 연결한다면 websearch_to_tsquery가 가장 무난합니다.
sqlstudy_db=# — tsvector @@ tsquery 매칭 + 랭킹
-- 'run' 질의가 어간 분석 덕에 'running'이 든 문서까지 매칭
SELECT title FROM docs WHERE search @@ to_tsquery('english', 'run');
--        title
-- -------------------
--  Postgres indexing

-- ts_rank로 관련도 순 정렬
SELECT title, ts_rank(search, q) AS rank
FROM docs, to_tsquery('english', 'index | search') AS q
WHERE search @@ q ORDER BY rank DESC;
--        title       |    rank
-- -------------------+-------------
--  JSONB and GIN     |  0.06079271
--  Postgres indexing | 0.037995443
--  Full text search  | 0.037995443

ts_rank가 매기는 점수는 단어가 몇 번 나왔는지, 문서에서 얼마나 중요한 위치인지를 반영합니다. 검색 결과를 "관련도 높은 순"으로 보여주는 데 그대로 쓸 수 있습니다.

한국어 기본 사전은 한국어를 모릅니다. Postgres 기본 텍스트 검색 사전은 영어를 비롯한 일부 언어의 형태소만 압니다 — 한국어 형태소 분석은 기본 제공되지 않습니다. 그래서 한국어는 'simple' 설정(공백으로 자르고 소문자화만, 어간 분석 없음)으로 다루거나, 아래의 pg_trgm으로 보완합니다. 예를 들어 to_tsvector('simple', '포스트그레스 전문검색 예제')는 '예제':3 '전문검색':2 '포스트그레스':1처럼 공백 단위로만 끊깁니다. "전문"으로 검색하면 "전문검색"이 안 걸린다는 뜻이죠.

가장 흔한 함정 — 인덱스를 못 타는 전문검색

전문검색을 붙였는데 여전히 느리다면, 십중팔구 이 함정입니다.

WHERE to_tsvector('english', body) @@ ...는 매번 풀스캔입니다.

이유는 단순합니다. to_tsvector(body)는 쿼리를 실행하는 시점에 계산되는 값이라, 미리 만들어둔 인덱스가 있을 리 없습니다. 그래서 Postgres는 모든 행에 대해 to_tsvector를 새로 계산한 뒤 비교합니다 — 느린 정도가 아니라 LIKE보다 더 나쁠 수도 있습니다.

정답은 tsvector를 미리 계산해 저장하는 것입니다. Week 2에서 배운 생성 컬럼(GENERATED ALWAYS AS (...) STORED)이 여기서 완벽하게 들어맞습니다. 그 컬럼에 GIN 인덱스를 걸면 끝입니다.

sqlstudy_db=# — tsvector 생성 컬럼 + GIN (함정 회피)
CREATE TABLE docs_big (
  id    int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title text NOT NULL,
  body  text NOT NULL,
  search tsvector GENERATED ALWAYS AS (              -- 저장 시점에 미리 계산
    to_tsvector('english', title || ' ' || body)
  ) STORED                                            -- ← STORED 필수 (인덱스를 걸어야 하므로)
);
-- generate_series로 5,000행 적재 (code/03-fulltext.sql 참고)
CREATE INDEX idx_docsbig_search ON docs_big USING gin (search);

-- 충분한 행(5,000)에서 @@ 검색이 실제로 GIN을 탄다
EXPLAIN (COSTS OFF)
SELECT title FROM docs_big WHERE search @@ to_tsquery('english', 'fuzzy');
--                       QUERY PLAN
-- ------------------------------------------------------
--  Bitmap Heap Scan on docs_big
--    Recheck Cond: (search @@ '''fuzzi'''::tsquery)
--    ->  Bitmap Index Scan on idx_docsbig_search     ← 인덱스 사용!
--          Index Cond: (search @@ '''fuzzi'''::tsquery)

실행 계획에 'fuzzi'라고 나온 것을 보세요. 우리가 검색한 단어는 fuzzy였는데 어간 분석을 거쳐 fuzzi로 변환된 것입니다. 문서 쪽도 같은 방식으로 변환돼 있으니 서로 만날 수 있는 거죠.

주의 Week 2에서 다뤘듯 PG18부터는 STORED를 생략하면 virtual이 기본이고, virtual 생성 컬럼에는 인덱스를 걸 수 없습니다. 전문검색용 tsvector 컬럼에는 STORED를 반드시 명시하세요.
🔤

pg_trgm — 오타 허용과 부분일치

전문검색이 "단어 단위"로 동작한다면, pg_trgm은 완전히 다른 접근을 씁니다. 문자열을 세 글자씩 잘게 쪼개(trigram) 비교하는 방식입니다.

비유 — 단어를 조각내어 겹쳐보기. postgres를 세 글자씩 자르면 pos, ost, stg, tgr, gre, res가 나옵니다. postgrey도 자르면 pos, ost, stg, tgr, gre, rey죠.

둘을 겹쳐보면 6개 중 5개가 같습니다. 마지막 글자만 틀렸으니까요. 그래서 similarity()가 높은 점수를 줍니다. 단어 전체를 비교하는 게 아니라 조각의 겹침 비율을 보기 때문에, 오타가 있어도 대부분의 조각이 살아남아 매칭됩니다.

sqlstudy_db=# — 유사도 점수와 오타 허용
CREATE EXTENSION IF NOT EXISTS pg_trgm;

SELECT similarity('postgres', 'postgrey') AS sim;   -- 오타에도 높은 점수
--     sim
-- -----------
--  0.6363636

-- % : 유사도가 임계값(기본 0.3) 이상이면 참 → 오타 'Postgrez'도 찾아낸다
SELECT title FROM docs WHERE title % 'Postgrez';
--        title
-- -------------------
--  Postgres indexing

하지만 pg_trgm의 진짜 위력은 다른 데 있습니다. 트라이그램 GIN 인덱스를 만들면, 앞에서 "절대 인덱스를 못 탄다"고 했던 선두 와일드카드 ILIKE '%...%'가 인덱스를 탑니다.

원리는 자연스럽습니다. %fuzzy%를 조각내면 fuz, uzz, zzy가 되고, GIN 인덱스는 "이 조각들을 가진 행 번호"를 이미 알고 있으니까요. 앞뒤에 뭐가 붙어 있든 상관없습니다.

sqlstudy_db=# — trigram GIN이 ILIKE '%..%'를 가속
CREATE INDEX idx_docsbig_body_trgm ON docs_big USING gin (body gin_trgm_ops);

EXPLAIN (COSTS OFF)
SELECT title FROM docs_big WHERE body ILIKE '%fuzzy%';
--                     QUERY PLAN
-- --------------------------------------------------
--  Bitmap Heap Scan on docs_big
--    Recheck Cond: (body ~~* '%fuzzy%'::text)
--    ->  Bitmap Index Scan on idx_docsbig_body_trgm   ← 선두 와일드카드인데 인덱스를 탄다!
--          Index Cond: (body ~~* '%fuzzy%'::text)
한국어 검색에는 pg_trgm이 현실적인 답입니다. 앞서 봤듯 한국어는 기본 형태소 사전이 없어 tsvector의 효과가 제한적입니다. 반면 트라이그램은 언어를 전혀 몰라도 됩니다 — 글자를 세 개씩 자를 뿐이니까요. "전문검색"을 자르면 전문검, 문검색이 되므로 "문검"으로 검색해도 걸립니다. 형태소 분석 없이도 실용적인 부분일치 검색이 됩니다. 정밀한 자연어 검색이 필요해지면 그때 전용 한국어 형태소 확장을 도입하면 됩니다.
MySQL — 익숙한 방식

FULLTEXT 인덱스 + MATCH(col) AGAINST('word')로 전문검색을 합니다. 자연어/불리언 모드를 지원하지만, 오타 허용·트라이그램 유사도 검색은 기본 제공하지 않습니다.

PostgreSQL — 이렇게 다르다

tsvector + @@ + ts_rank로 어간 분석·랭킹까지 하는 본격 전문검색을 제공하고, 거기에 더해 pg_trgm으로 오타·부분일치를 인덱스로 가속합니다. 둘을 상황에 맞게 조합할 수 있는 게 강점입니다.

셀프 체크

Q LIKE '%x%'는 왜 느린가요?

B-tree 인덱스는 값을 앞 글자부터 정렬해 두기 때문에, "앞이 무엇이든 상관없이 중간에 x가 들어간 것"을 찾는 선두 와일드카드에는 정렬이 아무 도움이 안 됩니다. 결국 모든 행을 풀스캔합니다. 참고로 LIKE 'x%'(뒤쪽 와일드카드)는 인덱스를 탈 수 있습니다. 부분일치가 꼭 필요하면 pg_trgm 트라이그램 GIN 인덱스가 정답입니다.

Q to_tsvector를 WHERE 절에서 매번 계산하면 안 되는 이유는?

쿼리 실행 시점에 계산되는 값이라 그 값을 담은 인덱스가 존재할 수 없어 모든 행에 대해 새로 계산하는 풀스캔이 됩니다. 정답은 생성 컬럼(STORED)에 tsvector를 미리 저장하고 그 컬럼에 GIN 인덱스를 거는 것입니다. PG18에서는 STORED를 생략하면 virtual이 되어 인덱스를 못 걸므로 반드시 명시하세요.

Q pg_trgm이 특히 잘하는 것은?

오타 허용과 부분일치입니다. 문자열을 세 글자 조각으로 쪼개 겹침 비율을 보므로, 한두 글자가 틀려도 대부분의 조각이 살아남아 매칭됩니다. 트라이그램 GIN 인덱스를 만들면 ILIKE '%..%'까지 인덱스를 탑니다.

Q 한국어 검색은 어떻게 접근해야 하나요?

Postgres 기본 사전에는 한국어 형태소 분석이 없습니다. 'simple' 설정을 쓰면 공백 단위로만 끊겨 "전문"으로 "전문검색"을 못 찾습니다. 현실적인 답은 pg_trgm 트라이그램 인덱스로 ILIKE '%검색어%'를 가속하는 것입니다 — 트라이그램은 언어를 몰라도 되기 때문에 한국어에서도 잘 작동합니다. 정밀한 자연어 검색이 필요하면 전용 한국어 형태소 확장을 별도로 도입합니다.
