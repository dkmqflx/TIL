인덱스 종류 — B-tree · GIN · GiST · BRIN · partial · expression

인덱스는 책 뒤의 찾아보기입니다. 그런데 Postgres에는 찾아보기가 한 종류가 아닙니다 — 데이터 모양에 맞는 색인을 골라 쓰는 것이 이 레슨의 전부입니다.

한 줄 요약. 인덱스는 읽기를 빠르게 하는 대신 쓰기와 공간을 대가로 내는 거래입니다. 그래서 "많이 만들수록 좋다"가 절대 아니고, 실제 쿼리에 근거해 필요한 것만 만들어야 합니다.

학습 목표

  • 인덱스가 왜 빠른지, 그리고 무엇을 대가로 치르는지 설명한다
  • B-tree · GIN · GiST · BRIN을 각각 언제 쓰는지 구분한다
  • partial · expression 인덱스로 인덱스를 작고 정확하게 만든다
  • 멀티컬럼 인덱스의 왼쪽 접두 규칙을 이해하고 컬럼 순서를 정한다
📇

인덱스 기본 — 왜 빠르고, 무엇을 치르는가

비유 — 500쪽 요리책에서 "양파" 찾기. 첫 장부터 끝까지 넘기며 찾으면(=Seq Scan) 확실하긴 하지만 오래 걸립니다. 반면 책 뒤의 찾아보기에서 "양파 → 12, 88, 301쪽"을 보면 그 세 곳으로 바로 펼치면 됩니다. DB 인덱스도 똑같습니다 — 컬럼 값을 미리 정렬해 두고 "이 값 → 몇 번 행"을 기록해 둔 것이죠.

그런데 찾아보기에는 대가가 있습니다. 책 뒤에 수십 쪽이 더 붙고(공간), 내용을 한 줄이라도 고치면 찾아보기도 함께 고쳐야 합니다(쓰기 비용). DB도 똑같아서 INSERT·UPDATE·DELETE가 일어날 때마다 관련 인덱스를 전부 갱신해야 합니다.

읽기 빨라짐 ↔ 쓰기 느려짐 + 디스크 공간 증가

그래서 인덱스는 "많을수록 좋은" 것이 아니라 저울질의 대상입니다. 이 감각을 갖고 시작합시다.

기본이자 가장 많이 쓰는 것은 B-tree입니다. 등호(=), 범위(< > BETWEEN), 정렬(ORDER BY), 그리고 접두 LIKE('서울%')까지 처리합니다. 특별한 이유가 없으면 B-tree라고 생각하면 됩니다. 10만 행 테이블에서 실제로 인덱스를 타는 모습을 봅시다.

sqlstudy_db=# — B-tree, 10만 행에서 등호 검색
CREATE INDEX idx_users_age ON users (age);
ANALYZE users;                          -- 통계 갱신(중요! Lesson 02 참고)

EXPLAIN (ANALYZE, BUFFERS, COSTS OFF)
SELECT * FROM users WHERE age = 25;
--                                         QUERY PLAN
-- ------------------------------------------------------------------------------------------
--  Bitmap Heap Scan on users (actual time=0.120..0.547 rows=1667.00 loops=1)
--    Recheck Cond: (age = 25)
--    ->  Bitmap Index Scan on idx_users_age (actual time=0.068..0.068 rows=1667.00 loops=1)
--          Index Cond: (age = 25)

10만 행 중 1,667행만 정확히 집어냈습니다. 참고로 결과가 이렇게 어느 정도 많을 때 Postgres는 Index Scan 대신 Bitmap Index Scan을 자주 고릅니다 — 왜 그런지는 다음 레슨에서 다룹니다.

🗂️

종류별 용도 — 데이터 모양에 맞춰 고른다

MySQL을 쓰다 온 사람이 가장 놀라는 부분입니다. Postgres에는 인덱스 종류가 여러 개이고, 모두 같은 문법(USING)으로 만듭니다. 무엇을 언제 쓰는지 한 표로 정리하면 이렇습니다.

종류언제 쓰나예시 쿼리
B-tree (기본)등호·범위·정렬·접두 LIKE — 대부분의 경우WHERE age > 30 ORDER BY created_at
GIN한 행에 값이 여러 개 — jsonb·배열·전문검색WHERE data @> '{...}'
GiST범위 겹침·기하·근접 검색range &&, ORDER BY pt <-> ...
BRIN거대한 자연정렬 테이블(시계열 등) — 극도로 작음로그 WHERE ts BETWEEN ...
Hash등호 전용 — 드묾, 보통 B-tree로 충분WHERE token = '...'

GIN과 GiST는 이미 만났습니다 — Week 3의 jsonb·전문검색이 GIN, Week 2의 EXCLUDE 예약 충돌 방지가 GiST였죠. 여기서는 앱 개발에서 잘 보이지 않지만 알면 무기가 되는 BRIN을 살펴보겠습니다.

비유 — 서가마다 붙은 "이 칸은 A~C" 팻말.

B-tree가 모든 책의 위치를 하나하나 적은 목록이라면, BRIN은 서가 칸마다 "여기는 A~C가 있어요" 팻말만 붙여둔 것입니다. 정보가 훨씬 성기죠.

그런데 책이 알파벳순으로 꽂혀 있다면 이 팻말만으로도 충분합니다. "K로 시작하는 책"을 찾을 때 A~C 칸, D~F 칸을 전부 건너뛰고 J~L 칸만 뒤지면 되니까요. 대신 책이 무작위로 꽂혀 있다면 모든 팻말이 "A~Z"라고 적혀 있을 테니 아무 도움이 안 됩니다.

이게 BRIN의 전부입니다. 데이터가 디스크에 정렬된 순서로 쌓여 있을 때만 작동하지만, 그 조건이 맞으면 믿기 힘들 만큼 작습니다.

sqlstudy_db=# — BRIN vs B-tree 크기 비교 (50만 행 시계열)
CREATE INDEX idx_sensors_ts_brin  ON sensors USING brin (ts);
CREATE INDEX idx_sensors_ts_btree ON sensors (ts);
SELECT
  pg_size_pretty(pg_relation_size('idx_sensors_ts_brin'))  AS brin_size,
  pg_size_pretty(pg_relation_size('idx_sensors_ts_btree')) AS btree_size;
--  brin_size | btree_size
-- -----------+------------
--  24 kB     | 11 MB          ← 약 450배 차이!

-- BRIN으로도 범위 조회가 잘 된다 (B-tree 제거 후 실행)
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF)
SELECT count(*) FROM sensors WHERE ts BETWEEN '2024-01-02' AND '2024-01-03';
--                           QUERY PLAN
-- --------------------------------------------------------------------
--  Aggregate (actual time=8.230..8.231 rows=1.00 loops=1)
--    ->  Bitmap Heap Scan on sensors (... rows=86401.00 loops=1)
--          Recheck Cond: ((ts >= ...) AND (ts <= ...))
--          ->  Bitmap Index Scan on idx_sensors_ts_brin (... rows=6400.00 loops=1)
BRIN의 정식 이름이 곧 설명입니다. Block Range INdex — 각 행이 아니라 물리 블록 묶음마다 최소/최대값만 저장합니다. 그래서 24 kB로 11 MB짜리 B-tree와 비슷한 범위 조회를 해냅니다. 조건은 하나 — 컬럼 값이 디스크에 정렬된 순서로 쌓여 있어야 합니다. 로그의 ts, 자동증가 id가 대표적입니다. 무작위 UUID(v4) 같은 값에는 아무 효과가 없습니다.
🎯

partial · expression 인덱스 — 정확히 필요한 것만

partial index — 일부 행만 색인하기

partial index는 테이블의 일부 행만 인덱싱합니다. 예를 들어 회원 10만 명 중 inactive가 5%뿐인데 "비활성 계정 조회"가 잦다면, 그 5%만 색인하면 됩니다.

비유 — 목차를 전체가 아니라 "부록"만 만들기. 500쪽 책에서 부록(25쪽)만 자주 찾아본다면, 책 전체 찾아보기를 만들 필요 없이 부록 전용 색인만 만들면 됩니다. 훨씬 얇고, 만들기도 유지하기도 쌉니다. 단, 부록 밖의 내용을 찾을 때는 쓸 수 없죠 — 그래서 쿼리의 WHERE가 partial 조건과 맞아야 인덱스가 사용됩니다.
sqlstudy_db=# — partial index (inactive 5%만) + 크기 비교
CREATE INDEX idx_users_inactive ON users (id) WHERE status = 'inactive';

EXPLAIN (ANALYZE, BUFFERS, COSTS OFF)
SELECT id FROM users WHERE status = 'inactive';
--                                             QUERY PLAN
-- ---------------------------------------------------------------------------------------------------
--  Index Only Scan using idx_users_inactive on users (actual time=0.019..1.057 rows=5000.00 loops=1)

-- 부분 인덱스(inactive 5%)는 전체 status 인덱스보다 훨씬 작다
--  partial_size | full_size
-- --------------+-----------
--  128 kB       | 696 kB

실무에서 partial index가 특히 잘 맞는 자리가 있습니다. "처리되지 않은 것"만 계속 조회하는 큐 테이블입니다. 주문 1,000만 건 중 pending은 항상 수백 건뿐이라면, WHERE status = 'pending' partial index는 영원히 작게 유지됩니다.

expression index — 함수 결과를 색인하기

expression index는 컬럼이 아니라 함수를 적용한 결과를 인덱싱합니다. 대소문자를 무시하는 로그인처럼 WHERE lower(email) = ...를 자주 쓴다면 반드시 필요합니다.

왜 필요한가. 일반 email 인덱스에는 User500@Example.com이 원래 형태 그대로 들어 있습니다. 그런데 우리는 lower(email) 즉 user500@example.com을 찾고 있죠. 인덱스에 없는 값을 찾는 셈이라 인덱스를 쓸 수 없습니다. 그래서 찾을 형태 그대로 색인해야 합니다. 이 함정은 다음 레슨에서 정면으로 다룹니다.
sqlstudy_db=# — expression index: lower(email)
CREATE INDEX idx_users_lower_email ON users (lower(email));

EXPLAIN (ANALYZE, BUFFERS, COSTS OFF)
SELECT id FROM users WHERE lower(email) = 'user500@example.com';
--                                           QUERY PLAN
-- -----------------------------------------------------------------------------------------------
--  Bitmap Heap Scan on users (actual time=0.592..0.593 rows=1.00 loops=1)
--    Recheck Cond: (lower(email) = 'user500@example.com'::text)
--    ->  Bitmap Index Scan on idx_users_lower_email (... rows=1.00 loops=1)
🔢

멀티컬럼 인덱스 · 컬럼 순서 · covering

여러 컬럼을 묶은 (a, b) 인덱스에는 반드시 알아야 할 규칙이 하나 있습니다. 왼쪽 접두(left-prefix) 규칙입니다.

비유 — 전화번호부는 "성 → 이름" 순. 전화번호부는 성으로 먼저 정렬하고, 같은 성 안에서 이름순으로 정렬돼 있습니다.

"김"씨를 찾는 건 쉽죠(선두 컬럼만 있어도 됨). "김철수"를 찾는 것도 쉽습니다(선두 + 두 번째). 그런데 "철수"만 알고 성을 모른다면? 정렬이 아무 도움이 안 됩니다 — 처음부터 끝까지 넘겨야 하죠.

인덱스도 똑같습니다. (a, b) 인덱스는 a 단독이나 a+b에는 쓰이지만, b만으로는 쓸 수 없습니다. 그래서 컬럼 순서가 성능을 좌우합니다 — 항상 WHERE에 등장하는 컬럼을 앞에 두세요.

여기에 INCLUDE를 붙이면 covering index가 됩니다. 자주 함께 조회하는 컬럼을 인덱스에 얹어 두면, 테이블 본체를 열어보지 않고 인덱스만으로 결과를 돌려줄 수 있습니다(Index Only Scan). 찾아보기 옆에 "이 단어가 나온 문장"까지 적어둔 셈이죠.

sqlstudy_db=# — (email, age) 복합 인덱스의 왼쪽 접두 규칙
CREATE INDEX idx_users_email_age ON users (email, age) INCLUDE (status);

-- ① 선두 컬럼(email) + age → 복합 인덱스 사용. INCLUDE(status) 덕에 Index Only Scan
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF)
SELECT status FROM users WHERE email = 'User500@Example.com' AND age = 38;
--                                            QUERY PLAN
-- -------------------------------------------------------------------------------------------------
--  Index Only Scan using idx_users_email_age on users (actual time=0.018..0.019 rows=1.00 loops=1)
--    Index Cond: ((email = 'User500@Example.com'::text) AND (age = 38))
--    Heap Fetches: 1

-- ② 선두 컬럼(email) 없이 age만으로는 이 인덱스를 못 쓴다 → Seq Scan
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF)
SELECT * FROM users WHERE age = 30;
--                             QUERY PLAN
-- -------------------------------------------------------------------
--  Seq Scan on users (actual time=0.007..2.268 rows=1667.00 loops=1)
--    Filter: (age = 30)
--    Rows Removed by Filter: 98333      ← 9만 8천 행을 읽고 버렸다
PG18 skip scan — 왼쪽 접두 규칙의 예외. PostgreSQL 18은 B-tree skip scan을 추가했습니다. 선두 컬럼의 서로 다른 값이 아주 적으면(예: status가 active/inactive 둘뿐), 플래너가 그 몇 개 값을 하나씩 "건너뛰며" 훑어서 선두 컬럼 조건 없이도 복합 인덱스를 쓸 수 있습니다. 다만 위 예처럼 선두 컬럼이 email(고유값이 수만 개)이면 건너뛸 게 너무 많아 무의미하므로 평소처럼 Seq Scan이 됩니다. 큰 줄기는 여전히 "선두 컬럼을 빼지 마라"입니다.
MySQL — 익숙한 방식

InnoDB는 사실상 B-tree 하나가 주력입니다. 전문검색은 FULLTEXT, 공간 데이터는 SPATIAL로 별도 취급합니다. partial index는 없고(생성 컬럼으로 우회), 함수 인덱스·INCLUDE는 최근 버전에서 제한적으로 지원합니다.

PostgreSQL — 이렇게 다르다

여러 인덱스 방식을 같은 문법(USING)으로 다룹니다. jsonb·배열·전문검색은 전부 GIN 하나로, 거대한 시계열은 BRIN으로. partial·expression·covering이 모두 1급 기능이라 데이터 모양에 맞춰 정밀하게 고를 수 있습니다.

인덱스 남발은 부채입니다. 인덱스가 많을수록 읽기는 빨라질 수 있어도 모든 쓰기가 느려지고 공간이 늘어납니다 — INSERT 한 번에 인덱스 10개를 전부 갱신해야 하니까요. 게다가 아무도 안 쓰는 인덱스는 이득 없는 순수 비용입니다. 실제 쿼리(WHERE/JOIN/ORDER BY)에 근거해 만들고, pg_stat_user_indexes로 사용량을 주기적으로 점검해 안 쓰는 것은 지우세요.
✅

셀프 체크

Q 인덱스를 많이 만들면 왜 안 되나요?

인덱스는 별도의 디스크 공간을 차지하고, 행이 바뀔 때마다 함께 갱신해야 하므로 모든 INSERT/UPDATE/DELETE가 느려집니다. 특히 아무도 안 쓰는 인덱스는 이득 없이 비용만 냅니다. pg_stat_user_indexes로 사용량을 점검해 정리하세요.

Q GIN 인덱스는 언제 쓰나요?

한 행에 값이 여러 개 들어 있고 그 안의 원소·키를 검색할 때입니다 — jsonb(@> 포함 검색), 배열(원소 포함), 전문검색(tsvector). GIN은 값을 잘게 쪼개 "이 값 → 이 행들"이라는 역색인을 만듭니다.

Q BRIN은 언제 효과가 있고, 언제 무용지물인가요?

컬럼 값이 디스크에 정렬된 순서로 쌓여 있을 때만 효과가 있습니다(시계열 ts, 자동증가 id). 블록 묶음마다 최소/최대값만 저장하므로 극도로 작습니다(예제에서 24 kB vs B-tree 11 MB). 반면 무작위로 흩어진 값(UUIDv4 등)에는 모든 블록의 범위가 겹쳐 아무 효과가 없습니다.

Q (a, b) 인덱스를 b만으로 검색에 쓸 수 있나요?

원칙적으로 못 씁니다 — 왼쪽 접두 규칙 때문입니다. 인덱스가 a로 먼저 정렬돼 있어서, a 조건이 없으면 어디서 읽기 시작할지 알 수 없습니다(전화번호부에서 성을 모르고 이름만 아는 상황). 그래서 컬럼 순서를 정할 때 항상 WHERE에 등장하는 컬럼을 앞에 둬야 합니다. PG18의 skip scan은 선두 컬럼의 값 종류가 아주 적을 때에 한해 예외를 허용합니다.
