EXPLAIN ANALYZE — 플래너 · 통계 · 인덱스 함정

"이 쿼리 왜 느리지?"를 추측으로 답하지 마세요. EXPLAIN ANALYZE는 Postgres가 쿼리를 실제로 어떻게 실행하는지 보여주는 X-레이입니다.

한 줄 요약. Postgres의 모든 성능 판단은 통계에서 나옵니다. 통계가 정확하면 좋은 실행 계획이, 통계가 낡으면 인덱스가 있어도 엉뚱한 계획이 나옵니다. 그래서 이 레슨의 절반이 "통계" 이야기입니다.

학습 목표

  • EXPLAIN(추정)과 EXPLAIN ANALYZE(실측)를 읽고 구분한다
  • Seq Scan · Index Scan · Bitmap Heap Scan을 플래너가 언제 고르는지 안다
  • 통계가 낡으면 왜 플랜이 망가지는지 실제로 재현해 본다
  • 인덱스를 못 타게 만드는 대표적인 실수 네 가지를 피한다
🔬

EXPLAIN 읽는 법 — 추정 vs 실측

먼저 두 명령의 차이부터 확실히 해둡시다. 이름은 비슷한데 하는 일이 전혀 다릅니다.

🗺️
EXPLAIN — 실행하지 않는다
쿼리를 실행하지 않고 플래너의 계획과 비용 추정만 보여줍니다. cost는 임의 단위의 추정치, rows는 예상 행 수입니다. 안전하지만 "정말 그럴까?"는 알 수 없습니다.
⏱️
EXPLAIN ANALYZE — 진짜 실행한다
쿼리를 실제로 실행한 뒤 actual time(실측 시간)과 실제 rows를 함께 보여줍니다. BUFFERS를 추가하면 읽은 페이지 수(I/O)까지 나옵니다.
EXPLAIN ANALYZE는 쿼리를 진짜로 실행합니다. SELECT야 상관없지만, UPDATE나 DELETE에 붙이면 데이터가 실제로 변경됩니다. 운영 DB에서 변경 쿼리의 계획을 보고 싶다면 BEGIN; → EXPLAIN ANALYZE ... → ROLLBACK;으로 감싸세요.
sqlstudy_db=# — EXPLAIN(추정만) vs EXPLAIN ANALYZE(실측)
-- 추정만: 실행하지 않고 비용 추정만 (cost, 예상 rows)
EXPLAIN
SELECT * FROM orders WHERE user_id = 42;
--                                   QUERY PLAN
-- -------------------------------------------------------------------------------
--  Bitmap Heap Scan on orders  (cost=4.45..74.81 rows=20 width=30)
--    Recheck Cond: (user_id = 42)
--    ->  Bitmap Index Scan on idx_orders_user  (cost=0.00..4.44 rows=20 width=0)
--          Index Cond: (user_id = 42)

-- 실측: 실제 실행 + actual time/rows + 버퍼(I/O)
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE user_id = 42;
--  Bitmap Heap Scan on orders  (cost=4.45..74.81 rows=20 ...) (actual time=0.050..0.072 rows=20.00 loops=1)
--    Recheck Cond: (user_id = 42)
--    Buffers: shared hit=20 read=2
--    ->  Bitmap Index Scan on idx_orders_user (...) (actual time=0.042..0.042 rows=20.00 loops=1)
--          Index Cond: (user_id = 42)
--  Execution Time: 0.085 ms

실행 계획은 아래에서 위로 읽습니다. 들여쓰기가 깊은 안쪽 노드(->)가 먼저 실행되고, 그 결과가 위로 전달됩니다. 위 예에서는 ① 인덱스로 행 위치들을 모으고(Bitmap Index Scan) → ② 그 위치로 테이블에서 실제 행을 가져옵니다(Bitmap Heap Scan).

가장 먼저 볼 것 하나만 꼽으라면: 추정 rows와 실제 rows의 차이입니다. 위에서는 rows=20 추정에 실제도 rows=20.00 — 통계가 정확하다는 좋은 신호입니다. 이 둘이 10배 이상 벌어지면 거의 확실히 통계 문제입니다.

🔀

Seq Scan vs Index Scan vs Bitmap Heap Scan

"인덱스가 있으면 무조건 인덱스를 탄다"는 아주 흔한 오해입니다. Postgres 플래너는 선택도(selectivity) — 즉 "전체 중 몇 %를 가져오는가"를 보고 더 싼 쪽을 고릅니다.

비유 — 500쪽 책에서 찾기.

"양파가 나오는 3쪽"을 찾는다면 → 찾아보기를 보고 그 3쪽만 펼치는 게 압도적으로 빠릅니다(Index Scan).

그런데 "소금이 나오는 480쪽"을 찾는다면? 찾아보기에서 480개 페이지 번호를 읽고 책장을 480번 왔다 갔다 넘기느니, 그냥 처음부터 순서대로 넘기는 게 빠릅니다(Seq Scan). 순서대로 넘기는 건 이리저리 점프하는 것보다 훨씬 쌉니다.

디스크도 똑같습니다. 순차 읽기는 무작위 읽기보다 훨씬 빠릅니다. 그래서 결과가 많으면 인덱스가 오히려 손해입니다.

같은 컬럼·같은 테이블에서 선택도만 바꿔 두 경우를 모두 봅시다. status는 shipped가 5%, pending이 95%입니다.

sqlstudy_db=# — 낮은 선택도 → Index Scan / 높은 선택도 → Seq Scan
-- (a) shipped 5% : 적게 골라내므로 인덱스 경로가 이득
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF)
SELECT * FROM orders WHERE status = 'shipped';
--  Index Scan using idx_orders_status on orders (actual time=0.025..1.020 rows=5000.00 loops=1)
--    Index Cond: (status = 'shipped'::text)
--    Buffers: shared hit=736 read=6

-- (b) pending 95% : 거의 다 가져오므로 인덱스가 손해 → Seq Scan
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF)
SELECT * FROM orders WHERE status = 'pending';
--  Seq Scan on orders (actual time=0.006..4.725 rows=95000.00 loops=1)
--    Filter: (status = 'pending'::text)
--    Rows Removed by Filter: 5000

인덱스는 똑같이 존재하는데 플래너가 스스로 판단해 (b)에서는 쓰지 않았습니다. 이건 문제가 아니라 올바른 판단입니다.

스캔 방식동작유리한 상황
Seq Scan테이블을 처음부터 통째로 읽는다작은 테이블, 또는 결과가 대부분일 때
Index Scan인덱스로 행을 하나씩 찾아 본체로 점프결과가 아주 적을 때
Bitmap Heap Scan인덱스로 행 위치를 먼저 다 모은 뒤, 본체를 블록 순서대로 한 번에 읽는다중간 규모 결과 — 무작위 점프를 줄이려고
Bitmap Heap Scan이 존재하는 이유. Index Scan은 "인덱스 보고 → 점프 → 인덱스 보고 → 점프"를 반복해서, 결과가 늘어나면 디스크를 이리저리 헤매게 됩니다. Bitmap 방식은 갈 곳을 전부 먼저 적어둔 다음, 디스크 순서대로 한 번에 훑습니다. 마치 장보기 목록을 먼저 만들고 매장을 한 바퀴 도는 것과 같죠. 그래서 결과가 "적지도 많지도 않을 때" 가장 효율적입니다.
📊

통계와 ANALYZE — 추정이 틀리면 플랜도 틀린다

여기가 이 레슨의 핵심입니다. 앞에서 본 플래너의 모든 판단은 통계에 근거합니다. Postgres는 각 컬럼의 값 분포(어떤 값이 얼마나 자주 나오는지, 값의 범위는 어떤지)를 pg_statistic에 저장해 두고, 그걸 보고 "이 조건이면 대략 몇 행"인지 추측합니다.

비유 — 작년 지도로 길 찾기. 통계는 DB가 갖고 있는 데이터 지도입니다. 지도가 최신이면 최단 경로를 잘 찾죠. 그런데 대량 UPDATE로 데이터 분포가 확 바뀌었는데 지도를 갱신하지 않으면, 플래너는 여전히 옛 지도를 보고 "이쪽이 지름길"이라 판단합니다. 결과는 엉뚱하게 느린 실행 계획입니다. 인덱스를 아무리 잘 만들어도 소용없습니다.

통계는 ANALYZE 명령이나 백그라운드의 autovacuum이 갱신합니다. 평소엔 자동으로 관리되지만, 대량 변경 직후에는 갱신이 따라오지 못할 수 있습니다. 일부러 망가뜨려서 직접 확인해 봅시다.

sqlstudy_db=# — 통계가 낡으면 플랜이 틀린다
UPDATE orders SET status = 'shipped' WHERE id <= 90000;  -- 5% → 90%로 급변

-- ANALYZE 전: 여전히 'shipped'=5%로 착각 → 인덱스 경로(잘못된 선택)
EXPLAIN (ANALYZE, COSTS OFF)
SELECT * FROM orders WHERE status = 'shipped';
--  Index Scan using idx_orders_status on orders (actual time=3.343..9.765 rows=90500.00 loops=1)
--    Index Cond: (status = 'shipped'::text)
--    ↑ 9만 행을 인덱스로 하나씩 찾아 점프 — 9.7ms

-- ANALYZE 후: 통계 갱신 → Seq Scan으로 교정
ANALYZE orders;
EXPLAIN (ANALYZE, COSTS OFF)
SELECT * FROM orders WHERE status = 'shipped';
--  Seq Scan on orders (actual time=0.442..5.830 rows=90500.00 loops=1)
--    Filter: (status = 'shipped'::text)
--    Rows Removed by Filter: 9500
--    ↑ 같은 결과인데 5.8ms — 통계만 고쳤을 뿐인데 40% 빨라졌다

쿼리도 인덱스도 전혀 바꾸지 않았습니다. 오직 통계만 갱신했는데 실행 계획이 바뀌고 빨라졌습니다. 이게 "통계가 성능을 좌우한다"는 말의 실체입니다.

추정이 자꾸 틀린다면 이렇게 하세요.

① 대량 적재·삭제 직후에는 ANALYZE 테이블명;을 직접 실행해 통계를 새로 고칩니다. 배치 작업 스크립트 마지막 줄에 넣어두면 좋습니다.

② 분포가 심하게 치우친 컬럼이라면 표본이 부족한 것일 수 있습니다. default_statistics_target(기본 100)을 올리거나, 특정 컬럼만 ALTER TABLE ... ALTER COLUMN ... SET STATISTICS 1000으로 조정합니다.

③ 진단 신호는 언제나 같습니다 — 플랜의 추정 rows와 실제 rows가 크게 다르면 통계를 의심하세요.

🕳️

인덱스 함정 — 만들어 놓고 못 쓰는 실수들

"인덱스를 만들었는데도 느려요"라는 질문의 대부분은 이 네 가지 중 하나입니다. 가장 흔한 것부터 봅시다.

함정 ① 인덱스 컬럼에 함수나 연산을 씌운다

WHERE upper(status) = 'SHIPPED'는 status 인덱스를 쓰지 못합니다. 이유는 단순합니다 — 인덱스에는 status의 원래 값(shipped)이 들어 있는데, 우리가 찾는 건 upper(status)(SHIPPED)이니까요. 인덱스에 없는 값을 찾는 셈입니다.

sqlstudy_db=# — 함정과 교정
-- (함정) upper(status)는 status 인덱스를 못 탄다 → Seq Scan
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF)
SELECT * FROM orders WHERE upper(status) = 'SHIPPED';
--  Seq Scan on orders (actual time=0.872..14.114 rows=5000.00 loops=1)
--    Filter: (upper(status) = 'SHIPPED'::text)
--    Rows Removed by Filter: 95000        ← 14ms

-- (교정) 찾는 형태 그대로 색인하면 다시 인덱스를 탄다
CREATE INDEX idx_orders_upper_status ON orders (upper(status));
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF)
SELECT * FROM orders WHERE upper(status) = 'SHIPPED';
--  Bitmap Heap Scan on orders (actual time=0.197..1.111 rows=5000.00 loops=1)
--    Recheck Cond: (upper(status) = 'SHIPPED'::text)
--    ->  Bitmap Index Scan on idx_orders_upper_status (... rows=5000.00 loops=1)
--    ↑ 1.1ms — 약 13배 빨라졌다

함정 ② 앞 와일드카드 LIKE

LIKE '%ipped'처럼 %로 시작하면 B-tree를 쓸 수 없습니다. Week 3에서 봤듯 B-tree는 앞 글자부터 정렬돼 있어서, 시작 글자를 모르면 어디서부터 읽을지 알 수 없기 때문입니다.

sqlstudy_db=# — 앞 와일드카드 LIKE '%ipped' → Seq Scan
EXPLAIN (ANALYZE, COSTS OFF)
SELECT * FROM orders WHERE status LIKE '%ipped';
--  Seq Scan on orders (actual time=0.331..4.821 rows=5000.00 loops=1)
--    Filter: (status ~~ '%ipped'::text)
--    Rows Removed by Filter: 95000

해법은 Week 3에서 배운 pg_trgm 트라이그램 GIN 인덱스입니다. 반대로 LIKE 'ship%'(뒤쪽 와일드카드)는 일반 B-tree로도 잘 동작합니다.

함정 ③·④ 타입 불일치와 OR 조건

함정왜 문제인가해법
③ 암묵적 타입 캐스팅
WHERE varchar_col = 123		비교하려고 캐스팅이 끼어들면 함정 ①과 같은 상황이 됩니다 — 인덱스의 원래 값과 다른 것을 찾게 되죠양쪽 타입을 맞춰서 비교
④ OR 조건
WHERE a=1 OR b=2		서로 다른 컬럼의 인덱스를 합치기 어려워 종종 Seq Scan이 됩니다UNION으로 분리하면 각자 인덱스를 탈 수 있습니다
네 함정을 한 문장으로. "인덱스에 들어 있는 값 그대로 비교하고 있는가?"를 물어보세요. 함수를 씌우거나(①), 앞을 가리거나(②), 타입을 바꾸면(③) — 전부 인덱스에 없는 값을 찾는 셈이 됩니다. 이 하나의 원리로 세 가지가 설명됩니다.
MySQL — 익숙한 방식

EXPLAIN으로 계획을 봅니다(전통적으로 한 행 표 형태, 8.0+는 FORMAT=TREE·JSON 지원). EXPLAIN ANALYZE는 8.0.18+부터 실측을 보여줍니다. type(ALL=풀스캔), rows, key 열을 읽는 식입니다.

PostgreSQL — 이렇게 다르다

노드 트리로 훨씬 상세하게 보여줍니다. EXPLAIN (ANALYZE, BUFFERS)는 각 노드의 추정 vs 실측 rows, 시간, 버퍼 I/O까지 나란히 보여주므로 "통계가 틀렸는지"를 바로 진단할 수 있습니다.

셀프 체크

Q cost와 actual time의 차이는?

cost는 플래너가 실행 전에 매긴 추정 비용(임의 단위), actual time은 ANALYZE로 실제 실행한 뒤 측정한 밀리초입니다. EXPLAIN만 쓰면 추정만, EXPLAIN ANALYZE를 쓰면 둘 다 나옵니다. 진단할 때 가장 먼저 볼 것은 추정 rows와 실제 rows의 차이입니다.

Q 인덱스가 있는데도 Seq Scan이 나오면 문제인가요?

대부분 문제가 아니라 올바른 판단입니다. 찾는 행이 테이블의 큰 비중(예: 95%)을 차지하면, 인덱스로 하나씩 찾아 점프하는 무작위 I/O보다 통째로 순차 읽는 게 더 쌉니다. 작은 테이블에서도 마찬가지입니다. 다만 결과가 적은데도 Seq Scan이 나온다면 통계나 인덱스 함정을 의심하세요.

Q 데이터를 대량으로 바꾼 뒤 쿼리가 느려졌습니다. 무엇부터 확인할까요?

ANALYZE 테이블명;으로 통계를 갱신해 보세요. 대량 변경 직후에는 통계가 옛 분포를 담고 있어 플래너가 잘못된 계획을 고를 수 있습니다. 실제로 예제에서 쿼리와 인덱스를 전혀 바꾸지 않고 ANALYZE만 실행했더니 계획이 Index Scan에서 Seq Scan으로 교정되며 빨라졌습니다.

Q WHERE 컬럼에 함수를 쓰면 왜 인덱스를 못 타나요?

인덱스에는 컬럼의 원래 값이 저장돼 있는데, upper(status) 같은 함수 결과는 그 안에 없기 때문입니다 — 인덱스에 없는 값을 찾는 셈이라 Seq Scan이 됩니다. 해법은 찾을 형태 그대로 색인하는 expression index(CREATE INDEX ... (upper(status)))입니다. 같은 원리로 앞 와일드카드 LIKE와 암묵적 타입 캐스팅도 인덱스를 무력화합니다.
