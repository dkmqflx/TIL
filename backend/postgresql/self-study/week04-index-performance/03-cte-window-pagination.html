CTE · 윈도우 함수 · keyset pagination · N+1

분석과 리포팅 SQL의 세 가지 무기입니다. CTE로 복잡한 쿼리를 단계로 쪼개고, 윈도우 함수로 순위·누계를 내고, keyset으로 깊은 페이지를 빠르게 넘깁니다.

한 줄 요약. 이 레슨의 도구들은 전부 "앱 코드에서 반복문으로 하던 일을 SQL 한 문장으로 옮기는" 것입니다. 왕복이 줄어드는 만큼 빨라지고, 코드도 짧아집니다.

학습 목표

  • WITH(CTE)와 재귀 CTE로 복잡한 쿼리를 읽기 쉽게 분해한다
  • 윈도우 함수로 순위·누계·전후 비교를 내고 GROUP BY와 구분한다
  • OFFSET 페이지네이션의 문제를 이해하고 keyset으로 바꾼다
  • N+1 패턴을 알아보고 한 번의 쿼리로 합친다
🪜

CTE(WITH) — 단계를 쪼개고, 재귀로 계층을 순회

CTE(Common Table Expression)는 쿼리 안에서 중간 결과에 이름을 붙이는 도구입니다. 문법은 WITH 이름 AS (...) 한 줄이 전부인데, 효과는 큽니다.

비유 — 레시피를 단계로 나눠 적기. "양파를 볶은 것 위에 미리 삶아둔 면을 넣고…"처럼 한 문장에 다 우겨넣으면 읽기 힘듭니다. "① 면 삶기 → ② 양파 볶기 → ③ 합치기"로 나눠 적으면 훨씬 명확하죠. CTE가 하는 일이 정확히 이것입니다 — 서브쿼리가 3중, 4중으로 중첩된 괴물 SQL을 위에서 아래로 읽히는 단계로 펼칩니다.

그리고 CTE에는 일반 SQL로는 도저히 할 수 없는 일을 해내는 특별한 형태가 있습니다. WITH RECURSIVE입니다.

댓글 트리를 생각해 보세요. 댓글에 답글이 달리고, 그 답글에 또 답글이 달립니다. 깊이가 몇 단계인지 미리 알 수 없죠. 일반 JOIN으로는 "3단계까지"처럼 미리 정해야만 쓸 수 있습니다. 재귀 CTE는 끝까지 알아서 내려갑니다.

sqlstudy_db=# — 재귀 CTE로 댓글 트리 순회 (depth 계산)
WITH RECURSIVE tree AS (
  -- ① 앵커: 출발점 — 루트(부모 없는 댓글)에서 시작
  SELECT id, parent_id, body, 0 AS depth
  FROM comments WHERE parent_id IS NULL
  UNION ALL
  -- ② 재귀: 방금 찾은 행들의 자식을 찾아 depth + 1 (더 찾을 게 없을 때까지 반복)
  SELECT c.id, c.parent_id, c.body, t.depth + 1
  FROM comments c JOIN tree t ON c.parent_id = t.id
)
SELECT id, depth, repeat('  ', depth) || body AS thread FROM tree ORDER BY id;
--  id | depth |      thread
-- ----+-------+------------------
--   1 |     0 | 원댓글
--   2 |     1 |   답글 A
--   3 |     1 |   답글 B
--   4 |     2 |     답글 A-1
--   5 |     3 |       답글 A-1-1

구조는 항상 똑같습니다. 앵커(출발점) + UNION ALL + 재귀(한 단계 더 내려가기). Postgres는 재귀 부분이 더 이상 새 행을 못 찾을 때까지 반복하고 멈춥니다. 조직도(상사→부하), 카테고리 트리, 자재명세(BOM) 등에 그대로 응용됩니다.

CTE는 기본적으로 인라인 최적화됩니다. 예전 Postgres에서 CTE는 항상 독립적으로 먼저 실행(materialize)되어, 의도치 않게 최적화를 막는 벽이 되곤 했습니다. PG12부터는 (한 번만 참조되고 부작용이 없으면) 본 쿼리에 인라인해 함께 최적화합니다. 반대로 일부러 한 번만 계산해 재사용하고 싶다면 WITH x AS MATERIALIZED (...)로 명시할 수 있습니다.
🪟

윈도우 함수 — 행을 접지 않고 옆에 계산 붙이기

윈도우 함수를 이해하는 가장 빠른 길은 GROUP BY와 나란히 놓고 보는 것입니다.

비유 — 성적표 두 가지.

GROUP BY는 반 평균만 적힌 요약본입니다. 개별 학생 줄은 사라지고 "1반 82점, 2반 79점"만 남죠. 행을 접어서 줄이니까요.

윈도우 함수는 학생별 성적표에 "반 평균"과 "반에서 몇 등" 칸이 추가된 것입니다. 원래 줄은 하나도 사라지지 않고, 옆에 계산 결과가 붙습니다.

둘은 대체 관계가 아니라 용도가 다릅니다. "지역 총합만" 필요하면 GROUP BY, "각 일자를 보면서 지역 내 순위와 누계도" 필요하면 윈도우 함수입니다.

문법의 핵심은 OVER (...) 하나입니다. 그 안의 두 부분만 알면 됩니다.

부분의미비유
PARTITION BY region어떤 단위로 나눠서 계산할지"반별로"
ORDER BY ymd그 안에서 어떤 순서로 볼지"날짜순으로"
sqlstudy_db=# — ROW_NUMBER / RANK / 누계 / LAG / LEAD
SELECT
  region, ymd, amount,
  ROW_NUMBER() OVER (PARTITION BY region ORDER BY amount DESC) AS rn,
  RANK()       OVER (PARTITION BY region ORDER BY amount DESC) AS rnk,
  DENSE_RANK() OVER (PARTITION BY region ORDER BY amount DESC) AS d_rnk,
  SUM(amount)  OVER (PARTITION BY region ORDER BY ymd)         AS running_total,
  amount - LAG(amount)  OVER (PARTITION BY region ORDER BY ymd) AS vs_prev,
  LEAD(amount)          OVER (PARTITION BY region ORDER BY ymd) AS next_amt
FROM sales ORDER BY region, ymd;
--  region |    ymd     | amount | rn | rnk | d_rnk | running_total | vs_prev | next_amt
-- --------+------------+--------+----+-----+-------+---------------+---------+----------
--  Busan  | 2024-01-01 |    200 |  2 |   2 |     2 |           200 |         |      180
--  Busan  | 2024-01-02 |    180 |  3 |   3 |     3 |           380 |     -20 |      220
--  Busan  | 2024-01-03 |    220 |  1 |   1 |     1 |           600 |      40 |
--  Seoul  | 2024-01-01 |    100 |  3 |   3 |     3 |           100 |         |      150
--  Seoul  | 2024-01-02 |    150 |  1 |   1 |     1 |           250 |      50 |      120
--  Seoul  | 2024-01-03 |    120 |  2 |   2 |     2 |           370 |     -30 |

결과를 하나씩 뜯어봅시다. running_total은 지역별로 날짜순 누적 합계입니다(부산: 200 → 380 → 600). vs_prev는 전날 대비 증감이고, 첫 행은 비교할 이전 행이 없어 비어 있습니다. next_amt는 반대로 다음 행의 값을 미리 당겨온 것이라 마지막 행이 비어 있죠.

순위 세 형제는 동점을 어떻게 다루느냐만 다릅니다.

함수동점 처리예 (100, 100, 90)
ROW_NUMBER()동점이어도 무조건 고유 번호1, 2, 3
RANK()동점은 같은 순위, 다음은 건너뜀1, 1, 3
DENSE_RANK()동점은 같은 순위, 건너뛰지 않음1, 1, 2

위 예제 데이터에는 동점이 없어서 rnk와 d_rnk가 같게 나왔습니다. "공동 2등 다음이 4등인가 3등인가"를 결정하는 게 이 차이입니다.

📄

keyset pagination — OFFSET의 깊은 페이지 문제

페이지네이션을 LIMIT 10 OFFSET 50000으로 구현하면, 5,000번째 페이지에서 눈에 띄게 느려집니다. 왜 그럴까요?

비유 — 책갈피 없이 매번 처음부터 세기. OFFSET 50000은 DB에게 "앞의 5만 행을 읽어서 버리고, 그다음 10개를 줘"라고 요청하는 것입니다. 건너뛰라고 했지만 실제로는 다 읽습니다 — 읽어야 몇 개인지 셀 수 있으니까요. 페이지가 깊어질수록 버리는 양이 선형으로 늘어납니다. 반면 keyset은 "어제 읽던 곳에 꽂아둔 책갈피"를 쓰는 것과 같습니다. "마지막으로 본 게 50000번이었으니 그 다음부터"라고 직접 지목하므로, 몇 페이지째든 항상 똑같이 빠릅니다.

10만 행 피드에서 둘을 비교해 봅시다. 정렬 키 (created_at, id)에 복합 인덱스가 걸려 있는 상태입니다.

sqlstudy_db=# — OFFSET 50000 vs keyset
-- (a) OFFSET 깊은 페이지: 앞 50,010행을 읽고 버린다 (느림)
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF)
SELECT id, created_at FROM feed ORDER BY created_at, id OFFSET 50000 LIMIT 10;
--  Limit (actual time=6.475..6.477 rows=10.00 loops=1)
--    Buffers: shared hit=368 read=194
--    ->  Index Only Scan using idx_feed_created on feed (actual ... rows=50010.00 loops=1)
--          Heap Fetches: 50010                 ← 5만 행을 읽고 버렸다

-- (b) keyset: 마지막으로 본 (created_at, id)보다 큰 행부터 → 인덱스로 즉시 점프
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF)
SELECT id, created_at FROM feed
WHERE (created_at, id) > (timestamptz '2024-01-01' + interval '50000 seconds', 50000)
ORDER BY created_at, id LIMIT 10;
--  Limit (actual time=0.006..0.007 rows=10.00 loops=1)
--    Buffers: shared hit=4
--    ->  Index Only Scan using idx_feed_created on feed (actual ... rows=10.00 loops=1)
--          Index Cond: (ROW(created_at, id) > ROW(..., 50000))
--          Heap Fetches: 10                    ← 딱 10행만 읽었다

숫자를 비교하면 차이가 분명합니다. OFFSET은 50,010행 · 버퍼 562 · 6.5ms, keyset은 10행 · 버퍼 4 · 0.007ms. 같은 인덱스를 쓰는데도 이만큼 차이가 납니다.

비결은 (created_at, id) > (값, 값)이라는 행 비교(튜플 비교) 문법입니다. 이게 복합 인덱스의 Index Cond로 그대로 들어가 정확히 그 지점부터 읽기 시작합니다.

OFFSET의 문제는 속도만이 아닙니다.

중복과 누락이 생깁니다. 1페이지를 본 뒤 2페이지를 요청하는 사이에 새 글이 하나 올라오면, 전체가 한 칸씩 밀려서 1페이지 마지막 글이 2페이지에 또 나옵니다. 반대로 글이 삭제되면 한 개가 통째로 건너뛰어집니다. 무한 스크롤에서 같은 글이 두 번 보이는 흔한 버그의 정체가 이것입니다.

keyset은 "이 값 다음"을 내용 기준으로 지목하므로 이런 흔들림이 없습니다. 단, 정렬 키에 유일성이 있어야 합니다 — created_at만으로는 같은 시각의 행이 여럿일 수 있으니 (created_at, id)처럼 고유 컬럼을 마지막에 붙이는 것이 정석입니다.

➕

N+1 — 여러 번 쿼리 대신 한 방에

ORM을 쓰다 보면 반드시 만나는 함정입니다. 이름 그대로 쿼리 1번 + N번이 나가는 패턴이죠.

비유 — 장 볼 때마다 마트에 다시 가기. 요리 재료 20개가 필요한데 하나 사고 집에 왔다가 또 나가기를 20번 반복하는 것과 같습니다. 각 왕복은 짧아도 20번 쌓이면 하루가 갑니다. 글 목록 20개를 가져온 뒤 각 글의 작성자를 한 명씩 20번 더 조회하면 쿼리가 21번 — DB는 안 느린데 왕복 시간이 쌓여 응답이 느려집니다. 해결책은 당연히 목록을 만들어 한 번에 사오는 것입니다.
sqlstudy_db=# — N+1 대신 JOIN 한 방
-- 각 행마다 따로 조회하지 말고 한 쿼리로 합친다
SELECT s.region, s.ymd, s.amount, t.region_total
FROM sales s
JOIN (
  SELECT region, SUM(amount) AS region_total FROM sales GROUP BY region
) t ON t.region = s.region
ORDER BY s.region, s.ymd;
--  region |    ymd     | amount | region_total
-- --------+------------+--------+--------------
--  Busan  | 2024-01-01 |    200 |          600
--  Busan  | 2024-01-02 |    180 |          600
--  Busan  | 2024-01-03 |    220 |          600
--  Seoul  | 2024-01-01 |    100 |          370
--  Seoul  | 2024-01-02 |    150 |          370
--  Seoul  | 2024-01-03 |    120 |          370
사실 위 쿼리는 윈도우 함수 한 줄이면 됩니다. SUM(amount) OVER (PARTITION BY region)으로 바꾸면 서브쿼리도 JOIN도 필요 없이 같은 결과가 나오고, 읽기도 훨씬 쉽습니다. 판단 기준은 이렇습니다 — 다른 테이블의 엔티티를 붙일 땐 JOIN, 같은 테이블의 집계를 각 행 옆에 붙일 땐 윈도우 함수.
MySQL — 익숙한 방식

윈도우 함수·CTE·재귀 CTE는 MySQL 8.0부터 지원됩니다(그 이전엔 사용자 변수나 서브쿼리로 우회해야 했습니다). keyset pagination의 개념과 문법은 동일합니다.

PostgreSQL — 이렇게 다르다

윈도우 함수·CTE를 오래전부터 지원해 왔습니다. 특히 행 비교 (a,b) > (x,y)를 복합 인덱스의 Index Cond로 그대로 밀어 넣어 keyset을 깔끔하게 구현할 수 있고, MATERIALIZED로 CTE 최적화도 직접 제어할 수 있습니다.

✅

셀프 체크

Q 윈도우 함수와 GROUP BY의 차이는?

GROUP BY는 행을 접어서 그룹당 한 줄로 줄입니다(개별 행이 사라짐). 윈도우 함수는 원본 행을 그대로 두고 각 행 옆에 계산값(순위·누계·전후 비교)을 덧붙입니다. "반 평균만 적힌 요약본"과 "학생별 성적표에 반 평균 칸이 추가된 것"의 차이입니다.

Q OFFSET 페이지네이션의 두 가지 문제는?

① 느립니다. OFFSET 50000은 건너뛸 5만 행을 실제로 읽은 뒤 버립니다. 페이지가 깊어질수록 선형으로 느려집니다. ② 결과가 흔들립니다. 페이지를 넘기는 사이 행이 삽입·삭제되면 전체가 밀려서 중복이나 누락이 생깁니다. keyset은 "이 값 다음"을 내용 기준으로 지목하므로 두 문제가 모두 없습니다.

Q keyset pagination의 정렬 키를 정할 때 주의할 점은?

정렬 키에 유일성이 있어야 합니다. created_at만 쓰면 같은 시각의 행이 여럿일 때 경계에서 중복·누락이 생깁니다. (created_at, id)처럼 고유 컬럼을 마지막에 붙여 순서를 확정하고, 그 키 조합에 복합 인덱스를 만들어야 Index Cond로 곧장 점프합니다.

Q 재귀 CTE는 어디에 쓰나요?

깊이를 미리 알 수 없는 계층·그래프 구조를 순회할 때입니다 — 댓글 트리, 조직도, 카테고리 트리, 자재명세(BOM) 등. 앵커(루트)에서 시작해 UNION ALL로 자식을 따라 내려가며, 더 이상 새 행을 못 찾을 때까지 반복합니다. 일반 JOIN으로는 "몇 단계까지"를 미리 정해야만 가능합니다.
