트랜잭션과 격리 수준 — 동시에 도는 작업들을 어떻게 조율하나

트랜잭션은 "전부 아니면 전무"입니다. 격리 수준은 동시에 도는 트랜잭션이 서로를 얼마나 보는가를 정하는 다이얼이고요 — Postgres의 기본값은 READ COMMITTED입니다.

MySQL에서 넘어왔다면 이것부터. MySQL의 기본 격리 수준은 REPEATABLE READ, Postgres는 READ COMMITTED입니다. 그래서 MySQL에서 당연했던 "한 트랜잭션 안에서 읽은 값이 안 변한다"가 Postgres 기본값에서는 성립하지 않습니다. 이 레슨에서 가장 중요한 실무 차이입니다.

학습 목표

  • BEGIN/COMMIT/ROLLBACK과 SAVEPOINT로 트랜잭션을 다룬다
  • 격리 수준이 낮을 때 생기는 네 가지 이상현상을 구분한다
  • 격리 수준 4단계를 알고, Postgres가 표준보다 강한 지점을 안다
  • MySQL과의 기본값 차이가 실무에서 무엇을 뜻하는지 이해한다
🏦

트랜잭션 기본 — ACID · BEGIN/COMMIT · SAVEPOINT

비유 — 송금. "Alice 계좌에서 200을 빼고, Bob 계좌에 200을 더한다." 이 둘은 반드시 같이 성공하거나 같이 취소되어야 합니다. 인출만 되고 입금이 실패하면 돈이 세상에서 사라집니다. 트랜잭션은 여러 문장을 하나의 "전부 아니면 전무" 단위로 묶는 장치입니다.

트랜잭션이 보장하는 네 가지 성질을 머리글자로 ACID라고 부릅니다.

글자이름뜻
AAtomicity (원자성)전부 적용되거나 전부 취소된다 — 중간 상태는 없다
CConsistency (일관성)제약·규칙을 깨뜨린 채로 끝나지 않는다
IIsolation (격리성)동시에 도는 트랜잭션이 서로를 방해하지 않는다 ← 이 레슨의 주제
DDurability (영속성)COMMIT한 결과는 서버가 죽어도 살아남는다
sqlstudy_db=# — BEGIN/COMMIT(송금)과 ROLLBACK(취소)
-- 송금: 인출과 입금을 한 트랜잭션으로 묶는다 (둘 다 성공 또는 둘 다 취소)
BEGIN;
  UPDATE accounts SET balance = balance - 200 WHERE owner = 'Alice';
  UPDATE accounts SET balance = balance + 200 WHERE owner = 'Bob';
COMMIT;
--  owner | balance
-- -------+---------
--  Alice |  800.00
--  Bob   |  700.00

-- ROLLBACK: 중간에 취소하면 변경이 없던 일이 된다
BEGIN;
  UPDATE accounts SET balance = balance - 300 WHERE owner = 'Alice';
ROLLBACK;
--  owner | balance
-- -------+---------
--  Alice |  800.00     ← 그대로 (롤백됨)
--  Bob   |  700.00

긴 트랜잭션 안에서 일부만 되돌리고 싶을 때는 SAVEPOINT를 씁니다. 책갈피를 꽂아두고 거기까지만 되감는 셈이죠.

sqlstudy_db=# — SAVEPOINT / ROLLBACK TO (부분 취소)
BEGIN;
  UPDATE accounts SET balance = balance + 50 WHERE owner = 'Alice';
  SAVEPOINT sp1;                                                    -- 책갈피
  UPDATE accounts SET balance = balance + 9999 WHERE owner = 'Bob';  -- 실수!
  ROLLBACK TO sp1;   -- Bob 변경만 취소, Alice +50은 살아 있음
  UPDATE accounts SET balance = balance + 10 WHERE owner = 'Bob';    -- 다시 정상 처리
COMMIT;
--  owner | balance
-- -------+---------
--  Alice |  850.00     ← +50 유지
--  Bob   |  710.00     ← +10만 반영 (잘못된 +9999는 취소됨)
앱에서는 직접 BEGIN을 쓰지 않는 경우가 많습니다. 대부분의 드라이버·ORM은 트랜잭션 블록(with conn.transaction():, @Transactional 등)을 제공합니다. 블록을 정상 통과하면 커밋, 예외가 던져지면 자동 롤백이죠. 참고로 psql에서 BEGIN 없이 실행한 단일 문장은 그 자체가 하나의 트랜잭션입니다(autocommit).
👻

이상현상 — 동시 트랜잭션이 만드는 네 가지 사고

격리가 약하면 동시에 도는 트랜잭션들이 서로의 미완성 작업을 들여다보며 이상현상(anomaly)을 일으킵니다. SQL 표준이 정의한 네 가지를 비유와 함께 봅시다.

이상현상무슨 일이 벌어지나일상 비유
Dirty read
더러운 읽기		아직 커밋되지 않은 남의 변경을 읽는다 — 곧 롤백될 수도 있는 값남의 연필로 쓴 초안을 확정본인 줄 알고 베낌
Non-repeatable read
반복 불가 읽기		같은 행을 두 번 읽었는데 그 사이 누가 커밋해서 값이 달라짐계산기를 두 번 눌렀는데 답이 다름
Phantom read
유령 읽기		같은 조건으로 두 번 조회했는데 행 개수가 달라짐참석자 명단을 다시 세니 한 명이 늘어 있음
Serialization anomaly
직렬화 이상		각각은 성공했는데, 그 결과가 어떤 순서로 하나씩 실행해도 나올 수 없는 상태두 당직자가 서로 "쟤가 있으니 나는 빠져도 돼"라고 판단해 둘 다 빠짐
마지막 것이 가장 어려우니 조금 더. 병원에 당직 의사가 항상 1명 이상이어야 한다고 합시다. 지금 Alice와 Bob 둘이 당직 중입니다. 두 사람이 동시에 "다른 한 명이 남아 있으니 나는 빠져도 되겠지"라고 확인하고 각자 빠집니다. 각자의 판단은 옳았고 각 트랜잭션도 성공했는데, 결과는 당직 0명입니다. 순서대로 한 명씩 실행했다면 절대 나올 수 없는 상태죠. 이런 걸 write skew라 부르고, 이걸 막으려면 SERIALIZABLE이 필요합니다.

아래 표는 PostgreSQL의 실제 동작입니다(공식 문서 Table 13.1 기준). 표준이 "허용될 수 있다"고 둔 칸도 PG는 더 강하게 막는 경우가 있습니다.

격리 수준Dirty readNon-repeatablePhantomSerialization anomaly
READ UNCOMMITTED막힘 PG가능가능가능
READ COMMITTED (기본)막힘가능가능가능
REPEATABLE READ막힘막힘막힘 PG가능
SERIALIZABLE막힘막힘막힘막힘

PG 표시가 표준과 다른 부분입니다. PostgreSQL은 READ UNCOMMITTED에서도 dirty read를 절대 허용하지 않고(아예 구현하지 않았습니다), REPEATABLE READ가 phantom까지 막습니다.

🎚️

격리 수준 4단계 — 안전과 성능 사이의 다이얼

격리 수준은 "동시성 안전"과 "성능·재시도 부담" 사이의 다이얼입니다. 위로 갈수록 안전하지만 충돌과 재시도가 늘어납니다.

수준보는 방식실무 메모
READ UNCOMMITTED표준에선 미완성 데이터도 읽음PG에선 READ COMMITTED와 동일 — dirty read를 구현하지 않음
READ COMMITTED
(PG 기본)		각 문장이 시작될 때의 스냅샷을 본다커밋된 값만 읽지만, 한 트랜잭션 안에서도 문장마다 스냅샷이 갱신된다
REPEATABLE READ트랜잭션 시작 시점의 스냅샷을 끝까지 본다PG에선 phantom까지 함께 막힘. 충돌 쓰기 시 직렬화 실패 가능
SERIALIZABLE위에 SSI를 더해 직렬화 이상까지 차단가장 안전. 대신 앱이 재시도를 구현해야 함

비유 — 스냅샷은 "그 순간 찍은 사진".

READ COMMITTED는 문장을 실행할 때마다 새로 사진을 찍습니다. 그래서 한 트랜잭션 안이라도 첫 번째 SELECT와 두 번째 SELECT가 다른 세상을 볼 수 있죠.

REPEATABLE READ는 트랜잭션 시작할 때 사진을 한 장 찍고 끝까지 그것만 봅니다. 그 사이에 세상이 아무리 바뀌어도 내가 보는 화면은 고정입니다.

sqlstudy_db=# — 기본값 확인 & 트랜잭션 단위 설정
-- Postgres 기본 격리 수준
SHOW default_transaction_isolation;
--  default_transaction_isolation
-- -------------------------------
--  read committed

-- 이번 트랜잭션만 REPEATABLE READ로 (스냅샷 격리)
BEGIN;
  SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
  SELECT current_setting('transaction_isolation') AS lvl;
COMMIT;
--        lvl
-- -----------------
--  repeatable read

-- SERIALIZABLE도 같은 방식 (직렬화 실패 시 앱이 재시도해야 함)
BEGIN ISOLATION LEVEL SERIALIZABLE;
  SELECT current_setting('transaction_isolation') AS lvl;
COMMIT;
--      lvl
-- --------------
--  serializable

높은 격리 수준을 켤 때 반드시 알아야 할 두 가지.

① REPEATABLE READ 이상에서는 트랜잭션이 실패할 수 있습니다. 다른 트랜잭션과 충돌하는 쓰기를 만나면 could not serialize access due to concurrent update 에러로 통째로 abort됩니다. 낮은 격리 수준에서는 그냥 기다렸다 진행했을 상황이죠.

② SERIALIZABLE은 재시도가 전제입니다. SSI(Serializable Snapshot Isolation)는 직렬화 불가를 감지하면 한쪽을 40001 에러로 중단시킵니다. 앱이 이 에러를 잡아 같은 트랜잭션을 처음부터 다시 실행하는 루프를 갖춰야 합니다. 락으로 미리 막는 게 아니라 낙관적으로 실행하고 나중에 검증하는 방식이라, 평소엔 빠르지만 충돌 처리 책임이 앱에 있습니다.

⏱️

두 세션 타임라인 — non-repeatable read를 눈으로

이상현상은 두 트랜잭션이 동시에 돌 때만 관찰됩니다. psql 창 하나로는 재현할 수 없으니(자기 자신과는 충돌하지 않으니까요), 터미널을 두 개 띄워 따라 해보시길 권합니다. 먼저 기본값인 READ COMMITTED입니다.

시각Session A READ COMMITTEDSession B
t1BEGIN;
t2SELECT balance ... 'Alice'; → 800
t3UPDATE ... SET balance=900 ...; COMMIT;
t4SELECT balance ... 'Alice'; → 900 😱
t5COMMIT; — 같은 트랜잭션인데 값이 바뀌었다

t2와 t4는 같은 트랜잭션 안의 같은 쿼리인데 다른 답이 나왔습니다. 이게 non-repeatable read입니다. "잔액을 확인하고 그에 따라 판단하는" 로직이라면 심각한 버그가 됩니다.

같은 시나리오에서 Session A만 REPEATABLE READ로 바꿔봅시다.

시각Session A REPEATABLE READSession B
t1BEGIN ISOLATION LEVEL REPEATABLE READ;
t2SELECT balance ... 'Alice'; → 800
t3UPDATE ... =900; COMMIT;
t4SELECT balance ...; → 800 ✅ (스냅샷 고정)
t5COMMIT; — 트랜잭션 내내 일관된 값

A는 시작 시점의 사진을 끝까지 보므로 B의 커밋이 보이지 않습니다. 주의할 점은 이게 "B의 변경을 무시한다"는 뜻이 아니라는 것입니다 — A가 그 행을 고치려 하면 그때 직렬화 실패가 발생합니다.

MySQL — 익숙한 방식

InnoDB의 기본은 REPEATABLE READ입니다. 일반 SELECT는 트랜잭션 시작 스냅샷을 보고, phantom은 갭 락(gap lock)으로 막습니다. 그래서 "한 트랜잭션 안에서 읽기가 안 변한다"는 감각이 기본값에서 성립합니다.

PostgreSQL — 이렇게 다르다

기본이 READ COMMITTED입니다. 각 문장마다 새 스냅샷을 뜨므로, 한 트랜잭션 안에서도 문장 사이에 남의 커밋이 보입니다. MySQL에서 넘어온 팀이 가장 자주 헛디디는 지점입니다 — 읽기 일관성이 필요하면 명시적으로 REPEATABLE READ를 켜세요.

✅

셀프 체크

Q READ COMMITTED와 REPEATABLE READ의 차이는?

READ COMMITTED는 문장마다 새 스냅샷을 떠서, 한 트랜잭션 안에서도 남의 커밋이 다음 문장에 보입니다(non-repeatable read 가능). REPEATABLE READ는 트랜잭션 시작 시점의 스냅샷을 끝까지 유지해 보는 데이터가 변하지 않습니다(PG에선 phantom까지 방지). 대신 충돌 쓰기를 만나면 직렬화 실패로 끝날 수 있습니다.

Q PostgreSQL의 기본 격리 수준은? MySQL과 무엇이 다른가요?

PostgreSQL은 READ COMMITTED, MySQL InnoDB는 REPEATABLE READ입니다. 그래서 MySQL에서 당연하던 "한 트랜잭션 내 읽기 불변"이 PG 기본값에서는 성립하지 않습니다. PG에서 같은 보장을 원하면 트랜잭션을 명시적으로 REPEATABLE READ로 시작해야 합니다. 마이그레이션 시 가장 조심해야 할 차이입니다.

Q SERIALIZABLE을 쓸 때 앱이 반드시 준비해야 할 것은?

재시도(retry) 로직입니다. SERIALIZABLE은 SSI로 직렬화 불가를 감지하면 한쪽 트랜잭션을 40001(serialization failure) 에러로 abort합니다. 앱은 이 에러를 잡아 같은 트랜잭션을 처음부터 다시 실행해야 합니다. 락이 아닌 낙관적 방식이라 평소엔 빠르지만, 충돌 처리 책임이 애플리케이션에 있습니다.

Q SAVEPOINT는 언제 쓰나요?

긴 트랜잭션 안에서 일부만 되돌리고 싶을 때입니다. SAVEPOINT sp1;으로 책갈피를 찍고 ROLLBACK TO sp1;으로 그 지점까지만 취소하면, 그 이전의 작업은 그대로 살아 있습니다. 여러 단계로 이뤄진 배치 처리에서 한 단계만 실패했을 때 유용합니다.
