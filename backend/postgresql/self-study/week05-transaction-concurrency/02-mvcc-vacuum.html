MVCC · VACUUM — Postgres의 심장을 들여다보기

Postgres는 행을 덮어쓰지 않습니다. 새 버전을 쓰고 옛 버전을 "죽은 튜플"로 남기죠(MVCC). 그리고 그 시체를 치우는 청소부가 VACUUM입니다.

왜 이걸 알아야 하나. Postgres 운영에서 발생하는 성능 문제의 상당수가 이 한 가지 메커니즘에서 나옵니다. "왜 테이블이 계속 커지지?", "왜 쿼리가 점점 느려지지?"의 답이 대부분 여기 있습니다. MySQL에는 대응되는 개념이 없기 때문에 특히 낯설고, 그래서 특히 중요합니다.

학습 목표

  • MVCC의 원리를 xmin·xmax·스냅샷으로 이해한다
  • 죽은 튜플이 왜 생기는지, VACUUM이 무엇을 회수하는지 안다
  • autovacuum과 bloat(팽창)의 관계를 이해하고 모니터링 지표를 안다
  • 긴 트랜잭션이 왜 위험한지 설명하고 예방한다
🧬

MVCC 원리 — UPDATE는 덮어쓰기가 아니다

MVCC는 Multi-Version Concurrency Control, 즉 다중 버전 동시성 제어의 약자입니다. 이름 그대로 한 행의 여러 버전을 동시에 유지하는 방식이죠.

비유 — 문서를 고칠 때 덮어쓰지 않고 새 버전으로 저장하기.

공유 문서를 여러 명이 동시에 보고 있습니다. 누군가 내용을 고칠 때 원본을 지우고 덮어쓰면, 지금 읽고 있던 사람들의 화면이 갑자기 바뀌어 버립니다. 읽는 도중에 문장이 사라질 수도 있죠.

그래서 Postgres는 옛 버전을 그대로 두고 새 버전을 따로 저장합니다. 읽던 사람은 자기가 시작할 때의 버전을 끝까지 보고, 새로 들어온 사람은 최신 버전을 봅니다. 읽는 사람과 쓰는 사람이 서로 기다리지 않는 비결이 바로 이것입니다.

이게 Week 1에서 "Postgres의 강점"으로 언급했던 "읽는 사람과 쓰는 사람이 서로 기다리지 않는다"의 실체입니다. 그럼 DB는 "어느 버전을 보여줄지"를 어떻게 판단할까요? 모든 행에 붙어 있는 숨은 시스템 컬럼을 씁니다.

숨은 컬럼담고 있는 것
xmin이 버전을 만든 트랜잭션 ID
xmax이 버전을 만료시킨 트랜잭션 ID (아직 살아 있으면 0)
ctid이 버전의 물리적 위치 (블록 번호, 오프셋)

"이 버전이 내 눈에 보이는가"는 내 스냅샷과 xmin/xmax를 비교해 결정됩니다. 대략 "내가 시작하기 전에 커밋된 트랜잭션이 만들었고, 아직 만료되지 않았다면 보인다"는 규칙이죠. 직접 확인해 봅시다.

sqlstudy_db=# — UPDATE 3번 → ctid가 바뀐다 (새 물리 버전)
-- 처음 상태: xmin은 만든 트랜잭션, xmax=0(살아 있음), ctid=(블록,오프셋)
SELECT xmin, xmax, ctid, * FROM items;
--  xmin | xmax | ctid  | id |  name  | price
-- ------+------+-------+----+--------+-------
--   804 |    0 | (0,1) |  1 | coffee |  4500

-- 같은 논리적 행을 세 번 UPDATE → 매번 새 물리 버전 생성
UPDATE items SET price = 4600 WHERE name = 'coffee';
UPDATE items SET price = 4700 WHERE name = 'coffee';
UPDATE items SET price = 4800 WHERE name = 'coffee';

-- 살아 있는 버전은 하나지만 ctid가 (0,1) → (0,4)로 옮겨졌다
SELECT xmin, xmax, ctid, * FROM items;
--  xmin | xmax | ctid  | id |  name  | price
-- ------+------+-------+----+--------+-------
--   807 |    0 | (0,4) |  1 | coffee |  4800
--                 ↑ 1번 자리가 아니라 4번 자리에 있다!

ctid가 (0,1)에서 (0,4)로 옮겨간 것이 결정적 증거입니다. 같은 자리를 고친 게 아니라 매번 새 자리에 새 버전을 쓴 것이죠. 그리고 (0,1), (0,2), (0,3)에는 아무도 못 보는 옛 버전 3개가 그대로 남아 있습니다.

따라 할 때 참고. xmin/xmax는 트랜잭션 ID라서 실행할 때마다 값이 달라집니다(위의 804·807은 이 실행에서 나온 예시일 뿐입니다). 반면 ctid는 물리 위치라 같은 시나리오면 그대로 재현됩니다.
🧹

죽은 튜플과 VACUUM — 시체 치우기

방금 남겨진 옛 버전 3개를 죽은 튜플(dead tuple)이라고 부릅니다. 어떤 트랜잭션도 더는 볼 수 없는데 디스크 공간은 계속 차지하고 있죠. 이걸 회수하는 것이 VACUUM의 일입니다.

items 테이블의 물리적 상태 (UPDATE 3번 후)
ctidprice상태
(0,1)4500dead — 아무도 못 봄
(0,2)4600dead — 아무도 못 봄
(0,3)4700dead — 아무도 못 봄
(0,4)4800live — 현재 버전
sqlstudy_db=# — n_dead_tup: VACUUM 전 3, 후 0
-- 통계는 비동기로 모이므로 잠깐 기다린 뒤 갱신
SELECT pg_sleep(1);  ANALYZE items;
SELECT relname, n_live_tup, n_dead_tup
FROM pg_stat_user_tables WHERE relname = 'items';
--  relname | n_live_tup | n_dead_tup
-- ---------+------------+------------
--  items   |          1 |          3     ← 살아있는 1개 + 죽은 3개

-- VACUUM: 죽은 튜플을 회수해 그 공간을 "재사용 가능"하게 만든다
VACUUM (VERBOSE) items;
-- INFO:  finished vacuuming "study_db.public.items": index scans: 0
--   tuples: 3 removed, 1 remain, 0 are dead but not yet removable ...

SELECT pg_sleep(1);  ANALYZE items;
SELECT relname, n_live_tup, n_dead_tup
FROM pg_stat_user_tables WHERE relname = 'items';
--  relname | n_live_tup | n_dead_tup
-- ---------+------------+------------
--  items   |          1 |          0     ← 죽은 튜플 회수됨

중요한 오해 — VACUUM은 디스크를 OS에 돌려주지 않습니다.

일반 VACUUM은 죽은 튜플이 있던 공간을 "이 테이블이 다시 써도 좋다"고 표시만 합니다. 파일 크기는 거의 그대로예요. 비유하자면 방을 비운 것이지 방을 없앤 게 아닙니다 — 곧 새 데이터가 그 자리에 들어오니 오히려 효율적이죠.

디스크를 정말로 OS에 반환하려면 VACUUM FULL이 테이블을 통째로 재작성해야 합니다. 하지만 그동안 테이블에 ACCESS EXCLUSIVE 락이 걸려 읽기조차 막힙니다. 운영 중인 서비스에서는 절대 함부로 쓰지 마세요 — 필요하다면 pg_repack 같은 무중단 도구를 검토합니다.

🎈

autovacuum과 bloat — 청소를 못 따라가면 부푼다

죽은 튜플을 매번 사람이 치울 수는 없습니다. 그래서 Postgres는 백그라운드에서 autovacuum 데몬을 돌립니다. 죽은 튜플이 일정 수준을 넘으면 자동으로 VACUUM과 ANALYZE를 실행하죠.

sqlstudy_db=# — autovacuum 임계치와 모니터링
SHOW autovacuum_vacuum_threshold;       -- 50
SHOW autovacuum_vacuum_scale_factor;    -- 0.2 (= 행의 20%)
-- → 죽은 튜플이 (50 + 0.2 × 행수)를 넘으면 autovacuum 발동

-- 마지막 (auto)vacuum 시각 모니터링
SELECT relname, last_vacuum, last_autovacuum
FROM pg_stat_user_tables WHERE relname = 'items';
--  relname |         last_vacuum          | last_autovacuum
-- ---------+------------------------------+-----------------
--  items   | 2026-06-09 13:02:18.98198+00 |

문제는 autovacuum이 변경 속도를 따라가지 못할 때 생깁니다. 죽은 튜플이 계속 쌓여 테이블과 인덱스가 bloat(팽창)됩니다. 살아 있는 행은 그대로인데 파일만 계속 커지고, 스캔할 페이지가 늘어 쿼리가 느려지죠.

비유 — 쓰레기를 안 치운 방. 물건(살아 있는 행)은 하나뿐인데 쓰레기(죽은 튜플)가 방을 가득 채우면, 물건 하나를 찾으려고 방 전체를 뒤져야 합니다. 방 크기가 곧 검색 비용이 되는 거죠. 그래서 bloat이 심해지면 데이터는 그대로인데 쿼리만 느려지는 이상한 현상이 나타납니다.

일부러 만들어 보겠습니다. 한 행을 999번 UPDATE합니다(autovacuum을 꺼둔 테이블입니다).

sqlstudy_db=# — 1행을 999번 UPDATE → 죽은 튜플 폭증 = bloat
DO $$ BEGIN FOR k IN 1..999 LOOP
  UPDATE items SET price = price + 1 WHERE name = 'coffee';
END LOOP; END $$;

SELECT pg_sleep(1);  ANALYZE items;
SELECT relname, n_live_tup, n_dead_tup,
       pg_size_pretty(pg_table_size('items')) AS table_size
FROM pg_stat_user_tables WHERE relname = 'items';
--  relname | n_live_tup | n_dead_tup | table_size
-- ---------+------------+------------+------------
--  items   |          1 |        999 | 88 kB      ← 살아있는 행은 1개인데 88kB (처음엔 16kB)

-- VACUUM으로 회수: 죽은 튜플은 0이 되지만 파일 크기는 줄지 않는다
VACUUM items;
SELECT pg_sleep(1);  ANALYZE items;
SELECT relname, n_live_tup, n_dead_tup,
       pg_size_pretty(pg_table_size('items')) AS table_size
FROM pg_stat_user_tables WHERE relname = 'items';
--  relname | n_live_tup | n_dead_tup | table_size
-- ---------+------------+------------+------------
--  items   |          1 |          0 | 88 kB      ← 죽은 튜플은 0, 크기는 그대로(재사용용 빈 공간)

마지막 결과가 앞서 말한 "방을 비운 것이지 없앤 게 아니다"를 그대로 보여줍니다. 88 kB의 빈 공간은 다음 UPDATE들이 재사용하므로, 이 상태 자체는 정상입니다.

실무에서 볼 지표 두 개. 잦은 UPDATE/DELETE가 일어나는 테이블은 pg_stat_user_tables에서 n_dead_tup(죽은 튜플 수)과 last_autovacuum(마지막 자동 청소 시각)을 지켜보세요. 죽은 튜플이 계속 늘어나거나 autovacuum이 며칠째 안 돌았다면 팽창이 진행 중입니다. 그런 핫한 테이블은 autovacuum_vacuum_scale_factor를 테이블 단위로 낮춰(예: 0.02) 더 자주 청소하게 만들 수 있습니다.
⏳

긴 트랜잭션이 VACUUM을 막는다

이 섹션은 짧지만 실무에서 가장 자주 사고가 나는 지점입니다.

VACUUM은 아무 죽은 튜플이나 치우지 않습니다. "살아 있는 어떤 트랜잭션도 더는 볼 수 없는" 것만 회수할 수 있죠. 그런데 오래 열려 있는 트랜잭션이 하나라도 있으면, 그 트랜잭션이 볼 수도 있는 옛 버전들을 전부 보존해야 합니다.

비유 — 한 명이 안 나가서 청소를 못 하는 회의실. 회의가 끝나 다들 나갔는데 한 사람이 노트북을 켜둔 채 자리를 지키고 있습니다. 청소부는 "저분이 아직 쓰고 계시니 이 자료들을 버릴 수 없다"며 회의실 전체를 그대로 둡니다. 그 사이 다른 팀들이 쓰고 간 자료가 계속 쌓이죠. Postgres에서 딱 하나의 방치된 트랜잭션이 DB 전체의 청소를 막는 상황이 정확히 이렇습니다.

트랜잭션은 짧게 — 화면을 보며 트랜잭션을 열어두지 마세요.

사고의 전형은 이렇습니다. "BEGIN 후 사용자 입력을 기다린다", "분석 쿼리를 한 시간째 돌린다", "커넥션을 잡고 그대로 잊어버린 좀비 트랜잭션". 이런 오래된 스냅샷이 VACUUM의 회수 지점을 과거에 묶어두고, 그동안 DB 전체에 bloat이 누적됩니다.

진단: SELECT * FROM pg_stat_activity WHERE state <> 'idle' ORDER BY xact_start;로 가장 오래된 트랜잭션을 찾습니다.
예방: idle_in_transaction_session_timeout을 설정해 방치된 트랜잭션을 자동 종료시키세요.

MySQL — 익숙한 방식

InnoDB도 MVCC를 쓰지만 옛 버전을 테이블 밖의 undo log에 둡니다. 현재 행은 제자리에서 갱신되고, 옛 버전이 필요하면 undo를 따라 되돌려 재구성합니다. 정리는 purge 스레드가 하죠. 긴 트랜잭션이 있으면 undo가 쌓여 "history list length"가 길어지는데, 증상은 PG의 bloat와 비슷합니다.

PostgreSQL — 이렇게 다르다

옛 버전을 테이블 안에 그대로 두고 xmin/xmax로 가시성을 판단합니다. 그래서 죽은 튜플이 테이블에 직접 쌓이고, 이를 VACUUM/autovacuum이 회수합니다. 별도 undo 로그가 없는 대신 VACUUM 운영이 PG 성능 관리의 핵심이 됩니다.

✅

셀프 체크

Q 하나의 UPDATE는 무엇을 만드나요?

새 행 버전 하나와 죽은 튜플 하나(만료된 옛 버전)를 만듭니다. Postgres는 행을 제자리에서 덮어쓰지 않고, 새 버전을 쓴 뒤 옛 버전의 xmax를 채워 만료시킵니다. 그래서 같은 행을 N번 UPDATE하면 죽은 튜플이 약 N개 쌓이고, ctid(물리 위치)가 계속 옮겨집니다.

Q VACUUM과 VACUUM FULL의 차이는?

일반 VACUUM은 죽은 튜플 공간을 같은 테이블이 재사용하도록 표시만 합니다 — 파일 크기는 거의 그대로이고 테이블을 잠그지 않아 운영 중에도 안전합니다. VACUUM FULL은 테이블을 통째로 재작성해 디스크를 OS에 반환하지만, ACCESS EXCLUSIVE 락으로 읽기까지 막으므로 운영 중에는 위험합니다.

Q 긴 트랜잭션이 bloat을 부르는 이유는?

VACUUM은 "살아 있는 어떤 트랜잭션도 더는 볼 수 없는" 죽은 튜플만 회수할 수 있습니다. 오래 열린 트랜잭션이 하나라도 있으면 그 스냅샷이 볼 수도 있는 옛 버전들을 전부 보존해야 하므로, DB 전체에서 죽은 튜플이 회수되지 못하고 쌓입니다. pg_stat_activity로 오래된 트랜잭션을 찾고, idle_in_transaction_session_timeout으로 방치된 것을 자동 종료시키세요.

Q 테이블이 계속 커지는데 행 수는 그대로입니다. 무엇을 볼까요?

pg_stat_user_tables의 n_dead_tup과 last_autovacuum입니다. 죽은 튜플이 계속 쌓이는데 autovacuum이 안 돌고 있다면 bloat이 진행 중입니다. 원인은 보통 ① 변경이 너무 잦아 임계치를 따라가지 못하거나, ② 긴 트랜잭션이 회수를 막고 있는 경우입니다. 핫한 테이블은 autovacuum_vacuum_scale_factor를 낮춰 더 자주 돌게 할 수 있습니다.
