락 · FOR UPDATE · 데드락 · advisory lock

MVCC 덕분에 "읽기"는 서로를 막지 않습니다. 그런데 둘이 같은 행을 고치려 들면 이야기가 다르죠. 그 순간을 조율하는 것이 락입니다.

한 줄 요약. 락의 원칙은 "짧게 잡고 빨리 놓기" 하나뿐입니다. 그리고 여러 개를 잡아야 한다면 "항상 같은 순서로". 이 두 문장이 동시성 사고의 대부분을 예방합니다.

학습 목표

  • 행 수준 락(FOR UPDATE/FOR SHARE)과 NOWAIT·SKIP LOCKED를 구분한다
  • 데드락이 왜 생기는지 이해하고, 구조적으로 회피하는 법을 안다
  • advisory lock으로 "행이 아닌 것"을 잠근다
  • SKIP LOCKED로 외부 큐 없이 작업 큐를 만든다
🔒

행 잠금 — FOR UPDATE · FOR SHARE · NOWAIT

비유 — 탈의실 문을 안에서 잠그기. 한 사람이 쓰는 동안 다른 사람은 그 칸을 쓸 수 없습니다. SELECT ... FOR UPDATE는 고른 행에 "내가 곧 고칠 거다"라는 표시를 걸어, 다른 트랜잭션이 같은 행을 건드리려 하면 내 트랜잭션이 끝날 때까지 기다리게 만듭니다. FOR SHARE는 더 약해서 "읽는 건 괜찮지만 고치진 마" 정도입니다.

왜 필요할까요? 읽고-판단하고-고치는(read-modify-write) 패턴 때문입니다. "재고를 읽어서 1 이상이면 1 줄이기"를 생각해 보세요. 읽는 시점과 고치는 시점 사이에 다른 요청이 끼어들면, 둘 다 "재고 1개 있네"를 보고 둘 다 판매해 재고가 -1이 됩니다. FOR UPDATE는 그 틈을 막습니다.

sqlstudy_db=# — FOR UPDATE / NOWAIT
-- 이 행을 "곧 고칠 거다"라고 잠금
BEGIN;
  SELECT id, payload FROM jobs WHERE id = 1 FOR UPDATE;
COMMIT;
--  id |   payload
-- ----+--------------
--   1 | send-email-1

-- NOWAIT: 이미 잠겨 있으면 기다리지 말고 즉시 에러
BEGIN;
  SELECT id FROM jobs WHERE id = 2 FOR UPDATE NOWAIT;
COMMIT;

단, 위 코드를 psql 창 하나에서 실행하면 충돌 장면을 볼 수 없습니다 — 자기 자신과는 충돌하지 않으니까요. 실제로 두 세션이 부딪히면 이렇게 됩니다.

시각Session ASession B
t1BEGIN; SELECT ... id=1 FOR UPDATE; → 행 1 잠금 획득
t2(작업 처리 중…)SELECT ... id=1 FOR UPDATE; → 대기 중 ⏳
t3UPDATE jobs SET status='done' ...; COMMIT; → 락 해제(여전히 대기)
t4대기 풀림 → 갱신된 행 1을 잠그고 진행 ✅

t4를 주목하세요. B는 A가 고친 뒤의 값을 봅니다. 이게 FOR UPDATE의 핵심 효과입니다 — 낡은 값을 보고 판단하는 일이 없어집니다.

락을 잡은 채 기다리지 마세요. 행 락은 트랜잭션이 끝날 때 풀립니다. 그런데 FOR UPDATE로 행을 잠근 채 사용자 확인을 기다리거나 외부 API를 호출하면, 그동안 그 행을 건드리려는 모든 요청이 줄을 섭니다. 외부 API가 30초 걸리면 30초간 서비스가 멈추는 셈이죠. 원칙은 잠그기 → 빠르게 갱신 → 즉시 커밋입니다. 오래 기다려야 한다면 락 대신 낙관적 잠금(버전 컬럼 비교)이나 큐를 쓰세요.
💀

데드락 — 서로의 락을 기다리다 멈춤

비유 — 좁은 골목에서 마주친 두 차. A는 앞으로 가려면 B가 비켜야 하고, B는 앞으로 가려면 A가 비켜야 합니다. 둘 다 상대가 먼저 움직이기를 기다리며 영원히 멈춰 있죠. 이게 데드락입니다. DB에서는 A가 행1을 잡고 행2를 원하고, B가 행2를 잡고 행1을 원할 때 발생합니다.

다행히 Postgres는 이 상황을 자동으로 감지합니다. 순환 대기를 발견하면 한쪽 트랜잭션을 ERROR: deadlock detected로 강제 종료하고 나머지 한쪽을 진행시킵니다. 즉 서비스가 영원히 멈추지는 않습니다 — 대신 한쪽 요청이 실패합니다.

시각Session ASession B
t1UPDATE ... WHERE id=1; → 행 1 잠금UPDATE ... WHERE id=2; → 행 2 잠금
t2UPDATE ... WHERE id=2; → B가 쥔 행 2 대기 ⏳UPDATE ... WHERE id=1; → A가 쥔 행 1 대기 ⏳
t3PG가 순환 대기 감지 → abort (40P01)락을 얻어 진행

데드락 회피의 황금률 — 항상 같은 순서로 잠그기.

위 표를 다시 보세요. 데드락이 난 이유는 A는 1→2 순서로, B는 2→1 순서로 잠갔기 때문입니다. 만약 두 트랜잭션 모두 id 오름차순으로 잠갔다면 어떻게 될까요? B는 행 1부터 시도하다 A를 기다리게 되고, A는 방해 없이 1·2를 다 잡고 끝냅니다. 순환이 생길 수가 없습니다.

그래서 규칙은 하나입니다 — 여러 행·테이블을 잠가야 한다면 모든 코드가 동일한 순서(예: 항상 id 오름차순)를 따를 것. 여기에 더해 트랜잭션을 짧게 유지하고, 한 번에 잠그는 행 수를 줄이며, 그래도 드물게 나는 데드락(40P01)은 재시도 가능한 에러로 다루면 됩니다.

🗝️

advisory lock — 행이 아니라 "앱이 정한 키"로 잠그기

때로는 잠그고 싶은 대상이 특정 행이 아닌 경우가 있습니다. "이 크론 작업은 서버가 여러 대여도 한 번에 하나만 돌게", "이 사용자에 대한 정산을 동시에 두 번 하지 않게" 같은 것들이죠. 잠글 행이 없거나, 행 하나로 표현되지 않는 추상적인 자원입니다.

비유 — 화장실 열쇠. 카페 화장실 열쇠가 카운터에 하나뿐이라면, 열쇠를 가진 사람만 쓸 수 있습니다. 열쇠 자체는 화장실의 일부가 아니고, "열쇠를 든 사람만 들어간다"는 건 그냥 모두의 약속이죠. advisory lock이 정확히 이렇습니다 — DB는 그 정수 키가 무슨 뜻인지 전혀 모르고, 잠금 규칙은 전적으로 앱들 사이의 약속입니다. 그래서 이름이 "advisory(권고적)"입니다.
sqlstudy_db=# — pg_try_advisory_lock: 기다리지 않고 성공 여부 반환
-- try_ 계열은 기다리지 않고 t/f를 즉시 반환 (스크립트가 멈추지 않는다)
SELECT pg_try_advisory_lock(42) AS got_lock;    -- 이 세션이 키 42를 잡음
--  got_lock
-- ----------
--  t

-- 같은 세션은 재진입 가능(카운트 증가). 다른 세션이었다면 f를 받는다.
SELECT pg_try_advisory_lock(42) AS got_again;   -- t

-- 잡은 만큼 풀어줘야 한다 (두 번 잡았으니 두 번 unlock)
SELECT pg_advisory_unlock(42) AS released_1;    -- t
SELECT pg_advisory_unlock(42) AS released_2;    -- t

-- 현재 들고 있는 advisory lock 확인 (모두 풀었으니 0)
SELECT count(*) AS held_advisory_locks
FROM pg_locks WHERE locktype = 'advisory';
--  held_advisory_locks
-- ---------------------
--                    0

세션 범위 vs 트랜잭션 범위 — 이 선택이 중요합니다.

pg_advisory_lock(key)·pg_try_advisory_lock(key)는 세션 범위입니다. 명시적으로 pg_advisory_unlock하거나 세션이 끊겨야 풀립니다. 즉 푸는 걸 잊으면 그대로 남습니다.

반면 pg_advisory_xact_lock(key) 계열은 트랜잭션 범위라 커밋·롤백 시 자동 해제됩니다. 실수의 여지가 없으니 이쪽을 기본으로 삼는 편이 안전합니다.

그리고 분산 락처럼 쓰더라도, 이 잠금은 이 DB 인스턴스 한정임을 잊지 마세요 — DB를 여러 대 쓰면 서로를 모릅니다.

📬

SKIP LOCKED 큐 패턴 — 워커가 안 겹치게 작업 집어가기

이 섹션은 실무 활용도가 가장 높은 패턴입니다. 작업 큐 테이블에서 여러 워커가 동시에 다음 작업을 집어가는 상황을 생각해 보세요.

순진하게 짜면 문제가 생깁니다. 그냥 SELECT ... LIMIT 1이면 두 워커가 같은 작업을 집어 이메일이 두 번 발송됩니다. 그렇다고 FOR UPDATE를 붙이면? 이번엔 모든 워커가 맨 앞의 같은 행에서 줄을 서서 사실상 워커가 한 명인 것과 같아집니다.

비유 — 뷔페에서 접시 집기. FOR UPDATE만 쓰면 모두가 첫 번째 접시 앞에 줄을 서는 꼴입니다. SKIP LOCKED는 "누가 이미 집은 접시는 건너뛰고 다음 걸 집어라"입니다. 그래서 워커 A는 1번, 워커 B는 2번, 워커 C는 3번을 기다림 없이 동시에 가져갑니다.
sqlstudy_db=# — FOR UPDATE SKIP LOCKED로 큐에서 작업 집기
-- 잠긴 행은 건너뛰고 안 잠긴 다음 행을 가져온다
BEGIN;
  SELECT id, payload
  FROM jobs
  WHERE status = 'queued'
  ORDER BY id
  FOR UPDATE SKIP LOCKED
  LIMIT 1;
  UPDATE jobs SET status = 'done' WHERE id = 1;  -- 처리 후 상태 변경
COMMIT;
--  id |   payload
-- ----+--------------
--   1 | send-email-1

SELECT id, payload, status FROM jobs ORDER BY id;
--  id |    payload     | status
-- ----+----------------+--------
--   1 | send-email-1   | done
--   2 | send-email-2   | queued
--   3 | resize-image-3 | queued

실제 운영에서 워커 A와 B가 동시에 이 쿼리를 실행하면, A는 행 1을 잡고 B는 그 행을 건너뛰어 행 2를 가져갑니다. 락 대기 없이 병렬로 큐를 비우죠. Redis나 RabbitMQ 없이 Postgres만으로 작업 큐를 만드는 실무 단골 패턴입니다.

마지막으로, 락을 무한정 기다리고 싶지 않을 때 쓸 수 있는 안전장치가 하나 더 있습니다.

sqlstudy_db=# — lock_timeout: 락을 너무 오래 기다리면 포기
-- 락을 1초 넘게 기다리면 포기하고 에러
SET lock_timeout = '1s';
SHOW lock_timeout;
--  lock_timeout
-- --------------
--  1s

BEGIN;
  SELECT id FROM jobs WHERE id = 3 FOR UPDATE;  -- 충돌 없음 → 즉시 성공
COMMIT;
-- 다른 세션이 행 3을 잡고 있었다면 1초 뒤:
-- ERROR:  canceling statement due to lock timeout
세 가지 대기 전략, 이렇게 고르세요. 기다린다(기본) — 순서가 중요하고 언젠가는 처리돼야 할 때. NOWAIT — 즉시 실패하고 사용자에게 "지금 처리 중입니다"를 보여주고 싶을 때. SKIP LOCKED — 어떤 행이든 상관없고 남은 것 중 아무거나 처리하면 될 때(작업 큐). 여기에 lock_timeout을 더하면 "일정 시간까지만 기다리기"도 가능합니다.
MySQL — 익숙한 방식

InnoDB도 SELECT ... FOR UPDATE·FOR SHARE를 지원하고, 8.0부터 NOWAIT·SKIP LOCKED가 추가돼 같은 큐 패턴을 쓸 수 있습니다. 데드락도 자동 감지합니다. advisory lock에 해당하는 것은 GET_LOCK(name, timeout)·RELEASE_LOCK(name)입니다(문자열 키를 쓴다는 점이 다릅니다).

PostgreSQL — 이렇게 다르다

FOR UPDATE에 NOWAIT·SKIP LOCKED를 제공하고 데드락을 자동 감지해 한쪽을 40P01로 abort합니다. SKIP LOCKED 큐 패턴과 정수 키 기반 advisory lock이 잘 갖춰져 있어, 외부 큐 시스템 없이도 DB 안에서 가벼운 작업 큐·분산 락을 만들기 좋습니다.

셀프 체크

Q SELECT ... FOR UPDATE는 어떤 문제를 푸나요?

읽고-판단하고-고치는 사이에 다른 트랜잭션이 끼어드는 문제를 막습니다. "재고를 읽어서 1 이상이면 1 줄이기"에서 두 요청이 동시에 "1개 있네"를 보고 둘 다 판매하는 사고를 방지하죠. 락은 트랜잭션 종료 시 풀리므로 짧게 잡고 빨리 커밋하는 것이 원칙입니다.

Q 데드락을 구조적으로 회피하는 방법은?

모든 트랜잭션이 자원을 같은 순서로 잠그는 것입니다(예: 항상 id 오름차순). 데드락은 A가 1→2, B가 2→1처럼 순서가 엇갈릴 때만 생기므로, 순서를 통일하면 순환이 원천적으로 만들어질 수 없습니다. 여기에 트랜잭션을 짧게 유지하고, 그래도 나는 데드락(40P01)은 재시도 가능한 에러로 처리하면 됩니다.

Q advisory lock은 언제 쓰나요? 세션/트랜잭션 범위 중 무엇을?

잠글 행이 없거나 행으로 표현되지 않는 추상적인 자원을 잠글 때입니다 — "이 크론 작업은 한 번에 하나만", "이 사용자 정산을 중복 실행하지 않게" 등. 범위는 트랜잭션 범위(pg_advisory_xact_lock)를 기본으로 삼는 편이 안전합니다. 커밋·롤백 시 자동 해제되어 푸는 걸 잊을 위험이 없기 때문입니다.

Q SKIP LOCKED가 없으면 작업 큐에 어떤 문제가 생기나요?

FOR UPDATE만 쓰면 모든 워커가 맨 앞의 같은 행에서 줄을 서서 사실상 직렬 처리가 됩니다(워커를 늘려도 소용없음). 반대로 락 없이 SELECT만 하면 두 워커가 같은 작업을 중복 처리합니다. FOR UPDATE SKIP LOCKED는 이미 잠긴 행을 건너뛰어 각 워커가 서로 다른 작업을 대기 없이 병렬로 가져가게 합니다.
