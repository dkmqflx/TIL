RLS — 앱의 WHERE를 DB가 강제하게 만들기

한 테이블에 여러 고객사의 데이터가 섞여 있어도, RLS를 켜면 DB가 행 단위로 "네가 볼 수 있는 행"만 돌려줍니다. 개발자가 WHERE를 깜빡해도 데이터가 새지 않습니다.

왜 이게 중요한가. 멀티테넌트 서비스에서 WHERE tenant_id = ?를 단 한 곳에서만 빠뜨려도 다른 고객사 데이터가 노출됩니다. 그리고 그런 코드는 수백 군데에 있습니다. RLS는 그 필터를 앱이 아니라 DB에 두어, 실수의 여지를 구조적으로 없앱니다.

학습 목표

  • RLS가 무엇을 해결하는지, 왜 앱 코드보다 안전한지 설명한다
  • 정책의 USING(가시성)과 WITH CHECK(쓰기 제약)를 구분한다
  • 세션 변수와 정책으로 멀티테넌시를 구현하고 실제로 행이 걸리는 것을 확인한다
  • superuser·owner가 RLS를 우회한다는 함정을 알고 대응한다
🛡️

RLS란 & 왜 필요한가

비유 — 도서관 대출 창구. 창구 직원은 모든 사람의 대출 기록이 든 같은 장부를 보고 있습니다. 그런데 여러분에게는 여러분의 기록만 보여주죠. 남의 카드 번호를 대며 "그 사람 기록도 보여주세요"라고 해도 나오지 않습니다. 창구가 "네 것만"이라는 규칙을 강제하기 때문입니다. RLS가 정확히 이 창구 역할을 합니다.

구체적인 상황으로 봅시다. 멀티테넌트 SaaS는 보통 한 테이블에 여러 고객사(테넌트)의 행을 함께 담고 tenant_id로 구분합니다. 스토리지도 아끼고 운영도 단순하니까요.

문제는 앱이 모든 쿼리마다 WHERE tenant_id = ?를 빠뜨리지 않아야 한다는 것입니다. 조회 API, 목록 API, 통계 쿼리, 관리자 페이지, 배치 스크립트, 급하게 만든 리포트… 단 한 곳만 빠져도 다른 고객사의 데이터가 그대로 노출됩니다. 그리고 이런 사고는 실제로 자주 일어납니다.

앱이 WHERE를 붙임 → 한 곳이라도 빠지면 유출
DB가 강제함 (RLS) → 앱이 깜빡해도 안전

RLS(Row Level Security, 행 수준 보안)는 그 필터를 애플리케이션이 아니라 DB가 행 단위로 강제하게 만듭니다. 앱 코드에 검사를 두는 것과 병행하는 "깊이 있는 방어(defense in depth)"죠 — 앱이 뚫려도 DB가 막습니다.

📜

켜기와 정책 — USING vs WITH CHECK

RLS 설정은 두 단계입니다. 먼저 테이블에 스위치를 켜고, 그다음 정책(policy)으로 "어떤 행을 허용할지" 규칙을 씁니다.

중요한 기본값 — RLS를 켰는데 정책이 하나도 없으면 아무 행도 안 보입니다(deny-all). "일단 켜두고 정책은 나중에"라고 하면 서비스가 그 순간 멈춥니다. 정책을 먼저 준비하고 마지막에 스위치를 켜는 순서가 안전합니다.

정책에는 두 종류의 조건을 쓸 수 있고, 이 둘의 구분이 핵심입니다.

조건무엇을 검사하나적용되는 명령
USING기존 행이 보이는지 — 대상이 될 수 있는 행을 거른다SELECT · UPDATE · DELETE
WITH CHECK새로 쓰이는 행이 규칙을 지키는지 — 결과 행을 검사한다INSERT · UPDATE
sqlstudy_db=# — RLS 켜고 테넌트 격리 정책 만들기
-- 1) 테이블에 RLS 스위치 켜기 (정책이 없으면 기본 deny-all)
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;

-- 2) 정책: 세션 변수 app.current_tenant와 같은 tenant_id 행만 허용
--    current_setting(..., true): 변수가 없으면 에러 대신 NULL 반환
CREATE POLICY tenant_isolation ON documents
  USING      (tenant_id = current_setting('app.current_tenant', true)::int)
  WITH CHECK (tenant_id = current_setting('app.current_tenant', true)::int);

왜 둘 다 필요할까요? — USING만 있으면 생기는 구멍.

USING만 두면 "내 테넌트 행은 보고 고칠 수 있다"까지는 됩니다. 그런데 INSERT로 남의 tenant_id를 적어 넣는 것은 막지 못합니다. USING은 이미 있는 행을 거르는 조건이지, 새로 들어오는 행을 검사하지 않으니까요.

둘을 같은 조건으로 주면 "내 테넌트 행만 보이고, 새로 넣는 행도 반드시 내 테넌트여야 한다"가 완성됩니다. 필요하면 다르게 줄 수도 있습니다 — 예를 들어 "읽기는 팀 전체, 쓰기는 본인 것만" 같은 정책이 가능하죠.

🏢

멀티테넌시 실전 — 같은 쿼리, 다른 결과

앱은 요청을 처리할 때 커넥션에 "지금 이 요청은 어느 테넌트인가"를 세션 변수로 설정합니다. 정책이 그 변수를 참조하므로, 완전히 똑같은 쿼리라도 변수 값에 따라 다른 행이 돌아옵니다.

그런데 실습에는 걸림돌이 하나 있습니다. 지금 psql로 접속한 study 유저는 SUPERUSER라서 RLS를 통째로 우회합니다. 정책을 켜도 모든 행이 그대로 보이죠. 이건 버그가 아니라 다음 섹션에서 다룰 중요한 함정입니다.

sqlstudy_db=# — SUPERUSER(study)는 RLS를 우회 → 전체가 보인다
-- 접속 유저 study는 SUPERUSER라 정책을 무시한다 (다음 섹션 참고)
SELECT id, tenant_id, title FROM documents ORDER BY id;
--  id | tenant_id |        title
-- ----+-----------+----------------------
--   1 |         1 | Acme 분기 보고서
--   2 |         1 | Acme 채용 계획
--   3 |         2 | Globex 신제품 로드맵
--   4 |         2 | Globex 가격표
--   5 |         3 | Initech 회의록
-- (5 rows)   ← 정책을 켰는데도 전부 보인다!

그래서 RLS가 실제로 행을 거르는 장면을 보려면 SUPERUSER가 아닌 앱 롤로 바꿔야 합니다. SET ROLE로 잠시 그 롤이 되어봅시다.

sqlstudy_db=# — app_user(NOSUPERUSER)로 바꾸면 RLS가 행을 거른다 ⭐
-- 앱 롤이 된다 (SUPERUSER도 owner도 아니므로 정책 적용을 받는다)
SET ROLE app_user;

-- 테넌트 1로 설정 → 테넌트 1 행만 보인다
SET app.current_tenant = '1';
SELECT id, tenant_id, title FROM documents ORDER BY id;
--  id | tenant_id |      title
-- ----+-----------+------------------
--   1 |         1 | Acme 분기 보고서
--   2 |         1 | Acme 채용 계획
-- (2 rows)

-- 똑같은 쿼리인데 테넌트 2로 바꾸면 → 완전히 다른 행! (DB가 거른 것)
SET app.current_tenant = '2';
SELECT id, tenant_id, title FROM documents ORDER BY id;
--  id | tenant_id |        title
-- ----+-----------+----------------------
--   3 |         2 | Globex 신제품 로드맵
--   4 |         2 | Globex 가격표
-- (2 rows)

여기가 이 레슨의 핵심 장면입니다. 쿼리에 WHERE를 한 글자도 쓰지 않았는데 DB가 알아서 걸러줬습니다. 앱 개발자가 필터를 깜빡할 수가 없죠 — 애초에 쓸 필요가 없으니까요.

쓰기 쪽도 확인해 봅시다. WITH CHECK가 어떻게 막는지 보세요.

sqlstudy_db=# — WITH CHECK: 남의 테넌트 행은 못 넣는다
-- 현재 테넌트는 2. 테넌트 1 행을 몰래 넣으려 하면 거부된다.
INSERT INTO documents (tenant_id, title) VALUES (1, '몰래 넣기');
-- ERROR:  new row violates row-level security policy for table "documents"

-- 같은 테넌트(2) 행은 정상 INSERT
INSERT INTO documents (tenant_id, title) VALUES (2, 'Globex 추가 메모');
-- INSERT 0 1

RESET ROLE;  -- 다시 study(superuser)로 복귀
⚠️

함정 — superuser·owner는 RLS를 우회한다

"RLS를 켰는데 안 먹어요"라는 질문의 거의 대부분이 이것입니다. 반드시 알고 넘어가야 합니다.

① SUPERUSER는 RLS를 통째로 우회합니다. 정책이 아무리 잘 짜여 있어도 모든 행이 보입니다.

② 테이블 OWNER도 기본적으로 우회합니다. 테이블을 만든 롤이 그대로 앱 접속 계정이라면 RLS는 사실상 꺼진 것과 같습니다.

그래서 앱이 superuser나 owner로 붙으면 RLS는 아무 의미가 없습니다. 다음 레슨에서 "앱 전용 최소 권한 유저"를 강조하는 이유가 바로 이것입니다. owner에게도 정책을 강제하려면 ALTER TABLE t FORCE ROW LEVEL SECURITY;를 켜야 합니다.

실제로 켜고 카탈로그에서 확인해 봅시다.

sqlstudy_db=# — FORCE RLS 설정 & 카탈로그 확인
-- owner에게도 RLS 강제 (기본은 owner 우회)
ALTER TABLE documents FORCE ROW LEVEL SECURITY;

-- relrowsecurity = RLS 켜짐, relforcerowsecurity = owner에게도 강제
SELECT relname, relrowsecurity, relforcerowsecurity
FROM pg_class WHERE relname = 'documents';
--   relname  | relrowsecurity | relforcerowsecurity
-- -----------+----------------+---------------------
--  documents | t              | t

-- 정의된 정책 목록 (polcmd '*' = 모든 명령에 적용)
SELECT polname, polcmd FROM pg_policy
WHERE polrelid = 'documents'::regclass;
--      polname      | polcmd
-- ------------------+--------
--  tenant_isolation | *

나머지 두 가지 주의점도 짚고 넘어가겠습니다.

주의점내용
정책 여러 개는 어떻게 합쳐지나기본(PERMISSIVE) 정책들은 OR로 결합됩니다 — 하나라도 통과하면 허용. RESTRICTIVE 정책은 AND로 결합되어 반드시 모두 만족해야 합니다.
성능도 챙겨야 한다정책 조건은 결국 모든 쿼리의 WHERE에 더해집니다. 그러니 정책이 참조하는 컬럼(tenant_id)에 인덱스가 없으면 전체 쿼리가 느려집니다.
Supabase가 RLS를 보안 모델의 중심으로 쓰는 이유. Supabase 같은 Postgres 기반 BaaS는 브라우저가 DB에 직접 쿼리합니다. 언뜻 위험해 보이지만, 로그인한 사용자의 JWT가 세션 변수로 들어오고 RLS 정책(auth.uid() = user_id 같은)이 행을 걸러주기 때문에 안전합니다. "앱 코드가 아니라 DB가 권한을 강제한다"는 RLS의 발상이 그대로 제품 아키텍처가 된 사례입니다.
MySQL — 익숙한 방식

행 수준 보안 정책이 기본으로 없습니다. 보통 뷰(VIEW)로 테넌트 필터를 감싸거나, 애플리케이션에서 매 쿼리에 WHERE tenant_id = ?를 직접 붙입니다. 즉 필터를 빠뜨리지 않을 책임이 전적으로 앱에 있어, 한 곳만 실수해도 데이터가 샙니다.

PostgreSQL — 이렇게 다르다

네이티브 RLS 정책을 제공합니다. ENABLE ROW LEVEL SECURITY + CREATE POLICY로 "누가 어떤 행을 보고 쓸 수 있는지"를 DB 차원에 선언하면, 앱이 WHERE를 깜빡해도 DB가 강제합니다. 단 앱은 superuser·owner가 아닌 최소 권한 롤로 붙어야 실제로 적용됩니다.

✅

셀프 체크

Q USING과 WITH CHECK는 무엇이 다른가요?

USING은 기존 행의 가시성을 거릅니다 — SELECT·UPDATE·DELETE가 대상으로 삼을 수 있는 행을 결정하죠. WITH CHECK는 새로 삽입·수정되는 행이 만족해야 할 제약으로, INSERT/UPDATE의 결과 행을 검사합니다. WITH CHECK가 없으면 남의 tenant_id를 적어 넣는 INSERT를 막지 못하므로, 멀티테넌시에서는 보통 둘을 같은 조건으로 줍니다.

Q 정책을 켰는데도 모든 행이 다 보입니다. 무엇을 의심할까요?

접속한 롤이 SUPERUSER이거나 테이블 OWNER일 가능성이 가장 큽니다 — 둘 다 기본적으로 RLS를 우회합니다. owner에게도 적용하려면 ALTER TABLE t FORCE ROW LEVEL SECURITY;를 켜고, 앱은 최소 권한 롤로 접속해야 합니다. 그다음으로는 ENABLE ROW LEVEL SECURITY 자체를 안 켰을 가능성을 확인하세요.

Q 세션 변수(app.current_tenant)는 어떤 역할인가요?

정책이 참조하는 "지금 이 커넥션이 누구인가"를 담는 값입니다. 앱은 요청 처리 시작 시 SET app.current_tenant = '...'로 설정하고, 정책은 tenant_id = current_setting(...)::int로 비교합니다. 커넥션 풀을 쓸 때는 각별히 주의하세요 — 요청마다 이 변수를 반드시 설정·초기화해야 앞 요청의 값이 남아 다른 테넌트 데이터가 새지 않습니다.

Q RLS를 켤 때 성능에서 챙길 것은?

정책 조건은 결국 모든 쿼리의 WHERE에 자동으로 더해집니다. 그러니 정책이 참조하는 컬럼(예: tenant_id)에 인덱스가 없으면 모든 쿼리가 느려집니다. RLS를 도입할 때는 정책 컬럼 인덱스를 함께 준비하세요.
