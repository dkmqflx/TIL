ROLE · GRANT — 앱 전용 최소 권한 유저 만들기

Postgres에서는 유저와 그룹이 모두 ROLE입니다. 그리고 앱은 절대 superuser로 붙어서는 안 됩니다 — 꼭 필요한 권한만 가진 롤로 접속해야 합니다.

앞 레슨과 이어집니다. RLS를 아무리 잘 설정해도 앱이 superuser로 붙으면 전부 무의미합니다. 이 레슨은 "그럼 앱은 어떤 계정으로 붙어야 하나"에 대한 답입니다.

학습 목표

  • ROLE 모델(유저 = 그룹 = ROLE)과 LOGIN 속성을 이해한다
  • Postgres 특유의 스키마 USAGE 단계를 알고 권한을 올바르게 부여한다
  • 읽기 전용·읽기쓰기 롤을 만들어 최소 권한 원칙을 적용한다
  • ALTER DEFAULT PRIVILEGES로 미래에 만들 테이블까지 대비한다
👤

ROLE = 유저 + 그룹 — LOGIN 여부가 가른다

비유 — 회사 출입카드. 어떤 카드는 개인에게 발급되고(로그인하는 유저), 어떤 카드는 "개발팀" 같은 그룹에 발급됩니다. 사람을 그룹에 넣으면 그룹이 가진 출입 권한을 그대로 물려받죠. Postgres에서는 이 둘이 구분 없이 모두 ROLE입니다 — 차이는 딱 하나, 직접 로그인할 수 있느냐뿐입니다.

정리하면 이렇습니다. USER란 LOGIN 속성을 가진 ROLE입니다. 실제로 CREATE USER는 CREATE ROLE ... LOGIN의 별칭일 뿐이죠. 반대로 NOLOGIN 롤은 직접 접속은 못 하지만 권한 묶음(그룹)으로 쓰입니다.

ROLE + LOGIN = 우리가 말하는 "유저"
ROLE + NOLOGIN = 권한 묶음 "그룹"
sqlstudy_db=# — 앱 유저 롤 두 개 만들기 (둘 다 NOSUPERUSER)
-- app_rw: 읽기/쓰기, app_ro: 읽기 전용. LOGIN이라 곧 '유저'.
CREATE ROLE app_rw NOSUPERUSER LOGIN PASSWORD 'rw_pw';
CREATE ROLE app_ro NOSUPERUSER LOGIN PASSWORD 'ro_pw';

-- rolcanlogin = t 면 로그인 가능 = 통상적 의미의 '유저'
SELECT rolname, rolsuper, rolcanlogin
FROM pg_roles WHERE rolname IN ('app_rw','app_ro') ORDER BY rolname;
--  rolname | rolsuper | rolcanlogin
-- ---------+----------+-------------
--  app_ro  | f        | t
--  app_rw  | f        | t

그룹을 쓰고 싶다면 GRANT 그룹롤 TO 유저롤로 멤버십을 만들면 됩니다. 멤버는 그룹의 권한을 상속하므로, 개발자 10명에게 각각 권한을 주는 대신 "개발팀" 롤 하나에 권한을 주고 10명을 넣는 방식이 관리하기 훨씬 편합니다.

권한 — 스키마 USAGE부터, 그다음 테이블

MySQL에서 넘어온 사람이 가장 자주 막히는 지점입니다. "테이블에 SELECT 권한을 분명히 줬는데 permission denied for schema public이 나요."

비유 — 방 열쇠는 줬는데 건물 출입증을 안 준 것. Week 1에서 배운 대로 Postgres는 데이터베이스(건물) → 스키마(층) → 테이블(방)의 두 단계 구조입니다. 그래서 방 열쇠(테이블 권한)만 줘서는 안 되고, 그 층에 들어갈 수 있는 출입증(스키마 USAGE)도 함께 줘야 합니다. MySQL은 이 층 개념이 없어서 이 단계가 존재하지 않죠.
sqlstudy_db=# — 스키마 USAGE + 테이블 권한 부여
-- 1) 스키마를 쓸 수 있게 USAGE부터 (이걸 빠뜨리면 permission denied for schema)
GRANT USAGE ON SCHEMA public TO app_rw, app_ro;

-- 2) app_rw는 읽기+쓰기, app_ro는 읽기만
GRANT SELECT, INSERT, UPDATE, DELETE ON orders TO app_rw;
GRANT SELECT ON orders TO app_ro;

-- 참고: orders.id는 GENERATED ALWAYS AS IDENTITY.
-- IDENTITY 컬럼은 뒤의 시퀀스 USAGE가 따로 필요 없다 — 테이블 INSERT 권한이면 충분.
-- 시퀀스 USAGE는 레거시 serial이나 앱이 직접 nextval()을 호출할 때만 필요:
--   GRANT USAGE ON ALL SEQUENCES IN SCHEMA public TO app_rw;
PUBLIC 의사 롤 — 모두에게 자동 부여되는 함정. PUBLIC은 모든 롤이 자동으로 속하는 가상의 롤입니다. 과거 버전에서는 public 스키마에 PUBLIC이 기본 CREATE 권한을 갖고 있어서, 접속만 하면 누구나 테이블을 만들 수 있었습니다. PostgreSQL 15부터는 이 기본 권한이 제거돼 더 안전해졌습니다. 그래도 REVOKE로 PUBLIC 권한을 명시적으로 회수해 "기본은 막고 필요한 롤에만 허용"하는 것이 안전한 습관입니다.

앱 전용 최소 권한 유저 — superuser로 붙지 마라

운영에서 가장 흔한 실수는 앱을 superuser(또는 DB 소유자)로 접속시키는 것입니다. 편하니까요 — 권한 문제가 아예 생기지 않습니다. 하지만 그 대가가 큽니다.

위험구체적으로 무슨 일이
① RLS 무력화앞 레슨에서 봤듯 superuser·owner는 RLS를 우회합니다. 정책을 아무리 잘 짜도 소용없습니다
② 사고 시 피해 무제한SQL 인젝션 한 번에 DROP TABLE, 심하면 DROP DATABASE까지 갈 수 있습니다

대신 딱 필요한 권한만 가진 롤을 쓰세요. 읽기/쓰기는 app_rw, 대시보드·리포트는 app_ro처럼요. 각 롤이 실제로 어떻게 동작하는지 SET ROLE로 검증해 봅시다.

sqlstudy_db=# — 각 롤의 권한을 SET ROLE로 검증
-- (A) app_ro: SELECT는 되고, INSERT는 거부된다 (의도된 동작)
SET ROLE app_ro;
SELECT count(*) AS visible_rows FROM orders;   -- 3 (읽기 OK)

INSERT INTO orders (amount) VALUES (999.00);
-- ERROR:  permission denied for table orders   ← 정상적인 차단
RESET ROLE;

-- (B) app_rw: SELECT와 INSERT 모두 성공
SET ROLE app_rw;
INSERT INTO orders (amount) VALUES (500.00);
-- INSERT 0 1
SELECT count(*) AS rows_after_rw_insert FROM orders;   -- 4
RESET ROLE;

그런데 여기에 실무에서 반드시 부딪히는 문제가 있습니다. GRANT ... ON orders는 지금 존재하는 테이블에만 적용됩니다. 내일 마이그레이션으로 새 테이블을 만들면? 앱 유저는 그 테이블을 못 읽습니다.

비유 — "앞으로 만들 방도 이 사람은 출입 가능"이라고 미리 등록해두기. 방을 새로 만들 때마다 열쇠를 다시 나눠주는 건 번거롭고, 한 번 깜빡하면 장애로 이어집니다. ALTER DEFAULT PRIVILEGES는 "앞으로 이 스키마에 만들어질 테이블에는 자동으로 이 권한을 부여하라"고 미리 예약해 두는 설정입니다.
sqlstudy_db=# — ALTER DEFAULT PRIVILEGES: 미래 테이블에 자동 부여
-- study가 앞으로 public에 만들 테이블은 app_ro가 자동으로 읽을 수 있게
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT ON TABLES TO app_ro;

-- 검증: 설정 후 새 테이블을 만들고 app_ro가 바로 읽히는지 확인
CREATE TABLE invoices (id int GENERATED ALWAYS AS IDENTITY PRIMARY KEY, total numeric);
INSERT INTO invoices (total) VALUES (10), (20);

SET ROLE app_ro;
SELECT count(*) AS invoices_readable_by_ro FROM invoices;  -- 2 (권한을 안 줬는데 읽힌다!)
RESET ROLE;

-- 등록된 default privilege 확인 (app_ro에게 read(r)가 예약됨)
SELECT defaclobjtype, defaclacl FROM pg_default_acl;
--  defaclobjtype |    defaclacl
-- ---------------+------------------
--  r             | {app_ro=r/study}
주의 — ALTER DEFAULT PRIVILEGES는 "누가 만든 객체인지"에 묶입니다. 위 설정은 study 롤이 만든 테이블에만 적용됩니다. 마이그레이션을 다른 롤로 돌리면 그 롤에 대해서도 따로 설정해야 합니다. 그래서 실무에서는 스키마 변경 전용 owner 롤을 하나로 고정하고, 그 롤에 대해 default privileges를 걸어두는 구성이 깔끔합니다.
권장 구성 한 장 요약. app_migrator(스키마 변경 전용, 배포 시에만 사용) → 테이블을 만들고 소유합니다. app_rw(앱 서버가 사용) → 데이터 CRUD만 가능, DDL 불가. app_ro(대시보드·분석) → 읽기만. 그리고 app_migrator에 대해 ALTER DEFAULT PRIVILEGES를 걸어두면 새 테이블 권한이 자동으로 따라갑니다.

인증 — scram-sha-256과 PG18의 OAuth 2.0

지금까지는 "이 롤이 무엇을 할 수 있는가"(권한, authorization)를 다뤘습니다. 이제 그 앞 단계인 "누가 이 롤로 접속할 수 있는가"(인증, authentication)를 짚어봅시다.

PostgreSQL의 기본 패스워드 인증은 scram-sha-256입니다. 비밀번호를 그대로 보내지 않고 챌린지-응답 방식으로 검증하므로, 네트워크를 엿봐도 비밀번호를 알아낼 수 없습니다(옛 md5 방식보다 훨씬 안전합니다).

그리고 "어떤 클라이언트가, 어떤 DB에, 어떤 방식으로 접속할 수 있는가"는 pg_hba.conf 파일이 한 줄씩 규칙으로 정합니다(HBA = Host-Based Authentication). 접속 출처 IP, 대상 DB, 유저, 인증 방식을 조합해 적는 방식이죠.

PG18 OAuth 2.0 인증 지원. PostgreSQL 18부터 외부 IdP(Okta, Entra ID 등)가 발급한 토큰으로 DB에 접속할 수 있게 됐습니다. 이전에는 DB마다 비밀번호를 따로 관리하고, 퇴사자가 생기면 모든 DB를 뒤져 계정을 지워야 했죠. 이제 조직의 SSO 체계에 DB 접근까지 통합할 수 있습니다 — 중앙에서 계정을 비활성화하면 DB 접근도 함께 끊깁니다.
MySQL — 익숙한 방식

유저를 'user'@'host' 형태로 정의해 접속 출처까지 유저 정의에 포함합니다. 권한은 GRANT ... ON db.* TO 'u'@'%'처럼 주고, 그룹 개념은 롤(8.0+)로 나중에 도입됐습니다. 스키마 USAGE 같은 별도 단계가 없어 상대적으로 단순합니다.

PostgreSQL — 이렇게 다르다

유저와 그룹을 ROLE 하나로 통합하고, 접속 출처는 pg_hba.conf에서 별도로 다룹니다. 테이블 권한 전에 스키마 USAGE가 필요한 것이 가장 자주 막히는 차이입니다. PG18부터는 scram-sha-256에 더해 OAuth 2.0도 쓸 수 있습니다.

셀프 체크

Q Postgres에서 "USER"란 무엇인가요?

유저와 그룹은 구분 없이 모두 ROLE이며, USER란 LOGIN 속성을 가진 ROLE입니다. CREATE USER는 CREATE ROLE ... LOGIN의 별칭일 뿐이죠. NOLOGIN 롤은 접속은 못 하지만 권한 묶음(그룹)으로 쓰이고, GRANT 그룹롤 TO 유저롤로 멤버십을 만들면 권한을 상속합니다.

Q 테이블에 SELECT 권한을 줬는데 "permission denied for schema"가 납니다.

스키마 USAGE 권한이 빠진 것입니다. Postgres는 데이터베이스 → 스키마 → 테이블의 두 단계 구조라, 테이블 권한(방 열쇠)만으로는 부족하고 그 스키마에 접근할 권한(층 출입증)도 필요합니다. GRANT USAGE ON SCHEMA public TO 롤;을 먼저 실행하세요.

Q 앱을 최소 권한 유저로 붙여야 하는 이유는?

두 가지입니다. ① RLS 우회 방지 — superuser·테이블 owner는 RLS를 우회하므로, 앱이 그런 롤로 붙으면 행 수준 격리가 완전히 무력화됩니다. ② 피해 범위 제한 — SQL 인젝션이나 버그가 있어도 app_rw가 가진 권한(특정 테이블의 CRUD)까지만 피해가 갑니다. 스키마 변경 권한은 별도 owner 롤로 분리하세요.

Q ALTER DEFAULT PRIVILEGES는 어떤 문제를 푸나요?

일반 GRANT는 이미 존재하는 객체에만 적용되므로, 마이그레이션으로 새 테이블을 만들 때마다 권한을 다시 줘야 하고 한 번 깜빡하면 장애가 됩니다. ALTER DEFAULT PRIVILEGES IN SCHEMA ... GRANT ... TO 롤은 "앞으로 만들 객체에 자동으로 이 권한을 부여하라"는 예약 설정입니다. 단, "누가 만든 객체인지"에 묶이므로 마이그레이션 실행 롤을 고정해 두는 편이 좋습니다.
