연결 풀링 · 확장 · 백업 — 그리고 6주 회고

운영의 마지막 조각입니다. 연결을 풀로 아끼고(PgBouncer), 확장으로 기능을 더하고(pgcrypto·pgvector), 정기적으로 백업합니다. 그리고 6주를 돌아봅니다.

여기서 Week 1과 이어집니다. 첫 레슨에서 배운 "Postgres는 연결 하나 = 프로세스 하나라서 연결이 비싸다"가 기억나시나요? 그 문제의 실제 해법이 이 레슨의 첫 섹션입니다. 6주가 한 바퀴 돌아 제자리로 옵니다.

학습 목표

  • 연결 풀링의 원리와 PgBouncer 풀 모드를 이해한다
  • 서버리스 환경의 connection storm에 대응하는 법을 안다
  • 확장 생태계(pgcrypto · pg_trgm · pgvector)를 활용한다
  • 논리 백업과 물리 백업의 차이를 알고, "복구 테스트"의 중요성을 이해한다

연결 풀링 — "연결은 비싸다"의 해법

비유 — 택시 콜센터. 손님이 올 때마다 차를 새로 사지 않습니다. 대기 중인 택시 풀에서 한 대를 배차하고, 운행이 끝나면 다시 풀로 돌려받죠. 손님이 1,000명이어도 택시 30대로 돌릴 수 있습니다. DB 연결도 똑같습니다.

Week 1에서 본 대로 PostgreSQL은 연결마다 OS 프로세스를 하나 띄웁니다. 그래서 연결을 만드는 것도 유지하는 것도 비싸고, 매 요청마다 새로 연결하면 금방 max_connections 한계에 부딪힙니다.

PgBouncer는 앱과 DB 사이에 끼어 소수의 실제 연결을 여러 클라이언트가 돌려 쓰게 해주는 경량 풀러입니다. 핵심은 "언제 연결을 반납할 것인가", 즉 풀 모드 선택입니다.

풀 모드연결을 언제 반납특징과 주의점
session클라이언트 연결이 끊길 때가장 안전(세션 상태 보존). 재사용 효율은 낮음
transaction
(가장 널리 쓰임)		트랜잭션이 끝날 때마다재사용 효율이 높음. 단 세션 상태(prepared statement, SET 등)가 다음 사용자에게 안 넘어가니 주의
statement문장 하나가 끝날 때마다가장 공격적. 여러 문장으로 된 트랜잭션 불가
transaction 모드를 쓸 때 주의 — RLS 세션 변수. 앞 레슨에서 RLS에 쓴 SET app.current_tenant를 기억하세요. transaction 모드에서는 트랜잭션이 끝나면 연결이 다른 요청에게 넘어갑니다. 세션 변수를 트랜잭션 밖에서 설정하면 다른 테넌트의 요청이 그 값을 물려받을 수 있습니다. 반드시 트랜잭션 안에서 set_config(..., true)(local=true)로 설정해 트랜잭션 종료 시 함께 사라지게 하세요.

풀 크기는 어떻게 정할까요? 직관과 반대입니다 — 무작정 늘리면 안 됩니다. 실제로 동시에 일하는 연결은 CPU 코어 수에 가깝게 두는 것이 좋습니다(보통 코어 수의 몇 배 이내). 그 위에서 PgBouncer가 수천 개의 클라이언트 연결을 소수의 서버 연결로 접어줍니다. 당연히 PgBouncer의 풀 크기 합은 DB의 max_connections보다 작아야 합니다.

서버리스의 connection storm. Lambda나 Edge Function 같은 서버리스 환경은 요청마다 인스턴스가 떴다 사라지며 저마다 새 DB 연결을 엽니다. 트래픽이 몰리면 순식간에 수천 개의 연결이 DB를 덮쳐 too many connections로 무너집니다.

해법은 앞단에 외부 풀러를 두거나(PgBouncer 등), 매니지드 Postgres가 제공하는 서버리스 전용 연결 풀러/HTTP 드라이버를 쓰는 것입니다. 이때 transaction 풀 모드가 단골 선택입니다 — 인스턴스가 짧게 살다 사라지므로 세션을 붙들고 있을 이유가 없으니까요.

확장(extension) — Postgres에 기능을 끼워 넣기

Week 1에서 "브라우저 확장 프로그램처럼 DB에 기능을 끼워 넣는다"고 했던 그 확장입니다. CREATE EXTENSION 한 줄로 새 함수·타입·인덱스 방식이 추가됩니다. 여기서는 공식 이미지에 이미 들어 있는(contrib) 두 가지를 직접 써봅니다.

sqlstudy_db=# — pgcrypto로 비밀번호 해싱
CREATE EXTENSION IF NOT EXISTS pgcrypto;
CREATE EXTENSION IF NOT EXISTS pg_trgm;

-- crypt + gen_salt(bcrypt): 같은 비밀번호도 salt 때문에 매번 다른 해시가 나온다
SELECT crypt('s3cret', gen_salt('bf')) <> crypt('s3cret', gen_salt('bf'))
       AS two_hashes_differ;
--  two_hashes_differ
-- -------------------
--  t

-- 저장된 해시로 검증: 맞는 비번이면 같은 값으로 재계산된다
WITH h AS (SELECT crypt('s3cret', gen_salt('bf')) AS stored)
SELECT (stored = crypt('s3cret', stored)) AS right_password_ok,
       (stored = crypt('wrong',  stored)) AS wrong_password_ok
FROM h;
--  right_password_ok | wrong_password_ok
-- -------------------+-------------------
--  t                 | f
이 코드가 보여주는 것 — salt의 원리. 같은 비밀번호 's3cret'를 두 번 해싱했는데 결과가 다릅니다. 매번 무작위 salt가 섞이기 때문이죠. 그래서 해시 값만 봐서는 두 사용자가 같은 비밀번호를 쓰는지조차 알 수 없습니다. 검증할 때는 crypt('s3cret', stored)처럼 저장된 해시를 salt로 재사용해 다시 계산하면 같은 값이 나옵니다. 이게 bcrypt 검증의 원리입니다.
헷갈리기 쉬운 점. gen_random_uuid()는 pgcrypto가 아니라 PG13+ 코어 함수입니다(확장 없이 바로 쓸 수 있습니다). pgcrypto의 고유한 가치는 crypt()·gen_salt()·digest()·hmac() 같은 암호화·해싱 함수들입니다.

그리고 2026년 현재 가장 주목받는 확장은 단연 pgvector입니다. AI 임베딩을 저장하고 의미 기반 유사도 검색(RAG)을 수행하죠. Postgres가 별도의 벡터 DB 없이 그 자체로 벡터 검색 엔진이 되는 셈입니다.

단, pgvector는 공식 postgres 이미지에 없습니다. vector 확장은 postgres:18 이미지에 포함돼 있지 않아, 아래 코드를 그대로 실행하면 CREATE EXTENSION vector에서 실패합니다. 쓰려면 pgvector/pgvector:pg18 이미지를 쓰거나 확장을 직접 설치해야 합니다. 아래는 "이렇게 쓴다"는 개념 예시입니다.
sql개념 예시 (pgvector 이미지 필요) — 실행 안 함
CREATE EXTENSION vector;                  -- 공식 postgres:18엔 없음!

CREATE TABLE docs (
  id        bigserial PRIMARY KEY,
  content   text,
  embedding vector(1536)                  -- 임베딩 차원
);

-- 코사인 거리(<=>)로 질의 벡터와 가장 가까운 5개 (RAG 검색)
SELECT id, content FROM docs
ORDER BY embedding <=> $1 LIMIT 5;

-- 근사 최근접(ANN) 인덱스: HNSW 또는 IVFFlat
CREATE INDEX ON docs USING hnsw (embedding vector_cosine_ops);

마지막 줄을 눈여겨보세요. Week 4에서 배운 USING 문법 그대로입니다. 확장이 새로운 인덱스 방식(hnsw)을 추가하고, 우리는 이미 아는 문법으로 그걸 씁니다. Postgres 확장 생태계의 우아함이 여기 있습니다.

백업 — 복구 테스트까지 해야 진짜 백업

백업 방식은 크게 둘로 나뉩니다. 차이를 비유로 잡아둡시다.

비유 — 레시피 적어두기 vs 주방 통째로 사진 찍기. 논리 백업(pg_dump)은 레시피를 글로 적어두는 것입니다. "이 테이블은 이런 구조고, 데이터는 이렇다"를 SQL로 기록하죠. 다른 버전·다른 서버에서도 재현할 수 있고, 필요한 테이블만 골라 복원할 수도 있습니다. 물리 백업(pg_basebackup)은 주방을 통째로 촬영하는 것입니다. 파일을 그대로 복사하니 빠르고 완전하지만, 같은 버전의 Postgres에만 되돌릴 수 있습니다.
bashshell — 백업/복원 명령 정리
# 논리 백업: 커스텀 포맷(-Fc) → 압축 + pg_restore로 선택 복원 가능
pg_dump -Fc study_db > study.dump
pg_restore -d study_db study.dump

# 롤(권한)·테이블스페이스 등 클러스터 전역 객체까지 (DB 안에 없는 것들)
pg_dumpall --roles-only > roles.sql

# 물리 백업: 클러스터 파일 전체 (복제 구성·PITR의 토대)
pg_basebackup -D /backup -Ft -z

# (PG17+) 증분 백업: 직전 백업 이후 바뀐 블록만
pg_basebackup --incremental=backup_manifest -D /backup2

두 번째 명령을 놓치기 쉽습니다. 롤과 권한은 특정 DB가 아니라 클러스터 전역에 저장되므로, pg_dump만으로는 백업되지 않습니다. 복구했더니 테이블은 있는데 앱 유저가 없어 접속이 안 되는 사고가 여기서 나옵니다.

PITR(Point-In-Time Recovery)는 베이스 백업 + WAL 아카이브를 합쳐 "장애 직전 특정 시각"으로 되돌리는 기법입니다. "실수로 DELETE를 날린 오후 3시 27분 직전으로" 같은 복구가 가능하죠. PG17부터는 pg_basebackup --incremental로 바뀐 블록만 떠서 백업 비용을 크게 줄일 수 있습니다.

복구 테스트 없는 백업은 백업이 아닙니다.

가장 흔한 운영 사고는 "백업은 매일 잘 돌고 있었는데, 막상 복구해 보니 안 됐다"입니다. 권한이 빠졌거나, 파일이 손상됐거나, 스크립트가 조용히 실패하고 있었거나. 백업 파일이 존재한다는 것과 복구가 가능하다는 것은 전혀 다른 이야기입니다.

정기적으로 별도 환경에 실제로 복원해 보는 리허설까지 해야 진짜 백업입니다. 그리고 두 숫자를 미리 정하세요 — RTO(복구에 걸려도 되는 시간)와 RPO(잃어도 되는 데이터의 양). 그 목표를 만족하는지가 백업 전략의 합격 기준입니다.

MySQL — 익숙한 방식

연결을 스레드로 다뤄 연결 비용이 낮고, 풀링 없이도 비교적 많은 연결을 버팁니다. 기능은 상당수가 엔진에 내장되는 경향이고, 백업은 mysqldump(논리)·xtrabackup(물리)을 씁니다.

PostgreSQL — 이렇게 다르다

연결마다 프로세스를 쓰므로 다수 연결 환경에서 외부 풀러가 사실상 필수입니다. 대신 확장 생태계(pgcrypto·pg_trgm·pgvector·PostGIS…)로 기능을 자유롭게 더할 수 있고, 백업은 pg_dump(논리)와 pg_basebackup(물리·증분)으로 다룹니다.

6주 회고 & 다음 로드맵

여기까지 오셨습니다 — 축하합니다! "기본 SQL은 알지만 Postgres 고유 기능은 처음"이던 자리에서 시작해, 이제 실무에서 Postgres를 자신 있게 다룰 토대를 갖추셨습니다. 6주를 한 줄씩 돌아봅시다.

1
큰 그림 · 환경 · 타입 — "연결 하나 = 프로세스 하나"라는 Postgres의 정체성, Docker + psql 환경, 그리고 IDENTITY·uuidv7()·timestamptz·numeric이라는 타입 선택의 원칙.
2
스키마 · 쓰기의 힘 — 무결성을 앱이 아니라 DB에 맡기는 제약, RETURNING·UPSERT로 왕복과 경쟁 상태를 없애기, 트리거로 updated_at·감사 로그 자동화.
3
JSONB · 검색 — 관계형을 포기하지 않고 유연함을 얻는 jsonb와 GIN 인덱스, 배열·enum·range, 그리고 tsvector·pg_trgm으로 하는 진짜 검색.
4
인덱스 · 성능 — 데이터 모양에 맞춰 색인을 고르기, EXPLAIN ANALYZE로 추측 대신 측정하기, 통계의 중요성, 그리고 CTE·윈도우 함수·keyset 페이지네이션.
5
트랜잭션 · MVCC — MySQL과 다른 기본 격리 수준, 행을 덮어쓰지 않는 MVCC와 VACUUM, 그리고 락·데드락·SKIP LOCKED 큐 패턴.
6
RLS · 권한 · 운영 — DB가 강제하는 행 수준 보안, 최소 권한 롤 설계, 연결 풀링·확장·백업까지.

다음 단계 — 더 깊이 가고 싶다면.

① 파티셔닝 — 대규모 시계열·로그 테이블을 범위/리스트로 쪼개 관리와 성능을 동시에 잡습니다(PARTITION BY). Week 4의 BRIN과 함께 쓰면 강력합니다.
② 논리 복제 · CDC — 변경 데이터를 다른 시스템(분석 DB, 검색 엔진, 이벤트 스트림)으로 흘려보냅니다.
③ 모니터링 — pg_stat_statements로 느린 쿼리를 추적하고, pg_stat_activity로 현재 상태를 관찰합니다. Week 5의 "긴 트랜잭션 찾기"가 여기서 이어집니다.
④ 고가용성 · 레플리케이션 — 스트리밍 복제와 페일오버로 무중단 운영을 만듭니다.

이 6주가 그 모든 주제로 가는 탄탄한 출발점입니다. 수고하셨습니다! 🎉

셀프 체크

Q PgBouncer는 어떤 문제를 푸나요?

PostgreSQL은 연결마다 프로세스를 띄워 연결 생성·유지 비용이 크고 max_connections 한계도 있습니다. PgBouncer는 앱과 DB 사이에서 소수의 실제 연결을 재사용(특히 transaction 풀 모드)해, 수천 개의 클라이언트 연결을 소수의 서버 연결로 접어줍니다. 서버리스의 connection storm처럼 연결이 폭증하는 환경에서 특히 중요합니다.

Q transaction 풀 모드에서 RLS 세션 변수를 쓸 때 주의할 점은?

트랜잭션이 끝나면 연결이 다른 요청에게 넘어가므로, 트랜잭션 밖에서 SET app.current_tenant를 하면 다음 요청이 그 값을 물려받아 다른 테넌트 데이터가 샐 수 있습니다. 반드시 트랜잭션 안에서 set_config(..., true)(local=true)로 설정해 트랜잭션 종료와 함께 사라지게 하세요.

Q pg_dump와 pg_basebackup의 차이는?

pg_dump는 논리 백업으로 특정 DB의 스키마·데이터를 SQL/아카이브로 추출합니다("레시피를 적어두기") — 선택적 복원과 버전 간 이식에 유리합니다. pg_basebackup은 물리 백업으로 클러스터의 데이터 파일 자체를 복사합니다("주방을 통째로 촬영") — 복제 구성·PITR의 토대이고 PG17+는 증분 백업도 됩니다. 그리고 롤·권한은 pg_dumpall --roles-only로 따로 떠야 한다는 점을 잊지 마세요.

Q "백업은 잘 돌고 있다"만으로 충분한가요?

충분하지 않습니다. 백업 파일의 존재와 복구 가능성은 다른 이야기입니다. 가장 흔한 운영 사고가 "백업은 있었는데 막상 복구해 보니 안 됐다"입니다. 정기적으로 별도 환경에 실제로 복원해 보는 리허설을 하고, RTO(복구 소요 시간)와 RPO(허용 데이터 손실량) 목표를 정해 그 기준을 만족하는지 검증해야 합니다.
