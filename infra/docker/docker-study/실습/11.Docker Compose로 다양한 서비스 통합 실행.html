Docker Compose로 다양한 서비스 통합 실행

Compose로 Flask 앱 + MySQL을 하나로 묶어 실행해봅니다. Dockerfile로 이미지를 빌드하고, compose.yml로 두 서비스를 정의한 뒤, app.py의 재시도 로직이 depends_on의 한계를 어떻게 보완하는지까지 코드 레벨에서 확인합니다.
🚀1. 들어가며

지금까지는 docker run으로 컨테이너 하나씩을 다뤘습니다. 이번 실습은 Flask 웹 애플리케이션과 MySQL 데이터베이스, 두 개의 서비스를 docker compose up 명령어 하나로 함께 띄우는 것이 목표입니다.

디렉토리 안에는 4개의 파일이 있습니다.

  • Dockerfile — Flask 애플리케이션을 담을 이미지를 빌드하는 설계도
  • compose.yml — app(Flask) + db(MySQL) 두 서비스를 정의하고, 둘을 하나의 네트워크로 묶는 설정
  • app.py — 환경변수로 MySQL에 접속하고, 메시지를 저장·조회하는 Flask 애플리케이션
  • requirements.txt — Flask 애플리케이션이 필요로 하는 Python 패키지 목록

이 문서는 이 4개 파일을 Dockerfile → compose.yml → app.py 순서로 읽으면서, 여러 서비스를 하나로 통합 실행할 때 실제로 무엇을 신경 써야 하는지(서비스 간 통신, 데이터 영속성, 시작 순서와 준비 상태의 차이)를 코드 레벨에서 확인합니다.

💡 참고: Compose 자체의 개념(왜 필요한지, depends_on/environment/volumes 문법)은 이미 05강. Docker Compose 완전 정복에서 다뤘습니다. 이 문서는 그 개념을 실제 동작하는 Flask + MySQL 예제에 적용해보는 실습편입니다.
🐳2-1. Dockerfile — Flask 이미지 빌드
dockerfile
# ====================================
# Flask 애플리케이션 Docker 이미지 빌드
# ====================================
# 이 Dockerfile은 Flask 웹 애플리케이션을 Docker 컨테이너에서 실행하기 위한
# 이미지를 생성합니다. MySQL 데이터베이스와 함께 작동합니다.

# Step 1: Use a lightweight Python base image
# python:3.13-slim은 전체 Python 이미지보다 크기가 작아 컨테이너 이미지 최적화에 유리함
FROM python:3.13-slim

# Step 2: Set the working directory inside the container
# 컨테이너 내부에서 모든 명령이 실행될 기본 디렉토리 설정
WORKDIR /app

# Step 3: Copy the application code into the container
# 호스트의 현재 디렉토리의 모든 파일을 컨테이너의 /app 디렉토리로 복사
# (app.py, requirements.txt 등이 포함됨)
COPY . /app

# Step 4: Install Python dependencies
# requirements.txt에 정의된 패키지들을 설치
# --no-cache-dir 옵션으로 캐시를 저장하지 않아 이미지 크기 감소
RUN pip install --no-cache-dir -r requirements.txt

# Step 5: Expose the port the application will run on
# 포트 5000을 외부에 노출 (Flask는 기본적으로 5000 포트에서 실행)
# 이 포트는 docker-compose.yml에서 호스트 포트와 매핑됨
EXPOSE 5000

# Step 6: Define the default command to run the application
# 컨테이너가 시작될 때 자동으로 실행될 명령어
# Flask 애플리케이션(app.py)을 Python 인터프리터로 실행
CMD ["python", "app.py"]
requirements.txt
text
flask==2.3.2
mysql-connector-python==8.1.0

이 Dockerfile은 05강에서 다룬 "Dockerfile은 이미지를 어떻게 빌드할지 정의하고, docker compose build(또는 up 시 자동 빌드)가 이를 읽어 이미지를 만든다"는 흐름 그대로입니다. compose.yml의 app 서비스가 build: context: .로 바로 이 Dockerfile을 가리킵니다.

📄2-2. compose.yml — app + db 두 서비스 정의
yaml
# ================================================
# Docker Compose 설정 파일
# ================================================
# 이 파일은 Flask 웹 애플리케이션과 MySQL 데이터베이스를 함께 실행하는
# 멀티 컨테이너 Docker 환경을 정의합니다.
#
# 실행 명령어: docker-compose up
# 중지 명령어: docker-compose down

services:
  # ================================================
  # Flask 웹 애플리케이션 서비스
  # ================================================
  app:
    build:
      # 현재 디렉토리의 Dockerfile을 사용하여 이미지 빌드
      context: .

    ports:
      # 호스트의 포트 5001 → 컨테이너의 포트 5000으로 매핑
      # 웹 브라우저에서 localhost:5001로 접근 가능
      - "5001:5000"

    depends_on:
      # db 서비스가 먼저 시작된 후에 app 서비스가 시작되도록 순서 지정
      - db

    # 환경 변수: Flask 앱에서 데이터베이스에 연결하기 위해 필요한 설정
    environment:
      - MYSQL_HOST=db          # Docker 네트워크 내에서 MySQL 서비스의 호스트명
      - MYSQL_USER=root        # MySQL 사용자명
      - MYSQL_PASSWORD=password # MySQL 루트 사용자 비밀번호
      - MYSQL_DATABASE=exampledb # 사용할 데이터베이스명

  # ================================================
  # MySQL 데이터베이스 서비스
  # ================================================
  db:
    # Docker Hub의 공식 MySQL 8.0 이미지 사용
    image: mysql:8.0

    # MySQL 초기 설정 환경 변수
    environment:
      MYSQL_ROOT_PASSWORD: password  # 루트 사용자 비밀번호 설정
      MYSQL_DATABASE: exampledb      # 초기 데이터베이스 자동 생성

    ports:
      # 호스트의 포트 3306 → 컨테이너의 포트 3306으로 매핑
      # 호스트 환경에서 MySQL 클라이언트로 접근 가능
      - "3306:3306"

    volumes:
      # db_data 볼륨을 MySQL 데이터 디렉토리에 마운트
      # 컨테이너가 종료되어도 데이터가 호스트에 지속됨 (데이터 영속성)
      - db_data:/var/lib/mysql

    # 서비스 상태 확인 설정
    # Flask 앱이 연결하기 전에 MySQL이 완전히 준비되었는지 확인
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "--silent"]  # MySQL 응답 확인
      interval: 5s     # 5초마다 상태 확인
      timeout: 10s     # 10초 내에 응답하지 않으면 실패 판정
      retries: 3       # 최대 3회까지 재시도

# ================================================
# 볼륨(Storage) 정의
# ================================================
volumes:
  # MySQL 데이터 영속성 보장을 위한 명명 볼륨
  # Docker에서 자동으로 관리하는 호스트 디렉토리에 저장됨
  db_data:

# ================================================
# 문제 해결 (Troubleshooting)
# ================================================
# 만약 문제가 발생하면 다음 명령어로 모든 볼륨과 이미지를 제거합니다:
# docker-compose down --rmi all --volumes --remove-orphans
#
# 주의: 이 명령어는 db_data 볼륨의 모든 데이터를 삭제하므로 조심하세요!

app 서비스와 db 서비스는 같은 compose.yml 안에 정의되었기 때문에 Compose가 자동으로 만들어주는 공통 네트워크에 함께 연결됩니다. 그래서 app의 environment에 있는 MYSQL_HOST=db처럼 서비스 이름을 그대로 호스트명으로 사용할 수 있습니다.

🐍2-3. app.py — MySQL 접속과 재시도 로직
python
import os
from flask import Flask
import mysql.connector
import time

app = Flask(__name__)

# Database configuration
DB_CONFIG = {
    'host': os.getenv("MYSQL_HOST"),  # MySQL service name from docker-compose.yml
    'user': os.getenv("MYSQL_USER"),
    'password': os.getenv("MYSQL_PASSWORD"),
    'database': os.getenv("MYSQL_DATABASE"),
}

# Function to retry database connection
def connect_with_retry(retries=5, delay=2):
    for attempt in range(retries):
        try:
            connection = mysql.connector.connect(
                host=DB_CONFIG['host'],
                user=DB_CONFIG['user'],
                password=DB_CONFIG['password'],
            )
            print("Connected to the database!")
            return connection
        except mysql.connector.Error as e:
            print(f"Attempt {attempt + 1} failed: {e}")
            time.sleep(delay)
    raise Exception("Failed to connect to the database after multiple attempts.")

# Initialize the database and table
def initialize_database():
    try:
        connection = connect_with_retry()
        cursor = connection.cursor()
        cursor.execute(f"CREATE DATABASE IF NOT EXISTS {os.getenv('MYSQL_DATABASE')}")
        cursor.execute(f"USE {os.getenv('MYSQL_DATABASE')}")
        cursor.execute("""
            CREATE TABLE IF NOT EXISTS messages (
                id INT AUTO_INCREMENT PRIMARY KEY,
                content VARCHAR(255) NOT NULL
            )
        """)
        connection.commit()
        print("Database and table initialized.")
    except Exception as e:
        print(f"Error initializing the database: {e}")
    finally:
        if 'connection' in locals() and connection:
            connection.close()

@app.route('/')
def home():
    try:
        connection = mysql.connector.connect(**DB_CONFIG)
        cursor = connection.cursor()

        # Insert a message into the table
        cursor.execute("INSERT INTO messages (content) VALUES ('Hello from MySQL!')")
        connection.commit()

        # Retrieve messages from the table
        cursor.execute("SELECT * FROM messages")
        rows = cursor.fetchall()
        return f"Messages in database: {rows}"
    except Exception as e:
        return f"Error interacting with the database: {e}"
    finally:
        if 'connection' in locals() and connection:
            connection.close()

if __name__ == "__main__":
    initialize_database()
    app.run(host='0.0.0.0', port=5000)

흐름은 다음과 같습니다.

  • DB_CONFIG는 compose.yml의 environment에 정의된 4개 값(MYSQL_HOST, MYSQL_USER, MYSQL_PASSWORD, MYSQL_DATABASE)을 os.getenv로 그대로 읽어옵니다. 코드에 접속 정보를 하드코딩하지 않고 Compose 쪽에서 주입받는 구조입니다.
  • 컨테이너가 시작되면 if __name__ == "__main__": 블록에서 initialize_database()를 먼저 호출해 데이터베이스와 messages 테이블을 준비하고, 그다음 app.run(...)으로 Flask 서버를 띄웁니다.
  • initialize_database()는 직접 mysql.connector.connect(...)를 호출하지 않고 connect_with_retry()를 거칩니다.
  • / 라우트(home())에 접속하면 messages 테이블에 'Hello from MySQL!'을 INSERT하고, 다시 전체 행을 SELECT해서 "Messages in database: [...]" 형태로 반환합니다.
🔁3. depends_on은 시작 순서만 보장한다 — retry 로직과 healthcheck의 역할

05강에서 이미 짚었던 depends_on의 주의점이, 이 예제에서는 실제 코드로 어떻게 대응되는지 확인할 차례입니다.

⚠️ depends_on의 실체: compose.yml의 app 서비스에 있는 depends_on: - db는 "db 컨테이너의 프로세스가 시작된 뒤에 app 컨테이너를 시작하라"는 뜻일 뿐입니다. MySQL 컨테이너가 뜨는 것과, MySQL 서버가 커넥션을 받을 수 있을 만큼 초기화를 끝내는 것은 전혀 다른 이야기입니다. MySQL은 최초 구동 시 데이터 디렉토리 초기화에만 수 초~수십 초가 걸릴 수 있는데, depends_on의 짧은 목록 형식 (- db)은 이 준비 시간을 전혀 기다려주지 않습니다.

그래서 app.py에는 connect_with_retry(retries=5, delay=2)라는 방어 로직이 들어 있습니다. mysql.connector.connect(...)가 실패하면 예외를 잡아서 2초를 쉬었다가 다시 시도하기를 최대 5번 반복합니다. 즉 "db 컨테이너가 시작됐다"와 "MySQL이 연결을 받을 준비가 됐다" 사이의 간극을, Compose가 아니라 애플리케이션 코드가 재시도로 메꾸는 것입니다. initialize_database()가 테이블을 만들기 전에 반드시 connect_with_retry()를 거치는 이유도 여기에 있습니다 — 이 시점이 바로 MySQL이 아직 준비되지 않았을 가능성이 가장 큰 타이밍이기 때문입니다.

한편 db 서비스에는 이미 healthcheck 블록이 정의되어 있습니다.

yaml
healthcheck:
  test: ["CMD", "mysqladmin", "ping", "--silent"]
  interval: 5s
  timeout: 10s
  retries: 3

이 설정은 5초마다 컨테이너 내부에서 mysqladmin ping을 실행해서, MySQL이 실제로 연결을 받을 수 있는 상태인지 Docker가 스스로 판단하게 합니다. 다만 지금 이 compose.yml의 depends_on은 - db라는 짧은 목록 형식이라, 이 healthcheck 결과를 참조하지 않습니다. 만약

yaml
depends_on:
  db:
    condition: service_healthy

처럼 조건부 형식으로 바꾼다면, Compose가 db의 healthcheck가 healthy로 판정될 때까지 app 컨테이너 시작 자체를 미뤄줍니다 — 즉 애플리케이션이 재시도 로직 없이도 "이미 준비된 DB"에만 연결을 시도하게 만드는, 더 근본적이고 견고한 해결책입니다. 지금 이 예제는 그 대신 애플리케이션 레벨의 connect_with_retry로 같은 문제를 해결하고 있으며, healthcheck 블록은(조건부 depends_on으로 연결하면 그대로 활용 가능한) 더 견고한 대안이 이미 준비되어 있음을 보여줍니다.

🚀 한 줄 정리: depends_on(순서) + connect_with_retry(코드 레벨 방어) + healthcheck(더 견고한 대안)는 같은 문제("DB가 준비되기 전에 앱이 연결을 시도하는 상황")를 서로 다른 층위에서 다루는 3가지 접근입니다.
💻4. 실행 명령어 — up → 접속 확인 → down
bash
# 1. app + db 두 서비스를 빌드하고 실행합니다.
docker compose up

# 2. 브라우저 또는 curl로 Flask 앱에 접속합니다.
#    compose.yml의 "5001:5000" 포트 매핑에 따라 호스트 포트는 5001입니다.
#    http://localhost:5001

# 접속할 때마다 messages 테이블에 새 행이 INSERT되고,
# 응답으로 "Messages in database: [(1, 'Hello from MySQL!'), (2, 'Hello from MySQL!'), ...]" 형태가 출력됩니다.

# 3. 실습이 끝나면 compose.yml 하단의 트러블슈팅 주석에 따라 정리합니다.
#    --rmi all      : 빌드/사용된 이미지까지 모두 제거
#    --volumes      : db_data 볼륨까지 제거 (MySQL 데이터가 모두 사라짐, 주의!)
#    --remove-orphans : compose.yml에 더 이상 없는 orphan 컨테이너까지 정리
docker compose down --rmi all --volumes --remove-orphans
🔧 안내: docker compose down --rmi all --volumes --remove-orphans는 compose.yml 파일 맨 아래 주석에 이미 적혀 있는 명령어입니다. --volumes가 db_data Named Volume까지 삭제하므로, 저장된 메시지 데이터를 보존하고 싶다면 이 옵션 없이 docker compose down만 사용하세요.
🔗5. 04강 · 05강과의 연결
📦 04강 — Docker Volume 완전 정복

compose.yml의 volumes: - db_data:/var/lib/mysql은 04강에서 다룬 Named Volume입니다. 컨테이너를 docker compose down (볼륨 옵션 없이)으로 내렸다가 다시 docker compose up해도, db_data 볼륨에 저장된 MySQL 데이터는 그대로 유지됩니다. 반대로 위 4번 섹션의 --volumes 옵션을 붙이면 이 Named Volume 자체가 삭제되어 데이터가 사라진다는 점도 04강의 "볼륨의 생명주기는 컨테이너와 분리되어 있다"는 개념과 정확히 맞닿아 있습니다.

🔗 05강 — Docker Compose 완전 정복

app 서비스의 environment에 있는 MYSQL_HOST=db는 05강 7절 "컨테이너 간 통신"에서 설명한 서비스 이름 = 호스트명 규칙을 그대로 사용한 예시입니다. app.py가 os.getenv("MYSQL_HOST")로 읽어온 "db"라는 문자열은, IP 주소가 아니라 compose.yml에 정의된 MySQL 서비스의 이름이며, Compose가 두 서비스를 같은 네트워크에 묶어주기 때문에 이 이름만으로 연결이 가능합니다. 또한 이 문서 3절에서 다룬 depends_on의 한계도 05강 4절에서 이미 "시작 순서만 보장하고 준비 완료는 보장하지 않는다"고 언급했던 내용을 실제 코드(connect_with_retry)로 확인한 것입니다.

compose.yml의 healthcheckmysqladmin ping으로 DB 준비 상태를 판별하는, 조건부 depends_on과 결합 가능한 더 견고한 대안
volumes: db_data04강의 Named Volume — MySQL 데이터 영속화
MYSQL_HOST=db05강의 서비스 간 통신 — 서비스 이름이 곧 호스트명
docker compose down --rmi all --volumes --remove-orphans이미지·볼륨·orphan 컨테이너까지 모두 정리하는 완전 초기화 명령어
🚀 핵심 한 문장: 여러 서비스를 하나로 통합 실행할 때는 depends_on으로 시작 순서만 맞추는 것으로는 부족하며, 애플리케이션의 재시도 로직이나 healthcheck 기반의 조건부 대기로 "준비 완료"까지 보장해야 안정적으로 동작한다.
