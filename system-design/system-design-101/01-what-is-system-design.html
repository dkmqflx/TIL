시스템 디자인이 뭐예요?

딱 한 문장으로 말하면, 시스템 디자인은 "어떤 문제를 풀기 위해, 필요한 부품들을 어떻게 배치하고 서로 연결할지 큰 그림을 그리는 일"입니다.

비유 — 집을 짓기 전 설계도
집을 지을 때 벽돌부터 쌓지 않습니다. 먼저 설계도를 그리죠. "방은 몇 개, 화장실은 어디, 부엌은 거실 옆에, 배관은 이렇게…" 시스템 디자인이 바로 이 설계도입니다. 벽돌을 쌓는 일(=코딩)을 시작하기 전에, 전체 구조를 먼저 정하는 단계예요.

좀 더 풀어서 설명하면

우리가 소프트웨어를 만드는 이유는 항상 "해결하고 싶은 문제(=비즈니스 요구사항)"가 있기 때문입니다. 시스템 디자인은 그 요구사항을 만족시키는 솔루션(해결책)의 구조를 설계하는 과정이에요. 구체적으로는 이런 것들을 정합니다.

  • 어떤 부품(자원)이 필요한가? — 서버, 데이터베이스, 캐시 같은 하드웨어·소프트웨어 자원
  • 부품들을 어떻게 배치할까? — 무엇을 앞에 두고 무엇을 뒤에 둘지
  • 부품들이 어떻게 서로 대화할까? — 데이터가 어디서 어디로 흐르는지
  • 어떻게 하면 더 효율적일까? — 더 빠르고, 더 안정적이고, 더 잘 늘어나게
핵심 — 시스템 디자인은 "추상적"이고 "하이 레벨"입니다.
코드 한 줄 한 줄이 아니라 "구현(코드)"이 아닌 "구조(뼈대)"에 집중합니다. 세세한 함수 이름이 아니라 "요청이 들어오면 → 로드 밸런서 → 서버 → DB 순으로 흐른다" 같은 큰 그림을 그리는 거예요.

코딩과 시스템 디자인은 뭐가 다를까?

🔍 코딩 (구현 / Low Level)
"이 함수는 어떻게 짜지?"
"이 반복문을 어떻게 최적화하지?"
"변수 이름을 뭐라고 하지?"

→ 나무 한 그루를 자세히 봅니다.
🗺️ 시스템 디자인 (구조 / High Level)
"서버를 몇 대 둘까?"
"DB가 터지면 어떻게 하지?"
"사용자가 100배 늘면 감당될까?"

→ 숲 전체를 멀리서 봅니다.
🤔

왜 배워야 하나요?

"난 그냥 기능만 잘 만들면 되는 거 아냐?"라고 생각할 수 있어요. 하지만 서비스가 커지는 순간, 시스템 디자인을 모르면 벽에 부딪힙니다.

🌱
트래픽이 늘어도 안 터진다
사용자가 100명일 때는 아무 구조나 괜찮습니다. 하지만 10만 명이 되면? 미리 대비한 사람만 살아남습니다.
🧩
전체 그림이 보인다
내가 짠 코드가 거대한 시스템 어디에 붙어 돌아가는지 이해하면, 훨씬 좋은 결정을 내릴 수 있습니다.
💬
개발자끼리 대화가 된다
"여기 캐시 하나 두죠", "리버스 프록시로 받읍시다" 같은 대화가 통해야 협업이 됩니다.
🎯
면접에 나온다
"URL 하나 검색 시스템을 설계해 보세요" 같은 시스템 디자인 인터뷰는 개발자 채용의 단골 주제입니다.
🎯

좋은 시스템의 4가지 목표

시스템을 설계할 때 우리는 무작정 만들지 않습니다. "좋은 시스템이란 무엇인가"라는 기준을 놓고 그걸 향해 설계하죠. 대표적인 4가지 목표는 다음과 같습니다.

🛡️
1. 신뢰성 (Reliability)
일부가 고장 나도 서비스가 멈추지 않는 것. 24시간 불 켜진 편의점처럼요.
🧱
2. 유지보수성 (Maintainability)
부품을 레고처럼 갈아끼우기 쉬운 것. 한 곳을 고쳐도 전체가 무너지지 않아야 합니다.
⚡
3. 성능 (Performance)
빠르고 안정적인 것. 버튼을 눌렀는데 5초씩 기다리면 사용자는 떠납니다.
📈
4. 확장성 (Scalability)
사용자·데이터가 늘어나도 감당되는 것. 손님이 몰려도 대처할 수 있어야 합니다.

하나씩, 비유로 이해하기

🛡️ 신뢰성 — 언제 가도 열려 있는 편의점

편의점 알바생 한 명이 갑자기 아파도 편의점은 문을 닫지 않죠. 다른 알바생이 대신 나옵니다. 좋은 시스템도 마찬가지로 서버 한 대가 죽어도 다른 서버가 대신 일해서 사용자는 아무 일 없었다는 듯 서비스를 계속 씁니다.

🧱 유지보수성 — 레고 블록처럼

시스템을 하나의 커다란 덩어리로 만들면, 작은 수정 하나에도 전체가 흔들립니다. 대신 부품(모듈) 단위로 나눠 두면 필요한 블록만 쏙 빼서 갈아끼울 수 있어요. 이렇게 나눠 두는 걸 모듈화(modularization)라고 합니다.

⚡ 성능 — 빠르고 안정적으로

성능을 높이는 대표적인 도구가 두 가지 있는데, 이 가이드에서 앞으로 다룰 주제와 바로 연결됩니다.

DB 인덱싱이 뭐예요? 500쪽짜리 책에서 "로드 밸런서"라는 단어를 찾는다고 해봅시다. 1쪽부터 다 읽으면 느리죠. 하지만 책 뒤 '찾아보기(색인)'를 보면 "로드 밸런서 … 321쪽"이라고 바로 알려줍니다. 데이터베이스 인덱스도 똑같이, 자주 찾는 값에 대해 미리 '색인'을 만들어 두어 조회를 훨씬 빠르게 만드는 기술입니다.

📈 확장성 — 손님이 몰려도 대처하기

확장성은 워낙 중요해서 바로 다음 섹션에서 수직 확장 / 수평 확장이라는 두 가지 방법으로 자세히 다룹니다.

📈

수직 확장 vs 수평 확장

사용자가 늘어서 서버 한 대가 버거워졌습니다. 어떻게 감당할까요? 방법은 크게 두 가지입니다.

비유 — 손님이 몰리는 1인 식당
요리사 한 명이 주문을 다 처리하다가 손님이 몰려 감당이 안 됩니다. 두 가지 선택지가 있어요.
① 그 요리사에게 더 좋은 칼·더 큰 화구를 준다 (한 명을 더 강하게) → 수직 확장
② 똑같은 요리사를 여러 명 더 고용한다 (사람 수를 늘림) → 수평 확장

⬆️ 수직 확장 (Vertical Scaling) — 한 대를 더 강하게

서버 한 대의 하드웨어 성능을 업그레이드하는 방법입니다. CPU 코어를 늘리고, RAM을 키우고, 더 빠른 디스크로 교체하는 거죠.

🖥️ 서버 (약함)
→
🖥️ 서버 (CPU↑ RAM↑ 디스크↑)
수직 확장의 한계 두 가지
① 물리적 한계: 하드웨어는 아무리 좋은 걸로 바꿔도 어느 순간 더 이상 올릴 수 없습니다. (사람도 아무리 훈련해도 한계가 있듯)
② 단일 장애점: 결국 서버는 한 대입니다. 그 한 대가 죽으면 전체 서비스가 멈춥니다.

➡️ 수평 확장 (Horizontal Scaling) — 여러 대로 나누기

같은 일을 하는 서버를 여러 대로 늘리는 방법입니다. A 서버가 있으면 똑같은 B, C 서버를 만들어서 요청을 나눠 처리하죠.

🖥️ 서버 A
🖥️ 서버 B
🖥️ 서버 C
…필요하면 계속 추가
서버가 여러 대가 되면 "들어온 요청을 어느 서버로 보낼까?"를 정해주는 교통정리 담당이 필요합니다. 그게 바로 로드 밸런서(Part 4)예요. 한 대가 죽어도 나머지가 일하니 신뢰성까지 좋아집니다.

비유요리사 1명을 강하게요리사를 여러 명 고용
한계하드웨어 성능 한계가 있음이론상 거의 무제한

한 줄 정리: 수직 확장은 "임시방편", 수평 확장은 "제대로 된 확장"이라고 기억하세요. 큰 서비스는 대부분 수평 확장으로 갑니다.

기능적 vs 비기능적 요구사항

설계는 항상 요구사항에서 출발합니다. 그런데 요구사항은 성격이 다른 두 종류로 나뉩니다.

비유 — 자동차로 이해하기
기능적 요구사항 = 자동차가 "무엇을 하는가" → 앞으로 간다, 멈춘다, 방향을 튼다
비기능적 요구사항 = 그걸 "얼마나 잘 하는가" → 얼마나 빠르게, 얼마나 안전하게, 연비는 얼마나 좋게

검색 엔진을 만든다고 해봅시다

영상의 예시를 따라가 볼게요. 검색 엔진을 설계한다면 요구사항은 이렇게 나뉩니다.

✅ 기능적 요구사항 — "무엇을 하는가"
시스템이 해야 하는 일(기능)을 나열합니다.

🔍 검색 — 키워드로 검색할 수 있어야 함
📄 결과 출력 — 검색 결과를 보여줘야 함
↕️ 정렬 — 결과를 원하는 순서로 정렬
🔽 필터링 — 조건으로 결과를 걸러냄
🖥️ UI — 사용자가 쓸 화면
📐 비기능적 요구사항 — "얼마나 잘 하는가"
시스템의 품질 기준을 정합니다.

⚡ 성능 — 검색 결과를 2초 안에 응답
📈 확장성 — 사용자 1천 명 → 10만 명 대비
🔁 일관성 — 검색 색인이 항상 정확하게 유지
🛡️ 가용성 — 언제 접속해도 잘 동작
🔒 보안 — 안전하게 보호
왜 이 구분이 중요할까? 초보자는 보통 기능적 요구사항(무엇을 만들지)만 생각합니다. 하지만 서비스가 죽고 사는 건 대부분 비기능적 요구사항에서 갈립니다. "기능은 되는데 너무 느려서", "사람 몰리니까 터져서" 같은 문제가 전부 여기에 속하거든요.
🗺️

시스템을 이루는 구성요소 (전체 지도)

앞으로 이 가이드에서 하나씩 배울 부품들이, 실제 시스템에서 어떻게 이어져 있는지 전체 지도를 먼저 보여드릴게요. 지금은 이름만 눈에 익혀도 충분합니다.

비유 — 인터넷은 거대한 음식 배달 시스템
여러분(브라우저)이 앱으로 주문하면, 그 주문이 여러 단계를 거쳐 주방(서버)에 도착하고, 음식(데이터)이 다시 여러분에게 돌아옵니다. 아래 각 부품은 이 배달 과정의 담당자들이라고 생각하면 됩니다.
