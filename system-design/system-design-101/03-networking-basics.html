네트워킹 기초

시스템의 부품들은 결국 네트워크를 통해 대화합니다. 이 차시에서는 그 대화가 가능하게 해주는 최소한의 약속 — 컴퓨터의 주소인 IP와 포트, 이름을 주소로 바꿔주는 DNS, 그리고 데이터를 실어 나르는 두 가지 방식인 TCP와 UDP를 배웁니다. 마지막에는 주소창에 URL을 치는 순간 이 모든 게 어떤 순서로 일어나는지 한 줄로 꿰어봅니다.

IP / Port DNS TCP UDP Handshake
📮

IP 주소와 포트

인터넷에 연결된 컴퓨터끼리 데이터를 주고받으려면, 먼저 "어디로 보낼지"를 알아야 합니다. 그 주소가 IP 주소(IP address)이고, 같은 컴퓨터 안에서 "어느 프로그램한테 줄지"를 가리키는 번호가 포트(port)입니다.

비유 — 아파트 주소와 호수
택배를 보낼 때 "○○아파트 101동"까지만 쓰면 경비실에서 멈춥니다. "1502호"까지 써야 사람 손에 닿죠.
IP 주소 = 아파트 동 주소(어느 컴퓨터인가), 포트 = 호수(그 컴퓨터 안의 어느 프로그램인가)입니다. 컴퓨터 한 대에서 웹 서버·데이터베이스·캐시가 동시에 돌아가도 헷갈리지 않는 건 포트 번호가 다르기 때문이에요.

우리가 가장 많이 보는 IP 형식은 IPv4입니다. 142.250.x.x처럼 점으로 나뉜 숫자 네 덩어리로 되어 있고, 각 덩어리는 0부터 255까지의 값을 가집니다. 주소가 모자라서 더 긴 형식인 IPv6도 함께 쓰이지만, 지금은 "컴퓨터마다 붙는 번호"라는 것만 기억하면 충분합니다.

자주 보게 되는 포트 번호

포트 번호는 0부터 65535까지 있지만, 그중 몇 개는 "이 번호는 이 용도"라고 관례로 굳어져 있습니다. 개발하다 보면 아래 다섯 개는 거의 매일 마주칩니다.

브라우저 주소창에 https://youtube.com만 치는데도 잘 열리는 이유는, 포트를 안 쓰면 브라우저가 알아서 443을 붙여주기 때문입니다. 반대로 개발할 때 localhost:3000처럼 포트를 직접 쓰는 건, 3000번은 관례 포트가 아니라 우리가 정한 번호라서예요.
함정 — 공인 IP와 사설 IP는 다릅니다
공인 IP(public IP)는 인터넷 전체에서 유일한 주소로, 바깥에서 찾아올 수 있습니다. 반면 192.168.0.5 같은 사설 IP(private IP)는 집·회사 공유기 안에서만 통하는 내부 번호예요. 아파트로 치면 공인 IP는 도로명 주소, 사설 IP는 그 건물 안에서만 쓰는 내선 번호입니다. 그래서 내 노트북의 사설 IP를 친구에게 알려줘도 친구는 접속할 수 없습니다.

DNS: 인터넷 전화번호부

방금 컴퓨터끼리는 IP 주소로 통신한다고 했습니다. 그런데 우리는 IP를 외우고 다니지 않죠. 이 간극을 메워주는 게 DNS 조회인데, 초보자에게 가장 낯선 부분이라 따로 자세히 볼게요.

비유 — 스마트폰 연락처
전화를 걸 때 우리는 "010-1234-…" 번호를 외우지 않고 "엄마"라는 이름을 누릅니다. 연락처 앱이 이름을 실제 번호로 바꿔주니까요.
인터넷도 똑같습니다. 우리는 youtube.com이라는 이름을 치지만, 컴퓨터끼리는 IP 주소라는 숫자로 통신합니다. 이 이름 → 숫자 변환을 해주는 게 DNS(Domain Name System)예요.

DNS는 어떤 순서로 IP를 찾을까?

1
먼저 캐시(기억) 확인
"전에 이 사이트 가본 적 있나?" 브라우저가 캐시에 저장해 둔 IP가 있으면 바로 그걸 씁니다. 조회 과정을 통째로 건너뛰니 제일 빠르죠.
2
캐시에 없으면 DNS 서버에 물어봄
보통 ISP(인터넷 서비스 제공업체, 예: KT·SK)가 운영하는 DNS 리졸버에게 "youtube.com의 IP가 뭐야?"라고 요청합니다.
3
IP 주소를 받아서 접속
DNS 리졸버가 IP를 찾아 돌려주면, 브라우저는 그 IP로 실제 접속을 시작합니다. (이 결과도 다음을 위해 캐시에 저장!)

TCP vs UDP: 등기 vs 엽서

주소(IP·포트)를 알았으니 이제 데이터를 실어 보낼 차례입니다. 데이터를 어떻게 실어 나를지 정한 약속을 전송 프로토콜(transport protocol)이라고 하는데, 실무에서 만나는 건 사실상 두 가지 TCP와 UDP뿐입니다.

비유 — 등기우편과 엽서
TCP는 등기우편입니다. 보내기 전에 "받으실 수 있나요?"를 확인하고, 도착하면 수령 확인을 받고, 중간에 없어지면 다시 보냅니다. 확실하지만 절차가 많아 느리죠.
UDP는 엽서입니다. 우체통에 그냥 넣고 끝. 도착했는지 확인하지 않고, 없어져도 다시 보내지 않습니다. 대신 아주 빠릅니다.
📮 TCP — 확실하게
보내기 전에 연결부터 맺습니다.
도착 순서를 보장합니다.
빠진 조각은 다시 보냅니다.
받았다는 확인을 주고받습니다.

→ 확인 절차가 많아 조금 느립니다.
📨 UDP — 빠르게
연결을 맺지 않고 그냥 던집니다.
도착 순서가 뒤바뀔 수 있습니다.
빠진 조각은 그냥 잃어버립니다.
확인 절차가 아예 없습니다.

→ 군더더기가 없어 아주 빠릅니다.

TCP가 연결을 맺는 법 — 3-way 핸드셰이크

TCP는 데이터를 보내기 전에 "우리 이제 대화 시작합니다"라는 인사를 세 번 주고받습니다. 이걸 3-way 핸드셰이크(three-way handshake)라고 해요. 전화를 걸었을 때 서로 목소리가 들리는지 확인하는 과정과 똑같습니다.

1
SYN — 클라이언트 → 서버
"여보세요, 들리세요?" 클라이언트가 연결하고 싶다는 신호를 먼저 보냅니다.
2
SYN-ACK — 서버 → 클라이언트
"네 들려요. 그쪽도 제 말 들리세요?" 서버가 받았다는 확인과 함께 자기 쪽 연결 신호도 같이 보냅니다.
3
ACK — 클라이언트 → 서버
"저도 들려요." 이 확인이 끝나야 비로소 진짜 데이터가 오갑니다.
왜 이걸 알아야 할까? 핸드셰이크는 공짜가 아닙니다. 연결 한 번마다 오고 가는 시간이 들죠. 그래서 뒤에서 배울 여러 기술 — 연결을 재사용하거나, 아예 연결을 계속 열어두는 방식 — 이 전부 "이 인사를 줄이자"는 발상에서 나옵니다.

그래서 어디에 뭘 쓰나?

🌐
웹 · 이메일 → TCP
글자 하나만 빠져도 페이지가 깨집니다. 정확성이 속도보다 중요한 곳은 전부 TCP를 씁니다.
🎮
영상통화 · 게임 → UDP
화면 한 프레임을 다시 받느니 버리고 다음 프레임을 보는 게 낫습니다. 늦게 온 과거보다 지금이 중요하니까요.
📇
DNS 조회 → 주로 UDP
질문도 답도 짧아서 연결을 맺는 비용이 아깝습니다. 답이 안 오면 그냥 한 번 더 물어보면 되고요.
🚀

URL을 입력하면 벌어지는 일

주소창에 youtube.com을 치고 엔터를 누르면, 화면이 뜨기까지 눈에 안 보이는 여러 단계가 순식간에 일어납니다. 지금까지 배운 것들이 여기서 순서대로 등장하니, 하나씩 따라가 볼게요.

1
DNS 조회 — 도메인을 IP 주소로 변환
youtube.com이라는 이름을 컴퓨터가 알아듣는 IP 주소(예: 142.250.x.x)로 바꿉니다. (📇 DNS 섹션에서 본 그 과정입니다)
2
TCP 연결 — 3번의 인사
알아낸 IP의 443번 포트로 3-way 핸드셰이크를 해서 연결을 맺습니다. (📦 TCP vs UDP 섹션 참고)
3
HTTPS 암호화 인사
https라면 여기서 한 번 더 인사를 주고받아, 이후 대화를 남이 못 읽게 암호화할 열쇠를 나눠 갖습니다.
4
HTTP 요청 — 서버에 "페이지 주세요"
이제 열린 연결 위로 HTTP 요청을 보냅니다. "이 페이지 데이터를 달라"는 주문서예요.
5
서버 응답 — HTML·CSS·JS 도착
서버가 요청을 받아 웹페이지를 이루는 HTML·CSS·JavaScript 파일들을 돌려줍니다.
6
렌더링 — 받은 코드를 화면으로
브라우저가 받은 HTML 구조(DOM)를 바탕으로 실제 화면을 그립니다. (04차시 · 화면에 그려지는 과정에서 자세히)
