서버와 클라이언트

네트워크 양 끝에는 요청을 보내는 쪽과 응답을 돌려주는 쪽이 있습니다. 이 차시에서는 사용자와 가장 가까운 클라이언트·브라우저가 하는 일부터, 서버 한 대 안에서 요청이 처리되는 순서, 그리고 서버를 여러 대로 늘리기 위한 가장 중요한 조건인 무상태(stateless) 설계까지 이어서 봅니다.

Client Browser Rendering Request / Response Stateless
🖥️

클라이언트 vs 브라우저

시스템 디자인에서 브라우저(클라이언트)는 사용자에게 가장 많이 노출되는 부품입니다. 시스템의 가장 앞선(최전선)에서 사용자와 직접 대화하는 역할이죠. 그런데 '클라이언트'와 '브라우저'는 자주 섞어 쓰지만, 사실 다른 뜻입니다.

📱
클라이언트 (Client)
서버에 요청을 보내는 쪽을 통틀어 부르는 넓은 개념. 스마트폰·노트북 같은 기기일 수도, 앱 같은 프로그램일 수도 있습니다.
🌐
브라우저 (Browser)
클라이언트의 한 종류. 웹페이지를 불러와 화면에 보여주는 소프트웨어입니다. (크롬, 사파리, 엣지…)
핵심 관계 — 브라우저는 클라이언트에 "속한다"
즉 브라우저 ⊂ 클라이언트. 모든 브라우저는 클라이언트지만, 모든 클라이언트가 브라우저는 아닙니다. (예: 모바일 앱, 게임 클라이언트, curl 같은 명령어 도구도 전부 클라이언트예요.)
비유 — "손님"과 "웹 보러 온 손님"
가게에 오는 손님 전체가 클라이언트라면, 그중 "웹사이트를 보러 온 손님"이 브라우저입니다. 손님에는 전화 주문 손님(모바일 앱), 배달 손님(다른 프로그램)도 있으니까요.
🌐

브라우저가 하는 일

브라우저는 우리가 인터넷을 접속하는 창구입니다. 하는 일을 크게 3가지로 나눌 수 있어요.

🔎
1. 웹페이지 탐색
주소창에 입력한 곳으로 이동해 웹페이지(데이터)를 불러옵니다.
🎨
2. 화면에 표시 (렌더링)
불러온 HTML·CSS를 사람이 볼 수 있는 화면으로 그려줍니다.
👆
3. 상호작용 처리
클릭·입력 같은 사용자 동작을 받아 반응합니다.
정리하면 브라우저는 "불러오고 → 그리고 → 반응하는" 일을 합니다. 이 중 불러오는 과정은 03차시 · URL을 입력하면 벌어지는 일에서 이미 따라가 봤죠. 여기서는 그 다음, 받아온 코드를 화면으로 그리는 단계를 봅니다.
🎨

화면에 그려지는 과정 (렌더링)

서버가 돌려준 HTML은 사실 글자로 된 설계도일 뿐입니다. 브라우저는 이 설계도를 읽어 실제 화면으로 그려내는데, 이 과정을 렌더링(rendering)이라고 합니다.

1
HTML → DOM 트리
브라우저가 HTML을 읽어 DOM이라는 나무 모양의 구조로 바꿉니다. "제목 안에 글자, 그 아래 버튼…" 같은 구조·뼈대를 만드는 단계예요.
2
CSS → 스타일 입히기
CSS를 읽어 "이 글자는 빨간색, 이 버튼은 둥글게" 같은 디자인(옷)을 뼈대에 입힙니다.
3
화면에 그리기
구조 + 디자인을 합쳐 실제 픽셀로 화면에 그립니다. 드디어 우리 눈에 페이지가 보입니다.
4
JavaScript로 살아 움직이게
JS가 이벤트를 처리합니다. 버튼 클릭·폼 제출 같은 상호작용을 받아 화면을 바꾸거나 서버에 새 요청을 보내죠. JS는 이벤트 기반 언어라 "무슨 일이 일어나면 → 무엇을 한다"로 동작합니다.
비유 — 집을 완성하는 과정
HTML(뼈대·골조) → CSS(페인트·인테리어) → 화면 그리기(입주 완료) → JavaScript(전등 스위치·초인종처럼 눌렀을 때 반응하는 것들).

💡 브라우저 동작 원리, 왜 알아야 할까?

🏗️
웹 개발의 기본기
브라우저가 어떻게 페이지를 불러오고 그리는지 알아야, 그 위에서 제대로 된 웹을 만들 수 있습니다.
⚡
성능 최적화
캐싱과 렌더링 과정을 이해하면 페이지를 더 빠르게 만들 수 있습니다.
😊
더 좋은 사용자 경험
빠르고 매끄러운 화면은 곧 좋은 UX로 이어집니다.
여기까지가 사용자와 가장 가까운 부품 이야기였습니다. 이제 반대편으로 건너가서, 그 요청을 받아 응답을 만들어 주는 서버 쪽을 들여다봅니다.
🔁

요청-응답 사이클

클라이언트와 서버가 대화하는 방식은 놀랄 만큼 단순합니다. 클라이언트가 묻고, 서버가 답한다. 이 한 번의 주고받음을 요청-응답 사이클(request-response cycle)이라고 부르고, 웹에서 벌어지는 거의 모든 일이 이 사이클의 반복입니다.

비유 — 식당에서 주문하기
손님이 클라이언트, 주문서가 요청, 주방이 서버, 나온 요리가 응답입니다.
손님이 먼저 말을 걸지 않으면 주방은 아무것도 만들지 않습니다. 그리고 주방은 주문서에 적힌 것만 만들어 줍니다. 서버가 먼저 손님 자리로 찾아와 말을 거는 일도 없죠. 이 "손님이 먼저"라는 규칙이 웹의 기본 성격입니다.
🙍 클라이언트
— 요청 →
🖥️ 서버
← 응답 —
🙍 클라이언트
서버는 특별한 컴퓨터가 아닙니다. "서버"라고 하면 데이터센터에 꽂힌 시커먼 장비를 떠올리기 쉬운데, 시스템 디자인에서 말하는 서버는 요청을 기다리며 계속 켜져 있는 프로그램에 가깝습니다. 내 노트북에서 localhost:3000을 띄우면 그 노트북도 그 순간 서버예요. 하드웨어가 아니라 역할의 이름입니다.

서버 한 대 안에서는 무슨 일이 일어날까?

요청이 도착한 뒤 응답이 나가기까지, 서버 안에서는 보통 다음 순서로 일이 진행됩니다.

1
요청 받기
열어 둔 포트로 들어온 요청을 받습니다. "누가, 무엇을, 어떤 조건으로 달라고 했는지"를 읽는 단계예요.
2
로직 처리
우리가 짠 코드가 실행됩니다. 권한이 있는 사용자인지 확인하고, 값이 올바른지 검사하고, 무엇을 돌려줄지 결정합니다.
3
데이터베이스 조회
필요한 데이터를 창고에서 꺼내옵니다. 대개 이 단계가 가장 오래 걸려서, 뒤에서 배울 캐시가 여기에 붙습니다.
4
응답 만들기
꺼내온 데이터를 클라이언트가 알아들을 형태(HTML이나 JSON)로 포장합니다.
5
응답 보내기
포장한 결과를 왔던 연결로 돌려보냅니다. 여기서 한 사이클이 끝나고, 서버는 다시 다음 요청을 기다립니다.
🧳

상태 있는 서버 vs 없는 서버

앞의 사이클에서 서버는 요청 하나를 처리하고 끝냈습니다. 그런데 로그인처럼 "아까 그 사람"이라는 걸 기억해야 하는 기능도 있죠. 이 기억(상태, state)을 어디에 두느냐에 따라 서버는 두 종류로 갈립니다.

비유 — 동네 카페와 프랜차이즈
동네 단골 카페는 사장님이 내 취향을 기억합니다. "늘 마시던 걸로요"가 통하죠. 대신 그 사장님이 있어야만 통합니다. 옆 가게에 가면 처음부터 다시 설명해야 하고, 사장님이 쉬는 날엔 아무도 나를 모릅니다. → 상태 있는(stateful) 서버
프랜차이즈는 아무 지점에 가도 똑같은 서비스를 받습니다. 직원이 나를 기억해서가 아니라, 내가 멤버십 카드를 내밀기 때문이에요. 기억은 본사 시스템에 있고 지점은 그걸 조회할 뿐입니다. → 무상태(stateless) 서버
🏠 Stateful — 서버가 기억
로그인 정보를 그 서버의 메모리에 둡니다.
그래서 같은 서버로만 다시 가야 합니다.
그 서버가 죽으면 기억도 같이 사라집니다.

→ 서버를 늘리기가 까다롭습니다.
🧳 Stateless — 아무도 기억 안 함
로그인 정보를 공유 저장소에 둡니다.
어느 서버로 가도 똑같이 동작합니다.
서버가 죽어도 기억은 남아 있습니다.

→ 서버를 마음껏 늘릴 수 있습니다.

왜 무상태가 수평 확장의 전제 조건일까?

02차시에서 봤듯이 트래픽을 감당하는 제대로 된 방법은 수평 확장, 즉 같은 서버를 여러 대 두는 것이었습니다. 그런데 서버가 각자 자기 메모리에 로그인 정보를 들고 있으면 문제가 생깁니다. 1번 서버에서 로그인한 사용자가 다음 요청에서 2번 서버로 가면, 2번 서버는 그 사람을 모르니 다시 로그인하라고 하겠죠.

해결책은 기억을 서버 밖으로 빼는 것입니다. 세션 정보를 각 서버의 메모리가 아니라 Redis나 데이터베이스처럼 모두가 함께 보는 저장소에 두면, 어느 서버가 요청을 받든 거기서 꺼내 보면 됩니다. 서버는 아무것도 기억하지 않는 교체 가능한 부품이 되고, 그래서 몇 대든 늘리고 줄일 수 있습니다.

서버 한 대의 한계

서버 한 대로도 사용자 몇백 명은 무리 없이 받습니다. 문제는 그 다음이에요. 사용자가 늘면 서버는 세 군데 중 한 곳에서 먼저 막힙니다.

🔥
CPU
계산할 일이 밀립니다. 요청은 도착했는데 처리할 차례를 기다리느라 응답이 늦어집니다.
🧠
메모리
동시에 붙은 사용자 수만큼 메모리를 씁니다. 다 차면 프로그램이 그냥 죽습니다.
🚧
네트워크
주고받을 데이터가 회선 굵기를 넘어섭니다. 서버는 한가한데 길이 막혀 느린 상황이죠.

가장 먼저 떠오르는 해결책은 그 한 대를 더 좋은 장비로 바꾸는 수직 확장이지만, 02차시 · 수직 확장 vs 수평 확장에서 봤듯이 하드웨어에는 한계가 있고 결국 서버는 여전히 한 대라 그 한 대가 죽으면 전체가 멈춥니다.

그래서 다음 차시부터 서버 앞뒤에 부품을 하나씩 붙입니다 — 먼저 클라이언트와 서버가 쓰는 대화 규칙(HTTP)부터요.
