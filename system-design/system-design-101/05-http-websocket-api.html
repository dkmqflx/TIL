HTTP, WebSocket, API

앞 차시에서 클라이언트가 묻고 서버가 답한다는 걸 봤습니다. 그럼 그 "말"은 어떤 양식으로 오갈까요? 이 차시에서는 웹의 공통 대화 규칙인 HTTP를 뜯어보고, 메서드·상태 코드·헤더·쿠키를 익힌 뒤, 서버가 먼저 말을 걸어야 하는 실시간 통신과 API 스타일까지 이어서 봅니다.

HTTP Method Status Code Cookie WebSocket REST API
📨

HTTP: 웹의 대화 규칙

04차시에서 클라이언트가 요청을 보내면 서버가 응답을 돌려준다고 했습니다. 그런데 세상에는 수많은 브라우저와 수많은 서버가 있는데, 어떻게 처음 보는 사이인데도 말이 통할까요? 서로 같은 양식으로 적어 보내기로 약속했기 때문입니다. 그 약속이 HTTP(HyperText Transfer Protocol)예요.

비유 — 식당의 주문서 양식
처음 가는 식당에서도 주문이 되는 건, 주문서에 메뉴 이름 쓰는 칸과 수량 쓰는 칸이 어디에나 똑같이 있기 때문입니다. 손님이 양식을 아니까 어느 가게든 갈 수 있고, 가게도 양식을 아니까 어느 손님이든 받을 수 있죠.
HTTP는 웹 전체가 쓰는 이 주문서 양식입니다. 규격을 지키기만 하면 크롬이든 아이폰 앱이든 curl이든 같은 서버와 대화할 수 있어요.

요청과 응답은 어떻게 생겼을까

HTTP 메시지는 맨 윗줄 하나 + 메모 몇 줄 + 빈 줄 + 내용물이라는 네 부분으로 되어 있습니다. 실제로 사진 한 장을 달라고 하는 대화는 이렇게 생겼어요.

http
GET /photos/42 HTTP/1.1
Host: api.example.com

HTTP/1.1 200 OK
Content-Type: application/json

{ "id": 42, "title": "노을" }

위의 두 줄이 요청, 빈 줄 아래가 서버가 돌려준 응답입니다. 네 부분이 각각 무슨 역할인지 짝지어 보면 이렇습니다.

구성요청에서는응답에서는
시작줄무엇을 어디에 — GET /photos/42결과가 어땠나 — 200 OK
헤더부가 정보 메모 — Host:부가 정보 메모 — Content-Type:
빈 줄"메모 끝, 여기부터 내용물" 이라는 구분선
본문(body)보낼 데이터 (GET은 보통 비어 있음)돌려줄 데이터 (JSON, HTML, 이미지…)

HTTPS는 뭐가 다를까

지금 본 메시지는 그냥 글자입니다. 중간에 거쳐 가는 누군가가 들여다보면 아이디도 비밀번호도 그대로 읽힙니다. 그래서 요즘 웹은 거의 전부 HTTPS를 씁니다. 대화 내용은 똑같고, 그 대화를 봉투에 넣어 봉인해서 보내는 것만 다릅니다. 봉투를 뜯을 열쇠는 보낸 쪽과 받는 쪽만 가지고 있어서, 중간에 누가 가로채도 알아볼 수 없는 글자 덩어리만 보이죠.

HTTP가 딛고 선 두 가지 성질

첫째, HTTP는 "무슨 말을 어떤 양식으로"만 정합니다. 그 글자를 빠짐없이 순서대로 실어 나르는 일은 아래층의 TCP가 맡아요 — 03차시 · TCP vs UDP에서 본 그 TCP입니다. 둘째, HTTP는 요청 하나를 처리하면 깨끗이 잊습니다. 방금 온 사람인지 처음 온 사람인지 몰라요. 이 무상태(stateless) 성질이 왜 확장에 유리한지는 04차시 · 무상태 서버에서 봤죠.

양식을 알았으니 이제 칸을 채우는 법을 볼 차례입니다. "무엇을 해달라"를 적는 칸이 메서드, "어떻게 됐다"를 적는 칸이 상태 코드예요.

🔤

메서드와 상태 코드

요청 시작줄의 첫 단어가 메서드(method)입니다. 같은 /photos/42라는 주소라도 앞에 GET을 붙이면 "보여줘", DELETE를 붙이면 "지워줘"가 됩니다. 대상은 주소가, 동작은 메서드가 나타내는 구조예요.

비유 — 도서관에서 책 한 권을 다루는 다섯 가지 방법
책 자체는 하나인데 할 수 있는 일은 여러 가지입니다. 읽기(GET), 새 책을 꽂기(POST), 같은 자리에 다른 책으로 통째로 바꾸기(PUT), 책 속 오타 한 줄만 고치기(PATCH), 빼서 버리기(DELETE). 주소는 책장 위치, 메서드는 그 책에 무슨 짓을 할지입니다.
메서드하는 일예시멱등?
GET읽기 — 가져오기만 하고 바꾸지 않음GET /photos/42✅ 예
POST만들기 — 새 자원을 추가POST /photos❌ 아니오
PUT통째로 바꾸기 — 보낸 내용으로 전체 교체PUT /photos/42✅ 예
PATCH일부만 바꾸기 — 지정한 필드만 수정PATCH /photos/42❌ 보통 아니오
DELETE삭제 — 자원을 없앰DELETE /photos/42✅ 예
멱등(idempotent)이 뭐길래?
같은 요청을 몇 번 보내든 결과 상태가 같으면 멱등입니다. 엘리베이터 버튼을 다섯 번 눌러도 엘리베이터는 한 번만 오는 것과 같아요. 네트워크가 끊겨 응답을 못 받았을 때 다시 보내도 안전한지를 판단하는 기준이라 중요합니다.
DELETE를 두 번 보내면 두 번째는 "없는데요"라고 답하겠지만 지워진 상태는 그대로죠. 반면 POST는 다시 보내면 사진이 두 장 올라갑니다. 결제 버튼을 두 번 누르면 두 번 결제되는 게 딱 이 이야기예요.

상태 코드 — 서버의 세 자리 대답

응답 시작줄의 200 OK 같은 숫자가 상태 코드(status code)입니다. 세 자리인데, 사실 첫 자리만 봐도 절반은 안 것입니다.

✅
2xx · 성공
달라는 대로 잘 됐습니다. 가장 보고 싶은 번호대죠.
🔀
3xx · 이동 / 그대로
"거기 말고 저기로 가세요" 또는 "안 바뀌었으니 갖고 있던 걸 쓰세요".
🙅
4xx · 네 잘못
요청이 잘못됐습니다. 클라이언트가 고쳐야 풀립니다.
🔥
5xx · 내 잘못
요청은 멀쩡한데 서버가 처리하다 실패했습니다.
📌
자주 보는 열두 개
200 잘 됐다 · 201 새로 만들었다 · 301 영구 이동 · 302 임시 이동 · 304 안 바뀜(갖고 있던 거 쓰세요) · 400 요청이 이상함 · 401 로그인 안 됨 · 403 권한 없음 · 404 그런 주소 없음 · 429 너무 자주 부름 · 500 서버가 터짐 · 503 지금은 못 받음
헷갈리기 쉬운 두 쌍
401 vs 403 — 401은 "당신이 누군지 모르겠어요(로그인부터)", 403은 "누군지는 알겠는데 그건 못 봐요"입니다.
301 vs 302 — 301은 영구 이동이라 브라우저와 검색엔진이 새 주소를 기억해 버리고, 302는 임시라 매번 원래 주소로 다시 물어봅니다. 이 차이는 13차시 · URL Shortener에서 "단축 URL을 301로 보낼까 302로 보낼까"를 고를 때 결정적인 문제가 됩니다. 지금은 301은 기억되고 302는 안 된다만 기억해 두세요.
🍪

헤더와 쿠키

시작줄이 "무엇을"이라면, 헤더(header)는 "어떤 조건으로"를 적는 자리입니다. 본문에 담긴 내용 자체는 아니고, 그 내용을 어떻게 다뤄야 하는지 알려주는 메모예요.

비유 — 택배 상자 겉면의 메모
상자 안의 물건이 본문이라면, 겉면에 붙은 "깨지기 쉬움", "냉동 보관", "받는 사람 확인 필수" 스티커가 헤더입니다. 물건과는 별개지만, 이 메모가 없으면 받는 쪽이 어떻게 다뤄야 할지 몰라요.
헤더붙는 곳무슨 메모인가
Content-Type요청·응답본문이 무슨 형식인지. application/json이면 "JSON으로 읽으세요".
Authorization요청"저 이런 사람입니다" — 토큰 같은 신분증을 담아 보냅니다.
Cache-Control응답(요청도 가능)이 응답을 얼마나 오래 보관해도 되는지. 06차시 · 캐싱의 주인공입니다.
Set-Cookie응답"이 쪽지 갖고 있다가 다음에 올 때 보여주세요."

무상태인 HTTP에서 나를 기억시키는 법

HTTP는 요청 하나를 처리하고 나면 잊는다고 했죠. 그런데 로그인은 계속 기억돼야 합니다. 이 모순을 푸는 아주 단순한 방법이 쿠키(cookie)예요. 서버가 기억하는 대신, 기억할 쪽지를 손님에게 맡깁니다.

1
로그인 요청
아이디와 비밀번호를 담아 POST /login을 보냅니다. 서버는 맞는지 확인하죠.
2
서버가 쪽지를 쥐어 줌
응답에 Set-Cookie: session_id=a1b2c3을 붙여 보냅니다. "당신은 a1b2c3번 손님이에요"라는 번호표입니다.
3
브라우저가 자동 보관
브라우저가 그 쪽지를 저장합니다. 개발자가 코드를 짜지 않아도 알아서 합니다.
4
다음 요청부터 자동 첨부
같은 사이트로 가는 모든 요청에 Cookie: session_id=a1b2c3이 저절로 붙습니다. 서버는 번호표를 보고 "아, 그 손님"이라고 알아봅니다.

여기서 자연스럽게 다음 질문이 나옵니다 — "a1b2c3번 손님이 누구인지"라는 명단은 어디에 두지? 서버 한 대의 메모리에 두면 그 서버로만 가야 하고, 공유 저장소에 두면 아무 서버로 가도 됩니다. 이 갈림길이 바로 04차시 · 상태 있는 서버 vs 없는 서버에서 본 이야기예요.

편한 만큼 조심할 것
쿠키의 장점인 "자동으로 붙는다"는 그대로 약점이기도 합니다. 남이 만든 페이지가 우리 서버로 요청을 보내게 유도해도 쿠키는 따라갑니다. 그래서 실무에서는 HttpOnly(자바스크립트가 못 읽게), Secure(HTTPS에서만), SameSite(다른 사이트에서 온 요청엔 안 붙임) 같은 옵션을 함께 걸어 둡니다. 지금은 "쿠키는 자동이라 편하고, 자동이라 위험하다"만 챙겨 가면 충분합니다.
⚡

실시간 통신: 폴링 → 롱폴링 → SSE → WebSocket

지금까지 본 HTTP에는 큰 제약이 하나 있습니다. 언제나 클라이언트가 먼저 물어야 한다는 것. 서버는 먼저 말을 걸 수 없습니다. 그런데 채팅 메시지나 주식 시세는 서버 쪽에서 먼저 생기는 일이죠. 이 어긋남을 메우려고 사람들이 방법을 하나씩 발전시켜 왔습니다.

비유 — 택배가 왔는지 확인하는 네 가지 방법
① 1분마다 문을 열어 본다 → 폴링. 대부분 헛걸음이고 다리만 아픕니다.
② 경비실에 가서 "오면 알려주세요" 하고 기다린다 → 롱폴링. 헛걸음은 없지만 그동안 경비실 앞에 서 있어야 하죠.
③ 단지 방송으로 "○○호 택배 도착" 안내를 듣는다 → SSE. 듣기만 하면 되고, 대신 방송으로 대답은 못 합니다.
④ 경비실과 인터폰을 상시 연결해 둔다 → WebSocket. 양쪽 다 아무 때나 말을 걸 수 있습니다.
1
폴링(polling) — 계속 물어보기
클라이언트가 몇 초마다 "새 거 있어요?" 요청을 반복합니다. 서버는 있으면 주고 없으면 빈손으로 답하죠.
문제 — 열 번 물어 아홉 번이 헛수고입니다. 요청 수는 많고, 새 메시지는 다음 물어볼 때까지 늦게 도착합니다.
2
롱폴링(long polling) — 답을 붙잡아 두기
요청을 받은 서버가 바로 답하지 않고 새 데이터가 생길 때까지 응답을 들고 있습니다. 생기는 순간 답하고, 클라이언트는 받자마자 다시 요청을 겁니다.
해결 — 헛수고와 지연이 줄었습니다. 남은 문제 — 연결을 오래 붙잡고 있어야 해서 동시 접속이 많아지면 서버가 버겁고, 매번 응답을 받을 때마다 요청을 새로 만듭니다.
3
SSE(Server-Sent Events) — 서버가 계속 흘려보내기
연결을 한 번 열어 두면 서버가 그 통로로 계속 데이터를 밀어 넣습니다. HTTP 위에서 그대로 동작하고 브라우저가 끊기면 알아서 다시 붙습니다.
해결 — 매번 요청을 새로 만들 필요가 없습니다. 남은 문제 — 서버 → 클라이언트 한 방향뿐이라 반대로 보낼 땐 따로 요청을 보내야 합니다.
4
WebSocket — 아예 상시 연결
연결 하나를 열어 두고 양쪽 모두 아무 때나 말을 겁니다. 매번 헤더를 새로 붙이지 않아서 주고받는 양도 가볍습니다.
해결 — 진짜 양방향 실시간. 대신 연결을 계속 유지해야 하고, 서버 쪽 설계가 그만큼 복잡해집니다.
폴링롱폴링SSEWebSocket
연결 방식짧은 요청 반복답을 붙잡은 요청 반복연결 하나 열어 둠연결 하나 열어 둠
방향클라이언트가 요청클라이언트가 요청서버 → 클라이언트양방향
서버 부담요청 수가 많음대기 연결이 쌓임연결 유지연결 유지 + 상태 관리
어울리는 곳가끔 바뀌는 값WebSocket이 막힌 환경알림·주식 시세·진행률채팅·협업 편집·게임

WebSocket은 HTTP로 시작해서 갈아탄다

WebSocket이 HTTP와 전혀 다른 세계처럼 보이지만, 시작은 평범한 HTTP 요청입니다. 클라이언트가 Upgrade: websocket이라는 헤더를 붙여 "이 연결, 프로토콜을 바꿔서 계속 쓸까요?"라고 묻고, 서버가 101 Switching Protocols로 답하면 그때부터 같은 연결 위에서 WebSocket으로 대화합니다. 지하철 타고 가다 환승역에서 갈아타는 셈이죠 — 길은 그대로인데 타고 있는 것만 바뀝니다.

함정 — "실시간이니까 WebSocket"은 성급합니다
WebSocket은 연결을 계속 붙들고 있습니다. 동시 접속 10만이면 연결 10만 개를 유지해야 하고, 서버를 늘릴 때 "이 사용자의 연결이 어느 서버에 붙어 있는지"까지 신경 써야 합니다. 알림처럼 한 방향으로 흘려보내기만 하면 되는 일은 SSE로 충분하고, 몇 분에 한 번 바뀌는 값이라면 그냥 폴링이 제일 단순합니다. 필요한 만큼만 무거운 방식을 고르세요.
🧩

REST vs GraphQL vs gRPC

API(Application Programming Interface)는 프로그램끼리 대화하기 위해 정해 둔 창구입니다. 서버가 "이 주소로 이렇게 물으면 이런 걸 돌려주겠다"고 공개해 둔 규격이죠. 그 창구를 어떤 스타일로 만들지에는 몇 가지 유행이 있는데, 대표 셋만 알면 됩니다.

비유 — 콘센트 규격
전자제품 회사와 발전소가 서로를 몰라도 플러그를 꽂으면 전기가 들어옵니다. 모양과 전압을 미리 약속해 뒀기 때문이죠. API가 딱 그 콘센트입니다. 안쪽에서 서버가 뭘 어떻게 하든, 창구 모양만 지키면 어느 앱이든 꽂아 쓸 수 있어요.
🗂️
REST
자원(URL) + 메서드로 표현하는 방식. GET /users/42처럼 앞서 배운 HTTP를 그대로 씁니다. 압도적으로 가장 흔하고, 처음 배우기에 가장 쉽습니다.
🎯
GraphQL
창구는 하나만 두고, 클라이언트가 필요한 필드를 직접 적어 요청합니다. 화면 하나에 필요한 데이터를 한 번에 받을 수 있어 프론트엔드가 주도권을 갖습니다.
⚙️
gRPC
사람이 읽는 글자 대신 바이너리로 주고받아 빠르고 가볍습니다. 브라우저에서 바로 쓰긴 까다로워서 주로 서버끼리 대화할 때 씁니다.
RESTGraphQLgRPC
주고받는 형식JSON (사람이 읽음)JSON (쿼리로 요청)바이너리 (Protocol Buffers)
장점단순하고 자료가 많음, HTTP 캐싱이 그대로 통함필요한 것만 받음, 화면 하나에 요청 한 번빠르고 가벼움, 규격이 코드로 강제됨
단점안 쓸 필드까지 오거나, 여러 번 호출해야 함캐싱이 까다롭고 서버 구현이 복잡함브라우저에서 직접 쓰기 어렵고 눈으로 못 읽음
어울리는 곳대부분의 웹·모바일 API화면마다 필요한 데이터가 제각각인 앱마이크로서비스 사이의 내부 통신
지금 해야 할 일은 하나뿐입니다 — REST부터.
셋 중 무엇이 우월한 게 아니라 불편한 지점이 서로 다른 것뿐입니다. REST를 충분히 써 보면 "요청이 너무 많아지네", "이 통신은 너무 느리네" 같은 불편이 먼저 느껴지는데, GraphQL과 gRPC는 그때 꺼내 보는 대안입니다. 지금은 "이럴 때 다른 선택지가 있다"는 것만 알아 두면 충분해요.
✍️

좋은 API 설계 습관

API는 한 번 공개하면 남의 코드가 거기에 기대게 됩니다. 그래서 처음에 규칙을 잡아 두는 값이 아주 큽니다. 화려한 기술이 아니라 이름 짓는 습관에 가까운 이야기예요. 대원칙은 딱 한 줄입니다 — 주소는 명사, 동작은 메서드. 주소에 동사를 넣기 시작하면 /getUser, /fetchUser, /loadUser가 제각각 생겨나 아무도 외우지 못하거든요.

🙅 이렇게 하지 마세요
GET /getUserPhotos?id=42
POST /deletePhoto?id=7
GET /photo_list_all
POST /updateUserName
🙆 이렇게 하세요
GET /users/42/photos
DELETE /photos/7
GET /photos?page=1
PATCH /users/42

챙겨 두면 좋은 여섯 가지

  • 자원은 명사, 그리고 복수형으로 — /users/42/photos. "42번 사용자의 사진들"이 주소만 봐도 읽힙니다.
  • 동작은 메서드로 — 지우기는 DELETE, 일부 수정은 PATCH. 주소에 delete를 쓰지 않습니다.
  • 목록은 반드시 잘라서 준다(페이지네이션) — ?page=2&size=20 같은 방식이 쉽고, 데이터가 계속 추가되는 목록이라면 "마지막으로 본 지점"을 넘기는 커서 방식이 흔들림 없이 안전합니다. 전부 다 돌려주는 API는 언젠가 반드시 터집니다.
  • 주소에 버전을 박아 둔다 — /v1/users. 나중에 규격을 바꿔야 할 때, 옛날 앱을 쓰는 사용자를 버리지 않고 /v2를 새로 열 수 있습니다.
  • 에러 응답 형식을 하나로 통일한다 — 상태 코드는 상황에 맞게 주고, 본문은 언제나 같은 모양(code, message)으로. 실패할 때마다 다른 모양이 오면 쓰는 쪽이 매번 새로 대응해야 합니다.
  • 너무 많이 부르면 막는다 — 잘 만든 API일수록 남용됩니다. 일정 횟수를 넘기면 429로 돌려보내야 하는데, "1분에 몇 번까지"를 어떻게 세고 서버가 여러 대일 때 그 숫자를 어디서 공유할지가 전부 설계 문제라 아예 한 차시를 씁니다 — 12차시 · Rate Limiter.
여기까지가 클라이언트와 서버가 어떻게 대화하는가였습니다. 그런데 아무리 대화를 잘 정리해도, 매번 서버까지 갔다 오는 것 자체가 느립니다. 다음 차시에서는 갔다 오는 횟수를 줄이는 방법 — 캐싱과 CDN을 봅니다.
