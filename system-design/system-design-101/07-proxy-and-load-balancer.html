프록시와 로드 밸런서

클라이언트와 서버 사이에는 중계자가 서 있습니다. 누구 편에 서서 누구를 감추느냐에 따라 Forward Proxy와 Reverse Proxy로 나뉘고, Reverse Proxy의 핵심 기능인 로드 밸런싱은 서버를 여러 대로 늘릴 때 반드시 필요한 교통정리입니다. 이 차시에서 그 둘을 한 번에 정리합니다.

Proxy Reverse Proxy Load Balancer Health Check SPOF
🔀

프록시(Proxy)란?

프록시는 시스템 디자인, 특히 네트워크 계층에서 자주 등장하는 용어입니다. 한마디로 "중간에서 통신을 대신 중계해 주는 대리인"이에요. 클라이언트와 서버 사이, 혹은 서버와 서버 사이에 서서 대화를 중계하고 통제합니다.

비유 — 심부름 대리인
내가 직접 가게에 가는 대신 심부름꾼을 보낸다고 해봅시다. 가게 주인은 심부름꾼만 볼 뿐, 진짜 나(원래 요청자)가 누군지 모릅니다. 게다가 심부름꾼은 "이 가게는 가지 마세요", "이건 지난번에 사둔 거니 그냥 드릴게요(캐싱)" 같은 통제·최적화도 할 수 있어요.

프록시의 핵심은 "두 대상의 직접 연결을 감추고, 중간에서 제어한다"는 점입니다. 대표적인 종류가 두 가지 있는데, 누구 편에 서서 누구를 감추느냐가 다릅니다.

➡️
Forward Proxy
클라이언트 편에 서서 클라이언트를 감춰줍니다.
⬅️
Reverse Proxy
서버 편에 서서 서버를 감춰줍니다.
➡️

Forward Proxy — 클라이언트 편

Forward Proxy는 클라이언트 쪽에 서서, 클라이언트를 대신해 서버에 요청을 보냅니다. 그래서 서버 입장에서는 프록시의 IP만 보이고, 진짜 클라이언트가 누군지 알 수 없습니다.

비유 — 회사 정문의 경비실
직원이 외부로 나갈 때 반드시 정문 경비실을 거칩니다. 경비실은 "이 사이트는 가지 마세요"라고 막기도 하고, 누가 언제 나갔는지 기록도 합니다. 바깥에서 보면 전부 '회사 정문'에서 나온 것처럼 보이죠. Forward Proxy가 바로 이 경비실입니다.

Forward Proxy가 하는 일

🕶️
익명성 (IP 숨김)
서버는 프록시 IP만 봅니다. 진짜 클라이언트 IP는 가려집니다.
🚧
접근 제어 / 필터링
특정 사이트·IP 차단, 특정 시간대만 허용, 유해·비업무 사이트 차단 등을 설정할 수 있습니다.
⚡
캐싱
자주 요청되는 응답을 프록시에 저장해 두고 재사용 → 응답 지연(딜레이)을 줄입니다.
📝
모니터링 / 로깅
누가 어떤 사이트에 얼마나 접속했는지 기록이 쌓입니다. 트래픽을 감시할 수 있죠.
어디서 쓰나? 학교·기업·공공기관처럼 클라이언트(내부 사용자)를 보호·통제해야 할 때 씁니다. 한마디로 Forward Proxy는 "클라이언트의 방패막"이에요.
⬅️

Reverse Proxy — 서버 편

Reverse Proxy는 Forward Proxy와 정반대입니다. 이번엔 서버 쪽에 서서 서버들을 보호합니다. 클라이언트는 서버에 직접 접근하지 못하고, 반드시 프록시를 거쳐야 합니다. 그래서 진짜 서버의 IP가 클라이언트에게 감춰집니다.

비유 — 건물 1층 안내데스크
방문객은 무조건 안내데스크를 먼저 상대합니다. 실제 직원들이 몇 층 어느 자리에 있는지 방문객은 몰라요. 안내데스크가 "김 대리는 지금 바쁘니 이 대리에게 안내(분산)", "출입증 없는 사람은 차단(보안)"을 해줍니다. 이게 Reverse Proxy예요.

Reverse Proxy가 하는 일

🛡️
서버 IP 보호
클라이언트는 프록시 IP만 압니다. 진짜 서버 주소가 숨겨져 보안이 강해집니다.
🚫
DDoS 공격 방어
서버가 프록시 뒤에 숨어 있어, 서버를 직접 노리는 대규모 공격을 어렵게 만듭니다.
⚖️
로드 밸런싱
한 서버에 몰릴 트래픽을 여러 서버로 나눠줍니다. (대표 도구: Nginx) → 이 차시 뒷부분에서 자세히!
⚡
캐싱
자주 요청되는 콘텐츠를 저장해 두고 재사용 → 네트워크 요청↓, 응답 시간↓.
한마디로 Reverse Proxy는 "서버의 방패막"입니다. 우리가 자주 듣는 Nginx가 대표적인 Reverse Proxy이자 로드 밸런서예요.
⚖️

로드 밸런서(Load Balancer)란?

서버 한 대의 한계를 넘기 위해 여러 대를 두면(수평 확장, 02차시), 곧바로 질문이 하나 생깁니다. 누가 요청을 나눠 줄까?

로드 밸런서는 여러 서버 앞단에 서서, 들어오는 요청을 각 서버에 고르게 분산시켜 주는 장치입니다. 한 서버에 트래픽이 몰리지 않도록 미리 받아서 골고루 뿌려주죠.

비유 — 마트 계산대 안내 직원
계산대가 여러 개인데 손님이 한 줄로만 몰리면 비효율적이죠. 그래서 안내 직원이 "손님, 3번 계산대가 비었어요!"라며 골고루 보내줍니다. 로드 밸런서가 바로 이 안내 직원이고, 계산대가 서버입니다.

로드 밸런서가 존재하는 이유

⚡
성능 향상
부하를 여러 서버로 나눠 각 서버가 여유 있게 일하니 전체가 빨라집니다.
🛡️
고가용성 (High Availability)
서버 한 대가 죽어도 나머지가 처리하니 서비스가 멈추지 않습니다.
한 줄 정리: 로드 밸런서의 존재 이유 = 성능 + 고가용성. 가장 핵심 역할은 요청을 고르게 분산하는 것입니다.
🧮

분산 알고리즘 4가지

"고르게 분산한다"고 했지만, 어떤 기준으로 나눌지는 여러 방법이 있습니다. 대표적인 4가지를 비유와 함께 봅시다.

1️⃣ 라운드 로빈 (Round Robin) — 순서대로

서버 성능은 따지지 않고 1 → 2 → 3 → 다시 1 → 2 → 3… 순서대로 돌아가며 요청을 분배합니다. 가장 간단하고 균형 잡힌 방법이에요.

비유 — 카드 딜러가 순서대로 한 장씩 나눠주듯. 단점: 서버마다 성능이 다른데도 똑같이 나눠줘서, 성능 좋은 서버의 여유를 낭비할 수 있습니다.

2️⃣ 가중 라운드 로빈 (Weighted Round Robin) — 성능만큼 더

라운드 로빈의 단점을 보완합니다. 각 서버에 가중치(weight)를 매겨, 성능 좋은 서버에 더 많은 요청을 보냅니다.

비유 — 힘센 사람에게 짐을 더 많이 맡기듯. 예를 들어 서버 A가 B·C보다 2배 빠르면, A에 2번 갈 동안 B·C엔 각 1번씩 보냅니다.

3️⃣ 최소 연결 (Least Connection) — 가장 한가한 곳으로

지금 연결(처리 중인 작업)이 가장 적은 서버에 요청을 보냅니다. 각 서버의 현재 상태를 실시간으로 살펴 부하가 적은 곳으로 보내죠.

비유 — 마트에서 줄이 가장 짧은 계산대로 가듯. 서버 1이 과부하로 느려지면, 완화될 때까지 서버 2·3 위주로 보냅니다.

4️⃣ IP 해시 (IP Hash) — 단골은 늘 같은 서버로

클라이언트의 IP 주소를 기준으로, 같은 IP는 항상 같은 서버로 보냅니다. 특정 사용자를 계속 같은 서버에 붙여둬야 할 때(연결 지속) 유용합니다. 다만 세션을 서버에 두지 않는 무상태 설계라면 이런 고정 자체가 필요 없어집니다.

비유 — 단골 손님은 항상 같은 담당 직원에게 안내하듯. 로그인 세션처럼 "같은 사용자는 같은 서버가 기억하고 있어야" 할 때 씁니다.
알고리즘기준비유특징
라운드 로빈순서대로카드 딜러간단하지만 서버 성능 차이 무시
가중 라운드 로빈성능(가중치)힘센 사람에 짐 더성능 좋은 서버에 더 많이
최소 연결현재 부하줄 짧은 계산대실시간 상태 기반, 부하 적은 곳
IP 해시클라이언트 IP단골 = 같은 직원같은 사용자를 같은 서버로 고정

한 걸음 더: 헬스 체크 & L4/L7

🩺 헬스 체크 (Health Check)

로드 밸런서는 죽은 서버에 요청을 보내면 안 됩니다. 그래서 각 서버에 주기적으로 "너 살아있니?"라고 신호를 보내 상태를 확인하는데, 이걸 헬스 체크라고 합니다. 응답이 없는 서버는 목록에서 잠시 빼두고, 살아있는 서버에만 요청을 보냅니다.

비유 — 안내 직원이 "3번 계산대 직원 자리 비었네?"를 미리 확인하고, 손님을 그리 안 보내는 것과 같습니다.

🔀 L4 vs L7 로드 밸런싱

로드 밸런서는 무엇을 보고 판단하느냐에 따라 두 종류로 나뉩니다. 지금은 "이런 게 있구나" 정도만 알아두면 됩니다.

L4 — 빠른 분류
IP 주소·포트만 보고 분산합니다. 편지 겉봉투(받는 주소)만 보고 나눠주는 우체국처럼요.

→ 내용을 안 보니 빠릅니다.
L7 — 똑똑한 분류
URL·쿠키 등 내용까지 보고 분산합니다. 편지 내용을 읽고 "이건 민원팀, 저건 배송팀"으로 나눠주듯.

→ 더 똑똑하지만 조금 더 무겁습니다.
🛡️

단일 장애점과 다중 LB

로드 밸런서 덕분에 서버 한 대가 죽어도 안전해졌습니다. 그런데 여기서 아주 중요한 질문 하나. "그럼 로드 밸런서 자체가 죽으면?"

로드 밸런서가 다운되면 모든 트래픽이 중단됩니다. 서버들이 멀쩡해도 요청을 나눠줄 장치가 없으니 서비스 전체가 멈추죠. 이렇게 "한 곳이 죽으면 전체가 멈추는 지점"을 단일 장애점(SPOF, Single Point of Failure)이라고 합니다.

해결책은? 서버를 여러 대 뒀던 것처럼, 로드 밸런서도 여러 대 두면 됩니다. 첫 번째 LB가 죽으면 두 번째 LB로 트래픽을 넘기는 거죠. 구성 방식은 크게 두 가지입니다.

🟢🟢 Active-Active
LB A와 B가 동시에 작동합니다. 둘 다 일하다가 하나가 죽으면 나머지가 그 몫까지 처리합니다.

→ 평소에도 둘 다 활용 (효율적)
🟢⚪ Active-Passive
LB A만 작동하고 B는 대기(standby) 상태로 쉽니다. A에 문제가 생기면 그때 B가 활성화되어 넘겨받습니다.

→ 평소엔 B가 놀지만 구성이 단순 (예비군)
비유 — Active-Active는 계산대 안내 직원 2명이 늘 함께 근무, Active-Passive는 1명이 근무하고 1명은 대기실에서 대기하다 무슨 일이 생기면 투입.
이 차시 정리
프록시는 중계자이고, 그중 서버 편에 서는 리버스 프록시의 핵심 기능이 로드 밸런싱이었습니다. 로드 밸런서는 시스템의 성능 · 확장성 · 고가용성을 극대화하는 핵심 부품으로, 라운드 로빈·IP 해시 등 다양한 알고리즘으로 상황에 맞게 트래픽을 분산하고, LB를 여러 대로 구성해 단일 장애점까지 없앨 수 있습니다.

여기까지가 요청이 서버에 닿기까지의 이야기입니다. 다음 차시부터는 서버 뒤편 — 데이터가 실제로 쌓이는 스토리지로 들어갑니다.
