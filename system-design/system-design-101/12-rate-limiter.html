Rate Limiter 설계

두 번째 사례는 처리율 제한 장치(rate limiter)입니다. 하는 일을 한 줄로 적으면 "정해진 시간 안에 몇 번까지만 통과시킨다"가 전부라, 혼자 쓰는 프로그램이라면 변수 하나로 끝나는 문제예요. 그런데 이 세는 일이 초당 수천 번 일어나고, 세는 주체가 서버 열 대로 흩어지는 순간 갑자기 어려워집니다. 어떤 방식으로 셀 것인지(알고리즘 다섯 가지), 그 숫자를 어디에 둘 것인지(Redis), 여러 대가 같은 숫자를 볼 때 무엇이 깨지는지(경쟁 조건과 동기화), 그리고 막을 때 사용자에게 무엇을 돌려줄 것인지(429와 헤더)를 차례로 풉니다.

1단계 · 문제 이해와 요구사항

면접관이 말합니다. "처리율 제한 장치를 설계해 보세요." 이번에도 첫 일은 그리기가 아니라 좁히기입니다 — 10차시의 4단계 절차에서 5분을 여기에 쓰기로 했으니까요. 다만 이 문제에는 11차시에 없던 함정이 하나 있습니다. 무엇을 기준으로 셀 것인가를 정하지 않으면 뒤의 설계가 통째로 달라져요. IP 기준과 사용자 기준은 완전히 다른 시스템이 됩니다.

비유 — 놀이공원 놀이기구 탑승 제한
인기 많은 롤러코스터 앞에 직원이 서 있습니다. 이 직원이 하는 일은 딱 하나예요. 한 회차에 24명까지만 태우고, 25번째 손님부터는 다음 회차로 돌려보내는 것.
이 규칙이 없으면 어떻게 될까요? 사람들이 계속 밀고 들어와 기구 자체가 고장 나고(과부하), 자유이용권으로 같은 사람이 스무 번 연속 탈 수도 있고(독점), 결국 다른 손님은 하루 종일 한 번도 못 탑니다(공정성 붕괴).
중요한 건 이 직원이 모든 손님을 한 명도 빠짐없이 거친다는 점입니다. 그러니 직원이 손님 한 명 세는 데 5초씩 걸리면, 그 5초가 모든 손님의 대기 시간에 그대로 더해집니다. 처리율 제한 장치가 무엇보다 빨라야 하는 이유가 여기 있어요.

왜 필요한가

설계에 들어가기 전에 이 장치를 왜 다는지부터 분명히 해 둡시다. 이유가 셋인데, 셋이 각각 다른 요구사항을 만들어 냅니다.

🛡️
공격 막기
한 곳에서 초당 수만 건을 쏟아부어 서버를 마비시키는 서비스 거부 공격(DoS)을 앞단에서 끊습니다. 로그인 API를 무한히 두드려 비밀번호를 맞춰 보는 시도도 같은 방법으로 막혀요.
💰
비용 지키기
요청 한 건이 돈인 경우가 많습니다. 외부 API 호출료, 서버 사용료, 문자 발송비처럼요. 한도가 없으면 버그 하나가 밤새 돌면서 요금 고지서를 만들어 냅니다.
⚖️
공정하게 나누기
서버 자원은 한정돼 있습니다. 한 사용자가 전체 처리량의 90%를 가져가면 나머지 모두가 느려져요. 한도는 자원을 골고루 나누는 규칙이기도 합니다.

기능 요구사항

이 문제의 기능은 놀랄 만큼 짧습니다. 대신 "무엇을 기준으로"가 기능 안에 들어간다는 점을 놓치지 마세요.

🚦
규칙을 넘으면 막는다
예를 들어 "IP 하나당 분당 100회". 101번째 요청부터는 서버까지 가지 못하고 여기서 끊깁니다. 이게 이 시스템의 전부예요.
🎯
기준을 고를 수 있다
IP · 사용자 ID · API 엔드포인트 중 무엇을 기준으로 셀지 규칙마다 정합니다. 로그인 전에는 IP 말고 쓸 게 없고, 로그인 후에는 사용자 ID가 훨씬 정확합니다.
🎛️
규칙은 배포 없이 바꾼다
"분당 100회"를 200회로 올리는 데 서버 재배포가 필요하면 장애 대응이 늦어집니다. 규칙은 코드가 아니라 설정이어야 해요.
📣
막았다는 사실을 알린다
그냥 연결을 끊어 버리면 클라이언트는 서버가 죽은 줄 알고 더 세게 재시도합니다. 왜 막혔고 언제 다시 오면 되는지를 알려 줘야 해요.

비기능 요구사항 — 여기가 진짜 문제

02차시의 기능/비기능 구분이 이번에도 그대로 쓰입니다. 그리고 이번 문제의 어려움은 전부 아래 넷에 있어요. 특히 첫 줄은 이 시스템의 성격 자체를 규정합니다.

⚡
아주 낮은 지연
모든 요청이 이 장치를 거칩니다. 여기서 10ms를 쓰면 서비스의 모든 API가 10ms씩 느려져요. 목표는 요청당 1ms 이내입니다.
🪶
적은 메모리
사용자 한 명당 상태를 들고 있어야 하는데, 사용자가 수백만이면 그 상태가 곧 비용입니다. 한 명당 몇 바이트냐가 알고리즘을 고르는 기준이 돼요.
🌐
분산 환경에서 동작
서버가 열 대인데 각자 세면 한도가 열 배가 됩니다. 여러 대가 같은 숫자를 봐야 해요. 이 한 줄이 가장 어려운 절을 만듭니다.
🚑
실패해도 서비스는 계속
문지기가 쓰러졌다고 가게 문을 닫을 수는 없습니다. 리미터가 고장 나면 일단 통과시키는 쪽(fail-open)을 기본으로 잡습니다. 뒤에서 예외도 봅니다.

면접관에게 물어볼 질문

위 요구사항은 아래 질문에 답을 받아서 적은 것입니다. 특히 두 번째 질문에 어떻게 답하느냐로 설계의 절반이 갈립니다.

  • 무엇을 기준으로 세나요? IP인가요, 사용자 ID인가요? — IP는 로그인 전에도 쓸 수 있지만 회사·카페처럼 여러 명이 한 IP를 쓰면 애먼 사람이 막힙니다. 사용자 ID는 정확하지만 로그인한 요청에만 쓸 수 있어요.
  • 규모는 어느 정도인가요? — 초당 몇 건을 받는 서비스인지가 저장소를 메모리로 할지 디스크로 할지를 정합니다. 바로 다음 절에서 계산합니다.
  • 서버는 몇 대인가요? 한 대인가요, 여러 대인가요? — 한 대면 이 문제는 30분이면 끝납니다. 여러 대라는 답을 받는 순간 이 차시의 나머지가 전부 필요해집니다.
  • 막힌 사용자에게 무엇을 돌려줄까요? — 즉시 거절할지, 잠깐 기다리게 할지, 큐에 넣어 나중에 처리할지. 응답 설계가 여기서 정해집니다.
  • 리미터가 죽으면 열어야 하나요, 닫아야 하나요? — 일반 API는 열어 주는 쪽이지만 결제나 로그인은 반대일 수 있습니다. 이건 기술이 아니라 사업 판단이라 반드시 물어봐야 해요.
🧮

봉투 뒷면 계산

공식과 외워 둘 숫자는 10차시 · 봉투 뒷면 계산에 있으니, 여기서는 이 문제의 숫자만 굴립니다. 이번 계산이 답해야 할 질문은 하나예요 — 카운터를 어디에 둘 것인가.

비유 — 출입 명부를 어디에 둘까
건물 경비실에 출입 명부가 있습니다. 사람이 들어올 때마다 한 줄씩 적죠. 이 명부를 책상 위에 둘지, 지하 서고에 둘지는 명부의 두께가 정합니다.
한 권이면 책상 위에 펼쳐 두고 즉시 넘겨 봅니다. 그런데 명부가 백 권이라면 책상에 다 못 올려요. 서고에 두고 필요할 때마다 내려가야 하는데, 그러면 한 사람 확인하는 데 3분이 걸립니다. 출입이 막히죠.
책상 위가 메모리, 지하 서고가 디스크입니다. 아래 계산은 딱 이걸 정합니다 — 우리 명부는 책상 위에 올라가는가?
1
가정을 소리 내어 말한다
일 사용자(DAU) 100만 명, 한 사람이 하루에 API를 100번 부른다고 잡겠습니다. 규칙은 사용자당 분당 100회로요. 이 세 줄을 먼저 확인받고 시작합니다.
2
초당 요청 수를 구한다
100만 명 × 100건 = 1억 건/일
1억 ÷ 10만 초 = 1,000 QPS, 피크는 두 배로 잡아 약 2,000 QPS.
여기서 중요한 건 숫자 자체가 아닙니다. 리미터의 QPS = 서비스 전체의 QPS라는 사실이에요. 모든 요청이 빠짐없이 이 장치를 거치니까요.
3
지연 예산을 정한다
그래서 예산은 요청당 1ms 이내로 못 박습니다. 같은 데이터센터 안의 메모리 저장소를 한 번 왕복하는 데 보통 1ms가 안 걸리니 이 목표는 현실적이에요. 대신 디스크 데이터베이스를 왕복하면 수십 ms라 예산이 통째로 날아갑니다.
4
카운터 하나의 크기를 잡는다
키는 user:1234567:1698300060처럼 사용자 ID + 시각이라 30바이트쯤, 값은 그냥 정수 하나입니다. 저장소가 키마다 붙이는 부가 정보까지 넉넉하게 더해 한 명당 100바이트로 잡죠.
5
전체 메모리를 구한다
100바이트 × 100만 명 = 1억 바이트 = 100MB
게다가 이건 최악의 경우입니다. 실제로는 카운터에 유효기간을 걸어 두어 최근 1분 안에 요청한 사람 것만 남거든요. 100만 명이 동시에 접속하는 일은 없으니 실제 사용량은 이보다 훨씬 작습니다.
6
결론을 내린다
수십~수백 MB는 서버 한 대의 메모리에 여유롭게 들어갑니다. 그러면 답은 정해졌어요 — 카운터는 디스크 데이터베이스가 아니라 메모리 저장소에 둔다. 다음다음 절에서 그 저장소로 Redis를 고르는 이야기가 나옵니다.
단, 세는 방법에 따라 이 숫자가 수십 배로 뜁니다
위의 100MB는 사람마다 숫자 하나만 들고 있을 때의 이야기입니다. 만약 다음 절에서 볼 슬라이딩 윈도 로그 방식을 고르면, 사람마다 요청 시각을 최대 100개씩 저장해야 해요. 항목 하나에 수십 바이트씩만 잡아도 한 명당 수 KB가 되고, 100만 명이면 수 GB입니다.
같은 문제인데 알고리즘 선택 하나로 100MB가 5GB가 됩니다. 봉투 뒷면 계산의 진짜 쓸모가 이거예요 — 계산은 알고리즘을 고르는 기준을 만들어 줍니다. 그러니 다음 절의 비교 표에서 메모리 칸을 특히 눈여겨보세요.

2단계 · 개략 설계

이제 박스를 그립니다. 이 문제의 개략 설계에서 정할 것은 사실상 딱 하나예요 — 이 장치를 어디에 둘 것인가. 두는 자리에 따라 무엇을 알 수 있고 무엇을 못 막는지가 완전히 달라집니다.

비유 — 검표소를 어디에 세울까
놀이공원에서 표를 확인하는 자리는 세 군데 중 하나입니다.
① 손님 주머니 속 — "알아서 하루 세 번만 타세요"라고 부탁하는 것. 양심적인 손님에게는 통하지만 지키지 않는 사람은 그냥 안 지킵니다.
② 놀이기구마다 직원 배치 — 기구별 사정을 잘 압니다. 대신 기구가 서른 개면 직원도 서른 명이고, 규칙을 바꾸려면 서른 명에게 다 알려야 해요.
③ 공원 정문 — 모든 손님이 반드시 여기를 지납니다. 한자리에서 전부 걸러지죠. 대신 정문 직원은 손님이 어느 기구를 탈지 모르고, 정문이 막히면 공원 전체가 막힙니다.

어디에 둘까

📱
클라이언트 — 믿을 수 없다
앱이나 웹 코드에서 스스로 횟수를 세는 방식입니다. 방어 수단으로는 쓸 수 없어요. 코드는 뜯어고칠 수 있고, 아예 앱을 거치지 않고 서버에 직접 요청을 보내면 이 코드는 실행조차 되지 않으니까요. 사용자 경험을 위한 보조 장치로만 씁니다.
🧩
서버 안 미들웨어
애플리케이션 코드 앞단에 끼워 넣는 방식입니다. 요청을 처리하기 직전이라 로그인한 사용자가 누구인지, 어떤 요금제인지까지 다 압니다. 대신 서비스가 여러 개면 서비스마다 따로 붙여야 하고, 언어가 다르면 구현도 따로예요.
🚪
API 게이트웨이 — 기본 선택
모든 요청이 반드시 지나는 입구에 두는 방식입니다. 여기서 걸린 요청은 서버 근처에도 못 옵니다. 게이트웨이는 정체가 07차시의 리버스 프록시이고, 처리율 제한은 인증·로깅과 함께 거기에 얹는 대표적인 기능이에요.

서비스가 하나뿐이고 규칙이 단순하면 미들웨어가 빠르고 편합니다. 서비스가 여러 개로 늘어나는 순간 게이트웨이 쪽이 이겨요. 같은 규칙을 한자리에서 관리할 수 있고, 무엇보다 공격 트래픽이 서비스에 도달하기 전에 끊기니까요. 이 차시는 게이트웨이에 둔 경우를 기준으로 그립니다.

규칙은 이렇게 생겼다

규칙은 코드가 아니라 설정이라고 요구사항에 적었습니다. 그러니 사람이 읽고 고칠 수 있는 형태여야 해요. 실무에서 흔한 모양은 이 정도입니다.

yaml
- match: user_id
  limit: 100
  unit: minute

세 줄이 전부입니다. 무엇을 기준으로 셀지(match), 몇 번까지 허용할지(limit), 그 기준이 되는 시간 단위(unit). 이런 줄을 여러 개 두고 하나라도 걸리면 거부하는 식으로 겹쳐 쓸 수 있어요. IP 기준 한 줄과 사용자 기준 한 줄을 함께 두는 식이죠.

알고리즘 5가지: 어떻게 셀 것인가

3단계 상세 설계의 첫 번째 주제입니다. "분당 100회"라는 규칙을 실제로 어떻게 세느냐는 방법이 하나가 아니에요. 다섯 가지가 널리 쓰이는데, 각각 정확도·메모리·순간 몰림 허용을 다르게 맞바꿉니다. 다섯을 다 외울 필요는 없고, 왜 다섯이나 되는지를 이해하면 됩니다.

비유 — 양동이 두 개
마당에 양동이가 둘 있습니다. 생김새는 비슷한데 하는 일이 정반대예요.
① 동전 양동이 — 누가 1초에 한 개씩 동전을 넣어 주고, 최대 열 개까지 담깁니다. 놀이기구를 타려면 동전을 하나 꺼내야 해요. 열 개가 쌓여 있으면 연속 열 번도 탈 수 있지만, 다 쓰고 나면 1초에 한 번으로 돌아옵니다.
② 구멍 뚫린 양동이 — 위로 물을 아무리 급하게 부어도 아래 구멍에서는 늘 일정한 속도로만 나옵니다. 양동이가 넘치면 넘친 물은 버려지고요.
①이 토큰 버킷, ②가 누출 버킷입니다. ①은 쌓아 뒀다 몰아 쓰기를 허락하고, ②는 어떤 경우에도 속도를 일정하게 만듭니다. 나머지 세 가지는 양동이 없이 달력에 바를 정(正) 자를 그리는 방식들이에요.

1. 토큰 버킷 (token bucket)

양동이 하나에 토큰을 담아 두고, 요청이 올 때마다 하나씩 꺼내 씁니다. 꺼낼 토큰이 없으면 거부예요. 설정할 값은 딱 둘입니다.

1
버킷 크기(capacity)를 정한다
양동이에 담기는 토큰의 최대 개수입니다. 이 숫자가 한 번에 몰아 쓸 수 있는 양이에요. 10으로 잡으면 쉬다 온 사용자는 연속 10번까지 통과합니다.
2
리필 속도(refill rate)를 정한다
초당 몇 개씩 토큰을 채워 넣을지입니다. 이 숫자가 장기적으로 허용하는 평균 속도예요. 초당 2개면 아무리 오래 써도 평균 초당 2회를 넘지 못합니다. 양동이가 꽉 차면 넘치는 토큰은 그냥 버립니다.
3
요청이 오면 토큰을 하나 꺼낸다
있으면 통과, 없으면 거부. 판단은 이 한 줄이 전부입니다. 실제로는 토큰을 계속 채워 넣는 대신 "마지막으로 만진 시각"과 "그때 남은 토큰 수" 두 개만 저장해 두었다가, 요청이 올 때 흐른 시간 × 리필 속도를 더해 계산합니다.

3번의 마지막 문장이 이 알고리즘의 숨은 장점입니다. 저장할 것이 숫자 두 개뿐이고, 타이머를 돌릴 필요도 없어요. 그리고 파라미터 둘이 사람 말로 바로 번역됩니다 — "평소엔 초당 2회, 대신 몰아서 10회까지는 봐준다."

2. 누출 버킷 (leaking bucket)

이번엔 요청을 정해진 크기의 대기열(FIFO 큐)에 넣습니다. 그리고 일정한 속도로 하나씩 꺼내 처리해요. 큐가 꽉 찬 상태에서 새 요청이 오면 그 요청은 버립니다.

토큰 버킷과 결정적으로 다른 점은 출력이 언제나 매끈하다는 것입니다. 앞에서 요청이 아무리 몰려도 뒤로 나가는 속도는 정확히 초당 2건이에요. 뒤에 있는 시스템이 일정 속도까지만 감당할 수 있을 때 — 오래된 결제 게이트웨이나 문자 발송 업체 같은 곳 — 이 성질이 필요합니다.

대가도 분명합니다. 큐에서 기다리는 만큼 응답이 늦어집니다. 큐가 길면 사용자는 몇 초 뒤에 처리될 요청을 붙잡고 기다려야 해요. 그리고 쉬다 온 사용자를 봐주는 일이 없습니다. 하루 종일 놀았어도 속도는 똑같이 초당 2건이거든요.

3. 고정 윈도 카운터 (fixed window counter)

가장 단순한 방식입니다. 시간을 1분짜리 칸으로 자르고, 칸마다 카운터를 하나 둡니다. 요청이 오면 지금 칸의 카운터를 1 올리고, 한도를 넘으면 거부해요. 분이 바뀌면 새 칸에서 0부터 다시 셉니다. 저장할 것은 숫자 하나뿐이라 메모리가 가장 적게 듭니다.

그런데 이 단순함에는 대가가 있습니다. 한도를 분당 100회로 두고 어떤 사용자의 요청을 따라가 볼게요.

1
10:00:59 — 100건이 통과한다
10시 00분 칸의 카운터가 100이 됩니다. 여기까지는 규칙대로예요.
2
10:01:00 — 칸이 바뀌며 카운터가 리셋된다
1초 만에 카운터가 0으로 돌아갑니다.
3
10:01:00 — 100건이 더 통과한다
새 칸이니 전부 허용됩니다. 1·3번 사이의 간격은 고작 1초예요.
4
10:00:30 ~ 10:01:30을 잘라 보면 200건
이 1분 구간 안에 두 무리가 모두 들어옵니다. 한도의 정확히 두 배가 통과한 셈이에요.
함정 — "1분"을 어디서부터 세느냐에 따라 답이 달라집니다
위 사용자는 규칙을 어긴 적이 한 번도 없습니다. 두 무리가 각각 다른 칸에 들어갔을 뿐이에요. 그런데도 어떤 1분 구간에서는 한도의 두 배가 통과했습니다. 문제의 뿌리는 창을 미리 잘라 고정해 둔 것 자체에 있어요.
칸을 1초로 잘게 자르면 완화되지만, 그만큼 카운터 개수가 늘어납니다. 이 함정을 제대로 푸는 것이 다음 두 알고리즘이에요.

4. 슬라이딩 윈도 로그 (sliding window log)

경계 문제가 생긴 이유는 1분을 미리 잘라 놨기 때문입니다. 그러면 자르지 말고, 요청이 올 때마다 그 시점 기준으로 지난 1분을 세면 되지 않을까요? 그게 이 방식입니다.

1
요청 시각을 전부 기록한다
사용자마다 요청이 들어온 시각의 목록을 들고 있습니다. 시각순으로 정렬된 집합에 넣어 두면 다루기 편해요.
2
낡은 기록을 지운다
새 요청이 오면 먼저 (지금 − 1분)보다 오래된 시각을 목록에서 전부 지웁니다. 남은 것이 곧 지난 1분 동안의 요청이에요.
3
남은 개수로 판단한다
목록의 크기가 한도보다 작으면 통과시키고 지금 시각을 목록에 추가합니다. 창이 요청이 올 때마다 미끄러지듯 따라오므로 경계 문제가 아예 생기지 않습니다.

정확도는 다섯 중 최고입니다. 어느 1분 구간을 잘라 봐도 한도를 넘지 않아요. 문제는 메모리예요. 사용자마다 한도 개수만큼의 시각을 들고 있어야 하니, 앞 절에서 계산한 대로 100MB가 수 GB로 부풀어 오릅니다. 게다가 거부한 요청의 시각까지 목록에 남기는 구현이 흔한데, 그러면 공격받는 동안 메모리가 더 빨리 찹니다.

5. 슬라이딩 윈도 카운터 (sliding window counter)

마지막 방식은 앞의 둘을 섞은 절충안입니다. 아이디어는 이래요 — 고정 윈도 카운터를 쓰되, 직전 칸의 숫자를 겹치는 비율만큼 빌려 온다.

한도가 분당 100회이고 지금이 10:01:30이라고 해 봅시다. 지금 기준의 "지난 1분"은 10:00:30 ~ 10:01:30인데, 이 구간은 10시 00분 칸의 뒤쪽 절반과 10시 01분 칸의 앞쪽 절반에 걸쳐 있습니다. 그러니 직전 칸의 숫자를 절반만 세는 거예요.

추정치 = 현재 칸 개수 + 직전 칸 개수 × 겹치는 비율

1
직전 칸(10:00)의 개수를 꺼낸다
80건이었다고 해 봅시다. 이미 지나간 칸이지만 버리지 않고 남겨 둡니다.
2
현재 칸(10:01)의 개수를 꺼낸다
30건. 지금 칸에서 실제로 센 숫자라 그대로 씁니다.
3
겹침 비율로 합쳐 한도와 비교한다
30 + 80 × 0.5 = 70 → 100보다 작으니 통과. 만약 직전 칸에 몰아친 200건이 있었다면 30 + 200 × 0.5 = 130이라 거부됩니다. 3번의 경계 함정이 이렇게 막혀요.

단, 이건 추정치입니다. "직전 칸의 요청이 그 1분 안에 고르게 퍼져 있었다"고 가정하고 비례배분한 값이거든요. 실제로는 직전 칸의 요청이 앞쪽 30초에 몰려 있었을 수도 있죠. 그래도 실무에서 널리 쓰이는 이유는, 이 가정이 어긋나는 경우가 드물고 어긋나도 오차가 아주 작다고 알려져 있기 때문입니다. 그러면서 저장할 것은 카운터 두 개뿐이에요.

Redis로 만들기

알고리즘을 골랐으니 이제 그 숫자를 어디에 둘지를 정합니다. 봉투 뒷면 계산에서 이미 "메모리 저장소"라는 결론을 냈는데, 실무에서 이 자리는 거의 항상 Redis입니다. 왜 그런지부터 봅시다.

비유 — 유통기한 스티커
냉장고에 반찬을 넣을 때마다 "60초 뒤 자동 폐기"라고 적힌 스티커를 붙일 수 있다고 해 봅시다. 시간이 지나면 반찬이 알아서 사라집니다.
이게 왜 좋을까요? 냉장고를 뒤지며 상한 것을 골라내는 사람이 필요 없기 때문입니다. 카운터가 100만 개인데 지난 분의 카운터를 지우러 다니는 청소부를 따로 두면, 그 청소 작업이 또 하나의 부하가 되고 청소부가 죽으면 메모리가 계속 찹니다.
Redis의 TTL이 정확히 이 스티커입니다. 카운터를 만들 때 "60초"만 적어 두면 그 뒤는 신경 쓸 일이 없어요. 그래서 메모리에 남는 것은 최근에 요청한 사람들의 카운터뿐입니다.

⚡
메모리에 있어 빠르다
데이터를 메모리에 두므로 읽고 쓰는 데 마이크로초가 걸립니다. 네트워크 왕복을 더해도 같은 데이터센터 안이면 1ms 예산 안에 들어와요.
➕
원자적으로 증가시킨다
INCR 명령 하나가 "1 더하고 결과를 알려 주기"를 통째로 처리합니다. 여러 요청이 동시에 불러도 중간에 끼어들 틈이 없어요. 이게 왜 결정적인지는 바로 아래에서 봅니다.
⏳
유효기간을 걸 수 있다
EXPIRE로 "60초 뒤 삭제"를 지정하면 알아서 사라집니다. 06차시의 TTL과 같은 개념이 여기서는 청소부 없이 메모리를 지키는 장치로 쓰여요.
🤝
여러 서버가 공유한다
서버 열 대가 같은 Redis를 바라보면 카운터도 하나입니다. 이게 분산 환경 문제의 출발점이자 해답이에요.

고정 윈도 카운터를 만들어 보기

가장 단순한 고정 윈도 카운터로 흐름을 따라가 봅시다. 명령 두 개면 끝납니다.

1
키를 만든다
user:42:1698300060 — 기준(사용자 42)과 분 단위로 잘라 낸 시각을 이어 붙입니다. 시각을 키에 넣어 두면 분이 바뀌는 순간 자동으로 다른 키가 되므로, 카운터를 0으로 되돌리는 코드가 아예 필요 없어요.
2
INCR로 1 올린다
키가 없으면 Redis가 0에서 시작해 1로 만들어 줍니다. "먼저 만들고 그 다음 올리기"를 나눠 할 필요가 없어요. 그리고 올린 뒤의 값을 곧바로 돌려줍니다.
3
결과가 1이면 EXPIRE를 건다
돌려받은 값이 1이라는 건 이번 분의 첫 요청이라는 뜻입니다. 그때만 EXPIRE key 60으로 유효기간을 걸어요. 매번 걸면 유효기간이 계속 갱신돼서 키가 영영 안 사라집니다.
4
값과 한도를 비교한다
돌려받은 값이 100보다 크면 거부, 아니면 통과. 그리고 100 − 값이 응답 헤더에 실을 "남은 횟수"가 됩니다.
5
60초 뒤 Redis가 키를 지운다
우리가 할 일은 없습니다. 그래서 메모리에는 최근 1분 안에 요청한 사람들의 카운터만 남아요. 앞 절의 100MB보다 실제로는 훨씬 작아지는 이유입니다.
절대 하지 말 것 — 읽고 나서 올리기
위 2번을 순진하게 짜면 이렇게 됩니다. ① 값을 읽는다 → ② 한도보다 작은지 본다 → ③ 1을 올린다. 사람이 생각하는 순서 그대로라 자연스러워 보이죠. 그런데 이건 틀립니다.
요청 두 개가 거의 동시에 도착했다고 해 봅시다. 둘 다 ①에서 99를 읽습니다. 둘 다 ②에서 "아직 여유 있네"라고 판단합니다. 그리고 둘 다 ③에서 1을 올려 카운터는 101이 되고, 두 요청 모두 통과했습니다. 한도를 넘겼는데 아무도 막지 못했어요.
고치는 방법은 순서를 뒤집는 것입니다. 먼저 INCR로 올리고, 돌려받은 값을 보고 판단하세요. Redis는 명령 하나를 끝까지 처리한 뒤에야 다음 명령을 받으므로, 두 요청은 각각 100과 101을 돌려받습니다. 101을 받은 쪽만 정확히 거부되고요. 읽기와 쓰기 사이에 틈을 만들지 않는 것이 핵심입니다.

남은 틈 하나 — INCR과 EXPIRE 사이

순서를 뒤집어 첫 번째 문제는 풀었습니다. 그런데 아직 명령이 두 개라는 사실이 남아 있어요. INCR은 성공했는데 바로 다음 줄의 EXPIRE를 부르기 직전에 리미터 프로세스가 죽거나 네트워크가 끊기면 어떻게 될까요?

유효기간이 없는 카운터가 Redis에 남습니다. 이 키는 영원히 사라지지 않고, 값은 계속 올라가기만 해요. 그러면 그 사용자는 분이 바뀌어도 계속 100을 넘은 상태가 되어 영구히 차단됩니다. 몇 년에 한 번 날 법한 일 같지만, 초당 2,000건이 흐르는 곳에서는 생각보다 자주 일어납니다.

해결책은 두 명령을 하나로 묶는 것입니다. Redis는 Lua 스크립트를 하나의 명령처럼 끝까지 실행하므로, 스크립트 중간에 다른 요청이 끼어들 수도 없고 절반만 실행되고 끝나는 일도 없습니다.

lua
local n = redis.call('INCR', KEYS[1])
if n == 1 then
  redis.call('EXPIRE', KEYS[1], ARGV[1])
end
return n

다섯 줄이 전부입니다. 올리고, 처음이면 유효기간을 걸고, 결과를 돌려줍니다. 리미터는 돌려받은 숫자를 한도와 비교하기만 하면 돼요. 스크립트를 쓰기 싫다면 MULTI로 두 명령을 한 묶음으로 보내는 방법도 있지만, 조건 판단("1일 때만")이 들어가는 순간 Lua 쪽이 훨씬 깔끔합니다.

이 절에서 얻은 것과 새로 생긴 걱정
얻은 것은 정확한 카운터입니다. 동시에 들어온 요청 때문에 한도가 새는 일도, 죽지 않는 키가 남는 일도 없어졌어요.
새로 생긴 걱정은 Redis에 전부를 걸었다는 것입니다. 이제 모든 요청이 Redis를 한 번씩 다녀옵니다. Redis가 느려지면 서비스 전체가 느려지고, Redis가 죽으면 단일 장애점이 그대로 현실이 돼요. 그 걱정을 다음 절에서 다룹니다.
🌐

분산 환경의 문제

지금까지는 리미터가 한 대라고 은근슬쩍 가정하고 있었습니다. 실제로는 트래픽을 받아 내려고 리미터를 여러 대 띄우고 앞에 로드 밸런서를 두죠. 그 순간 지금까지 만든 것이 조용히 무너집니다.

비유 — 창구 직원마다 수첩이 따로인 은행
은행에서 "1인당 하루 100만 원까지" 인출 한도를 두기로 했습니다. 그런데 창구 직원 열 명이 각자 수첩에 적어서 관리해요.
눈치 빠른 손님은 금방 방법을 찾아냅니다. 1번 창구에서 100만 원, 2번 창구에서 또 100만 원… 열 개 창구를 돌면 1,000만 원입니다. 각 직원은 규칙을 완벽히 지켰는데도 은행 전체로 보면 한도가 열 배가 됐어요.
해결은 뻔합니다. 수첩을 없애고 창구 뒤에 공용 장부 하나를 두는 것. 어느 창구에서 처리하든 같은 장부에 적고 같은 장부를 보면 됩니다.
수첩이 서버 각자의 메모리, 공용 장부가 중앙 Redis입니다.

문제 1 — 카운터가 흩어진다

리미터가 열 대이고 각자 자기 메모리에 카운터를 두면, 로드 밸런서가 요청을 흩뿌리는 대로 카운터도 열 갈래로 나뉩니다. 한도 100이 실질적으로 1,000이 되는 거예요. 앞 절의 INCR을 아무리 원자적으로 만들어도, 애초에 세는 곳이 열 군데면 소용이 없습니다.

해법은 비유 그대로입니다 — 카운터를 서버 밖의 공용 Redis에 둡니다. 그러면 리미터 서버들은 자기만 아는 상태를 하나도 들고 있지 않게 돼요. 04차시의 무상태 서버가 바로 이 성질이고, 덕분에 어느 리미터가 요청을 받아도 답이 같아집니다. 리미터를 늘리고 줄이는 것도 자유로워지고요.

문제 2 — Redis 한 대로 모자라면

공용 장부가 하나면 그 장부 앞에 줄이 섭니다. 초당 요청이 계속 늘어 Redis 한 대의 처리량이나 메모리를 넘어서면 나눠야 해요. 다행히 이 문제는 08차시의 샤딩이 아주 깔끔하게 풀어 줍니다.

키를 사용자 ID로 나누면 됩니다. user:42로 시작하는 키는 언제나 같은 Redis로 가게 하는 거예요. 그러면 한 사용자의 카운터가 두 군데로 갈라지는 일이 없으므로 정확도가 전혀 손상되지 않습니다. 기준이 IP인 규칙이라면 IP로 나누고요. 여기서 노드를 늘리고 줄일 때 11차시의 안정 해시를 쓰면 대이동 없이 넘어갈 수 있습니다.

주의할 점은 기준마다 샤딩 키가 다르다는 것입니다. IP 기준 규칙과 사용자 기준 규칙을 함께 쓰면 두 종류의 키가 서로 다른 노드에 흩어져요. 한 요청을 판단하려고 Redis를 두 번 다녀와야 할 수도 있고, 그러면 1ms 예산이 빠듯해집니다.

문제 3 — 아무리 해도 조금은 틀린다

공용 Redis를 써도 완벽하게 정확하지는 않습니다. 리미터가 Redis를 다녀오는 데 걸리는 짧은 시간 동안, 다른 리미터들도 동시에 판단을 내리고 있거든요. 정확히 100번째에서 딱 끊기지 않고 102번, 103번쯤에서 끊길 수 있습니다.

조금 틀려도 됩니다 — 목적을 다시 보세요
완벽하게 정확히 세려면 요청마다 잠금(lock)을 걸어 한 줄로 세워야 합니다. 그러면 리미터가 병목이 되어 1ms 예산이 통째로 날아가요. 모든 요청이 거치는 장치에서 이건 최악의 거래입니다.
그런데 애초에 한도 100의 목적이 무엇이었나요? 101번째 요청을 잡아내는 게 아니라, 1,000번과 10,000번을 막는 것이었습니다. 봉투 뒷면 계산에서 소수점이 아니라 자릿수가 중요했던 것과 똑같아요. 103에서 끊겨도 목적은 완벽히 달성됩니다.
그러니 여기서는 약간의 부정확함을 사서 속도를 얻는 쪽이 옳습니다. 다만 "정확히 몇 건"이 계약으로 정해진 유료 API라면 이야기가 달라져요. 그때는 느려지는 걸 감수하고 정확도를 택합니다. 무엇이 중요한지는 기술이 아니라 사업이 정합니다.

문제 4 — Redis가 죽으면

모든 요청이 Redis를 거치므로, Redis가 답을 못 하는 순간 리미터는 판단할 근거를 잃습니다. 이때 무엇을 할지는 둘 중 하나고, 이 선택에는 정답이 없습니다.

🔓 열어 준다 (fail-open)
판단할 수 없으면 일단 통과시킵니다.

좋은 점 — 리미터 장애가 서비스 장애로 번지지 않습니다. 문지기가 쓰러졌다고 가게 문을 닫지는 않는다는 발상이에요.

나쁜 점 — 그 몇 분 동안은 아무도 막지 못합니다. 하필 공격받는 중이었다면 최악의 타이밍이고요.

일반 API의 기본값입니다. 1단계 요구사항에서 고른 쪽이기도 하고요.
🔒 막는다 (fail-closed)
판단할 수 없으면 전부 거부합니다.

좋은 점 — 한도를 넘는 요청이 절대 새어 나가지 않습니다. 오남용 피해가 돈이나 신뢰로 직결되는 곳에 맞아요.

나쁜 점 — 리미터 장애 = 서비스 장애입니다. 사용자 입장에서는 멀쩡한 서비스가 통째로 멈춘 것으로 보이고요.

결제·로그인·문자 발송처럼 한 번의 오남용이 비싼 곳에만 씁니다.

어느 쪽을 고르든 Redis 자체를 튼튼하게 만드는 일은 따로 해야 합니다. 복제본을 두어 한 대가 죽어도 넘어가게 하고, 리미터는 규칙만큼은 자기 메모리에 캐시해 두어 Redis가 흔들려도 규칙 조회 때문에 멈추지는 않게 만듭니다.

📣

거부할 때 어떻게 알릴까

막기로 결정했습니다. 그런데 막았다는 사실을 어떻게 전달하느냐가 남았어요. 여기를 대충 만들면 이상한 일이 벌어집니다 — 막힌 클라이언트가 더 세게 재시도해서 상황을 악화시키거든요.

비유 — 안내판이 있는 대기줄과 없는 대기줄
놀이기구 앞에서 말없이 줄을 막아 세우면 손님들은 계속 앞으로 밀어붙입니다. 왜 막혔는지, 언제 열리는지 모르니까요. 앞사람에게 물어보고, 다시 줄을 서 보고, 직원에게 항의합니다. 막았는데 혼잡은 오히려 심해졌어요.
반대로 "현재 회차 마감 · 다음 탑승 5분 뒤"라는 안내판 하나만 세워 두면 손님들은 조용히 5분을 기다립니다. 물어보는 사람도, 밀어붙이는 사람도 줄어요.
HTTP에서 이 안내판이 상태 코드와 응답 헤더입니다. 왜 막혔는지와 언제 다시 오면 되는지, 이 두 줄이 핵심이에요.

상태 코드는 429

한도를 넘어 거부할 때 쓰는 코드는 429 Too Many Requests입니다. 05차시에서 본 것처럼 4로 시작하는 코드는 "요청한 쪽에 문제가 있다"는 뜻이에요. 실제로 그렇습니다. 서버는 멀쩡하고 이 클라이언트가 약속한 한도를 넘은 것이니까요.

흔한 실수는 503 Service Unavailable을 돌려주는 것입니다. 503은 서버가 지금 감당을 못 한다는 뜻이라 의미가 다르고, 실질적인 문제도 생겨요. 많은 클라이언트 라이브러리가 503을 서버 탓으로 보고 공격적으로 재시도하도록 만들어져 있거든요. 한도를 넘긴 클라이언트에게 더 빨리 다시 오라고 신호를 보내는 셈입니다.

헤더로 상황을 알려 준다

상태 코드만으로는 "언제"에 답할 수 없습니다. 그래서 헤더 세 개를 함께 실어 보냅니다.

헤더예시 값뜻
X-RateLimit-Limit 100 이 시간 단위에서 허용되는 전체 횟수입니다. 클라이언트가 자기 예산의 크기를 알게 됩니다.
X-RateLimit-Remaining 23 지금 남은 횟수입니다. 거부된 응답뿐 아니라 성공한 응답에도 실어 주는 게 좋아요. 그래야 클라이언트가 0에 가까워지기 전에 스스로 속도를 줄입니다.
Retry-After 30 몇 초 뒤에 다시 오면 되는지입니다. 이 한 줄이 무의미한 재시도를 없애 줍니다. 앞의 둘과 달리 HTTP 표준 헤더라 많은 라이브러리가 알아서 해석해요.

X-로 시작하는 앞의 두 헤더는 표준이 아니라 널리 쓰이는 관례입니다. 이름이 조금씩 다른 서비스도 많아요. 그래도 이 형태를 따르는 이유는 많은 API가 이미 이렇게 쓰고 있어서 클라이언트 개발자가 설명 없이 알아보기 때문입니다. 그리고 응답 본문에는 사람이 읽을 메시지를 한 줄 담아 줍니다 — "분당 100회 한도를 초과했습니다. 30초 후 다시 시도하세요." 처럼요.

거부한 요청을 버릴까, 큐에 넣을까

"거부"에도 두 가지 방식이 있습니다. 어느 쪽이 맞는지는 그 요청의 결과가 지금 당장 필요한지가 정합니다.

🗑️
버린다 (drop)
즉시 429를 돌려주고 요청은 없던 일이 됩니다. 리미터는 아무것도 들고 있지 않아 가볍고 빠르며, 사용자는 곧바로 결과를 압니다. 화면을 보며 기다리는 대화형 API의 기본값이에요.
📨
큐에 넣는다 (queue)
거부 대신 09차시의 메시지 큐에 쌓아 두고 여유가 생기면 처리합니다. 사용자에게는 "접수했다"고만 답하고요. 이메일 발송이나 대량 업로드처럼 결과가 급하지 않은 일에 맞습니다.

큐에 넣는 방식은 누출 버킷이 하던 일과 정확히 같습니다. 그때 지적한 대가도 그대로예요 — 큐에 크기 상한이 없으면 밀린 요청이 무한정 쌓여 메모리를 먹고, 몇 시간 전에 접수된 일을 지금 처리하는 의미 없는 작업이 됩니다. 큐를 쓴다면 상한과 유효기간을 반드시 함께 정해야 합니다.

재시도를 클라이언트에게 맡길 때의 함정
Retry-After: 30을 받은 클라이언트가 1,000개라고 해 봅시다. 모두 성실하게 정확히 30초를 기다렸다가 다시 요청을 보냅니다. 그러면 30초 뒤 그 순간에 1,000건이 한꺼번에 도착해요. 막으려던 몰림이 시간만 옮겨서 그대로 재현됩니다.
그래서 클라이언트에게 두 가지를 안내합니다. 첫째, 재시도 간격을 점점 늘리기(2초 → 4초 → 8초). 둘째, 거기에 무작위 값을 조금 섞기. 무작위를 섞는 이유는 모두가 같은 시각에 몰리지 않게 흩뜨리기 위해서예요. 이 둘이 없으면 착한 클라이언트가 모여서 공격이 됩니다.
✅

4단계 · 마무리와 트레이드오프

마지막 5분입니다. 부품을 나열하는 것과 왜 그걸 골랐고 무엇을 포기했는지 말하는 것은 완전히 다른 답이라고 11차시에서 확인했죠. 이번에도 같은 일을 합니다.

비유 — 자물쇠를 달고 밖에서 흔들어 보기
현관에 새 자물쇠를 달았습니다. 여기서 끝내는 사람과, 밖으로 나가 직접 흔들어 보는 사람이 있어요.
흔들어 보는 사람은 금방 알아냅니다. "뒷문은 그대로네"(계층별 제한이 없다), "열쇠를 잃어버리면 나도 못 들어가네"(리미터가 죽으면?), "택배 기사는 매번 막히겠네"(정상 사용자가 걸리면?).
자물쇠를 단 것 자체는 둘 다 똑같습니다. 다른 건 자기 설계의 빈틈을 자기가 먼저 말할 수 있는가예요. 아래 표와 질문 목록이 그 흔들어 보기입니다.

무엇을 왜 골랐나

부품어떤 요구사항 때문에대신 무엇을 포기했나
API 게이트웨이에 배치 분산 환경 동작 — 모든 요청이 반드시 지나는 한 길목이라 규칙을 한자리에서 관리하고, 걸린 요청은 서버에 닿지도 않습니다. 게이트웨이가 새 병목이자 장애점이 됩니다. 요금제 같은 애플리케이션 내부 정보를 쓰려면 따로 넘겨줘야 하고요.
토큰 버킷 적은 메모리 + 낮은 지연 — 숫자 두 개로 끝나고, 사람이 만드는 순간 몰림을 자연스럽게 받아 줍니다. 버킷 크기만큼은 한 번에 통과합니다. 뒤에 있는 시스템이 일정 속도만 감당한다면 누출 버킷으로 바꿔야 해요.
중앙 Redis + Lua 분산 환경 동작 + 정확성 — 여러 서버가 같은 카운터를 보고, 원자적 실행이라 동시 요청에 한도가 새지 않습니다. 요청마다 네트워크 왕복 1회가 추가되고, Redis가 서비스 전체의 급소가 됩니다.
사용자 ID 샤딩 확장 — Redis 한 대의 메모리·처리량을 넘어설 때 정확도를 잃지 않고 나눌 수 있습니다. 규칙의 기준(IP·사용자·API)마다 샤딩 키가 달라 운영이 복잡해지고, 한 요청에 왕복이 두 번 필요할 수도 있습니다.
fail-open 실패해도 서비스는 계속 — 리미터 장애가 서비스 장애로 번지지 않습니다. 그동안은 아무도 막지 못합니다. 결제처럼 오남용이 비싼 API는 반대로 골라야 해요.
429 + 안내 헤더 명확한 안내 — 클라이언트가 언제 다시 오면 되는지 알아 무의미한 재시도가 사라집니다. 남은 횟수를 알려 주면 공격자도 한도를 정확히 알게 됩니다. 딱 그 아래로 맞춰 계속 두드릴 수 있어요.

더 물어보면 좋은 확장 질문

시간이 남았거나 면접관이 더 파고 싶어 할 때 꺼낼 카드들입니다. 전부 지금 설계에서 자연스럽게 이어지는 질문이에요.

  • 하드 제한과 소프트 제한을 나누면? — 하드는 한도를 넘는 순간 무조건 거부합니다. 소프트는 잠깐은 넘겨 주되 경고를 보내거나 초과분을 과금해요. 갑자기 트래픽이 튄 정상 고객을 끊어 버리지 않으면서도 남용은 잡을 수 있어, 유료 API에서 자주 쓰는 방식입니다.
  • 계층을 나눠서 겹쳐 걸면? — IP당 분당 1,000회, 사용자당 분당 100회, 로그인 API는 분당 5회처럼 규칙을 여러 층으로 두고 하나라도 걸리면 거부합니다. 로그인 전에는 IP 층이, 로그인 후에는 사용자 층이 주로 일하죠. 대신 왕복이 층마다 늘어난다는 대가가 있습니다.
  • 규칙을 클라이언트에게 공개할까? — 문서와 응답 헤더로 알려 주면 클라이언트가 스스로 속도를 조절해 서로 편해집니다. 대신 공격자도 한도를 정확히 알게 되니, 공개용 한도와 내부 방어선을 다르게 두기도 해요.
  • 요금제마다 한도를 다르게 하려면? — 규칙을 사용자 등급과 묶고, 리미터가 요청을 받을 때 그 사용자의 등급으로 규칙을 골라 적용합니다. 등급 조회가 또 한 번의 왕복이 되지 않도록 토큰 안에 등급을 담아 보내는 방법을 씁니다.
  • Redis 왕복마저 아까우면? — 리미터 서버가 아주 짧은 시간 동안 자기 메모리에서 먼저 세고 주기적으로 Redis에 합치는 방법이 있습니다. 왕복 횟수가 확 줄지만 정확도를 조금 더 팝니다. "조금 틀려도 된다"를 한 발 더 밀고 간 거래예요.
  • 429가 갑자기 늘면 무엇을 봐야 하나? — 공격일 수도, 규칙이 너무 빡빡해 정상 사용자가 걸리는 것일 수도, 클라이언트 쪽 버그로 무한 재시도가 도는 것일 수도 있습니다. 셋의 대응이 전혀 다르니 거부된 요청의 기준값과 경로를 남겨 구분할 수 있어야 해요.
두 번째 사례를 통과했습니다
문제를 좁히고(1단계), 규모를 어림잡아 메모리 저장소라는 결론을 내고(계산), 둘 자리를 정한 뒤(2단계), 어려운 부품 넷을 깊게 팠습니다 — 알고리즘 선택 · 원자적 카운터 · 분산과 실패 · 응답 설계. 그리고 마지막에 이유와 약점을 정리했고요. 10차시의 네 걸음 그대로입니다. 문제가 바뀌어도 순서는 바뀌지 않아요.
