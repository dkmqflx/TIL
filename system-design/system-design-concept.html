Part 1 · 컴퓨터의 기본 구조

비트와 바이트 — 컴퓨터가 쓰는 언어

대규모 분산 시스템을 설계하기 전에, 먼저 컴퓨터 한 대가 우리 코드를 어떻게 실행하는지 큰 그림을 잡아야 합니다. 컴퓨터는 여러 계층(layer)이 층층이 쌓인 구조이고, 각 계층은 서로 다른 작업에 최적화되어 있어요. 이 계층들이 어떻게 협력하는지 하나씩 살펴봅시다.

가장 밑바닥 — 컴퓨터는 0과 1만 안다
컴퓨터는 오직 0과 1(이진수, binary)만 이해합니다. 이 0 또는 1 하나가 비트(bit), 즉 컴퓨팅에서 가장 작은 데이터 단위예요. 비트 8개가 모이면 1바이트(byte)가 되고, 1바이트는 문자 하나('a')나 숫자 하나(1)를 표현할 수 있습니다.

여기서부터 단위가 커집니다. 바이트가 모여 킬로바이트(KB), 메가바이트(MB), 기가바이트(GB), 테라바이트(TB)가 됩니다.

단위크기비유 (대략)
1 비트 (bit)0 또는 1전등 스위치 하나 (켜짐/꺼짐)
1 바이트 (byte)8비트문자 한 글자 'a'
1 KB약 1,000 바이트짧은 문단 하나
1 MB약 100만 바이트고화질 사진 한 장
1 GB약 10억 바이트영화 한 편
1 TB약 1조 바이트영화 수백 편
💽

저장장치 — 데이터를 오래 보관하는 창고

이제 이 데이터를 어디에 보관할까요? 가장 먼저 디스크 저장장치(disk storage)가 있습니다. 컴퓨터의 1차 데이터 보관소로, 종류는 크게 HDD와 SSD 두 가지예요.

핵심 특징 — 비휘발성(non-volatile)
디스크는 전원이 없어도 데이터를 유지합니다. 컴퓨터를 끄거나 재시작해도 데이터가 그대로 남아 있죠. 그래서 운영체제(OS), 설치한 프로그램, 내가 만든 파일이 전부 여기 저장됩니다. 용량은 보통 수백 GB에서 수 TB까지예요.

HDD vs SSD

HDD (하드디스크)SSD (솔리드 스테이트)
읽기 속도약 80 ~ 160 MB/s약 500 ~ 3,500 MB/s (훨씬 빠름)
가격저렴상대적으로 비쌈
원리회전하는 원판 + 물리적 헤드전자식 메모리 (움직이는 부품 없음)
비유 — 창고: 디스크는 물건을 잔뜩 쌓아두는 큰 창고입니다. 용량은 크지만, 창고 안쪽 깊은 곳에서 물건을 꺼내오려면 시간이 걸려요. HDD는 사다리를 타고 올라가 꺼내는 오래된 창고, SSD는 버튼만 누르면 물건이 나오는 자동화 창고라고 생각하면 됩니다.
🧠

RAM — 지금 작업 중인 것들을 올려두는 책상

디스크 다음으로 CPU가 접근하는 곳이 RAM(Random Access Memory, 램)입니다. RAM은 지금 당장 사용 중이거나 처리 중인 데이터를 담아 두는 곳이에요. 프로그램이 실행되면 그 변수, 중간 계산값, 실행 스택(runtime stack) 같은 것들이 전부 RAM에 올라옵니다. 읽고 쓰는 속도가 빠르기 때문이죠.

핵심 특징 — 휘발성(volatile)
RAM은 전원이 있어야만 내용을 유지합니다. 컴퓨터를 재시작하면 RAM에 있던 데이터는 사라질 수 있어요. 그래서 "오래 보관"은 디스크가, "지금 작업"은 RAM이 맡습니다. 용량은 소비자용 기기에서 수 GB, 고성능 서버에서는 수백 GB까지 갑니다.

속도는 어떨까요? RAM의 읽기/쓰기 속도는 흔히 초당 5,000 MB를 넘습니다. 이건 가장 빠른 SSD보다도 빠른 수치예요. 그래서 방금 쓸 데이터는 디스크가 아니라 RAM에 올려두는 겁니다.

비유 — 책상 위 작업 공간: 창고(디스크)에서 필요한 서류만 꺼내 책상(RAM) 위에 펼쳐 놓고 일합니다. 책상이 넓을수록 한 번에 많은 일을 벌여 놓을 수 있죠. 하지만 퇴근하며 책상을 치우면(전원 종료) 펼쳐둔 건 사라집니다. 그래서 중요한 건 다시 창고(디스크)에 넣어둬야 해요.
⚡

캐시 — 손 닿는 곳에 둔 메모지

RAM도 충분히 빠르지만, 가끔은 이 속도로도 부족합니다. 그래서 등장하는 게 캐시(cache)예요. 캐시는 RAM보다 훨씬 작지만(보통 MB 단위), 접근 속도는 RAM보다도 더 빠릅니다. L1 캐시는 접근에 몇 나노초(nanosecond)밖에 안 걸려요.

CPU가 데이터를 찾는 순서

L1 캐시
→ 없으면
L2 캐시
→ 없으면
L3 캐시
→ 없으면
RAM

CPU는 데이터가 필요하면 가장 빠른 L1 캐시부터 확인합니다. 거기 없으면 L2 → L3 → 마지막으로 RAM 순서로 찾아 내려가요. 캐시의 목적은 자주 쓰는 데이터를 미리 가까이 두어, 평균 접근 시간을 줄이는 것입니다. 그래야 CPU가 놀지 않고 계속 일할 수 있거든요.

비유 — 책상 위 메모지: 창고(디스크)도 책상(RAM)도 있지만, 가장 자주 보는 전화번호는 아예 모니터에 붙인 포스트잇(캐시)에 적어둡니다. 손만 뻗으면 바로 보이죠. 대신 포스트잇은 작아서 정말 자주 쓰는 것만 붙여둘 수 있습니다.

CPU — 컴퓨터의 두뇌 (그리고 컴파일)

CPU(중앙처리장치)는 컴퓨터의 두뇌입니다. 명령을 가져오고(fetch) → 해석하고(decode) → 실행하는(execute) 일을 반복하죠. 우리가 코드를 실행하면, 그 안의 연산을 실제로 처리하는 게 바로 CPU입니다.

그런데 CPU는 우리 코드를 바로 못 읽는다

우리는 Java, C++, Python 같은 고수준 언어(사람이 읽기 쉬운 언어)로 코드를 씁니다. 하지만 CPU는 기계어(machine code, 0과 1)만 이해해요. 그래서 중간에 번역이 필요합니다. 이 번역을 해주는 게 컴파일러(compiler)예요.

고수준 코드
(Java / C++ / Python)
→ 컴파일러가 번역 →
기계어
(0과 1)
→ 실행 →
CPU

번역이 끝나면 CPU가 그 기계어를 실행하면서, 필요에 따라 RAM·디스크·캐시에서 데이터를 읽고 씁니다. 그리고 이 모든 부품을 하나로 연결해 데이터가 오갈 길을 제공하는 판이 메인보드(motherboard)예요.

비유 — 요리사와 주방: CPU는 요리하는 요리사(두뇌), 레시피(코드)는 외국어로 적혀 있어 번역가(컴파일러)가 요리사가 아는 말로 바꿔줍니다. 재료 창고(디스크), 조리대(RAM), 손 옆 양념통(캐시)을 오가며 요리하고, 이 모두를 잇는 주방 바닥과 동선이 메인보드입니다.
🪜

메모리 계층 — 왜 이렇게 여러 겹일까?

지금까지 본 캐시·RAM·디스크를 한 줄로 세우면 메모리 계층(memory hierarchy)이 됩니다. 위로 갈수록 빠르지만 작고 비싸고, 아래로 갈수록 느리지만 크고 쌉니다.

계층속도크기가격전원 꺼지면?

🧠 RAM매우 빠름 (5,000 MB/s+)중간 (GB~수백 GB)중간사라짐
💽 SSD빠름 (500~3,500 MB/s)큼 (수백 GB~TB)저렴유지됨 ✅

왜 굳이 여러 겹으로 나눌까? — 전부 캐시로 만들면 눈이 튀어나올 만큼 비싸고, 전부 HDD로 만들면 너무 느립니다. 그래서 "자주·급하게 쓰는 건 빠른 곳 위쪽에, 어쩌다 쓰는 건 싼 곳 아래쪽에" 나눠 담아 속도와 비용의 균형을 맞추는 겁니다. 이 "빠른 소량 vs 느린 대량"의 트레이드오프는 시스템 디자인 전체를 관통하는 핵심 아이디어예요.

CI/CD 파이프라인 — 코드가 배포되는 자동 컨베이어

컴퓨터 한 대를 봤으니, 이제 실제 서비스(프로덕션 앱)가 어떤 부품들로 이뤄지는지 아주 높은 곳에서 내려다봅시다. 지금은 이름만 눈에 익혀도 충분합니다. 대부분 뒤에서 자세히 다시 다뤄요.

첫 번째 부품은 CI/CD 파이프라인입니다. CI는 지속적 통합(Continuous Integration), CD는 지속적 배포(Continuous Deployment)의 약자예요. 우리가 작성한 코드가 저장소(repository) → 여러 테스트와 검사 → 프로덕션 서버까지, 사람 손 없이 자동으로 흘러가게 해줍니다. Jenkins, GitHub Actions 같은 도구로 구성하죠.

비유 — 공장 컨베이어 벨트: 부품(코드)을 벨트에 올리면 검수 → 조립 → 포장 → 출하가 사람 개입 없이 자동으로 진행됩니다. 중간에 불량(테스트 실패)이 발견되면 벨트가 멈춰 불량품이 매장(프로덕션)에 나가지 않게 막아주죠.

외부 스토리지 & 다른 서비스들

서버는 데이터를 저장해야 합니다. 그런데 이 데이터는 보통 프로덕션 서버와 같은 곳이 아니라, 네트워크로 연결된 별도의 외부 스토리지 서버에 저장합니다. 왜 굳이 떼어 놓을까요? 서버가 하나 죽어도 데이터는 안전하게 남고, 저장 공간과 처리 서버를 따로따로 확장할 수 있기 때문이에요.

또한 우리 서버는 다른 서버(서비스)들과도 통신합니다. 이런 서비스는 하나가 아니라 여러 개일 수 있어요 (결제 서비스, 알림 서비스, 검색 서비스 …). 큰 시스템일수록 이렇게 역할별로 쪼개진 여러 서비스가 서로 대화하며 돌아갑니다.

비유 — 식당과 외부 냉동창고: 주방(서버) 안에 모든 식재료를 쌓아두지 않습니다. 대형 외부 냉동창고(스토리지 서버)를 따로 두고 필요할 때 배송받죠. 주방에 불이 나도 창고의 재료는 무사하고, 주방과 창고를 각자 필요한 만큼 키울 수 있습니다.
📈

로깅 & 모니터링 — 시스템의 CCTV

모든 게 잘 돌아가는지 확인하려면 지켜봐야 합니다. 그래서 로깅(logging)과 모니터링(monitoring) 시스템이 모든 미세한 상호작용을 감시하고, 로그를 저장하고, 데이터를 분석합니다.

  • 로그 저장 위치: 로그는 보통 주 프로덕션 서버 바깥의 외부 서비스에 저장하는 게 표준입니다. (서버가 죽어도 로그는 남아야 원인을 찾을 수 있으니까요.)
  • 백엔드 로깅: pm2 같은 도구로 서버 프로세스를 로깅·모니터링합니다.
  • 프론트엔드 에러: Sentry 같은 플랫폼으로 사용자 화면에서 발생한 에러를 실시간으로 캡처·리포트합니다.
비유 — 매장의 CCTV와 녹화 서버: 매장(서버) 곳곳에 CCTV(모니터링)를 달고, 녹화본(로그)은 매장 밖 별도 건물(외부 로그 저장소)에 보관합니다. 매장에 사고가 나도 녹화본이 남아 있어야 무슨 일이 있었는지 되돌려 볼 수 있으니까요.
🔔

알림 (Alerting) — 문제가 생기면 바로 알려준다

모니터링이 실패한 요청이나 이상 징후를 감지하면, 다음으로 알림 서비스(alerting)가 발동합니다. 그러면 담당자에게 푸시 알림이 날아가요. 알림 내용은 뭉뚱그린 "뭔가 잘못됨"부터 구체적인 "결제 실패"까지 다양합니다.

요즘은 이런 알림을 개발자가 이미 쓰고 있는 도구, 특히 Slack에 바로 꽂아 넣는 게 일반적입니다. 전용 Slack 채널에 문제가 뜨는 순간 알림이 올라오면, 개발자가 거의 즉시 뛰어들어 문제가 커지기 전에 원인을 잡을 수 있죠.

비유 — 화재경보기: CCTV(모니터링)가 연기를 감지하면 경보(알림)가 울립니다. 그것도 사람들이 늘 보고 있는 단톡방(Slack)으로요. 불씨(작은 오류)일 때 알아채야 큰 화재(장애)로 번지지 않습니다.
🐛

디버깅 흐름 — 문제를 잡는 정석 순서

알림을 받은 개발자는 이제 문제를 해결해야 합니다. 정석적인 순서는 이렇습니다.

1
문제 식별 — 앞서 쌓아둔 로그가 첫 번째 단서입니다. 개발자는 로그를 뒤지며 원인을 가리키는 패턴이나 이상 징후를 찾습니다.
2
안전한 곳에서 재현 — 황금률 절대 프로덕션에서 직접 디버깅하지 않습니다. 대신 스테이징/테스트 환경에서 문제를 똑같이 재현해요. 그래야 실제 사용자가 디버깅 과정에 영향받지 않습니다.
3
도구로 관찰하며 디버깅 — 실행 중인 앱 내부를 들여다보는 도구를 써서 원인을 찾아 들어갑니다.
4
핫픽스(hotfix) 배포 — 버그를 고치면 빠른 임시 수정본을 먼저 내보내 서비스를 정상화합니다. 더 완성도 높은 근본 해결책은 그 뒤에 적용해요. (급한 불부터 끄는 패치)
왜 프로덕션에서 디버깅하면 안 될까? 프로덕션은 실제 손님이 밥을 먹고 있는 영업 중인 식당입니다. 그 한복판에서 가스레인지를 뜯어 고치면 손님이 다칩니다. 그래서 똑같이 꾸민 연습용 주방(스테이징)에서 재현하고 고친 뒤, 검증된 수정만 영업장에 반영합니다.
🏛️
Part 3 · 좋은 설계의 기둥

좋은 설계란 무엇인가?

본격적인 기술로 들어가기 전에, "좋은 설계란 무엇인가"를 먼저 정해야 합니다. 목표를 알아야 그쪽으로 설계할 수 있으니까요. 좋은 설계는 크게 세 가지 원칙에 집중합니다.

📈
확장성 (Scalability)
사용자가 늘어나도 시스템이 함께 성장할 수 있는가?
🧱
유지보수성 (Maintainability)
미래의 개발자가 시스템을 이해하고 개선할 수 있는가?
⚙️
효율성 (Efficiency)
자원을 최대한 알뜰하게 쓰고 있는가?
좋은 설계 = "실패까지 대비하는 것"
진짜 좋은 설계는 모든 게 잘 돌아갈 때뿐 아니라, 문제가 터졌을 때도 침착함을 유지합니다. 그래서 "고장 나면 대신할 백업(이중화)"이나 "일부 기능이 죽어도 핵심은 살아 있게(우아한 성능 저하, graceful degradation)" 같은 걸 미리 설계에 넣습니다.
모든 결정에는 트레이드오프(trade-off)가 있다
읽기(read)에 최적화한 시스템은 쓰기(write)가 느려질 수 있고, 성능을 얻으려면 복잡도를 조금 감수해야 할 수도 있습니다. 완벽한 정답은 없습니다. 시스템 디자인은 "우리의 구체적인 상황에 가장 알맞은 답"을 찾는 일이고, 그건 "어디서 무엇을 양보할지"를 현명하게 정하는 것입니다. 이 사고방식을 꼭 기억하세요.
🔄

시스템의 심장 — 데이터의 3요소

시스템 디자인의 한가운데에는 결국 데이터가 있습니다. 그리고 데이터로 하는 일은 크게 세 가지로 나뉩니다.

🚚
1. 데이터 이동 (Moving)
데이터가 시스템의 한 부분에서 다른 부분으로 매끄럽게 흐르게 하는 것. 사용자 요청이 서버로, 서버 데이터가 DB로. 속도와 보안을 최적화합니다.
📦
2. 데이터 저장 (Storing)
단순히 SQL/NoSQL 선택이 아닙니다. 접근 패턴, 인덱싱 전략, 백업까지 이해해서, 안전하게 저장하면서도 필요할 때 바로 꺼낼 수 있게 하는 것.
🔧
3. 데이터 변환 (Transforming)
날것의 데이터(raw data)를 의미 있는 정보로 바꾸는 것. 로그를 모아 분석하거나, 사용자 입력을 다른 형식으로 가공하는 일 등.
비유 — 택배 물류: 데이터를 택배 상자라고 하면 — 이동은 배송(트럭·비행기), 저장은 물류창고 보관(어디에 둬야 빨리 꺼낼까), 변환은 부품을 조립해 완제품으로 만드는 가공이라고 볼 수 있어요. 시스템은 이 세 가지를 끊임없이 반복합니다.
⚖️

CAP 정리 — 셋 중 둘만 고를 수 있다

분산 시스템(여러 대의 컴퓨터가 협력하는 시스템)을 설계할 때 반드시 아는 개념이 CAP 정리(CAP theorem)입니다. 컴퓨터 과학자 에릭 브루어(Eric Brewer)의 이름을 따 브루어 정리라고도 해요. 분산 시스템의 세 가지 핵심 속성 사이에서 현명한 트레이드오프를 하도록 안내하는 원칙입니다.

🟦 C
일관성 (Consistency)
모든 노드가 같은 시각에 같은 데이터를 가집니다. 한 노드를 바꾸면 모든 노드에 즉시 반영돼요.
🟩 A
가용성 (Availability)
뒤에서 무슨 일이 있든 시스템은 항상 동작하고 요청에 응답합니다.
🟨 P
분할내성 (Partition tolerance)
노드 사이 통신이 끊겨도(네트워크 분할) 시스템이 계속 동작합니다.

비유로 이해하기

속성비유
🟦 일관성구글 독스(Google Docs) — 한 명이 수정하면 모두에게 즉시 똑같이 보임
🟩 가용성믿음직한 온라인 상점 — 언제 방문해도 항상 열려 있고 주문을 받아줌
🟨 분할내성단톡방 — 한 명이 연결이 끊겨도 나머지는 계속 대화함
핵심 — 셋 중 둘만! CAP 정리에 따르면 분산 시스템은 세 속성을 동시에 다 가질 수 없고, 최대 두 개만 만족할 수 있습니다. 예를 들어 일관성 + 분할내성을 택하면 가용성을 일부 포기해야 할 수 있어요.
예시 — 은행 시스템: 은행은 돈 계산이 정확해야 하므로 일관성(C) + 분할내성(P)을 택합니다. 그 대가로 어떤 거래는 처리에 시간이 조금 더 걸릴 수 있죠(가용성 일부 희생). "잔액이 잠깐 틀리게 보이는 것"보다 "잠깐 기다리는 것"이 낫기 때문입니다.

👉 CAP은 이 자료 곳곳(가용성, DB 확장 등)에서 계속 등장합니다. "무엇을 양보할지 정하는 게 설계다"라는 Part 3의 메시지를 압축한 정리예요.
🟢
Part 4 · 시스템 품질 지표

가용성 (Availability) — "필요할 때 켜져 있는가?"

시스템의 중요한 측정 지표 중 하나가 가용성(availability)입니다. 시스템의 운영 성능과 신뢰성을 재는 지표로, 본질은 이 질문이에요. "사용자가 필요할 때 우리 시스템이 켜져서 돌아가고 있는가?"

가용성은 보통 백분율(%)로 나타내고, 업계는 이른바 "파이브 나인(5 nines)", 즉 99.999%를 이상적인 목표로 삼습니다. 9가 하나 늘어날 때마다 허용되는 다운타임(downtime, 서비스가 멈춘 시간)이 극적으로 줄어들어요.

가용성별칭연간 허용 다운타임
99%투 나인약 3.65일
99.9%쓰리 나인약 8.76시간
99.99%포 나인약 52분
99.999%파이브 나인 🏆약 5분
9 하나가 이렇게 크다 — 99.9%면 1년에 약 8.76시간이나 서비스가 멈출 수 있습니다. 여기에 9를 두 개 더 붙여 99.999%가 되면 다운타임은 연 약 5분으로 줄어요. 1초가 아쉬운 서비스(결제, 증권 등)에서는 이 차이가 어마어마합니다.

가용성은 흔히 업타임(uptime, 켜져 있던 시간)과 다운타임(downtime)으로 이야기합니다. 그리고 이 목표를 문서로 약속한 것이 바로 다음에 볼 SLO·SLA예요.

📜

SLO vs SLA — 목표와 계약의 차이

가용성 이야기가 나오면 SLO와 SLA가 따라옵니다. 둘 다 "얼마나 잘 서비스할지"를 정하지만, 하나는 스스로 세운 목표이고 다른 하나는 고객과 맺은 계약이라는 점이 다릅니다.

SLO — 서비스 수준 "목표"
Service Level Objective
우리 팀이 스스로 세운 성능·가용성 목표입니다.

예) "웹 서비스는 요청의 99.9%를 300ms 이내에 응답한다."

→ 내부적으로 "이 정도는 지키자"고 정한 다짐/기준선.
SLA — 서비스 수준 "계약"
Service Level Agreement
고객·사용자와 맺는 공식적인 계약입니다. 최소로 보장하는 서비스 수준을 명시해요.

예) "가용성 99.99%를 보장한다. 못 지키면 환불·보상한다."

→ 어기면 실제로 돈이 나가는 약속.
한 줄 정리: SLO는 "우리끼리의 목표", SLA는 "고객과의 계약". 그래서 보통 SLA(계약)보다 SLO(내부 목표)를 더 빡세게 잡아둡니다. 내부 목표를 먼저 못 지키면 경고등이 켜져서, 계약 위반이라는 진짜 사고로 번지기 전에 손을 쓸 수 있으니까요.
🛡️

회복탄력성 — 신뢰성 · 장애내성 · 이중화

시스템에 회복탄력성(resilience)을 넣는다는 건 "예상치 못한 일을 예상하는 것"입니다. 이를 위한 세 가지 개념을 기억하세요.

✅
신뢰성 (Reliability)
시스템이 올바르고 일관되게 동작하는 것. "부르면 항상 제대로 답하는가?"
🧯
장애내성 (Fault Tolerance)
문제에 대비하는 것. 예상치 못한 고장이나 공격을 시스템이 어떻게 견디는가?
👯
이중화 (Redundancy)
백업을 두는 것. 한 부분이 고장 나면 대신할 다른 부분이 준비돼 있는가?
비유 — 비행기의 엔진: 여객기는 엔진이 여러 개(이중화)라, 하나가 꺼져도 나머지로 안전하게 비행합니다(장애내성). 그리고 매 비행마다 흔들림 없이 잘 나는 것(신뢰성)이죠. 좋은 시스템도 똑같이 "하나 고장 나도 괜찮게" 만듭니다.
🏎️

처리량 vs 지연시간 — 시스템의 속도 두 얼굴

시스템의 속도는 두 가지 다른 지표로 잽니다. 이 둘을 헷갈리면 안 돼요.

처리량 (Throughput)
일정 시간에 얼마나 많이 처리할 수 있는가.

🖥️ 서버 처리량 — RPS(초당 요청 수). 동시에 얼마나 많은 사용자를 감당하는지.
🗄️ DB 처리량 — QPS(초당 쿼리 수).
📶 데이터 처리량 — bytes/s (초당 전송 바이트).

→ 값이 클수록 좋음. "한 번에 몇 명?"
지연시간 (Latency)
요청 하나를 처리하는 데 걸리는 시간.

요청을 보내고 응답을 받기까지의 시간이에요.

→ 값이 작을수록 좋음. "한 명이 얼마나 빨리?"
둘은 자주 상충한다 (트레이드오프) — 예를 들어 요청을 모아서 한꺼번에 처리하는 배칭(batching)을 하면 처리량은 올라가지만, 모으는 동안 기다려야 하므로 지연시간은 늘어날 수 있어요. 하나를 최적화하면 다른 하나를 희생하기 쉽습니다.
비유 — 고속도로: 처리량은 "1시간에 지나가는 차의 수"(차선을 넓히면 증가), 지연시간은 "내 차가 이 구간을 통과하는 데 걸린 시간"입니다. 차선을 늘려 처리량을 키워도, 신호가 많으면 내 통과 시간(지연시간)은 그대로일 수 있죠.
왜 설계를 처음부터 잘해야 할까? 코드는 리팩터링으로 쉽게 고치지만, 시스템 재설계는 거대한 작업입니다. 그래서 처음부터 미래의 기능과 사용자 증가를 버틸 탄탄한 기초를 놓는 데 시간을 투자해야 합니다.
📍
Part 5 · 네트워킹 기초

IP 주소 — 인터넷 세상의 집 주소

네트워킹의 핵심은 "컴퓨터들이 서로 어떻게 대화하는가"입니다. 그 대화의 중심에 IP 주소(IP address)가 있어요. IP 주소는 네트워크상 각 기기의 고유 식별자, 즉 인터넷 세상에서의 집 주소입니다.

IPv4IPv6
비트 수32비트128비트
주소 개수약 40억 개사실상 무한에 가까움
예시 모양192.168.0.12001:0db8:85a3::8a2e:0370:7334
왜 IPv6가 등장했을까? IPv4의 약 40억 개 주소는 처음엔 넉넉해 보였지만, 스마트폰·IoT 등 인터넷에 연결되는 기기가 폭증하면서 부족해졌습니다. 그래서 훨씬 더 많은 주소를 담을 수 있는 IPv6(128비트)로 넘어가는 중이에요.
📦

패킷 — 데이터를 잘게 쪼갠 소포

두 컴퓨터가 네트워크로 통신할 때, 데이터를 통째로 보내지 않고 패킷(packet)이라는 작은 조각들로 나눠 주고받습니다. 각 패킷에는 IP 헤더(IP header)가 붙는데, 여기에 보내는 사람과 받는 사람의 IP 주소 같은 필수 정보가 들어 있어 데이터가 정확한 목적지에 도착하도록 합니다.

이 과정을 규정하는 규칙이 인터넷 프로토콜(IP, Internet Protocol)이에요. 그리고 IP 계층 위에는 애플리케이션 계층(application layer)이 있어서, 앱마다 정해진 프로토콜(예: 웹은 HTTP)에 맞춰 데이터가 담깁니다. 그래야 받는 쪽이 내용을 올바르게 해석할 수 있죠.

비유 — 큰 짐을 여러 소포로 나눠 부치기: 큰 이삿짐을 트럭 하나에 다 못 실으면 여러 소포(패킷)로 나눠 부칩니다. 각 소포에는 보내는 이·받는 이 주소(IP 헤더)가 붙어 있어, 서로 다른 길로 가더라도 결국 같은 목적지에 모입니다.
🚚

TCP vs UDP — 꼼꼼한 택배 vs 빠른 전단지

패킷을 실제로 실어 나르는 전송 계층(transport layer)에는 두 가지 대표 프로토콜이 있습니다. TCP와 UDP예요.

TCP — 신뢰성 최우선
확실하고 빠짐없는 배달을 보장합니다.

• 시퀀스 번호로 패킷 순서를 추적
• 3-way handshake로 안정적인 연결을 먼저 수립
• 누락이 있으면 다시 보냄

→ 정확함이 중요한 곳: 웹, 파일 전송, 이메일
UDP — 속도 최우선
TCP보다 빠르지만 덜 신뢰합니다.

• 연결을 미리 맺지 않고 바로 전송
• 전달·순서를 보장하지 않음
• 그래서 오버헤드가 적어 빠름

→ 속도가 중요하고 약간의 손실은 OK: 영상통화, 라이브 스트리밍
비유로 기억하기 — TCP는 "받았는지 서명까지 확인하는 등기 택배 기사". 빠짐없이, 순서대로 배달했는지 하나하나 확인합니다. UDP는 "일단 뿌리고 보는 전단지 배포". 몇 장 못 받아도 신경 안 쓰고 빠르게 많이 돌립니다. 영상통화에서 프레임 몇 개 끊겨도 대화가 이어지는 게 이 방식이에요.
3-way handshake(3방향 악수)란? TCP가 데이터를 보내기 전에 "보낼게(SYN) → 준비됐어(SYN-ACK) → 좋아 시작(ACK)" 3단계로 서로 연결이 준비됐는지 먼저 확인하는 절차입니다. 통화 전에 "여보세요? 들려요? 네 말씀하세요"로 연결을 확인하는 것과 같아요.
📇

  • 레지스트라(Registrar) — 가비아, GoDaddy처럼 ICANN의 인증을 받아 도메인을 판매하는 업체.

포트 & 방화벽 — 건물의 호수와 경비원

공인 IP vs 사설 IP, 그리고 고정 vs 동적

  • 공인 IP(public) — 인터넷 전체에서 고유한 주소. / 사설 IP(private) — 집·회사 같은 로컬 네트워크 안에서만 고유.
  • 고정 IP(static) — 기기에 영구 할당. / 동적 IP(dynamic) — 시간에 따라 바뀜. 가정용 인터넷에서 흔히 사용.

포트 — 한 기기 안의 여러 서비스 구분

한 컴퓨터(IP) 안에서도 여러 프로그램이 동시에 네트워크를 씁니다. 이들을 구분하는 게 포트(port)예요. IP + 포트가 합쳐지면 하나의 고유한 네트워크 서비스 식별자가 됩니다. 일부 포트는 특정 프로토콜용으로 예약돼 있어요.

포트용도
80HTTP (웹)
443HTTPS (암호화된 웹)
22SSH (원격 접속)

그리고 이 네트워크를 지키기 위해 방화벽(firewall)을 둡니다. 방화벽은 들어오고 나가는 네트워크 트래픽을 감시·통제하는 문지기예요.

비유 — 아파트 건물: IP 주소는 건물 주소, 포트는 그 안의 호수(101호, 202호…)입니다. "OO아파트 80호"처럼 IP+포트가 있어야 정확한 집(서비스)에 도착하죠. 방화벽은 건물 입구의 경비원으로, 수상한 사람(트래픽)의 출입을 막습니다.

Part 6 · 애플리케이션 계층 프로토콜

HTTP — 웹의 기본 대화 규칙

가장 흔한 애플리케이션 계층 프로토콜은 HTTP(HyperText Transfer Protocol)입니다. 앞서 본 TCP/IP 위에서 동작하며, 요청(request)-응답(response) 방식으로 대화해요.

HTTP는 "기억이 없는" 대화 (Stateless)
HTTP를 기억력이 없는 대화라고 생각하세요. 각 상호작용은 서로 독립적이고, 과거를 기억하지 않습니다. 그래서 서버는 요청 사이의 맥락을 저장할 필요가 없어요. 대신 각 요청이 필요한 정보를 전부 스스로 담고 옵니다.

요청과 응답은 헤더(header)와 바디(body)로 나뉩니다. 헤더에는 URL·메서드(Method) 같은 정보가, 바디에는 실제 내용물이 담겨요.

http
POST /api/products HTTP/1.1
Host: shop.example.com
Content-Type: application/json     ← 헤더 (부가 정보)

{                                   ← 바디 (실제 내용물)
  "name": "무선 키보드",
  "price": 39000
}
🔢

상태 코드 & 메서드 — 응답의 결과와 요청의 의도

상태 코드 (Status Code) — "요청이 어떻게 됐나?"

모든 응답에는 상태 코드가 붙어, 클라이언트의 요청이 서버에서 어떻게 처리됐는지 알려줍니다. 백의 자리 숫자로 대분류를 기억하세요.

코드대의미대표 예시
2xx성공 — 요청이 잘 처리됨200 OK, 201 Created
3xx리다이렉션 — 추가 동작 필요(다른 곳으로)301 Moved, 304 Not Modified
4xx클라이언트 오류 — 요청이 잘못됨400 Bad Request, 404 Not Found
5xx서버 오류 — 서버에서 문제 발생500 Internal Server Error

메서드 (Method) — "무엇을 하고 싶은가?"

각 요청에는 메서드가 있어 의도를 나타냅니다.

메서드용도
GET데이터 조회 (가져오기)
POST데이터 생성 (서버에 새로 만들기)
PUT / PATCH데이터 수정 (기존 레코드 갱신)
DELETE데이터 삭제 (레코드 제거)

WebSocket — 끊기지 않는 양방향 대화

HTTP는 기본적으로 한 방향(요청하면 응답) 연결입니다. 하지만 실시간 업데이트가 필요하면 어떻게 할까요? 이때 WebSocket(웹소켓)을 씁니다. WebSocket은 하나의 오래 유지되는 연결 위에서 양방향(two-way) 통신을 제공해, 서버가 클라이언트에게 실시간으로 데이터를 밀어 넣을(push) 수 있어요.

HTTP (요청-응답)
클라이언트가 물어봐야만 서버가 답합니다.
"새 메시지 있어?" → "없어" → "지금은?" → "없어" …

→ 실시간엔 비효율적 (계속 물어봐야 함)
WebSocket (양방향)
연결을 한 번 열어두면 서버가 알아서 밀어줍니다.
(조용히 대기) → 서버: "새 메시지 도착!" → 즉시 표시

→ 채팅, 실시간 스포츠 중계, 주식 시세에 딱
비유 — HTTP는 편지(보내야 답장이 옴), WebSocket은 전화 통화(연결을 열어두고 양쪽이 아무 때나 말함)입니다. 반복해서 "왔어? 왔어?"를 묻는 HTTP 요청-응답의 오버헤드 없이, 끊임없이 오는 업데이트를 실시간으로 주고받을 수 있죠.
✉️

이메일 프로토콜 — 보내기와 받기

이메일에는 보내는 프로토콜과 받는(가져오는) 프로토콜이 따로 있습니다.

📤
SMTP — 보내기
인터넷에서 이메일 전송의 표준. 서버 사이에서 메일을 보낼 때 사용. 대부분의 메일 클라이언트가 발송에 SMTP를 씀.
📥
IMAP — 받기(동기화)
서버에서 메일을 가져와 열람·관리. 메일이 서버에 남아 있어 여러 기기에서 접근하기 좋음.
📩
POP3 — 받기(내려받기)
서버에서 로컬로 메일을 다운로드. 보통 한 기기에서만 메일을 관리할 때 사용.
IMAP vs POP3 한 줄 구분: 폰·노트북 등 여러 기기에서 같은 메일함을 보고 싶으면 IMAP(서버에 원본 유지), 한 기기로만 받아서 관리하면 POP3(내려받아 보관)라고 기억하세요.
🧰

기타 주요 프로토콜 — 파일 · 원격접속 · 실시간 · 메시징

프로토콜한 줄 설명대표 용도
FTP클라이언트-서버 간 파일 전송의 전통적 프로토콜웹사이트 관리, 대용량 파일 전송·백업
SSH안전하지 않은 네트워크에서 안전하게 원격 접속·명령 실행원격 서버 로그인, 명령 실행, 파일 전송
WebRTC플러그인 없이 브라우저 간 음성·영상·파일 공유화상회의, 라이브 스트리밍
MQTT가벼운 메시징. 저사양·저대역폭 환경에 적합IoT 기기
AMQP견고하고 안전한 메시지 지향 미들웨어 프로토콜엔터프라이즈 메시징(예: RabbitMQ)
이걸 전부 외울 필요는 없습니다. "상황마다 최적화된 전용 프로토콜이 따로 있다"는 감만 잡으세요. 파일은 FTP, 원격 접속은 SSH, 실시간 미디어는 WebRTC, IoT 메시징은 MQTT처럼요.
📞

RPC — 남의 컴퓨터 함수를 내 함수처럼 부르기

RPC(Remote Procedure Call, 원격 프로시저 호출)는 한 컴퓨터의 프로그램이 다른 컴퓨터(서버)의 코드를 실행하게 해주는 프로토콜입니다. 마치 로컬 함수를 호출하듯 함수를 부르지만, 실제로는 그 함수가 원격 기계에서 실행돼요.

RPC는 네트워크 통신의 세부사항을 감춰(추상화), 개발자가 원격 함수를 마치 내 앱 안의 로컬 함수처럼 다루게 해줍니다. 실제로 많은 애플리케이션 계층 프로토콜이 내부적으로 RPC 방식을 씁니다. (예: 웹 서비스의 HTTP 요청이 백엔드에서 RPC 호출을 유발하기도 합니다.)

비유 — 리모컨: 내 손의 리모컨 버튼(로컬 함수 호출)을 누르면, 실제 동작은 저 멀리 있는 TV(원격 서버)에서 일어납니다. 중간에 적외선 신호가 어떻게 오가는지(네트워크 통신)는 몰라도 되죠. RPC가 그 복잡함을 감춰 줍니다.
✏️
Part 7 · API 설계

CRUD — API가 하는 네 가지 기본 동작

API 설계는 "우리 서비스가 어떤 입력을 받고 어떤 출력을 주는지"를 정하는 일입니다. 예를 들어 쇼핑몰(Shopify 같은 e-커머스)의 상품 API라면, 입력은 판매자가 넣는 상품 정보, 출력은 누군가 상품을 조회할 때 돌려주는 정보가 되겠죠.

대부분의 데이터 기반 앱은 CRUD라는 네 가지 기본 동작으로 이뤄집니다.

동작메서드 & 엔드포인트설명
Create (생성)POST /api/products바디에 상품 정보를 담아 새로 추가
Read (조회)GET /api/products상품 목록을 가져옴
Read (단건)GET /api/products/{id}특정 상품 하나를 가져옴
Update (수정)PUT/PATCH /api/products/{id}해당 상품 정보를 갱신
Delete (삭제)DELETE /api/products/{id}해당 상품을 제거

이 밖에도 통신 프로토콜(HTTP, WebSocket 등)과 데이터 전송 형식(JSON, XML, Protocol Buffers)을 함께 정합니다. 아래에서 볼 API 패러다임이 이 선택들을 크게 좌우해요.

🔀

REST vs GraphQL vs gRPC — 3가지 API 패러다임

API를 만드는 방식(패러다임)은 여러 가지이고, 각자 장단점이 다릅니다. 가장 널리 쓰이는 세 가지를 비교해 봅시다.

REST
가장 흔한 방식. Representational State Transfer.

• 무상태(stateless) — 각 요청이 필요한 정보를 다 담음
• 표준 HTTP 메서드(GET/POST/…) 사용
• 브라우저·모바일 등 어디서나 쉽게 소비
• 보통 JSON으로 주고받음

단점 필요한 데이터를 위해 여러 엔드포인트가 필요해 over/under-fetching 발생
GraphQL
필요한 것만 콕 집어 요청.

• 클라이언트가 원하는 필드만 요청 → over/under-fetching 회피
• 강타입(strongly typed) 쿼리
• 모든 요청이 POST
• 에러가 나도 보통 HTTP 200으로 응답(에러는 바디에)

단점 복잡한 쿼리는 서버 부하를 키울 수 있음
gRPC
Google Remote Procedure Call.

• HTTP/2 기반(멀티플렉싱, 서버 푸시)
• Protocol Buffers로 데이터 직렬화 → 대역폭·자원 효율적
• 마이크로서비스에 특히 적합

단점 JSON보다 사람이 읽기 어렵고, HTTP/2 지원이 필요
over-fetching / under-fetching이 뭐예요? — over-fetching은 이름만 필요한데 프로필 전체가 딸려 와 불필요하게 많이 받는 것, under-fetching은 한 화면을 채우려고 여러 번 요청해야 하는 것입니다. GraphQL은 "필요한 필드만" 요청해 이 둘을 동시에 해결하려는 시도예요.

관계 & 엔드포인트 — 데이터의 연결을 URL로 표현

실제 서비스의 데이터는 서로 관계가 있습니다. 예를 들어 사용자 → 주문들, 주문 → 상품들처럼요. 이 관계를 중첩된 엔드포인트로 표현합니다. 특정 사용자의 주문 목록을 원한다면:

http
GET /users/{userId}/orders          ← 이 사용자의 주문 목록

GET /products?limit=20&offset=40    ← 페이지네이션 (20개씩, 40번째부터)
GET /products?start=2026-01-01&end=2026-06-30   ← 날짜로 필터링

이렇게 limit / offset으로 페이지네이션(한 번에 조금씩 나눠 조회)을 하거나, start / end 같은 조건으로 필터링을 합니다. 덕분에 사용자는 시스템을 압도하지 않고 원하는 데이터만 골라 받을 수 있어요.

✅

API 모범 사례 — 멱등성 · 버저닝 · Rate Limit · CORS

멱등성 (Idempotency)

잘 설계된 GET 요청은 멱등(idempotent)해야 합니다. 즉 여러 번 호출해도 결과가 바뀌지 않고 항상 같은 답을 줘야 하고, 절대 데이터를 변경하지 않아야 합니다. GET은 오직 조회용이에요. 데이터를 만들거나 바꾸려면 POST / PUT을 써야 합니다.

버저닝 (Versioning) — 하위 호환성 지키기

엔드포인트를 수정할 때는 기존 클라이언트가 깨지지 않도록(하위 호환성) 해야 합니다. 흔한 방법은 새 버전을 도입하는 것이에요.

  • REST: /v2/products처럼 새 버전을 만들어, v1은 옛 클라이언트를 계속 지원하고 v2가 최신 클라이언트를 담당.
  • GraphQL: 기존 필드를 지우지 않고 새 필드를 추가해, 기존 클라이언트를 깨지 않으면서 API를 발전시킴.

Rate Limiting (요청 제한)

일정 시간 동안 한 사용자가 보낼 수 있는 요청 수를 제한합니다. 한 사용자가 API에 요청을 지나치게 많이 퍼붓는 것을 막아, DoS 공격 같은 위협을 방어해요.

CORS (교차 출처 리소스 공유)

어떤 도메인이 우리 API에 접근할 수 있는지를 제어하는 설정입니다. 원치 않는 교차 사이트(cross-site) 접근을 막아줍니다.

비유로 묶어보기 — 멱등성은 "엘리베이터 버튼을 여러 번 눌러도 한 번 부른 것과 같음", 버저닝은 "옛 손님용 메뉴판을 없애지 않고 새 메뉴판을 추가", Rate Limit은 "1인당 시식 코너 3개까지", CORS는 "우리 매장에 들어올 수 있는 손님 명단"이라고 생각하면 쉽습니다.

Part 8 · 캐싱 & CDN

캐싱이란? — 멀리 있는 데이터를 가까이

한 회사가 웹사이트를 핀란드의 구글 클라우드 데이터센터에 두고 있다고 해봅시다. 유럽 사용자에겐 약 100ms면 로드되지만, 멕시코 사용자에겐 3~5초나 걸릴 수 있어요. 물리적으로 멀기 때문이죠. 이런 먼 거리 사용자의 지연시간을 줄이는 대표 전략이 캐싱(caching)과 CDN입니다.

캐싱의 정의 — 데이터의 복사본을 임시 저장소에 두어서, 이후에 같은 데이터를 요청하면 더 빠르게 돌려주는 기법입니다. (Part 1의 CPU 캐시와 원리가 똑같아요. "자주 쓰는 걸 가까이 둔다.")
📍

캐시가 사는 곳 — 4가지 위치

캐시는 흔히 네 군데에 둡니다. 사용자와 가까운 쪽부터 볼게요.

🖥️
1. 브라우저 캐시
웹사이트 리소스(HTML·CSS·JS 번들 등)를 사용자 로컬 컴퓨터에 저장. 재방문 시 서버에서 다시 안 받고 로컬에서 로드. 개발자 도구(예: Chrome Network 탭 "Disable cache")로 끌 수 있음.
🗄️
2. 서버 캐시
자주 접근하는 데이터를 서버 쪽에 저장해 비싼 작업(DB 쿼리 등)을 줄임. Redis 같은 인메모리 저장소나 디스크에 둠.
💾
3. DB 캐시
쿼리 결과를 캐싱. DB 시스템 자체 안에서 하거나 Redis·Memcached 같은 외부 캐시 계층으로. 읽기 위주 앱에서 효과적.
🌍
4. CDN
지리적으로 분산된 서버망에 정적 콘텐츠를 캐싱. (바로 아래에서 자세히!)

캐시 유효기간은 Cache-Control 헤더로 지정합니다. 예를 들어 Cache-Control: max-age=7200은 "이 콘텐츠를 7,200초(=2시간) 동안 캐싱하라"는 뜻이에요.

Cache Hit / Miss / Ratio — 캐시가 잘 되고 있나?

용어의미
Cache Hit ⚡요청한 데이터가 캐시에 있음 → 빠르게 반환
Cache Miss캐시에 없어서 원본(DB 등)에서 다시 가져와야 함
Cache Ratio전체 요청 중 캐시로 처리된 비율. 높을수록 캐시가 효과적
응답의 X-Cache 헤더를 보면 캐시 적중 여부를 알 수 있습니다. 예를 들어 X-Cache: MISS면 캐시에 없어서 원본을 다녀온 것, HIT이면 캐시에서 바로 준 것이에요.
✍️

쓰기(Write) 정책 — 캐시와 저장소에 어떻게 쓸까

데이터를 쓸 때 캐시와 영구 저장소(DB)에 어떤 순서로 반영할지에 따라 세 가지 정책이 있습니다.

↪️
Write-Around
캐시를 건너뛰고 영구 저장소에 바로 씀. 쓰기 성능이 덜 중요할 때 사용.
➡️
Write-Through
캐시와 영구 저장소에 동시에 씀. 일관성이 좋지만 write-around보다 느릴 수 있음.
🔙
Write-Back
캐시에 먼저 쓰고, 나중에 영구 저장소에 반영. 쓰기 성능은 좋지만 서버 크래시 시 데이터 손실 위험.
여기서도 트레이드오프가 보이죠? write-back은 빠르지만 위험하고, write-through는 안전하지만 느립니다. "우리 서비스는 속도가 중요한가, 데이터 안전이 중요한가?"에 따라 고릅니다. (Part 3의 트레이드오프 사고방식!)
🧹

제거(Eviction) 정책 — 캐시가 꽉 차면 무엇을 버릴까

캐시는 작기 때문에 꽉 차면 공간을 비워야 합니다. 이때 "무엇을 버릴지" 정하는 규칙이 eviction(제거) 정책이에요.

정책버리는 기준기억법
LRU (Least Recently Used)가장 오랫동안 안 쓴 것"오래 안 봤으니 빼자"
FIFO (First In First Out)가장 먼저 들어온 것"먼저 온 순서대로 빼자"
LFU (Least Frequently Used)가장 드물게 쓴 것"제일 안 쓰니 빼자"

참고로 서버·DB 캐시도 이 동일한 eviction 정책들을 사용합니다.

🌍

CDN — 전 세계에 뿌려둔 '동네 지점'

CDN(Content Delivery Network)은 지리적으로 분산된 서버들의 네트워크입니다. 주로 정적 콘텐츠(JavaScript·HTML·CSS·이미지·영상 파일)를 제공하는 데 씁니다. 원본 서버의 콘텐츠를 미리 받아 두고, 사용자에게는 가장 가까운 CDN 서버에서 전달해요.

Pull 방식 vs Push 방식

Pull 기반 CDN
사용자가 처음 요청할 때 CDN이 원본 서버에서 콘텐츠를 자동으로 당겨와(pull) 캐싱.

→ 정적 콘텐츠가 많고 자주 갱신되는 사이트에 적합. CDN이 알아서 최신화하므로 관리가 덜 필요.

→ 큰 파일인데 자주 안 바뀌지만 갱신 시 빠르게 퍼뜨려야 할 때 적합. 무엇을 올릴지 직접 관리해야 함.
CDN·캐싱의 이점 — ① 지연시간↓(가까운 곳에서 제공) ② 고가용성·확장성(높은 트래픽·하드웨어 장애에 강함) ③ 보안(DDoS 방어, 트래픽 암호화 등) ④ 원본 서버 부하↓. 단, 동적 콘텐츠나 실시간 처리·복잡한 서버 로직이 필요한 요청은 여전히 원본 서버를 거쳐야 합니다.

Part 9 · 프록시 서버

프록시란? — 사이에 낀 중개자

프록시 서버(proxy server)는 리소스를 요청하는 클라이언트와 그 리소스를 주는 서버 사이에 낀 중개자입니다. 요청을 받아 적절한 서버에 전달하고, 서버의 응답을 다시 클라이언트에 돌려줘요. 그 과정에서 캐싱, 익명화(IP 숨김), 로드밸런싱 같은 여러 역할을 합니다.

프록시에는 여러 종류가 있지만, 실무에서 가장 중요한 건 Forward Proxy(포워드)와 Reverse Proxy(리버스) 두 가지예요. 나머지는 아래 표로 가볍게 훑고 넘어가면 됩니다.

종류한 줄 설명
Forward Proxy클라이언트 앞에 서서 대신 요청 (내부망의 인터넷 접근 통제 등)
Reverse Proxy서버 앞에 서서 요청을 가로챔 (로드밸런싱·보안 계층)
Transparent Proxy요청을 수정하지 않고 통과. 클라이언트에게 보임. 캐싱·콘텐츠 필터링
Anonymous / Elite Proxy클라이언트의 실제 IP를 숨겨 익명 브라우징 (Elite는 프록시 사용 자체를 감춤)
➡️

Forward Proxy — 클라이언트 편에 서는 프록시

포워드 프록시는 클라이언트(내부망 컴퓨터 등)와 외부 서버(인터넷 웹사이트) 사이에 낍니다. 클라이언트가 요청을 보내면 먼저 포워드 프록시로 가고, 프록시가 규칙에 따라 허용·수정·차단을 결정한 뒤 대신 요청을 보냅니다. 이때 목표 서버 입장에서는 요청이 프록시에서 온 것처럼 보여 클라이언트의 실제 IP가 가려집니다.

대표 활용 사례

  • 인터넷 사용 통제·모니터링 — 회사가 업무 무관 사이트를 차단하거나, 들어오는 콘텐츠의 바이러스·악성코드를 검사.
  • 자주 쓰는 콘텐츠 캐싱 — 인기 사이트를 캐싱해 대역폭을 아끼고 속도를 높임(대역폭이 비싼 망에서 특히 유용).
  • 익명 웹 접근 — 실제 IP·신원을 숨겨 웹사이트가 사용자를 추적하기 어렵게 함. (예: 여러 계정을 관리하는 "인스타그램 프록시")
⬅️

Reverse Proxy — 서버 편에 서는 프록시

리버스 프록시는 반대로 하나 이상의 웹 서버 앞에 서서, 클라이언트 요청이 서버에 닿기 전에 가로챕니다. 포워드 프록시가 클라이언트를 숨긴다면, 리버스 프록시는 서버의 정체(그리고 서버가 여러 대라는 사실)를 숨깁니다. 클라이언트는 오직 리버스 프록시하고만 대화하고, 뒤에 서버가 몇 대 있는지 몰라도 돼요.

Part 10 · 로드 밸런서

로드 밸런서란? — 트래픽 배차 담당

로드 밸런서(load balancer)는 앞서 본 프록시 서버의 가장 대표적인 활용입니다. 들어오는 트래픽을 여러 서버에 나눠주어, 어느 한 서버도 과부하되지 않게 합니다. 요청을 효과적으로 분산해 애플리케이션의 수용력(capacity)과 신뢰성을 함께 끌어올리죠.

비유 — 대형 마트 계산대: 손님(요청)이 한 계산대(서버)에만 몰리면 줄이 끝없이 길어집니다. 안내 직원(로드 밸런서)이 "3번 계산대 비었어요!"라며 손님을 여러 계산대에 고르게 보내면, 전체가 훨씬 빨리 처리됩니다.
🧮

분산 알고리즘 — 어느 서버로 보낼지 정하는 법

"들어온 요청을 어느 서버로 보낼까?"를 정하는 규칙이 로드 밸런싱 알고리즘입니다. 대표적인 것들을 봅시다.

알고리즘동작 방식적합한 상황
Round Robin
(라운드 로빈)		서버에 순서대로 돌아가며 배정. 마지막 서버 다음엔 다시 처음으로.서버 스펙이 비슷하고 부하가 균등할 때
Least Connections
(최소 연결)		활성 연결이 가장 적은 서버로 보냄.작업이 길거나 부하가 고르지 않을 때
Least Response Time
(최소 응답시간)		응답이 가장 빠르고 연결이 적은 서버로.가장 빠른 응답이 목표일 때
IP Hashing
(IP 해싱)		클라이언트 IP를 해시해 서버를 결정. 같은 클라이언트는 항상 같은 서버로.세션 지속성(같은 서버 유지)이 필요할 때
Weighted
(가중치)		서버 성능에 따라 가중치를 줘, 강한 서버가 더 많은 요청을 처리. (가중 라운드 로빈 등)서버들의 CPU·RAM이 제각각일 때
Geographic
(지리적)		사용자와 지리적으로 가까운 서버로 보냄.글로벌 서비스, 지연시간 최소화가 우선일 때
Consistent Hashing
(일관된 해싱)		해시 링(ring) 위에 노드와 데이터를 함께 해시해 배치. 같은 키는 같은 서버로 일관되게 감.서버 추가·제거가 잦아도 매핑을 안정적으로 유지할 때
왜 "세션 지속성(같은 서버 유지)"이 필요할까? 어떤 서버가 특정 사용자의 로그인 상태 등을 메모리에 들고 있으면, 그 사용자의 다음 요청도 같은 서버로 가야 상태가 유지됩니다. IP 해싱·일관된 해싱이 바로 이걸 보장해 줘요.

헬스 체크 & 로드 밸런서의 종류

헬스 체크 (Health Check)

로드 밸런서의 필수 기능은 서버들의 지속적인 상태 점검(health checking)입니다. 온라인이고 정상 응답하는 서버로만 트래픽을 보내기 위해서예요. 어떤 서버가 죽으면 로드 밸런서는 그 서버가 다시 살아날 때까지 트래픽을 보내지 않습니다.

어떤 형태로 존재하나

🔩
하드웨어 LB
전용 장비. 고성능·다기능. F5 BIG-IP, Citrix(구 NetScaler).
💿
소프트웨어 LB
소프트웨어로 구현. HAProxy(오픈소스), Nginx(웹서버 겸 LB·리버스 프록시).
☁️
클라우드 LB
클라우드 관리형. AWS ELB, Azure Load Balancer, GCP Load Balancer.
🛡️

로드 밸런서가 죽으면? — 단일 장애점 대응

로드 밸런서는 강력하지만 한 가지 함정이 있습니다. 모든 트래픽이 그곳을 통과하므로, 로드 밸런서 자체가 죽으면 뒤의 서버가 아무리 멀쩡해도 클라이언트는 아무 서버에도 닿지 못합니다. 이렇게 "혼자 죽으면 전체가 마비되는 지점"을 단일 장애점(SPOF, Single Point of Failure)이라고 해요.

로드 밸런서 = 잠재적 단일 장애점. 교통정리를 하던 유일한 경찰이 쓰러지면, 차선이 몇 개든 교차로 전체가 멈춰버리는 것과 같습니다.

대응 전략

1
이중 로드 밸런서 (Redundant LB) — 로드 밸런서를 쌍(pair)으로 둡니다. 하나가 죽으면 다른 하나가 넘겨받아요. 이 전환을 페일오버(failover)라고 합니다.
2
LB 자체 모니터링·헬스체크 — 로드 밸런서의 상태도 계속 지켜봐, 문제를 사고로 번지기 전에 조기에 잡습니다.
3
오토스케일링·셀프힐링 — 현대 인프라는 로드 밸런서의 장애를 자동으로 감지하고, 사람 개입 없이 새 인스턴스로 교체합니다.
4
DNS 페일오버 — 더 이상 연결을 받지 않는 IP(죽은 LB)에서 미리 준비한 대기(standby) IP(새 LB)로 트래픽을 다시 라우팅합니다.

Part 11 · 데이터베이스

데이터베이스 종류 — 상황마다 다른 그릇

데이터베이스는 종류마다 잘하는 일이 다릅니다. 크게 세 부류를 봅시다.

🗄️
관계형 (SQL)
잘 정리된 서류함. 모든 파일이 서랍·폴더로 깔끔히 분류됨. PostgreSQL·MySQL·SQLite. 테이블에 저장하고 SQL로 질의. 트랜잭션·복잡 쿼리·무결성에 강함. ACID 준수.
🧩
NoSQL
포스트잇 보드. 자유롭게 붙이고 뗌(유연). MongoDB·Cassandra·Redis. key-value, document, graph 등 종류 다양. 스키마가 없어 테이블 간 외래키로 엮지 않음. 비정형 데이터·확장성·빠른 반복에 좋음.
🧠
인메모리 (In-memory)
빠른 계산용 화이트보드. 모든 게 메모리에 있어 번개처럼 빠름. Redis·Memcached. 주로 캐싱·세션 저장에 사용.
NoSQL의 종류 예시 — key-value(Redis), document(MongoDB), graph(Neo4j). "정형·엄격 = SQL", "유연·자유 = NoSQL", "초고속 임시 = 인메모리"로 큰 그림을 잡으세요.
🔒

ACID — 관계형 DB가 지키는 4가지 약속

관계형 DB는 ACID라는 성질을 지킵니다. 신뢰할 수 있는 데이터 처리를 위한 네 가지 약속이에요. (NoSQL은 확장성을 위해 이 중 일관성(C)을 완화하곤 합니다.)

글자이름의미
A원자성 (Atomicity)트랜잭션은 전부 되거나 전부 안 되거나. 중간까지만 반영되는 일은 없음.
C일관성 (Consistency)트랜잭션이 끝나면 DB는 항상 일관된 상태여야 함.
I격리성 (Isolation)동시에 실행되는 트랜잭션들은 서로 독립적이어야 함.
D지속성 (Durability)한 번 커밋(commit)된 데이터는 (장애가 나도) 사라지지 않고 유지됨.
비유 — 계좌 이체: A가 B에게 만 원을 보낼 때, "A에서 만 원 빠짐 + B에 만 원 들어옴"은 둘 다 되거나 둘 다 안 돼야 합니다(원자성). A에서만 빠지고 B에 안 들어오면 큰일이죠. 은행이 SQL·ACID를 쓰는 이유가 바로 이겁니다.
📈

DB 확장 — 수직(scale up) vs 수평(scale out)

데이터가 늘어 DB가 버거워지면 확장(scaling)해야 합니다. 방법은 두 가지예요.

⬆️ 수직 확장 (Scale Up)
DB가 도는 서버 한 대의 성능을 끌어올림.

• CPU 늘리기 • RAM 키우기
• 더 빠른 디스크 • 네트워크 업그레이드

한계 한 대에 넣을 수 있는 자원엔 물리적 상한이 있어 매우 제한적.
➡️ 수평 확장 (Scale Out)
머신을 여러 대로 늘려 기존 자원 풀에 추가.

데이터를 여러 머신에 분산합니다. 방법은 두 가지:
• 샤딩(sharding)
• 복제(replication)

장점 이론상 거의 무제한으로 확장.
Part 4에서 본 서버 확장과 완전히 같은 개념입니다. "한 대를 강하게(수직)" vs "여러 대로 나누기(수평)". DB에서는 그 "나누기"를 샤딩·복제로 구현해요. 바로 아래에서 봅니다.
🍰

샤딩 & 복제 — 나누기와 복사하기

🍰 샤딩 (Sharding) — 데이터를 조각내 나누기

샤딩은 데이터셋을 여러 조각(shard)으로 나눠 여러 서버에 분산하는 것입니다. 데이터를 작은 덩어리로 쪼개 서버마다 다른 부분을 맡깁니다.

users 테이블을 이름 첫 글자로 샤딩한 예
샤드담당 범위저장 서버
Shard 1A ~ HDB 서버 #1
Shard 2I ~ PDB 서버 #2
Shard 3Q ~ ZDB 서버 #3
  • 범위 기반(range-based) — 특정 키의 범위로 나눔 (예: 이름 A~H는 1번, I~P는 2번…).
  • 디렉터리 기반(directory-based) — 룩업 서비스(주소록)가 "이 데이터는 몇 번 DB에 있다"고 알려줘 그리로 보냄.
  • 지리 기반(geographic) — 지역별로 DB를 나눔 (한국 사용자 데이터는 한국 DB에).

👯 복제 (Replication) — 데이터를 복사해 여러 곳에

복제는 같은 데이터의 복사본을 여러 서버에 두어 고가용성을 얻는 방법입니다.

Master-Slave 복제
Master 1대(쓰기 담당) + 여러 Slave(읽기 전용).

쓰기는 Master로, 읽기는 여러 Slave가 나눠 처리 → 읽기 부하 분산에 유리.
Master-Master 복제
여러 DB가 모두 읽기·쓰기를 다 할 수 있음.

쓰기 지점이 여러 곳이라 유연하지만, 서로 충돌을 맞추는 처리가 더 복잡해짐.
샤딩 vs 복제 한 줄 구분 — 샤딩은 "나누기"(서버마다 다른 데이터 → 용량·쓰기 분산), 복제는 "복사"(서버마다 같은 데이터 → 가용성·읽기 분산)입니다. 실무에선 둘을 함께 쓰기도 해요.

DB 성능 기법 — 더 빠르게 접근하기

확장이 "더 많이 감당하기"라면, 성능 기법은 "더 빨리 꺼내기"입니다. 대표적인 세 가지를 봅시다.

⚡
1. 캐싱
Redis 같은 인메모리 DB로 자주 실행되는 쿼리 결과를 캐싱해 성능을 높임. (Part 8 그대로!)
🔖
2. 인덱싱
자주 조회하는 컬럼에 인덱스를 만들면 조회 속도가 크게 빨라짐.
🔧
3. 쿼리 최적화
JOIN을 최소화하고, EXPLAIN 같은 도구로 쿼리 성능을 분석해 개선.
인덱스가 뭐예요? — 500쪽짜리 책에서 특정 단어를 찾을 때 1쪽부터 다 읽으면 느리죠. 하지만 책 뒤 '찾아보기(색인)'를 보면 "그 단어 … 321쪽"이라고 바로 알려줍니다. DB 인덱스도 똑같이, 자주 찾는 컬럼에 미리 색인을 만들어 조회를 훨씬 빠르게 합니다.
sql
-- email 컬럼으로 자주 조회한다면, 인덱스를 만들어 두면 빨라진다
CREATE INDEX idx_users_email ON users (email);

-- 쿼리가 어떻게 실행되는지(인덱스를 타는지) 확인
EXPLAIN SELECT * FROM users WHERE email = 'kim@example.com';
🎓 마지막으로 — 항상 CAP 정리를 떠올리세요. 어떤 시스템을 설계하든 일관성 · 가용성 · 분할내성 중 둘만 가질 수 있습니다. 면접에서 주어진 요구사항에 따라 "우리는 이 둘을 우선한다"고 근거를 대며 고르는 것 — 그게 바로 시스템 디자인의 핵심입니다. 완벽한 정답을 찾는 게 아니라, 우리 상황에 맞는 최선의 트레이드오프를 고르는 것이죠.
