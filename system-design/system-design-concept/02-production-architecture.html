CI/CD 파이프라인 — 코드가 배포되는 자동 컨베이어

컴퓨터 한 대를 봤으니, 이제 실제 서비스(프로덕션 앱)가 어떤 부품들로 이뤄지는지 아주 높은 곳에서 내려다봅시다. 지금은 이름만 눈에 익혀도 충분합니다. 대부분 뒤에서 자세히 다시 다뤄요.

먼저 전체 그림 한 장

프로덕션 서비스에는 세 갈래의 흐름이 있습니다. 코드가 서버로 가는 길, 사용자 요청이 서버로 오는 길, 그리고 서버를 곁에서 지켜보는 장치들이에요. 이 Part는 이 순서 그대로 따라갑니다.

첫 번째 부품은 CI/CD 파이프라인입니다. CI는 지속적 통합(Continuous Integration), CD는 지속적 배포(Continuous Deployment)의 약자예요. 우리가 작성한 코드가 저장소(repository) → 여러 테스트와 검사 → 프로덕션 서버까지, 사람 손 없이 자동으로 흘러가게 해줍니다. Jenkins, GitHub Actions 같은 도구로 구성하죠.

비유 — 공장 컨베이어 벨트: 부품(코드)을 벨트에 올리면 검수 → 조립 → 포장 → 출하가 사람 개입 없이 자동으로 진행됩니다. 중간에 불량(테스트 실패)이 발견되면 벨트가 멈춰 불량품이 매장(프로덕션)에 나가지 않게 막아주죠.

로드밸런서 & 리버스 프록시 — 요청 교통정리

앱이 프로덕션에 올라가면 이제 수많은 사용자 요청을 감당해야 합니다. 이걸 담당하는 게 로드밸런서(load balancer)와 리버스 프록시(reverse proxy, 예: nginx)예요. 이들은 사용자 요청을 여러 서버에 고르게 나눠주어, 트래픽이 갑자기 몰려도 서비스가 매끄럽게 유지되도록 합니다.

외부 스토리지 & 다른 서비스들

서버는 데이터를 저장해야 합니다. 그런데 이 데이터는 보통 프로덕션 서버와 같은 곳이 아니라, 네트워크로 연결된 별도의 외부 스토리지 서버에 저장합니다. 왜 굳이 떼어 놓을까요? 서버가 하나 죽어도 데이터는 안전하게 남고, 저장 공간과 처리 서버를 따로따로 확장할 수 있기 때문이에요.

또한 우리 서버는 다른 서버(서비스)들과도 통신합니다. 이런 서비스는 하나가 아니라 여러 개일 수 있어요 (결제 서비스, 알림 서비스, 검색 서비스 …). 큰 시스템일수록 이렇게 역할별로 쪼개진 여러 서비스가 서로 대화하며 돌아갑니다.

비유 — 식당과 외부 냉동창고: 주방(서버) 안에 모든 식재료를 쌓아두지 않습니다. 대형 외부 냉동창고(스토리지 서버)를 따로 두고 필요할 때 배송받죠. 주방에 불이 나도 창고의 재료는 무사하고, 주방과 창고를 각자 필요한 만큼 키울 수 있습니다.
📈

로깅 & 모니터링 — 시스템의 CCTV

모든 게 잘 돌아가는지 확인하려면 지켜봐야 합니다. 그래서 로깅(logging)과 모니터링(monitoring) 시스템이 모든 미세한 상호작용을 감시하고, 로그를 저장하고, 데이터를 분석합니다.

  • 로그 저장 위치: 로그는 보통 주 프로덕션 서버 바깥의 외부 서비스에 저장하는 게 표준입니다. (서버가 죽어도 로그는 남아야 원인을 찾을 수 있으니까요.)
  • 백엔드 로깅: pm2 같은 도구로 서버 프로세스를 로깅·모니터링합니다.
  • 프론트엔드 에러: Sentry 같은 플랫폼으로 사용자 화면에서 발생한 에러를 실시간으로 캡처·리포트합니다.
비유 — 매장의 CCTV와 녹화 서버: 매장(서버) 곳곳에 CCTV(모니터링)를 달고, 녹화본(로그)은 매장 밖 별도 건물(외부 로그 저장소)에 보관합니다. 매장에 사고가 나도 녹화본이 남아 있어야 무슨 일이 있었는지 되돌려 볼 수 있으니까요.
🔔

알림 (Alerting) — 문제가 생기면 바로 알려준다

모니터링이 실패한 요청이나 이상 징후를 감지하면, 다음으로 알림 서비스(alerting)가 발동합니다. 그러면 담당자에게 푸시 알림이 날아가요. 알림 내용은 뭉뚱그린 "뭔가 잘못됨"부터 구체적인 "결제 실패"까지 다양합니다.

요즘은 이런 알림을 개발자가 이미 쓰고 있는 도구, 특히 Slack에 바로 꽂아 넣는 게 일반적입니다. 전용 Slack 채널에 문제가 뜨는 순간 알림이 올라오면, 개발자가 거의 즉시 뛰어들어 문제가 커지기 전에 원인을 잡을 수 있죠.

비유 — 화재경보기: CCTV(모니터링)가 연기를 감지하면 경보(알림)가 울립니다. 그것도 사람들이 늘 보고 있는 단톡방(Slack)으로요. 불씨(작은 오류)일 때 알아채야 큰 화재(장애)로 번지지 않습니다.
🐛

디버깅 흐름 — 문제를 잡는 정석 순서

알림을 받은 개발자는 이제 문제를 해결해야 합니다. 정석적인 순서는 이렇습니다.

1
문제 식별 — 앞서 쌓아둔 로그가 첫 번째 단서입니다. 개발자는 로그를 뒤지며 원인을 가리키는 패턴이나 이상 징후를 찾습니다.
2
안전한 곳에서 재현 — 황금률 절대 프로덕션에서 직접 디버깅하지 않습니다. 대신 스테이징/테스트 환경에서 문제를 똑같이 재현해요. 그래야 실제 사용자가 디버깅 과정에 영향받지 않습니다.
3
도구로 관찰하며 디버깅 — 실행 중인 앱 내부를 들여다보는 도구를 써서 원인을 찾아 들어갑니다.
4
핫픽스(hotfix) 배포 — 버그를 고치면 빠른 임시 수정본을 먼저 내보내 서비스를 정상화합니다. 더 완성도 높은 근본 해결책은 그 뒤에 적용해요. (급한 불부터 끄는 패치)
왜 프로덕션에서 디버깅하면 안 될까? 프로덕션은 실제 손님이 밥을 먹고 있는 영업 중인 식당입니다. 그 한복판에서 가스레인지를 뜯어 고치면 손님이 다칩니다. 그래서 똑같이 꾸민 연습용 주방(스테이징)에서 재현하고 고친 뒤, 검증된 수정만 영업장에 반영합니다.
