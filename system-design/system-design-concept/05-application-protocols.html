HTTP — 웹의 기본 대화 규칙

가장 흔한 애플리케이션 계층 프로토콜은 HTTP(HyperText Transfer Protocol)입니다. 앞서 본 TCP/IP 위에서 동작하며, 요청(request)-응답(response) 방식으로 대화해요.

HTTP는 "기억이 없는" 대화 (Stateless)
HTTP를 기억력이 없는 대화라고 생각하세요. 각 상호작용은 서로 독립적이고, 과거를 기억하지 않습니다. 그래서 서버는 요청 사이의 맥락을 저장할 필요가 없어요. 대신 각 요청이 필요한 정보를 전부 스스로 담고 옵니다.

요청과 응답은 헤더(header)와 바디(body)로 나뉩니다. 헤더에는 URL·메서드(Method) 같은 정보가, 바디에는 실제 내용물이 담겨요.

http
POST /api/products HTTP/1.1
Host: shop.example.com
Content-Type: application/json     ← 헤더 (부가 정보)

{                                   ← 바디 (실제 내용물)
  "name": "무선 키보드",
  "price": 39000
}
HTTP/1.1 → 2 → 3, 뭐가 다른가요? 대화 규칙(메서드·상태코드)은 그대로이고 실어 나르는 방식만 좋아졌습니다. 1.1은 한 연결에서 요청이 줄을 서고, 2는 한 연결에 여러 요청을 동시에(멀티플렉싱), 3은 TCP 대신 UDP 기반 QUIC 위에서 더 빨리 연결합니다. 뒤에 나올 gRPC가 HTTP/2를 쓰는 이유가 이 "동시에"예요.
🔒

HTTPS — HTTP에 자물쇠를 채운 것

HTTP는 내용이 그대로 노출된 채 오갑니다. 카페 Wi-Fi에서 누군가 중간에서 엿보면 비밀번호도 읽을 수 있죠. 그래서 실제 서비스는 거의 전부 HTTPS를 씁니다. HTTPS는 HTTP + TLS로, TLS라는 암호화 층이 HTTP 대화를 통째로 감쌉니다. 포트도 80 대신 443을 써요.

🔐
암호화
중간에서 가로채도 내용을 읽을 수 없다.
🪪
신원 확인
인증서(certificate)로 "진짜 그 사이트"인지 확인. 브라우저 주소창의 자물쇠가 이것.
🧾
무결성
오가는 도중 내용이 바뀌지 않았음을 보장.

연결을 시작할 때 TLS 핸드셰이크를 한 번 거칩니다. 서버가 인증서를 보여주고, 둘만 아는 비밀 열쇠를 합의한 뒤, 그 열쇠로 이후 대화를 전부 암호화해요. TCP의 3-way handshake 뒤에 악수를 한 번 더 하는 셈이라 첫 연결이 조금 느리지만, 그 뒤로는 거의 차이가 없습니다.

비유 — 엽서와 봉투: HTTP는 엽서(배달부 누구나 읽을 수 있음), HTTPS는 봉인된 봉투 + 발신인 신분증 확인입니다. 나중에 리버스 프록시에서 나오는 "SSL 오프로딩"은 이 봉투를 뜯고 봉하는 일을 서버 대신 프록시가 해 주는 것이에요.
🔢

상태 코드 & 메서드 — 응답의 결과와 요청의 의도

상태 코드 (Status Code) — "요청이 어떻게 됐나?"

모든 응답에는 상태 코드가 붙어, 클라이언트의 요청이 서버에서 어떻게 처리됐는지 알려줍니다. 백의 자리 숫자로 대분류를 기억하세요.

코드대의미대표 예시
2xx성공 — 요청이 잘 처리됨200 OK, 201 Created
3xx리다이렉션 — 추가 동작 필요(다른 곳으로)301 Moved, 304 Not Modified
4xx클라이언트 오류 — 요청이 잘못됨400 Bad Request, 404 Not Found
5xx서버 오류 — 서버에서 문제 발생500 Internal Server Error

메서드 (Method) — "무엇을 하고 싶은가?"

각 요청에는 메서드가 있어 의도를 나타냅니다.

메서드용도
GET데이터 조회 (가져오기)
POST데이터 생성 (서버에 새로 만들기)
PUT / PATCH데이터 수정 (기존 레코드 갱신)
DELETE데이터 삭제 (레코드 제거)
🔌

WebSocket — 끊기지 않는 양방향 대화

HTTP는 기본적으로 한 방향(요청하면 응답) 연결입니다. 하지만 실시간 업데이트가 필요하면 어떻게 할까요? 이때 WebSocket(웹소켓)을 씁니다. WebSocket은 하나의 오래 유지되는 연결 위에서 양방향(two-way) 통신을 제공해, 서버가 클라이언트에게 실시간으로 데이터를 밀어 넣을(push) 수 있어요.

HTTP (요청-응답)
클라이언트가 물어봐야만 서버가 답합니다.
"새 메시지 있어?" → "없어" → "지금은?" → "없어" …

→ 실시간엔 비효율적 (계속 물어봐야 함)
WebSocket (양방향)
연결을 한 번 열어두면 서버가 알아서 밀어줍니다.
(조용히 대기) → 서버: "새 메시지 도착!" → 즉시 표시

→ 채팅, 실시간 스포츠 중계, 주식 시세에 딱
비유 — HTTP는 편지(보내야 답장이 옴), WebSocket은 전화 통화(연결을 열어두고 양쪽이 아무 때나 말함)입니다. 반복해서 "왔어? 왔어?"를 묻는 HTTP 요청-응답의 오버헤드 없이, 끊임없이 오는 업데이트를 실시간으로 주고받을 수 있죠.
✉️

이메일 프로토콜 — 보내기와 받기

이메일에는 보내는 프로토콜과 받는(가져오는) 프로토콜이 따로 있습니다.

📤
SMTP — 보내기
인터넷에서 이메일 전송의 표준. 서버 사이에서 메일을 보낼 때 사용. 대부분의 메일 클라이언트가 발송에 SMTP를 씀.
📥
IMAP — 받기(동기화)
서버에서 메일을 가져와 열람·관리. 메일이 서버에 남아 있어 여러 기기에서 접근하기 좋음.
📩
POP3 — 받기(내려받기)
서버에서 로컬로 메일을 다운로드. 보통 한 기기에서만 메일을 관리할 때 사용.
IMAP vs POP3 한 줄 구분: 폰·노트북 등 여러 기기에서 같은 메일함을 보고 싶으면 IMAP(서버에 원본 유지), 한 기기로만 받아서 관리하면 POP3(내려받아 보관)라고 기억하세요.
🧰

기타 주요 프로토콜 — 파일 · 원격접속 · 실시간 · 메시징

프로토콜한 줄 설명대표 용도
FTP클라이언트-서버 간 파일 전송의 전통적 프로토콜웹사이트 관리, 대용량 파일 전송·백업
SSH안전하지 않은 네트워크에서 안전하게 원격 접속·명령 실행원격 서버 로그인, 명령 실행, 파일 전송
WebRTC플러그인 없이 브라우저 간 음성·영상·파일 공유화상회의, 라이브 스트리밍
MQTT가벼운 메시징. 저사양·저대역폭 환경에 적합IoT 기기
AMQP견고하고 안전한 메시지 지향 미들웨어 프로토콜엔터프라이즈 메시징(예: RabbitMQ)
이걸 전부 외울 필요는 없습니다. "상황마다 최적화된 전용 프로토콜이 따로 있다"는 감만 잡으세요. 파일은 FTP, 원격 접속은 SSH, 실시간 미디어는 WebRTC, IoT 메시징은 MQTT처럼요.
📞

RPC — 남의 컴퓨터 함수를 내 함수처럼 부르기

RPC(Remote Procedure Call, 원격 프로시저 호출)는 한 컴퓨터의 프로그램이 다른 컴퓨터(서버)의 코드를 실행하게 해주는 프로토콜입니다. 마치 로컬 함수를 호출하듯 함수를 부르지만, 실제로는 그 함수가 원격 기계에서 실행돼요.

RPC는 네트워크 통신의 세부사항을 감춰(추상화), 개발자가 원격 함수를 마치 내 앱 안의 로컬 함수처럼 다루게 해줍니다. 실제로 많은 애플리케이션 계층 프로토콜이 내부적으로 RPC 방식을 씁니다. (예: 웹 서비스의 HTTP 요청이 백엔드에서 RPC 호출을 유발하기도 합니다.)

비유 — 리모컨: 내 손의 리모컨 버튼(로컬 함수 호출)을 누르면, 실제 동작은 저 멀리 있는 TV(원격 서버)에서 일어납니다. 중간에 적외선 신호가 어떻게 오가는지(네트워크 통신)는 몰라도 되죠. RPC가 그 복잡함을 감춰 줍니다.
