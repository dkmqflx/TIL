카카오톡 시스템 디자인 — 채팅 앱은 어떻게 만들까

"내가 보낸 카톡이 어떻게 상대방 폰에 바로 뜰까?" 이 단순한 질문 하나를 끝까지 따라가면 웹소켓 · 메시지 큐 · SQL vs NoSQL이라는 시스템 디자인의 핵심 부품 세 개가 왜 필요한지 자연스럽게 알게 됩니다. 어려운 용어는 나올 때마다 비유로 풀어드릴게요.

카카오톡 1:1 채팅 그룹 채팅 Polling WebSocket Message Queue Pub/Sub Key-Value Store Fan-out
이 자료를 읽는 법: 정답을 외우려 하지 말고, "왜 이 부품이 필요해졌을까?"를 따라가며 읽어보세요. 이 자료는 ① 문제가 생기고 → ② 부품 하나를 넣어 풀고 → ③ 그 다음 문제가 생기는 순서로 이어집니다. 마지막에 다다르면 채팅 앱 하나가 통째로 머릿속에 그려질 거예요.
💬

채팅 앱은 무슨 문제를 풀까?

🎬 원본 강의: 코맹탈출 — 카카오톡 시스템 디자인 | WebSocket | 메시지 큐 | SQL vs NoSQL

오늘의 주인공은 국민 앱 카카오톡입니다. 다만 카카오톡 내부 구조를 그대로 파헤치는 건 아니고, 카카오톡·왓츠앱·페이스북 메신저처럼 "채팅 앱"이라면 대체로 이렇게 생겼다는 일반적인 설계를 봅니다. 어느 회사 채팅 앱이든 풀어야 하는 문제는 비슷하거든요.

채팅 앱에는 기능이 정말 많죠. 일대일 채팅, 그룹 채팅, 읽음 표시(1이 사라지는 것), 상대가 지금 접속 중인지 보여주는 온라인 표시… 이걸 다 다루면 끝이 없으니, 오늘은 딱 두 가지에만 집중합니다.

👤
일대일 채팅
A가 B에게 메시지를 보내면 B의 화면에 바로 뜬다. 채팅 앱의 뼈대입니다.
👥
그룹 채팅
A가 보낸 메시지가 그룹 멤버 전원에게 간다. 일대일 위에 얹는 기능입니다.
비유 — 집을 지을 때 뼈대부터
읽음 표시나 온라인 표시는 인테리어 같은 겁니다. 뼈대(일대일 채팅)가 서 있어야 그 위에 올릴 수 있죠. 그래서 오늘은 뼈대를 세우고, 그 위에 방 하나(그룹 채팅)만 더 올려봅니다.
🌊

먼저 트래픽 특성 3가지

설계에 들어가기 전에 이 서비스에 어떤 트래픽이 들어오는지부터 봅니다. 왜냐하면 나중에 "어떤 DB를 쓸까?"를 결정할 때, 지금 볼 이 특성들이 결정적인 근거가 되기 때문이에요. 지금은 가볍게 읽고 넘어가도 됩니다. 뒤에서 다시 불러올 거예요.

🌊
1. 양이 어마어마하다
인스타그램에 사진 한 장 올리는 동안 카톡은 수십 개 보내죠. 페이스북·왓츠앱 기준 하루 약 600억 개의 메시지가 오갑니다.
🕐
2. 오래된 채팅은 잘 안 본다
몇 년 전 대화를 가끔 뒤지긴 하지만, 비율로 보면 압도적으로 최근 메시지를 봅니다.
⚖️
3. 읽기 : 쓰기 ≈ 1 : 1
대화는 주고받는 것이라 하나 읽고 하나 보내는 식. 읽기·쓰기 둘 다 빨라야 합니다.
비교해 보면 — 트위터는 읽기가 쓰기보다 25배쯤 많은 read-heavy 서비스라서 "읽기를 미리 준비해 두는" 설계를 골랐습니다(01 · 트위터의 선택). 채팅은 읽기와 쓰기가 비슷하니 한쪽만 편애하는 설계로는 안 됩니다. 같은 "메시지"를 다루는 서비스인데도 트래픽 성격이 다르면 설계가 달라진다는 걸 기억해 두세요.
🚪

HTTP의 근본 한계 — 서버는 먼저 말을 걸 수 없다

일대일 채팅부터 시작합니다. 시나리오는 아주 단순해요. 유저 A가 유저 B에게 메시지를 보낸다. 그런데 이 단순한 일을 하려고 하니 첫 번째 벽에 부딪힙니다. 클라이언트(앱)와 서버가 어떤 방식으로 대화해야 할까?

우리가 웹에서 늘 쓰는 건 HTTP죠. HTTP는 항상 클라이언트가 먼저 말을 거는 구조입니다. 앱이 "이거 주세요"(요청)라고 하면 서버가 "여기요"(응답)라고 답하고 끝. 서버는 요청이 없으면 아무 말도 못 합니다.

👤 A
→
🖥️ 서버
A의 요청은 잘 받음 ✅
→
👤 B
서버가 먼저 못 보냄 ❌

A가 서버에 메시지를 보내는 것까지는 HTTP로 문제없어요. 문제는 그 다음입니다. 서버가 B에게 "너한테 메시지 왔어!"라고 먼저 말을 걸 방법이 없습니다. B가 먼저 물어보기 전까지 서버는 입을 다물고 있어야 하니까요.

비유 — 가게 카운터
HTTP는 가게 카운터와 같습니다. 손님(클라이언트)이 와서 말을 걸어야 점원(서버)이 대답하죠. 점원이 집에 있는 손님에게 먼저 전화를 걸 수는 없습니다. 그래서 "B에게 새 메시지가 왔다는 걸 어떻게 알려줄까?"가 첫 번째 풀어야 할 문제가 됩니다. 이 문제의 해법이 세 가지 있고, 하나씩 보면서 왜 마지막 것이 정답인지 확인할 거예요.
🔁

방법 1: 폴링(Polling) — 계속 물어보기

서버가 먼저 말을 못 건다면, 가장 단순한 해법은 B가 계속 물어보는 것입니다. 이걸 폴링이라고 해요. 물어보는 간격은 우리 마음대로 정할 수 있는데, 여기서는 1초에 한 번이라고 해봅시다.

B: 새 메시지 있나요?
→
서버: 없어요
→
(1초 뒤) 있나요?
→
없어요
→
(1초 뒤) 있나요?
→
있어요! 📨

이렇게 하면 일단 동작은 합니다. A가 서버에 메시지를 보내놓으면, B가 다음에 물어볼 때 받아갈 수 있으니까요. 그런데 단점이 두 가지 있어요.

🗑️
단점 ① 헛요청이 대부분
대부분의 경우 답은 "없어요"입니다. 그런데도 요청은 계속 날아가죠. 유저가 수천만 명이면 "없어요"만 답하느라 서버가 바빠집니다.
⏱️
단점 ② 지연이 생긴다
A가 보내자마자 B에게 가는 게 아니라, B가 다음에 물어볼 때 갑니다. 1초 간격이면 최대 1초 늦게 받는 거예요.
딜레마 — 지연을 줄이려고 간격을 0.1초로 줄이면 헛요청이 10배로 늘고, 요청을 줄이려고 간격을 10초로 늘리면 메시지가 10초 늦게 옵니다. 어느 쪽을 고쳐도 다른 쪽이 나빠지는 구조예요. 그래서 폴링은 "일단 되긴 하는" 방법이지 채팅의 답은 아닙니다.
⏳

방법 2: 롱 폴링(Long Polling) — 답을 미뤄두기

이름이 비슷하죠? 폴링과 같은 계열의 기법인데, 한 가지를 바꿉니다. B가 "새 메시지 있나요?"라고 물었을 때 서버가 바로 "없어요"라고 답하지 않고, 메시지가 생길 때까지 대답을 미뤄두는 거예요. 메시지가 오면 그때 응답하고, B는 응답을 받자마자 다시 물어봅니다.

B: 새 메시지 있나요?
→
서버: (잠깐만… 기다려)
→
A 메시지 도착 → 바로 응답 📨
→
B: 다시 물어봄
👍 폴링보다 나아진 점
헛요청이 확 줄어듭니다. "없어요"를 1초마다 듣는 대신, 한 번 물어놓고 기다리니까요.
지연도 줄어듭니다. 메시지가 생기는 순간 응답이 가니, 다음 폴링까지 기다릴 필요가 없어요.
👎 여전히 남는 문제
응답을 받을 때마다 연결을 다시 맺어야 합니다. 여전히 HTTP 요청·응답의 반복이에요.
서버는 답을 안 한 채 수많은 요청을 붙들고 있어야 하고, 너무 오래 기다리면 끊기는 타임아웃도 챙겨야 합니다.
비유 — 전화 대기
폴링이 1초마다 전화를 걸어 "왔어요?" 하고 끊는 거라면, 롱 폴링은 전화를 걸어놓고 "오면 말해주세요" 하고 수화기를 들고 기다리는 겁니다. 낫긴 하죠. 하지만 소식을 하나 들을 때마다 끊고 다시 걸어야 합니다. "아예 계속 통화 상태로 두면 안 되나?" — 그게 바로 다음 방법입니다.
🔌

방법 3: 웹소켓(WebSocket) — 연결을 열어두기 (정답)

결론부터 말하면 채팅의 답은 웹소켓입니다. HTTP는 "요청 하나 → 응답 하나 → 끝"인데, 웹소켓은 클라이언트와 서버가 한 번 연결하고 나면 그 연결을 계속 열어둡니다. 그리고 열려 있는 동안은 양쪽 모두 아무 때나 말을 걸 수 있어요.

🌐 HTTP
요청 → 응답 → 끝. 매번 새로 말을 겁니다.
말을 거는 쪽은 항상 클라이언트. 서버는 먼저 못 보냅니다.
🔌 웹소켓
한 번 연결 → 계속 열어둠.
열려 있는 동안 양방향. 서버가 B에게 먼저 메시지를 밀어줄(push) 수 있습니다.

그러니까 B가 카카오톡을 켜는 순간 서버와 웹소켓을 하나 열어두면, 그 다음부터 B에게 가는 메시지가 도착할 때마다 서버가 그 연결을 통해 곧바로 밀어주면 됩니다. 물어볼 필요도, 기다릴 필요도, 다시 연결할 필요도 없어요.

비유 — 택배를 기다리는 세 가지 방법
폴링: 택배 왔나 하고 1초마다 현관문을 열어보는 것. 대부분 헛걸음.
롱 폴링: 경비실에 전화 걸어놓고 "오면 말해줘요" 하고 기다리는 것. 한 번 들으면 끊고 다시 걸어야 함.
웹소켓: 택배기사와 인터폰을 계속 연결해 둔 것. 도착하는 순간 "택배 왔어요!" 하고 바로 알려줌.
오늘 알아야 할 건 딱 두 가지입니다. ① 웹소켓은 열린 연결을 유지한다. ② 그 연결로 양방향 소통이 된다. 웹소켓이 내부적으로 어떻게 동작하는지(핸드셰이크 등)는 시스템 디자인 101 · HTTP·WebSocket·API에서 따로 다룹니다. 그리고 폴링·롱 폴링을 굳이 설명한 이유는, 채팅엔 안 쓰더라도 시스템 디자인 곳곳에서 자주 등장하는 기법이라 알아두면 좋기 때문이에요.
🏗️

채팅 서버 vs API 서버 — 왜 나눌까?

웹소켓으로 가기로 했으니 이제 서버를 그려봅시다. 그런데 웹소켓은 HTTP와 성격이 하나 다릅니다. HTTP 요청은 올 때마다 처리하고 끝이지만, 웹소켓은 열린 연결을 계속 붙들고 있어야 해요. 유저가 접속해 있는 내내 그 연결을 기억하고 관리해야 합니다.

그래서 이 연결 유지 업무만 전담하는 서버를 따로 두는 게 좋습니다. 이걸 채팅 서버(Chat Server)라고 부를게요. 그리고 로그인, 프로필 사진 바꾸기, 친구 목록 불러오기 같은 평범한 요청은 지금까지처럼 HTTP로 처리하는 API 서버가 맡습니다.

🔌
채팅 서버 (WebSocket)
접속 중인 유저들과 열린 연결을 유지. 메시지를 실시간으로 받고 밀어주는 일만 담당합니다.
🌐
API 서버 (HTTP)
로그인, 프로필 변경 등 실시간이 아니어도 되는 일반 요청. 필요하면 나중에 더 잘게 마이크로서비스로 쪼갤 수도 있습니다.
모든 걸 웹소켓으로 할 필요는 없습니다. 실시간이 필요한 채팅만 웹소켓(채팅 서버)으로, 나머지는 HTTP(API 서버)로. "웹소켓이 좋다"고 해서 전부 바꾸는 게 아니라, 성격이 다른 일은 다른 서버에 맡기는 겁니다. 오늘은 API 서버 쪽은 깊게 들어가지 않고 채팅 서버에 집중합니다.
비유 — 콜센터와 안내데스크
통화를 계속 붙들고 있어야 하는 콜센터(채팅 서버)와, 잠깐 물어보고 가는 안내데스크(API 서버)는 다른 직원이 맡는 게 낫죠. 콜센터 직원에게 안내데스크 일까지 시키면 통화가 끊기니까요.
📮

메시지 큐(Message Queue)란?

더 깊이 들어가기 전에 부품 하나를 먼저 소개해야 합니다. 카프카(Kafka)나 RabbitMQ라는 이름을 들어본 적 있으신가요? 이들이 바로 메시지 큐예요. 한 줄로 말하면 서비스들끼리 데이터를 주고받는 방법 중 하나입니다.

메시지 큐가 없을 때는 어떻게 주고받나?

보통은 REST API나 RPC 호출을 씁니다. 서비스 A가 서비스 B에게 필요한 게 있으면 직접 요청을 보내고, B가 처리해서 바로 응답을 줍니다. 요청하고 답이 올 때까지 기다리니 동기(synchronous) 방식이에요. 메시지 큐를 쓰면 이걸 비동기(asynchronous)로 바꿀 수 있습니다.

📞 REST / RPC (동기)
A → B에게 직접 요청. B가 처리해서 바로 응답.
A는 B가 누구인지, 어디 있는지 알아야 하고, 답이 올 때까지 기다립니다.
📮 메시지 큐 (비동기)
A는 큐에 "이런 일이 생겼어"만 넣고 바로 자기 일로 돌아감.
누가 그걸 꺼내 처리할지 A는 몰라도 됩니다.

등장인물 둘 — 퍼블리셔와 서브스크라이버

📢 퍼블리셔 (Publisher)
어떤 이벤트가 일어났을 때 그 소식을 큐에 넣는 쪽. "새 메시지 도착!"을 던지고 나면 퍼블리셔의 할 일은 끝입니다.
👂 서브스크라이버 (Subscriber)
"이 이벤트가 생기면 나한테 알려줘"라고 큐에 구독 신청해 둔 쪽. 이벤트가 들어오면 큐가 구독자 전원에게 알려주고, 각자 자기 일을 합니다.
📢 서비스 A
(퍼블리셔)
→
📮 메시지 큐
"토픽 1에 새 이벤트!"
→
👂 서비스 B
👂 서비스 C
👂 서비스 D
비유 — 신문 구독
신문사(퍼블리셔)는 신문을 배달소(큐)에 넘기면 끝입니다. 구독 신청한 집(서브스크라이버)마다 배달소가 알아서 넣어주죠. 신문사는 누가 구독하는지 몰라도 되고, 구독자는 신문사에 직접 전화할 필요가 없습니다. 이 "서로 몰라도 된다"가 다음 섹션의 핵심입니다.
🧩

메시지 큐를 왜 쓸까? — 디커플링(Decoupling)

REST나 RPC로도 되는데 굳이 메시지 큐를 쓰는 이유는 여러 가지가 있습니다. 오늘은 그중 가장 중요한 하나, 디커플링만 봅니다. 채팅 서버로 예를 들어볼게요.

메시지 큐가 없다면

유저가 메시지 하나를 보냈을 때 해야 할 일이 생각보다 많습니다. ① DB에 저장해야 하고 ② 받는 유저에게 전달해야 하고 ③ 받는 유저가 로그아웃 상태면 푸시 알림을 보내야 하고 ④ 경우에 따라 이메일도 보내야 할 수 있죠. 이걸 전부 채팅 서버가 직접 호출하면 이렇게 됩니다.

💬 채팅 서버
→
💾 DB 저장 호출
📨 전달 호출
🔔 푸시 호출
📧 이메일 호출
채팅 서버가 네 개 서비스의 존재와 호출 방법을 전부 알아야 합니다. 새 기능이 붙을 때마다 채팅 서버 코드가 늘어나고, 테스트는 어려워지고, 하나가 고장 나면 채팅 서버까지 흔들립니다. 이렇게 서로 단단히 얽힌 상태를 커플링(coupling)이 심하다고 하고, 시스템 디자인에서는 나쁜 신호로 봅니다.

메시지 큐를 사이에 끼우면

채팅 서버는 이제 큐에 "유저 A가 B에게 메시지를 보냈어"라는 이벤트 하나만 넣고 끝입니다. 채팅 서버의 의존성은 큐 하나로 줄어요. DB 저장, 전달, 푸시, 이메일 서비스는 각자 그 이벤트를 구독하고 있다가 큐가 알려주면 자기 일을 합니다.

💬 채팅 서버
(퍼블리셔)
→
📮 메시지 큐
→
💾 DB 저장
📨 전달
🔔 푸시
📧 이메일
하는 일은 완전히 똑같습니다. 달라진 건 채팅 서버가 B·C·D가 존재한다는 사실조차 몰라도 된다는 것. 그래서 나중에 "슬랙으로도 알림 보내자"가 추가돼도 채팅 서버는 한 줄도 안 고칩니다. 새 구독자 하나가 큐에 붙기만 하면 돼요. 이것이 디커플링(느슨하게 떼어놓기)입니다.
비유 — 우체국
편지를 우체국(큐)에 맡기면 우체국이 관련된 모든 곳에 배달합니다. 나는 받는 사람이 어디 사는지, 몇 명인지 신경 쓸 필요가 없죠. 디커플링 말고도 메시지 큐의 장점(버퍼 역할, 재시도 등)은 더 있지만 주제가 커서 오늘은 여기까지만 합니다.
🔄

일대일 채팅 — 전체 흐름 따라가기

부품이 다 모였습니다. 이제 전체 그림을 그려놓고, 유저 A가 유저 B에게 메시지를 보내는 과정을 처음부터 끝까지 따라가 봅시다. 등장인물은 이렇습니다.

🟢
로그인 유저
각자 어느 채팅 서버와 웹소켓이 열려 있음. 채팅 서버는 여러 대이고, 유저마다 붙은 서버가 다를 수 있습니다.
🔴
로그아웃 유저
웹소켓 연결이 없음. 실시간으로 밀어줄 통로가 없으니 푸시 알림이 필요합니다.
📮
메시지 큐
유저마다 큐가 하나씩 있다고 생각하면 편합니다. "B의 큐"에 들어간 메시지는 B에게 가야 할 메시지예요.
💾🔔
DB · 푸시 알림 서비스
둘 다 큐를 구독하고 있는 서브스크라이버입니다.

A가 "전송"을 누르면

① A가 전송
(웹소켓)
→
② A와 연결된 채팅 서버가
B의 큐에 메시지 넣음
→
③ 큐가 B의 큐를
구독 중인 모두에게 알림
→
④ 구독자 각자 처리

④에서 구독자들이 동시에, 서로 상관없이 자기 일을 합니다.

📨
B가 로그인 상태라면
B와 웹소켓이 열려 있는 채팅 서버가 B의 큐를 구독하고 있다가 알림을 받고, 웹소켓으로 B에게 즉시 밀어줍니다. 이게 "카톡이 바로 뜨는" 순간이에요.
💾
DB 저장
DB 서비스가 같은 알림을 받아 메시지를 기록합니다. 나중에 채팅방을 다시 열었을 때 보이는 건 이 덕분입니다.
🔔
B가 로그아웃 상태라면
밀어줄 웹소켓이 없으니 푸시 알림 서비스가 "새 메시지가 왔어요"를 폰에 띄웁니다.
핵심은 ②에서 끝난다는 것. A 쪽 채팅 서버는 B가 로그인 중인지, B가 어느 채팅 서버에 붙어 있는지 전혀 몰라도 됩니다. 그냥 "B의 큐"에 넣으면 끝. B가 어디에 있든 B의 큐를 구독 중인 서버가 알아서 받아갑니다. 앞에서 배운 디커플링이 여기서 그대로 힘을 발휘하는 거예요.
비유 — 아파트 우편함
A는 편지를 B네 우편함(B의 큐)에 넣기만 합니다. B가 집에 있으면(로그인) 관리인(채팅 서버)이 인터폰(웹소켓)으로 "편지 왔어요" 하고, 집에 없으면(로그아웃) 문자(푸시)를 보내죠. 그리고 관리사무소 장부(DB)에는 항상 기록이 남습니다.
🗄️

어떤 DB를 쓸까? — SQL vs NoSQL

지금까지 "DB"라고만 뭉뚱그렸는데, 이제 어떤 종류의 DB를 쓸지 정해야 합니다. 여기서 맨 처음 봤던 트래픽 특성을 다시 불러옵니다. 거기에 하나를 더 얹어요.

🌊
양이 어마어마하다
→ 데이터가 늘어도 쉽게 확장되어야 함
🕐
최근 것 위주로 본다
→ 최근 메시지를 빠르게 읽을 수 있어야 함
⚖️
읽기 : 쓰기 ≈ 1 : 1
→ 읽기·쓰기 둘 다 효율적이어야 함
🔗
(추가) 조인할 일이 거의 없다
채팅 메시지는 다른 테이블과 엮어서 볼 일이 거의 없음. 메시지는 메시지끼리만 봅니다.

후보 둘을 비교하면

🐘 관계형 DB (MySQL, PostgreSQL)
여러 테이블을 조인하는 게 강점. 하지만 데이터와 인덱스가 많아질수록 점점 느려집니다.
채팅은 애초에 조인할 일이 별로 없어서 가장 큰 강점을 써먹지 못해요.
🔑 키-값 스토어 (Key-Value Store)
확장하기 쉽고, 읽기 지연(read latency)이 낮습니다.
조인이 필요 없는 대용량 데이터에 딱. 실제로 페이스북·디스코드가 카산드라(Cassandra)를 씁니다.
비유 — 키-값 스토어는 '번호 사물함'
번호(키)만 대면 그 칸의 내용물(값)을 즉시 꺼내주는 사물함입니다. 옆 사물함과 엮어서 볼 일(조인)은 없고, 사물함이 부족하면 옆에 한 줄 더 세우면(확장) 그만이죠. 채팅 메시지 저장에 안성맞춤입니다.

한 가지 설계 팁 — 키를 '레인지 스캔'하기 좋게

키-값 스토어를 쓸 때 신경 쓸 게 딱 하나 있습니다. 채팅은 시간 순서대로 쭉 읽는 경우가 대부분이죠. 채팅방을 열면 최근 메시지 30개, 위로 올리면 그 전 30개… 이렇게 연속된 범위를 한 번에 읽는 것을 레인지 스캔(range scan)이라고 하는데, 키를 이 스캔에 유리하게 설계해야 합니다.

가장 쉬운 방법은 메시지 ID를 계속 증가시키는 겁니다. 그러면 키 순서가 곧 채팅 순서가 되니까, "이 채팅방의 ID 101부터 130까지"처럼 범위만 지정하면 시간순으로 쭉 나옵니다.

키 (채팅방 ID + 메시지 ID)값
room42 : 000101A: 점심 뭐 먹지?
room42 : 000102B: 김치찌개?
room42 : 000103A: 콜
→ room42 : 000101 ~ 000103 범위를 한 번에 읽으면 그대로 시간순
반대로 키를 무작위 값(예: 랜덤 UUID)으로 만들면, 같은 채팅방 메시지가 사물함 여기저기 흩어져 시간순으로 모으려면 일일이 찾아야 합니다. 키를 어떻게 만드느냐가 읽기 속도를 좌우한다는 것, 키-값 스토어를 쓸 때 늘 떠올려야 할 포인트입니다.
👥

그룹 채팅 얹기

일대일 채팅 뼈대가 완성됐습니다. 이제 그 위에 그룹 채팅을 얹어 봅시다. 그런데 설계를 시작하기 전에 먼저 정해야 할 질문이 하나 있어요. "한 그룹에 몇 명까지 지원할 것인가?"

이 숫자에 따라 설계가 완전히 달라집니다. 100만 명이 들어가는 초대형 그룹까지 지원할 건지, 적당한 선에서 인원을 제한할 건지. 여기서는 한 그룹 최대 200명이라고 가정하겠습니다. 200명 정도면 뒤에 나올 팬아웃이 감당할 만한 수준이라고 볼 수 있어요.

A가 그룹(A·B·C)에 메시지를 보내면

① A가 그룹에 전송
(웹소켓)
→
② 채팅 서버가 그룹챗 DB에
"이 그룹 멤버 누구?" 조회
→
③ 멤버 = A·B·C 확인
→
④ B의 큐, C의 큐에
각각 메시지 넣기 (팬아웃)

④ 이후는 일대일 채팅과 완전히 똑같습니다. B의 큐, C의 큐에 메시지가 들어갔으니, 각 큐를 구독 중인 채팅 서버가 웹소켓으로 밀어주고, DB에 저장되고, 로그아웃 유저에겐 푸시가 갑니다. 일대일을 잘 만들어 두면 그룹은 "큐에 넣는 횟수만 늘어난" 셈이에요.

🐘
그룹챗 DB는 관계형이어도 OK
"어느 그룹에 누가 있나"는 멤버·유저 정보를 엮어서(조인) 볼 일이 있는 데이터입니다. 굳이 키-값 스토어일 필요가 없어요.
🔑
메시지 본문은 키-값 스토어
앞 섹션 그대로. 데이터 성격에 따라 DB를 나눠 쓰는 것이 자연스럽습니다.
여기서 팬아웃(Fan-out)이 등장합니다. 메시지 하나가 멤버 수만큼 여러 갈래로 퍼지는 게 팬아웃이에요. 200명이면 큐에 200번 넣는 정도라 괜찮지만, 만약 "수백만 명짜리 초대형 그룹"만 지원하는 앱이라면 메시지 하나에 수백만 번 넣어야 하니 이 설계는 무너집니다. 그때는 트위터의 인플루언서 문제처럼 큰 그룹만 다르게 처리하는 방법을 고민해야 해요. 서로 다른 서비스에서 같은 문제가 반복됩니다.
비유 — 단체 문자
친구 200명에게 단체 문자를 보내는 건 폰이 200번 전송하면 되니 금방 끝나죠. 그런데 200만 명에게 보내야 한다면 폰 하나로는 무리고, 아예 다른 방식(방송)이 필요합니다. "몇 명까지?"를 먼저 정하는 이유가 바로 이거예요.
📌

한눈에 정리 — 카카오톡에서 배운 것

🔌
웹소켓
HTTP는 서버가 먼저 말을 못 건다 → 폴링·롱 폴링은 임시방편 → 연결을 열어두는 웹소켓이 답. 연결 유지는 채팅 서버가 전담.
📮
메시지 큐 & 디커플링
퍼블리셔는 큐에 던지기만, 서브스크라이버는 구독만. 채팅 서버는 "B의 큐에 넣기"까지만 하면 저장·전달·푸시는 알아서.
🔑
키-값 스토어
대량 · 최근 위주 · 읽기≈쓰기 · 조인 없음 → 확장 쉽고 빠른 키-값 스토어(카산드라). 키는 증가하는 ID로 시간순 레인지 스캔.
👥
그룹 채팅 & 팬아웃
"몇 명까지?"를 먼저 정한다. 200명이면 멤버 조회 후 큐에 팬아웃으로 충분. 초대형 그룹은 트위터 인플루언서 문제와 같아진다.
이 사례의 큰 흐름: ① HTTP로는 서버가 유저에게 먼저 말을 못 걸어서 웹소켓을 골랐다 → ② 열린 연결을 관리하는 채팅 서버를 따로 뒀다 → ③ 후속 작업들을 깔끔히 떼어내려고 메시지 큐를 넣었다 → ④ 트래픽 특성에 맞춰 키-값 스토어를 골랐다 → ⑤ 그룹 채팅에서 팬아웃을 만났고, 인원 제한으로 감당했다. 부품 하나하나가 앞 단계의 문제 때문에 등장했다는 걸 기억하면, 다른 서비스를 설계할 때도 같은 사고 흐름을 쓸 수 있습니다.
